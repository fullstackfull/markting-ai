headers, card/table structures, where KPIs live, what is primary vs secondary,

## Findings

### G5-01 — Findings is a primary nav module with no producer in the codebase
- **Severity:** P2
- **Classification:** VERIFIED_CODE
- **Evidence:** `platform/apps/cloud/components/nav.tsx:32` (primary nav link); `platform/apps/cloud/app/dashboard/findings/page.tsx:10` (lists `new PostgresFindingsStore(...).list()`); `platform/apps/cloud/lib/cloud/repository.ts:436-480` (store has `list/get/save`, `save` does the only `insert into public.findings` at `:477`); `grep -rn "\.save(" over findings` → no caller anywhere in `platform/` or `services/`. The two runtime builders only *construct* the store (`lib/cloud/runtime.ts:145`, `lib/markting/runtime.ts:25`); nothing invokes `.save()`.
- **Description:** "Findings" occupies a top-level primary nav slot and the page renders a severity/finding/provider/account/status/updated table (`findings/page.tsx:26-41`), i.e. the UI claims an audit-findings capability. But no code path in the platform ever writes a finding row. The engine does not write to this table either (it is a cloud-Postgres table). So in any normal deployment the page is permanently the empty state.
- **Impact:** A primary module advertises a capability the system does not deliver; users navigating to it see "no findings" indefinitely and cannot tell whether that means "healthy" or "feature not wired". It consumes one of only eight primary nav positions. Per the audit rule, code that claims to provide a feature it does not is a defect, not a mere gap.
- **Recommendation:** Either wire a producer (engine audit pass or a cloud job that calls `PostgresFindingsStore.save`) or demote Findings out of primary nav until it is populated. If it is intended to be engine-produced, document and verify the write path.

### G5-02 — Overview, not the Assistant, is the hub; the "AI media buyer" action surface is secondary
- **Severity:** P3
- **Classification:** VERIFIED_CODE
- **Evidence:** `nav.tsx:27` (Overview = first, `exact` landing at `/dashboard`); `nav.tsx:28` (Assistant = second link, no special prominence); `shell.tsx:34` (`Nav` is a flat list, no command bar / global ask affordance); `app/dashboard/page.tsx:22-66` (landing page is a passive normalized read: KPI row + campaign table + connections + governance counts); `README.md` claims an "AI media buyer".
- **Description:** The product is positioned as an AI media buyer, yet the default surface is a read-only reporting dashboard. The Assistant — the only surface that turns intent into action (`lib/markting/assistant.ts:28` forwards to the engine and, on a change proposal, mints an approval) — is a peer nav link with no presence in the shell. There is no persistent "Ask AI" composer, no command palette, and the Overview offers no entry point into the Assistant.
- **Impact:** The IA frames the system around looking at numbers rather than acting on them. The highest-value loop (ask → propose → approve → apply) is two clicks away and discoverable only as one of eight sidebar links. This undersells the product and buries its differentiator.
- **Recommendation:** Make "Ask AI" the hub: a persistent composer/command bar in the shell (or on Overview), with the dashboard reframed as answer/brief surfaces the Assistant can deep-link into. See proposed IA below.

### G5-03 — KPIs live in exactly one place and are computed client-side, with no per-account or trend context
- **Severity:** P3
- **Classification:** VERIFIED_CODE
- **Evidence:** Only KPI row in the app is `live-data.tsx:51-54` (Spend, Clicks, Conversions, ROAS) fed by `/api/dashboard/summary` (`app/api/dashboard/summary/route.ts:9`, `last_7_days`). Totals and ROAS are summed/divided in the browser (`live-data.tsx:34-41`). No other page renders a `Metric` (grep `Metric label` → only `live-data.tsx`). Reports (`reports/page.tsx`) and the engine-report card show tables, not headline KPIs.
- **Description:** The four headline numbers exist solely on Overview, over a fixed 7-day window, with no comparison to a prior period, no per-account breakdown, and no trend/sparkline. ROAS is derived in `live-data.tsx` rather than by the engine's deterministic compute (the engine explicitly keeps "all arithmetic … so the model never derives a figure in prose", `engine/.../tools/summary.py:1-6`), so the dashboard's headline ROAS is computed on a different footing than engine reports.
- **Impact:** There is no "account health at a glance" layer; a user cannot see which account/campaign is driving a KPI without reading the 12-row table. Headline numbers have no direction (up/down vs last week), which is the single most useful piece of a media-buying dashboard.
- **Recommendation:** Add period-over-period deltas (engine `compare_periods` already produces them, `engine/.../tools/compare_periods.py`), move ROAS computation server-side for parity with reports, and add a per-account health rollup (see Account Health in the IA).

### G5-04 — Overview "Campaign activity" and Reports "Campaigns" are near-duplicate tables differing only by window
- **Severity:** P3
- **Classification:** VERIFIED_CODE
- **Evidence:** `live-data.tsx:72-86` renders campaign rows (Campaign/Provider/Status/Spend/Clicks/Conv/ROAS) over `last_7_days`. `reports/page.tsx:34-50` renders the same entity rows with the same `Provider`/status regex rendering and an extra Impressions column over `last_30_days` (`reports/page.tsx:10`). Both share the `row.entity` / `row.metrics` shape and the identical `/paused|disabled|removed/i` status styling.
- **Description:** Two primary surfaces present essentially the same table with different time windows and one differing column. There is no single "campaign explorer" with a window selector; the window is baked into the route.
- **Impact:** Redundant IA: the user must learn that "Overview = 7d, Reports = 30d" rather than choosing a window in one place. Maintenance cost (two tables, two formatters) and inconsistency risk (Overview has ROAS but no Impressions; Reports has both).
- **Recommendation:** Consolidate into one campaign/entity explorer with a window control and drill-down; keep Overview as a summarized brief that links into it. Reserve the Reports route for the engine's deterministic weekly/monthly deliverables.

### G5-05 — No decision/outcome layer: applied changes are not tracked for effect, only logged as events
- **Severity:** P3 (GAP bordering on P2 for an "AI media buyer")
- **Classification:** VERIFIED_CODE
- **Evidence:** Audit log records `validated/applied/rejected` events with actor + one-line summary (`app/dashboard/audit/page.tsx:9-10,33-41`). Approvals shows pending ops with assistant provenance (`approvals/page.tsx:36-40`). There is no surface that links an *applied* change to its subsequent performance delta; `grep outcome track` → 0, and engine "outcome" is `RunOutcome` run plumbing, not a performance outcome (`engine/.../surfaces/api/app.py:61`).
- **Description:** The system can propose, approve, and log a change, but nothing closes the loop by showing what the change did (before/after spend, CPA, ROAS). Decision History exists only implicitly as the raw Audit log, which is event-centric, not decision-centric.
- **Impact:** For a product whose value is autonomous/assisted optimization, the absence of outcome attribution means users cannot build trust in the agent's changes or measure its value. This is the missing half of the action loop.
- **Recommendation:** Add a Decision History view keyed on applied operations (join audit `applied` events to the originating proposal) and an Outcome Tracking surface that re-reads the affected entity over a post-change window via `compare_periods`.

## What a world-class system would need (gaps, concrete)

1. **Ask AI as the spine, not a tab.** Persistent composer/command bar in `shell.tsx`; every brief/alert/opportunity card carries an "Ask about this" deep-link that seeds a thread. Thread history and saved answers.
2. **A daily Morning Brief** generated on a schedule (engine already has cadence machinery, `engine/.../reports/cadence.py`): top movers, pacing risks, pending approvals, and 1-3 recommended actions — the real landing page.
3. **Account Health rollup**: per-account status, spend pacing vs budget, ROAS/CPA with period-over-period deltas (use engine `compare_periods`), and a single health signal per account. KPIs computed server-side for parity with reports.
4. **Opportunities & Recommendations queue**: engine-produced, ranked, each a one-click proposal that flows into the existing Approvals bridge. Today recommendations are trapped inside static report HTML.
5. **Alerts** with user-set thresholds (spend spikes, ROAS drops, disapprovals) feeding a notifications surface — distinct from the error `role="alert"` reuse.
6. **Creative Intelligence**: the `CREATIVE` entity level is already read/normalized by the engine; a creative-level view (fatigue, top/bottom assets) is a natural, data-backed addition.
7. **Budget Optimizer** surface: proposed reallocations across campaigns/accounts, each routed through Approvals (never auto-applied without the existing policy/approval gate).
8. **Decision History + Outcome Tracking**: a decision-centric ledger (proposal → who approved → applied → measured post-change delta) that closes the action loop and quantifies agent value.
9. **One campaign/entity explorer** with a window selector, replacing the Overview/Reports table duplication (G5-04).
10. **Consistent primary vs secondary split**: workspace config (Connections, Accounts, Agent access, Policies, Team, Plan) belongs in a settings group; the primary rail should be the work loop (Brief, Health, Opportunities, Approvals, Decisions/Outcomes, Ask AI).

A pragmatic reorganized IA:
- **Primary (the loop):** Ask AI · Morning Brief (home) · Account Health · Opportunities/Recommendations · Approvals · Decisions & Outcomes.
- **Analyze:** Reports · Campaign Explorer · Creative Intelligence · Alerts.
- **Settings (utility):** Connections · Accounts · Agent access · Policies · Team · Plan.

- `README.md` positions the product as an "AI media buyer", but the implemented IA defaults to a passive read dashboard (`app/dashboard/page.tsx`); the agentic loop is one of eight sidebar links with no shell presence (G5-02). DOCUMENTED vs VERIFIED_CODE mismatch of emphasis.
- The Findings nav entry and page imply an active audit-findings capability (`nav.tsx:32`, `findings/page.tsx`), but no code populates it (G5-01). The UI claim is contradicted by the absence of any `save` caller.
- The assistant page copy says every suggested change "becomes a previewed operation on the Approvals page" (`lib/i18n/messages/assistant.ts` `description`) — this is VERIFIED_CODE accurate (`assistant.ts:60-75` bridges to a pending op), a rare doc/code agreement worth noting as a strength.
