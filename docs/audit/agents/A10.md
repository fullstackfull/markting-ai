## Findings

### A10-01 — The AI engine cannot see Spotify at all (no platform enum, no Pipeboard endpoint, no fixture, no normalization, no skill)
- Severity: GAP (becomes P1 only if the product markets Spotify as an AI-managed channel)
- Classification: MISSING / VERIFIED_CODE
- Evidence: `engine/src/paid_media_agent/domain/common.py:12-22` (`Platform` enum: google_ads, meta_ads, reddit_ads, tiktok_ads, pinterest_ads, snap_ads, google_analytics, linkedin_ads, x_ads, openai_ads — no spotify); `common.py:25-34` `PIPEBOARD_PLATFORMS` excludes it; `common.py:38-42` `FIXTURE_PLATFORMS` = google/meta/reddit only; `engine/src/paid_media_agent/tools/normalize.py:14-27` `_SPEND_KEYS` has no Spotify mapping (a Spotify payload would raise "platform metrics have no verified spend-unit mapping", line 95-97); `engine/src/paid_media_agent/tools/direct/` contains only `openai_ads.py`, `x_ads.py`; `engine/config/accounts.example.toml` and `write-policy.example.toml` have no Spotify rows; `rg -i spotify engine/` → 0 matches.
- Description: The "AI media buyer" (paid-media-agent) has no concept of Spotify Ads. It cannot read Spotify data offline (fixtures) or live (Pipeboard/direct), cannot normalize its metrics, and has no skill text about audio/podcast buying.
- Impact: Any Spotify "management" happens only through the adport MCP/API tools, i.e. a human or a generic LLM client calling tools directly — the engine's analysis, anomaly detection, pacing and proposal loop never touch Spotify.
- Recommendation: Add `Platform.SPOTIFY_ADS`, a direct adapter (there is no Pipeboard Spotify connector in the enum) or a bridge to adport's `report` tool, a spend-unit mapping (SPEND in whole currency units), a synthetic fixture dataset, and skill guidance for audio KPIs.

### A10-02 — The Arabic-first assistant bridge cannot route proposals to Spotify
- Severity: GAP
- Classification: MISSING / VERIFIED_CODE
- Evidence: `platform/apps/cloud/lib/markting/translate.ts:13-14` (`EnginePlatform` list, no spotify), `:19` (`BridgeProvider = 'sandbox' | 'google' | 'meta' | 'reddit' | 'tiktok' | 'snapchat'`), `:72-73` (`PLATFORM_TO_PROVIDER` has no spotify), `:103-121` (`budgetInput`/`statusInput` switch has no spotify case); `platform/apps/cloud/lib/markting/sandbox-provider.ts:43-47` (demo accounts: google, meta, reddit, snapchat only).
- Description: Even if the engine produced a Spotify proposal, `translate.ts` cannot map it to `spotify_set_budget` / `spotify_set_campaign_status`. The Spotify writes use `ad_set_id` (budget) vs `campaign_id` (status), which the bridge's campaign-centric `budgetInput` shape does not model.
- Impact: Spotify is reachable only through raw tool calls (`/api/v1/tools/[tool]`, MCP), not through the product's assistant flow.
- Recommendation: Extend `BridgeProvider` and the translation switch; note that Spotify budgets live on ad sets, so the proposal schema must carry an ad-set target.

### A10-03 — Reporting is LIFETIME-aggregate only: no time series, no breakdowns, no reach/frequency/audio metrics
- Severity: GAP (code does not claim otherwise) — but see A10-04 for a doc nuance
- Classification: EXISTS_BUT_LIMITED / VERIFIED_CODE
- Evidence: `platform/packages/spotify/src/provider.ts:16` (`FIELDS` = SPEND, IMPRESSIONS, CLICKS, PURCHASES, REVENUE only), `:17-20` (derived ctr/cpc/cpm/cpa/roas), `:83` (`granularity: 'LIFETIME'` hard-coded), `:89` (rejects any non-LIFETIME response), `:70` (90-day cap), `platform/packages/spotify/src/schemas.ts:29` (schema would accept DAY/HOUR but provider never requests them); normalized model `platform/packages/core/src/model.ts:1-12` (10 metrics) and `:15` (4 entity levels); no breakdown/dimension concept anywhere in core (rg → 0).
- Description: An expert Spotify buyer runs on reach, frequency, audio completion rate, video views/completes, paid listens / streams, podcast downloads, conversions by type, by day/hour, by age/gender/country/platform. None of these is requested or representable. Conversions are PURCHASES only; other Spotify conversion events (SIGN_UP, ADD_TO_CART, etc., if present in the API) are not exposed. CPM/CPC/CTR are computed client-side from totals, which is correct for lifetime totals.
- Impact: Dashboards and any LLM reasoning over Spotify are limited to spend/impressions/clicks/purchases/revenue totals over one window. No pacing (requires daily series + budget), no fatigue (requires frequency over time), no audience insight.
- Recommendation: Expose DAY granularity and the full Spotify field set behind a provider-specific read tool (e.g. `spotify_report`), add reach/frequency/completion to a provider-specific output, and consider a core "extended metrics" escape hatch.

### A10-04 — Spotify report rows carry no `currency`; the core report tool must backfill it with an extra `listAccounts()` call
- Severity: P3
- Classification: VERIFIED_CODE
- Evidence: `platform/packages/spotify/src/provider.ts:95` builds `ReportRow` without `currency` even though `listAccounts()` knows `currency_code` (`:35`); `platform/packages/core/src/model.ts:41-42` documents the field; `platform/packages/core/src/tools/builtin.ts:118-129` backfills from `listAccounts()` when rows lack currency; `platform/packages/core/src/report-summary.ts:10-11` otherwise groups unlabelled rows per account. Compare `platform/packages/snapchat/src/provider.ts:33` which at least labels accounts.
- Description: Works via core's fallback, but costs a businesses+ad_accounts crawl per report (`provider.ts:31-36`) for direct `provider.report()` callers (cloud `AccountScopedProvider` supplies inventory, mitigating it there). `BudgetDelta.currency` is also omitted (`provider.ts:158`), so policy previews show micros with no currency label.
- Recommendation: Attach `currency` to rows and budget deltas from the account lookup already performed.

### A10-05 — `report_end` sent as `${end}T00:00:00Z`; inclusive-end semantics are asserted by tests and docs but NOT verified against Spotify
- Severity: P2 if Spotify treats `report_end` as an exclusive instant (would silently drop the final day of every report); otherwise none
- Classification: NOT_VERIFIED
- Evidence: `platform/packages/spotify/src/provider.ts:83`; test `platform/packages/spotify/test/spotify.test.ts:135` asserts the literal `2026-08-07T00:00:00Z` for an inclusive range ending 2026-08-07; `platform/docs/providers/spotify.md:36,39` claims "UTC inclusive dates"; docs fetch blocked (EGRESS_BLOCKED).
- Description: The core `DateRange` is inclusive on both ends (`model.ts:21`). If the Spotify API interprets `report_end` as the end *timestamp*, the last day's 24 hours are excluded; `yesterday` preset (`model.ts:63`) would then return zero data. The test only pins the current behaviour, it cannot prove it is right.
- Recommendation: Verify against a live allowlisted account (compare a one-day window to Ads Manager). If exclusive, send `${end+1d}T00:00:00Z` or `${end}T23:59:59Z`.

### A10-06 — All wire-format tests are synthetic; no live or recorded Spotify responses exist
- Severity: P2 (production readiness; the docs are honest about it)
- Classification: VERIFIED_TEST (coverage) / DOCUMENTED_ONLY (correctness vs real API)
- Evidence: `platform/packages/spotify/test/spotify.test.ts:12-14` ("Fixtures follow Spotify's official v3 reference shapes … not responses captured from a live account"); `platform/docs/providers/spotify.md:43` ("not live API verification. Live account discovery/reporting awaits an authorized, allowlisted app"); `schemas.ts:3` "reviewed 2026-08-31"; git history shows a single vendoring commit (`fa7bf19`), so no evidence of live verification since import.
- Description: 45 tests pass, but every fixture was hand-written from documentation. Draft creation body (`provider.ts:123`: name, purchase_order?, delivery_goal_group, status) is especially suspect — real `createCampaignDraft` likely requires more fields (objective, schedule), and the provider's own doc admits the reference examples are internally inconsistent (`spotify.md:41`).
- Recommendation: Run the read-only paths against a NO_DELIVERY_NO_BILLING test account and record golden responses; do not enable `SPOTIFY_OAUTH_ENABLED=true` for tenants before that.

### A10-07 — Test-account type is discarded; sandbox/no-billing accounts are indistinguishable from real ones downstream
- Severity: P3
- Classification: VERIFIED_CODE
- Evidence: `platform/packages/spotify/src/schemas.ts:10` parses `test_account_type`; `provider.ts:35` maps only id/name/currency/status into `Account`; `platform/packages/core/src/provider.ts:4-10` `Account` has no test flag.
- Description: A `NO_DELIVERY_NO_BILLING` account would appear in Accounts, dashboards and reports as an ordinary account with permanently empty metrics ("empty reports are expected", `spotify.md:43`).
- Recommendation: Surface test-account type in the account name or a status suffix so operators and the LLM don't chase phantom zero-delivery.

### A10-08 — Policy's absolute cap is named "daily" but Spotify budget writes may be LIFETIME
- Severity: P3
- Classification: VERIFIED_CODE
- Evidence: `platform/packages/core/src/policy/policy.ts:14-15` `max_daily_budget_micros`; `platform/packages/core/src/policy/engine.ts:136-141` applies it to every `budgetDeltas[]` entry regardless of type; `platform/packages/spotify/src/provider.ts:151-158` preserves `current.budget.type` (DAILY or LIFETIME) and emits one delta with `target: "ad set <id> LIFETIME budget"`.
- Description: A legitimate 30-day lifetime budget (e.g. 3,000 EUR) is compared against a per-day cap. Over-blocking, not under-blocking, so safe, but the operator UX is misleading. The 25% delta cap (`policy.ts:13`) applies sensibly to both.
- Recommendation: Either expose a `max_lifetime_budget_micros` or have the Spotify provider document that lifetime budgets trip the daily cap.

### A10-09 — Budget policy is evaluated at validate time only; current budget may drift before apply
- Severity: P3 (core, not Spotify-specific; 15-minute TTL bounds the window)
- Classification: VERIFIED_CODE
- Evidence: `platform/packages/core/src/policy/engine.ts:58-62` (`checkBudgetPolicy` in `validate`), `:87-113` (`apply` re-runs only `checkStaticPolicy`); `provider.ts:150` re-reads the ad set in `plan()` at apply, so the PATCH itself uses fresh `type`, but the delta % was computed from the preview-time value; `policy.ts:19` TTL default 15 min.
- Recommendation: Re-run `checkBudgetPolicy` against the apply-time preview in `apply()`.

### Writes and gating
All four writes are declared via `guardedWriteTool` (`tools.ts:12-19`) → `PolicyEngine.validate/apply` (`core/src/tools/write.ts:39-66`, `policy/engine.ts:58-125`): pending token, canonical-hash equality, TTL, protected accounts, absolute and percentage budget caps, audit `validated/applied/rejected`. End-to-end test `spotify.test.ts:237-255` confirms the gate for `spotify_set_budget` (pending token required, "differs" on changed args, cap rejection, protected account, audit events). In cloud, `AccountScopedProvider` re-asserts the account scope on preview and apply (`account-scope.ts:81-89`).

### Server-validated vs client-side preview
Everything is client-side preview: the provider reads the current entity (campaign or ad set) and diffs (`provider.ts:137-140,150-158`); the draft preview makes no API call at all (test `:190-197`). Correctness of the pending change is only checked *after* the mutation by comparing the response (`:129,143,161-165`) — i.e. a wrong body is detected post hoc and surfaces as "inspect before retrying", not prevented.

### Test coverage map (VERIFIED_TEST)
Covered: auth URL + no scopes (`:51-55`), code exchange form/basic auth (`:56-66`), refresh single-flight/rotation (`:67-82`), 401 retry/no write replay (`:83-94`), 403 message hygiene (`:95-99`), path injection (`:100-104`), malformed account responses (`:105-108`), business→account discovery (`:112-117`), campaign paging + stall (`:118-129`), report field selection, dates, granularity, continuation, limit/truncation, level mapping, suppression, empty, malformed (`:130-186`), draft create preview/apply, direct-create refusal, status PATCH, budget type retention, delivery-only PATCH, ID mismatch, full policy gate, env/store credentials (`:190-272`).
Not covered: multi-account report iteration when `accountIds` omitted (`provider.ts:79`); `report()` with >1 account; 90-day boundary exactly; token `expires_in` expiry path (60 s margin, `client.ts:83`); mutate on 5xx/429 (no backoff anywhere — `client.ts:58-80` has no rate-limit handling); `onRefreshToken` failure during refresh; draft create when guard `forcePausedCreation=false` with `status: ACTIVE`; `setDeliverySchema` + budget combination rejection; `listAccounts` partial failure across businesses; any `DAY` granularity (never requested); cloud `AccountScopedProvider` + Spotify read tools (cloud test only checks `listAccounts` → `[]` and rotation, `provider-expansion-runtime.test.ts:70-71`).

## What a world-class system would need (gaps, concrete)
1. Engine awareness: `Platform.SPOTIFY_ADS`, a direct adapter (OAuth client-credentials/refresh per `client.ts`), `_SPEND_KEYS` mapping (whole units), fixture dataset, write-policy rows with `readback_tool` (`spotify_get_ad_set`), bridge translation to `spotify_set_budget {ad_set_id, budget_micros}`.
2. Full reporting: DAY/HOUR granularity, fields for REACH, FREQUENCY, audio/video completion (starts/quartiles/completes), paid listens/streams, podcast downloads, all conversion types, plus demographic/geo/platform/format breakdowns; a provider-specific `spotify_report` tool returning typed extended metrics with currency.
3. Entity reads: list ad sets per campaign (with budget, schedule, targeting, format, bid), list ads with creative/asset metadata and review status, campaign objective and flight dates.
4. Pacing & flighting: join daily spend to DAILY/LIFETIME budget and flight dates; alert under/over-pacing; frequency-cap awareness (Spotify is reach/frequency driven).
5. Creative ops: audio/video asset upload, companion image, CTA, landing URL; creative fatigue by frequency and completion-rate decay.
6. Safer writes: real dry-run where the API offers validation; re-check budget policy at apply (A10-09); lifetime vs daily cap semantics (A10-08); ad-level status; bid/strategy edits behind the same gate.
7. Account health: parse `status` values (and billing/test-account flags) into normalized health states; surface `NO_DELIVERY_NO_BILLING`.
8. Verification: golden responses recorded from an allowlisted test account; confirm `report_end` inclusivity (A10-05); rate-limit/backoff handling for 429.
9. Localization: Arabic labels and glossary for Spotify-specific terms (audio completion, paid listens) — currently only a hard-coded English `shortLabel` (`provider-connections.tsx:118`).
