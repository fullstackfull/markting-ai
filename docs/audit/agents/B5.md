## Findings

### B5-01 — GAP: no incrementality measurement capability exists in code (doctrine only)
- Severity: GAP
- Classification: VERIFIED_CODE
- Evidence: `engine/workspace/skills/paid-media-wiki/metrics-and-attribution.md:39-43` ("The agent **may recommend** a holdout, geo test, conversion lift study, or other experiment"); grep of `engine/src`/`engine/domain` for geo/holdout/lift/experiment returns only `engine/src/paid_media_agent/testing/demo_script.py:126`; tool directory `engine/src/paid_media_agent/tools/` has no experiment/holdout/geo module; `platform`/`services`/`infra` grep returns nothing.
- Description: The system can neither run nor read out any incrementality experiment. There is no geo-holdout assignment, no conversion-lift / brand-lift study integration, no ghost-ad / PSA holdout, no MER / blended sanity top-line, and no causal estimator. The wiki tells the LLM it *may recommend* such experiments; nothing executes or measures them.
- Impact: The product positions itself as an autonomous "AI media buyer," yet it has no way to establish that spend is causally driving outcomes. Budget/scaling proposals rest entirely on platform-attributed numbers.
- Recommendation: Treat incrementality as an unbuilt capability, not a shipped one. A real toolkit would need holdout/geo-split assignment, a lift read-out tool, and these results surfaced *alongside* attributed numbers.

### B5-02 — P2: the only guardrail separating attributed from incremental lift is prompt text; code does not enforce it on the live path
- Severity: P2
- Classification: VERIFIED_CODE
- Evidence: `engine/instructions.md:20` ("Do not imply that platform attribution is the same as incremental or pipeline impact"); `engine/workspace/skills/paid-media-wiki/metrics-and-attribution.md:31` ("Do not add their conversion counts as if they were deduplicated people or incremental outcomes") and `:43` ("It must not label attributed performance as incremental without evidence"); `SKILL.md:43` ("Platform data ... does not by itself prove incrementality"). No code in `tools/writes.py`, `tools/write_tools.py`, `tools/write_policy.py`, `tools/compare_periods.py`, or `tools/summary.py` inspects, flags, or refuses an incrementality claim — grep for `increment|lift|causal` in those files returns nothing.
- Description: The distinction between platform-attributed lift and incremental lift is enforced only as instruction to the model. There is no deterministic gate: a proposal's `reason`/`measurement_plan` is free text (`demo_script.py:160-168`), `classify_risk` has no incrementality dimension, and no tool refuses a budget change justified by attributed ROAS. On the live (non-demo) path the model's compliance is voluntary.
- Impact: A reliability/financial risk proportional to the product's autonomy: a prompt-only guardrail can be eroded by context, long sessions, or model drift, letting attributed performance be presented or acted on as if it were incremental return. Not a P0/P1 because read/analysis is the dominant path and writes still require typed proposal + approval (B5 did not find a path where an incrementality mislabel directly executes spend unreviewed).
- Recommendation: Add a deterministic caveat/flag emitted by the compute/summary layer whenever ROAS/CPA is reported (machine-inserted "platform-attributed, not incremental"), and an eval that fails when an answer labels attributed performance as incremental.

### B5-03 — P3: the "not incrementality" disclaimer is a hard-coded demo literal and does not demonstrate live behavior
- Severity: P3
- Classification: VERIFIED_CODE, VERIFIED_TEST
- Evidence: `engine/src/paid_media_agent/testing/demo_script.py:125-128` — `compose_answer` appends the fixed string "spend shifts above are platform-attributed delivery facts, not incrementality." This prose is produced by `ScriptedChatModel` (deterministic), not an LLM. `engine/tests/behavior/test_scripted_behavior.py:55` asserts `"incrementality" in answer`; that test passes (exit 0) purely because the literal is hard-coded.
- Description: The single code-level occurrence of the incrementality guardrail lives on the demo path and is asserted by a test that only checks the literal exists. It proves the demo transcript contains the word, not that the live agent separates attributed from incremental lift. This is the inverse of "demo reaching production": the demo's correct disclaimer is unique to the scripted path and is NOT part of the live answer-composition code.
- Impact: Readers of the test suite / phase reports may over-credit the system with an enforced guardrail that only exists as a demo string plus a prompt instruction.
- Recommendation: Do not cite `test_scripted_behavior.py:55` as evidence of a live incrementality guardrail; it tests a fixture literal.

### B5-04 — P3: the eval does not automatically check the incrementality expectations
- Severity: P3
- Classification: VERIFIED_CODE
- Evidence: `engine/tests/eval/questions.json:9,14` (q08 pipeline, q13 attribution) carry `expect` strings about separating platform attribution from pipeline/incremental and not deduplicating conversions. `engine/tests/eval/grade.py:55-69` (`expected_figures`) and `:88-110` (`main`) only check numeric figures for q01/q02/q05; every other question's `expect` is printed for human judgment. `run_questions.py:1-40` requires a live agent server (LLM), so it is not part of the offline pytest suite.
- Description: No automated check verifies that the system refrains from presenting attributed performance as incremental. The attribution/incrementality questions are graded by a human reading a printed table.
- Impact: Regression risk — a model or prompt change could start conflating attribution and incrementality with no test failing.
- Recommendation: Add a programmatic grader assertion (or LLM-judge with fixed rubric) for q08/q13 that fails when attributed numbers are labeled incremental or summed as deduplicated people.

## What a world-class system would need (gaps, concrete)
1. Holdout/geo-split assignment primitive (deterministic, auditable) with a lift read-out tool, results shown beside attributed numbers and never silently replacing them.
2. A machine-inserted "platform-attributed, not incremental" qualifier on every ROAS/CPA figure in structured output, independent of the LLM.
3. A deterministic gate in the write path: any proposal justified by attributed return must carry a measurement/incrementality plan, and scaling claims about "return" must be downgraded in confidence absent lift evidence (a tiered confidence model keyed to experiment evidence).
4. Programmatic eval coverage for attribution-vs-incrementality conflation (q08/q13-style), run offline.
5. Optional conversion-lift / brand-lift API ingestion per provider, and an MER/blended cross-channel sanity metric.

## Disagreements / claims in docs that the code contradicts
- The demo answer and `test_scripted_behavior.py:55` can be read as proof the agent "handles incrementality." Code shows the disclaimer is a hard-coded demo string from `ScriptedChatModel`, not live-LLM behavior (B5-03). The guardrail is doctrine + one fixture literal, not an enforced mechanism.
- Wiki text implies the agent "may recommend a holdout, geo test, conversion lift study" as a live option (`metrics-and-attribution.md:42`). No such experiment can be configured, run, or read out anywhere in the code (B5-01); it is advice the model can speak, not a capability.
