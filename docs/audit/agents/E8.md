## Findings

### E8-01 — Stripe events applied with no ordering/version guard (stale state can re-grant entitlements)
- Severity: P1  Classification: VERIFIED_CODE
- Evidence: `platform/apps/cloud/lib/cloud/billing.ts:57-116` (applySubscription writes status/plan straight from `event.data.object`), `:119-138` (processStripeEvent dispatches on type only), `platform/supabase/migrations/20260828120000_cloud_plans_and_account_scope.sql:51-55` (billing_events stores no event `created` timestamp or subscription version).
- Description: Stripe explicitly does not guarantee webhook delivery order. The handler takes whatever `event.data.object` contains and overwrites `organization_subscriptions` (plan, status, current_period_end, cancel_at_period_end) and re-runs plan-based account enablement. Nothing compares `event.created`, the Stripe-side object version, or re-fetches the live subscription. Each distinct event passes the by-id dedup, so an out-of-order `customer.subscription.updated` (status=active) delivered after `customer.subscription.deleted` (status=canceled) will reactivate the org to a paid plan and re-enable ad accounts after cancellation.
- Impact: Entitlement/financial drift: a canceled or downgraded organization can be left on a higher plan with more active ad accounts than it is paying for, or vice-versa. Because active plan controls `maxActiveAccounts` enforcement (billing.ts:91-106) this directly governs how many ad accounts can spend.
- Recommendation: On each subscription event, re-fetch the authoritative object via `stripe.subscriptions.retrieve(id)` before writing, or persist and compare a monotonic marker (event `created` plus a per-subscription high-water mark) and drop stale writes. Add a regression test delivering two out-of-order updates.

### E8-02 — Idempotency check is not atomic with processing (TOCTOU on concurrent re-delivery)
- Severity: P3  Classification: VERIFIED_CODE
- Evidence: `platform/apps/cloud/lib/cloud/billing.ts:120-123` (SELECT dedup), `:129` (applySubscription), `:132-136` (INSERT ... on conflict do nothing) — three separate `db()` calls, not one transaction.
- Description: The duplicate check reads `private.billing_events` first, processes, then inserts the marker last. Two concurrent deliveries of the same `event.id` (Stripe retries; also a replay inside the signature tolerance window) can both observe no existing row, both run `applySubscription`, then both insert (second is a no-op via `on conflict`). `applySubscription`'s DB updates are idempotent, but it also inserts an `audit_events` row each pass (billing.ts:108-115) and re-runs the account-disable scan, so duplicates are processed rather than rejected. The existing test asserts exactly one `subscription_updated` audit row (`test/database.integration.test.ts:235-239`) but never delivers the same event twice, so this path is unverified by tests.
- Impact: Duplicate audit entries and redundant work under concurrent re-delivery; limited state damage because updates are idempotent. Compounds E8-01 if a stale duplicate wins the race.
- Recommendation: Claim the event first inside the processing transaction — `insert into private.billing_events ... on conflict do nothing returning 1`; if no row returned, treat as duplicate and skip. Run `applySubscription` in the same transaction so the claim rolls back on failure (preserving Stripe retry behavior).

### E8-03 — Authenticated support endpoint has no rate limit (email amplification / cost)
- Severity: P3  Classification: VERIFIED_CODE
- Evidence: `platform/apps/cloud/app/api/support/route.ts:16-41` — no `enforceRateLimit` call; each POST calls `notifySupportMessage` (outbound email) at `:29-34`.
- Description: Unlike waitlist (which rate-limits per IP and globally), the support route performs no throttling. It requires a valid session, but a single authenticated tenant user can submit unbounded feedback/support/bug messages, each triggering a transactional email send. The honeypot (`website: z.string().max(0)`, `:13`) rejects filled values by raising a ZodError → 400, which signals the rejection to a bot rather than silently accepting (contrast waitlist `:79` which returns `{ok:true}`).
- Impact: An authenticated account can flood the support inbox and run up email-provider cost; minor honeypot information leak.
- Recommendation: Add `enforceRateLimit('support:org:<orgId>', n)` and a global bucket; make the honeypot path return a success-shaped response instead of a 400.

## What a world-class system would need
- Transactional event-claim-before-process for Stripe (E8-02) and ordering/version enforcement or live re-fetch (E8-01), with tests for duplicate and out-of-order delivery.
- Handling (or explicit documented ignore) of `invoice.payment_failed` / `checkout.session.completed`; today only `customer.subscription.{created,updated,deleted}` mutate state (billing.ts:126-131) — other lifecycle signals are silently `ignored`.
- A dead-letter / alert path for webhook events that persistently fail `applySubscription` (e.g., subscription not bound to an org, billing.ts:74) instead of relying solely on Stripe's retry window and a one-line console error.
- Rate limiting + silent honeypot on the support endpoint.

## Disagreements / claims in docs that the code contradicts
- None directly contradicted. The billing webhook's inline comments and the PR-era framing imply robust "replay protection via private.billing_events, event ordering"; the code provides replay de-dup (by id) but provides no event ordering and the de-dup is non-atomic — the "ordering" expectation in the workstream brief is not met by the code.
