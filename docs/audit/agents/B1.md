## Findings

### B1-01 — `reconciled=yes` is tautological without provider totals — P2 — VERIFIED_RUNTIME
Evidence: `compute.py:216-224` (the always-present `entity_rows_sum_to_platform_spend` check), `compute.py:225-248` (provider checks added only when `provider_totals` is truthy), `analysis.py:123-125` (`reconciled = all checks passed`), `reads.py:266` (`provider_totals = result.payload.get("totals") or {}` — empty dict when the provider gives no totals).
Description: The only unconditional reconciliation check compares the per-entity spend sum to the platform spend. Both sides derive from the same `aggregate()` over the same rows partitioned by `entity_ref`, so it is mathematically identical and always passes. Probe output: with no provider totals, `checks = [('entity_rows_sum_to_platform_spend', True)]` → `reconciled=True`. External checks (`rows_reconcile_to_provider_spend`, `row_count_matches_provider`) run only when the provider returned a non-empty `totals`.
Impact: `AnalysisSummary.reconciled=True` is surfaced to the model/report as a trust signal, but it can mean "our sum equals our own sum" with zero external corroboration. A silently truncated or partially-fetched provider read still reports `reconciled=yes`.
Recommendation: Represent reconciliation as tri-state (`reconciled` / `not_reconciled` / `no_external_oracle`) or require at least one provider-sourced check before `reconciled` can be true; never let the tautological self-check alone yield `reconciled=yes`.

### B1-02 — Ratios blend full spend with partial conversion data (CPA overstated, ROAS understated) — P2 — VERIFIED_RUNTIME
Evidence: `compute.py:49-57` (`_sum_optional_int`), `compute.py:60-68` (`_sum_optional_decimal` — sums only non-None values), `compute.py:78-92` (`conversions`/`conversion_value` summed over present rows while `spend` is summed over all rows, then `cpa`/`roas` derived), `normalize.py:143-144` (per-row `MISSING_METRIC` flag).
Description: Within one entity/window, `spend` is always summed over every row, but `conversions`/`conversion_value` are summed only over rows that reported them. When some days are missing conversions, CPA = full_spend / partial_conversions and ROAS = partial_value / full_spend. Probe: 7 days × $100 spend with conversions on only 2 days (10 conv, $500 value) → `cpa=70.00`, `roas=1.43`; the two converting days alone give CPA $20 / ROAS 5.0 — a ~3.5× distortion. The number is still emitted as an authoritative figure; the `MISSING_METRIC` flag is attached but the ratio is not suppressed or annotated as partial.
Impact: Headline CPA/ROAS can be materially wrong on partially-reported windows and drive bad budget/bid decisions (P1-adjacent financially), while the surface still prints a precise-looking value.
Recommendation: When a ratio's numerator metric is missing on any row that contributes spend to the denominator (or vice-versa), either suppress the ratio to `unavailable` or compute it only over the subset of rows where both sides are present, and label which basis was used.

### B1-03 — `current_window.is_complete` mislabeled incomplete when only the PREVIOUS window had incomplete rows — P3 — VERIFIED_RUNTIME
Evidence: `compute.py:181-186` (platform_flags unions INCOMPLETE_WINDOW from BOTH current and previous entity rows), `compute.py:203-207` (`current_complete` additionally requires `INCOMPLETE_WINDOW not in platform_flags`), `compute.py:208-210` (`previous_complete` omits that platform_flags guard — asymmetric).
Description: Probe: current window (Aug 3–4) rows all complete+full, previous window has one incomplete row → output `current_window.is_complete = False`. The previous window's incompleteness leaks into the current window's completeness via the shared `platform_flags` set.
Impact: Safe direction for totals (over-suppresses), but the per-window completeness label is wrong — the summary renders the current window as "(incomplete)" (`compute.py:344-346`) when it is actually complete, misleading the reader and the model.
Recommendation: Compute each window's completeness only from its own rows; do not gate `current_complete` on `platform_flags` that also carries previous-window flags.

### B1-04 — Provider reconciliation fails spuriously when the read covered rows outside current∪previous — P3 — VERIFIED_RUNTIME
Evidence: `compute.py:226` (`all_rows = current_rows + previous_rows`), `compute.py:230-238` (compares that sum to `provider_totals["spend"]`), `reads.py:258-266` (`provider_totals` is the provider total for the entire read window).
Description: `provider_totals` is the provider's total for the whole read, but the reconciliation sums only rows inside the two comparison windows. Probe: a read of Aug 1–3 compared as Aug 1 vs Aug 2 (Aug 3 is a buffer/gap day) → `rows_reconcile_to_provider_spend` FALSE (`provider 1109 vs rows 110`) and `row_count_matches_provider` FALSE, hence `reconciled=no`, despite correct data.
Impact: Any non-contiguous windows or a read with a buffer makes `reconciled=no` even when the pipeline is sound, eroding the signal's usefulness (and interacting with B1-01 to make `reconciled` close to noise).
Recommendation: Reconcile the provider total against the rows over the exact window(s) the provider total covers, or store a per-window provider total; don't compare a whole-read total to a windowed row subset.

### B1-05 — Two divergent measurement engines (Python Decimal vs TypeScript float) with different null semantics — P2 — VERIFIED_CODE
Evidence: `compute.py:71-95` (Decimal, sums present values, derives ratios) vs `report-summary.ts:19-31` (JS `number`/float; `total()` returns null unless EVERY row has the metric — `group.rows.every(... available ...)`).
Description: The engine computes metrics with exact `Decimal`; the platform core computes "the same" cross-platform report with floating-point `number`, and uses stricter null rules (all-rows-required) than the engine (any-row-present, see B1-02). ROAS reconstruction in TS (`spend * roas` summed, then `value/spend`) accumulates float error on money.
Impact: The same account/window can produce different spend/ROAS/CPA depending on which subsystem rendered it; float accumulation can drift cents on large sums. Divergent null semantics also mean one surface shows a number where the other shows `null`.
Recommendation: Define one canonical metric contract (precision, rounding, null policy) and have both engines conform, or route all authoritative numbers through one engine; add a cross-engine golden test.

### B1-06 — Reconciliation covers only spend and row_count; ROAS/CPA numerators never reconciled — P3 — VERIFIED_CODE
Evidence: `compute.py:225-248` — only `provider_totals["spend"]` and `["row_count"]` are checked; `conversions`/`conversion_value` are never reconciled to provider totals.
Impact: The inputs that most directly drive ROAS/CPA (conversions and value) are never cross-checked against the provider, so `reconciled=yes` says nothing about the correctness of the conversion figures.
Recommendation: Add provider reconciliation for conversions and conversion_value where the provider supplies them, and down-rank `reconciled` when they are unavailable.

### B1-07 — Cross-platform total combines windows with equal dates but possibly different timezones — P3 — INFERRED
Evidence: `compute.py:325` (equality check on `(start, end)` only, timezone excluded), `compute.py:330-331` (`_combine` ignores timezone), `compute.py:152-156` (timezone is tracked per platform).
Impact: Two platforms both labeled "2026-08-15..2026-08-28" in different timezones have different wall-clock day boundaries; combining them silently mixes slightly different real intervals. Low magnitude, but the model tracks timezone precisely elsewhere and then discards it here.
Recommendation: Either require matching timezones to combine, or attach a `TIMEZONE_MISMATCH` note to the cross-platform total.

### B1-08 — Daily day-over-day change compares nearest present days, not calendar-adjacent days — P3 — VERIFIED_CODE
Evidence: `summary.py:108-127` — `days = sorted(present days)`; `previous` is the prior element in that list, and `spend_change`/`conversions_change` plus `DAY_CHANGE_FLAG` are computed against it regardless of calendar gaps.
Impact: If a day has no rows, the next present day is compared to one several days earlier but labeled `*_change` (day-over-day) and can trip the ±50% flag, implying a one-day swing that spans a gap.
Recommendation: Compute change against the calendar-previous day and emit `null`/a gap marker when it is absent.

### B1-09 — `pacing` uses active-day average, which can read as over-budget for intermittent entities — P3 — INFERRED
Evidence: `summary.py:88-89` (`active_days = len(distinct days with rows)`; `average_daily = spend / active_days`), `summary.py:104` (`pacing = average_daily / budget`), `summary.py:145-147` (`over_budget` when `pacing > 1`).
Impact: An entity that ran 2 of 7 days is paced on its active-day average, so a burst on active days flags it over-budget even if its window-average is well under budget. Defensible (daily cap) but the per-active-day basis is not surfaced and can mislead readers who assume window-average pacing.
Recommendation: Surface `active_days` alongside pacing (already present) and document the basis, or offer both active-day and window-day pacing.

### B1-10 — Reconciliation uses exact Decimal equality after per-row 6dp quantization — P3 — VERIFIED_CODE
Evidence: `normalize.py:159` (each row spend quantized to 1e-6), `compute.py:229-238` (provider spend quantized once, compared with `==` to the sum of already-quantized rows).
Impact: Summing many independently 6dp-rounded rows and comparing with `==` to a single-quantized provider total can diverge by sub-micro rounding, producing rare spurious `reconciled=no`. Low probability at 6dp but it is exact equality on floats-turned-Decimals from providers.
Recommendation: Reconcile with a tolerance (e.g. within one currency minor unit) rather than exact equality.

## What a world-class system would need
- A single metric contract (precision, rounding mode, null policy, ratio-basis rules) enforced by both engines, with cross-engine golden tests.
- Ratio integrity rule: a ratio is emitted only when numerator and denominator cover the same row/day set, else suppressed or explicitly labeled "partial basis" with the covered denominator.
- A meaningful, tri-state reconciliation signal that requires an external oracle and reconciles conversions/value (not just spend/row_count), with tolerance-based comparison.
- Per-window completeness and per-window provider totals so reconciliation and the `(incomplete)` label are each scoped to their own window.
- Timezone-aware combination (match or flag) for cross-platform totals.
- Attribution-window / data-freshness metadata carried onto conversions so ROAS deltas are not compared across shifting attribution (the `ATTRIBUTION_DIFFERS` flag exists in the enum, common.py:64, but is not set anywhere in scope — NOT_VERIFIED that it is ever populated).

## Disagreements / claims in docs that the code contradicts
- builtin.ts tool description (`tools/builtin.ts:57`) and summary.py docstrings advertise authoritative, deterministic numbers; in practice CPA/ROAS can silently blend full spend with partial conversions (B1-02) and `reconciled=yes` can be tautological (B1-01). The numbers are deterministic but not always meaningful.
- `report-summary.ts:6` ("unknown currencies must stay account-scoped") and the engine's "never average ratios" guidance are honored, but the two engines disagree on null semantics and precision (B1-05), so "the metric" is not single-valued across the product.
