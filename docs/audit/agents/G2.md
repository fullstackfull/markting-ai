## Findings

### G2-01 — The Assistant and the "AI analysis reports" never analyse the tenant's connected accounts (engine is pinned to fixture data in both modes)
- **Severity:** P1  **Classification:** VERIFIED_CODE (capability: MOCK_ONLY)
- **Evidence:**
  - `services/engine-demo/serve_demo.py:383-388` — `resolved = demo_settings(base) if mode == "demo" else base.model_copy(update={"paid_media_data_mode": "sample"})`; both branches force `paid_media_data_mode = "sample"`.
  - `services/engine-demo/serve_demo.py:139-165` — `assert_fail_closed` refuses to start unless `paid_media_data_mode == "sample"` (`:163-165`) and `PIPEBOARD_API_TOKEN` is unset (`:142-143`).
  - `engine/src/paid_media_agent/runtime/catalog.py:51-57` — `sample` loads `build_fixture_catalog()` with `read_provider=None`.
  - `engine/src/paid_media_agent/runtime/profiles.py:71-75` — `sample` loads accounts from `config/accounts.example.toml`.
  - `platform/apps/cloud/lib/markting/engine-client.ts:111-137` — the only engine calls are `sendMessage`, `getProposal`, `rejectProposal`, `runReport`, `listReports`, `fetchReportFile`; nothing pushes adport's tenant report rows into the engine.
  - UI copy contradicted: `platform/apps/cloud/lib/i18n/messages/assistant.ts:5` ("Ask about performance across your connected accounts"), `README.md:83` ("Analyses connected accounts (spend, conversions, CPA, ROAS)").
- **Description:** `MARKTING_ENGINE_MODE=live` only swaps the scripted model for a real LLM; the data the model reasons over stays the engine's three fixture accounts. A buyer who connects a real Google/Meta account through OAuth and then asks the Assistant "what needs attention this week" gets an analysis of `demo-google`/`demo-meta`/`demo-reddit`, and any proposal maps to adport accounts only via the alias table seeded by `infra/seed/seed-demo.mjs:58` (there is no UI to create aliases; `upsertAlias` has no caller outside tests: `lib/markting/repository.ts:52`).
- **Impact:** The two screens that are supposed to carry the "AI media buyer" value proposition cannot inform a real decision. The Assistant description and demo banner (`assistant/page.tsx:21`) tell the user it is demo only when `MARKTING_DEMO_MODE=true`; with demo mode off and live engine mode on, the UI presents fixture analysis as real.
- **Recommendation:** Either (a) feed the engine the tenant's normalized `report` rows per turn (adport already has them; `lib/cloud/reads.ts:48`), or (b) make the Assistant/Reports cards state explicitly, in both locales and regardless of `MARKTING_DEMO_MODE`, that analysis runs on sample data until a per-tenant data path exists. Do not ship the current copy.

### G2-02 — Engine report runs are global, not per-organization; any signed-in user lists and downloads every run
- **Severity:** P1 (becomes P0 cross-tenant in any multi-tenant deployment where engine data is real)  **Classification:** VERIFIED_CODE
- **Evidence:**
  - `platform/apps/cloud/app/api/reports/engine/route.ts:16-24` — `GET` validates the session (`sessionPrincipal(organizationId)`) and returns `engineClient().listReports()` with no org filter.
  - `platform/apps/cloud/app/api/reports/engine/[name]/route.ts:13-15` — file download checks only that a session exists, then proxies any `rpt_*`/`art_*` file.
  - `services/engine-demo/serve_demo.py:252-260, 299-301, 355-358` — one `markting-reports.json` index under `workspace/out`, last 50 entries, `requested_by` = the shared token's caller name.
  - `platform/apps/cloud/lib/markting/env.ts:12` — a single `MARKTING_ENGINE_TOKEN` for all organizations.
- **Description:** The Reports card titled "AI analysis reports" (`engine-reports.tsx:45`) shows a shared, cross-org queue. Org A's "Run weekly report" appears in Org B's list; Org B can download its PDF. The `requested_by` column cannot distinguish organizations because adport authenticates to the engine as one caller.
- **Impact:** Today the report content is fixture data (G2-01) so no tenant data leaks, but the UX is wrong (a buyer sees runs they did not trigger, with no author, and may act on them), and the moment the engine is given real data this is a cross-tenant disclosure.
- **Recommendation:** Namespace runs by organization on the adport side (store run ids in a `markting_report_runs` table keyed by org, filter `listReports()` results, and refuse downloads for ids the org does not own), or send an org identifier to `/reports/run` and have the host index per caller/org.

### G2-03 — Overview ROAS tile is always "0×" because `conversion_value` is never requested
- **Severity:** P2  **Classification:** VERIFIED_CODE
- **Evidence:**
  - `platform/apps/cloud/lib/cloud/reads.ts:54` — `metrics: ['spend', 'impressions', 'clicks', 'conversions', 'roas']` (no `conversion_value`).
  - `platform/apps/cloud/app/dashboard/live-data.tsx:39,41` — `value: sum.value + (row.metrics.conversion_value ?? 0)` then `roas = totals.spend > 0 ? totals.value / totals.spend : 0`.
  - Providers project to the requested metrics only: `platform/packages/google/src/provider.ts:232`, `platform/packages/meta/src/provider.ts:230`, `platform/apps/cloud/lib/markting/sandbox-provider.ts:138` (`Object.fromEntries(query.metrics.map(...))`).
  - `platform/packages/core/src/model.ts:1-12` — `conversion_value` is a valid `MetricName`.
- **Description:** The headline ROAS metric on the first screen a buyer sees is structurally zero while the per-row ROAS column (`live-data.tsx:76`) shows real values, so the page contradicts itself. The footer "Conversion value ÷ spend" (`overview.ts:25`) describes a computation that cannot succeed.
- **Impact:** The one blended efficiency number on the overview is wrong for every tenant, demo or live.
- **Recommendation:** Request `conversion_value` (and ideally use `summary.groups[].metrics.roas` from the tool, see G2-04) or drop the tile until it can be computed honestly.

### G2-04 — Overview sums spend and ROAS across currencies and discards the tool's currency-separated summary
- **Severity:** P2  **Classification:** VERIFIED_CODE
- **Evidence:**
  - `platform/apps/cloud/app/dashboard/live-data.tsx:34-41` — single `reduce` over all rows regardless of `row.currency`; the `Summary` interface (`live-data.tsx:8`) does not even carry `currency`.
  - `platform/apps/cloud/lib/cloud/reads.ts:53-58` — the `report` tool result is destructured to `{ rows, truncated, errors }`; `summary` is dropped.
  - `platform/packages/core/src/tools/builtin.ts:57` — tool description: "Use summary.groups for currency-separated totals and spend-weighted ROAS; never average row ratios or combine currencies."
  - `platform/packages/core/src/report-summary.ts:7-40` — `summarizeReport` already produces per-currency totals and a correctly derived ROAS with `roas_method`.
  - `platform/packages/core/src/model.ts:41-42` — `ReportRow.currency` exists ("Never infer FX").
- **Description:** A tenant with a SAR Snapchat account and a USD Google account sees one "Spend" number that adds SAR to USD. The footer "account currencies" (`overview.ts:20`) acknowledges the mix without preventing it. The same table on `/dashboard/reports` shows no currency column either (`reports/page.tsx:33-45`).
- **Impact:** For a GCC media buyer, mixed SAR/AED/USD accounts are the norm; the headline spend is not a number anyone can budget against.
- **Recommendation:** Render `summary.groups` (one tile group per currency, using `formatMoney` from `components/ui.tsx:67` which exists but is unused on these pages), and add a currency column to both tables.

### G2-05 — The approval row is not actionable enough: summary only, no before/after, deltas, risk or plans; reject has no reason field
- **Severity:** P2  **Classification:** VERIFIED_CODE
- **Evidence:**
  - `platform/apps/cloud/app/dashboard/approvals/page.tsx:30` — shows `operation.preview?.summary ?? operation.operation.tool` and the pending id; `preview.changes`, `preview.coercions`, `preview.budgetDeltas`, `preview.serverValidated` (`platform/packages/core/src/provider.ts:32-40`) are never rendered.
  - `approvals/page.tsx:37` — engine provenance shows tool name, `account_ref/target_ref` and `reason` sliced to 160 characters; `before`, `after`, `risk`, `risk_flags`, `measurement_plan`, `reversal_plan` (`lib/markting/translate.ts:24-45`) are stored in `markting_engine_proposals.proposal` but not shown.
  - `approval-actions.tsx:19` — apply confirmation is a bare `window.confirm` with a generic string (`approvals.ts:20`); no restatement of the change.
  - `approval-actions.tsx:22-25` — reject posts `{ organizationId }` only, while `app/api/approvals/[id]/reject/route.ts:15` accepts and audits a `reason` (300 chars). The UI never offers it.
  - `approvals/page.tsx:39` — expiry shown as an absolute UTC timestamp; default TTL is 15 minutes (`platform/packages/core/src/policy/policy.ts:19`), no countdown or "expires in" phrasing.
  - `docs/TODO.md` §6 admits: "Approvals page: show the full preview (changes, coercions, budget deltas) inline, not only the summary."
- **Description:** A buyer approving a budget change cannot see the current budget, the new budget, the percentage delta, whether the platform dry-run validated it, or the engine's stated measurement and rollback plan, all of which exist in the data the row already loads. The Assistant's own BridgeCard (`assistant-chat.tsx:104-114`) shows more (changes + coercions) than the Approvals page, and that card is only visible to the requester, who is by default forbidden from applying (`apply/route.ts:22-24`).
- **Impact:** The approver, the one person whose judgment the whole architecture depends on, sees the least information. The 15-minute window makes a "check elsewhere then come back" workflow impractical.
- **Recommendation:** Expand each row (or a detail drawer) with `changes`, `budgetDeltas` (before → after, % delta, currency), `coercions`, `serverValidated`, engine `before/after`, `risk` + `risk_flags`, full `reason`, `measurement_plan`, `reversal_plan`, requester identity and relative expiry. Add a reject-reason input. Replace `window.confirm` with an inline confirmation that restates the change.

### G2-06 — Apply button is offered to the requester although the server will refuse self-approval
- **Severity:** P3  **Classification:** VERIFIED_CODE
- **Evidence:** `approvals/page.tsx:14` (`canApply = canAdminister(tenant)`, role only) and `:40`; `app/api/approvals/[id]/apply/route.ts:22-24` rejects when `row.createdBy === principal.userId` unless `MARKTING_ALLOW_SELF_APPROVAL=true`. `listPendingOperations` returns `createdBy` (`lib/cloud/repository.ts:684-707`) so the page has the data to hide the button.
- **Impact:** An owner/admin who asked the Assistant for a change sees "Apply", confirms, and gets a 403 message. Confusing, and it hides the "someone else must approve" rule that the product depends on.
- **Recommendation:** Compare `operation.createdBy` with `tenant.userId` and render "Needs a second approver" instead of the button.

### G2-07 — Assistant conversations are lost on reload; no thread list, no streaming, blocking composer
- **Severity:** P2  **Classification:** VERIFIED_CODE
- **Evidence:** `assistant-chat.tsx:24-25` — `messages` and `threadId` live in `useState` only; `lib/markting/repository.ts:29-36` — `listThreads` exists and `markting_threads` stores title/last message, but nothing calls it from the UI (grep: only `repository.ts`). `assistant-chat.tsx:92` disables the textarea while `busy`; `lib/markting/env.ts:18` allows up to 240 s per turn (default) and `app/api/assistant/messages/route.ts:7` sets `maxDuration = 300`; `engine-client.ts:113` documents the synchronous call. `assistant-chat.tsx:77` renders replies as `<pre>` (no markdown, no tables). `docs/TODO.md` §6 acknowledges both items.
- **Impact:** A buyer cannot return to yesterday's analysis, cannot find the thread that produced a pending operation (the Approvals page shows no thread link), and waits with a frozen input for a minutes-long turn.
- **Recommendation:** List threads from `markting_threads`, persist and replay messages (engine threads are addressable by id), link each pending operation to its thread, stream or at least poll, and render markdown.

### G2-08 — Findings page is display-only and hides the evidence it claims to carry
- **Severity:** P3 (feature is a GAP; the copy over-claims)  **Classification:** VERIFIED_CODE
- **Evidence:** `findings/page.tsx:12` lists all statuses unfiltered although the store supports `{status, provider}` filters (`lib/cloud/repository.ts:438-466`); `:26-34` renders severity, title, recommendation, provider, account, status, updated. Not rendered: `detail`, `entity` (which campaign), `metrics`, `dateRange`, `proposedAction`, `ruleId` (`platform/packages/core/src/audit/types.ts:12-30`). No dismiss/apply controls although the core exposes `recommendation_dismiss` and `recommendation_apply` (`platform/packages/core/src/audit/tools.ts:82,94`). Copy: `findings.ts:5` "Persisted, evidence-backed audit results".
- **Impact:** A buyer sees "critical: X" without the numbers or the campaign name, cannot dismiss noise, and cannot turn a finding with a `proposedAction` into a preview from the page. Dismissed and applied findings are mixed with open ones.
- **Recommendation:** Show entity name, detail and metrics; default to `open`; add Dismiss and "Preview this action" (through `recommendation_apply`, which already routes through the policy engine).

### G2-09 — No date control, period comparison, breakdown, sort, drill-down or export on any data screen
- **Severity:** GAP (not a defect; code does not claim them)  **Classification:** VERIFIED_CODE
- **Evidence:** Overview is hard-wired to `last_7_days` (`app/api/dashboard/summary/route.ts:9`), Reports to `last_30_days` (`reports/page.tsx:11`), both at `level: 'campaign'` with `limit: 250` (`reads.ts:53-55`); `readReport`'s signature only accepts those two presets (`reads.ts:48`) although core supports `today`, `yesterday`, `this_month` and custom ranges (`platform/packages/core/src/model.ts:18,56-58`) and `account | campaign | ad_group | ad` levels (`model.ts:15`). The overview table is `rows.slice(0, 12)` (`live-data.tsx:68`); neither table has sort, filter, pagination, search, CSV export or a per-campaign page (campaign cells are plain `<strong>`; `live-data.tsx:70`, `reports/page.tsx:37`). Metrics shown are spend/impressions/clicks/conversions/ROAS only; CTR, CPC, CPM, CPA (`model.ts:7-10`) are never requested. Engine `POST /reports/run` accepts an `end` date (`app/api/reports/engine/route.ts:34`) but `engine-reports.tsx:35` never sends one, so a buyer cannot reproduce last month's report.
- **Impact:** A media buyer's core daily questions (what changed vs. last week, which ad set is burning budget, which account in which currency) cannot be answered on these screens; they must leave for the native platform UIs.

## What a world-class system would need (concrete, in priority order for a GCC media buyer)

1. **Honest data provenance.** Every analysis screen must say which accounts and which window it analysed; the Assistant and Reports cards must not call fixture data "your connected accounts" (G2-01). The engine needs a per-tenant data path (adport already normalizes the rows).
2. **Currency-aware KPI strip** with one group per currency (SAR, AED, USD), a working ROAS, CPA/CTR/CPC/CPM, and a previous-period delta on every tile (`summary.groups` + a second `report` call for the prior window).
