## Findings

### F6-01 — Concurrent `apply()` with the same pending id executes the provider write twice
- Severity: **P1**
- Classification: **VERIFIED_RUNTIME** (file store), **VERIFIED_CODE** (Postgres store)
- Evidence:
  - `platform/packages/core/src/policy/engine.ts:90` (`pending.get`), `:113` (`provider.applyWrite`), `:114-122` (`audit.append('applied')`), `:123` (`pending.delete`) — the pending row is consumed only *after* the provider mutation, and nothing between `get` and `applyWrite` claims the id.
  - `platform/apps/cloud/lib/cloud/repository.ts:385-411` — `PostgresPendingStore.get` is a plain `select ... where consumed_at is null`; `:413-418` — `delete` is `update ... set consumed_at = now() where id = ... and organization_id = ...` with **no** `consumed_at is null` predicate, no `returning`, and no row-count check; the result is discarded.
  - `platform/packages/core/src/policy/pending.ts:41-52` — file store `get`/`delete` are equally unconditional (`fs.readFile` / `fs.rm force`).
  - `platform/apps/cloud/lib/cloud/runtime.ts:140` and `platform/apps/cloud/lib/markting/runtime.ts:24` — every hosted tenant runtime (MCP, REST, dashboard bridge) uses this engine + store, so the hazard is live in production paths, not only the CLI.
  - `platform/packages/core/src/tools/write.ts:64` — the MCP/REST tool handler calls `ctx.engine.apply(...)` directly with the caller-supplied `pending_operation_id`; there is no idempotency key or per-id mutex (`grep -rni idempotency platform/apps/cloud` → no matches).
  - Runtime reproduction, command #1: both appliers fulfilled, `applyWriteCalls: 2`, audit `[validated, applied, applied]`.
  - Contrast: the same repository already contains the correct pattern for other single-use artifacts — `repository.ts:81-100` (`for update` + consume inside `db().begin` for OAuth state) and `mcp-oauth-repository.ts:221-253` (refresh-token rotation), and the Python engine claims before executing (see F6-C1). The pending store simply does not use it.
- Description: Two requests carrying the same `pending_operation_id` that overlap in time (client retry after a timeout, a double-clicked dashboard button, an MCP client resending `tools/call`, or two replicas serving the same tenant) both pass `get()`, both pass the hash/expiry checks, and both call `provider.applyWrite`. For `kind: 'create'` operations this produces duplicate campaigns / ad sets / ads on the ad platform; for updates it issues the provider write twice. The audit log then contains two `applied` events for one pending id, so the "exactly one approved execution per preview" contract that the whole two-step design rests on is not enforced under concurrency. The in-test comment `// Pending id is single-use.` (`policy-engine.test.ts:100`) is only true for sequential calls.
- Impact: Duplicate ad-platform mutations and duplicate spend objects. Mitigating factor that keeps this at P1 rather than P0: the default policy coerces created campaigns to `PAUSED` (`engine.ts:55`, tested at `policy-engine.test.ts:78-90`), so duplicates created under default policy do not spend until someone enables them; with `paused_creation: false` the duplicates are live. Also a secondary failure mode: if `audit.append` or `pending.delete` throws after a successful `applyWrite` (`engine.ts:114-123`), the pending id stays unconsumed and can be replayed later within its TTL.
- Recommendation: Claim before executing. For Postgres: `update public.pending_operations set consumed_at = now() where id = $1 and organization_id = $2 and consumed_at is null and expires_at > now() returning ...` and treat zero rows as `PENDING_NOT_FOUND`/`PENDING_EXPIRED`; for the file store, use an atomic `rename` to a `.claimed` name (or `open` with `O_EXCL` on a marker). Extend `PendingOperationStore` with a `claim(id)` (or make `delete` return a boolean) and call it *before* `provider.applyWrite`, recording the outcome afterwards. Add a concurrent test (`Promise.all` of two `apply` calls with a slow mock `applyWrite`) asserting exactly one provider call, and a Postgres-backed equivalent.

### F6-02 — Dashboard "reject" cannot stop an in-flight "apply": the rejected operation still executes
- Severity: **P2**
- Classification: **VERIFIED_CODE** (ordering), **INFERRED** (timing window)
- Evidence: `platform/apps/cloud/app/api/approvals/[id]/apply/route.ts:20-27` (read via `listPendingOperations(...).find`, then `applyPending`, then `markPendingOutcome('applied')`); `.../reject/route.ts:13-21` (read, then unconditional `PostgresPendingStore.delete`, then audit `rejected`, then `markPendingOutcome('rejected')`); `engine.ts:90-113` (no re-check of consumption between `get` and `applyWrite`).
- Description: Approver A clicks Apply while approver B clicks Reject. A's request passes `engine.apply`'s `get()`; B's `delete` sets `consumed_at`; A proceeds to `provider.applyWrite` anyway because nothing re-validates the row after the initial `get`. The audit trail then shows `rejected` followed by `applied` for one pending id, and `markting_engine_proposals.status` ends in whichever route finishes last (`repository.ts:107-112` is an unconditional update). The same read-then-act shape makes two concurrent Apply clicks a direct instance of F6-01.
- Impact: A human reject is not authoritative once an apply has started; the audit trail becomes contradictory. Requires the same tenant and overlapping requests, so it is a reliability/safety-control deficiency rather than a cross-tenant issue.
- Recommendation: Same atomic claim as F6-01 (a reject that wins the claim must make the apply fail with `PENDING_NOT_FOUND`); make `markPendingOutcome` conditional on current status.

### F6-03 — Budget policy is not re-evaluated at apply time (validate→apply TOCTOU)
- Severity: **P3**
- Classification: **VERIFIED_CODE**
- Evidence: `engine.ts:110-111` re-runs only `checkStaticPolicy` (protected accounts); `checkBudgetPolicy` runs only in `validate` (`engine.ts:62`) against `preview.budgetDeltas.fromMicros` captured at validate time; `engine.ts:104` compares only the operation hash. Sandbox CAS compares state loaded inside `applyWrite` itself, not the preview-time state (`sandbox-provider.ts:144-147`, `:178-180`).
- Description: Within `pending_ttl_minutes`, the live baseline can change (another operator, another pending op, or the platform). The percentage cap was computed against a stale `fromMicros`; apply does not recompute it, and real providers have no CAS at all. Example: validate `12.4M → 15.4M` (24 %) while a concurrent op lowers the budget to `10M`; apply still writes `15.4M`, a 54 % jump relative to the live value.
- Impact: The percentage-delta rail can be exceeded under concurrent edits. Absolute cap (`max_daily_budget_micros`) is unaffected because it depends only on `toMicros`.
- Recommendation: In `apply`, re-run `previewWrite` (or a cheap read of the target) and re-apply `checkBudgetPolicy`, or fail with `PENDING_MISMATCH` when the live baseline differs from `preview.budgetDeltas[].fromMicros`.

### F6-04 — Stripe webhook dedupe is check-then-act, not atomic
- Severity: **P3**
- Classification: **VERIFIED_CODE**
- Evidence: `platform/apps/cloud/lib/cloud/billing.ts:120-123` (select by `event_id`, return `'duplicate'`), `:126-131` (`applySubscription` runs), `:132-136` (`insert ... on conflict (event_id) do nothing` **after** processing). Schema: `platform/supabase/migrations/20260828120000_cloud_plans_and_account_scope.sql:51-55` (`event_id` is the PK, so an insert-first approach would work). Only one delivery is tested (`database.integration.test.ts:219-233`; command #5).
- Description: Two concurrent deliveries of the same event (Stripe retries on slow 2xx) both see no row, both run `applySubscription` (a plan update plus account disabling plus an `audit_events` insert at `billing.ts:107-115`), and then both attempt the marker insert. Nothing compares `event.created` either, so an older `customer.subscription.updated` arriving after a newer one overwrites the newer plan/status (`billing.ts:77-87` is last-writer-wins).
- Impact: Duplicate `subscription_updated` audit rows and, in the out-of-order case, a stale plan/entitlement. Writes are idempotent for the *same* event, so this is bounded; the ordering case is the more consequential one for entitlements.
- Recommendation: Insert the marker first (`insert ... on conflict do nothing returning event_id`; zero rows → `'duplicate'`) inside the same transaction as `applySubscription`, and ignore events whose `created` is older than the stored subscription's last applied event timestamp.

### F6-06 — Provider OAuth refresh has no single-flight except LinkedIn; Microsoft rotates refresh tokens without coalescing
- Severity: **P3**
- Classification: **VERIFIED_CODE** (code shape), **INFERRED** (provider-side consequences)
- Evidence: single-flight present only in `platform/packages/linkedin/src/client.ts:52,96-97` (`this.refreshing` promise). Absent in `google/src/client.ts:57-77`, `microsoft/src/client.ts:53-83`, `apple/src/client.ts:37-70`, `snapchat/src/client.ts:126-136`: each checks `accessToken.expiresAt` then awaits a network refresh, so N concurrent requests on a cold client issue N refreshes. Microsoft additionally rotates: `microsoft/src/client.ts:79-82` persists whichever `refresh_token` arrives via `onRefreshTokenRotated`, and concurrent refreshes race on which rotated token is stored. Clients are constructed per tenant request in `lib/cloud/runtime.ts`, so in-process coalescing would not help across requests anyway.
- Description: Duplicate token-endpoint calls per cold start; for rotating providers, the stored refresh token may be superseded by a sibling refresh, risking `invalid_grant` on the next cold start. Not a security hazard; a reliability/quota one.
- Recommendation: Coalesce refreshes behind a promise (as LinkedIn does) and, for hosted multi-replica deployments, serialize credential rotation with `select ... for update` on `private.provider_credentials` before writing the rotated token.

### F6-07 — Non-atomic file writes in local-mode stores
- Severity: **P3**
- Classification: **VERIFIED_CODE** / **INFERRED**
- Evidence: `platform/packages/core/src/policy/pending.ts:38` (`fs.writeFile` directly to the final path), `platform/packages/core/src/audit/store.ts:55`, `platform/packages/core/src/credentials/store.ts:46`; `policy/audit.ts:34` (`appendFile` of one JSON line, which may exceed `PIPE_BUF` when `details` is large). - Description: A reader racing a writer (two CLI processes, or MCP server plus CLI) can observe a truncated JSON file and get a parse error rather than a clean `PENDING_NOT_FOUND`; audit lines longer than the atomic-append threshold can interleave. The "report index file" hazard named in the workstream does not exist in this codebase because there is no index file.
- Recommendation: Write to a temp file and `rename`; keep audit lines short or guard with a lock file.

## What a world-class system would need (gaps, concrete)

1. An atomic claim primitive in `PendingOperationStore` (`claim(id): Promise<PendingOperation | undefined>`) executed **before** the provider call, with the Postgres implementation as a single conditional `update ... returning` and the file implementation as `rename`; `apply` records `applied`/`failed` against the claimed row afterwards.
2. Provider-side idempotency keys on every `create` mutation (the Python engine already does `proposal_id:revision`, `writes.py:826-829`); adport could pass `pendingId` through `WriteOperation` so a replayed create is rejected by the platform even if the gate is bypassed.
3. A concurrency test matrix in `platform/packages/core/test/policy-engine.test.ts`: two `apply` calls racing, apply racing reject, and a delete failure after a successful write; mirrored against Postgres in `apps/cloud/test`.
4. CI with a Postgres service so every `*.database.test.ts` and `test_postgres_repositories_roundtrip` actually runs.
5. Re-validation of budget baselines at apply time (or a provider-level CAS such as Meta `etag`/Google `resource_name` + `update_mask` with a `validate_only` pre-check) so the percentage rail is enforced against live state.
6. Insert-first webhook idempotency plus `event.created` ordering for Stripe, inside one transaction with the plan update.
7. Refresh coalescing and `for update` on `private.provider_credentials` when persisting rotated refresh tokens across replicas.

- `docs/ARCHITECTURE.md:824` says 409 is returned for a concurrent-save conflict — **confirmed** for `/reject` and `/edit` (`app.py:134-137,144-147`); `/approve` maps `WriteDenied` to 403 (`app.py:120-123`), so a `proposal_changed` conflict on approve surfaces as 403, not 409 (minor doc/code mismatch).
- No document claims that the Postgres-backed concurrency tests run in CI; the gap is that nothing says they do not (F6-05).
