**One-paragraph verdict.** The product has **no committed, repeatable end-to-end suite**. The only file under an `e2e` directory (`engine/tests/e2e/console_walkthrough.mjs`) is the upstream paid-media-agent *setup-console* walkthrough, byte-for-byte as imported, exercising a surface markting-ai never deploys; Playwright is not resolvable from either tree and no browser binaries are installed. What *is* committed and green is a strong unit/contract layer for the bridge core (53 vitest cases + 7 pytest cases + 3 node tests via `make test`), plus DB-gated integration tests that need a local Supabase stack that is not available here. The new user-facing routes and components (Assistant chat, Approvals apply/reject, engine Reports) have **zero** test coverage of any kind above the library layer. Below I define the scenario matrix a production system needs and the infrastructure that would make it repeatable in CI.

## Findings

### F3-01 — No committed end-to-end suite for the product; documented browser runs are not reproducible
- **Severity:** GAP (coverage) with a DOCUMENTED_ONLY claim attached
- **Classification:** VERIFIED_CODE (absence), DOCUMENTED_ONLY (the claims)
- **Evidence:** commands 2, 3, 5, 7; `docs/PHASE1-REPORT.md:31` ("Browser end-to-end (Playwright, standalone build on :3100 + engine host) | sign in → Assistant … → Apply → row gone … → Reports: run weekly, PDF downloads"); `docs/PHASE2-REPORT.md:23` ("Browser walkthrough (Playwright, standalone build) | Default dir="rtl" lang="ar" … all 12 dashboard sections render Arabic headings …"); `docs/PHASE2-REPORT.md:24` ("Phase 1 functional flow re-run in English … OK"); `find` for `*.png` returns only upstream marketing/screenshot assets.
- **Description:** The two phase reports present Playwright walkthroughs as verification evidence. Nothing in the repository lets anyone re-run them: no spec files, no `playwright.config.*`, no package dependency, no screenshots, no transcript, no CI job. The claims may well have been true in the authoring session, but they are unverifiable from the repo and will silently rot with every UI change.
- **Impact:** Regressions in the single most important path of the product (chat → proposal → approval → apply → audit) can only be caught by hand. The Arabic/RTL conversion of ~560 strings across every page (`docs/PHASE2-REPORT.md:10-11`) has only dictionary-parity unit tests (`test/i18n.test.ts`), not a rendered check.
- **Recommendation:** Commit a Playwright project (see "What a world-class system would need") and move the two phase-report rows into it as the first two specs; until then, re-label those rows in the reports as "manual, not repeatable".

### F3-02 — `engine/tests/e2e/console_walkthrough.mjs` tests a surface markting-ai does not ship, and cannot run from the repository
- **Severity:** P3 (misleading coverage signal; no runtime defect)

### F3-04 — The documented happy path relied on self-approval; `.env.example` defaults ship demo mode and self-approval on
- **Severity:** P2 (demo/mock configuration reaches a production-shaped path by default; separation-of-duties control never exercised end-to-end)
- **Classification:** VERIFIED_CODE; INFERRED for "the Phase 1 run used self-approval"
- **Evidence:** `platform/apps/cloud/app/api/approvals/[id]/apply/route.ts:22-24` (requester == approver → 403 unless `MARKTING_ALLOW_SELF_APPROVAL === 'true'`); `platform/apps/cloud/lib/cloud/repository.ts:375-382` (`created_by` = the chatting user); `.env.example:47-48` (`MARKTING_DEMO_MODE=true`, `MARKTING_ALLOW_SELF_APPROVAL=true` as the shipped defaults); `infra/seed/seed-demo.mjs:27` creates exactly one user; `platform/apps/cloud/lib/markting/runtime.ts:19-27` (demo mode swaps in `SandboxProvider` behind the same `/dashboard/approvals` and audit log); `docs/PHASE1-REPORT.md:31` ("Apply → row gone").
- **Description:** With one seeded user, "Apply → row gone" is only reachable with `MARKTING_ALLOW_SELF_APPROVAL=true`. The two-person control (the product's main safety story on the Approvals page) therefore has no end-to-end evidence; its only coverage is the route's inline check, which no test imports (command 13). Independently, `.env.example` turns on both the sandbox provider and self-approval, so `make env && make up` produces a stack whose Approvals page mixes synthetic previews with real ones and lets a requester approve their own change. A production operator copying `.env.example` inherits both switches.
- **Impact:** Unsafe-ad-execution guardrail (requester ≠ approver) unverified; demo code path reachable in production configuration.
- **Recommendation:** E2E matrix must run with two users (owner + admin) and `MARKTING_ALLOW_SELF_APPROVAL=false`, asserting the 403 for the requester and success for the second person. Ship `.env.example` with both flags `false` and let `make env --demo` (or the seed script) flip them for the local demo; add a boot-time warning in the cloud app when either is `true` outside `NODE_ENV=development`.

### F3-05 — Engine report runs are not tenant-scoped; any signed-in user of any organization lists and downloads every run
- **Severity:** P3 today (engine is forced to `PAID_MEDIA_DATA_MODE=sample`, so the files are fixture data); P0 if the data-mode assertion is ever relaxed
- **Classification:** VERIFIED_CODE
- **Evidence:** `platform/apps/cloud/app/api/reports/engine/route.ts:18-26` (`await sessionPrincipal(organizationId); return noStoreJson(await engineClient().listReports())`, no org filter); `platform/apps/cloud/lib/markting/engine-client.ts:131` (`listReports()` → `GET /reports`, no parameters); `services/engine-demo/serve_demo.py:289-293` (`reports_list` returns the single global index) and `:236-237` (`requested_by` is the service caller, not the user); `platform/apps/cloud/app/api/reports/engine/[name]/route.ts:16-18` (any session can fetch any `rpt_*`/`art_*` name); `services/engine-demo/serve_demo.py:171-173` (`paid_media_data_mode != "sample"` refuses to start).
- **Description:** The report index is one JSON file per engine workspace. The cloud route only checks that the caller has *a* membership in *an* organization, then proxies the whole index and any file. A two-tenant e2e scenario (org A runs a report, org B sees it) would fail today.
- **Impact:** Cross-tenant metadata (run times, cadence) is visible; content is synthetic by construction, which keeps this at P3. Live-mode (`MARKTING_ENGINE_MODE=live`) does not change the data mode (`serve_demo.py:363-366`), so content stays synthetic unless the assertion is edited.
- **Recommendation:** Scope the engine report surface by caller-supplied `organization_id` (index per org, file names prefixed or indexed by org) and add the two-tenant scenario to the e2e matrix.
