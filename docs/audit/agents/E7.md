## Findings

### E7-01 — No RLS-enforced tenant isolation on the server (`adport_backend`) path
- Severity: P3 (architectural / defense-in-depth)
- Classification: VERIFIED_CODE
- Evidence: every table grants the backend role a blanket policy, e.g. `20260817171039_cloud_initial_schema.sql:319-327` (`*_backend_all ... using (true) with check (true)`), repeated in `20260828120000_cloud_plans_and_account_scope.sql:117-122`, `20261002000000_markting_bridge.sql:83-86`. No `force row level security` anywhere (`rg` exit 1).
- Description: For the `adport_backend` role (which runs every Next.js server query, `db.ts:13`), RLS is an unconditional allow. Cross-tenant safety on the server path depends ENTIRELY on each query carrying `where organization_id = ${principal.organizationId}`. The database provides no backstop: a future query that forgets the org predicate would silently read/write across tenants with no policy to stop it.
- Impact: One missing WHERE clause (or a `*`-select over a non-org-keyed column) becomes an immediate cross-tenant disclosure. The blast radius of a single application bug is unbounded at the DB layer.
- Mitigation currently in place (verified): `auth.ts:13` → `resolveMembership(userId, requestedOrganizationId)` (`repository.ts:30-49`) only returns a principal if the user actually has a membership row for the requested org, and all routes pass `principal.organizationId` downstream (e.g. `app/api/members/route.ts:18-19` passes `principal.organizationId`, not the raw query param, into `listOrganizationMembers`). I found no current query missing its org predicate.
- Recommendation: Consider session-GUC RLS for the backend role (e.g. `set local app.org = ...` + policies `using (organization_id = current_setting('app.org')::uuid)`) so the DB enforces tenant scope, or at minimum add a CI guard that rejects org-keyed queries lacking an `organization_id` predicate. Enable `force row level security` so the posture holds even if the runtime ever connects as the table owner.

### E7-02 — Server-path isolation silently depends on the runtime connecting as a non-owner role
- Severity: P3 (defense-in-depth)
- Classification: INFERRED
- Evidence: `db.ts:8-14` sets `connection: { role: env().ADPORT_DB_ROLE }` (default `adport_backend`, `env.ts:9`). No `force row level security` in any migration. `adport_backend` is `nologin noinherit` and `grant adport_backend to postgres` (`20260817171039_cloud_initial_schema.sql:6-11`).
- Description: RLS (including the `authenticated` member-select and restrictive server-only policies) only binds because `adport_backend` is not a table owner/superuser. If `SUPABASE_DB_URL` logs in as the owner/superuser and the `role` startup GUC is ever dropped or ignored, the session would bypass RLS entirely (owners skip RLS unless `force row level security` is set, which it is not).
- Impact: A deploy/config regression (wrong role GUC, owner login) would silently disable every policy at once, including the browser-facing `authenticated` deny policies, with no test catching it.
- Recommendation: Add a startup assertion / healthcheck that `current_user`/`current_setting('role')` is the non-privileged `adport_backend`, and `select rolbypassrls` is false; enable `force row level security` as belt-and-suspenders. NOT_VERIFIED: the actual login identity of `SUPABASE_DB_URL` at runtime.

### E7-03 — Inconsistent RLS enablement across `private.*` tables
- Severity: P3 (consistency / defense-in-depth)
- Classification: VERIFIED_CODE
- Evidence: `private.provider_credentials`, `private.oauth_transactions`, `private.rate_limit_buckets` (`20260817171039_cloud_initial_schema.sql:73-182`), the `private.mcp_oauth_*` tables (`20260825120000_mcp_oauth.sql`) and `private.billing_events` (`20260828120000...:51-55`) have NO `enable row level security`; whereas `private.provider_account_selections` (`20260831152537...:16`), `private.synthetic_reviewer_workspaces` (`20260906132858...:7`) and `private.cloud_waitlist` (`20260831140245...:11`) do.
- Description: The unprotected `private` tables rely solely on schema/table grants (`revoke all on schema private from public, anon, authenticated` at `:2`; `revoke all on all tables in schema private from public, anon, authenticated` at `:335-336`, plus per-table revokes). This is a real and sufficient control because the `private` schema is not PostgREST-exposed and `authenticated`/`anon` have no usage on it — but the mix is uneven and leans on grants alone for the most sensitive table of all (`private.provider_credentials`, which holds encrypted OAuth secrets).
- Impact: Low today (grants close the door), but the tables holding credentials and OAuth tokens have the weakest layered defense of the set, and the inconsistency invites a future table being added to `private` without either control.
- Recommendation: Enable RLS (default-deny, no permissive policy for non-backend roles) uniformly on every `private` table for symmetry with the grant revocations. NOT_VERIFIED: the deployed PostgREST `db-schemas` list (assumed default `public, graphql_public`; the schema-level revoke makes exposure moot regardless).

### E7-04 — Demo seed script connects as the Postgres superuser (RLS-bypassing) and the service-role key
- Severity: P3 (informational — demo/local tool)
- Classification: VERIFIED_CODE
- Evidence: `infra/seed/seed-demo.mjs:18` defaults `dbUrl` to `postgresql://postgres:postgres@127.0.0.1:55322/postgres`; `:24` builds a Supabase admin client with `SUPABASE_SECRET_KEY`; `:21-22` guard against placeholder creds but read whatever `.env` provides.
- Description: The seed runs as superuser (bypasses all RLS) and the service-role key (bypasses RLS via PostgREST). It is explicitly a local demo tool (header comment, `host.docker.internal`→`127.0.0.1` rewrite). All its SQL is parameterized tagged templates (`:31,:40,:44,:45-49,:57-61`), so it carries no injection risk itself.
- Impact: Not reachable from the application. Risk is only operational: if an operator points `SUPABASE_DB_URL`/`SUPABASE_SECRET_KEY` at a production project and runs it, it would write seed rows with full privilege. No automatic path to production exists.
- Recommendation: Keep it out of any deploy workflow; optionally assert the target host is loopback before executing. This is a GAP/operational note, not a code defect.

### E7-05 — SECURITY DEFINER functions are correctly hardened (positive control, recorded)
- Severity: GAP (no defect; documented as verified-safe)
- Classification: VERIFIED_CODE
- Evidence: `private.handle_new_user` (`:220-243`), `private.find_auth_user_id` (`:343-351`), `private.organization_member_directory` (`:353-366`), `private.apply_data_retention` (`:375-408`, redefined `20260828120000...:131-163`), `private.create_default_organization_subscription`/`_onboarding` all declare `set search_path = ''` and fully schema-qualify their objects. `find_auth_user_id`/`organization_member_directory` read `auth.users` but `execute` is revoked from `public, anon, authenticated` and granted only to `adport_backend` (`:368-371`). `set_updated_at` and `purge_expired_mcp_oauth_records` are `security invoker`.
- Description: No `search_path` hijack surface; the two definer functions that can read `auth.users` emails are not callable by browser roles, and the one caller (`tenant-admin.ts:20-24 listOrganizationMembers`) passes the membership-verified `principal.organizationId`.
- Recommendation: None. Noted so the audit records that this class of risk was checked and is clean.

## What a world-class system would need (gaps, concrete)
- DB-enforced tenant scope for the server role: per-request `set_config('app.current_org', ...)` inside each `db().begin` plus `organization_id = current_setting(...)::uuid` policies, so a dropped WHERE cannot leak across tenants.
- `alter table ... force row level security` on all tenant tables, so the posture survives an accidental owner/superuser connection.
- A static/CI lint that fails any query touching an org-keyed table without an `organization_id` predicate (closes the E7-01 residual risk mechanically).
- Uniform default-deny RLS on every `private` table (not grants alone), especially `provider_credentials` and the OAuth token tables.
- A runtime healthcheck asserting the DB session is the non-privileged `adport_backend` role with `rolbypassrls = false`.

## Disagreements / claims in docs that the code contradicts
- `20260817171039_cloud_initial_schema.sql:298-299` comment: "These tables are intentionally server-only. Explicit deny policies ... keep PostgREST closed even if a grant is added accidentally." VERIFIED accurate for `authenticated` (restrictive `using(false)`), but the comment should not be read as implying tenant isolation for the server path — the backend role still has `using(true)` and no org scoping (E7-01).
- `20261002000000_markting_bridge.sql:3-7` header claims the bridge tables "never hold a write path of their own" and isolation "is enforced here, keyed by organization and user." VERIFIED at the application layer (`claimThread`/`listThreads` scope by org+user, `markting/repository.ts:17-36`), but NOT enforced by RLS — the `markting_*` tables also use `backend_all using(true)` (`:83-86`), so the isolation claim is application-level only, consistent with E7-01.
- No doc claims the DB itself isolates tenants, so there is no outright contradiction — but READMEs that cite "RLS" as the isolation mechanism would overstate the server path, which is app-enforced.
