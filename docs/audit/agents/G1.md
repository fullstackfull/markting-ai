## Findings

### G1-01 — The Assistant and the "AI analysis reports" never read the tenant's connected accounts (engine is pinned to fixture data in every mode)
- Severity: **P1** (the product's headline promise is not deliverable; the UI claims it is)
- Classification: VERIFIED_CODE
- Evidence:
  - `services/engine-demo/serve_demo.py:489-494` — `build_app_async` forces `paid_media_data_mode: "sample"` for **both** `demo` and `live` modes, then `assert_fail_closed` (`serve_demo.py:160-163`) refuses to boot if the mode is anything but `sample`.
  - `serve_demo.py:265-275` — `run_report` runs `run_cadence_report(accounts=runtime.profile.accounts, ...)`; the account registry is the engine's global TOML (`engine/config/accounts.example.toml:5-19`: `demo-google`, `demo-meta`, `demo-reddit` with fixture ids). Nothing passes the organization's `organization_ad_accounts` or credentials to the engine.
  - `platform/apps/cloud/lib/markting/assistant.ts:40-47` — the only per-request inputs to the engine are the thread id and the user's text; `lib/markting/engine-client.ts:114-116` (`POST /threads/{id}/messages {text}`).
  - UI/README claims: `lib/i18n/messages/assistant.ts:5` ("Ask about performance across your connected accounts"), `assistant.ts:16` placeholder "Ask about your campaigns…" in live mode, `README.md` "Analyses connected accounts (spend, conversions, CPA, ROAS)".
- Description: In live mode (`MARKTING_ENGINE_MODE=live`, `MARKTING_DEMO_MODE=false`) the model analyses the bundled fixture campaigns, not the tenant's Google/Meta/TikTok data, and its proposals are then translated onto real accounts only if an alias row exists (see G1-02). The adport side (Overview, Reports campaign table, Approvals, Policies) is real; the AI side is a fixture replay. Every persona's primary value proposition ("the AI media buyer looks at my accounts") is therefore not available today.
- Impact: Small advertiser, agency, enterprise, e-commerce and multi-account buyer all get a demo, not an analysis. A proposal produced from fixture data could, with an alias row, be previewed against a real account whose actual state the model has never seen.
- Recommendation: Either (a) make the engine read through adport's `report`/`accounts_list` tools for the principal's organization (an MCP/REST adapter per tenant with the tenant's enabled-account scope), or (b) relabel the Assistant and AI-reports as "demo" in the UI and README until (a) exists. Do not let live-mode proposals reach a real account until the model's inputs are the tenant's data.

### G1-02 — Live-mode proposal flow is unusable without hand-written SQL: no alias management surface
- Severity: **P1** (production blocker for the only AI→write path)
- Classification: VERIFIED_CODE
- Evidence: `lib/markting/translate.ts:133-134` returns `unsupported: no adport account is mapped to engine alias` unless `markting_account_aliases` has a row; `lib/markting/repository.ts:40-50` loads rows only (plus sandbox aliases in demo mode); `upsertAlias` (`repository.ts:52`) has no caller outside `test/markting-repository.database.test.ts:47` (command #3); the demo seed inserts aliases with raw SQL (`infra/seed/seed-demo.mjs:50-62`). No dashboard page, API route or onboarding step creates or shows aliases.
- Description: An operator who flips `MARKTING_DEMO_MODE=false` gets an Assistant that answers from fixtures and refuses every proposal with "Proposal could not be mapped to an account" (`assistant-chat.tsx:125-130`).
- Impact: All personas in production. Combined with G1-01 the proposal→approval pipeline is demo-only.
- Recommendation: Add an admin UI (Accounts page) that binds an enabled `organization_ad_accounts` row to an engine alias with validation against the connected provider, and have the engine's account registry be derived per organization rather than from a global TOML.

### G1-03 — Engine report list and files are global across tenants
- Severity: **P1** (cross-tenant isolation defect; content is fixture-only today, otherwise P0)
- Classification: VERIFIED_CODE
- Evidence: `app/api/reports/engine/route.ts:16-24` — `GET` authenticates the session, then returns `engineClient().listReports()` with no organization filter; `serve_demo.py:243-256` — one index file `out/markting-reports.json` for the whole engine; `serve_demo.py:348-351` — `GET /reports` returns the entire index; `serve_demo.py:353-369` and `app/api/reports/engine/[name]/route.ts:10-15` — any signed-in user of any organization can download any `rpt_*/art_*` file by name. `requested_by` is the token's caller name, and the deployment uses one token for all tenants (`README.md`, "The engine runs with one service token").
- Description: The Reports page of organization A lists and lets its members download the report runs triggered by organization B. Today the report content is the same fixture data for everyone (G1-01), so no real spend data leaks, but the run history (timestamps, cadence) does, and the moment reports include tenant data this becomes a P0 leak.
- Impact: Agency and enterprise personas (confidentiality between clients) cannot be served by the Reports page as built.
- Recommendation: Key the index and the file store by organization (or carry `organization_id` in the request and filter server-side), and refuse file downloads whose run does not belong to the caller's organization.

### G1-04 — The Agency plan sells "Separate client workspaces" that do not exist
- Severity: **P2** (paid feature advertised in-product with no implementation; billing/consumer-trust risk)
- Classification: VERIFIED_CODE (DOCUMENTED_NOT_IMPLEMENTED capability)
- Evidence: `lib/cloud/plans.ts:36-42` (`clientWorkspaces: true` on `agency` and `enterprise`); `app/dashboard/billing/page.tsx:95` renders `billing.featureClientWorkspaces` ("Separate client workspaces", `lib/i18n/messages/billing.ts:55`; Arabic `billing.ts:92` "مساحات عمل للعملاء"); command #2 shows no other reader of the flag; no table, route or page implements client/sub-workspaces (`find platform/apps/cloud/app -maxdepth 2 -type d`, command #1).
- Description: An organization is a flat container: one `organizations` row created per sign-up by the `handle_new_user` trigger (`20260817171039_cloud_initial_schema.sql:225-240`), with members, connections, accounts, policy and audit all at that single level. There is no parent/child, no per-client policy, no per-client member scoping, no per-client report.
- Impact: The agency persona pays €149/month for a bullet that does nothing; Stripe checkout for the Agency plan is live (`app/dashboard/billing/actions.ts:13-38`).
- Recommendation: Remove the bullet until a client-workspace model exists, or implement it (see "What a world-class system would need").

### G1-05 — No organization switcher: a user with several memberships can only ever see the oldest one
- Severity: **P2**
- Classification: VERIFIED_CODE
- Evidence: `lib/cloud/dashboard.ts:27-42` — `requireDashboardTenant` selects memberships `order by created_at asc limit 1`; `components/shell.tsx:26-28` renders the organization name as static text; every dashboard page passes `tenant.organizationId` from that single resolution (e.g. `app/dashboard/page.tsx:13`, `live-data.tsx:24`). The API layer does accept an explicit `organization_id` (`lib/cloud/repository.ts:30-48`), so the server supports multi-membership but the UI never exposes it. No route creates a second organization (command #4).
- Description: The only workaround for "one workspace per client" (separate sign-ups per client) forces a media buyer invited into N client organizations to use N browser profiles; the dashboard will always show the first org they joined.
- Impact: Blocks the agency and the 50-account media buyer personas; also affects a freelancer invited by two advertisers.
- Recommendation: Add an organization switcher (cookie or path segment), an "Create organization" action, and make `requireDashboardTenant` honour the selection.

### G1-06 — One OAuth grant per provider per organization
- Severity: **P2** (structural limitation for multi-client operation; not a defect in the single-advertiser case)
- Classification: VERIFIED_CODE
- Evidence: `supabase/migrations/20260817171039_cloud_initial_schema.sql:66` — `connections` has `unique (organization_id, provider)`; `app/dashboard/connections/provider-connections.tsx:39-41,68-69` renders exactly one row per provider and finds the connection by provider id; `lib/cloud/repository.ts:618-628` loads enabled accounts by joining that single connection.
- Description: All Meta ad accounts an organization wants must be reachable from one Meta user token; all Google customers from one Google login (manager mapping exists: `lib/cloud/types.ts:29-30`). Client accounts living in separate Business Managers with separate logins cannot be connected side by side.
- Impact: Agency / 50-account buyer must first consolidate partner access on the platform side; otherwise they cannot onboard.
- Recommendation: Allow N connections per provider (keyed by external grant id), or implement client workspaces each with its own connection set.

### G1-07 — Approvals need a second human per organization; the only bypass is a deployment-wide environment flag that the shipped example turns on
- Severity: **P2**
- Classification: VERIFIED_CODE
- Evidence: `app/api/approvals/[id]/apply/route.ts:19` (only owner/admin may apply) and `:22-24` (requester cannot apply unless `MARKTING_ALLOW_SELF_APPROVAL=true`); `lib/markting/env.ts:16` default `false`; root `.env.example:49` sets `MARKTING_ALLOW_SELF_APPROVAL=true` (and `.env.example:47` `MARKTING_DEMO_MODE=true`); plan caps `lib/cloud/plans.ts:24-31` (Free: 1 member, no write; Operator: 2 members).
- Description: A solo advertiser on the Operator plan can ask for a change but can never apply it unless they invite a second admin or the operator sets a flag that disables four-eyes for every tenant at once. Conversely, a deployment that copies `.env.example` ships with self-approval and sandbox mode on for all tenants.
- Impact: Small advertiser persona is blocked from the end-to-end loop on the plan sold to them; operators face an all-or-nothing safety switch.
- Recommendation: Make self-approval a per-organization policy setting (owner-controlled, audited) with a default that fits plan size; ship `.env.example` fail-closed.

### G1-08 — Overview KPIs sum spend and conversion value across currencies and compute ROAS on the mixed total
- Severity: **P2**
- Classification: VERIFIED_CODE
- Evidence: `app/dashboard/live-data.tsx:34-41` — `totals` reduces `row.metrics.spend` and `conversion_value` over all rows with no currency grouping, `roas = totals.value / totals.spend`; `platform/packages/core/src/model.ts` (`ReportRow.currency`, comment "Never infer FX") shows the currency is available on each row and ignored; the footnote only says "account currencies" (`lib/i18n/messages/overview.ts:20,57`). The Reports page table shows raw spend with no currency column (`app/dashboard/reports/page.tsx:33-45`).
- Description: A Gulf agency with SAR, AED and USD accounts sees a meaningless headline Spend and ROAS.
- Impact: Agency, enterprise and multi-account buyer personas cannot trust the first screen.
- Recommendation: Group KPI tiles by currency (or require a reporting currency with explicit FX source), and add a currency column to the campaign tables.

## What a world-class system would need (concrete gaps)

1. **Tenant-scoped AI inputs.** The engine must analyse the organization's enabled accounts through adport's scoped `report`/`accounts_list` tools (per-tenant MCP/REST credentials), with the organization's currency, goals and protected accounts in context. Today: fixtures only (G1-01).
2. **Alias/account binding UI** on the Accounts page, validated against `organization_ad_accounts` (G1-02).
3. **Agency model.** Parent organization → client workspaces, each with its own connections, policy, members (scoped roles: client admin, client approver, client viewer), reports and audit; an organization switcher; cross-client roll-up dashboard with per-client drill-down (G1-04, G1-05, G1-06, G1-11).
4. **Tenant-scoped engine artefacts** (reports indexed by organization, downloads authorised per organization) (G1-03).
5. **Approval UX.** Inline full preview, approve/reject with reason, bulk approve, per-org self-approval policy, notifications (email now, WhatsApp later), TTL that fits human approval latency, "re-validate" button (G1-07, G1-13).
6. **Alerting.** Daily pacing vs budget, spend spikes/drops, CPA/ROAS drift vs targets, disapproved ads, token expiry/connection errors, pending-approval reminders; delivery by email/WhatsApp/Slack; per-account thresholds (G1-14).
7. **Analytics surface.** Date-range picker with comparison, breakdowns by provider/account/campaign type, currency grouping or reporting currency with declared FX, saved views, CSV/Sheets export, scheduled report delivery in Arabic (G1-08, G1-15).
8. **Scale operations.** Multi-select enable/disable with one request, search and pagination on accounts, approvals, findings and audit; 50+ accounts without a full page refresh per toggle (G1-15).
9. **Commercial fit for the market.** SAR pricing and VAT, Arabic invoices, in-product enterprise request, rebranding away from Adport, onboarding that introduces the Assistant and captures business goals (G1-09, G1-10).
10. **Broader proposal catalogue** with the same guardrails: bids, ad-set status, creative pausing, keyword negatives, audience exclusions; e-commerce revenue connectors so ROAS uses store revenue (G1-16).
