## Findings

### J5-01 — The engine can never analyse a paying customer's real ad accounts
- Severity: **P1** (production blocker; the headline capability is demo-only)
- Classification: VERIFIED_CODE, VERIFIED_TEST
- Evidence:
  - `services/engine-demo/serve_demo.py:163-166` — `assert_fail_closed` refuses to start unless `paid_media_data_mode == "sample"`.
  - `services/engine-demo/serve_demo.py:383-387` — in `live` mode the settings are still overridden with `paid_media_data_mode: "sample"`; `demo` mode does the same via `demo_settings` (`:183-191`).
  - `services/engine-demo/serve_demo.py:142-143` — a configured `PIPEBOARD_API_TOKEN` (the engine's only multi-platform live read adapter) is a boot failure.
  - `engine/src/paid_media_agent/runtime/catalog.py:51-58` — `sample` returns `build_fixture_catalog()` with `read_provider=None`; `engine/src/paid_media_agent/runtime/profiles.py:72-76` — `sample` forces the alias registry to `config/accounts.example.toml` (fixture accounts `demo-google/meta/reddit`, `engine/config/accounts.example.toml:5-21`).
  - `services/engine-demo/tests/test_demo_api.py:71` asserts `health["catalog_source"] == "fixture"`; `:81-91` asserts boot fails with a Pipeboard token.
- Description: "live" engine mode only swaps the scripted model for a real LLM; the data the model reasons over remains the synthetic fixtures. The Assistant and the Reports card therefore describe fixture accounts no matter which Google/Meta/Snapchat accounts the customer connected through adport's OAuth. adport's own read path (`/api/v1`, dashboard reports) does read real accounts, but the AI layer never sees them.
- Impact: the first paying customer receives AI analysis and proposals about accounts that are not theirs. This is the single largest gap between what README.md sells ("Analyses connected accounts (spend, conversions, CPA, ROAS)", `README.md:83`, Arabic `:14`) and what the code does. It is not in the README "Not production-ready yet" list and not in `docs/TODO.md`.
- Recommendation: either (a) build an adport→engine read bridge (engine `CompositeReadProvider` fed by adport's normalized reports, keyed per organization), or (b) rewrite the README/marketing to say the AI layer is a demo over synthetic data until that exists. Do not ship (a) without per-organization data partitioning in the engine (see J5-03).

### J5-02 — No way to bind engine aliases to a real account; in live mode every proposal is "unsupported"
- Severity: **P1** (functional blocker for the core loop), with an UNSAFE_TO_AUTOMATE design note
- Classification: VERIFIED_CODE
- Evidence:
  - `platform/apps/cloud/lib/markting/repository.ts:40-50` — `loadAliasMap` starts from `{}` when `demoMode` is false and only adds rows from `markting_account_aliases`.
  - `platform/apps/cloud/lib/markting/repository.ts:52-58` — `upsertAlias` exists, but `rg upsertAlias platform/apps/cloud` finds callers only in `test/markting-repository.database.test.ts:47`. No route, page or script writes aliases except the demo seed (`infra/seed/seed-demo.mjs:50-62`, which writes `sandbox` provider rows).
  - `platform/apps/cloud/lib/markting/bridge.ts:135-141` — an unmapped alias yields `outcome: 'unsupported'`.
- Description: with `MARKTING_DEMO_MODE=false` the alias map is empty, so every engine proposal is recorded as unsupported and no preview is created. Conversely, if an operator hand-inserts a row mapping `demo-google` to a real Google account, a budget proposal computed from **synthetic** data (J5-01) is previewed against a **real** campaign. The policy gate and human approval still stand (`bridge.ts:143-151`, `app/api/approvals/[id]/apply/route.ts:18-24`), so this is not P0, but the pairing is unsafe to automate and nothing in the UI tells the approver the analysis came from fixture data.
- Recommendation: block live-mode alias rows whose engine `account_ref` is a fixture alias until J5-01 is solved; add an owner-only alias management surface with audit; show provenance ("analysis data source: synthetic") on Approvals.

### J5-03 — Engine reports are a single tenant-global index; any signed-in user of any organization can list and download every report
- Severity: **P1** (cross-tenant by design; today limited to synthetic data because of J5-01, so not yet P0 — it becomes P0 the day real data enters the engine)
- Classification: VERIFIED_CODE
- Evidence:
  - `services/engine-demo/serve_demo.py:62` (`REPORT_INDEX = "markting-reports.json"`), `:246-264` one file under `workspace/out`, `:304-306` global list capped at 50, `:355-358` `GET /reports` returns the whole index, `:360-374` any file name matching the regex is served; `requested_by` is the token caller name (`:343`, always `adport-bridge`, `docker-compose.yml:49`).
  - `platform/apps/cloud/app/api/reports/engine/route.ts:16-24` — `GET` only calls `sessionPrincipal(organizationId)` then returns `engineClient().listReports()` with no organization filter; `:27-36` `POST` runs a report with no organization context; `app/api/reports/engine/[name]/route.ts:10-26` streams any file after a session check only.
- Impact: tenant isolation of Assistant threads is enforced (`markting_threads`, `lib/markting/assistant.ts:34-38`), but reports are not. README (`:86`) claims the engine "runs with one service token; tenant isolation of conversations lives in adport's `markting_threads` table" — true for threads, silent about reports.
- Recommendation: key the index and files by organization (pass an org id to `/reports/run`, store per-org index, authorize `/reports/files/{name}` against it) before any real data reaches the engine. Add a test that a second principal cannot list the first's run.

### J5-04 — There is no production deployment artefact; the only stack is a destructive local dev stack
- Severity: **P1**
- Classification: VERIFIED_CODE; image build NOT_VERIFIED
- Evidence:
  - `Makefile:26-28` — `supabase-start` runs `supabase db reset --local --yes` **every time**; `Makefile:33` — `up: supabase-start`. Every `make up` wipes the adport database (users, connections, encrypted credentials, approvals).
  - `docker-compose.yml:24-27` — Supabase reached via `host.docker.internal`, Postgres as `postgres:postgres`; `engine-db` credentials `paid_media:paid_media` hardcoded (`:43,70-72`); `cloud` has no healthcheck; nothing terminates TLS; `.env` is mounted wholesale into both containers (`env_file: .env`, `:17,40`), so the cloud container receives engine-only values and vice versa.
  - `infra/cloud.Dockerfile:9` — `COPY . .` with no `.dockerignore` (verified absent) copies host `node_modules/`, `.turbo/`, `.next/` into the build context.
  - `docs/PHASE1-REPORT.md:36` and `docs/PHASE0-REPORT.md:59-60,70` — neither image has ever been built ("validated statically"); the browser flow was verified from source, not from the compose image.
  - Hosted Supabase: `rg "db push|supabase link"` finds only the generic comment in `platform/supabase/config.toml:60`; there is no project link, migration-push or seed procedure for a hosted project. `platform/apps/cloud/vercel.json` is upstream's (region `fra1`, adport build command).
  - `platform/docs/deployment-model.md:47-58` lists the production gates (hosted project, KMS, backups, monitoring, domains, OAuth review, legal, runbooks); none has a counterpart in this repo.
- Impact: nothing in the repository can be pointed at a customer. The one documented start command is data-destructive, which also matters for a long-running demo.
- Recommendation: split `make up` (start) from `make reset` (reset); add a `.dockerignore`; build both images in CI; write a hosted-Supabase runbook (`supabase link`, `db push`, role password for `adport_backend`, auth settings); add a reverse proxy/TLS and health endpoints; parameterize `engine-db` credentials.

### J5-09 — Secrets: env-file delivery, fixed key version, demo-oriented defaults in the only template
- Severity: **P2**
- Classification: VERIFIED_CODE
- Evidence:

- Recommendation: KMS/secret-manager delivery with `key_version` actually used; separate per-service env files; flip the root template defaults to `false` with a comment; set a stable engine signing key anyway.
