# A6 — Pinterest Ads expert

Audit question: can MARKTING-AI understand and manage Pinterest Ads like a senior media buyer, or does it merely have a connector? Everything below is derived from the code in this repository at the audited commit, from the official Pinterest OpenAPI 5.28.0 document (downloaded during the audit, see Commands), and from tests I ran. Documents (README, platform/docs/providers/pinterest.md, docs/ARCHITECTURE.md, engine/README.md) were treated as claims to disprove.

Short answer: the platform side ships a small, carefully guarded Pinterest **campaign-shell** adapter (3 writes, 1 read tool, 5 metrics) that has never been exercised against a live account; the AI engine side has **no** Pinterest normalization, fixtures, write policy or bridge mapping, so the "AI media buyer" cannot analyse or act on Pinterest at all today. Classification overall: platform adapter = EXISTS_BUT_LIMITED; engine/AI Pinterest capability = DOCUMENTED_NOT_IMPLEMENTED.

## Findings

### A6-01 — The AI engine cannot normalize, fixture-test or act on Pinterest data
- Severity: **P2** (substantial functional deficiency for the product's core promise)
- Classification: VERIFIED_CODE
- Evidence:
  - `engine/src/paid_media_agent/domain/common.py:17,30` — `Platform.PINTEREST_ADS` exists and is listed in `PIPEBOARD_PLATFORMS`.
  - `engine/src/paid_media_agent/tools/normalize.py:14-26` — `_SPEND_KEYS` / `PERFORMANCE_PLATFORMS` contain google, meta, reddit, linkedin, x, openai; no Pinterest. `normalize.py:95-97` raises `NormalizationError("platform metrics have no verified spend-unit mapping")` for anything else.
  - `engine/src/paid_media_agent/tools/reads.py:241` — normalization runs only when `entry.platform in PERFORMANCE_PLATFORMS`; otherwise `reads.py:303-330` stores a raw `provider_result` artifact.
  - `engine/src/paid_media_agent/reports/cadence.py:112-114` — a read whose `artifact_kind != "performance_rows"` is reported as "read returned no performance rows" and skipped.
  - `engine/src/paid_media_agent/domain/common.py:37-41` — `FIXTURE_PLATFORMS` = google, meta, reddit; `find engine/src -path "*fixture*"` shows no `pinterest_ads.json`.
  - `engine/src/paid_media_agent/tools/fixtures.py:26-33` — `FIXTURE_ADMITTED_MUTATIONS` has no Pinterest rows; `engine/config/write-policy.example.toml` has none; `engine/config/accounts.example.toml` has no Pinterest alias.
  - `engine/workspace/skills/paid-media-wiki/platform-differences.md:14` is the only skill mention: a platform list, no Pinterest operating knowledge (objectives, billable events, Pin/Idea/Collection formats, CBO vs ad-group budgets, 30/30/1 attribution, etc.).
- Description: the engine's only Pinterest-aware code is a Pipeboard endpoint URL (`config.py:144`), an `ad_account_id` scoping rule (`catalog.py:108`) and an account-list regex in the admin console (`admin/actions.py:457`). A Pipeboard Pinterest read, if it ever happens, lands as an opaque JSON blob; the comparison/anomaly/cadence reports cannot consume it; no write is admitted; there is no offline fixture so none of this is testable without a paid Pipeboard token.
- Impact: the "AI media buyer" has no Pinterest analysis path. The channel is UI-listed (`platform/apps/cloud/lib/markting/translate.ts:13`) and marketed (`engine/README.md:101`, `engine/OPERATIONS.md:150`, `engine/src/paid_media_agent/admin/routes.py:164`) as connectable, which is true only at the catalog-loading level.
- Recommendation: add a `Platform.PINTEREST_ADS` spend mapping (`SPEND_IN_MICRO_DOLLAR` ÷ 1e6, or Pipeboard's own field name once read from the live schema), a synthetic `pinterest_ads.json` fixture, a `demo-pinterest` alias, admitted `update_campaign_budget/status` rows with readback, and a Pinterest skill page.

### A6-02 — Markting bridge cannot route any Pinterest proposal to the adport Pinterest tools
- Severity: **GAP** (feature absent; the code does not claim to provide it — `BridgeProvider` is explicit)
- Classification: VERIFIED_CODE
- Evidence: `platform/apps/cloud/lib/markting/translate.ts:19` — `BridgeProvider = 'sandbox' | 'google' | 'meta' | 'reddit' | 'tiktok' | 'snapchat'`; `translate.ts:72-74` — `PLATFORM_TO_PROVIDER` has no `pinterest_ads`; `budgetInput`/`statusInput` (`translate.ts:103-123`) have no Pinterest case; `translateProposal` (`translate.ts:138-141`) returns `unsupported` for an unmapped platform.
- Description: even if A6-01 were fixed, an engine proposal for `pinterest_ads__update_campaign_budget` would be refused at the bridge. The adport tools `pinterest_set_budget` (`budget_micros`, preserves daily/lifetime) and `pinterest_set_campaign_status` exist and would be a direct mapping.
- Recommendation: add `pinterest_ads: 'pinterest'` to `PLATFORM_TO_PROVIDER`, a `pinterest` case in both switch statements (`budget_micros`, `status`), and extend `BridgeProvider` plus the alias store validation.

### A6-03 — Derived ratios return 0 (not null) when the denominator is 0, misreporting CPA/CPC/CPM as free
- Severity: **P2** (a media buyer or the model will read "CPA = 0" with spend > 0 as a success signal)
- Classification: VERIFIED_CODE
- Evidence: `platform/packages/pinterest/src/provider.ts:178-180` — `mapped[metric] = mapped[denominator] ? mapped[numerator]! / mapped[denominator]! * factor : 0`. `test/pinterest.test.ts:127` only covers non-zero denominators; no test covers `TOTAL_CHECKOUT = 0` or `OUTBOUND_CLICK_1 = 0`.
- Description: for any AWARENESS, CONSIDERATION, VIDEO_COMPLETION or LEADS campaign (Pinterest's own `CampaignObjectiveType`, OpenAPI), `TOTAL_CHECKOUT` is legitimately 0, so every such row reports `cpa: 0`. A campaign with spend and zero outbound clicks reports `cpc: 0`. The core model documents "Null metrics are unavailable" (`core/src/tools/builtin.ts:57`), so `0` here is semantically wrong. `summarizeReport` (`core/src/report-summary.ts`) recomputes ROAS from additive metrics and is not affected, but row-level values go to the model and UI unchanged.
- Recommendation: leave the metric absent (or null) when the denominator is 0, and add tests for zero-denominator rows.

### A6-04 — Only 5 of 185 synchronous columns are read; "conversions" means checkouts only and "clicks" means outbound clicks only
- Severity: **P2** for expert use (the metric set cannot support Pinterest objectives other than SALES/WEB_CONVERSION); the mapping itself is documented honestly
- Classification: VERIFIED_CODE + verified against OpenAPI 5.28.0
- Evidence: `provider.ts:17` — `FIELDS = { spend: SPEND_IN_MICRO_DOLLAR, impressions: PAID_IMPRESSION, clicks: OUTBOUND_CLICK_1, conversions: TOTAL_CHECKOUT, conversion_value: TOTAL_CHECKOUT_VALUE_IN_MICRO_DOLLAR }`. OpenAPI `ReportingColumnSync` has 185 values including `TOTAL_CLICKTHROUGH`, `CLICKTHROUGH_1`, `TOTAL_IMPRESSION`, `TOTAL_IMPRESSION_USER`, `TOTAL_IMPRESSION_FREQUENCY`, `TOTAL_CONVERSIONS`, `TOTAL_LEAD`, `TOTAL_SIGNUP`, `TOTAL_PAGE_VISIT`, `TOTAL_CLICK_ADD_TO_CART`, `TOTAL_ENGAGEMENT`, `REPIN_1`, `VIDEO_P100_COMPLETE_2`, `TOTAL_VIDEO_MRC_VIEWS`, `CHECKOUT_ROAS`, `PAGE_VISIT_ROAS`, `COST_PER_LEAD`, `ECPM_IN_MICRO_DOLLAR` (all confirmed present). The async `ReportingColumnAsync` enum has 626 values; `/ad_accounts/{id}/reports` is not used.
- Description: Pinterest Ads Manager's headline "Clicks"/"CTR" are pin clicks (`TOTAL_CLICKTHROUGH`/`CTR`), not outbound clicks, so the normalized `ctr` will be systematically lower than what the advertiser sees. Leads, sign-ups, add-to-cart, page visits, saves, video views, reach and frequency are invisible. `platform/docs/providers/pinterest.md:31` states "Conversion semantics are checkouts, not every conversion event" — the choice is disclosed, but nothing in the AI layer knows it.
- Recommendation: expose a Pinterest-native metrics read (a column allowlist, `granularity` parameter, `TOTAL_CONVERSIONS` with per-event breakdown) and record the semantic note on every row (e.g. `metric_semantics: { clicks: 'OUTBOUND_CLICK_1' }`).

### A6-05 — Attribution is only partly explicit: the engagement window is left at Pinterest's default
- Severity: **P3**
- Classification: VERIFIED_CODE + OpenAPI; contradicts a doc claim
- Evidence: `provider.ts:92` sends `click_window_days=30`, `view_window_days=1`, `conversion_report_time=TIME_OF_AD_ACTION` and omits `engagement_window_days`. OpenAPI `query_conversion_attribution_engagement_window_days`: "If not specified, defaults to `30` days" (engagement = saves, closeups, link clicks, carousel swipes). `platform/docs/providers/pinterest.md:33` claims "Attribution is explicit: 30-day click, 1-day view".
- Description: `TOTAL_CHECKOUT` therefore includes 30-day engagement-attributed checkouts that the documentation does not mention; the window is not configurable per query, so the model cannot compare Pinterest's 30/30/1 with Meta's 7/1 on equal terms. The parameter is also deprecated by Pinterest ("no longer returns new data … historic data through Sept 30, 2027"), which should be recorded as a known semantic drift.
- Recommendation: send `engagement_window_days` explicitly, surface all three windows in row metadata, and correct the doc.

### A6-06 — No time, placement, demographic, geo or device breakdowns; `granularity=TOTAL` only
- Severity: **GAP** (not claimed)
- Classification: VERIFIED_CODE + OpenAPI
- Evidence: `provider.ts:91` hard-codes `granularity: 'TOTAL'`. OpenAPI offers `DAY|HOUR|WEEK|MONTH`, `/ad_accounts/{id}/campaigns/targeting_analytics`, `/ad_groups/targeting_analytics`, `/ads/targeting_analytics`, `/targeting_analytics`, `/audience_insights`, `/insights/audiences`, `/keywords/metrics`, `/product_groups/analytics`, `/pins/analytics`, async `/reports` with `*_TARGETING` levels. None is referenced anywhere in the repository (`grep -rn targeting_analytics platform/` → no hits).
- Impact: no day-over-day trend, no hour-of-day, no placement (Search vs Browse), no age/gender/geo/device/interest/keyword diagnosis — i.e. none of the inputs a Pinterest buyer uses to optimize.

### A6-07 — Ad-group and ad entities are reachable for reporting only; bids, budgets, pacing, learning state and creative status are never read
- Severity: **GAP** (docs say so: `pinterest.md:21`)
- Classification: VERIFIED_CODE + OpenAPI
- Evidence: `tools.ts:8` exposes a single read tool `pinterest_list_campaigns`. `provider.ts:84` lists ad groups/ads internally with `entitySchema` (id, ad_account_id, name, status) for `report()` only. OpenAPI `AdGroup` carries `bid_in_micro_currency`, `bid_strategy_type` (AUTOMATIC_BID|MAX_BID|TARGET_AVG), `budget_in_micro_currency`, `budget_type` (DAILY|LIFETIME|CBO_ADGROUP), `pacing_delivery_type` (STANDARD|ACCELERATED), `optimization_goal_metadata`, `billable_event` (CLICKTHROUGH|IMPRESSION|VIDEO_V_50_MRC), `conversion_learning_mode_type` (learning phase), `lifetime_frequency_cap`, `targeting_spec`, `placement_group`, `summary_status`; `Ad` carries `creative_type`, `pin_id`, `review_status`, `rejected_reasons`, `rejection_labels`, `summary_status`. `Campaign.summary_status` (RUNNING|PAUSED|NOT_STARTED|COMPLETED|ADVERTISER_DISABLED|ARCHIVED|DRAFT|DELETED_DRAFT) is in the response but not in `campaignSchema` (`schemas.ts:9-13`) and not surfaced (the `looseObject` passes it through the list tool raw, with no semantics).
- Impact: no bidding controls, no learning-phase awareness, no pacing, no creative/approval health, no frequency cap visibility.

### A6-08 — Budget previews and report rows carry no currency; budgets are shown as bare micros
- Severity: **P3**
- Classification: VERIFIED_CODE
- Evidence: `provider.ts:101` builds `ReportRow` without `currency` although `listAccounts()` (`provider.ts:47`) has it; `provider.ts:140,154` build `BudgetDelta` without `currency` although `core/src/provider.ts:27` provides the field; preview strings read `"… 100000000 → 110000000 micros"` (`provider.ts:153`). Mitigation: the core `report` tool back-fills row currency from `listAccounts()` (`core/src/tools/builtin.ts:118-130`), and in the cloud that comes from the stored inventory (`runtime.ts:58-61`).
- Impact: approvers of a Pinterest write in an Arabic-first UI with SAR/AED/EGP accounts see unit-less micros; `summarizeReport` groups rows per account instead of per currency when the back-fill fails (`builtin.ts:123` warning path).
- Recommendation: fetch `/ad_accounts/{id}` (already done for account-level reports) and stamp `currency` on rows and deltas; render human amounts in previews.

### A6-09 — Successful writes can be reported as failures if Pinterest's batch echo omits or normalizes a field
- Severity: **P3** (message tells the operator to inspect before retrying, which contains the duplicate-create risk)
- Classification: INFERRED (schema-level reasoning; no live evidence)
- Evidence: `provider.ts:122-125` throws `campaign write response mismatch` unless `data.ad_account_id === accountId`, `data.id === body.id` and every `status|daily_spend_cap|lifetime_spend_cap` in the request is echoed with strict equality. OpenAPI `CampaignBatchResponseData` has **no required properties**. `pinterest.md:36` and `platform/README.md:122` confirm no live mutation has ever been observed.
- Impact: if the live echo omits `ad_account_id` or returns `lifetime_spend_cap: 0` for a `null` request, every create/update will "fail" after having succeeded. A retry would create a duplicate campaign (writes are not idempotent and `apply` has no idempotency key).
- Recommendation: treat the echo as advisory, and prove state through a follow-up `getCampaign` read-back (the engine's own doctrine, `engine/src/paid_media_agent/tools/providers.py:41`).

### A6-10 — Budget rails are evaluated at validate time only; apply re-plans against fresh state
- Severity: **P3** (shared PolicyEngine behaviour, visible on Pinterest)
- Classification: VERIFIED_CODE
- Evidence: `core/src/policy/engine.ts:58-62` runs `checkBudgetPolicy` in `validate`; `engine.ts:111-113` re-runs only `checkStaticPolicy` in `apply`; `provider.ts:146-156` re-reads the campaign on apply and recomputes `cap`/`from`. `pending_ttl_minutes` default 15 (`policy.ts:19`).
- Impact: a budget changed in Ads Manager between preview and apply (or a daily→lifetime switch) is executed without re-checking the 25 % delta cap or re-showing the preview. Bounded by the TTL; not exploitable cross-tenant.

### A6-11 — No 429 / backoff handling and a token refresh on every runtime assembly
- Severity: **P3** (reliability)
- Classification: VERIFIED_CODE
- Evidence: `client.ts:57-77` retries only `401` on `GET`, once; no `429`/`5xx` handling, no `Retry-After`. `client.ts:45` holds the 30-day access token in instance memory only; the cloud stores only `refreshToken` (`cloud/lib/cloud/types.ts:79`) and constructs a new client per `createTenantRuntime` (`runtime.ts:81`), so each tenant runtime build performs a `refresh_token` grant before its first read.
- Impact: Pinterest's per-app rate limits (not modelled anywhere) will surface as opaque `PROVIDER_ERROR: HTTP 429`; under load the token endpoint is hit once per request.

### A6-12 — Creation objective enum omits two official objectives
- Severity: **P3**
- Classification: VERIFIED_CODE + OpenAPI
- Evidence: `schemas.ts:19` allows AWARENESS, CONSIDERATION, WEB_CONVERSION, CATALOG_SALES, VIDEO_COMPLETION, APP_INSTALL, SALES, LEADS, CTV_CONSIDERATION. OpenAPI `CampaignObjectiveType` additionally has `VIDEO_VIEW` and `WEB_SESSIONS`.

### A6-13 — Pinterest is off by default in cloud deployments (two independent switches)
- Severity: informational (deliberate, documented) — recorded because it changes what "connected" means in production
- Classification: VERIFIED_CODE + VERIFIED_TEST
- Evidence: `platform/apps/cloud/lib/env.ts:66` `PINTEREST_OAUTH_ENABLED` default `'false'`; `.env.example:83` `ADPORT_PROVIDER_TEST_ORGANIZATION_IDS=` (empty string) which `provider-rollout.ts:12-15` treats as "deny every organisation" (test `provider-rollout.test.ts:22-25` confirms fail-closed). A stored Pinterest credential is silently not loaded when gated (`runtime.ts:79`).

### A6-14 — Nothing has been verified against a live Pinterest account
- Severity: **P3** (honest in docs; material for go-live)
- Classification: DOCUMENTED_ONLY / NOT_VERIFIED
- Evidence: `pinterest.md:36` "No live Pinterest API calls or ad mutations have been verified yet"; `platform/README.md:122` "cloud discovery returned no accounts"; `test/pinterest.test.ts:12-15` "Synthetic values, not a live-account capture"; `git log` shows no change since the vendored import. The OpenAPI cross-check below removes the *static* uncertainty but not the live one.

## What a world-class system would need (concrete)

1. Engine: Pinterest spend/metric mapping in `normalize.py`, a `pinterest_ads.json` fixture with campaigns → ad groups → ads and daily rows, `demo-pinterest` alias, admitted `update_campaign_budget/status` rows with `get_campaign` read-back, and a `paid-media-wiki/pinterest.md` skill (objectives ↔ billable events, CBO vs ad-group budgets, 30/30/1 attribution, Pin formats, Search vs Browse placements, seasonality/planning lead time, Performance+).
2. Bridge: `pinterest_ads → pinterest` mapping with `budget_micros` and `status` translations (A6-02).
3. Reads: ad-group and ad list tools exposing bid, bid strategy, budget/type, pacing, `optimization_goal_metadata`, `conversion_learning_mode_type`, `lifetime_frequency_cap`, `placement_group`, `targeting_spec`, `summary_status`, `review_status`/`rejected_reasons`; campaign `summary_status`, `objective_type`, `start/end_time`, `is_performance_plus`.
4. Metrics: configurable column allowlist (pin clicks, total conversions by event, leads, saves, video completes, reach, frequency, `*_ROAS`), `granularity=DAY|HOUR`, `/targeting_analytics` (age, gender, geo, device, interest, keyword, placement), async `/reports` for >90-day history; attribution windows as query parameters recorded on every row; `data_complete_through` signal (Pinterest conversion lag).
5. Writes: ad-group budget and bid updates (micros), ad-group/ad status, frequency cap, pacing; all with read-back verification instead of echo equality (A6-09); optional idempotency via name/time checks.
6. Health: `ADVERTISER_DISABLED`, rejected ads, zero-delivery with budget, learning-phase stalls, CBO with no active ad groups, lifetime campaigns past `end_time`.
7. Transport: 429/5xx backoff with `Retry-After`, access-token caching across requests, `ad_account_id` in POST bodies for Business Access shared accounts (agency use case), and a live Trial-access smoke test (a `docs/pinterest-live-checklist.md` like the existing Snapchat one).
8. UX: currency on every preview and row; Arabic labels for Pinterest objectives/statuses (none exist today).
