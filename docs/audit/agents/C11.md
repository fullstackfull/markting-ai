## Findings

### C11-01 — Retry-exhausted model failure returns HTTP 200 whose `text` is the raw, unredacted exception, persisted into the thread and shown to the user as a normal answer
- **Severity:** P2 (information disclosure to the authenticated user; silent failure; corrupts future model context)
- **Classification:** VERIFIED_RUNTIME, VERIFIED_CODE
- **Evidence:**
  - `engine/src/paid_media_agent/assembly.py:236-245` installs `ModelRetryMiddleware(max_retries=2, on_failure="continue")` for every non-`scripted` model.
  - Installed `langchain/agents/middleware/model_retry.py:189-195`: `content = f"Model call failed after {attempts_made} ... with {exc_type}: {exc_msg}"` → `AIMessage`. `_retry.py:70-74`: anything that is not a `ModelError` is retried, so every generic exception ends in this message.
  - `engine/src/paid_media_agent/surfaces/runner.py:130-133`: `text = _content_text(messages[-1].content)` — the failure `AIMessage` is the last message; `surfaces/api/app.py:91-101` returns it with 200.
  - `engine/src/paid_media_agent/middleware/redaction.py:65-87`: redaction wraps **tool** calls only; the retry middleware is the outermost `wrap_model_call` layer (`assembly.py:246-247`; installed `langchain/agents/factory.py:268-275` "first in list becomes outermost"), so no redaction sees its output.
  - Probe (`probe2.py` C1'): model raising `RuntimeError("... Bearer AbCd… sk-abc… https://llm.internal.example:8443/v1 ... postgresql://u:p@db/x")` → `status= 200`, `text: 'Model call failed after 3 attempts with RuntimeError: gateway https://llm.internal.example:8443/v1 refused; header Bearer AbCdEfGhIjKlMnOpQrStUv123456; key sk-abcdefghijklmnopqrstuvwxyz0123; db postgresql://u:p@db/x'`; `leaks -> bearer: True | sk-: True | host: True | dsn: True`. The next turn's state showed `ai=2, human=2`: the failure text is persisted as an assistant message and becomes model context.
  - Adport passes it through unchanged: `platform/apps/cloud/lib/markting/assistant.ts:68-74`; UI renders `result.text` as a normal (non-error) bubble: `app/dashboard/assistant/assistant-chat.tsx:46,75-77`. No code in `platform/` recognises the string (`rg "Model call failed" platform/apps/cloud` → none); only the admin console does (`engine/src/paid_media_agent/admin/actions.py:1045-1048`, by string prefix).
  - No server-side log: `runner.py` and `api/app.py` import no logger (`rg "logging|logger" …` → none) and `ModelRetryMiddleware` does not log.
- **Description:** With a real provider (langchain-openai maps 429/5xx/connection/timeout to retryable `ModelError`s, `langchain_openai/chat_models/base.py:594-606`; anthropic likewise, `langchain_anthropic/chat_models.py:976-984`), an outage ends after 3 attempts in a 200 whose answer is the SDK's exception string (which embeds the HTTP response body, request ids and sometimes URLs). The engine's own secret list (`assembly.py:293-306`) is never applied to this text.
- **Impact:** Users of an Arabic-first product see an English stack-trace-like message as the assistant's reply; operators get no signal; the thread history now contains a bogus assistant turn that the model will read on the next request; provider/gateway details leak to tenants.
- **Recommendation:** Pass a callable `on_failure` that logs the sanitised exception (`sanitize_exception`) and returns a fixed, localisable message; surface a machine-readable `status`/`error` field in `OutcomeView` so adport can render an error bubble and not persist the turn as an answer; alternatively use `on_failure="error"` and map the exception in `app.py` to 502/503 with sanitised detail.

### C11-02 — Concurrent or duplicate submissions on the same thread are not serialised; a checkpoint race drops a whole turn from persisted state while both callers get 200
- **Severity:** P2
- **Classification:** VERIFIED_RUNTIME (in-memory checkpointer), INFERRED for Postgres
- **Evidence:**
  - `engine/src/paid_media_agent/surfaces/runner.py:86-89`: `_config` only claims ownership (`persistence/memory.py:94-96`, `persistence/postgres.py:237-244`); there is no per-thread lock, lease or in-flight marker anywhere (`rg "asyncio.Lock|Semaphore|in_flight" engine/src/paid_media_agent/surfaces engine/src/paid_media_agent/runtime` → none; the only lock is the report lock in `services/engine-demo/serve_demo.py:324`).
  - `surfaces/api/app.py:91-101`: `POST /threads/{id}/messages` has no idempotency key and no in-flight check. The Slack surface has event/action dedupe (`surfaces/slack/service.py:79,142`); the API has none.
  - Probe (`probe2.py` B3, stateless model): two concurrent POSTs `first`/`second` to thread `b3` → both `200`; responses `"echo 1 humans; last='first'"` and `"echo 2 humans; last='second'"`; final persisted state `{'human': 1, 'ai': 1}` with humans `['first']` — the `second` turn and its answer are gone although the client received them.
  - Adport side: `lib/markting/assistant.ts:38` (`claimThread` is an upsert, not a lock), `lib/cloud/repository.ts:355-369` (rate limit 120/min only), `assistant-chat.tsx:92,95` (client-side `busy` flag only).
- **Description:** LangGraph does not lock a thread; two runs fork from the same checkpoint and the last writer wins. The realistic trigger is the C11-03 chain: the adport call aborts at 240 s, the user resends, and the engine is still running the first turn.
- **Impact:** Lost conversation turns, answers that do not match the persisted history, non-deterministic proposals. With `DATABASE_URL` set (the compose default, `docker-compose.yml:43`) the Postgres checkpointer is used (`serve_demo.py:208-219`); I did not run it, so the exact Postgres behaviour is NOT_VERIFIED, but nothing in the code adds serialisation there either.
- **Recommendation:** Per-thread mutex/lease in the runner (in-process `asyncio.Lock` keyed by thread id is sufficient for the single-worker uvicorn server, `cli.py:575-580`, `serve_demo.py:411-417`); reject or queue a second message with 409 while a run is active; accept an `Idempotency-Key` on `POST /messages`; on the adport side keep an `in_flight_until` on `markting_threads` and return 409 to the UI.

### C11-03 — Worst-case model-turn wall time is ~3× the configured per-call timeout (plus SDK retries and backoff), which exceeds adport's 240 s client abort and the route's 300 s budget; the engine keeps running after the client gives up
- **Severity:** P2
- **Classification:** VERIFIED_RUNTIME (scaled), VERIFIED_CODE
- **Evidence:**
  - `assembly.py:166` (`timeout`, `max_retries=2` on the SDK), `assembly.py:240-241` (retry outer, timeout inner), `middleware/timeout.py:36` (`asyncio.wait_for` per attempt), installed `factory.py:268-275` (first middleware is outermost → the 120 s cap applies per retry attempt, not per run). `config.py:118-121`: defaults 120 s per call and 40 calls per run; no run-level deadline exists.
  - Probe (`probe2.py` D): model blocked 14 s with `paid_media_model_timeout_seconds=10` → `status= 200 elapsed=33.1s model_calls= 3 text: 'Model call failed after 3 attempts with TimeoutError: model call exceeded 10 seconds'`. With the default 120 s that is ≈363 s for one stalled model call before any tool time.
  - Adport budget: `lib/markting/env.ts:18` (`MARKTING_ENGINE_TIMEOUT_MS` default 240 000), `engine-client.ts:73,81-82,97` (AbortController → `EngineError('Engine unreachable: AbortError', 503, 'unreachable')`), `app/api/assistant/messages/route.ts:7` (`maxDuration = 300`).
  - No client-disconnect handling in the engine: `app.py:91-101` does not take `Request`, never checks `is_disconnected()`; FastAPI does not cancel a handler on disconnect (INFERRED from framework behaviour, not exercised).
  - `docs/ARCHITECTURE.md:513-514` already states "there is no fixed upper bound on a request's duration" — the code agrees.
- **Description:** The budgets are not aligned: engine (≥363 s worst case for the model alone, unbounded with tools) > route (300 s) > adport client (240 s). A degraded-but-not-dead provider therefore produces an adport-side "unreachable" error while the engine still finishes the turn minutes later and writes it to the thread.
- **Impact:** User sees a failure, retries, and hits C11-02; the engine burns a full extra turn (and model tokens) nobody reads; the thread history diverges from what the user saw.
- **Recommendation:** Make the engine's total per-turn deadline the smallest budget (e.g. `PAID_MEDIA_RUN_DEADLINE_SECONDS` enforced with `wait_for` around `ainvoke` plus `ModelRetryMiddleware(max_delay=…)`), then size adport's timeout above it and `maxDuration` above that; or make the turn asynchronous (job id + poll/stream) so no HTTP call has to outlive a model retry cycle.

### C11-04 — Stale `awaiting_approval` proposals are re-returned on every later turn, and the bridge re-processes them: duplicate pending operations, a permanent "unsupported" callout, or a bricked thread (403 on every message)
- **Severity:** P2
- **Classification:** VERIFIED_RUNTIME (engine half), VERIFIED_CODE (adport half)
- **Evidence:**
  - `surfaces/runner.py:91-93,134`: `latest_proposal` returns the newest proposal on the thread regardless of state, every turn.
  - Probe (`probe.py` A): write intent → `A1 200 interrupted=True state=awaiting_approval`; then a new analysis message on the same thread without rejecting → `A2 200 interrupted=False proposal.state=awaiting_approval same_proposal=True`, and again on `A3`. The interrupt is dropped (`interrupts: 0, next: []`) but the proposal record stays `awaiting_approval` forever.
  - `lib/markting/assistant.ts:50-51`: bridges whenever `proposal.state === 'awaiting_approval'` — no "unseen (proposal_id, revision)" check, no `interrupted`/`available_actions` check, although `findEngineProposal` exists (`lib/markting/repository.ts:90-96`).
  - `lib/markting/bridge.ts:58-66`: for `translation.status === 'unsupported'` the function returns **without** `handoff` → the engine proposal is never rejected → it is bridged again on every following turn (the UI shows the unsupported callout for every later question in that thread, `assistant-chat.tsx:118-126`).
  - `bridge.ts:68-70`: a principal without `tools:write` throws `BridgeAccessError(…, 403)` before any handoff → every later message on that thread (even "what needs attention?") returns 403 "This workspace plan or role does not allow write previews" → the thread is unusable until the user starts a new one.
  - `bridge.ts:98-105`: `handoff` swallows every `rejectOnEngine` failure (comment: "The adport record is the source of truth"). If the reject fails (engine restart, 5xx, network), the proposal stays awaiting and every later turn runs `registry.call` again → `platform/packages/core/src/policy/engine.ts:64-70` creates a **new** `pending_operations` row each time (`randomUUID()`, no `opHash` dedupe on validate) → duplicate items on the Approvals page for one engine proposal; `repository.ts:84-86` upserts the provenance row and overwrites `pending_operation_id`, orphaning the earlier pending operation's provenance.
  - Translation failure modes are common, not exotic: `lib/markting/translate.ts:131-157` (`no adport account is mapped to engine alias`, tool not in allowlist, provider mismatch, budget out of range).
- **Description:** The engine API's "proposal = newest record on the thread" contract (documented at `docs/ARCHITECTURE.md:505-509`) is combined with a bridge that keys off `proposal.state` alone and does not always hand the proposal back.
- **Impact:** Duplicate approvals (an approver can apply the same budget change twice from two rows — each row is a separate pending operation with its own TTL), a permanently noisy thread, or a thread that can no longer answer anything for a viewer-plan user. Financially relevant because pending operations are real write previews.
- **Recommendation:** In `assistant.ts` bridge only when `outcome.interrupted && outcome.available_actions.includes('reject')` **and** `findEngineProposal(org, id, revision)` is empty; always hand off (reject) for unsupported and access-denied outcomes; surface handoff failures (retry with backoff, then audit `note`) instead of swallowing; engine-side (upstream request) include only proposals created in the current run in `RunOutcome`, or add `created_in_run`/`run_id`.

### C11-05 — The demo host's model keeps per-process mutable script state shared by every thread and user; any concurrency returns the "offline demo engine" filler instead of answers
- **Severity:** P2 (demo code on the production path: compose runs this host as *the* engine with `MARKTING_ENGINE_MODE` defaulting to `demo`)
- **Classification:** VERIFIED_RUNTIME
- **Evidence:** `services/engine-demo/serve_demo.py:84-115` (`seen_human_messages`, `call_count`, `steps` are instance fields mutated per call), `:194-198` (one instance for the whole app), `:132-136` (default mode `demo`), `docker-compose.yml:35-41,53` (the engine service runs `serve_demo.py`). Probe (`probe.py` B2): two concurrent POSTs to **different** threads → both `200`, both texts `'This is the offline demo engine: it replays a fixed investigation…'`, `same_as_baseline=False`; the sequential baseline (B0) returned the real analysis. B1 (same thread) also returned filler to both callers and kept one message.
- **Impact:** Two users (or one user double-clicking) in the demo deployment get wrong answers; with the write script, a proposal may fail to appear or appear on the wrong thread. This is the first impression of the product for every preview user.
- **Recommendation:** Make the demo model stateless: derive the step index from the message list (count of `AIMessage`s since the last `HumanMessage`) and the script from the last human text, with no instance mutation; or serialise with a lock per request (acceptable for a demo).

### C11-06 — A Pipeboard catalog endpoint that fails at boot is silently dropped for the lifetime of the process; `/health` keeps reporting `ok`
- **Severity:** P2
- **Classification:** VERIFIED_CODE
- **Evidence:** `engine/src/paid_media_agent/tools/pipeboard.py:33` (20 s), `:111-121` (any exception → `logger.warning` and `return []`), `:95-99` ("Loaded once per process; restart to pick up changes"), `:129-134` (catalog built from whatever loaded, including nothing). `surfaces/api/app.py:80-89`: `/health` is static (`status: ok`, revision, source) with no per-platform status, no model or DB probe. Covered by `tests/unit/test_pipeboard_catalog.py:139-142` as intended behaviour (one platform missing → catalog without it).

(Not reachable in the markting host, which forbids `PIPEBOARD_API_TOKEN` at boot, `serve_demo.py:142-143`; it matters for the upstream `serve`/MDA paths and for any future live mode.)
- **Recommendation:** Fail boot or mark the process degraded when a configured endpoint yields zero tools; add periodic/triggered `refresh()`; report per-platform tool counts in `/health` and let adport read it (`EngineClient.health()` exists but has no callers: `rg "\.health\(\)" platform/apps/cloud` → none).

### C11-07 — The adport engine client's timeout covers only response headers; the body read and the streamed report file have no deadline
- **Severity:** P3
- **Classification:** VERIFIED_CODE
- **Evidence:** `lib/markting/engine-client.ts:81-99`: the abort timer is cleared in `finally` as soon as `fetch` resolves (headers), and `response.json()` at `:108` runs afterwards with no signal; for `raw` responses the `Response` is returned and `app/api/reports/engine/[name]/route.ts:18` streams `upstream.body` with no timeout. A stalled engine body therefore hangs the route up to the platform limit.

### C11-08 — The friendly "engine not reachable" messages never reach the user; `apiError` rewrites every ≥500 to "Internal server error."
- **Severity:** P3
- **Classification:** VERIFIED_CODE
- **Evidence:** `lib/markting/assistant.ts:45` and `app/api/reports/engine/route.ts:11` build `HttpError('The analysis engine is not reachable right now.', 503)`; `lib/http.ts:26-28` replaces the message of any response with status ≥500 by `'Internal server error.'`; the chat renders `result.error` (`assistant-chat.tsx:43`). ### C11-10 — Non-retryable model errors and several `WriteDenied` reasons surface as unhandled or mis-mapped HTTP statuses from the engine API
- **Severity:** P3
- **Classification:** VERIFIED_RUNTIME, VERIFIED_CODE
- **Evidence:** Probe (`probe.py` C2): a `ModelAuthenticationError` (non-retryable per `langchain_core/exceptions.py:68-83`; real SDK auth errors inherit it, `langchain_openai/chat_models/base.py:576`, `langchain_anthropic/chat_models.py:957`) → `status= 500`, body `Internal Server Error`. `app.py:95-101` catches only `ThreadAccessDenied`. `app.py:116-123` maps every `WriteDenied` on approve to 403 (including `unknown_proposal`), while reject/edit map the same reasons to 409 (`:134-137,144-147`). ### C11-13 — `ModelTimeoutMiddleware` is a no-op on the sync path and cannot stop sync work on the async path
- **Severity:** P3 / GAP
- **Classification:** VERIFIED_CODE, VERIFIED_RUNTIME (side observation)
- **Evidence:** `middleware/timeout.py:24-28` returns `handler(request)` with no bound ("Sync calls cannot be cancelled safely"). ### C11-14 — No retry, idempotency or degraded-mode detection on the adport→engine edge
- **Severity:** GAP (nothing claims otherwise)
- **Classification:** VERIFIED_CODE
- **Evidence:** `engine-client.ts` has no retry for idempotent GETs; `runReport` has no idempotency key (the host serialises runs with `asyncio.Lock`, `serve_demo.py:324,344`, but a client timeout + retry produces two report runs in the index, `:304-306`); `EngineClient.health()` is never called; `/health` is static (C11-06).
- **Recommendation:** Retry idempotent GETs with jitter; accept a client-supplied run key on `/reports/run`; poll `/health` for a dashboard status chip.

### Positive observations (for balance)
- Write-side hung-call handling is strong and tested: `ProviderTimeout` is defined as "outcome unknown, not failed" (`tools/providers.py:28-30`), the executor caps mutations at 30 s, records `provider timed out after submission; no retry was attempted`, performs bounded readback and emits `verified`/`failed`/`unknown` receipts (`tools/writes.py:848-918`), uses single-use approval claims (`:810-814`) and an idempotency argument when the operation defines one (`:840-843`). Fixture behaviours `timeout_after_commit`/`timeout_without_commit` exist (`tools/fixtures.py:418-419,471-477`). In the markting host the write provider always raises (`serve_demo.py:69-81`), so this path is unreachable by design there.

## What a world-class system would need

1. **One budget hierarchy**: engine per-turn deadline (model + tools) < adport client timeout < route `maxDuration`, enforced in code (not by convention), with the engine cancelling the LangGraph run and recording a `timed_out` outcome on the thread.
2. **Asynchronous turns**: `POST /threads/{id}/messages` returns a run id; the client streams/polls; retries and reconnects become safe and `maxDuration` stops mattering. The runner already has an `on_event` streaming path (`runner.py:150-206`) that the API does not expose.
3. **Per-thread serialisation and idempotency**: a lease per thread (DB row with `in_flight_until`) plus `Idempotency-Key` on message and report endpoints; return the stored result for a duplicate key.
4. **Failure as data, not prose**: `OutcomeView.status ∈ {ok, model_failed, timed_out, cancelled}` with a sanitised `error_code`; adport renders an error bubble, does not persist the turn as an answer, and never shows SDK text to a tenant; the engine logs/metrics every retry exhaustion.
5. **Proposal lifecycle contract**: outcomes carry only proposals created in the run (`run_id` on `ProposalRecord`), adport bridges by `(proposal_id, revision)` novelty, and every bridge outcome (pending, unsupported, denied) hands the proposal back to the engine with retries and an audit trail; validate dedupes by `opHash` so one proposal can only ever yield one live pending operation.
6. **Dependency-aware health and degraded mode**: `/health` with per-platform tool counts, model reachability (cheap ping cached), checkpointer/DB status; adport reads it and shows a status chip; the engine refuses or flags boot when a configured catalog endpoint is empty and refreshes periodically.
7. **Stateless demo**: a replay model that derives its step from the message history so the demo survives concurrency, plus a per-process lock as belt-and-braces.
8. **Tests for the failure paths**: retry-exhausted turn through the real API (asserting status, redaction, no persistence), timeout cascade timing, concurrent posts to one thread, non-JSON/invalid engine responses, handoff failure leading to re-bridge.
