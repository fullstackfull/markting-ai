## Findings

### C11-01 — Model-call failures are returned to the user as HTTP 200 "answers" (English error sentinel), not errors
- Severity: P2 · Classification: VERIFIED_CODE + VERIFIED_RUNTIME
- Evidence: `engine/src/paid_media_agent/assembly.py:240` (`ModelRetryMiddleware(max_retries=MODEL_RETRY_ATTEMPTS, on_failure="continue")`); `.venv/.../langchain/agents/middleware/model_retry.py:192-195,210-219` (`_handle_failure` with `on_failure="continue"` returns an `AIMessage` "Model call failed after {n} attempts with {Type}: {msg}"); `surfaces/runner.py:131-133` (outcome `text` = last message content); `surfaces/api/app.py:91-101` + `surfaces/api/views.py:23-37` (post_message returns 200 with that text, no inspection); `platform/apps/cloud/lib/markting/engine-client.ts:101-108` (only `!response.ok` is treated as error — 200 passes through); `assistant.ts:68-72` (`text: outcome.text` returned verbatim); `app/dashboard/assistant/assistant-chat.tsx:46,77` (rendered directly in a `<pre>`). Runtime repro produced exactly `Model call failed after 3 attempts with ValueError: ...` as the assistant message.
- Description: When the model provider is down/overloaded (or any non-ModelError is raised, see C11-02), the retry middleware converts the failure into a normal assistant message. Every surface except the admin console treats that as a successful turn.
- Impact: During a model outage the end user sees a raw English string ("Model call failed after 3 attempts with APITimeoutError: ...") as a chatbot reply in an Arabic-first product — HTTP 200, no error state, no retry affordance, potentially leaking exception type/detail. Clients and dashboards log it as a successful answer; monitoring cannot distinguish an outage from a real reply.
- Recommendation: Detect the sentinel (or better, propagate a typed failure instead of `on_failure="continue"`) in `runner`/`outcome_view` and map to a 5xx (e.g. 502/503) with a localized message; have the engine-client/assistant surface it as an error, not chat text. The exact detection already exists in `admin/actions.py:1045` — lift it into the shared path.

### C11-02 — Deterministic/internal errors are retried as if transient, then swallowed
- Severity: P2 · Classification: VERIFIED_CODE + VERIFIED_RUNTIME
- Evidence: `.venv/.../langchain/agents/middleware/_retry.py:70-74` (`default_retry_on` returns `True` for every exception that is not a `ModelError`); `assembly.py:235-245` uses the default `retry_on`. Runtime repro: a plain `ValueError` from the selection middleware was retried to exhaustion and surfaced as "Model call failed after 3 attempts with ValueError".
- Description: Only `ModelError` with `is_retryable=False` short-circuits; any other exception (config bug, `ValueError`, `KeyError`, serialization error, a non-wrapped auth/400) is retried `MODEL_RETRY_ATTEMPTS`+1 times with exponential backoff and then masked as a model "answer".
- Impact: Deterministic bugs waste the full retry budget (3 attempts + ~1s/2s backoff) and are hidden behind the generic sentinel instead of failing fast/loudly. This directly caused the confusing contract-suite symptom (receipt simply "never appears") rather than a clear error. In production it would convert a code/config fault into a silent degraded turn.
- Recommendation: Pass an explicit `retry_on` limited to transient classes (timeouts, 429, 5xx) so programming/config errors propagate immediately; combine with C11-01 so what does remain surfaces as an error.

### C11-03 — Nested retry layers and no wall-clock cap per API request
- Severity: P2 · Classification: VERIFIED_CODE
- Evidence: `assembly.py:166` (`resolve_model` sets SDK `max_retries: 2` and `timeout`), `assembly.py:240-244` (middleware `ModelRetryMiddleware(max_retries=2)` + `ModelTimeoutMiddleware(120s)` + `ModelCallLimitMiddleware(run_limit=40)`); `config.py:118,120` (`timeout=120`, `max_model_calls=40`); `surfaces/api/app.py:91-101` (no request-level timeout); `middleware/timeout.py:24-28` (sync path is a no-op).
- Description: Each model inference can take up to 3 middleware attempts × 120s (the middleware `asyncio.wait_for` bounds the SDK's own 2 retries inside each attempt) ≈ 360s + backoff; a run may issue up to 40 model calls. There is no overall per-turn or per-HTTP-request deadline on the engine.
- Impact: A single `/threads/{id}/messages` call can legitimately run many minutes under provider stress, holding a worker and (with C11-04) outliving the client that is waiting.
- Recommendation: Add a run-level deadline (wall clock) and/or reduce stacked retries; document the realistic worst-case turn time and align server worker/timeouts to it.

### C11-04 — adport client timeout (240s) can abort while the engine keeps running (orphaned work, client sees false "unreachable")
- Severity: P2 · Classification: VERIFIED_CODE
- Evidence: `engine-client.ts:73` (`timeoutMs ?? 240_000`), `env.ts:18` (`MARKTING_ENGINE_TIMEOUT_MS` default 240_000), `engine-client.ts:81-99` (AbortController → on abort throws `EngineError('unreachable', 503)`); `assistant.ts:44-46` maps unreachable to "The analysis engine is not reachable right now." No cancellation is propagated to the engine; the FastAPI handler (`app.py:91-101`) continues to completion and the checkpoint advances.
- Description: The client-side abort fires at 240s, but C11-03 shows a turn can exceed that. The engine turn is not cancelled; it completes server-side (spending model tokens) while the user is told the engine is unreachable.
- Impact: Wasted model spend, user confusion (false outage message), and a diverged state: the thread checkpoint may now hold a completed turn the user never saw.
- Recommendation: Make the engine honor client disconnect / enforce a server deadline ≤ client timeout; return a resumable turn id so the UI can reconcile rather than silently drop.

### C11-05 — No per-thread concurrency control; duplicate/retried submissions race on the same thread
- Severity: P2 · Classification: VERIFIED_CODE
- Evidence: `surfaces/runner.py:86-89` (`_config` only `claim`s ownership) and `persistence/memory.py:94-96` / `postgres.py:237-245` (`claim` = "who owns this thread", returns True for the same caller every time — not a mutex); `app/api/assistant/messages/route.ts:14-15` and `assistant.ts:30-47` carry no idempotency key. The reports endpoint has an `asyncio.Lock` (`serve_demo.py:324`) but message posting does not.
- Description: Two concurrent `POST /threads/{id}/messages` for the same thread (user double-click, or a retry after the C11-04 abort while the first is still running) both reach `graph.ainvoke` on the same `thread_id`, concurrently writing the LangGraph checkpoint.
- Impact: Checkpointer write races / corrupted or interleaved thread state; duplicate processing of the same user text. With live writes this would be a correctness hazard; in this deployment (proposal-only) it is still a state-integrity/duplicate-turn risk.
- Recommendation: Serialize per `thread_id` (lock or DB advisory lock), reject a second in-flight turn with 409, and accept a client idempotency key on the message route.

### C11-06 — Catalog/provider outage at load is silently swallowed into a degraded (possibly empty) tool surface, loaded once per process
- Severity: P2 · Classification: VERIFIED_CODE
- Evidence: `tools/pipeboard.py:111-134` (`load_endpoint` catches `Exception`, logs a warning, returns `[]`; the catalog is built from whatever loaded); `pipeboard.py:95-99` (`current()` is loaded once — "restart to pick up changes"); `surfaces/api/app.py:80-89` `/health` still reports `status: ok` and the catalog revision regardless.
- Description: If one or all Pipeboard MCP endpoints are down/slow at boot (20s load timeout), their tools are dropped and the agent runs with a partial/empty read surface for the life of the process. Health does not reflect the degradation.
- Impact: During an upstream outage the agent will tell users it has no data / cannot find accounts rather than reporting an outage, and will stay degraded until a manual restart even after the provider recovers. (Not reachable in the default demo host, which uses the fixture catalog, but applies to any live/self-hosted deployment.)
- Recommendation: Surface per-endpoint load status in `/health`/metadata, fail boot (or mark unhealthy) when endpoints are missing, and add periodic catalog refresh with backoff.

### C11-07 — Write-execution reliability is strong, but single-attempt-no-retry is NOT test-verified in this tree (stale kill switch) and is unreachable in the product
- Severity: P3 (verification gap) · Classification: VERIFIED_CODE; tests currently red (see D1)
- Evidence: `tools/writes.py:775-915` — one `call_mutation` attempt wrapped in `asyncio.wait_for(timeout=30s)`; `ProviderTimeout`/`TimeoutError` → `outcome_reason="provider timed out after submission; no retry was attempted"` (writes.py:855-856); idempotency key = `proposal:revision` when configured (writes.py:840-845); claim consumed via `mark_used` before mutation with replay refusal (writes.py:810-814); cached-receipt short-circuit on re-execute (writes.py:781-783); bounded readback → `unknown` outcome (writes.py:713-768,896-915). Contract tests that assert these (`test_write_flows_graph.py:353,370-408` etc.) exist but fail here due to D1, and the product replaces the provider with `ProposalOnlyWriteProvider` (`serve_demo.py:69-82`) so this path never executes a live write in markting-ai.
- Description: The design correctly avoids duplicate submissions (no mutation retry, idempotency key, claim consumption, idempotent re-execute, reconciling readback). I could not get these green in this environment because of the stale kill switch, so they are VERIFIED_CODE only right now.
- Impact: The strongest reliability guarantees of the system are, in this working tree, unexercised by a green suite; a regression here would not be caught until the kill switch is cleared.
- Recommendation: Make the kill-switch path hermetic in tests (resolve against the configured workspace_root) so the write-flow contracts actually run; keep the no-retry/idempotency guarantees under CI.

### C11-08 — Streaming surfaces can duplicate partial text when a model call fails mid-stream and retries
- Severity: P3 · Classification: INFERRED
- Evidence: `surfaces/runner.py:158-178` emits `text` events as the model streams; `ModelRetryMiddleware` re-invokes the model on failure; `surfaces/slack/delivery.py:50-51,85-86` accumulates `last_text += event.text` and later appends the final text. The API/adport path is non-streaming (`runner.send` with `on_event=None`) so it is unaffected.
- Description: If attempt 1 streams partial text then errors, attempt 2 streams the full text; the Slack accumulator would show attempt-1 fragment followed by the full reply.
- Impact: Garbled/duplicated Slack output under transient model failures. Cosmetic, Slack-only.
- Recommendation: Reset per-attempt stream state on retry, or buffer text until the attempt succeeds.

### C11-09 — Sync model-timeout path is a no-op (acceptable, documented)
- Severity: P3 · Classification: VERIFIED_CODE
- Evidence: `middleware/timeout.py:24-28` (`wrap_model_call` returns `handler(request)` with no bound); docstring says sync calls rely on the SDK timeout. All product surfaces use the async graph (`ainvoke`/`astream`), so the SDK `timeout=120` (assembly.py:166) is the only sync bound.
- Description: Intentional; noted for completeness because a future sync caller would lose the hard cap that defends against a post-headers gateway stall.
- Recommendation: If any sync entrypoint is added, give it an equivalent hard bound (thread + join-with-timeout or executor).

## What a world-class system would need (gaps, concrete)
- Typed failure propagation end-to-end: engine returns a structured `error` (code + localized message) instead of `on_failure="continue"` text; adport renders an error state with a retry button, never a `<pre>` of a Python exception.
- A narrow `retry_on` (429/5xx/timeout only) plus jittered backoff; everything else fails fast and is alerted.
- A run-level deadline coordinated with the client timeout and the worker timeout, with cancellation propagated on client disconnect.
- Per-thread serialization + client idempotency keys so retries/double-clicks cannot race the checkpointer or double-charge the model.
- Health/readiness that reflects catalog completeness and per-endpoint MCP status; automatic catalog refresh so a transient boot-time outage self-heals.
- Localization of all operational messages (Arabic-first), including failure text.
- CI that actually exercises the write-execution contracts (hermetic kill-switch path).

## Disagreements / claims in docs that the code contradicts
- D1: The write-flow contract suite (`tests/contract/test_write_flows_graph.py`) is advertised as the proof of approval/mutation/readback contracts, but in this working tree 11/19 fail — solely because a stale `engine/workspace/KILL_SWITCH` (left by a prior `serve_demo` run; kill-switch path resolves against the project root at `runtime/profiles.py:58-60`, not the per-test `paid_media_workspace_root`). So the suite is not hermetic and the reliability guarantees it documents are currently unverified by a green run. Not a product defect in the engine's failure logic; a test-isolation defect + a dirty tree.
- D2: `assembly.py:235-238` comment says "Transient model failures should not kill a run; bounded, and tool effects never repeat." True for tool effects, but the mechanism also swallows NON-transient failures and masks them as a successful 200 answer (C11-01/C11-02) — the behavior is broader and less safe than the comment implies.
- D3: `engine-client.ts` header says a test "asserts that neither approve nor edit is ever requested" (write safety) — accurate — but there is no equivalent guard that a 200 body is a real answer and not the failure sentinel; the client trusts any 2xx body (C11-01).
