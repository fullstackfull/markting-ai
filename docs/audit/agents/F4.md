# F4 — API tester

Audit of the HTTP surface of markting-ai without a running stack: route handlers in
`platform/apps/cloud/app/api/**`, the engine host in `services/engine-demo/serve_demo.py`, and the
existing route/API tests. Where a claim could be exercised, I drove the **real route handlers** through
a scratch vitest harness with mocked persistence/auth and a stubbed engine `fetch` (29 checks, all
executed), so status codes and bodies below are observed, not predicted. Nothing outside this report
was written in the repository; scratch files live under the session scratchpad.

Classification tags: VERIFIED_CODE (read in source), VERIFIED_TEST (existing test asserts it),
VERIFIED_RUNTIME (observed by executing the handler/test in this session), DOCUMENTED_ONLY, INFERRED,
NOT_VERIFIED.

## Findings

### F4-01 — Engine report list/download is not tenant-scoped; any signed-in user of any organization reads every report
- Severity: **P2** today (synthetic data); becomes **P0** the moment the engine is pointed at real account data.
- Classification: VERIFIED_RUNTIME + VERIFIED_CODE
- Evidence: `platform/apps/cloud/app/api/reports/engine/route.ts:16-24` (GET only calls `sessionPrincipal`, then `engineClient().listReports()` with no org); `app/api/reports/engine/[name]/route.ts:10-26` (same for file download); `lib/markting/engine-client.ts:127-137` (`runReport`, `listReports`, `fetchReportFile` carry no tenant identifier); `services/engine-demo/serve_demo.py:304-306,355-374` (one global JSON index, `requested_by` is always the service caller `adport-bridge`, `docker-compose.yml:48`). Harness: `reports GET org B viewer => 200 {"reports":[...]}` with engine URL `http://engine.test/reports`; `report file org B viewer => 200 <html>report</html>` with `content-disposition: attachment`.
- Description: The Reports page passes `organizationId` only to pick the session's membership; the engine has one index shared by all tenants. A viewer in organization B lists and downloads runs triggered by organization A. The runs are over fixture data because the host forces `PAID_MEDIA_DATA_MODE=sample` in both modes (`serve_demo.py:183-191,383-388` and `assert_fail_closed` at `:163-166`), so no real advertiser data is exposed today.
- Impact: Cross-tenant read of report artifacts (synthetic now). The 50-entry cap at `serve_demo.py:306` also means one organization's runs evict another's.
- Recommendation: Namespace runs per organization (index key + file prefix, or one engine token per org as `docs/TODO.md:27` already suggests), filter `GET /reports` by requester, and bind file downloads to the run's organization before this surface ever sees non-fixture data.

### F4-02 — A viewer or reader-plan user who asks the Assistant for a change gets a 403 after the engine already paused on a proposal; the proposal is orphaned
- Severity: **P2**
- Classification: VERIFIED_RUNTIME + VERIFIED_CODE
- Evidence: `lib/markting/bridge.ts:68-70` (throws `BridgeAccessError` 403 before `record`/`handoff`); `lib/markting/assistant.ts:40-47,63-65` (engine is called first; the access error aborts the whole turn). Harness: `assistant viewer receives proposal => 403 {"error":"This workspace plan or role does not allow write previews (tools:write)."}` with `recordEngineProposal calls: 0; engine reject calls: 0`. `assistant viewer (allowed to chat) => 200` shows chat itself is permitted for viewers.
- Description: The scope check happens only after the engine has produced an `awaiting_approval` proposal. The user loses the assistant's text, no provenance row is written, and the engine is never told the proposal was handled, so its thread stays interrupted (upstream `surfaces/runner.py:208-213` resumes an interrupted graph only through `resume`; what `send` does next on that thread is INFERRED, not verified).
- Impact: Every viewer and every organization on the default free `reader` plan (`lib/cloud/plans.ts:24-27,93,103`) hits an error path on the most important demo flow; the engine accumulates dangling proposals.
- Recommendation: Decide before calling the engine (either refuse write-intent turns for principals without `tools:write`, or let the engine answer and convert the proposal into an `unsupported`/`not_allowed` bridge outcome with the hand-off still performed and the assistant text still returned).

### F4-03 — Requesting an organization you are not a member of returns 500 "Internal server error." (and logs an error) instead of 403
- Severity: **P2**
- Classification: VERIFIED_RUNTIME + VERIFIED_CODE
- Evidence: `lib/cloud/repository.ts:46-47` (`resolveMembership` throws a plain `Error`); routes translate only the string `'Authentication required.'` (`app/api/approvals/[id]/apply/route.ts:30`, `reject/route.ts:24`, `reports/engine/route.ts:10`, `assistant/messages/route.ts:17`); `lib/http.ts:21,26-29` maps any other `Error` to 500 and `console.error`s it. Harness: `apply wrong org => 500`, `reject wrong org => 500`, `reports GET wrong org => 500`, each with one `console.error` call.
- Impact: A trivial unauthenticated-adjacent probe (`organizationId` of another tenant) produces server-error noise and misleading "something broke" UX. No data is leaked (the membership check does hold).
- Recommendation: Throw `HttpError(…, 403)` from `resolveMembership` or translate that message alongside the authentication one in a shared helper used by all session routes.

### F4-04 — Engine error translation is inconsistent: 4xx details from the engine leak verbatim to the browser, engine 401 is relayed as a user 401, and the friendly 5xx messages are dead code
- Severity: **P2**
- Classification: VERIFIED_RUNTIME + VERIFIED_CODE
- Evidence: `lib/markting/engine-client.ts:101-107` (message embeds up to 300 chars of the upstream body); `app/api/reports/engine/route.ts:9-13`, `app/api/reports/engine/[name]/route.ts:29`, `lib/markting/assistant.ts:45` (pass `error.status` through for <500); `lib/http.ts:26-28` (any status ≥500 is rewritten to "Internal server error."). Harness: `reports GET engine 401 => 401 {"error":"Engine returned 401: {\"detail\":\"invalid bearer token\"}"}`; `assistant engine 403 => 403 {"error":"Engine returned 403: ..."}`; `reports POST engine 422 => 422 {"error":"Engine returned 422: {\"detail\":[{\"loc\":[\"body\",\"end\"]...`; `reports GET engine unreachable => 503 {"error":"Internal server error."}`; `reports GET no engine token configured => 503 {"error":"Internal server error."}`.
- Description: (a) A misconfigured `MARKTING_ENGINE_TOKEN` surfaces to end users as HTTP 401 with the engine's detail text, indistinguishable from a session problem. (b) Engine validation/conflict bodies are forwarded raw. (c) The messages "The analysis engine is not reachable right now." and "MARKTING_ENGINE_TOKEN is not configured." can never reach a client because `apiError` discards every ≥500 message; the UI then shows a generic failure.
- Impact: Operational confusion and minor information disclosure (engine internals, bearer-token wording). No secrets observed in the leaked text.
- Recommendation: Map engine errors to a small fixed vocabulary (502/503 with a stable code such as `engine_unavailable`, `engine_misconfigured`), never relay engine 401/403 as user auth statuses, and let `apiError` keep curated messages for 5xx.

### F4-05 — Apply is not atomic: concurrent applies of the same pending id can execute the provider write twice
- Severity: **P2** (candidate P1 if provider calls are slow or clients retry on timeout)
- Classification: VERIFIED_CODE for the ordering; INFERRED for the race outcome (not reproduced; needs a DB)
- Evidence: `platform/packages/core/src/policy/engine.ts:90-124` (`get` → `applyWrite` → `delete`, no claim/lock); `platform/apps/cloud/lib/cloud/repository.ts:413-418` (`delete` is an unconditional `update … set consumed_at = now()` with no `consumed_at is null` guard and no affected-row check); `app/api/approvals/[id]/apply/route.ts:20-27` adds a second non-atomic lookup. No upstream test exercises concurrent apply (`rg -i "concurren|twice" platform/packages/core/test` finds only the synthetic provider CAS test). Mitigation present: the dashboard button is disabled while busy (`approval-actions.tsx:34-35`).
- Impact: Two approvers, or one approver plus an API/MCP retry while the first call is in flight, can both pass the `get` and both call `provider.applyWrite`; for `*_create_campaign` this creates duplicates (spend), for budget/status it double-writes. Inherited from upstream adport.
- Recommendation: Claim the row atomically before the provider call (`update … set consumed_at = now() where id = … and consumed_at is null returning id`, fail with 409 if zero rows), and make `PendingOperationStore.delete` return whether it consumed.

### F4-06 — Report runs are not plan-gated and effectively unlimited; one member can monopolise the shared engine lock
- Severity: **P2**
- Classification: VERIFIED_CODE + VERIFIED_RUNTIME
- Evidence: `app/api/reports/engine/route.ts:31-35` (only `viewer` is refused; no `requireScope`, no plan check); `lib/cloud/repository.ts:355` (default limit 120/min per subject); `services/engine-demo/serve_demo.py:324,344` (every run serialises on one process-wide `asyncio.Lock`, each run renders HTML/PDF). Harness: `reports POST member reader-plan => 200 {"id":"run_2"}`; `reports POST cadence=yearly end=2026-13-99 => 200` with engine body `{"cadence":"weekly","end":"2026-13-99"}` (invalid date passes the regex at `route.ts:34` and is forwarded).
- Impact: Any member of any free organization can queue up to 120 renders a minute on the single engine, blocking other tenants' runs and assistant turns that share the process; `docs/TODO.md:8` admits engine usage is not metered.
- Recommendation: Gate `POST /api/reports/engine` on a plan entitlement, lower the per-org limit (e.g. a few per hour), validate `end` as a real date, and return 409/429 when the engine lock is busy.

### F4-07 — Provider write succeeds but the client is told it failed when post-write bookkeeping throws
- Severity: **P2**
- Classification: VERIFIED_RUNTIME + VERIFIED_CODE
- Evidence: `app/api/approvals/[id]/apply/route.ts:26-28` (`applyPending` then `markPendingOutcome`, no isolation). Harness: `apply write ok, provenance update fails => 500 {"error":"Internal server error."}` with `applyPending called: 1`.
- Impact: The approver sees "could not apply", the pending row is already consumed by `PolicyEngine.apply`, a retry returns 404 "not found, expired, or already applied" and the Approvals page no longer shows the row; the only truth is the `applied` audit event. Confusing after a real budget change.
- Recommendation: Treat provenance update as best-effort (log and still return `ok: true` with the result), or persist it in the same transaction as the pending consume.

### F4-08 — Body handling on session POST routes: malformed JSON is silently accepted, `null` body crashes to 500, no content-type/origin check, no size cap
- Severity: **P3**
- Classification: VERIFIED_RUNTIME + VERIFIED_CODE; the Next.js default body limit is INFERRED
- Evidence: `request.json().catch(() => ({}))` at `apply/route.ts:16`, `reject/route.ts:10`, `reports/engine/route.ts:29`, `assistant/messages/route.ts:11`; `app/api/v1/tools/[tool]/route.ts:12` (`await request.json()` uncaught). Harness: `apply bad JSON => 200` (org falls back to the default membership), `apply body=null => 500` (`TypeError` reading `.organizationId`), `apply body=[] => 200`, `apply text/plain body (origin evil.example) => 200`, `apply 5MB body => 200`, `reports POST bad JSON => 200 {"id":"run_2"}` (a report run is triggered by garbage), `v1 tools bad JSON => 500 {"error":"Internal server error."}`. CSRF posture: no `Origin`/`Sec-Fetch-Site` check anywhere except `/api/waitlist` (`waitlist/route.ts:13-19,47`); cookies are `SameSite=Lax` by library default (`@supabase/ssr` `dist/main/utils/constants.js:4-7`). Size: only `/api/waitlist` bounds the stream (`waitlist/route.ts:51-66`); `next.config.ts:33-35` limits server actions only.
- Impact: Garbage requests trigger real side effects (report runs) or 500s; defence against cross-site POST rests entirely on SameSite=Lax; large bodies are buffered in full. Low exploitability, poor hygiene.
- Recommendation: One `readJsonBody(request, schema, maxBytes)` helper (zod, 413 on size, 400 on parse, 415 on content-type) for all session routes; reject cross-site `Sec-Fetch-Site` on mutating session routes.

### F4-09 — `/api/support` maps every non-Zod failure to 403 and echoes raw error messages
- Severity: **P3**
- Classification: VERIFIED_RUNTIME + VERIFIED_CODE
- Evidence: `app/api/support/route.ts:43` (`apiError(error, error instanceof z.ZodError ? 400 : 403)` — a fixed <500 status means `apiError` returns `error.message` verbatim, `lib/http.ts:26-28`). Harness: `support DB error => 403 {"error":"connect ECONNREFUSED 10.0.0.5:5432 relation \"public.feedback\" does not exist"}`; `support bad JSON => 403 {"error":"Expected property name or '}' in JSON at position 1 ..."}`; `support unauthenticated => 403` (not 401); `support honeypot filled => 400` with the Zod issue naming `website` (the honeypot is disclosed, unlike `/api/waitlist` which returns `{ok:true}`, `waitlist/route.ts:79`).
- Impact: Infrastructure details (DB host:port, schema) can reach any signed-in user when the database misbehaves. `docs/ARCHITECTURE.md:331` documents this mapping as intended upstream behaviour; it is still a leak.
- Recommendation: Use the generic status mapping (`apiError(error)`) so unknown errors become 500 with a fixed message, return 401 for missing sessions, and make the honeypot answer indistinguishable from success.

### F4-10 — The requester≠approver rule exists only on the dashboard route, and the shipped `.env.example` turns it off
- Severity: **P2**
- Classification: VERIFIED_CODE + VERIFIED_RUNTIME
- Evidence: `app/api/approvals/[id]/apply/route.ts:22-24` is the only use of `MARKTING_ALLOW_SELF_APPROVAL` (`rg ALLOW_SELF_APPROVAL app lib`); `.env.example:49` ships `MARKTING_ALLOW_SELF_APPROVAL=true`; `Makefile:21` copies it to `.env` for every `make env`; `README.md:117` describes the flag as "single-user demos only". `/api/v1/tools/[tool]` and `/mcp` apply with `pending_operation_id` under the same credential that validated, with no requester check (`app/api/v1/tools/[tool]/route.ts:5-17`; core `tools/write.ts:40-52`). Harness: `apply createdBy=null => 200` (API-key-created rows have no creator and can be applied by any admin), `apply self-approval (env=true) => 200`.
- Impact: The four-eyes control described in `docs/PHASE1-REPORT.md:16` ("Requester ≠ approver unless …") is bypassable by design through API keys/MCP and is disabled by default in every deployment created by following the README.
- Recommendation: Default the flag to `false` in `.env.example`, apply the same rule in the REST/MCP second call (record `created_by` for API keys as the key id and compare), and document the remaining gap.

### F4-11 — `/api/dashboard/summary` collapses every failure into 400 and uses a different query-parameter name than every other route

## What a world-class system would need (gaps, concrete)

1. A single request-parsing layer for session routes (zod schema, byte cap, content-type and `Sec-Fetch-Site` checks, uniform 400/413/415) replacing the five hand-rolled `request.json().catch(() => ({}))` sites.
2. A single error-translation layer that returns stable machine codes (`not_member`, `engine_unavailable`, `pending_expired`, `self_approval_blocked`) in both Arabic and English rather than engine/DB prose, and never relays an upstream 401/403 as the user's own auth status.
3. Atomic consume-before-write for pending operations and an idempotency key on `apply`, with a contract test that fires two applies concurrently against Postgres.
4. Per-organization engine identity (token or namespace) so reports, threads and `requested_by` are tenant-bound, plus org-level quotas on runs and tokens.
5. Route-level test suites for every session API (positive, each negative case in F4-14, and engine fault injection), wired into `make test` together with the upstream engine contract suite.
6. The requester≠approver rule enforced at the PolicyEngine boundary (REST, MCP and dashboard alike), default-on, with `created_by` recorded for API-key principals.
7. Structured server logs with request ids on 5xx (today `console.error(error)` only), so a 500 from F4-03 can be told apart from a real outage.
