# C5 — RAG architect

Scope: how domain and tenant knowledge reaches the model in the engine (paid-media-agent) as deployed by markting-ai, whether any retrieval exists, where retrieval would add value, and how it could be designed with tenant isolation. Audit only; nothing outside this file was modified.

**Short answer.** There is no vector store, no embedding, no index and no semantic retrieval anywhere in the repository (VERIFIED_CODE, §2 cmd 6). Knowledge reaches the model through exactly one mechanism: the Deep Agents `SkillsMiddleware` injects the *name + description* of the five `SKILL.md` files under `/skills/` into the system prompt, and the model pulls full pages on demand with `read_file`/`grep`/`glob` over a `FilesystemBackend` whose root is the whole engine checkout (VERIFIED_RUNTIME, §2 cmd 12). The corpus is ~3.6k words of generic, English-only paid-media doctrine and ~4.4k words of skills/instructions, byte-identical to upstream (§2 cmd 17). The only tenant-knowledge mechanism the engine supports — a `company-context` skill folder — is absent, Git-ignored and deployment-global, and the markting product has no code path that creates it per organization. The shared filesystem root is also the engine's largest isolation hole: in the markting host one process, one `FilesystemBackend` and one `ArtifactStore` serve every organization, and Deep Agents' default summarization middleware writes evicted chat history to that shared root where another thread's model can `ls` and `read_file` it (VERIFIED_RUNTIME for the mechanics, §2 cmd 14; end-to-end trigger not exercised).

## Findings

### C5-01 — Deep Agents summarization offloads evicted chat history into the shared filesystem root, readable by every other thread/organization
- Severity: **P0** (cross-tenant exposure by construction; latent in the default demo configuration — see preconditions)
- Classification: VERIFIED_RUNTIME (write/list/read mechanics, cmd 14) + VERIFIED_CODE (wiring) + INFERRED (end-to-end trigger across two real organizations was not exercised)
- Evidence:
  - `create_deep_agent` appends `create_summarization_middleware(model, backend)` unconditionally to the main stack: `engine/.venv/lib/python3.11/site-packages/deepagents/graph.py:886-889`; `compile_graph` passes no profile or exclusion: `engine/src/paid_media_agent/runtime/local.py:59-82`.
  - History path for a non-composite backend is `/conversation_history/{session_id}.md` on the same backend the model's file tools use: `deepagents/middleware/summarization.py:607-611, 689-700, 1214-1243`.
  - The write goes through `backend.write/edit` directly, not through the filesystem *tools*, and permissions are enforced only at tool level: `deepagents/graph.py:486-488` ("Direct backend usage does not currently incorporate [permissions]"). So the `deny write /**` rule in `local.py:46` does not stop it.
  - Read side: `filesystem_permissions()` denies reads only for `/.env*`, `/.venv`, `/.git`, `/.mda`, `/.agents`, `/.claude`, `/config`, `/workspace/sources`, `/docs/org` (`engine/src/paid_media_agent/runtime/local.py:30-44`); `/conversation_history/**` is readable and listable (`ls` filtering uses the same read rules: `deepagents/middleware/filesystem.py:759-766`).
  - One process, one backend root for all organizations in the markting host: `services/engine-demo/serve_demo.py:201-240` (one `compile_graph(components, project_root=root, …)`), `docker-compose.yml:34-55` (one `engine` container), `platform/apps/cloud/lib/markting/assistant.ts:30-43` (every org's turn goes to the same engine with the same token; isolation is by thread id prefix only), `platform/supabase/migrations/20261002000000_markting_bridge.sql:9-10` ("the engine owns threads by a single service caller").
  - Runtime probe (cmd 14) wrote `conversation_history/sess-A.md` under a temp root and read back `<message type="human">secret tenant A fact: target CPA 90 SAR</message>` via `backend.read`.
- Preconditions for actual leakage: `MARKTING_ENGINE_MODE=live` (a real model, `docker-compose.yml:50-51`; with the scripted demo model nothing summarizes), a thread long enough to cross the summarization threshold, and a model in another org's thread calling `ls /conversation_history/` then `read_file`. `docs/TODO.md:40` states live mode "has not been exercised". The session-id file names use full uuid4 entropy (`summarization.py:684-686`), but `ls` defeats that.
- Impact: verbatim user prompts and model answers of organization A become readable by organization B's agent. Users type real business facts into the Assistant even when platform data is fixture-only.
- Recommendation: give each thread (or at least each organization) its own backend root, e.g. a `CompositeBackend` whose `/conversation_history`, `/workspace` and `/large_tool_results` routes map to a per-thread `StateBackend` or a per-org directory derived server-side from the thread id; add a read-deny for `/conversation_history/**` and `/large_tool_results/**` as a belt-and-braces rule; add a contract test that thread B cannot `ls` or `read_file` thread A's history. Treat this together with C5-02.

### C5-02 — One shared `/workspace` and one `ArtifactStore` for every thread and organization; any thread can list, read and write what other threads produced
- Severity: **P1** (tenant-isolation design defect; today the content is fixture-only data and model-authored notes, so not an active leak of platform data)
- Classification: VERIFIED_CODE + VERIFIED_TEST
- Evidence: `RuntimeProfile.workspace_root`/`artifacts=ArtifactStore(root)` are built once per process from `project_root / settings.paid_media_workspace_root` (`engine/src/paid_media_agent/runtime/profiles.py:168-174`); `FilesystemBackend(root_dir=project_root)` (`runtime/local.py:78`); write is *allowed* for `/workspace/**` except `/workspace/skills/**` (`local.py:45-46`), proven by `tests/contract/test_read_path_graph.py` asserting `/workspace/note.txt` is written (cmd 13); artifact files are `workspace/analysis/<id>.json` and `workspace/out/<id>.json` with no thread or org dimension (`tools/artifacts.py:20-27, 63-67, 115-120`); artifact reads are not persisted or scoped in Postgres (cmd 16). The HTTP artifact endpoint *is* thread-scoped (`surfaces/api/app.py:150-165`, `surfaces/runner.py:95-120`), so this finding concerns the model's filesystem view, not the REST surface.
- Impact: (a) cross-thread/cross-org disclosure of `performance_rows`/`provider_result` payloads once live providers exist; (b) a shared, writable scratch space is a prompt-injection channel: a model in thread A can write `/workspace/notes.md` which thread B's model may read and follow. Artifact *integrity* is protected (sha256 check in `artifacts.py:138-146`), but confidentiality and injection are not.
- Recommendation: per-org (or per-thread) workspace roots and `ArtifactStore` instances selected from `configurable.thread_id`; forbid model writes outside a per-thread scratch dir; keep the cross-thread `ls` surface empty by construction.

### C5-03 — The only tenant-knowledge mechanism (`company-context`) is absent, Git-ignored, deployment-global, and the product has no path to populate it per organization
- Severity: **GAP** (documented as a capability; engine code supports it when present; product never creates it) — P2 business impact
- Classification: VERIFIED_CODE + VERIFIED_RUNTIME + DOCUMENTED_ONLY (the capability claim)
- Evidence: absent (cmd 1, cmd 12 "not found"); ignored (`engine/.gitignore:30`); the prompt and three skills defer goals/targets/conversions/naming to it (`engine/instructions.md:12-14`, `workspace/skills/paid-media-analysis/SKILL.md:11-12`, `paid-media-wiki/SKILL.md:31-35`); docs list it as a shipped capability (`engine/docs/architecture/capability-map.md:18`, `engine/workspace/README.md:8`, `engine/README.md:108-118`). It is one folder per deployment: compose mounts `./engine/workspace/skills:/app/skills:ro` for all orgs (`docker-compose.yml:55`), the image copies it (`engine/Dockerfile:15`). Loading works when present (`tests/contract/test_read_path_graph.py:55-95`, cmd 13). The platform stores only a per-org alias→account map with a `targets jsonb` that is a target-id map, not business targets (`platform/supabase/migrations/20261002000000_markting_bridge.sql:22-33`, `platform/apps/cloud/lib/markting/translate.ts:142`); nothing per-org is sent to the engine except the thread id and text (`assistant.ts:43`, `engine-client.ts:114-116`).
- Impact: every analysis is, by the wiki's own rule, "directional" (`goals-and-economics.md:32-36`), and the system cannot be given SAR currency, Gulf seasonality, margins, conversion definitions or naming conventions for a tenant without redeploying a shared folder — which would leak one tenant's context to all.
- Recommendation: make organization context a first-class, versioned, bilingual record owned by adport (Postgres, RLS by `organization_id`) and inject it per turn (see design options A/B). Until then, say in the UI that no business goals are configured.

### C5-04 — Offloaded tool results are not recoverable by the model: the stub omits the artifact path and no deterministic tool accepts `tool_result` artifacts
- Severity: **P2** (functional/reliability)
- Classification: VERIFIED_CODE
- Evidence: the stub carries `artifact_id, byte_size, sha256, preview, note` but not `path` (`engine/src/paid_media_agent/middleware/offload.py:45-52`) and tells the model to "Use the artifact id with deterministic tools"; the deterministic consumers reject anything that is not `performance_rows`/`provider_result`/`analysis` (`tools/summary.py:155-171`, `tools/compute.py` via `compare_periods`); `ArtifactStore.read` is not exposed as a tool (`assembly.py:57-74`). Only the host knows how to unwrap an offloaded `render_report` result (`surfaces/runner.py:110-116`). Neither `instructions.md` nor any skill tells the model that artifacts live at `/workspace/analysis/<id>.json`.
- Impact: a `discover_tools`, `list_accounts`, `discover_write_operations`, `propose_change` or `get_proposal` result above 6,000 characters (`config.py:137`) becomes a 400-char preview; the model must guess a path to continue. Live Pipeboard catalogs are large (`paid-media-analysis/SKILL.md:21`).
- Recommendation: include `path` (and `kind`) in the stub, exempt small-but-essential tools (`discover_*`, `list_accounts`, proposal tools) from offloading or raise their budget, and add a contract test that an offloaded `discover_tools` result is still actionable.

### C5-05 — Knowledge layer is generic, English-only, US-centric and unchanged from upstream; no Arabic, Gulf-market or Snapchat/TikTok content for an Arabic-first product
- Severity: **GAP** (P3 polish today; becomes P2 once real Gulf tenants are served)
- Classification: VERIFIED_CODE
- Evidence: cmd 9 (no Arabic), cmd 10 (no regional/Snap/TikTok playbooks; `platform-playbooks.md` covers Google, Meta, LinkedIn, X, Reddit, OpenAI only), cmd 11/17 (zero local edits), `DESIGN.md:29-34` (Inter/IBM Plex Mono fonts, `Aug 22-28, 2026` date format), `docs/TODO.md:38-39` (report template hard-codes `lang="en"`, DejaVu fonts). Yet the platform ships a Snapchat provider (`platform/packages/snapchat`, commit `53970f3`) and the product is "Arabic-first" (`README.md`).
- Impact: the model's doctrine ignores Ramadan/Eid/White Friday seasonality, SAR/AED, RTL creative constraints, Snapchat's dominance in KSA; answers will be English-flavoured even when the user writes Arabic; brand rules cannot be per tenant (one `DESIGN.md` + one `tokens.j2`, `DESIGN.md:16-18`).
- Recommendation: add a bilingual regional wiki layer (shared namespace), Snapchat/TikTok playbooks, and move brand rules to per-org data (design option A).

### C5-06 — Retrieval is lexical and model-driven only; nothing is indexed, ranked, cited or evaluated
- Severity: **GAP**
- Classification: VERIFIED_CODE + VERIFIED_RUNTIME
- Evidence: skills reach the prompt as name+description only (`deepagents/middleware/skills.py:866-884`, cmd 12); full pages require the model to call `read_file` (`skills.py:740-741`); `discover_tools` is substring-count scoring over name+description, top 8 (`tools/catalog.py:248-262`); platform-tool *selection* is either provider-native tool search or an LLM selector (`middleware/tool_selection.py:149-178`) — no embeddings; the eval harness grades only numeric figures, never whether the wiki/company context was consulted (`tests/eval/grade.py:55-90`); no MemoryMiddleware is compiled (`runtime/local.py:70-82` passes no `memory=`), and MDA memory is documented as off and deployment-global (`engine/docs/customization.md:118-131`).
- Impact: for a 3.6k-word wiki this is adequate — progressive disclosure is the right pattern at this size. It stops being adequate as soon as tenant corpora (past campaigns, creatives, decisions, product catalogs, platform docs) exist: there is no place to put them and no way to find them.

### C5-07 — Skill paths and labels shown to the model differ between local layout and the Docker image
- Severity: **P3**
- Classification: VERIFIED_RUNTIME + VERIFIED_CODE
- Evidence: locally the symlink `engine/skills -> workspace/skills` is resolved, so the system prompt advertises `/workspace/skills/<skill>/SKILL.md` (cmd 12) while every skill text hard-codes `/skills/...` (`paid-media-wiki/SKILL.md:9`, `paid-media-analysis/SKILL.md:11`); in the image `workspace/skills` is copied to `/app/skills` and no `/app/workspace/skills` exists (`engine/Dockerfile:15-17`), so the advertised path is `/skills/...`. The source label renders as "**Skills Skills**" because a bare `/skills/` source hits deepagents' documented duplicate-label case (`deepagents/middleware/skills.py:55-61`).
- Impact: both paths resolve locally, so no functional break was observed; it is prompt noise and a parity gap between test and production prompts.
- Recommendation: pass `skills=[("/skills/", "Paid media")]` and keep one canonical path.

## Design options with tenant isolation (not implemented)

Common ground rules for all options: the organization id is bound **server-side** from the thread id prefix (`org_<uuid>__u_<uuid>__…`, `assistant.ts:34-37`, `repository.ts:12-14`) or from a per-org engine token (`docs/TODO.md:41`), never taken as a model argument; retrieved text is data, wrapped and labelled, never instructions (the wiki already states this, `customization.md:50-52`); every retrieved chunk carries `source_id`, version and hash so "cite the source" (`instructions.md:17`) can be enforced; RLS by `organization_id` with a restrictive policy for browser roles, mirroring `markting_bridge.sql:70-95`.

**Option A — Structured context injection (no vectors; prerequisite for everything else).**
adport owns `markting_org_context(organization_id, version, locale, sections jsonb, brand jsonb, markets jsonb, updated_by, updated_at)`; an onboarding form (Arabic-first) fills business, measurement, goals (explicit `unknown` allowed), conventions, calendar (Ramadan/Eid/White Friday dates), currency/timezone, brand tokens. Per turn the cloud server renders it to Markdown and sends it with the message; the engine host mounts it at `/skills/company-context/` through a `CompositeBackend` route backed by a per-thread `StateBackend` (deepagents ships `backends/composite.py`, `backends/state.py`), so the SkillsMiddleware picks it up unchanged and nothing lands on shared disk. This also fixes C5-01/C5-02 if `/workspace`, `/conversation_history` and `/large_tool_results` are routed to the same per-thread state or to per-org directories. Cost: engine-host change only (`serve_demo.py`), no upstream fork of `engine/`.

**Option B — Org-scoped structured retrieval (Postgres, no embeddings).**
Tables per org: campaign history snapshots (from adport providers), proposals/receipts (join `pma_*` with `markting_engine_proposals`), findings, creative metadata, product catalog. Expose deterministic read tools in `core_tools` (`assembly.py:184-190`): `search_history(query, window)`, `list_past_changes(entity)`, `get_product_margins(skus)`. Postgres FTS with `simple` config plus Arabic normalisation (alef/ya/ta-marbuta/diacritics) — Postgres has no Arabic stemmer, so pair FTS with trigram (`pg_trgm`) for recall. Results are written as `provider_result` artifacts so `summarize_window`/`compare_periods` can consume them and the offload path stays consistent. Isolation: `WHERE organization_id = $org` injected by the host from the thread id; tests assert that a thread of org B never returns org A rows.

**Option C — Hybrid RAG for unstructured tenant corpora (brand books, creatives, decisions, product descriptions, platform docs).**
Enable `vector` in Supabase (not enabled today, cmd 18); `markting_knowledge_chunks(id, organization_id nullable for the global namespace, source_type, source_id, source_version, locale, chunk_text, chunk_tsv, embedding vector(N), metadata jsonb, content_hash)`; ingestion jobs per source type with chunking that respects RTL/Arabic punctuation; a multilingual embedding model (Arabic-capable) chosen through the existing provider abstraction (`init_chat_model` has no embeddings path today — a separate, host-owned client is needed; never from skills). Query: hybrid FTS + ANN, filtered `organization_id IN (NULL, $org)`, reranked, top-k with per-source caps; return as an artifact with citations; the engine tool `search_knowledge(query, kinds, locale)` is `always_include`d like `discover_tools`. Namespaces: `global` (doctrine, platform docs, regional playbooks) and `org:<id>`. Guardrails: budget per turn, no raw Pipeboard rows in the index, PII scrub for creatives, versioned snapshots so an answer can be reproduced.

**What not to do:** do not index the 3.6k-word wiki; do not pass `organization_id` as a tool argument; do not populate the shared `workspace/skills/company-context/` with any real tenant's data; do not enable MDA `define_memory(scope="agent")` for a multi-tenant deployment (`customization.md:123-131` warns it is shared by every caller).

## What a world-class system would need (gaps, concrete)

1. Per-tenant, per-turn business context as a typed, versioned, bilingual record (Option A) with "unknown" first-class and surfaced in every answer when goals are missing.
2. Hard tenant isolation of the model's filesystem view: per-thread/per-org backend roots, no shared `/workspace`, `/conversation_history`, `/large_tool_results`; contract tests for cross-thread `ls`/`read_file`.
3. Regional and Arabic knowledge layer: Gulf calendar, SAR/AED, Snapchat and TikTok playbooks, Arabic answer-style page, RTL creative constraints; Arabic report template and fonts (`docs/TODO.md:38`).
4. Org-scoped history tools (Option B): past changes with outcomes, creative fatigue history, product margins — the inputs a media buyer actually reasons from.
5. Hybrid retrieval with citations for unstructured corpora (Option C), with freshness/versioning and an ingestion audit.
6. Offload that preserves actionability: path + kind in the stub, `read_artifact` deterministic tool, budgets per tool.
7. Knowledge-use evaluation: extend `tests/eval/questions.json` with questions that are only answerable from company context / history, and grade for citation and for refusing to invent targets.
8. Injection hygiene for retrieved text (wrap, label, strip imperative content) and a red-team test suite for cross-tenant and skill-override attempts.
