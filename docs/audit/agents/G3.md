## Findings

### G3-01 — Browser tab titles and meta description are English-only on every page
- Severity: P3 · Classification: VERIFIED_CODE
- Evidence: `platform/apps/cloud/app/layout.tsx:11-14` (`title: { default: 'Adport', template: '%s · Adport' }`, English `description`); static `export const metadata = { title: 'Approvals' }` etc. in `app/dashboard/approvals/page.tsx:8`, `app/dashboard/billing/page.tsx:13` (`'Plan'`), `app/dashboard/agents/page.tsx:8`, `app/login/page.tsx:6`, `app/onboarding/page.tsx:13`, `app/account-selection/page.tsx:12`, `app/oauth/provider-complete/page.tsx:4` and the other 10 dashboard pages (17 total).
- Description: Next.js static `metadata` objects cannot read the locale cookie, so an Arabic session shows "Approvals · Adport", "Plan · Adport" in the tab, history and bookmarks. Nothing in the catalogue is wired to `generateMetadata`.
- Impact: First-impression inconsistency for an "Arabic-first" product; screen readers announce English document titles.
- Recommendation (do not apply): replace each static object with `generateMetadata()` that calls `getT()` and returns `t('<area>.title')`; translate the root `description`.

### G3-02 — Arabic labels are set in a monospace stack with no Arabic face, uppercase and positive tracking
- Severity: P3 · Classification: VERIFIED_CODE + VERIFIED_RUNTIME
- Evidence: `--font-mono: ui-monospace, SFMono-Regular, Menlo, Monaco, Consolas, monospace` (`app/globals.css:21`) is applied with `text-transform: uppercase` and `letter-spacing: 0.06em–0.14em` to table headers `th` (l.233, 240), `.metric-label` (l.162), `.nav-label` (l.101), `.workspace-label` (l.117), `.plan-kicker` (l.200), `.policy-overview span` (l.343), `.field > span, .field-label` (l.535), `.connection-meta dt` (l.291), `.connection-list-heading` (l.296), `.upgrade-plan-line span` (l.386), `.auth-divider` (l.588), `.agent-panel-title p` (l.635); `.card-note` (l.180) and `.cell-sub` (l.241) are mono too. Runtime: `rtl-_dashboard_reports.png` shows the column headers التقرير/الفترة/المنصات/الملفات and the note "مقارنة فترات حتمية…" in a fallback monospace Arabic with visibly spaced letters; `rtl-_dashboard_policies.png` shows the kickers حارس الموافقة / حدود الميزانية the same way.
- Description: None of the mono fonts carry Arabic glyphs, so Arabic falls through to the OS monospace fallback (DejaVu Sans Mono in the container, Courier-like on macOS/Windows). Positive letter-spacing inserts gaps between joined Arabic letters, which is typographically wrong for a connected script; `text-transform: uppercase` is a no-op for Arabic but signals the rule was never reviewed for RTL.
- Impact: Every table header, metric label, form label and kicker in the Arabic UI looks lower quality than body copy; a Saudi media buyer will read it as "translated, not designed".
- Recommendation: under `html[lang="ar"]`, set these selectors to `font-family: var(--font-sans); letter-spacing: 0; text-transform: none;` and, if a mono look is wanted for ids/dates only, scope mono to `[dir="ltr"]`/numeric spans. Consider adding an Arabic-capable mono (IBM Plex Mono has no Arabic; use Plex Sans Arabic for labels).

### G3-03 — Negative letter-spacing on headings applies to Arabic
- Severity: P3 · Classification: VERIFIED_CODE
- Evidence: 25 declarations such as `h1 … letter-spacing: -0.04em` (`app/globals.css:129`), `h2 -0.015em` (l.130), `.plan-price strong -0.055em` (l.216), `.onboarding-hero h1 -0.055em` (l.417), `.upgrade-modal h2 -0.04em` (l.380), `.workspace-name -0.02em` (l.118); the RTL block (l.712-725) contains no reset.
- Description: Negative tracking tightens Latin display type but pulls Arabic glyph joins and marks (شدّة، تنوين) into each other. Screenshots render acceptably at 1280px because IBM Plex Sans Arabic is robust, but the rule is wrong by design for Arabic and is the first thing a native typographer will flag.
- Recommendation: `html[lang="ar"] :is(h1,h2,h3,.plan-price strong,.onboarding-hero h1,…) { letter-spacing: 0 }`.

### G3-04 — Physical-direction CSS remains; billing checkmarks overlap text in RTL
- Severity: P3 · Classification: VERIFIED_CODE + VERIFIED_RUNTIME
- Evidence: `.plan-features li { padding: 0.68rem 0 0.68rem 1.15rem }` (physical left padding, `app/globals.css:221`) while `.plan-features li::before { inset-inline-start: 0; content: "✓" }` (l.222) places the mark at the inline start (right in RTL). `rtl-_dashboard_billing.png` shows "✓" colliding with the first word of each feature line ("✓5 حسابات…", "✓سجل تدقيق…"). Other physical leftovers: `.policy-indent { margin: 0.25rem 0 0 1.55rem }` (l.355, indent on the wrong side; used by `app/dashboard/policies/policy-form.tsx:83`), `.upgrade-modal h2 { margin: 0.55rem 2rem 0.55rem 0 }` (l.380) reserving space on the right while `.modal-close` sits at `inset-inline-end` (l.382, i.e. the left in RTL), `.link-button { padding: 0.2rem 0.2rem 0.2rem 0 }` (l.107), `.agent-tab { padding: … 0.65rem 0.35rem 0.4rem }` (l.620), `select { padding: 0.5rem 2.1rem 0.5rem 0.95rem; background-position: right 0.85rem center }` (l.319; chevron rendered at the inline-start in `rtl-_dashboard_team.png`).
- Description: `docs/PHASE2-REPORT.md:13` claims "All 32 physical direction declarations converted to logical properties". Five 4-value shorthands and one `background-position: right` survive; one of them produces a visible overlap on the pricing page.
- Recommendation: `padding-inline-start: 1.15rem` on `.plan-features li`; `margin-inline-start` on `.policy-indent`; `margin-inline-end` on `.upgrade-modal h2`; `padding-inline` on `.link-button`/`.agent-tab`; `background-position: inline-end 0.85rem center` (or an `html[dir=rtl] select` override) for the chevron.

### G3-05 — `unicode-bidi: plaintext` on mixed lines reorders Arabic fragments and truncates names from the wrong side
- Severity: P3 · Classification: VERIFIED_CODE + VERIFIED_RUNTIME
- Evidence: `.cell-sub, .card-note, .metric-value, .status { unicode-bidi: plaintext }` (`app/globals.css:719`); `.workspace-name, .user-name, .user-sub { unicode-bidi: plaintext }` (l.725) combined with `text-overflow: ellipsis` (l.118). Lines whose first strong character is Latin: `app/dashboard/reports/engine-reports.tsx:68` (`<strong>{platform.platform}</strong> · {t('reports.platformLine', …)}`), `app/dashboard/agents/api-key-manager.tsx:79` (`{grant.scopes.join(', ')} · …`) and `:89` (`{key.keyPrefix}… · …`). Runtime: `rtl-_dashboard_reports.png` renders "google_ads · 5,467.89 USD الإنفاق (-13.3%) · CPA 26.04" — the Arabic label الإنفاق lands after its number; every screenshot shows the sidebar org name as "...o Media Buyer's organization" (ellipsis at the left, start of the English name cut).
- Description: `plaintext` makes each block pick its base direction from its first strong character. That is right for chat text and code, but for template strings the first token is often a platform id, key prefix or scope list, so Arabic sentences are laid out LTR. For the org/user name it flips the overflow side.
- Impact: The engine-report summary (a core media-buyer artefact) reads scrambled in Arabic; the workspace name is unreadable when truncated.
- Recommendation: drop `plaintext` from `.cell-sub`/`.workspace-name`; wrap Latin tokens in `<bdi>` or `<span dir="ltr">`; put the Arabic label first in `reports.platformLine` ("{platform} · الإنفاق {spend} …") or render platform ids in their own `dir="ltr"` span.

### G3-06 — Timestamps are UTC with a hard-coded Latin suffix, and two components format dates differently
- Severity: P2 · Classification: VERIFIED_CODE + VERIFIED_RUNTIME
- Evidence: `formatDate` uses `timeZone: 'UTC'` and appends `' UTC'` (`platform/apps/cloud/components/ui.tsx:71-74`); it is used for approval expiry (`app/dashboard/approvals/page.tsx:39`), audit times (`app/dashboard/audit/page.tsx:30`), findings (`findings/page.tsx:33`), credentials (`agents/api-key-manager.tsx:79,89`), last-verified (`connections/provider-connections.tsx:75`). `common.utc` (`messages/common.ts:187`) exists but is never referenced (`rg "common.utc"` → no hits). Two client components bypass it with `new Date(...).toLocaleString('ar-u-nu-latn')` (browser timezone, different pattern): `app/dashboard/assistant/assistant-chat.tsx:111`, `app/dashboard/reports/engine-reports.tsx:63`. Runtime: `rtl-_dashboard_reports.png` shows "2026/10/2 12:49:03 م" while `formatDate` pages show "2 أكتوبر 2026، 12:49 UTC"-style values.
- Description: The target user is in Asia/Riyadh (UTC+3). A pending budget change whose "تنتهي" column says 14:00 UTC actually expires at 17:00 local; the same run shows two different date styles and timezones on two pages. `toLocaleString` in a client component also renders on the server first (UTC) and again in the browser (local), which React reports as a hydration text mismatch.
- Impact: Misreading expiry windows on approvals is a functional deficiency for the approval workflow; inconsistency erodes trust in the audit trail. Not a security or money-loss issue, hence P2 not P1.
- Recommendation: format in the organization's/user's timezone (store a tz preference; default `Asia/Riyadh` for `ar`), use `timeZoneName: 'short'` instead of a literal suffix, route the two inline calls through `formatDate`, and compute formatted strings client-side only after mount (or pass pre-formatted strings from the server).

### G3-08 — Grammar, agreement and register defects in the Arabic catalogue
- Severity: P3 · Classification: VERIFIED_CODE (grammar judged by the auditor)
- Evidence and corrections (file:line → issue → suggested text):
  - `reports.ts:55` `'آخر 30 يومًا · {rows} صفًا'` → "{rows} صفًا" is only correct for 11–99; 1→"صف واحد", 2→"صفان", 3–10→"صفوف", 100+→"صف". `test/i18n.test.ts:76` only asserts the digit is present. Make it a plural key (`rows_zero…rows_other`) like `overview.operations`.
  - `assistant.ts:380` `'أي حملة ارتفعت فيها CPA أكثر؟'` → CPA is read as تكلفة (feminine) but the verb form is ambiguous; preferred: "في أي حملة ارتفعت تكلفة الاكتساب (CPA) أكثر؟" (keeps the ad term, satisfies the test).
  - `assistant.ts:390` `'تعديلات إلزامية: {list}'` for "Coercions" → "coercions" are value normalisations applied by the policy engine (`lib/markting/bridge.ts:17`); "إلزامية" (mandatory) misleads. Suggest "تعديلات تلقائية على القيم: {list}".
  - `approvals.ts:271` → "نداء التنفيذ الثاني المطابق تمامًا … مرتبط ببصمة وسائطه" is a literal rendering of "exact second call / hash-bound to its arguments"; no Saudi buyer speaks this way. Suggest: "تغييرات تمت معاينتها وتنتظر تأكيد التنفيذ. كل عملية مرتبطة ببصمة (hash) لبياناتها وتنتهي صلاحيتها وفق سياسة المؤسسة. «تنفيذ» يُرسل التغيير نفسه عبر محرك السياسات، و«رفض» يلغي المعاينة."

  - `billing.ts:95` `'الأفضل قيمة'` → "الأفضل قيمةً" or simply "الأكثر قيمة".
  - `billing.ts:98` `'/ شهريًا'` after "€19" → "€19 / شهريًا" is acceptable, but with EUR; see G3-10.
  - `support.ts:105` `'مساحة العمل مُتقاعدة'` → "retired" calqued; use "تم إيقاف مساحة العمل".
  - `support.ts:60,67` first-person "بريدي / أقرأ كل رسالة" with `talkTo: 'تحدّث مع Yannick'` → upstream founder voice; replace with the product's support identity.
  - `accounts.ts:98-99` `'{active} / {max} نشط'` → the adjective should agree: "{active} من {max} نشطة" (حسابات نشطة).
  - `misc.ts:83` says المنصات where the English says "provider"; align with المزوّد or (preferably) migrate everything to المنصة (see glossary).
  - `connections.ts:70` `working: 'جارٍ التنفيذ…'` → "جارٍ المعالجة…".
  - `audit.ts:59` `'مرفوض'` → "تم الرفض" for parallelism.

## What a world-class system would need (gaps, concrete)

1. Locale-aware `generateMetadata` on every route and an Arabic root description (G3-01).
2. An `html[lang="ar"]` typography layer: Plex Sans Arabic for all labels, `letter-spacing: 0`, no uppercase tricks, Arabic-safe mono only for ids/dates inside `dir="ltr"` spans (G3-02/03).
3. Finish the logical-property migration and add a stylelint rule (`plugin/use-logical-properties`) to CI so the count of physical declarations stays zero (G3-04).
4. Replace blanket `unicode-bidi: plaintext` with `<bdi>`/`dir="ltr"` on the Latin tokens; put Arabic labels first in mixed templates (G3-05).
5. Timezone-aware formatting with an org-level `Asia/Riyadh` default, one formatter path, no SSR/CSR drift; optional Hijri secondary date on reports (G3-06).
6. A shipped glossary (`docs/glossary-ar.md`) plus a vitest that fails on rejected variants; a review pass by a native Saudi media buyer (TODO.md:32 already lists this) (G3-07/08).
7. Engine language control: forward `locale`, Arabic system-prompt clause, Markdown rendering, Arabic refusal/coercion codes mapped through the catalogue, Arabic report templates with an Arabic font in the engine image (G3-09).
8. SAR pricing with VAT, `locale: 'ar'` on Stripe Checkout, SAR-first sandbox fixtures and KSA campaign naming in the demo (G3-10).
9. Accessibility in RTL: `aria-label`s are translated (good); add `lang="en"` on Latin-only spans (emails, ids, `codex mcp login adport`) so screen readers switch voice.
10. Visual regression tests for RTL (the existing `e2e-rtl.mjs` only checks `dir`, fonts and "English sentences"; it would not catch G3-04/05).
