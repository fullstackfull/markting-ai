## Findings

### B6-01 — No customer lifetime value (LTV) anywhere in either tree
- Severity: GAP · Classification: VERIFIED_CODE
- Evidence: `platform/packages/core/src/model.ts:1-12` (METRICS = spend, impressions, clicks, conversions, conversion_value, ctr, cpc, cpm, cpa, roas); `engine/src/paid_media_agent/domain/metrics.py:49-67` (`PerformanceRow` carries only spend/impressions/clicks/conversions/conversion_value + opaque account/entity refs); `engine/src/paid_media_agent/domain/analysis.py:16-27`. Grep for `ltv|lifetime value` returns zero src hits in both trees.
- Description: There is no concept of a customer, a customer identity, or value accrued across repeat transactions. The only "value" is `conversion_value`, a single-window, ad-platform-attributed number, never tied to a persistent customer.
- Impact: The system cannot compute LTV, LTV:CAC, or value-based bidding inputs. It optimizes first-touch attributed conversion value, which can diverge sharply from true customer worth.
- Recommendation: GAP, not a defect — nothing in code claims LTV. See data-requirements design below.

### B6-02 — No customer acquisition cost (CAC); CPA is cost-per-conversion, not CAC
- Severity: GAP · Classification: VERIFIED_CODE
- Evidence: `engine/src/paid_media_agent/tools/compute.py:91` (`cpa=_ratio(spend, conversions)`) and `:294`; `engine/src/paid_media_agent/reports/render.py:38` (`"cpa": "spend / conversions"`). `conversions` is a platform-attributed `Decimal` count (`metrics.py:64`) with no new-vs-returning split and no customer identity.
- Description: CPA divides spend by attributed conversions of any kind. CAC (spend per newly acquired *customer*) requires deduplicating to unique new customers, which needs identity the system never ingests. The two are conflated.
- Impact: A buyer reading "CPA" may mistake it for CAC; repeat-buyer conversions deflate apparent acquisition cost. No marginal CAC (cost of the next customer) is derivable either.
- Recommendation: GAP. Keep CPA labeled as cost-per-conversion; CAC requires store/CRM new-customer data (design below).

### B6-03 — No payback, cohort, or repeat-purchase analysis
- Severity: GAP · Classification: VERIFIED_CODE
- Evidence: `engine/src/paid_media_agent/tools/compute.py:71-375` exposes only `aggregate`, `deltas`, `compare_platform`, `compare_periods`, `summarize` — windowed period-over-period comparison of the metric set. No per-customer first-order date, no acquisition cohort, no repeat/retention curve. Grep `cohort|payback|repeat purchase` => zero src hits.
- Description: Analysis is entity×window aggregation only. There is no customer-time dimension, so payback horizon (months to recover CAC), cohort retention, and repeat-purchase rate cannot be produced.
- Impact: No answer to "when does this spend pay back" or "are these cheap conversions one-time buyers". Core subscription/e-commerce economics are absent.
- Recommendation: GAP. Requires an order/customer timeline source (design below).

### B6-04 — No store / CRM / e-commerce / warehouse integration feeding customer economics
- Severity: GAP · Classification: VERIFIED_CODE
- Evidence: `rg` for shopify/stripe/woocommerce/salesforce/hubspot/crm/bigquery/snowflake/first-party/customer_match/offline_conversion over `platform/packages`, `engine/src`, `services`, `infra` returns no implementation. `platform/apps/cloud/lib/markting/**` has zero economics terms. `engine/docs/customization.md:157-175` states warehouses/dbt/CRM are "optional extensions. This project does not include a warehouse connector or assume your company's schema." The only `customer_list` reference is a write-name risk flag (`engine/src/paid_media_agent/tools/writes.py:115`), not an ingest path.
- Description: Every revenue figure in the system is the platform's self-reported attributed `conversion_value`. There is no verified-revenue source and no customer master, so customer-level economics have no data to stand on.
- Impact: LTV/CAC/payback/cohorts are not implementable with current inputs; the platform is structurally limited to platform-attributed ROAS/CPA.
- Recommendation: GAP. Build read-only store/CRM connectors per the design below; this matches the stated intent in `docs/TODO.md:14-16`.

### B6-05 — Economics doctrine exists only as free-text LLM guidance; margin / allowable CAC never reaches code
- Severity: GAP · Classification: DOCUMENTED_ONLY
- Evidence: `engine/workspace/skills/paid-media-wiki/goals-and-economics.md:17-30` lists "gross margin or allowable acquisition cost when supplied", "marginal budget", and "sales or purchase lag" as economic questions the agent should ask, and warns "Average historical ROAS or CPA does not equal the return on the next dollar" (:29). No structured field for margin, allowable CAC, or payback window exists in any model (`metrics.py`, `analysis.py`, `model.ts`); it is advisory prose fed to the model, with "when supplied" never wired to a data path.
- Description: The product doctrine correctly names marginal economics and allowable CAC, but there is no deterministic computation or input schema behind it. Any such number the assistant states would be model-generated narrative, not computed.
- Impact: Risk of plausible-sounding but unbacked economic claims from the LLM; the determinism guarantee ("Every number here is computed by code" — `analysis.py:1`) does not cover LTV/CAC/payback because those are absent from the compute layer.
- Recommendation: When implemented, add a structured company-context entity (margin %, allowable CAC, payback horizon) that flows into a deterministic profit/CAC compute, keeping the model out of the arithmetic.

### B6-06 — "Break-even ROAS" rule is a naive ROAS < 1, margin-blind
- Severity: P3 · Classification: VERIFIED_CODE
- Evidence: `platform/packages/core/src/audit/packs/core-performance.ts:76-99` — `negativeRoas` rule flags campaigns where `roas < 1`, titled "(below break-even)"; recommendation text says "Check margins" but no margin is an input. `platform/website/index.html:330` surfaces "ROAS 0.8×, below break-even" as a marketing example.
- Description: True break-even ROAS is `1 / contribution-margin` (e.g. 40% margin → break-even ROAS 2.5). Hard-coding break-even at ROAS = 1 treats revenue as 100% profit, so it only catches campaigns losing money on *gross revenue*, missing the much larger band of campaigns above 1.0 but below margin-adjusted break-even.
- Impact: A buyer trusting the "below break-even" label underestimates losses; margin-negative-but-ROAS>1 campaigns are never flagged. Low severity because the rule is advisory, labeled, and routes to human review.
- Recommendation: Parameterize break-even by a configured contribution margin once a company-context entity exists; until then keep the label explicitly "gross ROAS < 1", not "break-even".

## What a world-class system would need (data-requirements design, not implemented)
1. **Customer/order ingest (read-only).** Store connectors (Salla/Zid/Shopify/WooCommerce) and/or a payments source (Stripe) exposing orders with: stable `customer_ref` (hashed), order timestamp, gross amount, currency, refund/cancellation status, and a new-vs-returning flag derived from first-order date. Engine-side `get_store_orders`/`get_store_customers` tools returning bounded aggregates with source metadata and trust level; never any write to the store. Mirrors `docs/TODO.md:14-16` and `customization.md:157-175`.
2. **Customer master / identity.** A deduplicated customer dimension with first-acquisition date and acquisition channel (where resolvable), so "new customer" is well-defined and CAC = spend ÷ new customers acquired in-window (with an explicit attribution definition).
3. **Company-context entity (structured, versioned).** Contribution margin per product line, allowable CAC, target LTV:CAC, payback horizon, VAT/COGS handling, sales/purchase lag. This replaces the "when supplied" prose (`goals-and-economics.md:24`) with typed fields feeding compute.
4. **Deterministic LTV/CAC compute layer** (beside `compute.py`, same invariants: None-never-zero, equal windows, completeness flags, currency-match-or-suppress): acquisition cohorts keyed on first-order month; cumulative revenue/contribution per cohort over age; CAC per cohort = channel spend ÷ cohort size; payback = first cohort age where cumulative contribution ≥ CAC; predicted LTV with a stated model (historical cumulative or a labeled parametric estimate) and confidence; marginal CAC from incrementality/spend-step data, not average. Keep attributed platform ROAS side-by-side with store-verified figures, never conflated.
5. **Trust tiers.** Attributed-only (T0) → store-verified revenue (T1) → customer-identity-resolved LTV/CAC (T2). The UI and policy engine must label which tier any economic figure rests on, and the assistant must never imply a store/CRM is connected until a configured read succeeds (`customization.md:175`).

## Disagreements / claims in docs that the code contradicts
- `README.md:14,83` claims only spend/conversions/CPA/ROAS — accurate; no LTV/CAC overclaim. `platform/website/index.html:330` shows only a ROAS-below-break-even example — no overclaim. So there is no README/marketing contradiction: the GAPs are honestly scoped.
- `engine/workspace/skills/paid-media-wiki/goals-and-economics.md:24` implies allowable acquisition cost and margin are usable "when supplied"; the code has no field or path to supply them (B6-05). This is a doctrine-vs-implementation gap, not a false public claim.
- `engine/src/paid_media_agent/domain/analysis.py:1` asserts "Every number here is computed by code, never by the model" — true for the metrics present, but it does not extend to LTV/CAC/payback, which are absent; any such figure would necessarily be model narrative. Worth stating explicitly so the guarantee is not over-read.
