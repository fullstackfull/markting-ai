## Findings

### I4-01 — Enterprise plan has no self-serve or automated provisioning path; only a manual DB write can grant it
- Severity: P1 · Classification: VERIFIED_CODE
- Evidence: `platform/apps/cloud/lib/cloud/billing.ts:38-45` (`planForPrice` maps only operator/premium/agency), `billing.ts:76` (`appliedPlan = plan ?? 'reader'` and `:72` throws "not mapped" for any unknown price); `platform/apps/cloud/app/dashboard/billing/page.tsx:15` (`PLAN_ORDER` excludes `enterprise`); `billing/page.tsx:119` enterprise CTA is a `mailto:`.
- Description: The enterprise tier exists in `PLANS` (`plans.ts:40-43`) but there is no Stripe price, no checkout, and no admin UI. Setting an org to `enterprise` requires a direct `update public.organization_subscriptions set plan='enterprise'` by a DBA. Any Stripe price that mapped to enterprise would be rejected by `planForPrice`.
- Impact: Closing an enterprise deal requires out-of-band manual database surgery per customer; no audit trail, no billing automation, no renewal/cancel lifecycle for the highest-value tier.
- Recommendation: Add an enterprise provisioning path (custom Stripe price / invoice billing mapped in `planForPrice`, or an internal admin console) with the same audit + lifecycle handling as other tiers.

### I4-02 — Advertised Enterprise features (SSO, regional hosting, SLA, dedicated onboarding) are not implemented; only custom retention exists
- Severity: P1 · Classification: VERIFIED_CODE
- Evidence: `platform/apps/cloud/lib/i18n/messages/billing.ts:58` ("Includes SSO, regional hosting, custom retention, SLA, and dedicated onboarding"); `platform/apps/cloud/app/login/actions.ts:8` (`socialProviders = new Set(['google','github'])`, password-only otherwise); `platform/supabase/config.toml:351` (`# tenant_region` commented out); no SLA/escalation logic anywhere. Only `maxRetentionDays: 3650` (`plans.ts:42`) is real and enforced (`tenant-admin.ts:174`, pg_cron).
- Description: Four of the five sold enterprise differentiators have no implementation. This is a sold-vs-shipped contradiction, not merely a missing feature.
- Impact: Mis-selling risk and procurement failure: an enterprise or Gulf agency that buys on these promises cannot be delivered SSO, data residency, or a contractual SLA.
- Recommendation: Either implement each gated behind the enterprise entitlement, or remove the claims from `billing.ts` until shipped.

### I4-03 — All enterprise, legal, and support surfaces route to the upstream third party (Yannick / Adport), not to markting-ai
- Severity: P1 · Classification: VERIFIED_CODE / DOCUMENTED_ONLY
- Evidence: `platform/apps/cloud/app/dashboard/billing/page.tsx:119` (`mailto:yannick@adport.dev`); `platform/apps/cloud/lib/i18n/messages/support.ts:10,14,15` ("Yannick from Adport", "Talk to Yannick"); `platform/website/privacy.html` ("operated by Yannick Westermann, trading as Yannick Westermann Labs", contact `yannick@adport.dev`); `terms.html` likewise Adport-branded.
- Description: The enterprise "Talk to" CTA, the in-app support widget, the privacy policy, and the terms all name the upstream vendor as the operating legal entity and the sole support contact. There is no markting-ai legal entity, support channel, or Arabic-market contact anywhere in the enterprise/legal surface.
- Impact: markting-ai cannot contract with an enterprise under its own name: the data controller/processor in the published privacy policy is a third party, support escalations go to one external person's inbox, and the enterprise sales lead is handed to the upstream author. Hard blocker for selling to a large Gulf agency with legal/procurement review.
- Recommendation: Replace operator identity, contact addresses, support routing, and legal documents with markting-ai's own entity; sign a flow-down agreement with the upstream vendor if infrastructure is shared.

### I4-04 — No audit export and the audit UI is capped at the most recent 150 events, despite selling up to 3650-day retention
- Severity: P2 · Classification: VERIFIED_CODE
- Evidence: `platform/apps/cloud/app/dashboard/audit/page.tsx:14` (`listAuditEvents(tenant.organizationId, 150)`), no export control in the page; `platform/apps/cloud/lib/cloud/repository.ts:719` (`listAuditEvents` is `order by created_at desc limit`); no `audit`/export route under `platform/apps/cloud/app/api/`.
- Description: Events are retained up to the configured period (purged daily by `apply_data_retention`) but the only way to view them is the last 150 rows in the dashboard. There is no pagination, date filter, search, or CSV/JSON export, and no API endpoint to pull the log.
- Impact: Compliance/audit teams cannot retrieve, filter, or export the audit history they are paying to retain; the "custom retention" value proposition is unrealizable in practice.
- Recommendation: Add a paginated/filterable audit view and an authenticated export endpoint (CSV/JSON, streamed), gated to admins.

### I4-05 — No data-residency control; privacy policy explicitly states international processing, contradicting the "regional hosting" claim
- Severity: P2 · Classification: VERIFIED_CODE / DOCUMENTED_ONLY
- Evidence: `platform/website/privacy.html` ("International processing … may process information in countries other than the user's country"); `platform/supabase/config.toml:351` (`# tenant_region` commented, default us); no region/residency selection in onboarding or settings (grep: no `residency`/`region` product code outside commented config).
- Description: The product runs against a single Supabase project whose region is fixed at project creation, outside the codebase. There is no per-tenant region, no EU/ME residency option, and the published policy affirmatively allows cross-border processing.
- Impact: A Gulf agency or regulated enterprise with KSA/UAE data-residency requirements cannot be served or contracted; directly contradicts the sold "regional hosting".
- Recommendation: Offer region-pinned deployments (separate Supabase projects per region) and a residency commitment in the DPA; stop advertising regional hosting until available.

### I4-06 — No enterprise SSO (SAML/OIDC) and no SCIM provisioning/deprovisioning
- Severity: P2 · Classification: VERIFIED_CODE
- Evidence: `platform/apps/cloud/app/login/actions.ts:8,23-33` (password + google/github social only); `find platform -type d -iname "*scim*"` → none; membership is manual invite only (`tenant-admin.ts`).
- Description: Authentication is consumer-grade. Enterprises cannot enforce central identity, cannot auto-provision/deprovision via SCIM, and have no domain auto-join.
- Impact: Standard enterprise identity/offboarding requirements are unmet — a common procurement gate.
- Recommendation: Add SAML/OIDC SSO and SCIM, gated to the enterprise entitlement.

### I4-07 — MFA is disabled in the committed Supabase config
- Severity: P3 · Classification: DOCUMENTED_ONLY
- Evidence: `platform/supabase/config.toml:303` (`[auth.mfa.totp] enroll_enabled = false`), `:308` (`[auth.mfa.phone] enroll_enabled = false`).
- Description: No MFA factor is enrollable in the committed configuration. The hosted production project may override this, which is not verifiable from the repo.
- Impact: Without MFA, enterprise security reviews fail; a security-sensitive apply/delete flow has no step-up auth.
- Recommendation: Enable TOTP/WebAuthn, enforce MFA for admin/owner roles and confirm the production project matches.

### I4-08 — No DPA or subprocessor register; legal docs are upstream-branded and listed as unmet production gates
- Severity: P2 · Classification: DOCUMENTED_ONLY
- Evidence: `platform/docs/deployment-model.md:55` ("the published privacy policy, terms, deletion path, and subprocessor records" listed as a *still-required* production gate); only `platform/website/privacy.html` + `terms.html` exist (Adport-branded, see I4-03); no DPA file (`find -iname "*dpa*"` → none).
- Description: Enterprise contracting needs a Data Processing Agreement, a subprocessor list, and SCCs. None exist; the repo's own deployment doc flags them as not yet done.
- Impact: No legal paperwork to complete an enterprise/agency procurement.
- Recommendation: Produce markting-ai DPA, subprocessor register (Supabase, Stripe, model/provider vendors), and SCCs.

### I4-09 — The combined self-host/on-prem story ships the engine in demo (proposal-only, sample-data) mode; no production self-host of the cloud control plane
- Severity: P3 (GAP) · Classification: VERIFIED_CODE
- Evidence: `docker-compose.yml:41-48` (engine command `serve_demo.py`, `PAID_MEDIA_DATA_MODE: sample`, `PAID_MEDIA_WRITES_ENABLED: "false"`); `platform/docs/deployment-model.md:3` ("intended to be run and verified locally before a production deployment"). `engine/docs/self-hosting.md` is the upstream engine-only guide and does not cover the platform/cloud app.
- Description: The repository-level self-host (compose) is a local demo: writes disabled, sample data, Supabase not even containerized. There is no production on-prem packaging for the markting cloud control plane as a unit.
- Impact: An enterprise wanting on-prem/VPC deployment has only a demo stack; the self-host story must be built.
- Recommendation: Provide a production self-host reference (Supabase self-host or managed Postgres, real engine mode, secrets/KMS) if on-prem is to be sold.

### I4-10 — API/MCP access is not an enterprise differentiator and has no per-plan limit
- Severity: P3 (GAP) · Classification: VERIFIED_CODE
- Evidence: `platform/apps/cloud/lib/cloud/repository.ts:292` (`createApiKey` has no plan gate / key-count cap); hosted MCP + REST available to all tiers (`deployment-model.md:32`). No enterprise-only API/MCP capability.
- Description: API and MCP work across plans (functionally strong), but there is no enterprise-specific API tier, quota, or SLA, and no per-plan key limits.
- Impact: Minor — "enterprise API access" cannot be sold as a distinct capability; also no abuse ceiling per org (see other workstreams on rate limiting).
- Recommendation: Define enterprise API entitlements (quotas, dedicated throughput) if used as a selling point.

## What a world-class system would need
- Self-serve/invoice enterprise provisioning with lifecycle + audit; an internal admin console to assign enterprise.
- SAML + OIDC SSO, SCIM provisioning/deprovisioning, domain auto-join, enforced MFA with step-up on apply/delete.
- Region-pinned deployments (EU, ME-Central) with a contractual residency commitment.
- Paginated/filterable audit view + streamed signed export (CSV/JSON) and a log-retrieval API; tamper-evident audit.
- markting-ai-owned legal stack: DPA, subprocessor register, SCCs, SLA with credits, security whitepaper, SOC2/ISO roadmap.
- Production on-prem/VPC packaging (self-hosted Supabase or managed Postgres, KMS, real engine mode, runbooks).
- markting-branded support with tiers/SLA, not a single personal inbox.

## Disagreements / claims the code contradicts
- `billing.ts:58` "Includes SSO, regional hosting, … SLA, dedicated onboarding" — only custom retention is real (I4-02).
- `privacy.html` claims markting-grade operation but names Yannick Westermann Labs / adport.dev as operator and sole contact (I4-03).
- `deployment-model.md:3` presents a deployment model, yet `:49-58` lists privacy/terms/subprocessor/residency as still-required gates — the enterprise posture is pre-production (I4-08).
- Enterprise "custom retention / audit history" value is contradicted by the 150-row, export-less audit UI (I4-04).
