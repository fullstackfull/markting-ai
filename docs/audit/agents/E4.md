# E4 — Multi-tenant isolation (attacker view)

Attempted, by code reading and local reasoning only, to break tenant isolation along every
surface named in the workstream. Summary: the **Postgres-backed** surfaces (pending ops,
threads, findings, sandbox, API keys, MCP tokens, members, settings, connections, dashboard
reads, v1 tools) are consistently scoped by a membership-validated `organizationId` and I could
not break them. The **shared engine** surface (`/reports`) is **not** tenant-scoped: any
authenticated user of any org can list and download every org's engine report objects. Its
blast radius today is limited because the engine is hard-wired to synthetic `sample` data, so
it is a confirmed cross-tenant IDOR that is a **latent P0** the moment real data is wired in.

## Findings

### E4-01 — Engine report list/download routes have no tenant scoping (cross-tenant IDOR on a single shared engine)
- **Severity:** P2 today (synthetic data only), **latent P0** under real data.
- **Classification:** VERIFIED_CODE.
- **Evidence:**
  - `platform/apps/cloud/app/api/reports/engine/route.ts:16-23` — `GET` calls `await sessionPrincipal(organizationId)` then `engineClient().listReports()`; the principal's org is never passed to or used against the engine.
  - `platform/apps/cloud/app/api/reports/engine/[name]/route.ts:10-26` — `GET` streams `engineClient().fetchReportFile(name)` to any signed-in user; `name` is caller-supplied and only format-validated, never ownership-checked.
  - `platform/apps/cloud/lib/markting/engine-client.ts:131,134-137` — `listReports()`/`fetchReportFile(name)` carry no tenant parameter.
  - `services/engine-demo/serve_demo.py:355-358` (`/reports` returns the whole `_load_index(runtime)`), `:360-374` (`/reports/files/{name}` reads one shared `workspace_root/out` dir), `:306` (`_save_index` keeps only `entries[:50]` **globally**).
  - `docker-compose.yml:22` (one `MARKTING_ENGINE_URL`), `:49` (`PAID_MEDIA_API_TOKENS: <token>:adport-bridge` — one token → one caller), `:54` (one shared `engine-workspace` volume). `.env.example:45` — a single `MARKTING_ENGINE_TOKEN`.
- **Description:** The engine is one shared process with one report index and one `out/` directory; the platform routes only check that the caller is *some* authenticated user and never scope reports to the caller's org. Org A can call `GET /api/reports/engine` to enumerate every org's report runs (ids, cadence, windows, timestamps, summaries, `requested_by`) and then `GET /api/reports/engine/{name}` to download any org's report HTML/PDF/JSON.
- **Impact:** Cross-tenant access. Today the engine is pinned to `data_mode=sample` (see E4-01 mitigant) so report *content* is synthetic fixture data identical across orgs; the exposed cross-tenant signal is run metadata (who/when/how many reports), and the global 50-entry cap means a busy org **evicts** another org's report-run history from the listing (cross-tenant data loss of history). The product's stated purpose is an "AI media buyer" over real accounts — the instant the engine is pointed at real ad data, these same routes leak one tenant's financial/performance analysis to every other tenant: a P0.
- **Recommendation:** Scope reports per org end-to-end: carry `organizationId` into the engine (per-org caller token, or an org-keyed report namespace/subdirectory and index), and filter `listReports`/`fetchReportFile` by the caller's org; make the index per-org so the 50-cap cannot evict across tenants.

### E4-01-mitigant — Engine is hard-pinned to synthetic `sample` data in all modes
- **Classification:** VERIFIED_CODE.
- **Evidence:** `services/engine-demo/serve_demo.py:163-166` (boot refuses unless `paid_media_data_mode == 'sample'`), `:188` (demo settings force `sample`), `:386` (even `live` mode `model_copy(update={"paid_media_data_mode": "sample"})`), plus `assert_fail_closed` rejecting any live ad credential (`:139-170`).
- **Note:** This is why E4-01 is rated P2 rather than P0 *at present*. It is a boot-time guard in a host file, not isolation; it caps the data sensitivity, not the cross-tenant access.

### E4-02 — Engine has no tenant concept; all threads/proposals/reports share one caller_ref `adport-bridge`
- **Severity:** P3 (defense-in-depth; not exploitable through the product today).
- **Classification:** VERIFIED_CODE.
- **Evidence:**
  - `engine/src/paid_media_agent/surfaces/api/app.py:91-99` (thread ownership gated only by `who`), `:104-115` (proposal visibility gated only by `who`), `:150-153` (artifact access gated by `runtime.threads.owner(thread_id) != who`).
  - `services/engine-demo/serve_demo.py:313-322` — `caller()` resolves from `api_token_map()`, which `docker-compose.yml:49` populates with a single token mapped to `adport-bridge`; every org's platform call presents the same bearer, so the engine sees one caller for all tenants.
  - Documented and acknowledged: `README.md:128`, `docs/PHASE1-REPORT.md:44`, `docs/PHASE0-REPORT.md:88`, `docs/TODO.md:27`.
- **Description:** The engine's own ownership/visibility checks are a no-op across tenants because every tenant maps to the same `caller_ref`. Isolation of engine-backed conversations is pushed entirely to the platform (threadId namespacing + `markting_threads`), and reports (E4-01) have no such platform compensation.
- **Impact:** Any future route that forwards a user-controlled `thread_id`/`proposal_id` to the engine without the platform's prefix/ownership check — or any direct exposure of the engine — yields trivial cross-tenant reads. The engine must not be treated as a tenant boundary.
- **Recommendation:** Issue one engine token per organization (TODO.md:27 already contemplates this) so the engine's own ownership checks become real, as defense-in-depth behind the platform gate.

### E4-03 — No database-level per-tenant RLS; isolation rests entirely on application WHERE clauses
- **Severity:** P3 (architecture / defense-in-depth).
- **Classification:** VERIFIED_CODE.
- **Evidence:** `platform/supabase/migrations/20261002000000_markting_bridge.sql:68-89` — RLS is enabled but the only policies are a `restrictive ... to authenticated` deny for browser roles and `markting_*_backend_all ... to adport_backend using (true) with check (true)`. `platform/apps/cloud/lib/db.ts:8-13` — the server connects as `role: ADPORT_DB_ROLE` (adport_backend), which these policies let read/write every row regardless of org.
- **Description:** There is no per-organization row policy (e.g. keyed off a `current_setting`); the backend role sees all rows. Tenant isolation is therefore exactly as correct as every hand-written `where organization_id = …` predicate. I verified the current predicates are all present and correct, but there is no second line of defense: a single future query that omits the predicate is an immediate cross-tenant breach.
- **Impact:** Fragile isolation; one missing WHERE clause = tenant breach with no DB backstop.
- **Recommendation:** Add per-org RLS using a session GUC set from `principal.organizationId`, or route reads through a role that cannot bypass org policies.

## What a world-class system would need (gaps, concrete)
- Per-organization engine identity (one token/caller_ref per org) so the engine's own ownership checks enforce tenancy, and org-namespaced report storage + index so `listReports`/`fetchReportFile` cannot cross tenants and the 50-cap cannot evict across tenants.
- Pass and enforce `organizationId` on the two reports routes before any engine call.
- Database per-tenant RLS keyed off a request-scoped GUC as a backstop behind the application predicates.
- An integration test that authenticates as org A and asserts it cannot see org B's report run ids or download org B's report files (the current engine-client test only exercises transport/error codes, not tenancy).

## Disagreements / claims in docs that the code contradicts
- `README.md:128` / `docs/PHASE1-REPORT.md:44` state tenant isolation "lives in adport's `markting_threads` table, not inside the engine." That is accurate **for conversations**, but the docs never extend the same reasoning to **reports**: the reports routes are served per authenticated session as if org-scoped while providing no isolation at all (E4-01). The documented isolation model has an unacknowledged hole on the reports surface.
- `docs/PHASE0-REPORT.md:88` / `docs/TODO.md:27` flag the single-`caller_ref` engine as a known hygiene issue and recommend per-org thread namespacing — which was implemented for threads but not for reports, leaving the reports surface in the exact unmitigated state the docs warned about.
