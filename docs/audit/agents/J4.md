# J4 — Independent AI skeptic

Audit date: 2026-10-02. Repository: `/home/user/markting-ai` at `d9c79f6`. I did not read any other agent report before writing this. All paths are relative to the repository root. Every conclusion carries a classification tag; nothing below was upgraded from inference to fact.

**One-paragraph verdict.** In the deployment this repository ships by default (`MARKTING_ENGINE_MODE=demo`, `docker-compose.yml:51`, `.env.example:51`) there is no artificial intelligence in the loop at all: the "Assistant" is a Python regex that picks one of two fixed tool-call scripts, the analysis prose is an f-string template, and the "recommendation" is a hard-coded budget cut on fixture campaign `g-103`. In `live` mode a real LLM is wired in through upstream `paid-media-agent`, with a genuinely strong deterministic numeric layer under it, but the host forces `paid_media_data_mode="sample"` in both modes and refuses to start with any provider credential, so the model can only ever reason about the three shipped synthetic accounts, never a tenant's connected accounts. The README's claim that the engine "analyses connected accounts" is therefore not implemented. The engine's numeric integrity (code-computed metrics, reconciliation, provenance, missing-is-not-zero) is real and tested; its *judgement* layer (significance, thin-data gating, structured evidence for a recommendation, evaluation) is prose guidance to the model plus an unexecuted 15-question eval.

## Findings

### J4-01 — The AI can never see a tenant's real ad data in this product; the README claims it analyses connected accounts
- **Severity:** P1 (production blocker for the advertised capability; not a safety defect)
- **Classification:** VERIFIED_CODE (contradiction with docs: DOCUMENTED_ONLY on the docs side)
- **Evidence:**
  - `services/engine-demo/serve_demo.py:383-388` — live mode is `base.model_copy(update={"paid_media_data_mode": "sample"})`; demo mode `demo_settings()` also forces `"sample"` (`:183-191`).
  - `services/engine-demo/serve_demo.py:139-170` — `assert_fail_closed` exits the process if `PIPEBOARD_API_TOKEN`, any `X_ADS_*`, `OPENAI_ADS_API_KEY` is set, or if `paid_media_data_mode != "sample"`.
  - `engine/src/paid_media_agent/runtime/profiles.py:73-77` — with `data_mode == "sample"` accounts come from `config/accounts.example.toml` (`demo-google`, `demo-meta`, `demo-reddit`, `engine/config/accounts.example.toml:5-21`); `profiles.py:146` — `read_provider=FixtureReadProvider(state)`.
  - `engine/src/paid_media_agent/runtime/mda.py:65-72` — a live read provider is only substituted when the catalog loaded live credentials, which the host forbids.
  - `README.md:83` — "Analyses connected accounts (spend, conversions, CPA, ROAS) and answers questions on the Assistant page." `README.md:8,77` — engine described as "AI analysis".
  - The cloud side confirms the gap from the other direction: `platform/apps/cloud/lib/markting/assistant.ts:40-47` forwards the user's text only; no account list, connection, or report data from the org is sent to the engine. The org's real connections (`createTenantRuntime`) are used solely to *preview a proposal* (`runtime.ts:19`).
- **Description:** Whatever the model is (scripted or a real LLM), its only data source is the three shipped JSON fixtures shifted so they end two days ago (`tools/fixtures.py:201-248`). An organisation that connects its real Google/Meta/Snapchat accounts through adport and asks the Assistant "how are my campaigns doing?" receives an analysis of `Brand Search - US`, `Performance Max - Prospecting`, etc. The engine's `list_accounts` returns demo aliases regardless of tenant.
- **Impact:** The headline value proposition ("AI media buyer that analyses your accounts") does not exist in the codebase; the design choice of a single write path (adport) was extended into a single *read* path too, but no read bridge from adport reports to the engine was built. Any "recommendation" is about synthetic campaigns.
- **Recommendation:** Either (a) build a read bridge: an adport-backed `ReadProvider`/catalog for the engine that serves the tenant's reports and campaign lists under org-scoped aliases (the engine's `ReadProvider` protocol and `AccountRegistry` already support this shape), or (b) change the README, Assistant UI and marketing to state that analysis is demo-only until that exists. Do not ship (a) without the thin-data and evidence controls in J4-05/J4-09.

### J4-02 — The demo intent router turns analysis questions into a budget-cut proposal that lands on the Approvals page

The demo's write step also ignores the requested platform, campaign, direction and amount ("Increase the Snapchat … budget by 50%" → cut Google PMax to 240).
- **Impact:** For an evaluator judging whether the product "understands" media buying, the default mode produces confidently wrong, actionable output. In demo mode the blast radius is the sandbox, and `translateProposal` refuses unknown aliases (`translate.ts:133-134`), so a fixture proposal cannot reach a real account unless an operator maps alias `demo-google` to a live provider (only the seed and a test call `upsertAlias`, `repository.ts:52`, `infra/seed/seed-demo.mjs:50-60`). `docs/PHASE1-REPORT.md:42` documents "always proposes g-103 → 240" but not that analysis questions trigger it.

### J4-03 — Shared scripted-model state leaks across Assistant threads; the second user's first message gets a broken answer
- **Severity:** P2 (reliability of the default mode; also an asyncio concurrency hazard)
- **Classification:** VERIFIED_RUNTIME
- **Evidence:**
  - `services/engine-demo/serve_demo.py:92-115` — `LoopingScriptedChatModel` stores `seen_human_messages` and `call_count` on the instance and resets only when `len(humans) != self.seen_human_messages`.
  - `serve_demo.py:224-227` — one model instance is built per process and passed into `build_agent_components`, so every thread shares it.
  - Command #7: thread userA (1 human msg) answered correctly with `call_count=5`; thread userB (also 1 human msg) was not reset → `call_count=6` → "This is the offline demo engine…" exhausted text. Command #6 showed the same failure as "No receipt was returned: no tool result" when the previous thread stopped mid-script at the interrupt.
  - `services/engine-demo/tests/test_demo_api.py:59-63` — each test builds a fresh app, so the suite cannot observe this.
- **Description:** The reset heuristic keys on the *count* of human messages, which is identical for every thread's first turn. In a multi-user organisation, or a single user opening a new conversation, the second thread's first turn silently misfires. The mutable counters are also updated from concurrent requests without a lock; FastAPI/uvicorn will interleave them.
- **Impact:** The Assistant appears to "forget how to answer" after one conversation per process; whether a turn yields an analysis, a proposal, a "No receipt" message or the exhausted text depends on what another user did last.
- **Recommendation:** Key the script on the thread (`config["configurable"]["thread_id"]`) or instantiate the scripted model per request, and add a two-thread test to `test_demo_api.py`.

### J4-05 — No computed significance, sample-size or magnitude gating anywhere; "confidence" is a model-authored word
- **Severity:** P2 for a product that intends to recommend budget changes (GAP in capability terms; a defect only in that the skills tell the model to express "confidence" that nothing computes)
- **Classification:** VERIFIED_CODE
- **Evidence:**
  - `engine/src/paid_media_agent/tools/compute.py:349-375` — `_attention_lines` selects the top-3 entities by absolute spend delta and prints relative percentages; no base-size check. `summary.py:27` — a day is "flagged" when spend or conversions move ≥ 50 % day-over-day, nothing more.
  - Command: `grep -rn -i "min_conversions|sample size|significan|confidence|p_value|z_score|stddev|variance" engine/src/paid_media_agent` → hits only in `domain/reports.py:58` (`confidence: str = Field(pattern="^(low|medium|high)$")`) and the HTML template. `tools/reports.py:33,93` — recommendations (target, action, evidence, expected_effect, confidence, measurement, reversal) are free-text fields *supplied by the model*.
  - `tools/writes.py:78-125` — `classify_risk` is keyword-based: `budget_delta`, `budget_increase` (any increase), `status_flip`, etc. No percentage or absolute threshold; a +1 % and a +1000 % budget change carry identical flags. `ProposalService.propose` (`writes.py:390-436`) accepts `reason`, `measurement_plan`, `reversal_plan` as free text with no required artifact id.
  - The only thin-data guidance is prose: `paid-media-wiki/anomaly-and-significance.md:21-28` ("Deterministic tools report exact values; they do not run significance tests. Be explicit…"), `bidding-and-budget.md:17-22`, `paid-media-analysis/SKILL.md:48` ("Do not use universal performance thresholds. Use configured goals or label the analysis as directional").
  - No `company-context` skill exists in the repo (command #9); `paid-media-analysis/SKILL.md:11` and `paid-media-wiki/SKILL.md:33-35` make goals and targets conditional on it.
  - Fixture scale (command #4): 2–3 campaigns per platform, 26–28 days, so a 7-day window per campaign has single- or low-double-digit conversions. The shipped weekly comparison for reddit shows "336.42 vs 776.03" (`tests/eval/questions.json` q01 expectation) — a −57 % move on a ~USD 50/day campaign.
- **Description:** The engine prevents the model from *miscalculating* (strong) but does nothing to prevent it from *over-interpreting*: a live model can call `compare_periods` on a 7-day window with 4 vs 7 conversions, read "−43 % CPA", and propose a budget change with "high" confidence; every number in the proposal will be exact and the proposal will still be unjustified. Without a company-context skill there is no configured goal, so every analysis is, by the skill's own rule, "directional" — yet proposals are typed and actionable.
- **Impact:** If J4-01 is ever fixed, the product would issue confidently-phrased, numerically exact, statistically unsupported recommendations on thin data, with a reviewer seeing 160 characters of reason (J4-09).
- **Recommendation:** Add code-owned evidence quality to `AnalysisSummary`/`PlatformHeadline`: conversions in both windows, day coverage ratio, a minimum-base flag (e.g. `< 30` conversions or `< 7` complete days ⇒ `low_evidence`), and a Wilson/Poisson interval or at least a `relative_change_meaningful: bool`. Make `propose_change` require `evidence_artifact_ids` and refuse budget proposals whose target's analysis carries `low_evidence` unless the user overrides explicitly. Add magnitude to `classify_risk` (`budget_increase_pct`). Ship a template `company-context` skill and make its absence visible in every answer.

## What a world-class system would need

1. **A real read path from the tenant's accounts to the engine.** An adport-backed `ReadProvider` + catalog (`list_campaigns`, `get_campaign_performance`, change history) under org-scoped aliases, so the engine's existing normalisation/reconciliation runs on real rows. Until then, nothing here is a media-buying intelligence for the customer's business.
2. **Evidence-quality as data, not prose.** Per entity and window: conversions count, days covered vs requested, lag/completeness, and an interval or at least a `low_evidence` flag computed in `compute.py`; carried into `AnalysisSummary`, `render_report` and `propose_change`. Refuse or downgrade proposals on low evidence.
3. **Decision policy in code.** Max step size (the wiki's "20–30 %"), minimum learning window since last change, no bid+budget simultaneous changes, cooling-off after a flagged anomaly — enforced in `classify_risk`/`ProposalService`, not only recommended in `bidding-and-budget.md`.
4. **Business context as a first-class object.** Goals, target CPA/ROAS, margins, seasonality (Ramadan, Eid, White Friday for the Gulf market), currency (SAR) stored per organisation and injected as the `company-context` skill; the skills already expect it.
5. **Counterfactual / measurement memory.** Record each applied proposal's before/after and automatically run the "measurement plan" after the stated window; feed outcomes back as evidence. The engine already produces measurement plans as text (`writes.py:399,431`); nobody executes them.
6. **A standing eval with Arabic and restraint cases**, run per model in CI against the host API, grading tool-call structure and refusal behaviour, not only substring figures.
7. **Honest UI**: mode, data source (demo/real), evidence artifact and confidence basis shown on every answer and every approval card.
