## Findings

### D3-01 — Demo model keeps per-process mutable state; second thread's first message gets the fallback text, concurrent turns corrupt each other
- **Severity:** P2 **Classification:** VERIFIED_RUNTIME
- **Evidence:** `services/engine-demo/serve_demo.py:84-116` (`LoopingScriptedChatModel` mutates `self.steps`, `self.call_count`, `self.seen_human_messages` inside `_generate`; the reset condition is `len(humans) != self.seen_human_messages`, a count, not a thread id); `serve_demo.py:194-198` (one model instance built per process); `engine/src/paid_media_agent/testing/scripted_model.py:185-229` (base class is also per-instance stateful); probe output above (commands 10, 11).
- **Description:** The host's scripted model is one object shared by every LangGraph thread. The script is reset only when the number of human messages in the *current* request differs from the number seen on the *previous* request, whatever thread that was. Two different conversations whose first messages arrive consecutively (the normal case: the cloud mints a fresh `org_<org>__u_<user>__<rand>` thread per conversation, `platform/apps/cloud/lib/markting/assistant.ts:34-36`) therefore collide: thread B's first question is answered with "This is the offline demo engine…" instead of the analysis. Under concurrency (two users at once) `_generate` runs in worker threads and the shared counters interleave: the analysis thread received the write script's "The proposal could not be staged." and the change-request thread received "No receipt was returned". The host's own test suite never sends two threads through one app instance (each test gets a fresh `client` fixture, `test_demo_api.py:59-63`), so the defect is invisible to `make test`.
- **Impact:** `MARKTING_ENGINE_MODE=demo` is the default (`serve_demo.py:133`, `.env.example:51`, `docker-compose.yml:51`). In the shipped default mode the Assistant works correctly only for the first conversation after boot and for strictly alternating message counts; a second user or a second tab breaks it. No safety impact (writes are impossible regardless), but it is a production-path functional defect of the demo product.
- **Recommendation:** Key the script state by `config["configurable"]["thread_id"]` (available via `RunnableConfig` passed to `_generate` through `**kwargs`/run_manager metadata) or build one scripted model per thread; guard the state with a lock; add a host test that sends two threads through one app sequentially and with `asyncio.gather`.

### D3-02 — Keyword "write intent" routing produces a fixed proposal that can contradict the user's request
- **Severity:** P3 **Classification:** VERIFIED_RUNTIME
- **Evidence:** `serve_demo.py:63-66` (`WRITE_INTENT` regex includes `budget`, `change`, Arabic verbs), `serve_demo.py:103-111`, `engine/src/paid_media_agent/testing/demo_script.py:387-399` (`_propose` always stages `google_ads__update_campaign_budget` on `g-103` → 240); probe rows `Q` and `M` above.
- **Description:** Any message containing "budget" (e.g. "What is my budget?") or an Arabic verb such as ارفع ("raise") is routed to the write script, which always proposes a Google Ads budget *cut* to 240 on `demo-google`, even when the user asked to raise a Meta budget to 500. The resulting `awaiting_approval` proposal is then handed to adport's bridge as if it were the user's intent.
- **Impact:** Demo fidelity only (the proposal is validated against the sandbox provider and still needs a human apply on the adport side), but a user asking a question in the default mode is shown a change proposal they did not request. The disclosure text appears only when the script is exhausted, not on the proposal itself.
- **Recommendation:** Narrow the regex to imperative patterns, or label scripted proposals in the `ProposalView`/UI as "demo replay"; document in the Assistant UI that demo mode replays one fixed change.

### D3-03 — Host forks `build_self_hosted_runtime` and imports the private `_postgres_checkpointer`; host is not mypy-clean under the engine's own config
- **Severity:** P3 **Classification:** VERIFIED_CODE / VERIFIED_TEST
- **Evidence:** `serve_demo.py:46` (`from paid_media_agent.runtime.self_hosted import SelfHostedRuntime, _postgres_checkpointer`); `serve_demo.py:201-243` vs `engine/src/paid_media_agent/runtime/self_hosted.py:65-105` (near-verbatim copy); command 4 (mypy, 4 errors). Upstream pin: `UPSTREAM.md` / commit `4162146 chore(engine): import paid-media-agent at 0cc8109`.
- **Description:** `build_self_hosted_runtime` exposes `model=` and `checkpointer=` but no hook to replace the write provider before `build_agent_components` captures it in `WriteExecutor` (`assembly.py:212-223`). The host therefore re-implements the builder and reaches into an underscore-private coroutine. The fork is *necessary* given upstream's API (a post-hoc `dataclasses.replace` on `runtime.profile` would not reach the executor), but it is a silent drift point: an upstream rename of `_postgres_checkpointer` or a change to the body (e.g. closing pools, new repositories) breaks or diverges the host at import time. The engine is `mypy --strict` clean (command 2); the host script is not (command 4), and the `# type: ignore[arg-type]` at `serve_demo.py:273` papers over the `Cadence` literal rather than typing `ReportRunIn.cadence` as `Literal["weekly","monthly"]`.
- **Impact:** Maintainability and upgrade risk; no runtime defect today.
- **Recommendation:** Upstream (or carry as a documented patch) a `write_provider: WriteProvider | None` / `profile_overrides` parameter on `build_self_hosted_runtime` and make `postgres_checkpointer` public; add `mypy ../services/engine-demo/serve_demo.py` to `make test`; type `cadence` as the `Cadence` literal.

### D3-04 — Postgres path (the compose default) is untested, pools are never closed, and sync DB calls block the event loop
- **Severity:** P3 **Classification:** VERIFIED_CODE (blocking/leak) · NOT_VERIFIED (runtime behaviour against Postgres)
- **Evidence:** `docker-compose.yml:42` sets `DATABASE_URL`, so production boots the Postgres branch `serve_demo.py:208-219`; command 14 (no test references `_postgres_checkpointer`/`AsyncPostgresSaver`); `self_hosted.py:45-62` (pool opened, never closed; no `close()` on `SelfHostedRuntime`), `persistence/postgres.py:52` (sync `ConnectionPool`, `open=True`), `tools/writes.py:553-555` (`_save` sync, called from `async def propose` at 389/447), `surfaces/runner.py:86-89` (`self._threads.claim` sync inside the request path), `surfaces/api/app.py` (no lifespan/shutdown hook).
- **Description:** The loop-binding concern called out in upstream's docstring (`self_hosted.py:8-9`) is handled correctly by the host: `build_app_async` is awaited inside the same `asyncio.run(_serve())` loop that then runs `uvicorn.Server.serve()` (`serve_demo.py:377-419`), and every graph call in `runner.py` is async (`ainvoke`/`aget_state`); the only sync `get_state` is in the CLI demo path with `InMemorySaver` (`testing/demo_script.py:268`). What is not handled: (a) proposals, approvals, receipts, dedupe and thread ownership use a *synchronous* psycopg pool called directly from coroutines, so every DB round-trip blocks the single event loop for all concurrent requests; (b) neither the sync pool nor the `AsyncConnectionPool` is closed on shutdown; (c) nothing in this repository (host tests or upstream tests collected here) ever runs the Postgres branch, so `repos.setup()` + `saver.setup()` ordering, migrations and reconnect behaviour are unverified in this codebase. Compose's `depends_on: service_healthy` + `restart: unless-stopped` mitigates boot-order failures only.
- **Impact:** Latency/throughput degradation under concurrent use; connection leaks on reload; an unverified production path.
- **Recommendation:** Wrap repository calls in `asyncio.to_thread` or use psycopg's async pool for repositories too; add a FastAPI lifespan that closes both pools; add an integration test (docker-compose `engine-db` or `testcontainers`) that boots the host with `DATABASE_URL` and exercises one message + one report.

### D3-05 — Running the host from source writes `KILL_SWITCH` into the upstream tree and silently breaks 19 upstream tests
- **Severity:** P3 **Classification:** VERIFIED_RUNTIME
- **Evidence:** `serve_demo.py:173-181` (`engage_kill_switch` resolves the default relative `workspace/KILL_SWITCH` against `project_root()`, i.e. `engine/`), `engine/src/paid_media_agent/config.py:158` (default path), `engine/.gitignore:32` (file is ignored, so `git status` hides it); command 13 (file exists, dated Oct 2 12:22, content matches the host's text); command 6 (19 failures, all `kill_switch: …/engine/workspace/KILL_SWITCH exists`) vs command 7 (same tests pass with the path redirected).
- **Description:** Upstream's tests resolve the kill switch through `RuntimeProfile.write_gate` (`profiles.py:201-204`) against `skills_root = project_root`, not `tmp_path`, so any file at `engine/workspace/KILL_SWITCH` flips every fake-write test to `rejected`. The markting host creates exactly that file when run from source with default settings (as `docs/PHASE1-REPORT.md:30` "Engine host run manually" implies). The behaviour test `test_demo_uses_the_fixture_anchor…` additionally writes `art_*.json` into `engine/workspace/{analysis,out}` (ignored; dozens present, command 13 listing) — an upstream hygiene issue.
- **Impact:** Anyone verifying the vendored engine in this checkout sees a red upstream suite with a misleading cause; upstream tests are also not hermetic. In the container the same file lands on the `engine-workspace` volume, which is intended.
- **Recommendation:** Have the host default `paid_media_kill_switch_path` to an absolute path under `paid_media_workspace_root` when running outside the container, or document `PAID_MEDIA_KILL_SWITCH_PATH` for local runs; add a `make engine-test` target that runs the upstream suite with an isolated workspace/kill-switch path; consider an upstream fix so tests pass `kill_switch_path` under `tmp_path`.

### D3-06 — The data-mode "boot assertion" is dead code (mode is coerced before the check)
- **Severity:** P3 **Classification:** VERIFIED_CODE
- **Evidence:** `serve_demo.py:381-388` (`demo_settings(base)` and the live branch both `model_copy(update={"paid_media_data_mode": "sample"})`) runs before `assert_fail_closed(resolved)` at `serve_demo.py:388`; the check at `serve_demo.py:163-166` can therefore never fire. `demo_settings` at `serve_demo.py:183-191` also uses `model_copy(update=…)`, which bypasses pydantic validation.
- **Description:** The docstring (`serve_demo.py:11-16`) and `docs/PHASE1-REPORT.md:12` describe "boot assertions that refuse to start when any live credential or write flag is set". That is true for the token/key/flag checks (tested at `test_demo_api.py:81-91`), but `PAID_MEDIA_DATA_MODE=live` set by an operator is silently overwritten to `sample` rather than refused, and the "live" engine mode is live *model* only — data is always synthetic.
- **Impact:** Safe outcome (the coerced value is the safe one) but misleading: an operator who sets `PAID_MEDIA_DATA_MODE=live` gets no error and synthetic data.
- **Recommendation:** Either assert on `base` before coercion and fail loudly, or drop the dead branch and document that the host always runs sample data.

### D3-07 — Report routes have no tenant scope and bypass upstream's per-thread artifact authorization; `/markting/info` is unauthenticated
- **Severity:** P3 today (synthetic data only); would be P1 if data mode ever became live **Classification:** VERIFIED_CODE
- **Evidence:** `serve_demo.py:360-376` (`GET /reports/files/{name}` accepts any `(rpt|art)_<id>.(html|pdf|json)` under `workspace/out` for any valid token, no thread/owner check) vs upstream `surfaces/api/app.py:150-166` (artifact download requires `threads.owner(thread_id) == who` and the name to be part of that thread's `render_report` results); `tools/artifacts.py:21-27` (`report` artifacts live in `out/`); `serve_demo.py:326-336` (`/markting/info` has no `caller()` dependency; returns aliases, mode, kill switch state); `serve_demo.py:355-358` (`GET /reports` returns the whole index); cloud passes any name through with session auth only (`platform/apps/cloud/app/api/reports/engine/[name]/route.ts:10-15`), and README admits the engine has no tenant concept (`README.md:124`).
- **Description:** Reports rendered inside any user's chat thread (via the agent's `render_report` tool) and all cadence runs share one `out/` directory and one index; any signed-in cloud user of any organisation can list and download all of them through the single service token. Upstream deliberately scoped artifact downloads to thread owners; the host's route removes that scope.
- **Impact:** None today beyond synthetic data (all modes force `sample`), but the structure is a cross-tenant leak waiting for the first live data source.
- **Recommendation:** Namespace report runs by caller/org (e.g. `requested_by` + an `org` header forwarded by the cloud) and filter `GET /reports` and `/reports/files` by it; require the bearer on `/markting/info` or reduce it to non-sensitive fields.

### D3-08 — Unsanitised exception text returned to the caller from `/reports/run`
- **Severity:** P3 **Classification:** VERIFIED_CODE
- **Evidence:** `serve_demo.py:350-353` (`detail=f"report failed: {type(exc).__name__}: {exc}"`) with the comment "the engine's own errors are informative and secret-free"; upstream provides `sanitize_exception` (`middleware/redaction.py:42-46`) and uses it everywhere errors reach a client or the model (`tools/writes.py`, `surfaces/slack/*`).
- **Description:** The comment is an assumption, not an enforcement. `run_cadence_report` catches provider errors itself (`reports/cadence.py:106-111`), but `ArtifactStore`/filesystem errors and future live providers would surface raw messages (paths, URLs).
- **Recommendation:** `detail=sanitize_exception(exc, secrets)`, and log the full traceback server-side only (already done via `log.exception`).

### D3-09 — Receipt can report `mutation_attempted=True` for the proposal-only provider
- **Severity:** P3 **Classification:** VERIFIED_CODE
- **Evidence:** `tools/writes.py:844` (`attempted = True` is set before `await self._provider.call_mutation(entry, arguments)`); a `ProviderError` from `ProposalOnlyWriteProvider` (`serve_demo.py:69-82`) yields `_receipt(record, "failed", attempted=attempted, …)`. Reachable only when the kill switch file is absent and an approval claim exists (impossible over the API with zero approvers; possible in-process).
- **Description:** Defence in depth holds (the provider raises before any network), but the audit record would say a mutation was attempted when none left the process. Operations with `validate_only_arg` (budget updates, `write_policy.py:180`) fail earlier with `attempted=False`, status updates do not.
- **Recommendation:** Let the host's provider raise a distinct subclass (e.g. `ProposalOnlyRefused(ProviderError)`) and have the executor record `attempted=False` for it, or document the semantics.

### D3-10 — Configuration is split across `Settings` and ad-hoc `os.environ`; host ignores the engine's log-level setting and `.env` key export
- **Severity:** P3 **Classification:** VERIFIED_CODE (split/log level) · INFERRED (dev-machine live mode)
- **Evidence:** `serve_demo.py:132-136` (`_mode()` reads `MARKTING_ENGINE_MODE` from `os.environ`), `serve_demo.py:330` (`info()` reads it again), while everything else is a `Settings` field (`config.py:108-176`); `serve_demo.py:399` (`logging.basicConfig(level=logging.INFO)`) vs CLI `cli.py:23-26` honouring `paid_media_log_level`; CLI exports allow-listed `.env` keys (`cli.py:49-51`, `admin/envfile.py:485-505`) but the host never calls `apply_env_file`, and `ANTHROPIC_API_KEY`/`OPENAI_API_KEY` are not `Settings` fields, so pydantic-settings will not read them from `.env`.
- **Description:** In the container this is harmless (`env_file: .env` injects every variable). On a developer machine `MARKTING_ENGINE_MODE=live` with the key only in `.env` would fail at the first model call — consistent with `docs/TODO.md:26` ("live mode has not been exercised"). Validation of `MARKTING_ENGINE_MODE` is a `SystemExit` string check rather than a typed `Literal` field.
- **Recommendation:** Subclass `Settings` in the host (`class HostSettings(Settings): markting_engine_mode: Literal["demo","live"] = "demo"`), use `settings.paid_media_log_level`, and call `apply_env_file(project_root())` (or document `set -a; . .env`).

### D3-12 — Report index is a flat JSON file with no pruning and no requester identity (GAP)
- **Severity:** GAP **Classification:** VERIFIED_CODE
- **Evidence:** `serve_demo.py:246-265` (`markting-reports.json` in `workspace/out`, truncated to 50 entries, files on disk never removed), `serve_demo.py:295` (`requested_by` = token caller, always `adport-bridge` per `docker-compose.yml:49`), in-process `asyncio.Lock` only (`serve_demo.py:324`).
- **Description:** Even with Postgres configured, report metadata lives in a file on the workspace volume; multiple host replicas would race; disk grows unbounded; no per-organisation attribution.
- **Recommendation:** Store runs in a `pma_`-style table (or reuse `ArtifactStore` metadata), prune files past the index cap, forward an org/user identifier from the cloud.

### D3-13 — Logging is minimal and unstructured (GAP)
- **Severity:** GAP **Classification:** VERIFIED_CODE
- **Evidence:** command 16 (3 engine modules log; `authorization.py:82,89` warnings, `pipeboard.py:118`); host logs one boot line (`serve_demo.py:404-410`) and `log.exception` on report failure. No request ids, no per-turn timing, no structured output; `RedactionMiddleware` protects tool results and model-facing errors (`redaction.py:49-80`) but nothing redacts log records.
- **Recommendation:** Add a logging filter that applies `redact()` to records, a request-id middleware, and per-turn duration/outcome logs.

## What a world-class system would need

1. A thread-keyed (or per-thread-instance) scripted model with a lock, plus a host test that drives two threads sequentially and concurrently through one app (closes D3-01).
2. An upstream extension point: `build_self_hosted_runtime(..., write_provider=…)` and a public `postgres_checkpointer`, so the host stops forking a private builder (D3-03); `mypy` of the host in CI.
3. Async-safe persistence: async psycopg repositories or `to_thread` wrappers, a FastAPI lifespan that closes both pools, and a Postgres-backed integration test of the host (D3-04).
4. Hermetic tests: upstream tests should pass `kill_switch_path`/workspace under `tmp_path`; the host should never write into `engine/` when run from source (D3-05).
5. Tenant scoping on everything the host adds: report index rows carry an org id forwarded by the cloud, `/reports*` filter by it, `/markting/info` behind the bearer (D3-07, D3-12).
6. One typed `HostSettings` (mode as a `Literal`, log level honoured), `sanitize_exception` on every client-visible error, redaction filter on log records, request ids (D3-08, D3-10, D3-13).
7. A genuine "live" mode definition: today "live" means live model over synthetic data; a product-grade engine needs a path to live *reads* (Pipeboard/direct adapters) while writes stay delegated — with the fail-closed assertions rewritten to allow read credentials but never write flags.
