behaviour, health checks, timeouts, resource limits, engine scaling, zero-downtime deploys and
rollback. Repository is source of truth; docs are claims to verify.

## Findings

### H4-01 — No graceful shutdown or connection draining; deploys can hang or drop in-flight work
- Severity: P1
- Classification: VERIFIED_CODE
- Evidence: `services/engine-demo/serve_demo.py:411-417` (uvicorn `Config` with only host/port/log
  level; no `timeout_graceful_shutdown`, no FastAPI `lifespan`); `engine/src/paid_media_agent/cli.py:575-581`
  (same pattern for `serve`); `engine/src/paid_media_agent/persistence/postgres.py:64-65`
  (`close()` defined but no caller — confirmed by grep); `engine/src/paid_media_agent/runtime/self_hosted.py:45-62`
  (async `AsyncConnectionPool` opened, never closed anywhere).
- Description: There is no shutdown path. On `SIGTERM`, uvicorn by default waits for outstanding
  requests with no configured `timeout_graceful_shutdown`, so a long assistant turn or report run
  (routes allow up to 300s) blocks container stop indefinitely; meanwhile the sync Postgres pool
  (`postgres.py:52`) and the async checkpointer pool (`self_hosted.py:52-59`) are never drained, so
  connections and any in-flight transaction are torn down abruptly by process kill.
- Impact: Rolling restarts/deploys either stall on an in-flight request or get SIGKILLed at the
  orchestrator's grace limit, aborting a run mid-flight and leaving Postgres connections to time
  out server-side. No clean drain → no safe zero-downtime deploy.
- Recommendation: Add a FastAPI `lifespan` that closes `PostgresRepositories.close()` and the
  checkpointer pool; set a bounded `timeout_graceful_shutdown` on `uvicorn.Config`; make the
  orchestrator grace period ≥ that bound; drain the report lock before exit.

### H4-02 — Report index is a single global, file-based, 50-entry store shared across all tenants
- Severity: P1
- Classification: VERIFIED_CODE
- Evidence: `services/engine-demo/serve_demo.py:62` (`REPORT_INDEX = "markting-reports.json"`),
  `:246-249` (one file under `workspace/out`), `:304-306` (`entries.insert(0, entry)` then
  `_save_index(runtime, entries[:50])` — global cap of 50), `:355-358` (`reports_list` returns the
  whole index to any authenticated caller); `platform/apps/cloud/app/api/reports/engine/route.ts:16-23`
  (`GET` calls `engineClient().listReports()` with no `organizationId` filter). The engine runs as
  one process behind one bridge token (`docker-compose.yml` `PAID_MEDIA_API_TOKENS=...:adport-bridge`)
  for all adport organizations.
- Description: Every org's report runs land in one JSON file capped at 50 entries total; `listReports`
  returns all of them and the adport route forwards them unfiltered. Writes are guarded only by an
  in-process `asyncio.Lock` (`serve_demo.py:324`), which does not serialize across engine replicas,
  and the file lives in the `engine-workspace` volume rather than the database — so it is unaffected
  by `DATABASE_URL`.
- Impact: (a) Operability/capacity: a busy tenant evicts other tenants' report history (global 50
  cap); (b) horizontal scaling is unsafe — two replicas doing read-modify-write on the shared file
  lose updates/corrupt it, and if the volume is per-replica, `listReports` returns different sets
  per request; (c) cross-tenant exposure of report metadata (defer P0 security classification to the
  security/multi-tenancy workstream, but the operability defect — unpartitioned shared state — is
  real here).
- Recommendation: Move the report index into Postgres keyed by organization (and scope the adport
  route by `organizationId`); drop the global 50 cap in favour of per-tenant retention; remove the
  reliance on a local file + in-process lock.

### H4-03 — Kill switch is a per-process local file; it does not propagate across replicas
- Severity: P1
- Classification: VERIFIED_CODE
- Evidence: `engine/src/paid_media_agent/tools/writes.py:195-196`
  (`kill_switch_engaged` = `self.kill_switch_path.exists()` — a local filesystem check);
  `engine/src/paid_media_agent/config.py:158` (`paid_media_kill_switch_path = workspace/KILL_SWITCH`);
  `services/engine-demo/serve_demo.py:173-180` (engaged per-process at boot into the workspace
  volume); CLI toggle writes the same local file (`cli.py:441-442`, `admin/actions.py:1061-1086`).
- Description: The kill switch — the emergency brake on live ad-platform writes — is a file on the
  instance's workspace volume. In a multi-replica live self-hosted deployment with per-replica
  volumes, engaging it via one replica's CLI/admin does not stop writes on the other replicas; they
  each consult their own path. If the workspace volume is not persisted across a redeploy, a
  previously-engaged kill switch is also silently cleared.
- Impact: The safety control that the product's core invariant depends on is not cluster-wide. The
  shipped markting host is proposal-only (writes unreachable), so this is latent there, but the live
  self-hosted write path (`docs/operations/live-write-runbook.md`) inherits it directly.
- Recommendation: Back the kill switch with shared state (DB row / shared config) checked on every
  write, not a local file; ensure any file-based fallback lives on persistent, cluster-shared
  storage; document that engaging it must reach all replicas.

### H4-04 — Health endpoint is shallow: never probes Postgres or the model (false-healthy)
- Severity: P2
- Classification: VERIFIED_CODE
- Evidence: `engine/src/paid_media_agent/surfaces/api/app.py:80-89` — `/health` returns static
  runtime metadata (`persistence` string, `catalog_revision`, `selection`, `writes_enabled`) and
  performs no DB ping or model reachability check; `docker-compose.yml` engine healthcheck hits this
  endpoint and `cloud.depends_on.engine.condition: service_healthy` treats it as readiness.
- Description: `/health` is a liveness-only signal masquerading as readiness. With `DATABASE_URL`
  set, if Postgres is down or the pool is exhausted, `/health` still returns 200, so the container
  stays "healthy" and the cloud keeps routing traffic that then fails at request time.
- Impact: No true readiness gate; dependency outages are invisible to the orchestrator and to
  `depends_on`. Harder incident detection; cascading 500s/503s instead of a deliberately unready
  node.
- Recommendation: Split liveness (`/health`, cheap) from readiness (`/ready`, pings Postgres with a
  short `SELECT 1` and reports pool saturation); point the compose/orchestrator healthcheck and
  `depends_on` at readiness.

### H4-05 — Single process / single event loop with synchronous Postgres repos on the loop
- Severity: P2
- Classification: VERIFIED_CODE
- Evidence: `engine/src/paid_media_agent/persistence/postgres.py:52` (sync `ConnectionPool`,
  `min_size=1, max_size=4`); sync saves invoked from async graph/runner execution at
  `engine/src/paid_media_agent/tools/writes.py:550,554,704` and `surfaces/runner.py:87,92,235`; the
  server is one uvicorn process with no `limit_concurrency` (`serve_demo.py:411-417`).
- Description: The engine is designed as one asyncio process ("the API and the Slack adapter run in
  one event loop" — `self_hosted.py:8-9,46-47`). Proposal/approval/receipt repositories use a
  blocking psycopg pool whose calls run directly inside async handlers (not via `to_thread`), so
  each DB round-trip blocks the event loop, serialising concurrent requests. `max_size=4` further
  caps DB concurrency.
- Impact: Throughput is bounded by one core and one event loop; under concurrent chat/report load,
  DB I/O stalls unrelated requests. No documented horizontal-scaling story that keeps the shared
  file state (H4-02) and local kill switch (H4-03) consistent.
- Recommendation: Offload sync repo calls with `asyncio.to_thread` (the codebase already uses this
  pattern elsewhere, e.g. `tools/reads.py:209`, `middleware/offload.py:61`) or adopt async repos;
  size the pool for the target concurrency; define a scale-out plan that externalises all shared
  state.

### H4-06 — No server-side request timeout; client abort does not cancel the run, and the report lock is held for the whole run
- Severity: P2
- Classification: VERIFIED_CODE
- Evidence: `platform/apps/cloud/lib/markting/env.ts:18` (client `MARKTING_ENGINE_TIMEOUT_MS` default
  240_000), `platform/apps/cloud/lib/markting/engine-client.ts:81-100` (AbortController aborts the
  *fetch*, client-side only), route budget `maxDuration = 300` (`.../reports/engine/route.ts:7`);
  engine has no per-request timeout — `serve_demo.py:344-353` runs the report inside
  `async with lock:` (`:324`) with only the model-call timeout (`config.py:118`, default 120s) as an
  internal bound.
- Description: When the client aborts at 240s, the engine keeps executing the handler (a fetch abort
  does not cancel the server coroutine), wasting compute. For reports, the single process-wide
  `asyncio.Lock` is held for the entire run, so a stuck/slow report blocks all other report runs in
  that process (head-of-line blocking).
- Impact: A single slow report (e.g. WeasyPrint PDF render) stalls the report surface for all
  tenants; aborted client requests leave orphaned server work.
- Recommendation: Wrap the engine handler in `asyncio.wait_for` with a server-side budget below the
  client timeout; make the report lock finer-grained or replace with DB-level concurrency; honour
  client disconnects.

### H4-07 — No resource limits, restart backoff caps, grace periods, or healthcheck start_period
- Severity: P3
- Classification: VERIFIED_CODE
- Evidence: `docker-compose.yml` and `engine/docker-compose.yml` — grep for
  `deploy|mem_limit|cpus|resources|replicas|stop_grace|start_period` returns nothing; services use
  only `restart: unless-stopped` with healthcheck `interval/timeout/retries` and no `start_period`.
- Description: No CPU/memory caps anywhere. A runaway report render or a large model context can
  grow memory unbounded and OOM the host, taking down the engine and (via `host.docker.internal`
  ordering) impacting the cloud. `restart: unless-stopped` with no backoff can crash-loop. No
  `start_period` means the healthcheck counts early-boot failures toward the retry budget.
- Impact: No blast-radius containment; noisy-neighbour and OOM risks are unbounded.
- Recommendation: Set memory/CPU limits and reservations; add `stop_grace_period` aligned with the
  graceful-shutdown bound (H4-01); add `start_period` to healthchecks; cap restart behaviour.

### H4-08 — No metrics, readiness, or tracing surface
- Severity: P3
- Classification: VERIFIED_CODE
- Evidence: grep for `prometheus|/metrics|/ready|/livez|opentelemetry` across `engine/src`,
  `services/engine-demo`, `platform/apps/cloud/lib/markting` → 0; the only observability is
  `logging.basicConfig(level=INFO, stream=sys.stderr)` (`serve_demo.py:399`).
- Description: There is no metrics endpoint, no readiness probe, no distributed tracing, and no
  structured request logging on the engine. SLOs (below) cannot be measured in production with what
  ships.
- Impact: No golden-signal visibility (latency, errors, saturation); incident detection depends on
  user reports or log scraping.
- Recommendation: Add a `/metrics` (Prometheus) endpoint with request latency/count/in-flight and
  pool saturation; emit structured JSON logs with request IDs; optionally OTel traces around model
  and DB calls.

### H4-09 — Schema bootstrap runs on every boot with no versioning or migration lock
- Severity: P3
- Classification: VERIFIED_CODE
- Evidence: `engine/src/paid_media_agent/persistence/postgres.py:11-45` (`SCHEMA_SQL` of
  `CREATE TABLE/INDEX IF NOT EXISTS`), `:58-60` (`setup()` executes it every boot);
  `engine/src/paid_media_agent/runtime/self_hosted.py:60-61` (`AsyncPostgresSaver.setup()` runs the
  langgraph checkpointer migrations at boot).
- Description: Every instance runs DDL at startup. Concurrent boots of two instances can race on
  `CREATE INDEX IF NOT EXISTS`/checkpointer migrations, and there is no schema version table or
  advisory lock. Rollback to a prior image is only safe because the app DDL is additive; the
  langgraph checkpointer schema is managed by the dependency version with no guard across up/down.
- Impact: Deploy-time races under scale-out; rollback across a langgraph version bump is unverified.
- Recommendation: Gate `setup()` behind a Postgres advisory lock; introduce an explicit, versioned
  migration step run once per deploy rather than per-process; pin and test checkpointer schema
  across the versions you roll between.

### H4-10 — In-memory fallback (no DATABASE_URL) loses pending interrupts, dedupe, and thread ownership on restart
- Severity: P2
- Classification: VERIFIED_CODE (behaviour) / DOCUMENTED_ONLY (restart loss, acknowledged in docs)
- Evidence: `services/engine-demo/serve_demo.py:220-223,229` and
  `engine/src/paid_media_agent/runtime/self_hosted.py:86-89,93-95` — when `settings.database_url is
  None`, `InMemoryDedupeStore`/`InMemoryThreadOwnershipStore` and `InMemorySaver` are used;
  `persistence/memory.py:76-96` (per-process sets/dicts); OPERATIONS.md (self-hosting / writes
  sections) states "Proposal/receipt repositories in the default MDA profile are process-local. A
  restart loses pending proposals ... the code fails closed."
- Description: Without `DATABASE_URL` the engine is strictly single-instance and non-durable:
  checkpointed interrupts (a pending change awaiting resume), dedupe keys, and thread ownership live
  only in the process. A restart drops them; a second replica cannot see another's threads. The
  shipped `docker-compose.yml` sets `DATABASE_URL` for the engine, so the product avoids this — but
  the report index stays file-based even in Postgres mode (see H4-02), so "Postgres mode" is not
  fully durable/stateless.
- Impact: Any operator running `paid-media-agent serve` without Postgres (a documented path) gets a
  non-durable, non-scalable engine; the demo host silently degrades to this if `DATABASE_URL` is
  unset.
- Recommendation: Make `DATABASE_URL` mandatory for any hosted deployment (fail boot if unset
  outside explicit local-demo); move the report index to Postgres so Postgres mode is genuinely
  stateless-restartable.

## What a world-class system would need (gaps, concrete)

Proposed SLOs (12-month, per environment), measurable only after H4-08 is addressed:
- Engine API availability (non-5xx on `/health`+core routes): 99.5% monthly (≈3h39m budget).
- Assistant turn latency (demo/scripted): P95 < 1.5s, P99 < 5s. Live model turn: P95 < 45s, hard
  cap at the 120s model timeout; abort surfaced as a retryable error, not a hang.
- Report generation success rate: ≥ 99% of `/reports/run` return a valid artifact; P95 end-to-end
  < 60s (well under the 300s route / 240s client budget).
- Write-safety invariant (operational SLO, zero error budget): 0 live ad-platform mutations
  originating from the engine; kill switch, when engaged, stops writes on 100% of replicas within
  one write cycle.
- Deploy: < 1 dropped in-flight request per rollout; rollback to previous image < 5 min.

Concrete gaps to reach that bar:
1. Readiness vs liveness split; dependency probes; `/metrics` + structured logs + request IDs.
2. Lifespan-based graceful shutdown with a bounded drain; orchestrator grace ≥ drain; connection
   pool close on exit.
3. Externalise all shared state: report index → Postgres (per-org), kill switch → shared config/DB,
   remove the in-process report lock in favour of DB concurrency — so N replicas are safe.
4. Server-side per-request timeout and disconnect handling so client aborts free engine resources.
5. Resource limits (mem/CPU) + `stop_grace_period` + healthcheck `start_period`; crash-loop backoff.
6. Versioned migrations behind an advisory lock; tested rollback across langgraph checkpointer
   schema versions.
7. A documented, tested horizontal-scaling runbook (today the code is implicitly single-instance).
8. Mandatory `DATABASE_URL` for hosted deploys; fail boot otherwise.

## Disagreements / claims in docs that the code contradicts

- `engine/OPERATIONS.md` (Self-hosting): "Compose includes PDF libraries and persists checkpoints
  and local artifacts." Verified true for checkpoints/artifacts via the `engine-workspace`/`pgdata`
  volumes, BUT "persists ... artifacts" understates that the **report index is only a local file**
  (`serve_demo.py:62,246-307`), not in the DB — so Postgres mode is not fully durable/stateless and
  does not scale horizontally. Partial contradiction.
- `docker-compose.yml` implies readiness via `cloud.depends_on.engine.condition: service_healthy`,
  but `/health` (`api/app.py:80-89`) is liveness-only and never checks Postgres/model — it is not a
  readiness signal (H4-04).
- `README.md` "ما ليس جاهزًا للإنتاج بعد" is honest: it states the engine runs under one service
  token and tenant isolation is in adport tables (`markting_threads`), "not inside the engine" —
  consistent with the code. However, it does not disclose that the **report index is a single global
  file visible across tenants** (H4-02); the docs undersell this operability/isolation gap.
- `engine/OPERATIONS.md` (Writes): "A restart loses pending proposals; the code fails closed."
  Confirmed for the in-memory profile (`memory.py`, `self_hosted.py:86-89`). Not contradicted, but
  note the shipped compose uses Postgres so this applies mainly to bare `serve` without
  `DATABASE_URL`.
