## Verdict in one paragraph

This is a well-guarded approval dashboard with a chat layer in front of it, not an intelligent media-buying system. The single-write-path invariant is real and defended in depth (VERIFIED_CODE and VERIFIED_TEST, see Capability table). But the "brain" never sees a tenant's accounts: the engine host forces `PAID_MEDIA_DATA_MODE=sample` in **both** `demo` and `live` modes, so every analysis, report and proposal is computed over three shipped JSON fixtures and the accounts in `engine/config/accounts.example.toml`. In the default (`demo`) mode the "AI" is a regular expression that picks between two canned scripts, and the "proposal" is always `demo-google / g-103 → 240`. In `live` mode a real LLM reasons over the same synthetic fixtures. There is no data path from adport's tenant credential vault into the engine, and no tenant concept inside the engine (one caller identity, one workspace volume, one Postgres without an organization column, one global report index). The adport half (policy engine, pending operations, RLS, account scoping) is solid and tenant-aware; the engine half is a single-tenant demo appliance wrapped so that it cannot write. The architectural decision that will hurt most is exactly that split: the hard problem (feeding each tenant's real data to the engine, and isolating tenants inside it) was deferred, while effort went into a demo that is visually indistinguishable from intelligence.

## Findings

### J1-01 — The intelligence layer never observes tenant data; product copy says it does
- Severity: **P1** (headline capability absent while the UI and README claim it). Classification: **VERIFIED_CODE**.
- Evidence: `services/engine-demo/serve_demo.py:383-388` (live mode: `base.model_copy(update={"paid_media_data_mode": "sample"})`), `:163-166` (`assert_fail_closed` refuses anything but `sample`), `:183-191` (demo mode same); `engine/src/paid_media_agent/runtime/catalog.py:51-58` (`sample` → fixture catalog, `read_provider=None`); `engine/src/paid_media_agent/runtime/profiles.py:403-407` (accounts forced to `config/accounts.example.toml` when `sample`), `:477-478` (`FixtureReadProvider`); `engine/config/accounts.example.toml:5-20` (three fixture accounts); `engine/src/paid_media_agent/fixtures/data/{google_ads,meta_ads,reddit_ads}.json`; `platform/apps/cloud/lib/i18n/messages/assistant.ts:5` ("Ask about performance across your connected accounts"), `:16` (`placeholderLive: 'Ask about your campaigns…'`); `README.md:14,83` ("Analyses connected accounts (spend, conversions, CPA, ROAS)"). No adport→engine data client exists (`grep adport engine/src` → none).
- Description: In both engine modes the engine reads shipped synthetic JSON. A tenant who connects a real Snapchat/Google account and asks "what needs attention this week?" receives an analysis of `demo-google`, `demo-meta`, `demo-reddit`. "Live" mode changes the *model*, not the *data*. The Reports card ("AI analysis reports") likewise renders fixture numbers (`serve_demo.py:267-280` → `run_cadence_report` over `runtime.profile.accounts`).
- Impact: The product's core promise is not implemented; a paying customer would be shown analysis of accounts that are not theirs, labelled as theirs in live mode (the demo banner appears only when `MARKTING_DEMO_MODE=true`, `app/dashboard/assistant/page.tsx:21`, which is the *adport* toggle, not the engine's).
- Recommendation: Treat "engine reads tenant data through adport" as the next architectural milestone: an engine `ReadProvider` implemented over adport's normalized report API with a per-tenant, scope-limited token; a per-tenant `AccountRegistry` derived from `ad_accounts`; until then, remove the "connected accounts" copy and show the synthetic-data banner whenever the engine is in `sample` mode (i.e. always, today).

### J1-02 — Engine report surface is global across tenants
- Severity: **P2** today (content is synthetic), would be **P0** the moment the engine sees tenant data. Classification: **VERIFIED_CODE**.
- Evidence: `services/engine-demo/serve_demo.py:62` (one index file `markting-reports.json`), `:246-264` (global `workspace/out` index, no tenant key), `:304-306` (`entries[:50]` global cap), `:355-358` (`GET /reports` returns the whole index), `:360-374` (any valid token downloads any `rpt_*/art_*` file); `platform/apps/cloud/app/api/reports/engine/route.ts:16-24` (any signed-in principal of any organization lists all runs), `app/api/reports/engine/[name]/route.ts:10-15` (any signed-in principal downloads any file); `requested_by` is always the single caller `adport-bridge` (`serve_demo.py:343,268`; `.env.example:44`).
- Description: Report runs and files are not attributed to an organization anywhere. Tenant A's weekly run appears in tenant B's Reports page; 51 runs across all tenants evict the oldest regardless of owner.
- Impact: Cross-tenant visibility by construction. Harmless only because the data is fixture data (J1-01).
- Recommendation: Key the index and the file namespace by organization (or move report metadata into adport Postgres with `organization_id`), pass the organization through the engine call, and filter in the cloud route.

### J1-03 — Demo model is process-global mutable state shared by all threads and tenants
- Severity: **P2** (default mode; correctness under concurrency). Classification: **VERIFIED_CODE** for the shared state; **INFERRED** for the interleaving (not reproduced at runtime).
- Evidence: `services/engine-demo/serve_demo.py:194-198` (one `LoopingScriptedChatModel` per process), `:224-227` (passed as the single `model` to `build_agent_components`), `:92-115` (`_generate` mutates `self.steps`, `self.call_count`, `self.seen_human_messages` and chooses the script from `len(humans)` of *whatever thread is calling*); `engine/.venv/.../langchain_core/language_models/chat_models.py:2695-2697` (`_agenerate` runs `_generate` in a thread executor, so two concurrent `ainvoke`s interleave); `engine/src/paid_media_agent/surfaces/api/app.py:91-101` (async endpoint, no serialization).
- Description: Thread A (3 human messages, analysis script at step 2) and thread B (1 human message, write intent) calling concurrently: B's first call resets the script to `write_steps` and `call_count=0`; A's next call sees `len(humans)=3 != seen` and resets again, etc. Steps such as `_read_all`/`_compare` read `last_tool_results` from the other thread's messages. Outcomes range from "Script exhausted" prose to a proposal emitted on the wrong thread.
- Impact: The only mode that works without a model key is unreliable with more than one concurrent user.
- Recommendation: Build the scripted model per request (or key state by `thread_id` from the run config), or make the demo path explicitly single-flight.

### J1-04 — "Intent detection" is a regex and the proposal is canned; the mixed demo/live matrix is unguarded
- Severity: **P2** (misleading approval UX; financial risk only under a deliberate misconfiguration). Classification: **VERIFIED_CODE**.
- Evidence: `services/engine-demo/serve_demo.py:63-66` (`WRITE_INTENT` matches `change|budget|increase|reduce|pause|ميزاني|غيّر…`), `:109-111`; `engine/src/paid_media_agent/testing/demo_script.py:158-170` (always `demo-google`, `google_ads__update_campaign_budget`, `g-103`, `240`, reason "Performance Max spend fell while CPA rose…"); `platform/apps/cloud/app/dashboard/approvals/page.tsx:37` (that reason is rendered to the approver as the source rationale); independent toggles: `platform/apps/cloud/lib/markting/env.ts:237` (`MARKTING_DEMO_MODE`) vs `serve_demo.py:132-136` (`MARKTING_ENGINE_MODE`), nothing cross-checks them; alias rows may bind any alias to any provider (`lib/markting/repository.ts:190-196`, `translate.ts:133-145`).
- Description: Any message containing "change" or "budget" ("why did the budget change?") yields a budget-cut proposal to 240 for a campaign the user never mentioned, with a fabricated justification. With `MARKTING_DEMO_MODE=false` and an alias row `demo-google → google/<real account>` with `targets {g-103: <real campaign>}`, that canned proposal becomes a real `google_set_budget` preview of 240 USD/day on a real campaign, shown on Approvals with the fabricated reason. Human approval and the 25 % cap still stand, so this is not P0.
- Impact: Approvers may be persuaded by prose that is not analysis. The architecture does not prevent a scripted engine from targeting real accounts.
- Recommendation: Refuse to start (or refuse to bridge) when `MARKTING_ENGINE_MODE=demo` and `MARKTING_DEMO_MODE=false`; mark proposals from the scripted model with a `synthetic: true` flag the bridge treats as unsupported unless the alias is `sandbox`; never render engine prose as "reason" without a "model-generated / scripted" label.

### J1-05 — Live mode shares one filesystem workspace and one checkpoint store across all tenants
- Severity: **P1** for `live` mode (not reachable in the shipped default). Classification: **VERIFIED_CODE** (shared mounts and permissions); the cross-tenant *read* is a direct consequence, not runtime-verified.
- Evidence: `engine/src/paid_media_agent/assembly.py:59,211` (model keeps `ls, read_file, write_file, edit_file, glob, grep`); `engine/src/paid_media_agent/runtime/local.py:133-155` (write allowed under `/workspace/**`, reads allowed everywhere not denied), `:183` (`FilesystemBackend(root_dir=project_root)`), `docker-compose.yml:55-57` (one `engine-workspace` volume for the whole engine); `assembly.py:251-253` (`ResultOffloadMiddleware` writes tool results into that workspace); `engine/src/paid_media_agent/persistence/postgres.py:12-42` (`pma_*` tables have `thread_id` but no tenant column); `serve_demo.py:211-219` (single `DATABASE_URL`, single checkpointer). The scripted demo model never calls filesystem tools, so this is live-only.
- Description: In `live` mode an LLM acting for tenant A can `read_file` artifacts and notes produced in tenant B's threads, and can `write_file` into `/workspace/**` content that tenant B's model will later read (persistent prompt-injection vector). All tenants' LangGraph checkpoints and proposals sit in one database distinguishable only by the thread-id string convention.
- Impact: Cross-tenant information flow inside the engine; since J1-01 holds, what leaks today is users' typed messages, model prose and fixture analysis, not account data.
- Recommendation: Before enabling `live` for more than one organization: per-tenant workspace roots (or deny filesystem tools entirely in the host), tenant id in engine tables and checkpoint namespaces, and a tenant-scoped artifact store.

### J1-06 — Unsupported proposals are never handed back to the engine; the thread stays interrupted
- Severity: **P2**. Classification: **VERIFIED_CODE**.
- Evidence: `platform/apps/cloud/lib/markting/bridge.ts:136-141` (unsupported branch records and returns; no `handoff`), vs `:157` and `:169` (handoff only on policy rejection and success); `engine/src/paid_media_agent/surfaces/runner.py:91-93,134` (`latest_proposal` returns the last proposal on the thread regardless of state), `:139-141`; `platform/apps/cloud/lib/markting/assistant.ts:51` (bridges whenever `state === 'awaiting_approval'`).
- Description: When no alias row maps `account_ref` (the first-run state of every real tenant with `MARKTING_DEMO_MODE=false`, since `loadAliasMap` adds `SANDBOX_ALIASES` only in demo, `repository.ts:183`), the engine proposal stays `awaiting_approval` and the graph stays interrupted. Every later message on that thread re-reports the same stale proposal and the bridge re-records it as unsupported.
- Impact: A real tenant's first attempted change wedges the conversation thread.
- Recommendation: Call `handoff` (reject with "unsupported by adport") in the unsupported branch too, and have the runner only surface proposals in `awaiting_approval`.

### J1-07 — Synchronous, non-idempotent, single-process chat path
- Severity: **P2** (scale blocker; one tenant can starve all). Classification: **VERIFIED_CODE**.
- Evidence: `platform/apps/cloud/lib/markting/env.ts:241` (one HTTP call up to 240 s, max 900 s), `app/api/assistant/messages/route.ts:7` (`maxDuration = 300`), `engine-client.ts:113-116` (blocking POST, no streaming); `serve_demo.py:411-417` (one uvicorn server, one process); `platform/apps/cloud/lib/cloud/repository.ts:355` (cloud rate limit 120/min per user); no engine-side limit; retry of the same `text` re-runs the graph and can create a second proposal (no idempotency key in `MessageIn`, `surfaces/api/app.py:16-17`).
- Description: Each assistant turn pins a Next.js request and an engine coroutine for up to four minutes. The engine has no queue, no per-tenant fairness and no horizontal-scaling story (see J1-11).
- Recommendation: Job table + worker + SSE/streaming to the browser; idempotency key per client turn; per-tenant concurrency limits at the engine host.

### J1-08 — The engine container receives every secret in `.env`
- Severity: **P2** (least privilege). Classification: **VERIFIED_CODE**.
- Evidence: `docker-compose.yml:39` (`env_file: .env` for `engine`); `.env.example:7,12-14,21-22,34-35` (`SUPABASE_SECRET_KEY`, `ADPORT_CLOUD_ENCRYPTION_KEY`, `ADPORT_API_KEY_PEPPER`, `ADPORT_MCP_OAUTH_SIGNING_KEY`, `SNAPCHAT_CLIENT_SECRET`, `STRIPE_SECRET_KEY`); `engine/src/paid_media_agent/assembly.py:293-306` (`RedactionMiddleware` covers only the engine's own secrets).
- Description: The process that runs an LLM agent holds the adport vault encryption key and the Supabase service key it never needs. The virtual filesystem backend (`local.py:183`) does not expose `/proc`, so I found no in-model path to read them; the exposure is operational (crash dumps, logs, `docker inspect`, a future shell tool).
- Recommendation: Pass only `MARKTING_ENGINE_TOKEN`, `MARKTING_ENGINE_MODE`, model key and `PAID_MEDIA_*` to the engine service.

### J1-09 — Policy depth is far below what a media buyer needs; budget caps are not re-checked at apply
- Severity: **P3** (GAP where not claimed; the apply-time omission is an upstream defect already noted in `docs/TODO.md:104`). Classification: **VERIFIED_CODE**.
- Evidence: `platform/packages/core/src/policy/policy.ts:172-185` (only `%` delta, absolute cap, protected accounts, TTL; `require_validation` unused), `engine.ts:110-113` (apply re-runs `checkStaticPolicy` only), `:133-153` (cap is per operation, relative to the *current* value); `lib/i18n/messages/approvals.ts:5` ("Apply performs that second call through the same policy engine" — implies full re-check).
- Description: Ten successive +25 % approvals multiply a budget 9.3×; nothing tracks cumulative daily change, cooldowns, per-account spend ceilings or anomaly context. The budget preview compares against the budget at *validate* time; apply up to 15 minutes later does not re-read it.
- Recommendation: Cumulative and time-windowed caps, cooldowns per target, re-run `checkBudgetPolicy` against a fresh preview at apply.

### J1-10 — Pending-row lookup is an O(n) scan capped at 200
- Severity: **P3**. Classification: **VERIFIED_CODE**.
- Evidence: `platform/apps/cloud/app/api/approvals/[id]/apply/route.ts:20`, `reject/route.ts:13` (`listPendingOperations(org, 200).find(...)`); `lib/cloud/repository.ts:697-705` (ordered by `created_at desc limit`).
- Description: A valid pending operation older than the 200 most recent cannot be applied or rejected from the dashboard (404), and every action loads 200 JSON rows.
- Recommendation: Use `PostgresPendingStore.get(id)` (already tenant-scoped, `repository.ts:385-412`) plus `created_by` from a single-row query.

### J1-11 — Engine host state lives in files on one volume; cannot run more than one replica
- Severity: **P3** (architecture/scale). Classification: **VERIFIED_CODE**.
- Evidence: `serve_demo.py:246-264,304-306` (report index read-modify-write), `:324,344` (in-process `asyncio.Lock` is the only serialization), `:173-180` (kill switch is a file), `docker-compose.yml:55-57` (single named volume).
- Description: Two engine replicas would race on the index file and would not share the kill-switch decision except via the shared volume; the demo model state (J1-03) is per process. Horizontal scaling and blue/green deploys are precluded.
- Recommendation: Move report metadata and the kill switch to Postgres (adport's or the engine's), with tenant keys.

### J1-12 — Snapchat exists only on the adport side of the bridge

### J1-13 — Seeded `sandbox` alias rows break non-demo mode with a 500

- Evidence: `infra/seed/seed-demo.mjs:50-62` (aliases inserted with `provider='sandbox'`); `lib/markting/translate.ts:139-141` (sandbox bindings bypass the platform/provider check), `:105,116` (tool `sandbox_set_budget`); `lib/markting/runtime.ts:215` (non-demo → `createTenantRuntime`, which registers no sandbox module, `lib/cloud/runtime.ts:44-146`); `bridge.ts:146` (`registry.get` throws, `packages/core/src/tools/registry.ts:76-80`) outside the `BridgeAccessError` catch → `apiError` → "Internal server error" (`lib/http.ts:24-33`).

## What is genuinely good (so the above is not read as "nothing works")

- Single write path, defended four ways on the engine side (`ProposalOnlyWriteProvider` raising, kill switch engaged at boot, empty approver set, `sample` data mode: `serve_demo.py:69-81,139-180`) and on the adport side by hash-bound two-step writes (`packages/core/src/policy/engine.ts:58-125`, `tools/write.ts:39-66`), with the client refusing `approve`/`edit` paths (`engine-client.ts:61-79`). **VERIFIED_CODE + VERIFIED_TEST** (pytest 7/7, vitest 53/53).

- Translation is allowlist-based and refuses rather than guesses (`translate.ts:129-160`); the alias indirection keeps provider ids out of the engine.
- `engine/` is untouched (git diff empty), honest about it in `UPSTREAM.md`.

## What architectural decisions will hurt most at scale

1. **Engine singletons.** Process-global model state (J1-03), file-based report index and kill switch (J1-11), one workspace volume (J1-05), one caller identity and one DB without tenant keys. None of it can be sharded or replicated per tenant; the engine must be re-architected before the second replica, not after.
2. **Synchronous four-minute HTTP chat** through Next.js into a single uvicorn process (J1-07). Latency, retries and fairness are all unsolved.
3. **Alias indirection over a global fixture alias set.** `markting_account_aliases` maps *per org* onto an alias namespace that is *global* in the engine (`accounts.example.toml`). It cannot express "tenant X has 7 Google accounts"; it only re-labels the three fixture aliases. Real tenancy needs per-tenant account registries inside the engine run config.
4. **15-minute pending TTL** versus any human-speed approval channel (WhatsApp is planned, `docs/TODO.md:78`): proposals will expire; re-validation is not designed.
5. **O(n) dashboard lookups** (J1-10) and global `[:50]` report eviction (J1-02).

## What a previous team likely got wrong

- Picked a single-tenant, operator-configured agent (accounts in a TOML, identity from a static token map, a filesystem workspace) as the multi-tenant brain and then spent the effort on a bridge *out* of it, not on a data path *into* it. The hard problem — the engine reading each tenant's real accounts through adport's vault — has no code at all.
- Optimized for a convincing demo: regex intent detection and a canned proposal flow into the *real* Approvals page with a fabricated rationale, so the demo is indistinguishable from intelligence (J1-04). Two independent demo toggles make the matrix hard to reason about.
- Made "do not modify `engine/`" a goal in itself. The host then imports a private symbol (`_postgres_checkpointer`, `serve_demo.py:46`) and rebuilds the runtime by hand (`:201-240`), so upstream upgrades are fragile anyway, while the constraint blocked adding tenancy where it belongs.
- Documented limitations candidly in `README.md:124-131` and `docs/TODO.md`, but shipped product copy that contradicts them (`assistant.ts:5,16`, `README.md:14,83`).

## What a world-class system would need (concrete gaps)

1. A tenant data plane for the engine: an engine `ReadProvider` over adport's normalized `report` tools, authenticated per organization with a scoped token; per-tenant `AccountRegistry` built from `ad_accounts`; engine tables and checkpoint namespaces keyed by `organization_id`.
2. Isolation inside the engine: per-tenant workspace roots or no filesystem tools; per-tenant artifact store; report index in Postgres with tenant keys.
3. An asynchronous job model: queue + workers + streaming; idempotency keys per chat turn; per-tenant concurrency limits; engine replicas.
4. A real decision loop: scheduled anomaly detection over tenant data → typed proposals with evidence artifacts → approval → bounded execution → readback → measurement against the stated `measurement_plan` (the engine already has the receipt/readback machinery, `tools/writes.py`; nothing drives it).
5. Policy worthy of money: cumulative and windowed caps, cooldowns per target, per-account monthly ceilings, apply-time re-preview, mandatory "reason is model-generated" labelling, approval quorum/escalation, longer TTL with re-validation.
6. Evaluation: a backtest/eval harness for recommendations on historical tenant data, not only fixture determinism tests.
7. Operational hygiene: per-service env allowlists (J1-08), one engine token per environment and ideally per tenant, CI that builds images and runs `make test`.
