# D2 — TypeScript architect

Audit of TypeScript quality and module boundaries across `platform/packages/core`, the eleven provider
packages, `platform/packages/mcp`, and `platform/apps/cloud/lib` (upstream `cloud/` plus the markting-ai
`markting/` glue). Scope: zod typing of tool inputs/outputs, `any`/casts, unchecked JSON coming back from
Postgres `jsonb`, `AdportError` codes, structural vs nominal store contracts, duplicated types, dead exports.
All paths are relative to `/home/user/markting-ai`.

Headline: the TypeScript surface is in materially good shape — `pnpm typecheck` is clean under
`strict` + `noUncheckedIndexedAccess`, there is **zero** `any` in first-party source, a single zod 4.4.3 is
installed, and every write path is zod-validated at the registry boundary and re-validated on apply. The
defects found are P3 quality/maintainability issues (boundary types asserted instead of parsed, four
parallel error hierarchies glued by string matching, duplicated types, dead exports, no linter). Nothing
rises to P0–P2 within this workstream. One documentation claim (ARCHITECTURE.md §2.4) is contradicted by
the code.

## Findings

### D2-01 — Postgres stores satisfy core contracts only structurally; no `implements` on two of three
- Severity: **P3** — Classification: **VERIFIED_CODE**
- Evidence: `platform/apps/cloud/lib/cloud/repository.ts:371` (`export class PostgresPendingStore {` — no `implements PendingOperationStore`), `:428` (`export class PostgresAuditStore {` — no `implements AuditEntryStore`), `:436` (`PostgresFindingsStore implements FindingsRepository` — correct). Contracts: `platform/packages/core/src/policy/pending.ts:427-432`, `policy/audit.ts:502-504`. Use sites that force structural checking: `lib/cloud/runtime.ts:140`, `lib/markting/runtime.ts:24` (`new PolicyEngine(policy, new PostgresPendingStore(principal), new PostgresAuditStore(principal))`).
- Description: Because both instances are passed straight into `PolicyEngine`'s typed constructor, any shape drift still fails `tsc` — but at the call site, not at the class, and only as long as every construction path flows through that constructor. `PostgresPendingStore.delete` and `sweep` set `consumed_at` rather than deleting (`repository.ts:413-425`) — a legitimate semantic difference the interface's doc comments do not describe. ARCHITECTURE.md:221 already records the missing `implements`.
- Impact: Maintainability only; correctness is enforced today by the constructor parameter types.
- Recommendation: add `implements PendingOperationStore` / `implements AuditEntryStore`; document the consume-not-delete semantics in the core interface JSDoc so other hosted stores copy it.

### D2-02 — `jsonb` columns are asserted into TypeScript types, never parsed (except policy and sandbox state)
- Severity: **P3** — Classification: **VERIFIED_CODE**
- Evidence (unchecked): `repository.ts:386-394` (`operation: PendingOperation['op']; preview: PendingOperation['preview']` from `public.pending_operations`), `:441-467` (`finding: AuditFinding` from `public.findings`), `:684-704` (`PendingOperationRow`), `lib/markting/repository.ts:41-47` (`targets: Record<string, string>`, `row.provider as AliasBinding['provider']`), `:91-104` (`select *` into `EngineProposalRow` with `proposal`/`translation` jsonb). Evidence (checked, the good pattern): `repository.ts:52-55` (`policySchema.parse(rows[0]?.policy ?? {})`), `lib/markting/repository.ts:124` (`sandboxStateSchema.parse(rows[0].campaigns)`). DB side: `markting_account_aliases.provider` CHECK is `~ '^[a-z][a-z0-9_]*$'` (`supabase/migrations/20261002000000_markting_bridge.sql:34`) while the TS type is the 6-literal `BridgeProvider` (`translate.ts:19`).
- Description: Postgres `jsonb` comes back as `unknown`; the code uses postgres.js generic parameters (`db()<Array<{…}>>`, 64 such sites in `apps/cloud/lib`) to *assert* the row type. The rows are tenant-scoped and were written by this codebase, so the practical risk is a malformed/edited row producing a `TypeError` (500) rather than a typed `INVALID_INPUT`. I checked the write path specifically: apply re-sends the stored payload through `registry.call` (`lib/markting/bridge.ts:119-121`) so zod re-validates and `PolicyEngine.apply` re-hashes (`core/src/policy/engine.ts:349`) — the unchecked read cannot smuggle an unvalidated payload to a provider. The `provider` cast in `loadAliasMap` is also harmless in practice because `translateProposal` compares `binding.provider` to the platform-derived provider before dispatching (`translate.ts:138-141`).
- Impact: Fragility on schema drift and manual DB edits; inconsistent with the two places that do parse.
- Recommendation: parse `operation`/`preview`/`finding`/`translation`/`targets` through zod on read (core already has `writeOutput.shape.preview` and `findingOutput`; a `writeOperationSchema` is missing and should be added next to `outputs.ts`), and tighten the `provider` CHECK to the bridge's allowlist.

### D2-03 — Six providers cast `op.payload as never`; five re-validate with zod
- Severity: **P3** — Classification: **VERIFIED_CODE**
- Evidence: `platform/packages/google/src/provider.ts:273-275` (`// Tool input was already zod-validated at the registry boundary.` / `const payload = op.payload as never;`), `meta/src/provider.ts:294`, `microsoft/src/provider.ts:274`, `reddit/src/provider.ts:250`, `tiktok/src/provider.ts:240`, `apple/src/provider.ts:244`. Counter-examples: `snapchat/src/provider.ts:96,116`, `linkedin/src/provider.ts:122,158`, `pinterest/src/provider.ts:132,145`, `spotify/src/provider.ts:121-149`, `x/src/writes.ts:14,35`, `core/src/testing/synthetic-provider.ts:91`, `apps/cloud/lib/markting/sandbox-provider.ts:154,166`. Contract: `core/src/provider.ts:188` (`payload: Record<string, unknown>`), `:246-247` ("Only the policy engine may call this.").
- Description: `never` is assignable to every parameter type, so the per-tool `plan*` methods receive an unverified object. The invariant holds today because the only caller is `PolicyEngine`, which is only reached through `guardedWriteTool` after `ToolRegistry.call` parsed the input (`core/src/tools/registry.ts:84-89`, `tools/write.ts:130-142`). It is a defence-in-depth gap, not a live bug: `AdProvider.previewWrite/applyWrite` are public interface methods and the invariant is enforced by convention, not by type.
- Impact: A future direct caller (e.g. a hosted "retry from stored row" path) would bypass validation in these six providers but not in the other five.
- Recommendation: either make `WriteOperation.payload` generic and carry the parsed type, or have each provider `schema.parse(op.payload)` as the newer providers do (cheap; the schemas already exist in their `tools.ts`).

### D2-04 — Tool `output` schemas are declared but never enforced by the registry; the bridge re-types the result by hand
- Severity: **P3** — Classification: **VERIFIED_CODE / VERIFIED_TEST**
- Evidence: `core/src/tools/registry.ts:82-90` (`call` parses `input`, returns `tool.handler(...)` without touching `tool.output`), `:33` (`output?: z.ZodType` documented as "Successful result contract, shared by all transports"). REST returns the raw result: `apps/cloud/app/api/v1/tools/[tool]/route.ts:13`. Bridge: `lib/markting/bridge.ts:76` (`as PreviewOutput`), `:12-19` (hand-written `PreviewOutput` duplicating `writeOutput`, `core/src/tools/outputs.ts:231-239`, with `budgetDeltas: unknown[]`). `writeOutput` and the other output schemas are not exported from `core/src/index.ts:1-66`. MCP is the only transport that exercises outputs, through SDK client-side validation (`packages/mcp/src/index.ts:129-142`, test `packages/mcp/test/server.test.ts:92-130`, 82 tests passed, exit 0).
- Description: The output contract is advisory in core. The bridge compensates with a cast plus a manual check (`bridge.ts:85-87`) instead of `definition.output?.parse(result)`, which is available on the `AnyToolDefinition` it already fetched (`bridge.ts:71`).
- Impact: A provider returning an off-contract shape passes REST and the bridge silently; the MCP client would reject it. Duplicated type drifts from the schema.
- Recommendation: validate `output` in `ToolRegistry.call` (or at least in `bridgeProposal`), export the output schemas from core, and derive `PreviewOutput` as `z.infer<typeof writeOutput>`.

### D2-05 — Four parallel error hierarchies glued by string matching; `AdportError` codes stretched semantically
- Severity: **P3** — Classification: **VERIFIED_CODE**
- Evidence: `core/src/errors.ts:67-75` (8-code closed union). Cloud adds `HttpError` (`lib/http.ts:5`), `PlanLimitError` (`lib/cloud/plan-limit.ts`), `BridgeAccessError` (`lib/markting/bridge.ts:54`), `EngineError` (`lib/markting/engine-client.ts:47`). Authentication failure is a plain `Error('Authentication required.')` (`lib/cloud/auth.ts:12`, `lib/cloud/support.ts:24`) re-identified by message equality in six routes: `app/api/approvals/[id]/apply/route.ts:30`, `approvals/[id]/reject/route.ts:24`, `assistant/messages/route.ts:17`, `reports/engine/route.ts:10`, `reports/engine/[name]/route.ts:28`, `dashboard/summary/route.ts:17`. Code misuse: `lib/markting/sandbox-provider.ts:92` (`POLICY_VIOLATION` for "account not in sandbox" → 403 via `http.ts:15`), `sandbox-provider.ts:77` and `lib/markting/repository.ts:140` (`PENDING_MISMATCH` for optimistic-concurrency failure of sandbox state), `core/src/audit/tools.ts:107` (`PROVIDER_ERROR` for a missing registry, a programming error → 502). `POLICY_VIOLATION` carries `details: { policy: this.policy }` (`core/src/policy/engine.ts:408`), serialised to MCP callers by `err.toJSON()` (`packages/mcp/src/index.ts:188`).
- Description: Upstream's `POLICY_VIOLATION` reuse for account scope (`lib/cloud/account-scope.ts:22-26`, `core/src/testing/synthetic-provider.ts:42`) set the precedent the markting glue copied. The `PENDING_MISMATCH` reuse happens to map to a reasonable 409, but the message "Request a new preview" is emitted from a store, not from the policy engine, and the three "mismatch" meanings (hash, provider, CAS) are indistinguishable to clients. The string-matched auth error is fragile: one edit of the message silently turns 401s into 500s (`http.ts:12-22` falls through to 500 for plain `Error`).
- Impact: Maintainability and client-facing error fidelity; no security impact found (policy leak is to the tenant's own agent, and REST only returns `message`, `http.ts:26-32`).
- Recommendation: introduce a typed `AuthenticationError extends HttpError` and map it centrally in `apiError`; add `CONFLICT`/`NOT_FOUND`-style codes or a cloud-side `CloudError` with its own union instead of overloading core codes; drop `policy` from `POLICY_VIOLATION.details` or whitelist fields.

### D2-06 — Duplicated types and logic across module boundaries
- Severity: **P3** — Classification: **VERIFIED_CODE**
- Evidence:
  - `canonicalAccountId` copied verbatim: `core/src/tools/builtin.ts:17-21` vs `apps/cloud/lib/cloud/account-scope.ts:13-17` (upstream).
  - `dateRangeSchema` duplicated: `core/src/tools/builtin.ts:9-15` vs `core/src/audit/tools.ts:9-15` (upstream).
  - Engine report shape: `lib/markting/engine-client.ts:29-45` (`EngineReportRun`) vs `app/dashboard/reports/engine-reports.tsx:6-12` (`ReportRun`, hand-typed `summary.platforms`).
  - Assistant turn shape: `lib/markting/assistant.ts:17-23` (`AssistantTurn`) + `lib/markting/bridge.ts:49-52` (`BridgeResult`) vs `app/dashboard/assistant/assistant-chat.tsx:7-17` (`BridgeView`, `TurnResponse`).
  - Provenance record: `lib/markting/bridge.ts:21-34` (`BridgeRecord`) vs `lib/markting/repository.ts:72-74` (inline parameter type of `recordEngineProposal`) vs `:64-70` (`EngineProposalRow`).
  - `PreviewOutput` vs `writeOutput` (see D2-04).
  - `SandboxProvider` (`lib/markting/sandbox-provider.ts:85-186`) is a near-line-for-line adaptation of `SyntheticProvider` (`core/src/testing/synthetic-provider.ts:35-130`) including `InMemorySandboxStore` vs `SyntheticStateStore`; the author's comment explains the intent (different tool-name prefixes to pass the production-connector filter, `sandbox-provider.ts:7-8`, `packages/mcp/src/index.ts:91`).
- Description: Client components re-declare server response types instead of importing `type`-only exports from `lib/markting`, so server and browser contracts can drift without a type error.
- Impact: Maintainability; one real drift exists already — `ReportRun.summary.platforms` fields are typed on the client (`engine-reports.tsx:12`) but `EngineReportRun.summary` is `Record<string, unknown>` on the server (`engine-client.ts:44`), i.e. the client claims more than the server verifies.
- Recommendation: export `type AssistantTurn`, `type BridgeResult`, `type EngineReportRun` from the lib and import them in the client components; factor `canonicalAccountId`/`dateRangeSchema` into `core/src/model.ts`; consider parameterising `SyntheticProvider` by id/seed instead of copying it.

- Evidence (zero references outside the defining file, excluding tests where noted): `lib/markting/repository.ts:29` `listThreads`, `:62` `BridgeStatus` (type), `:10` `ThreadRow` (type); `lib/markting/engine-client.ts:118` `getProposal`, `:20-27` `EngineHealth`, `:111` `health()` (test-only, `test/markting-engine-client.test.ts:52`); `lib/markting/env.ts:31` `resetMarktingEnvForTests` (unused even by tests); `lib/markting/translate.ts:65` `EngineOperation`, `:76` `engineOperation`, `:84` `MAX_DAILY_BUDGET_MICROS` (used internally, exported needlessly); `lib/markting/sandbox-provider.ts:31` `sandboxCampaignSchema`; `lib/markting/bridge.ts:12` `PreviewOutput`. Upstream: `lib/cloud/repository.ts:264` `removeGoogleConnection`. Generated Supabase types `lib/supabase/database.types.ts` contain 0 `markting_*` tables and lack `waitlist`, `mcp_oauth*`, `provider_account_selections`, `billing_events` (only used to type the auth clients, `lib/supabase/{admin,browser,proxy,server}.ts`).
- Description: Moderate surface noise; `getProposal` is notable because `engine-client.ts:3-5` advertises a deliberately minimal API ("no approve or edit") and `FORBIDDEN_PATHS` (`:61`) guards it — an unused `getProposal` widens the surface for no caller.

- Recommendation: delete or un-export; regenerate `database.types.ts` or remove it if the typed Supabase client is only used for auth.

### D2-08 — Approval routes locate the pending row by scanning a 200-row list instead of a keyed query
- Severity: **P3** — Classification: **VERIFIED_CODE**
- Evidence: `app/api/approvals/[id]/apply/route.ts:20` and `approvals/[id]/reject/route.ts:13` (`(await listPendingOperations(principal.organizationId, 200)).find((candidate) => candidate.id === id)`); `listPendingOperations` orders newest-first with `limit` (`lib/cloud/repository.ts:696-704`). `apply/route.ts:26` re-casts `row.operation as { tool: string; accountId: string; payload: Record<string, unknown> }` although `PendingOperationRow.operation` is already `PendingOperation['op']` (`repository.ts:688`).
- Description: With more than 200 live pending operations in one organization a valid id returns 404 "not found, expired, or already applied"; every call also deserialises up to 200 jsonb payloads. The redundant cast hides that the row type already carries the needed fields.
- Impact: Reliability at scale (unlikely in the demo, plausible for an agency tenant); no safety impact — `PolicyEngine.apply` still re-reads by id (`core/src/policy/engine.ts:335`).
- Recommendation: add `getPendingOperation(organizationId, id)` to the repository and drop the cast.

### D2-09 — No linter in the workspace; `tsc` is the only static gate
- Severity: **P3** — Classification: **VERIFIED_RUNTIME**
- Evidence: command #12 (no eslint/biome/prettier binaries), `apps/cloud/package.json` scripts `dev/build/build:standalone/start/typecheck/test/clean` only; root `platform/package.json:11-17` has no lint task; the single `eslint-disable-line` comment (`app/dashboard/reports/engine-reports.tsx:30`) is inert.
- Description: Rules like `react-hooks/exhaustive-deps`, `no-floating-promises`, consistent-type-imports and import-cycle detection are not enforced anywhere. This is inherited from upstream adport, and the markting additions follow suit.
- Impact: Quality; the specific hook the disable comment targets does run `load()` once on mount with stale closure semantics by design.
- Recommendation: add `eslint` + `typescript-eslint` (type-aware) with `no-floating-promises`, `consistent-type-imports`, `no-unused-vars` (would have caught D2-07), wired into turbo.

### D2-10 — `as never` as the idiom for postgres.js `json()` and audit `details`
- Severity: **P3** — Classification: **VERIFIED_CODE**
- Evidence: 13 sites, e.g. `lib/cloud/repository.ts:288` (`db().json(entry.details as never)`), `:380` (`db().json(operation.op as never)`), `:481`, `:679`; `lib/markting/repository.ts:55,82,127,136-137`. Also `lib/cloud/runtime.ts:66` (`as typeof expected`), `:57` (`provider.id as keyof typeof enabledAccountIds`), `:63` (`credentials[provider]!`).
- Description: postgres.js's `json()` wants a `JSONValue`; the code opts out with `never` instead of narrowing or defining a `JsonValue`-compatible type. Harmless for the serialised values (all are plain objects), but it is the same erasure pattern as D2-03 and makes the 13 sites invisible to future type tightening.
- Recommendation: a small `toJson(value: object): JSONValue` helper with one documented cast.

### D2-11 — `defineTool` generic erasure (`handler: (input: never, …)`) is sound but leaks into every transport
- Severity: **P3** (observation, no defect) — Classification: **VERIFIED_CODE**
- Evidence: `core/src/tools/registry.ts:35` (`handler: (input: never, ctx) => Promise<unknown>`), `:57` (`as AnyToolDefinition`), `:89` (`tool.handler(parsed.data as never, ctx)`), `tools/write.ts:131-134` (`raw as Record<string, unknown> & {…}`), `lib/markting/sandbox-provider.ts:196-201` (spreads a `guardedWriteTool` result to override `annotations`, bypassing `defineTool`'s normalisation at `registry.ts:50-56`).
- Description: The design intentionally erases the input generic so a heterogeneous `AnyToolDefinition[]` can live in one registry; correctness rests on `call` always parsing with the same `input` schema that typed the handler — which it does. The sandbox annotation override is explicit and sets `openWorld: false`, which is correct for a credential-free provider, but it is the only place in the repo that mutates a tool definition after construction.
- Recommendation: expose an `annotations` override on `guardedWriteTool` instead of spreading its result.

## What a world-class system would need

5. **Type-aware ESLint** with `no-floating-promises`, `consistent-type-imports`, `no-unused-vars`, import cycles; plus `knip` or `ts-prune` in CI for dead exports.
