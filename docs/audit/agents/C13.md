# C13 — AI safety / autonomous-action specialist

Goal: try to break the invariant **AI proposes → policy preview → human approval → apply**.
Enumerate every path by which a write can reach a provider and whether each requires a prior
`validate` with identical arguments and a human approval.

## Findings

### C13-01 — Human approval is NOT enforced on adport's own REST and MCP write surfaces; only the dashboard enforces it
- Severity: **P1**
- Classification: **VERIFIED_CODE**
- Evidence: `platform/packages/core/src/tools/write.ts:52-65` (same handler validates when `pending_operation_id` absent, applies when present); `platform/apps/cloud/app/api/v1/tools/[tool]/route.ts:7-13` (only `requireScope(tools:write)`, then `registry.call(tool, input)` — a caller passes `pending_operation_id` in the same body to apply); `platform/apps/cloud/app/mcp/route.ts:40-63` + `platform/packages/mcp/src/index.ts:121-184` (MCP registers the write tool whenever scope+plan allow; the `approval:{arguments}` object at index.ts:176-179 is an *advisory hint in structuredContent*, not an enforced interrupt); contrast `platform/apps/cloud/app/api/approvals/[id]/apply/route.ts:18-24` where owner/admin role + non-self are enforced.
- Description: The product invariant "human approval → apply" is implemented only in the markting **dashboard** apply route. On the REST (`/api/v1/tools/{tool}`) and MCP (`/mcp`) surfaces the two-step contract is validate-then-apply by the **same** principal, with no second human and no server-side interrupt. The MCP connector is explicitly built for autonomous AI hosts, so an AI holding a `tools:write` key can validate and immediately apply a real mutation (budget change, status flip) constrained only by the policy rails (budget caps, protected accounts, paused-creation) and audit logging.
- Impact: An autonomous agent (or any script) with a `tools:write` credential performs unattended ad-platform writes. The "human approval" guarantee advertised for the product does not hold for the AI-facing surfaces; it holds only for the human dashboard.
- Recommendation: If "human approval" is meant to be universal, enforce an out-of-band approver on apply for REST/MCP (e.g. apply must reference a pending row whose `created_by`/key differs from an approver who clicked in the dashboard, or require a dashboard approval step before any apply token is honored). Otherwise document explicitly that REST/MCP apply is self-service within rails and scope the keys/plans that may hold `tools:write` accordingly.

### C13-02 — Pending-operation consumption is not atomic and apply passes no idempotency key → concurrent/duplicate apply can execute a live mutation twice
- Severity: **P2**
- Classification: **VERIFIED_CODE**
- Evidence: `platform/packages/core/src/policy/engine.ts:87-125` (`apply` does `get` → `provider.applyWrite` → `pending.delete`, no lock/transaction); `platform/apps/cloud/lib/cloud/repository.ts:413-418` (`delete` = unconditional `update … set consumed_at = now() where id and org`, no `and consumed_at is null`, no affected-row check); `platform/packages/core/src/provider.ts:79` (`applyWrite(op, guard)` — no idempotency parameter); `platform/apps/cloud/app/api/approvals/[id]/apply/route.ts:20-27` (finds row then applies with no advisory lock). The sandbox provider has a compare-and-set (`platform/apps/cloud/lib/markting/repository.ts:133-141`) that would reject a second demo apply with `PENDING_MISMATCH`, but **live providers have no equivalent guard**.
- Description: Two concurrent apply requests for the same `pending_operation_id` (double click, retried HTTP, two agent calls) both read the row as unconsumed (READ COMMITTED), both call `provider.applyWrite`, then both mark it consumed. No `SELECT … FOR UPDATE`, no conditional consume, no provider idempotency key.
- Impact: Duplicate real mutations — e.g. a budget set applied twice, or a status flip re-issued — a financial/reliability risk. Only demo (sandbox CAS) is protected.
- Recommendation: Consume atomically (`update … set consumed_at = now() where id = $1 and consumed_at is null returning *`, and treat zero rows as `PENDING_NOT_FOUND`), take `FOR UPDATE` across get+apply, and/or pass a deterministic idempotency key (the pending id) into `applyWrite`.

### C13-03 — Dashboard "requester cannot approve" guard is bypassed for API-key-created pending operations, and is absent entirely on REST/MCP
- Severity: **P2**
- Classification: **VERIFIED_CODE**
- Evidence: `platform/apps/cloud/app/api/approvals/[id]/apply/route.ts:22-24` guard is `if (row.createdBy && row.createdBy === principal.userId …)`; `platform/apps/cloud/lib/cloud/auth.ts:22-37` + `platform/apps/cloud/lib/cloud/repository.ts` `authenticateApiKey` returns a principal with **no `userId`** (only `organizationId`, `apiKeyId`, `scopes`); `platform/apps/cloud/lib/cloud/repository.ts:374-382` stores `created_by = principal.userId ?? null`. So a pending created via an API key has `created_by = null`, making the `row.createdBy && …` short-circuit skip the self-approval check.
- Description: Separation of duties ("the person who requested a change cannot approve it") only fires when the pending row's `created_by` matches the applying session user. A change staged through an API key (the natural path for an agent acting under a person's key) records `created_by = null`, so the same human can approve it from the dashboard. The guard is also wholly absent on the REST/MCP apply paths (see C13-01).
- Impact: The intended two-person control degrades to one person whenever the request originates from an API key; combined with C13-01 an agent key both stages and applies.
- Recommendation: Propagate the key owner's user id (or key id) into `created_by` and compare against it; default-deny when provenance is unknown unless `MARKTING_ALLOW_SELF_APPROVAL=true`.

### C13-04 — Budget-cap policy is re-checked at validate but not at apply
- Severity: **P3**
- Classification: **VERIFIED_CODE**
- Evidence: `platform/packages/core/src/policy/engine.ts:110-113` — the apply path comment says "Policy may have changed … re-check" but only `checkStaticPolicy` (protected accounts) runs; `checkBudgetPolicy` (abs + pct caps, engine.ts:133-153) runs only in `validate`.
- Description: Because apply re-uses the hash-identical stored op, the *values* cannot change between validate and apply; but if an operator tightens `max_budget_delta_pct` / `max_daily_budget_micros` in the window between validate and apply, the already-validated pending op still applies at the looser cap.
- Impact: A validated-but-not-yet-applied change can land after a stricter budget policy takes effect, within the TTL window (default 15 min, `policy.ts:19`). Protected-account changes are still re-enforced.
- Recommendation: Re-run `checkBudgetPolicy` against the current preview/policy inside `apply`, not only `checkStaticPolicy`.

### C13-05 — Engine contract tests are not isolated from the default-workspace kill switch (test hygiene; also positive evidence)
- Severity: **P3**
- Classification: **VERIFIED_RUNTIME**
- Evidence: a leftover `engine/workspace/KILL_SWITCH` (content `"engaged by markting-ai engine host: writes belong to adport"`, the exact string written by `services/engine-demo/serve_demo.py:179`, not git-tracked) caused 16 failures in `tests/contract/test_live_write_gates.py` and `test_write_flows_graph.py`; re-running with `PAID_MEDIA_KILL_SWITCH_PATH` pointed elsewhere → 30 passed. Default path is `engine/src/paid_media_agent/config.py:158` (`workspace/KILL_SWITCH`) and the gate resolves it relative to project root (`runtime/profiles.py:57-69`).
- Description: The live-gate/write-flow contract tests use the real default kill-switch path, so a developer/demo-engaged kill switch silently turns every write test red. This is a test-isolation defect, not a product defect. It is also *positive* evidence: with the switch engaged, every write — even fake-provider happy paths — is refused `kill_switch`, confirming the kill switch is fail-closed and global.
- Impact: Misleading CI/local failures; risk of a real regression being masked as "the usual kill-switch failures."
- Recommendation: Point the kill-switch path at a per-test tmp dir in `conftest` (as `services/engine-demo/tests` already does at `test_demo_api.py:47`).

## Write paths to a provider (enumeration)

Engine (python) — the only `WriteProvider.call_mutation` call site is `WriteExecutor.execute` (`writes.py:849`), reached from the model's `execute_change` tool (graph, interrupt-gated `write_tools.py:82-114`) or `runner.approve → resume → execute` (`runner.py:242-255`, API `/proposals/{id}/approve` `app.py:116-124`). In the markting host every one of these is dead-ended by: provider raises (`ProposalOnlyWriteProvider`), kill switch engaged, empty approver set, and boot refuses live flags. **No engine path reaches a real platform** (VERIFIED_TEST).

Adport (ts) — the real write path is `PolicyEngine.apply → provider.applyWrite` (`engine.ts:113`), reachable only via `guardedWriteTool` with a `pending_operation_id` through `runtime.registry.call`. Three entry surfaces: (1) dashboard apply route — owner/admin + non-self (with the C13-03 hole); (2) REST `/api/v1/tools/{tool}` — same key validate+apply, no second human; (3) MCP `/mcp` — same client validate+apply, advisory approval hint only. All three require a prior `validate` that created the pending row with a **hash-identical** op; none can apply without it (pending `get` filters `consumed_at is null` and hash must match). The bridge/assistant can only ever `validate`.

## Disagreements / claims in docs that the code contradicts

- `services/engine-demo/serve_demo.py:8-9` and `README.md` present "AI proposes → policy preview → human approval → apply" as the product invariant. **Engine-side the single-write-path claim is verified.** But adport's own REST and MCP surfaces apply writes with no enforced human approver (C13-01); "approval" on MCP is an advisory `structuredContent` field. The universal "human approval" framing overstates what the code enforces on the autonomous surfaces.
- `platform/apps/cloud/app/api/approvals/[id]/apply/route.ts` comment implies self-approval is blocked by default; the guard silently no-ops for API-key-created pending ops (C13-03).
