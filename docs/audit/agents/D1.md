## Findings

### D1-01 — Engine report surface has no tenant dimension; every signed-in org can list, run and download every other org's "engine reports"
- **Severity:** P1 (would be P0 the moment the engine holds non-synthetic data)
- **Classification:** VERIFIED_CODE
- **Evidence:**
  - `cloud/app/api/reports/engine/route.ts:18-20` — `GET` authenticates the session for `organizationId` and then returns `engineClient().listReports()` with no org filter; `:30-35` — `POST` runs a report with only `cadence`/`end`.
  - `cloud/app/api/reports/engine/[name]/route.ts:13-15` — downloads any `name` after `sessionPrincipal(organizationId)`; the org id is never used.
  - `cloud/lib/markting/engine-client.ts:127-137` — the client has no caller/tenant parameter at all; one shared token (`lib/markting/env.ts:12`).
  - `services/engine-demo/serve_demo.py:62,304-306` — a single global index file `markting-reports.json` per engine workspace; `:355-358` `GET /reports` returns the whole index for any valid token; `:360-374` `GET /reports/files/{name}` serves any artefact; `:316-322` the only check is "token is valid", and the compose stack has exactly one token/caller (`docker-compose.yml:49`).
  - `serve_demo.py:324,344` — one global `asyncio.Lock` serialises all report runs across all tenants; the cloud rate limit is per org only (`route.ts:32`, default 120/min from `cloud/lib/cloud/repository.ts:355`).
  - Mitigating fact: the host refuses to boot unless `paid_media_data_mode == 'sample'` (`serve_demo.py:163-166,386-388`), so today the leaked content is synthetic fixture data.
- **Description:** The Reports page (`cloud/app/dashboard/reports/page.tsx:20`) presents "Engine reports" inside an organization's dashboard, but the underlying list is global to the engine process. Org A's run (with its `requested_by`, windows, platform summaries and file names) appears on org B's page and B can download A's HTML/PDF. A tenant can also hold the global lock with back-to-back runs (120/min allowed) and starve every other tenant.
- **Impact:** Cross-tenant disclosure as soon as the engine is pointed at anything real (or a live model is given tenant-specific context); today a demo-only leak plus a shared-resource DoS vector. Also contradicts the way the UI frames the feature.
- **Recommendation:** Either (a) store engine report runs in adport Postgres keyed by `organization_id` and have the cloud filter/serve only its own rows (file names → org map), or (b) run one engine per tenant / pass an org-scoped `caller_ref` and make `serve_demo.py` partition the index and artefact directory per caller. Lower the report rate limit (e.g. 5/min/org) and queue runs instead of serialising them under one lock.

### D1-02 — Assistant is a single synchronous HTTP request that may run for minutes; no streaming, no job, no persisted messages
- **Severity:** P2
- **Classification:** VERIFIED_CODE
- **Evidence:** `cloud/app/api/assistant/messages/route.ts:7` (`maxDuration = 300`) — Next docs: "Deployment platforms can use `maxDuration`" (`node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/02-route-segment-config/maxDuration.md:6`), i.e. it does nothing on the standalone Node server. `cloud/lib/markting/env.ts:18` — default engine timeout 240 s, max 900 s; `engine-client.ts:81-82` single `fetch` under `AbortController`. `cloud/app/dashboard/assistant/assistant-chat.tsx:24-25,37-40` — the whole conversation lives in `useState`; `:92` the textarea is disabled while busy; no abort button. `cloud/lib/markting/repository.ts:29` `listThreads` is exported but never imported by app code (rg), so the `markting_threads` table only records ownership, never content.
- **Description:** A live-model turn can block one browser connection for up to 4–15 minutes behind any proxy/LB (most terminate idle responses at 60–120 s). Refreshing the page loses the conversation; a reconnect cannot resume a thread (`threadId` is only in React state). Under load, each in-flight turn pins a Node request and a DB pool slot (`cloud/lib/db.ts:9` `max: 10`).
- **Impact:** Unreliable in any deployment with a reverse proxy; poor UX; no conversation history; poor horizontal scalability.
- **Recommendation:** Make the engine call asynchronous (enqueue, poll or SSE/stream the engine's events), persist messages per thread in Postgres, add cancel/abort, and surface `threadId` in the URL so a reload resumes.

### D1-03 — Bridge throws outside its try/catch when the translated tool is not in the tenant registry; proposal is left dangling on the engine with no record
- **Severity:** P2
- **Classification:** VERIFIED_CODE (runtime behaviour NOT_VERIFIED)
- **Evidence:** `cloud/lib/markting/bridge.ts:71` `deps.runtime.registry.get(translation.tool)` runs before the `try` at `:75-84`; `platform/packages/core/src/tools/registry.ts:76-78` — `get` throws `AdportError('UNKNOWN_TOOL')`. `cloud/lib/markting/assistant.ts:63-66` rethrows anything that is not a `BridgeAccessError`; `cloud/lib/http.ts:17` maps `UNKNOWN_TOOL` to 404 with the raw message. Nothing calls `deps.record` or `handoff` on this path (`bridge.ts:98-105` only runs inside the success/policy-failure branches).
- **Description:** Happens whenever an alias is bound to a provider the organization has not connected (live mode: `createTenantRuntime` only registers providers with credentials, `cloud/lib/cloud/runtime.ts:69-139`), or when `MARKTING_DEMO_MODE` is flipped (sandbox aliases vs real tools). The engine thread stays `awaiting_approval` until its TTL, no provenance row is written, no audit note, and the user sees "Unknown tool: google_set_budget" with HTTP 404.
- **Impact:** Silent loss of a proposal, confusing error, inconsistent state between engine and adport.
- **Recommendation:** Move `registry.get` inside the guarded block (or pre-check with `registry.has`) and treat a missing tool as `unsupported`/`rejected_by_policy` with record + hand-off; add a bridge test for "alias bound to unconnected provider".

### D1-04 — Demo mode is a one-variable runtime swap that is enabled by default in the shipped `.env.example`
- **Severity:** P2 (fails in the safe direction, but demo code is on the production path)
- **Classification:** VERIFIED_CODE
- **Evidence:** `.env.example:47` `MARKTING_DEMO_MODE=true`, `:49` `MARKTING_ALLOW_SELF_APPROVAL=true` (the compose stack's env file; `cloud/.env.example:106,108` default both to `false`). `cloud/lib/markting/runtime.ts:18-26` — when demo mode is on, `createBridgeRuntime` replaces the tenant runtime (no `AccountScopedProvider`, no `authorizeToolCall`, compare `cloud/lib/cloud/runtime.ts:141-146`) and is used for both preview (`assistant.ts:53`) and apply (`app/api/approvals/[id]/apply/route.ts:25`). `cloud/app/dashboard/approvals/page.tsx:12` lists all pending rows regardless of which runtime produced them.
- **Description:** With the flag on, the Assistant and Approvals pages operate on synthetic campaigns while `/mcp` and `/api/v1` still use real providers; pending rows created by one runtime cannot be applied by the other (`UNKNOWN_TOOL`), and the Approvals page does not distinguish them. The sandbox tools bypass the account-scope authorizer (they carry their own account check, `sandbox-provider.ts:90-94`). The self-approval default removes the requester≠approver rule.
- **Impact:** A deployment that copies `.env.example` runs a demo write path in production. Failure direction is safe (the sandbox never reaches an ad platform), but the two toggles are the kind of thing that gets copied into a real environment.
- **Recommendation:** Default both flags to `false` in `.env.example`; refuse `MARKTING_DEMO_MODE=true` when `NODE_ENV=production` unless an explicit `MARKTING_ALLOW_DEMO_IN_PRODUCTION` is set; tag pending rows with the runtime (`provider = 'sandbox'`) and render that badge on Approvals; show a persistent banner.

### D1-05 — Docker build: no `.dockerignore`, whole workspace (incl. `node_modules`, `.next`, `.env.local`) is the context; `NEXT_PUBLIC_*` and CSP are frozen at build without build args
- **Severity:** P2
- **Classification:** VERIFIED_CODE + VERIFIED_RUNTIME (manifest) + INFERRED (effects)
- **Evidence:** `infra/cloud.Dockerfile:9` `COPY . .` with context `./platform` (`docker-compose.yml:14-15`); `ls platform/.dockerignore platform/apps/cloud/.dockerignore` → none. Present in context: `platform/node_modules` 577M, `platform/apps/cloud/.next` 364M, `platform/apps/cloud/.env.local` (gitignored by `platform/.gitignore:8-9`, but Docker does not read `.gitignore`). Next loads `.env.local` for `next build` (`node_modules/next/dist/docs/01-app/02-guides/environment-variables.md:272`) and inlines `NEXT_PUBLIC_*` at build time (`…environment-variables.md:158-166`). `cloud/next.config.ts:37-40` computes the CSP origin from `process.env.NEXT_PUBLIC_SUPABASE_URL` with fallback `http://127.0.0.1:55321`; the existing build's `cloud/.next/routes-manifest.json` contains `connect-src 'self' http://127.0.0.1:55321`, proving `headers()` is serialised at build. The Dockerfile passes no `ARG`/`ENV` for `NEXT_PUBLIC_*` during the build stage (`:5-12`). Standalone output contains no `.env*` (verified), so the final stage does not ship the file.
- **Description:** Image content depends on whatever is lying around in the developer's tree (a stale `.next`, local secrets in `.env.local`), the build is slow and the intermediate layer contains local secrets. The CSP `connect-src` baked into every image is the loopback fallback, not the runtime Supabase origin. Today this is harmless because the browser never contacts Supabase (`lib/supabase/browser.ts` is dead code; no client chunk contains a Supabase URL), but the header silently lies and any future client-side Supabase use would be blocked.
- **Impact:** Non-reproducible images, secret exposure in build layers, wrong CSP for any future browser→Supabase call.
- **Recommendation:** Add `platform/.dockerignore` (`node_modules`, `**/.next`, `**/.env*`, `!**/.env.example`, `.turbo`, `coverage`); pass `NEXT_PUBLIC_*` as `ARG`s; set the CSP origin from a runtime header in `proxy.ts` instead of `next.config.ts` if it must follow the environment.

### D1-06 — Apply is not atomic across concurrent approvers; dashboard scan of pending rows is O(n) with a hard 200 cap
- **Severity:** P2 (upstream weakness, newly exposed by a second human-driven apply surface)
- **Classification:** VERIFIED_CODE
- **Evidence:** `platform/packages/core/src/policy/engine.ts` `apply()`: `pending.get` → `provider.applyWrite` → `audit.append` → `pending.delete`; `cloud/lib/cloud/repository.ts` `PostgresPendingStore.get/delete` (`where … consumed_at is null` / `update … set consumed_at`) — no `select … for update`, no conditional `update … where consumed_at is null returning`. `cloud/app/api/approvals/[id]/apply/route.ts:20` `(await listPendingOperations(org, 200)).find(id)`; `:27` `markPendingOutcome('applied')` only after success. `approval-actions.tsx:34` disables only this component's button.
- **Description:** Two admins (or two tabs) clicking Apply within the provider's round-trip both pass `get`, both call `applyWrite`, both write an `applied` audit event. Only budget/status updates are translated (`translate.ts:65`), so the double write is idempotent on the ad platform, but the audit log double-counts. Beyond 200 live pending rows the dashboard returns 404 for a row that exists. If `audit.append` or `markPendingOutcome` fails after `applyWrite`, provenance stays `pending` with a consumed row.
- **Impact:** Audit integrity; latent double-apply if a non-idempotent tool is ever bridged; scale cliff at 200 pending rows.
- **Recommendation:** Consume the row first with `update … set consumed_at = now() where id = $1 and consumed_at is null returning *` (compensate on provider failure), or `select … for update skip locked`; fetch by id (`PostgresPendingStore.get`) instead of scanning; write provenance outcome in the same transaction.

### D1-07 — Approvals page shows "Apply" by role, API requires plan write access and answers with an API-key-flavoured message
- **Severity:** P3
- **Classification:** VERIFIED_CODE
- **Evidence:** `cloud/app/dashboard/approvals/page.tsx:14` `canApply = canAdminister(tenant)`; `cloud/app/api/approvals/[id]/apply/route.ts:18` `requireScope(principal, 'tools:write')` → `cloud/lib/cloud/auth.ts:40` `"API key lacks required scope: tools:write"`; `cloud/lib/cloud/plans.ts` `applyPlanToPrincipal` strips `tools:write` on the default `reader` plan.
- **Description:** An owner on the reader plan sees the button, confirms, and gets a 403 about an API key. The page already knows the entitlement (billing page uses it) but does not pass it down.
- **Recommendation:** Compute `canApply` from role AND `entitlement.plan.writeAccess`; return a `PlanLimitError` (402) so the existing upgrade modal handles it.

### D1-08 — Authentication failures travel as a plain `Error` whose message is string-matched in six routes
- **Severity:** P3
- **Classification:** VERIFIED_CODE
- **Evidence:** `cloud/lib/cloud/auth.ts:12` `throw new Error('Authentication required.')`; matched by text at `app/api/approvals/[id]/apply/route.ts:30`, `reject/route.ts:24`, `app/api/assistant/messages/route.ts:17`, `app/api/reports/engine/route.ts:10`, `[name]/route.ts:28`, `app/api/dashboard/summary/route.ts:17`. `resolveMembership` similarly throws `Error('You do not have access to this organization.')` (`repository.ts:30-48`), which these routes map to **500** via `apiError` (`http.ts:21`) and log as a server error.
- **Recommendation:** Throw `HttpError(401/403)` from `sessionPrincipal`/`resolveMembership` (upstream edit) or wrap once in a `requireSession()` helper used by the markting routes.

### D1-09 — Defence-in-depth gaps: `unsafe-inline` scripts, non-HttpOnly session cookies, no Origin check on cookie-authenticated JSON POSTs
- **Severity:** P3
- **Classification:** VERIFIED_CODE
- **Evidence:** `cloud/next.config.ts:18` production `script-src 'self' 'unsafe-inline'` (no nonce); `@supabase/ssr` defaults `sameSite: "lax", httpOnly: false` (`node_modules/.pnpm/@supabase+ssr@0.12.4_*/node_modules/@supabase/ssr/dist/main/utils/constants.js:4-11`) and `cloud/lib/supabase/{server,proxy}.ts` pass no overrides; only `app/api/waitlist/route.ts:14` reads `Origin`; the new POST routes accept `application/json` bodies on cookie auth (`approvals`, `assistant/messages`, `reports/engine`). Server actions are protected by Next's own origin check and `experimental.serverActions` (`next.config.ts:30-34`), route handlers are not.
- **Description:** CSRF is currently prevented by `SameSite=Lax` plus the JSON content type (cross-origin fetch would preflight), not by any explicit check. With `unsafe-inline` and JS-readable auth cookies, a single XSS equals session theft.
- **Recommendation:** Add a `Sec-Fetch-Site`/`Origin` assertion helper to cookie-authenticated mutating routes; generate a per-request nonce in `proxy.ts` and drop `'unsafe-inline'`; set `httpOnly: true` for auth cookies (the browser client is unused).

### D1-10 — Session refresh and principal resolution repeat per request and run on bearer-only routes
- **Severity:** P3
- **Classification:** VERIFIED_CODE (latency impact INFERRED)
- **Evidence:** `cloud/proxy.ts:7-8` matcher excludes only static assets, so `updateSession` (`lib/supabase/proxy.ts:21` `getUser()`) runs for `/mcp`, `/api/v1/*`, `/api/billing/webhook`, `/.well-known/*`, `/api/locale`; `lib/supabase/proxy.ts:8-9` reads env with `!` and no validation. Pages then call `getUser()` again (`lib/cloud/dashboard.ts:24-25`) and API routes call `sessionPrincipal` which does `getUser()` + membership query + `applyPlanToPrincipal` (entitlement + role query) on every call (`auth.ts:9-20`, `plans.ts`); `requireDashboardTenant` is `cache()`d, `sessionPrincipal` is not.
- **Recommendation:** Narrow the matcher to session routes (`/dashboard`, `/onboarding`, `/account-selection`, `/oauth/authorize`, `/api/(?!v1|billing)`); wrap `sessionPrincipal` in React `cache()`; validate the two public env vars once.

### D1-11 — i18n polish gaps: both dictionaries shipped to the browser, English-only `<title>`s, hydration mismatch in `global-error`, non-secure locale cookie
- **Severity:** P3
- **Classification:** VERIFIED_CODE
- **Evidence:** `cloud/components/i18n-provider.tsx:5,13` imports `makeTranslators` from `lib/i18n/index.ts:9`, which statically imports every message bundle (`lib/i18n/messages/*.ts`, ~89 KB source for both locales); `export const metadata = { title: '…' }` is English in 17 files (e.g. `app/dashboard/assistant/page.tsx:7`, `app/onboarding/page.tsx:13`), root metadata is still the upstream brand (`app/layout.tsx:12-13`); `app/global-error.tsx:7-11,17` reads `document.cookie` during render, so the server-rendered fallback (`ar`/`rtl`) can differ from the client (`en`/`ltr`) on fatal errors; `app/api/locale/route.ts:9` sets the cookie without `secure`.
- **Positive verification:** 0 physical-direction CSS declarations remain, 39 logical/`[dir]` rules (`globals.css:713,721`); `getLocale()` cookie → `Accept-Language` → `ar` (`lib/i18n/server.ts:7-14`); plural categories via `Intl.PluralRules` (`lib/i18n/index.ts:38-44`); `i18n.test.ts` enforces key parity and placeholders.
- **Recommendation:** Split dictionaries per locale with dynamic import (or pass only the active bundle from the server); use `generateMetadata` with `getT()`; pass the locale to `global-error` via a data attribute or accept the mismatch knowingly; add `secure` in production.

### D1-13 — Test harness flips database suites on whenever `cloud/.env.local` exists; new routes and client components have no tests
- **Severity:** P3
- **Classification:** VERIFIED_TEST

### D1-14 — Operability gaps in the container stack
- **Severity:** P3
- **Classification:** VERIFIED_CODE
- **Evidence:** `docker-compose.yml:30-32` cloud `depends_on: engine: condition: service_healthy` while the app is designed to degrade without the engine (`app/dashboard/assistant/page.tsx:20`, `engine-client.ts:97`); no healthcheck for `cloud`; `infra/cloud.Dockerfile` has no `HEALTHCHECK`; static assets are copied twice (`Dockerfile:19` and `scripts/prepare-standalone.mjs:13`); build runs `pnpm build` for every workspace package before the cloud build (`Dockerfile:11-12`).

### D1-15 — Route handler request bodies are unbounded
- **Severity:** P3
- **Classification:** VERIFIED_CODE
- **Evidence:** `cloud/next.config.ts:30-34` `bodySizeLimit: '1mb'` applies to server actions only (Next docs `server-actions.md:83`); the new routes call `request.json()` directly (`assistant/messages/route.ts:11`, `approvals/*`, `reports/engine/route.ts:29`) and only cap `text` after parsing (`assistant.ts:33`).
- **Recommendation:** Check `content-length` / read with a bounded reader in a shared helper, or terminate oversize bodies at the reverse proxy.

## What a world-class system would need

1. Tenant-partitioned engine artefacts (or engine-per-tenant), org-scoped report storage in adport, per-org quotas and a job queue instead of a global lock.
2. Asynchronous assistant turns: enqueue → stream engine events (SSE) → persist messages/proposals per thread; resumable threads from the URL; cancel.
3. Atomic consume-then-apply for pending operations, keyed lookups, outcome written transactionally with provenance; idempotency keys on provider writes.
4. Reproducible images: `.dockerignore`, build args for `NEXT_PUBLIC_*`, runtime CSP with nonces, `HEALTHCHECK`, non-root build, no dependence on `.env.local`.
5. Production guards for demo toggles (`MARKTING_DEMO_MODE`, `MARKTING_ALLOW_SELF_APPROVAL`) and visible runtime badges on Approvals.
6. Typed error contract (`HttpError` from `sessionPrincipal`/`resolveMembership`), request-scoped caching of principal resolution, narrow `proxy.ts` matcher, Origin assertion on cookie-authenticated mutations.
7. Localised metadata/titles, per-locale dictionary loading, locale-aware date/number components, Arabic engine report templates (noted as open in `docs/ARCHITECTURE.md:890`).
8. Route-handler and component tests for the markting surfaces; DB tests gated explicitly; CI job for `typecheck + vitest + build:standalone`.
9. Alias management UI (engine `account_ref` → adport provider/account/target map) so live mode is usable without SQL.
10. Organization switcher and per-org state in the dashboard.
