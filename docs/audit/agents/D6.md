## Findings

### D6-01 — Owners/admins can rewrite `policy` and `data_retention_days` directly via PostgREST, bypassing plan caps, validation and the audit log
- Severity: P2
- Classification: VERIFIED_CODE (schema + app code); runtime behaviour against PostgREST NOT_VERIFIED (no Supabase here)
- Evidence:
  - `platform/supabase/migrations/20260817171039_cloud_initial_schema.sql:277-289` (`organization_settings_update_admin` for update to authenticated, owner/admin) and `:332` (`grant select, update on public.organization_settings to authenticated`).
  - CHECK allows `data_retention_days between 1 and 3650` (`:49`); `policy` is unconstrained jsonb (`:48`).
  - Server path enforces the plan cap and writes an audit event only in `platform/apps/cloud/lib/cloud/tenant-admin.ts:167-195` (`dataRetentionDays > entitlement.plan.maxRetentionDays` → `PlanLimitError`), reached via `platform/apps/cloud/app/api/settings/route.ts:19-26` with `policySchema` validation (`:11`).
  - The browser can reach PostgREST: `connect-src 'self' ${supabaseOrigin}` (`platform/apps/cloud/next.config.ts:19,37-38`), the publishable key is public (`lib/supabase/browser.ts:7-10`), and `public` is an exposed schema (`platform/supabase/config.toml:14`).
  - Every reader of the column does `policySchema.parse(rows[0]?.policy ?? {})` (`platform/apps/cloud/lib/cloud/repository.ts:51-56`, `app/dashboard/policies/page.tsx:22`); `policySchema` is a plain `z.object` with `.positive()` numbers (`platform/packages/core/src/policy/policy.ts:7-20`), so an invalid value makes parse throw.
- Description: The browser-role RLS layer is otherwise read-only, but this one UPDATE policy lets an authenticated owner/admin `PATCH /rest/v1/organization_settings?organization_id=eq.<own org>` with any body. Three controls that exist only in the Next.js server are skipped: (a) the plan's `maxRetentionDays` (free `reader` plan = 30 days, `lib/cloud/plans.ts:25-26`; the CHECK allows 3650), (b) the `settings_updated` audit event, (c) `policySchema` validation. A malformed policy (e.g. `max_budget_delta_pct: -1`) makes every subsequent `getOrganizationPolicy` throw, breaking previews/approvals for that organization (self-inflicted, but there is no UI to recover other than the same route which will succeed with a valid body). A valid-but-permissive policy (`require_validation:false`, `max_budget_delta_pct:null`, `pending_ttl_minutes: 1e9`) can be set without any audit trail, which matters for a product whose safety story is "every write goes through policy + approval + audit".
- Impact: plan-limit bypass (storage/retention entitlement), audit evasion for safety-policy changes within one's own tenant, denial of service to one's own tenant. Not cross-tenant (the policy requires membership).
- Recommendation: drop `organization_settings_update_admin` and the `update` grant to `authenticated`; keep `select`. If a browser write path is ever wanted, expose it as a security-definer RPC that enforces the plan cap, validates the JSON and writes the audit row. Add a DB-side `check (jsonb_typeof(policy) = 'object')` at minimum.

### D6-02 — The `adport_backend` least-privilege boundary is advisory: the app logs in as `postgres` and only requests `role=adport_backend` as a startup parameter, with no login role and no assertion
- Severity: P2
- Classification: VERIFIED_CODE (mechanism); pooler behaviour NOT_VERIFIED; `postgres` role attributes INFERRED
- Evidence:
  - `platform/apps/cloud/lib/db.ts:8-13`: `postgres(env().SUPABASE_DB_URL, { ..., connection: { application_name: 'adport-cloud', role: env().ADPORT_DB_ROLE } })`.
  - postgres.js sends `options.connection` entries verbatim in the StartupMessage (`platform/node_modules/.pnpm/postgres@3.4.9/node_modules/postgres/src/connection.js:996-1006`), i.e. this is the wire-level equivalent of `SET ROLE` right after login; it is not a separate login.
  - `adport_backend` is `nologin noinherit` and granted to `postgres` (`20260817171039_cloud_initial_schema.sql:4-11`); no migration creates a LOGIN role that inherits it.
  - Default connection strings are the owner: `.env.example:8`, `docker-compose.yml:25`, `platform/apps/cloud/.env.example:5` → `postgresql://postgres:postgres@...:55322/postgres`.
  - No code checks `current_user`/`current_role` after connect (rg exit 1).
  - `platform/docs/deployment-model.md:45`: "A production database login should inherit only `adport_backend`; do not run application queries as a database owner." — there is no artefact in the repo that creates such a login.
  - `config.toml` enables a transaction-mode pooler on 55329 (`:46-55`); the app's `prepare: false` (`db.ts:12`) is pooler-compatible, so running through a pooler in production is plausible.
- Description: The design intent (restricted role; RLS policies written `to adport_backend`) is sound, but what is actually deployed is the database owner with a per-connection `SET ROLE`. Consequences: (1) any SQL that executes `RESET ROLE`/`SET ROLE postgres` regains full owner privileges, including the `private` schema and `auth` schema; today no `sql.unsafe` exists in app code, so this needs an injection to be exploitable, but the boundary is one statement thick; (2) if the connection goes through a transaction-mode pooler that drops or rejects unknown startup parameters, the app may silently run as `postgres` (which in Supabase is granted BYPASSRLS — INFERRED from Supabase defaults, not verified in this CLI version), and nothing in the code would notice; (3) the `postgres:postgres` default encourages the same pattern in production.
- Impact: privilege boundary between the web tier and the whole database (including `private.provider_credentials` ciphertext and `auth.users`) is not enforced by Postgres; it is enforced by "the app never runs raw SQL". Because of D6-03 the RLS layer adds nothing for the backend path either.
- Recommendation: add a migration that creates `adport_app` (LOGIN, `in role adport_backend`, `noinherit` off or explicit `set role` in `ALTER ROLE ... SET role = adport_backend`), connect with that user, and add a startup self-check in `db()` (`select current_user` must equal `ADPORT_DB_ROLE`, else refuse to serve). Document pooler compatibility (`ALTER ROLE ... SET role` survives poolers; startup parameters may not).

### D6-03 — RLS gives the backend path zero tenant isolation by design; all tenant scoping lives in hand-written WHERE clauses
- Severity: P3 (design/defence-in-depth; no concrete breach found)
- Classification: VERIFIED_CODE
- Evidence: every `*_backend_all` policy is `for all to adport_backend using (true) with check (true)` (`initial:319-327`, `plans:117-122`, `20260828140646:94-97`, `20261002000000_markting_bridge.sql:83-86`). I traced the markting repository (`lib/markting/repository.ts:17-146`: every statement filters `organization_id`; `claimThread` uses a conditional `on conflict ... do update where organization_id = ... and user_id ...` and returns `rows.length === 1`), `PostgresPendingStore` (`lib/cloud/repository.ts:371-426`: `get/delete/sweep` filter `organization_id`), `tenant-admin.ts` (all statements filter `organization_id`), `resolveMembership` (`repository.ts:30-48`), `app/api/deletion/route.ts:21` (deletes only `principal.organizationId`), `app/oauth/authorize/page.tsx:43-45`. Token/key lookups are legitimately global by hash (`repository.ts:325-328`, `mcp-oauth-repository.ts:198,235,282`).
- Description: Correct today, but a single forgotten predicate in any future `db()` call is a cross-tenant leak with no second line of defence. Postgres offers one cheaply: `set_config('app.organization_id', ..., true)` per transaction plus `using (organization_id = current_setting('app.organization_id')::uuid)` policies for `adport_backend`.
- Impact: maintainability/security posture; the markting tables double the number of hand-scoped queries.
- Recommendation: adopt per-transaction tenant GUC + RLS for `adport_backend` on all `organization_id` tables, keep `using(true)` only for the few global lookups (hash-keyed token tables), and add a negative test per table.

### D6-04 — Demo/sandbox state lives in the production schema and is switched on by a process-global env flag that ships as `true`
- Severity: P2
- Classification: VERIFIED_CODE
- Evidence: `.env.example:46-47` (`MARKTING_DEMO_MODE=true`); `platform/apps/cloud/lib/markting/env.ts:14,29`; `lib/markting/runtime.ts:18-26` (demo mode → `SandboxProvider` + `PostgresSandboxStore` for *every* organization, wired to the real `PostgresPendingStore`/`PostgresAuditStore`); `20261002000000_markting_bridge.sql:60-66` (`public.markting_sandbox_state`, comment "demo mode only"); `:24-35` (`markting_account_aliases.provider` only `check (provider ~ '^[a-z][a-z0-9_]*$')`, no FK to `connections`/`organization_ad_accounts`); `infra/seed/seed-demo.mjs:50-62` inserts `provider='sandbox'` aliases; `lib/markting/repository.ts:45` merges `SANDBOX_ALIASES` into every org's alias map when demo mode is on.
- Description: The upstream adport pattern for synthetic data is an admin-provisioned, per-organization table (`private.synthetic_reviewer_workspaces`, "never a public demo switch", `20260906132858:1`). The bridge instead uses one environment variable for the whole deployment, and the shipped example turns it on. A deployment that copies `.env.example` runs every tenant against the sandbox and writes `provider='sandbox'` rows into `pending_operations`/`audit_events` beside real ones. Conversely, in live mode, an alias row pointing at `provider='google', account_id='...'` is created only by seed/SQL today (no app writer for `upsertAlias` outside tests), but the schema does not tie aliases to connected, scope-enabled accounts.
- Impact: demo code reaching production tables/paths by misconfiguration; alias→account mapping not constrained by the account-scope model at the DB level.
- Recommendation: make demo a per-organization DB fact (e.g. `markting_sandbox_state` row present and admin-provisioned) rather than an env flag; default `.env.example` to `false`; add `foreign key (organization_id, provider, account_id) references organization_ad_accounts` for non-sandbox aliases, or a CHECK restricting `provider` to the `connections` list plus `sandbox`.

### D6-05 — `handle_new_user` rejects sign-ups whose email local part has no `[a-z0-9]` characters (e.g. Arabic local parts)
- Severity: P3 (P2 if internationalised email addresses are a real share of the target market)
- Classification: VERIFIED_CODE + simulated (python re-implementation of the same regexes; not executed in Postgres)
- Evidence: `20260817171039_cloud_initial_schema.sql:229` (`lower(regexp_replace(split_part(email,'@',1), '[^a-z0-9]+', '-', 'g'))`), `:233` (`left(trim(both '-' from base_slug), 48) || '-' || substr(uuid,1,8)`), `:27` (`slug ~ '^[a-z0-9][a-z0-9-]{2,62}$'`). Simulation: `'محمد' → '-c1a19ac0'` fails the CHECK; `'___'` fails likewise.
- Description: The trigger is `security definer` and runs inside GoTrue's insert into `auth.users` (`:241-243`); a CHECK violation aborts the sign-up with Supabase's generic "Database error saving new user". For an Arabic-first product, any provider that allows non-ASCII local parts produces an unexplained sign-up failure. The same path runs for `inviteUserByEmail` (`tenant-admin.ts:53`).
- Impact: hard sign-up failure for a class of users; opaque error.
- Recommendation: `coalesce(nullif(trim(both '-' from base_slug), ''), 'org')` before concatenation; add a regression test that inserts an `auth.users` row with an Arabic local part.

### D6-06 — Three FKs to `auth.users` have no `on delete` action, so deleting an auth user can fail or be blocked
- Severity: P3
- Classification: VERIFIED_CODE
- Evidence: `organizations.created_by` (`initial:28`), `connections.connected_by` (`:61`), `api_keys.created_by` (`:118`) — `references auth.users(id)` with no action. `app/api/deletion/route.ts:22-25` calls `auth.admin.deleteUser` when the user has no remaining memberships.
- Description: A user who created an organization (or connected a provider / created an API key) and was later removed from it still has rows pointing at them. `deleteUser` then fails with a FK violation (after the organization delete at `:21` already committed), and any erasure request for that user is blocked until an operator fixes the data by hand.
- Impact: partial failure of the deletion endpoint; GDPR-style erasure blocked for a subset of users.
- Recommendation: `on delete set null` (make the columns nullable, as `pending_operations.created_by`/`audit_events.actor_user_id` already are) or record actors in `profiles` rather than `auth.users`.

### D6-07 — Retention and purge gaps: MCP OAuth purge never scheduled, `markting_*` not covered, engine DB never purged or cascaded
- Severity: P3
- Classification: VERIFIED_CODE
- Evidence: `private.purge_expired_mcp_oauth_records()` defined `20260825120000_mcp_oauth.sql:71-82`, granted `:94`, referenced nowhere else (rg). `private.apply_data_retention()` final body `20260828120000_cloud_plans_and_account_scope.sql:131-163` covers audit_events, pending_operations, findings, deletion_requests, oauth_transactions, rate_limit_buckets, billing_events only; the bridge migration adds no retention. `markting_threads.title` stores the first 80 chars of the user's first message (`lib/markting/assistant.ts:38`); `markting_engine_proposals.proposal`/`translation` jsonb store the full proposal. ### D6-09 — Operational topology: two Postgres instances with different majors, `make up` wipes one of them every time, and no ordering/health between cloud and Supabase
- Severity: P3
- Classification: VERIFIED_CODE
- Evidence: `Makefile:25-28,33` (`up` → `supabase start` → **`supabase db reset --local --yes`** → `docker compose up`); `docker-compose.yml:1-5,24-25` (Supabase reached via `host.docker.internal`, not a compose service; `cloud` `depends_on` only `engine`, `:30-32`); `engine-db` is `postgres:16-alpine` (`:67`) while Supabase is `major_version = 17` (`config.toml:42`); `engine-pgdata` is a persistent volume (`:78-82`); engine-db has fixed credentials `paid_media:paid_media` (`:43,70-71`) and no published port (acceptable locally).
- Description: Every `make up` reinitialises the Supabase database (users, orgs, `markting_*`), while `engine-db` keeps `pma_proposals`, `pma_thread_owners` and LangGraph checkpoints. The two stores therefore diverge after the first restart (engine rows reference organization/user UUIDs that no longer exist). The cloud container also starts without any check that Supabase is up or migrated. There is no backup story for either database (`docs/TODO.md:20` acknowledges this for the engine).
- Impact: surprising local data loss; cross-store inconsistency that a future reconciliation feature would inherit; no transactional boundary between `markting_engine_proposals` (Supabase) and `pma_proposals` (engine).
- Recommendation: split `make up` (start) from `make reset`; add a `wait-for` on Supabase in the cloud entrypoint; decide on one Postgres (engine schema inside the Supabase DB, separate database or schema) or document the two-store consistency model and backups.

### D6-10 — Grant hygiene is uneven: explicit `revoke … from anon, authenticated` exists only for `api_keys`, `pending_operations` and `markting_*`; some browser-writable policies are not column-restricted
- Severity: P3
- Classification: VERIFIED_CODE; dependence on Supabase default privileges INFERRED
- Evidence: revokes at `initial:334` and `20261002000000_markting_bridge.sql:88`; other public tables receive only positive `grant select` (`initial:329-332`, `plans:124`, `20260828140646:99-100`). No `ALTER DEFAULT PRIVILEGES` (rg exit 1). `config.toml:20-25` documents the legacy Supabase behaviour of auto-granting new `public` tables to `anon/authenticated/service_role` (the `auto_expose_new_tables` flag). `feedback_insert_member` (`20260828140646:83-92`) with `grant select, insert on public.feedback to authenticated` (`:100`) has no column list, so a member can insert `notification_status='sent'`/`status='resolved'`/`resend_email_id` directly; `profiles_update_self` (`initial:257-259`) likewise allows updating `created_at`.
- Description: Safety today rests on RLS being enabled on every `public` table — which I verified is true for all 17 of them (`initial:245-253`, `plans:90-92`, `20260828140646:68-69`, `bridge:68-71`) — rather than on the grant layer. On a project where legacy default privileges apply, `anon` would hold table privileges that only RLS neutralises.
- Impact: low today; one `alter table … disable row level security` or one permissive policy away from exposure.
- Recommendation: add a hardening migration: `revoke all on all tables in schema public from anon, authenticated` followed by the intended positive grants, column-level `grant insert (organization_id, created_by, kind, subject, message, page_path)` on `feedback`, `grant update (display_name)` on `profiles`, and `alter default privileges for role postgres in schema public revoke all on tables from anon, authenticated`.

## What a world-class system would need (gaps, concrete)

1. A dedicated LOGIN role for the app (`adport_app in role adport_backend`, `alter role adport_app set role = adport_backend` for pooler safety), connection-time assertion of `current_user`, and `SUPABASE_DB_URL` never carrying the owner.
2. Per-transaction tenant context (`set_config('app.organization_id', $1, true)`) with `adport_backend` RLS policies keyed on it, so a missing WHERE clause fails closed; a generated negative test per table for `anon`, `authenticated` and a wrong-tenant backend context.
3. Server-only writes for `organization_settings` (drop the browser UPDATE policy), column-level grants on `feedback`/`profiles`, explicit `revoke all … from anon, authenticated` plus default-privilege revokes.
4. Demo as a per-organization provisioned fact, not an env flag; alias→account FK to `organization_ad_accounts`.
5. Retention that covers `markting_*`, MCP OAuth tables, and the engine store; deletion that fans out to the engine; backups and PITR for both databases (or a single database).
6. Robust `handle_new_user` (empty-slug fallback, i18n-neutral default organization name instead of `'s organization`), `on delete set null` for actor FKs, cascade for `markting_threads.user_id`.
7. CI that starts Supabase, applies migrations, runs every `*.database.test.ts`, and regenerates/diffs `database.types.ts`.
8. Committed production Supabase configuration (auth sign-up policy, confirmations, captcha, network restrictions, SSL enforcement, pooler mode) and a migration runbook (`supabase db push`, rollback, `cron` verification).
