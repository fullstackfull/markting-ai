## Findings

### J6-01 — The "AI analysis reports" a buyer sees are always synthetic fixture data, dated as if current, labelled "reconciled", with no demo marker
- Severity: **P1** — Classification: **VERIFIED_CODE** (+ VERIFIED_TEST for the engine side)
- Evidence:
  - `docker-compose.yml:47` pins `PAID_MEDIA_DATA_MODE: sample` for the engine container regardless of `MARKTING_DEMO_MODE`; there is no live-engine service or profile in the compose file.
  - `services/engine-demo/serve_demo.py:163-166` refuses to start unless `paid_media_data_mode == "sample"`; `:183-191` (`demo_settings`) and `:383-387` force `sample` in both `demo` and `live` engine modes. So the engine host **can only ever read the three shipped fixtures** (`domain/common.py:37-41`).
  - `tools/fixtures.py:201-214, 217-232, 242-248`: fixture dates are shifted so the newest complete day is `today − 2`; the synthetic campaigns ("Brand Search - US", "Performance Max - Prospecting", …) therefore always appear with current dates.
  - `serve_demo.py:267-307` (`run_report`) runs `run_cadence_report` over those fixtures and stores `reconciled`, per-platform spend/CPA strings; the cloud shows them in `platform/apps/cloud/app/dashboard/reports/engine-reports.tsx:117-125` with the badge `reports.reconciled` ("مُطابَق"), and the card is titled "AI analysis reports / تقارير التحليل الذكي" with note "Deterministic period comparison rendered by the analysis engine" (`lib/i18n/messages/reports.ts:23-24,65-66`).
  - `app/dashboard/reports/page.tsx` never imports `isDemoMode`; the only demo callout in the app is on the Assistant page (`app/dashboard/assistant/page.tsx:11,21`). `app/api/reports/engine/route.ts:16-39` does not gate on demo mode either.
  - The rendered HTML/PDF (`reports/render.py`, `reports/templates/report.html.j2`) and `AnalysisSummary` (`domain/analysis.py:221-238`) contain no data-source field (rg over templates and render.py: no match). The only place "fixture" is visible is the raw `fixture_data_window` key in the row artifact payload (`fixtures.py:406-409`) and `/health.catalog_source` (`surfaces/api/app.py:86`), neither of which the Reports UI reads.
  - `README.md:14,83` claims the product "Analyses connected accounts (spend, conversions, CPA, ROAS)".
- Description: With `MARKTING_DEMO_MODE=false` and real OAuth connections, the upstream campaign table on the Reports page shows real rows while, on the same page, the engine card shows fabricated Google/Meta/Reddit spend, CPA and "reconciled" status for accounts the tenant does not own, in USD, with this week's dates. The same synthetic analysis is what the Assistant answers from (both engine modes force `sample`), and the Assistant's demo banner is driven by the *cloud* flag, not by what the engine is actually reading (`lib/markting/assistant.ts:52,73` → `isDemoMode()`), so a `MARKTING_DEMO_MODE=false` + `MARKTING_ENGINE_MODE=live` deployment presents synthetic analysis without any banner.
- Impact: fabricated-looking numbers in a production path; a buyer could act (or lose trust) on figures that describe no real account. Cross-tenant: the report index is one file for the whole engine (`serve_demo.py:246-306`) and the list route only authenticates (`app/api/reports/engine/route.ts:18-20`), so every organization sees every other organization's runs — synthetic today, but the plumbing is tenant-blind.
- Recommendation: (1) Propagate a `data_source: fixture|live` field from the engine (`catalog.source` is already available) into `/reports`, `/threads/*/messages` and the report payload, and render a persistent "synthetic data" banner on the Reports card and in the HTML/PDF header whenever it is `fixture`. (2) Hide or disable the engine card when `catalog_source != live` and the cloud is not in demo mode. (3) Scope the report index by organization. (4) Fix the README claim or ship a live engine profile.

### J6-02 — `PAID_MEDIA_DATA_MODE=auto` (the engine default) mixes synthetic Google/Meta/Reddit tools into a live catalog when only direct adapters are configured
- Severity: **P2** (P1 for any deployment that runs `paid-media-agent serve` directly instead of `serve_demo.py`) — Classification: **VERIFIED_CODE**
- Evidence: `engine/src/paid_media_agent/runtime/catalog.py:61-86` — with no Pipeboard token and at least one direct adapter, the catalog is `fixture_raw_tools() + direct_tools` when mode is `auto`, source `"fixture+direct"`, read provider `CompositeReadProvider(FixtureReadProvider(), direct_providers)`. Default mode is `auto` (`config.py:124`, `engine/.env.example:15`). The in-code comment at `:72` ("Explicit live sessions never mix synthetic platforms") is true only for `mode=live`.
- Description: an operator with X Ads or OpenAI Ads keys and the default mode gets a catalog whose Google/Meta/Reddit reads return fixture rows with current dates; `compare_periods` will happily total them with live X spend (same currency USD, same-length windows) and label the result reconciled.
- Impact: synthetic and live figures combined in one analysis without any flag. Mitigation in this repo: `serve_demo.py:163-166` refuses non-`sample`; so the path is unreachable through `docker-compose.yml`, which is why this is not rated P1 here.
- Recommendation: change the default to `live`-or-`sample` (never mix), or mark fixture-sourced rows with a quality flag and suppress any total that mixes `source_endpoint` schemes (`fixture://` vs `direct://`/pipeboard).

### J6-03 — Overview ROAS tile is always "0×" and the spend tile sums across currencies and providers
- Severity: **P2** — Classification: **VERIFIED_CODE**
- Evidence: `platform/apps/cloud/lib/cloud/reads.ts:53-55` requests metrics `['spend','impressions','clicks','conversions','roas']` — never `conversion_value`. `app/dashboard/live-data.tsx:34-42` computes `value = Σ row.metrics.conversion_value ?? 0` and `roas = totals.spend > 0 ? totals.value / totals.spend : 0`, so `value` is always 0 and the headline reads `0×` whenever spend > 0 (`:49`). The same block sums `spend` across every row irrespective of `row.currency` and `row.provider`; the footer says "Last 7 days · account currencies" (`lib/i18n/messages/overview.ts:20`). `components/ui.tsx:66` `formatNumber(value = 0, …)` renders `undefined` as `0`, so a missing per-row `roas`/`conversions` prints as `0` / `0×` (`live-data.tsx:70-71`, `reports/page.tsx:43-44`).
- Description: the first number a connected buyer sees is a wrong ROAS and a spend figure that may add SAR, USD and EUR together; the per-row table prints `0×` for both "no conversion tracking" and "ROAS genuinely 0".
- Impact: wrong KPI on the landing page; currency mixing explicitly forbidden by the project's own doc (`platform/docs/reporting-semantics.md:15`).
- Recommendation: request `conversion_value` (or use `summary.groups[].roas` from the `report` tool, which already does spend-weighted ROAS per currency, `packages/core/src/report-summary.ts:27-31`), group headline tiles by currency, and render `null`/`undefined` as "—" rather than 0.

### J6-04 — Platform providers turn undefined ratios into 0; the sandbox copies the pattern
- Severity: **P2** — Classification: **VERIFIED_CODE**
- Evidence: `platform/packages/google/src/provider.ts:198-202`, `meta/src/provider.ts:210-214`, `tiktok/src/provider.ts:160-164`, `reddit/src/provider.ts:234-238`, `microsoft/src/provider.ts:235-239`, `apple/src/provider.ts:207-211` (`roas: 0` unconditionally), `snapchat/src/provider.ts:149` (`… ? … : 0`), `apps/cloud/lib/markting/sandbox-provider.ts:128-132`. Each writes `cpa = conversions > 0 ? spend/conversions : 0`, `roas = spend > 0 ? value/spend : 0`, etc.
- Contradicts: `platform/docs/reporting-semantics.md:13` ("Adport does not turn an unavailable value into zero"), the `report` tool description `packages/core/src/tools/builtin.ts:57` ("Null metrics are unavailable"), and the engine's own rule (`compute.py:40-46` returns `None` for a zero denominator; `tests/unit/test_compute.py:61-63`).
- Description: a campaign with spend and no tracked conversions shows CPA 0 and ROAS 0 — the best and worst possible readings — and the cross-provider summary cannot tell them apart from true zeros. `summarizeReport` is careful (`report-summary.ts:4,20,31`) but only sees what providers emit.
- Impact: misleading efficiency numbers to a buyer; conversions `0` for lead-gen Meta accounts because only `omni_purchase` is counted (`meta/src/provider.ts:190-191`).
- Recommendation: emit `undefined` for ratios with zero denominators and for conversion metrics the account does not track; render "—" in the UI.

### J6-05 — "Clicks" and "conversions" are summed across platforms with different definitions and attribution, and the engine never raises `ATTRIBUTION_DIFFERS`
- Severity: **P2** — Classification: **VERIFIED_CODE** (API semantics INFERRED where noted)
- Evidence:
  - Engine: `normalize.py:130` picks `clicks` before `link_clicks` (Meta `clicks` = all clicks incl. reactions; INFERRED from Meta API semantics; probe 5 shows `clicks=120` chosen over `link_clicks=40`); `normalize.py:28` accepts `results` as `conversions` (Meta "results" depend on campaign objective); the fixture's `attribution: "7d_click_1d_view"` and X's `attribution` payload key (`direct/x_ads.py:428`, `openai_ads.py:249`) are stored only in `source_fields`/payload and never compared. `compute.py:278-298` `_combine` sums `conversions` and `conversion_value` across platforms and derives cross-platform `cvr`, `cpa`, `roas`; `compare_periods` (`compute.py:315-326`) checks currency, completeness, missing fields and window equality — not attribution or timezone. `DataQualityFlag.ATTRIBUTION_DIFFERS` (`common.py:64`) is never raised (rg, exit 1; probe 8).
  - Platform: Meta counts `omni_purchase` with the account's default attribution (no `action_attribution_windows`/`use_unified_attribution_setting` sent, `meta/src/provider.ts:170-182`); Snapchat hard-codes `swipe_up_attribution_window: '28_DAY', view_attribution_window: '1_DAY'` and maps `swipes` to `clicks` (`snapchat/src/provider.ts:58-62,146`); TikTok uses `conversion` (objective result) and `total_complete_payment_rate` as value (`tiktok/src/provider.ts:124-125,150-152`); Reddit sums click + view purchases (`reddit/src/provider.ts:230`); Google uses `metrics.conversions` (all conversion actions, `google/src/provider.ts:31-32,191-193`). `summarizeReport` sums `conversions` across providers inside one currency group (`report-summary.ts:19-24`) and the engine's X adapter uses `clicks` while adport's X adapter uses `url_clicks` (`direct/x_ads.py:420` vs `packages/x/src/provider.ts:75`).
- Description: the only acknowledgement reaches the buyer as a sentence in the rendered engine report (`render.py:189-192`, chart caption `:300`) and in a doc; the model-facing `AnalysisSummary`, the dashboard tiles and the `report` tool summary carry no flag.
- Impact: cross-platform CPA/ROAS/CTR comparisons that look precise but mix 28-day swipe attribution with 7-day click, link clicks with all clicks, purchases with objective "results".
- Recommendation: carry an `attribution` and `click_definition` field on `PerformanceRow`/`ReportRow`, raise `ATTRIBUTION_DIFFERS` when they differ within a total, and suppress or caveat cross-platform ratio metrics (keep spend totals).

### J6-06 — Live reads have no provider-reported currency, timezone or completeness: labels come from a static TOML file and partial days count as complete
- Severity: **P2** — Classification: **VERIFIED_CODE**
- Evidence: `tools/pipeboard.py:186-193` returns `ProviderResult(payload=payload)` only; `direct/x_ads.py:424-430` and `direct/openai_ads.py:245-251` likewise omit `currency`, `timezone`, `data_complete_through` (even though X `list_ad_accounts` fetches `currency`/`timezone`, `x_ads.py:301-312`). `tools/reads.py:235-239,246-247` falls back to `binding.currency` / `binding.timezone` from `config/accounts.example.toml` (or the operator's file) and `complete_through=None`. `normalize.py:141-142,156` then marks every row `is_complete=True` (probe 6: today's row is complete) and never cross-checks a row-level `account_currency` (probe 10: SAR row labelled USD). `PerformanceRow.currency` only validates the regex (`domain/metrics.py:60`).
- Description: in live mode the engine's "incomplete window" machinery (the thing that suppresses totals and prints "(incomplete)") has no signal except "days with no rows", and the currency printed next to every figure is whatever the operator typed.
- Impact: today's partial spend compared against a full previous day shows as a "drop"; a mistyped or changed account currency mislabels every number; `summarize()` formats the cross-platform total in `platforms[0].currency` (`compute.py:404-406`).
- Recommendation: require providers to return account currency/timezone (X and OpenAI already have the data) and fail or flag when the row-level currency disagrees with the binding; derive `data_complete_through` as `today − lag` per platform at minimum.

### J6-07 — `compare_periods` double-counts duplicate sources and accepts overlapping windows
- Severity: **P2** — Classification: **VERIFIED_TEST** (probe) + VERIFIED_CODE
- Evidence: `tools/compare_periods.py:57-101` iterates `artifact_ids` with no uniqueness check on `(platform, account_ref)`; `compute.py:329-331` sums all platforms. Probe 1: the same artifact twice → platform spend `70.00 USD`, `cross_platform_total 140.00 USD`, `reconciled: True`. `engine/tests/unit/test_compute.py:141-146` encodes this behaviour as expected (`[complete, complete]` → `28.000000`). `compare_periods.py:44-53` checks ordering and equal length only; probe 2: current `08-05..08-11` vs previous `08-01..08-07` accepted. Contrast `summary.py:178-179`, which does reject a second artifact for the same platform/account.
- Description: the model chooses `artifact_ids`; a campaign-grain and an ad-group-grain read of the same account, or a retried read, produce two artifacts for one account and a doubled total.
- Impact: inflated cross-platform totals and distorted period deltas presented as reconciled.
- Recommendation: dedupe by `(platform, account_ref)` (reject or pick the latest), reject overlapping windows, and add a reconciliation check across artifacts of the same account.

### J6-08 — `INCOMPLETE_WINDOW` is both over- and under-sensitive
- Severity: **P2** — Classification: **VERIFIED_TEST** (probe 3) + VERIFIED_CODE
- Evidence: `compute.py:128-129` flags an entity incomplete when it has fewer rows than days; `:181-186,203-207` propagate entity flags into `platform_flags` and set `current_complete=False` if any entity is flagged; `compare_periods` then suppresses the total (`:319-322`). Probe 3: one campaign with rows on even days only → platform `incomplete_window`, total suppressed. Providers routinely omit zero-activity days and paused campaigns have none. Under-sensitivity: see J6-06 (no completeness signal in live mode). `docs/ARCHITECTURE.md:654` already documents that the default report run on fixtures is always "incomplete".
- Impact: totals suppressed and "(incomplete)" labels on genuinely complete data (noise), while truly partial live days pass (silence) — the flag cannot be trusted either way.
- Recommendation: entity-level coverage should not define platform completeness; use provider freshness (`data_complete_through`) for completeness and a separate `sparse_entity` note for coverage.

### J6-09 — Day assignment and time-zone handling make daily rows non-comparable across sources
- Severity: **P3** — Classification: **VERIFIED_CODE**
- Evidence: `normalize.py:106-109,152-157` reads `date|day|date_start` only and builds a one-day window, so a multi-day Meta row (`date_start`≠`date_stop`) is booked on its start day (probe 5). `direct/x_ads.py:199-210,369-383` slices and assigns days at **UTC** midnight, while `reads.py:247` labels the rows with the TOML timezone (e.g. `America/New_York`). On the platform side Reddit queries with `time_zone_id: 'UTC'` (`reddit/src/provider.ts:114,139`, confirmed by `reddit/test/reddit.test.ts:109`) while Google/Meta use account-local report dates and Snapchat/X compute account-local midnight (`snapchat/src/provider.ts:59-60,158-171`, `x/src/provider.ts:44-46`). Engine cross-platform totals ignore timezone differences (probe 4; `TIMEZONE_MISMATCH` never raised).
- Impact: boundary skew of up to a day between sources in the same "7-day" comparison; `platform/docs/reporting-semantics.md:27` describes this generally but understates it ("sends the resolved calendar dates to each provider") — Reddit is explicitly UTC.
- Recommendation: carry the provider's reporting timezone on each row, honour `date_stop`, and flag `TIMEZONE_MISMATCH` when combining.

### J6-10 — "reconciled" is a near-tautology surfaced to the buyer as assurance
- Severity: **P3** — Classification: **VERIFIED_CODE** (probe 7)
- Evidence: `compute.py:216-224` compares Σ(entity spend) with Σ(row spend) of the same rows; `:225-248` provider-total checks run only when `provider_totals` exists, which only the fixture supplies (`fixtures.py:386-391`; Pipeboard/X/OpenAI never return `totals`, `reads.py:266` stores `{}`). `PeriodComparison.reconciled` is `all(...)` over these (`domain/analysis.py:190-192`); `reports/render.py:245-285` checks the renderer reproduced its own numbers. The cloud prints "reconciled / مُطابَق" (`engine-reports.tsx:117`, `reports.ts:37,79`).
- Impact: a buyer reads "reconciled" as "matches the platform"; in live mode nothing external was checked.
- Recommendation: rename to "internally consistent" unless a provider total was compared, and show which checks ran.

### J6-11 — CTR unit differs between the two systems and is unlabelled in one of them
- Severity: **P3** — Classification: **VERIFIED_CODE**
- Evidence: engine `ctr = clicks/impressions` as a fraction (`compute.py:87`), formatted ×100 only in `render.py:59-60`; `summary.py:100,140` emits the raw fraction string (`"0.1"`) to the model with no unit. Adport defines `ctr` as a percentage (`reporting-semantics.md:11`; providers multiply by 100, e.g. `google/src/provider.ts:198`; sandbox `:128`).
- Impact: an Assistant answer or a bridge that mixes the two reads a 10% CTR as 0.1%.
- Recommendation: one convention, labelled in the payload (`ctr_pct`).

### J6-12 — Five data-quality flags exist in the type system but are never produced
- Severity: **P3** — Classification: **VERIFIED_CODE**
- Evidence: `domain/common.py:55-65` defines `CURRENCY_MISMATCH`, `TIMEZONE_MISMATCH`, `ATTRIBUTION_DIFFERS`, `SOURCE_UNAVAILABLE`, `STALE_CATALOG`; `rg` over `engine/src` finds no other reference (exit 1). Mixed currencies are handled by raising (`compute.py:149-151`) or suppressing (`:316-318`) without the flag; mixed timezones are not handled at all (probe 4).
- Impact: the enum advertises detections that do not exist; downstream code (and reviewers) may assume coverage.
- Recommendation: implement or delete.

### J6-14 — Dashboard tables omit currency while the doc claims currencies "stay provider-specific"
- Severity: **P2** — Classification: **VERIFIED_CODE**
- Evidence: `app/dashboard/reports/page.tsx:33-44` and `live-data.tsx:65-71` print `spend` with `formatNumber` (no currency) although every `ReportRow` carries `currency` (`core/src/model.ts:41-42`) and `formatMoney` exists (`components/ui.tsx:67-70`); `lib/i18n/messages/reports.ts:5,47` promises "Currencies stay provider-specific".

### J6-15 — Sandbox synthetic metrics: deliberately unlabelled tool names, process-global switch, formula-generated history
- Severity: **P3 / GAP** — Classification: **VERIFIED_CODE**; reachability **MOCK_ONLY**

- Impact: today the synthetic report rows cannot reach a dashboard; the risk is latent (any future `registry.call('report')` through the bridge runtime would return unlabelled synthetic rows). ## What a world-class system would need (gaps, concrete)

1. A `data_source` / provenance field on every row, summary, report and API response (`fixture`, `sandbox`, `live:<provider>`), enforced at render time with a visible banner and refused in production totals when mixed (J6-01, J6-02, J6-15).
2. Provider-reported `currency`, `timezone`, `attribution_setting`, `click_definition`, `freshness/data_complete_through` on `PerformanceRow` and `ReportRow`; totals that compare these and raise the already-defined flags (J6-05, J6-06, J6-09, J6-12).
3. Completeness derived from provider freshness plus a platform lag table (Google ~3h conversions lag, Meta up to 72h, Snapchat/TikTok D+1), not from entity row counts (J6-08).
4. Null, not zero, for undefined ratios end-to-end, with "—" rendering and an explicit "not tracked" state for conversions (J6-04, J6-03).
5. Per-currency KPI tiles and tables with currency codes; optional FX with sourced rate and timestamp (J6-03, J6-14).
6. Source dedupe in `compare_periods`, window-overlap rejection, and cross-grain reconciliation (campaign Σ = ad-group Σ, as the fixture already models in `fixtures.py:261-292`) (J6-07).
7. Real external reconciliation: provider account-level totals fetched independently of row reads and compared, with the result named honestly (J6-10).
8. A unit contract shared by engine and platform (`ctr_pct`, `roas_ratio`, money in major units with currency) (J6-11).
9. Captured, real API response fixtures for Reddit/Snap/TikTok/X unit assumptions (J6-13).
10. Tenant-scoped engine artifacts and report indexes (J6-01 note).
