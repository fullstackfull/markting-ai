# A7 — X Ads expert

Audit question: can MARKTING-AI understand and manage X Ads like a senior media buyer, or does it merely have a connector? Repository code is the source of truth; `platform/docs/providers/x.md`, `engine/OPERATIONS.md`, `docs/ARCHITECTURE.md` and the playbook skill are treated as claims.

Short answer: two independent, read-mostly X integrations exist. The **platform** package (`@adport/provider-x`) is a carefully engineered, contract-tested connector with three campaign-level writes behind the shared policy gate, but it exposes only spend/impressions/link-clicks totals and campaign-shell management. The **engine** direct adapter is a thinner, read-only daily-stats reader whose metric definitions (placement coverage, click definition, day boundaries, conversions) disagree with the platform package. The AI engine cannot act on X at all: `x_ads` is not a bridge provider and no X mutation is admitted. Nothing exists for breakdowns, audiences, bidding, line-item/creative management, attribution, pacing or fatigue. Classification overall for "expert X media buying": PARTIAL, heavily weighted toward reporting of three metrics.

## Findings

### A7-01 — Platform X report rows carry no currency although the provider knows it
- Severity: P2
- Classification: VERIFIED_CODE
- Evidence: `platform/packages/x/src/provider.ts:10` (internal `Entity.currency`), `provider.ts:48` (mixed-currency check uses it), `provider.ts:81` and `provider.ts:83` (rows pushed with `provider, accountId, entity, metrics` only); `platform/packages/core/src/model.ts:41-42` (`ReportRow.currency?` "absent when the provider cannot supply it"); `platform/packages/core/src/report-summary.ts:10-11,19-24` (rows without currency are grouped per provider/account and totals are emitted with `currency: null`); `platform/packages/x/src/entities.ts:9-11` (`listAccounts` omits currency), `platform/apps/cloud/lib/cloud/account-selection.ts:46,139` (inventory row stores `currency ?? null`).
- Description: campaigns and line items expose `currency` (`schemas.ts:15,19`) and the provider already enforces single-currency account totals, yet every emitted `ReportRow` drops it. Downstream summaries, the cloud account inventory and any Arabic-first UI therefore show X spend as unit-less numbers. The documented justification ("accounts have no currency") applies to the account object, not to campaign/line-item rows.
- Impact: X spend cannot be labelled or safely combined with other providers in the shared summary; a USD and a SAR X account in one workspace would be totalled per account with `currency: null` rather than flagged.
- Recommendation: populate `ReportRow.currency` from the entity (campaign/line-item) currency; for account level, use the single verified currency (the mixed-currency check already guarantees uniqueness).

### A7-02 — Engine direct adapter reports a single placement as the campaign total
- Severity: P2
- Classification: VERIFIED_CODE
- Evidence: `engine/src/paid_media_agent/tools/direct/x_ads.py:293-301` (`"placement": "ALL_ON_TWITTER"` only); contrast `platform/packages/x/src/analytics.ts:8` and `provider.ts:61-62` (iterates `ALL_ON_TWITTER`, `SPOTLIGHT`, `TREND` and sums); `platform/docs/providers/x.md:58-59` ("A single-placement report must not be labeled a full total"); tool description `x_ads.py:88-90` ("Daily campaign stats ... billed spend").
- Description: the engine's "campaign performance" is X's `ALL_ON_TWITTER` placement only. Spend and delivery on Spotlight/Trend takeovers are silently excluded while the row is presented as the campaign's daily spend.
- Impact: the AI engine and the platform package can report different spend for the same campaign and day; pacing or budget judgments made by the engine on accounts that use Spotlight/Trend placements will under-count real billed charge.
- Recommendation: either query all placements and sum (as the platform does) or label the payload explicitly as `placement=ALL_ON_TWITTER` and surface a data-quality flag.

### A7-03 — Engine uses X `clicks` (all engagements) where the platform uses `url_clicks`
- Severity: P2
- Classification: VERIFIED_CODE
- Evidence: `engine/src/paid_media_agent/tools/direct/x_ads.py:359` (`"clicks": _pick(metrics.get("clicks"), offset)`); `platform/packages/x/src/analytics.ts:13` and `provider.ts:65` (`url_clicks` -> `clicks`); `platform/docs/providers/x.md:64-65` ("`clicks` includes likes and other engagements; `url_clicks` measures link/Website Card clicks"); `engine/src/paid_media_agent/tools/normalize.py:125` (normalized `clicks` from `clicks`), and test `platform/packages/x/test/report.test.ts:270` ("maps micros and link clicks, not engagement clicks").
- Description: two code paths in one product define "clicks" differently. The engine's CTR/CPC for X will be inflated relative to the platform's and to any other provider's link-click metric, with no flag.
- Impact: cross-platform efficiency comparisons produced by the engine (its stated purpose, `platform-playbooks.md:58-60`) are wrong for X.
- Recommendation: request `url_clicks` in the engine adapter (or emit both `clicks` and `link_clicks` and let `normalize.py:125` prefer `link_clicks`).

### A7-04 — Engine stats windows ignore the account timezone the platform package treats as mandatory
- Severity: P2
- Classification: VERIFIED_CODE (behaviour), INFERRED (Ads Manager mismatch)
- Evidence: `engine/src/paid_media_agent/tools/direct/x_ads.py:138-149` (`stats_windows` slices at UTC midnight), `x_ads.py:308` (`day0` from the UTC window start); test `engine/tests/unit/test_direct_adapters.py:76-81` asserts UTC slicing; contrast `platform/packages/x/src/analytics.ts:117-134` (`xAccountMidnight`, DST handling, refuses non-whole-hour zones) and `provider.ts:42-46`; `platform/docs/providers/x.md:66-68`; engine binds a timezone per account (`config.py:69`) and labels rows with it (`reads.py:247`, `normalize.py:144-149`) but never uses it to build the request.
- Description: the engine labels a UTC day as the account's local day. For an account in e.g. `Asia/Riyadh` (UTC+3) the engine's "2026-08-01" row contains 03:00-03:00 local, not the Ads Manager day, and the platform package would compute 2026-07-31T21:00Z. For half-hour zones the platform refuses; the engine sends a request that X may reject (not verified live).
- Impact: daily figures from the engine do not reconcile with Ads Manager or with the platform package; day-over-day anomaly logic on X is unreliable.
- Recommendation: compute window boundaries at account-local midnight (reuse the binding timezone) and fail or flag on non-whole-hour offsets, mirroring `analytics.ts`.

### A7-05 — Engine claims account currency that X does not provide; operator default is USD
- Severity: P2
- Classification: VERIFIED_CODE
- Evidence: `engine/src/paid_media_agent/tools/direct/x_ads.py:55` ("with currency and timezone"), `x_ads.py:245` (`"currency": a.get("currency")`); X account schema has no currency (`platform/packages/x/src/schemas.ts:6-9`; `platform/docs/providers/x.md:37-38`); `engine/src/paid_media_agent/cli.py:235` (`accounts add --currency` default `USD`); `engine/src/paid_media_agent/tools/reads.py:246` (`currency=result.currency or binding.currency`; the X `ProviderResult` sets no currency, `x_ads.py:363-369`); campaign-level `currency` is read (`x_ads.py:266`) but not propagated into performance rows.
- Description: `accounts discover` prints an empty currency for X; an operator who accepts the default binds the account as USD; every normalized X row is then labelled USD regardless of the real funding-instrument currency. The engine has the campaign currency in hand and discards it.
- Impact: silent mislabelling of X spend currency in engine reports and cadence summaries for any non-USD advertiser (the product's primary market is Arabic-speaking, so non-USD is the normal case).
- Recommendation: set `ProviderResult.currency` from the campaign/line-item currency (fail if mixed), remove the "with currency" claim from the tool description, and make `--currency` required when no discovered currency exists.

### A7-06 — Engine treats `conversion_purchases` as a verified conversion metric; the platform package explicitly does not
- Severity: P3
- Classification: NOT_VERIFIED (contract), VERIFIED_CODE (inconsistency)
- Evidence: `engine/src/paid_media_agent/tools/direct/x_ads.py:299` (`WEB_CONVERSION` group), `x_ads.py:325-335` (reads `conversion_purchases.metric[offset]`), `x_ads.py:367` (`"attribution": "x_web_conversion_purchases"`); fixture is self-authored in `engine/tests/unit/test_direct_adapters.py:122`; `platform/packages/x/src/provider.ts:35` and `platform/docs/providers/x.md:76-80` ("purchase object contract and sale-amount units still need official verification ... never fabricated as zero").
- Description: the two halves of the product disagree on whether X purchase conversions are trustworthy. The engine also never reads `sale_amount`, so `conversion_value` is always missing and every X row is flagged `MISSING_METRIC` (`normalize.py:136-137`). Only purchases are counted; sign-ups, downloads, custom events are ignored. No attribution window or view-through control exists in either code path.
- Impact: ROAS is never available for X in the engine; conversion counts come from an unverified object shape.
- Recommendation: verify the `WEB_CONVERSION` object contract against the official analytics reference and either implement it in both code paths or mark it unverified in both.

### A7-07 — Zero/null metric series in X analytics break engine daily rows
- Severity: P2
- Classification: VERIFIED_CODE
- Evidence: `engine/src/paid_media_agent/tools/direct/x_ads.py:318-321` (row loop length is `len(impressions)`; `metrics.get("impressions") or []`), `x_ads.py:373-376` (`_pick` returns `None` when the series is not a list); `engine/src/paid_media_agent/tools/normalize.py:115-118` (`spend is None` -> `NormalizationError("row without spend")`), `reads.py:256-257` (any `NormalizationError` -> `ReadDenied` for the whole read); X documents null metric values as zero-equivalent (`platform/docs/providers/x.md:62-63,81-82`; platform handles this at `provider.ts:67`).
- Description: if X returns `impressions: null` for an entity in a window, that entity emits no rows (spend silently dropped); if it returns `billed_charge_local_micro: null` (zero spend, a normal state for paused campaigns), the row has `spend_micros: None` and normalization rejects the entire campaign-performance read.
- Impact: a single zero-spend campaign in the account can make the engine's X campaign report unavailable for the whole window; partial nulls silently drop spend.
- Recommendation: treat null scalar series as zero (per X FAQ), derive the day count from the window rather than from `impressions`, and keep per-row failures from denying the read.

### A7-08 — Engine `_get` has no HTTP-200 error-envelope check or response-size bound
- Severity: P3
- Classification: VERIFIED_CODE
- Evidence: `engine/src/paid_media_agent/tools/direct/x_ads.py:203-211` (status check, `response.json()`, dict check only); contrast `platform/packages/x/src/client.ts:66-70` (rejects `errors` envelopes), `analytics.ts:27,82-92` (20 MiB bound), `oauth.ts:10,20-35` (16 KiB bound).
- Description: an X 200 response with an `errors` array and no `data` becomes "malformed data" rather than a provider error with the documented guidance; a large body is buffered unbounded. Secrets handling itself is sound: `SecretStr` fields (`config.py:150-153`), header built from `get_secret_value()` only inside `_get` (`x_ads.py:194-202`), status errors never echo bodies (`_http.py:47-57`), transport errors are redacted (`_http.py:60-63`), redirects are not followed (httpx default), and `test_errors_never_carry_credentials` covers the status path (`test_direct_adapters.py:225-239`). The consumer key is held as a plain `str` after `get_secret_value()` (`x_ads.py:168,184`); it is an app identifier rather than a secret, but it is still declared `SecretStr` in settings.
- Impact: degraded diagnostics; minor memory exposure.
- Recommendation: mirror the platform client's envelope and size checks.

### A7-09 — Cloud runtime instantiates the X provider without checking `X_OAUTH_ENABLED`
- Severity: P3
- Classification: VERIFIED_CODE
- Evidence: `platform/apps/cloud/lib/cloud/runtime.ts:88-93` (conditions: stored grant, `providerAllowedForOrganization('x')`, consumer key/secret present); `platform/apps/cloud/lib/cloud/provider-oauth-x.ts:11-13,20` (flag checked only in the OAuth adapter); `platform/apps/cloud/lib/env.ts:72` (default `'false'`); `platform/apps/cloud/lib/cloud/provider-rollout.ts:12-13` (allowlist unset -> all gated providers allowed, confirmed by `test/provider-rollout.test.ts:8-11`).

- Impact: operators cannot use the flag as a kill switch for X traffic; limited because writes remain behind the policy engine and account scope.

### A7-10 — Budget deltas for X omit the currency the planner has already fetched
- Severity: P3
- Classification: VERIFIED_CODE
- Evidence: `platform/packages/core/src/provider.ts:23-30` (`BudgetDelta.currency?`); `platform/packages/x/src/writes.ts:24` (create delta without `currency` although `funding.currency` is in scope at `writes.ts:16,22`), `writes.ts:49` (update delta without `current.currency`); `platform/packages/core/src/policy/engine.ts:134-152` (absolute cap `max_daily_budget_micros` compared without currency awareness).
- Description: approvers see `toMicros` without a currency in the structured preview (the create path puts the currency only in the free-text `changes` string). The absolute micros cap in policy is currency-blind for every provider; for X this matters because campaigns within one account can carry different funding-instrument currencies (`schemas.ts:11,15`).
- Impact: a 25 000 000 micros cap means different things for SAR and USD campaigns; the human-review surface lacks the unit.
- Recommendation: set `currency` on both delta types; consider per-currency caps in policy.

### A7-11 — Asynchronous analytics job handles are process-local; long-range X reports in the cloud may not complete
- Severity: P3
- Classification: VERIFIED_CODE (behaviour), INFERRED (serverless impact), DOCUMENTED_ONLY (acknowledged limitation)
- Evidence: `platform/packages/x/src/analytics.ts:31-32` (in-memory `jobs`/`inflight` maps), `analytics.ts:50-71` (16 polls at 1 s then throws "still processing; retry this report to resume polling"), `provider.ts:59` (any range > 7 days, any range ending more than 7 days ago, and all `MEDIA_CREATIVE` reports go async); `platform/docs/providers/x.md:73-75` ("Restarting the process does not retain that in-memory handle"); `platform/apps/cloud/lib/cloud/runtime.ts:92` (a new `XAdsProvider`/`XAdsAnalytics` per tenant runtime build).
- Description: the `last_30_days` preset (`core/src/model.ts:67-68`) always takes the async path. Each `createTenantRuntime` call creates a fresh analytics instance, so a retry from a new request builds a new job instead of resuming. A job that X takes longer than ~15 s to produce fails the whole report.
- Impact: 30-day X reports in the hosted product are best-effort; repeated retries create duplicate jobs. For a product that will be asked for "last month" routinely, this is a reliability gap; it is documented, so P3.
- Recommendation: persist job handles (keyed by the request signature) in the tenant store, or run async analytics through a background worker.

### Writes: existence and gating
- Exactly three writes exist, all in the platform package: `x_create_campaign`, `x_set_campaign_status`, `x_set_budget` (`tools.ts:11-13`). VERIFIED_TEST: `report.test.ts:400-414` proves preview is read-only, argument drift is rejected, apply happens once, the 25 % budget-delta cap triggers, and protected accounts are refused.
- Cloud adds account scoping on both the tool argument (`account-scope.ts:36-56`) and the provider (`account-scope.ts:81-89`), and `PostgresPendingStore`/`PostgresAuditStore` (`runtime.ts:141`). VERIFIED_CODE.
- The engine has no X write path at all (A7-12).

### Server-validated vs client-side preview
- `capabilities()` returns `serverDryRun: false` and `previewWrite` returns `serverValidated: false` (`provider.ts:18-22`). The preview is a local plan built from reads (`getFundingInstrument` or `getCampaign`) with local invariants (daily <= total, funding usable, not deleted/draft, `LINE_ITEM` optimization) (`writes.ts:15-17,37,43-47`). Apply then re-plans, executes a signed POST/PUT with query parameters, and verifies that the returned campaign matches the approved fields (`writes.ts:27-29,55-58`); mismatches raise without retry. X offers no dry-run endpoint, so this is the correct shape, but a value X would reject (e.g. a budget below its minimum, or a name collision) is discovered only at apply time.

## What a world-class system would need (gaps, concrete)

1. Full entity model: line items with bid amount/strategy, optimization goal, start/end, pacing, placements; promoted tweets with tweet text/media; cards and media library; targeting criteria; tailored audiences; web event tags and conversion settings. Today only ids and a handful of fields exist (`schemas.ts`).
2. Analytics depth: `DAY`/`HOUR` granularity in the platform package; `segmentation_type` (age, gender, locations, platforms, devices, interests, keywords); all placements exposed as a breakdown; `MEDIA`, `VIDEO`, `WEB_CONVERSION`, `MOBILE_CONVERSION` groups with verified object contracts; reach/frequency; currency on every row.
3. One definition of each metric across platform and engine (link clicks, placement coverage, day boundaries, conversions) — A7-02/03/04/06.
4. Engine action path for X: bridge mapping and admitted mutations (A7-12), plus line-item budget/bid/status writes and promoted-tweet pause behind the same policy engine.
5. Pacing and anomaly logic: spend-to-date vs daily/total budget, flight progress, frequency-based fatigue, delivery stalls (requires 2 and a persisted time series).
6. Durable async analytics (A7-11) and a background refresh so "last 30 days" is a cached read, not a 15-second gamble.
7. Offline X fixture dataset for the engine, demos and regression tests (A7-13).
8. Account health: funding instrument balance/credit limit, account spend caps, approval and policy rejections surfaced as structured signals rather than HTTP error strings.
9. Arabic-first presentation needs currency codes on X rows; the current data model yields `currency: null` for X everywhere (A7-01, A7-05).
