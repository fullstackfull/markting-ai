## Findings

### C7-01 — adport's two-step write gate is not a human approval; an AI client can preview and apply in two calls
- Severity: **P1** (unsafe ad execution; contradicts the product's stated central invariant)
- Classification: VERIFIED_CODE (mechanism); DOCUMENTED_ONLY claim contradicted
- Evidence:
  - `platform/packages/core/src/tools/write.ts:143-156` — the same tool, called a second time with `pending_operation_id`, runs `ctx.engine.apply`.
  - `platform/packages/core/src/policy/engine.ts:87-125` — `apply` checks only pending-id existence, expiry, hash equality and `protected_accounts`; no actor, role or "different principal" check.
  - `platform/packages/mcp/src/index.ts:121-124,169` — every non-readOnly tool is registered on `/mcp` for principals holding `tools:write`; the callback is `runtime.registry.call(tool.name, args, ...)` with whatever args the client supplies, including `pending_operation_id`.
  - `platform/apps/cloud/app/api/v1/tools/[tool]/route.ts:10-13` — same for REST.
  - `platform/apps/cloud/app/api/approvals/[id]/apply/route.ts:17-24` — the human apply path (session principal, owner/admin, self-approval guard) exists only on the dashboard route; nothing forces pending operations created over MCP/REST to go through it.
  - `README.md:79` — "nothing is applied until a human approves it there"; `README.md:85` — "lets an admin apply or reject it on Approvals".
  - `docs/ARCHITECTURE.md:203-206` — `require_validation` is documented as inert.
- Description: For the Assistant (engine → bridge) path the claim holds, because the bridge never sends `pending_operation_id` (`lib/markting/bridge.ts:5-7,76`) and the engine client has no approve path (`engine-client.ts:61,77-79`). But the product also exposes the full adport write surface over `/mcp` and `/api/v1/tools/*` to any agent whose API key or OAuth grant carries `tools:write` (plan-gated, `app/mcp/route.ts:23-39,51`). Such an agent can call `google_set_budget` (or any `*_api_update`) once to get a pending id and immediately again to apply it. The Approvals page then shows the row as applied after the fact.
- Impact: Live spend/status changes without any human decision, within the budget-delta/absolute caps only. For an "AI media buyer" this is the exact failure mode the architecture says it prevents.
- Recommendation: In the markting cloud runtime, refuse `pending_operation_id` on `/mcp` and `/api/v1/tools/*` (or make `require_validation`/a new `require_human_apply` policy flag real: `PolicyEngine.apply` should require an approver principal distinct from the creator), so the dashboard apply route is the only second step. Add a contract test that an MCP client cannot apply its own pending operation.

### C7-02 — Generic escape-hatch write tools give the model arbitrary API-shaped mutations with keyword-only policy
- Severity: **P1** (serious financial/operational risk when exposed to an autonomous agent)
- Classification: VERIFIED_CODE; capability UNSAFE_TO_AUTOMATE
- Evidence (schemas):
  - `platform/packages/google/src/tools.ts:155-193` — `google_api_create` (`creates: z.array(z.record(z.string(), z.unknown()))`), `google_api_update` (`update: z.record(...)`, `update_mask: z.string()`), `google_api_remove` (`resource_names`, destructive).
  - `platform/packages/meta/src/tools.ts:387-418` — `meta_api_create` (`fields: z.record(z.string(), z.unknown())`), `meta_api_update`, `meta_api_delete`.
  - `platform/packages/tiktok/src/tools.ts:108-133` — `tiktok_api_create/update/delete` (`path`, `body: z.record(...)`).
  - `platform/packages/apple/src/tools.ts:111-145`, `platform/packages/microsoft/src/tools.ts:287-313`, `platform/packages/reddit/src/tools.ts:216-233` — same pattern.
- Evidence (policy depth):
  - Google update: `platform/packages/google/src/provider.ts:345-351` rejects only `service === 'campaignBudgets'` or `/budget/i` in `update_mask`; no check on `status` (ENABLED starts delivery), `cpc_bid_micros`, `target_cpa_micros`, `target_roas`, targeting criteria, ad schedules.
  - TikTok update: `provider.ts:288-291` rejects only keys matching `/budget/i` (`containsTikTokBudget`, `provider.ts:470-474`); `bid_price`, `conversion_bid_price`, `operation_status: 'ENABLE'`, schedule, targeting pass.
  - Meta update: `provider.ts:376-379` rejects `/budget/i` keys only (`containsMetaBudget`, `provider.ts:624-629`); `status: 'ACTIVE'`, `bid_amount`, `targeting`, `promoted_object` pass.
  - Microsoft update: `provider.ts:316-320` budget-key check only; Apple update: `provider.ts:502-519` path allowlist + money rejection; Reddit update uses a broader `MONEY_KEY` (`provider.ts:453`) and an ownership read (`provider.ts:402-407`) — the best of the set.
  - Creates: paused-status coercion exists everywhere (`google/provider.ts:319-325`, `meta/provider.ts:351-354`, `tiktok/provider.ts:268-274`, `reddit/provider.ts:434-451`, `microsoft/provider.ts:302`, `apple/provider.ts:775-786`), and budget-like keys are reported as `budgetDeltas` for the caps — but nothing else in the body is interpreted.
  - All generic writes report `serverValidated: false` on TikTok/Apple/Microsoft/Reddit (`tiktok/provider.ts:221-231`, `reddit/provider.ts:185-194`); the "preview" is a JSON echo of the body (`tiktok/provider.ts:277,295,311`).
- Description: These tools are upstream adport's deliberate "documented API passthrough". In this product they are registered in the tenant runtime for every connected provider (`platform/apps/cloud/lib/cloud/runtime.ts:103,108,113,117,126,138`) and surfaced to agents over MCP/REST. Combined with C7-01, an agent can e.g. `google_api_update {service:'campaigns', updates:[{update:{resourceName:'customers/…/campaigns/…', status:'ENABLED'}, update_mask:'status'}]}` twice and start delivery on a paused campaign with no human and no risk flag; or change bids by any factor (bid changes are explicitly excluded from budget caps, `google/provider.ts:689-690`).
- Impact: Uncapped financial exposure through bids/status/targeting; destructive deletes (`*_api_delete/remove`) are one preview away.
- Recommendation: For the markting product, do not register the `*_api_*` namespace tools in the tenant runtime by default (or gate behind an org policy flag off by default); for typed status tools, add a "starts delivery" risk flag and require human apply; add bid/target fields to the money detectors or route them to typed tools (`google_set_bid_ceiling`, `apple_set_bid` exist — mirror that elsewhere). Keep the generic tools for CLI/stdio operators only.

### C7-03 — Budget/bid detection is regex-by-key-name and inconsistent across providers
- Severity: **P2**
- Classification: VERIFIED_CODE (regexes); impact on real API field names INFERRED
- Evidence: TikTok `/budget/i` (`tiktok/provider.ts:470-474,485`); Meta `/budget/i` (`meta/provider.ts:611,628`); Google `/budget/i` on `update_mask` only (`google/provider.ts:346`), budget creates counted only when `service === 'campaignBudgets'` (`provider.ts:327`); Microsoft `collectMicrosoftBudgets` (`microsoft/provider.ts:543-555`); Reddit `MONEY_KEY = /(?:goal_value|spend_cap|bid_value|budget(?:_micros)?|daily_budget|lifetime_budget)$/i` (`reddit/provider.ts:453`); Apple `collectCreatedMoney` on Money shapes (`apple/provider.ts:807-821`).
- Description: Google's `google_api_create` with `service: 'campaigns'` can embed a `campaignBudget` resource reference to any existing budget and no delta is produced; a `campaignBudgets` create needs `amountMicros` (`provider.ts:875-884`) but a later `campaigns` update can re-point a campaign to a bigger budget without triggering `/budget/i` (mask `campaign_budget` does match `/budget/i` — fine — but `campaignBudget` camelCase mask also matches; re-pointing via `google_api_create` of a campaign referencing a large shared budget does not). TikTok `bid_price` and Meta `bid_amount` are never policy-checked. The policy engine's percent cap applies only when `fromMicros > 0` (`core/src/policy/engine.ts:143`), so creates and any delta without a current-value lookup bypass it.
- Impact: Caps are advisory for anything but the typed `*_set_budget` tools.
- Recommendation: Replace key regexes with per-provider explicit money/bid field maps; treat unknown fields in generic bodies as "requires human apply"; consider refusing generic writes whose body contains any field not on a per-service allowlist.

### C7-04 — Cloud account-scope authorizer covers only top-level `account_id`/`customer_id`; generic reads can cross accounts under one grant
- Severity: **P2** (cross-account data exposure within an organization's OAuth grant; the authorizer is the product's "enabled accounts" boundary)
- Classification: VERIFIED_CODE (authorizer and provider handlers); provider-side behaviour for the unscoped Apple case NOT_VERIFIED
- Evidence:
  - `platform/apps/cloud/lib/cloud/account-scope.ts:48-54` — checks `input.account_id` or `input.customer_id` only.
  - `platform/apps/cloud/lib/cloud/runtime.ts:72,77,82,86,92,103,108,113,117,126,138` — provider-namespaced read tools get the **unwrapped** provider; only the authorizer protects them (also stated in `docs/ARCHITECTURE.md:328`).
  - Reddit: `platform/packages/reddit/src/provider.ts:424-428` — `assertReadScoped` allows `campaigns/{id}`, `ad_groups/{id}`, `ads/{id}`, `structured_posts/{id}` for any id, without an `ad_account_id` ownership check (the write path does check ownership, `provider.ts:402-407`).
  - TikTok: `platform/packages/tiktok/src/provider.ts:207-208` — `advertiser_id` is overridden, but `params` is spread first and may carry `advertiser_ids`, `bc_id`, `owner_bc_id` for endpoints that accept them; `validateTikTokPath` (`provider.ts:437-443`) allows any `[a-z0-9_/-]` path.
  - Apple: `platform/packages/apple/src/tools.ts:15` — `account_id` optional; `provider.ts:154-157` — when omitted no `X-AP-Context` header is sent (`apple/src/client.ts:89`), and the authorizer skips the check because `explicit` is undefined. `APPLE_READ_GET_ROOTS` (`provider.ts:84`) includes `campaigns/{id}`, `adgroups/{id}`, `keywords/{id}`. Whether Apple serves those without an account context is NOT_VERIFIED.
  - Google: `google_gaql.customer_id` is normalized and must be 10 digits (`google/src/client.ts:32`) and is checked by the authorizer — scoped correctly. Meta: `meta_api_read` always prefixes `act_{account}` (`meta/provider.ts:263-268`) — scoped correctly.
- Impact: An organization that enabled only account A for agent access can still have the agent read campaign objects of account B (same Reddit/TikTok grant) by id.
- Recommendation: Wrap the provider handed to `<id>Tools()` in `AccountScopedProvider` too, or extend the authorizer with per-tool scope extractors (path/`advertiser_ids`); in Reddit `apiRead` call `assertOwnedResource` for single-resource paths; make Apple `account_id` required except for an explicit `acls|me` allowlist.

### C7-05 — Engine read scoping is by one argument name; other id-bearing arguments pass through
- Severity: **P2** (potential cross-account read with a shared Pipeboard token)
- Classification: VERIFIED_CODE (mechanism); exploitability against the live Pipeboard catalog NOT_VERIFIED
- Evidence: `engine/src/paid_media_agent/tools/catalog.py:150` — `account_arg = next(n for n in platform_policy.account_arg_names if n in properties)` picks the first match; `DEFAULT_LOCAL_POLICY` lists two names for Meta/LinkedIn/GA (`catalog.py:95-115`). `tools/reads.py:170-181` — rejects the chosen `account_arg` if supplied and any top-level string value equal to a *configured* provider id (`self._accounts.provider_ids()`), then injects the binding. Non-string/nested values and ids not in the registry are not checked. `model_facing_schema` removes only `entry.account_arg` from the model-facing schema (`reads.py:107-111`).
- Description: If a live tool exposes both `account_id` and `ad_account_id` (Meta), or `login_customer_id`/`manager_customer_id` (Google), or a list argument of ids, the model can name an account that is not configured as an alias and the host will forward it under the shared token. Fixture tools expose a single account argument, so tests cannot show this (`tools/fixtures.py:47-59`); `test_dispatcher_rejects_raw_ids_bad_schema_and_wrong_platform` (`engine/tests/unit/test_reads_and_surfaces.py:46`) covers the configured-id case only.
- Recommendation: Deny any schema property whose name is in `account_arg_names` or matches an id pattern unless it is the injected one; walk nested values when checking for provider ids; or keep an operator-reviewed per-tool argument allowlist alongside the write policy.

### C7-06 — Engine binds third-party tools to the model on the strength of their `readOnlyHint`
- Severity: **P2**
- Classification: VERIFIED_CODE (mechanism); VERIFIED_TEST for the deny cases that exist
- Evidence: `engine/src/paid_media_agent/tools/catalog.py:170-190` — `readOnlyHint is True` ⇒ `ToolClass.READ`, bound directly (`tools/reads.py:333-345`) and directly callable (`middleware/authorization.py:86-92` only blocks non-READ classes). Name deny list is `mutate|raw|delete|remove|purge` (`catalog.py:81-87`). `pipeboard.py:48-69` copies annotations from the MCP server verbatim. `PipeboardWriteProvider.call_mutation` has the inverse guard (`pipeboard.py:209-210`) but nothing guards a misannotated read. Tests: `engine/tests/unit/test_catalog_policy.py:30,39,48,64` (all passed).
- Description: Pipeboard is an external MCP server. A tool named `update_campaign_budget`, `create_audience` or `upload_customer_list` with `readOnlyHint: true` (misconfiguration or malicious server) becomes a direct model call with no proposal, approval, readback or risk flag. The deny patterns do not cover `create|update|set|pause|enable|upload|add|apply|publish|archive`.
- Recommendation: Add verb-based deny patterns for READ classification, and/or pin the read catalog revision the way live writes are pinned (`PAID_MEDIA_LIVE_WRITE_CATALOG_REVISION`, `tools/writes.py:208-216`) so a changed/added read tool needs operator review.

### C7-07 — Model filesystem write access covers the artifact store, report output and the kill switch
- Severity: **P2** (integrity of computed numbers and of served report files; self-DoS)
- Classification: VERIFIED_CODE; VERIFIED_TEST that writes outside `/workspace` and to `/workspace/skills` are denied (`engine/tests/contract/test_read_path_graph.py:26-36`)
- Evidence: `engine/src/paid_media_agent/runtime/local.py:47-49` — `write` allowed on `/workspace/**`, denied only on `/workspace/skills/**`. `assembly.py:60` — `write_file`, `edit_file` are always-included tools. `tools/artifacts.py:21-27,114-124` — artifacts live in `/workspace/analysis` and `/workspace/out`; integrity is a SHA-256 of the payload stored next to it in the same file (`artifacts.py:134-145`). `config.py:158` — kill switch default `workspace/KILL_SWITCH`; `tools/writes.py:195-203` — presence blocks every execution. `services/engine-demo/serve_demo.py:360-372` — `GET /reports/files/{name}` serves any `rpt_|art_*.html|pdf|json` from `workspace/out` after `ArtifactBridge.validate` (path/type checks per `engine/tests/unit/test_reads_and_surfaces.py:276`). `middleware/offload.py:17` — filesystem tools are exempt from result offloading.
- Description: The model may (a) create `/workspace/KILL_SWITCH` and halt all writes until an operator removes it (no delete tool, so it cannot clear it); (b) write a `/workspace/out/rpt_x.html` that is then served to dashboard users as a "reconciled report" — the HTML renderer escapes model text (`test_renderer_escapes_model_text`) but a hand-written file bypasses the renderer entirely; (c) write a forged `performance_rows` artifact — `compare_periods` would reject it unless the model also produces a matching SHA-256 of the canonical payload, which an LLM cannot reliably do, so (c) is mostly mitigated by accident rather than by policy.
- Recommendation: Deny writes to `/workspace/analysis/**`, `/workspace/in/**`, `/workspace/out/**` and the kill-switch path; give the model a dedicated notes directory; keep the HMAC-style integrity for artifacts (sign with a host key instead of a plain hash so a forged file can never validate).

### C7-08 — Self-approval guard on the dashboard apply route is skipped for rows created via API key or MCP
- Severity: **P2**
- Classification: VERIFIED_CODE
- Evidence: `platform/apps/cloud/app/api/approvals/[id]/apply/route.ts:22-24` — guard runs only when `row.createdBy` is truthy; `platform/apps/cloud/lib/cloud/repository.ts:374-383` — `created_by = this.principal.userId ?? null`, null for API-key/MCP principals (also noted in `docs/ARCHITECTURE.md:221`). The guard is an env flag (`MARKTING_ALLOW_SELF_APPROVAL`, `lib/markting/env.ts:16`) rather than organization policy.
- Impact: A user who drives an agent through their own API key can create a pending change and then approve it themselves from the dashboard; audit attribution of the creator is lost (`api_key_id` is only on the audit event, not the pending row).
- Recommendation: Record `api_key_id`/`oauth_token_id` and the key's owner on the pending row; treat a null creator as "unknown" and require two distinct humans; move the self-approval switch into `organization_settings.policy`.

### C7-09 — Three overlapping write vocabularies with inconsistent units are exposed to AI clients
- Severity: **P3** (ambiguity/maintainability; concrete mis-unit risk mitigated by the preview)
- Classification: VERIFIED_CODE
- Evidence: Engine `propose_change.changes` is "field → value" in account currency per day (`tools/write_tools.py:30-42`, `config/write-policy.example.toml:20-27`); adport typed budgets are `daily_budget_micros` (Google `tools.ts:59`, sandbox), `daily_budget_cents` (Meta `tools.ts:347`), `budget` float units (TikTok `tools.ts:105`, Apple, Microsoft), `budget_micros` (Reddit, Snapchat, Pinterest, X, LinkedIn, Spotify); statuses `ENABLED/PAUSED`, `ACTIVE/PAUSED`, `ENABLE/DISABLE`, `Active/Paused`. `lib/markting/translate.ts:103-123` reconciles only two operations for six providers; `meta_set_campaign_status` schema takes `campaign_id` (`meta/tools.ts:335`) while the handler also accepts `object_id`/`ad_set_id` (`meta/provider.ts:479`). The generic `*_api_*` tools add a third vocabulary (raw API fields).
- Impact: An LLM choosing between `tiktok_set_budget {budget: 240}` and `tiktok_api_update {body:{budget: 240000000}}` has no schema-level unit guard; descriptions carry the unit, schemas do not. Duplicates: `tiktok_set_campaign_status` (bulk ≤20) vs `tiktok_api_update campaign/status/update`; `google_set_budget` vs `google_api_update campaignBudgets` (blocked) vs `google_api_create campaignBudgets` (allowed).
- Recommendation: Normalize to one money representation on the tool boundary (e.g. `amount` + `currency` with integer minor units) and convert inside providers; remove the typed/generic duplication for agents.

### C7-15 — Sandbox tools are named to evade the production-only MCP guard

## What a world-class system would need (concrete)

1. One agent-facing write vocabulary with integer minor units and ISO currency on every money field, typed per intent (`set_daily_budget`, `set_status`, `set_bid_ceiling`, `set_target_cpa`), and no raw-body passthrough for agents (operators keep `*_api_*` behind a flag).
2. A real human-in-the-loop gate: `pending_operation_id` accepted only from an authenticated human session distinct from the creator; MCP/REST clients can only preview. Record creator identity (user, API key, OAuth client) on the pending row.
3. Risk classification on the adport side equivalent to the engine's `classify_risk` (`tools/writes.py:77-126`): `starts_delivery`, `budget_increase`, `destructive_change`, `bulk_capable`, with policy that routes high-risk flags to mandatory human apply and maybe dual approval.
4. Account scoping as a provider wrapper for *all* tools (reads included) plus per-tool scope extractors for path/list arguments; Apple `account_id` required.
5. Read-catalog pinning and verb-based deny patterns in the engine, so a third-party MCP server cannot promote a mutation to a direct call by annotation.
6. Narrow filesystem permissions: notes-only write directory; signed (HMAC) artifact envelopes; kill switch outside the model's reach.
7. Idempotency keys and server-side `validate_only` wherever the platform offers them (Google/Meta do; the adport `execute(validateOnly)` plumbing exists but TikTok/Apple/Microsoft/Reddit cannot use it).
8. Tool telemetry: per-tool call counts, denial reasons and latency per tenant (the engine keeps an in-memory `audit` list of 500 reads, `reads.py:61-64`; adport audits only writes).
9. Missing agent tools: change history/`change_event` summaries, pacing forecast against month budget, anomaly detection as a deterministic tool, creative/ad-level reads with normalization for all 11 providers, Snapchat/TikTok/Pinterest engine fixtures and normalizers.
