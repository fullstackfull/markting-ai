# K4 — Security Lead (Final Council memo)

## How to read this
This is the authoritative security adjudication for the markting-ai audit. I (K4) re-read the cited
code for **every P0/P1 security finding myself**, re-ran the E-series consolidation (E1–E11, deliverable
`05`) against the independent red team (J1–J6), and issue the final 15-invariant table and final
severities below. Where the earlier security lead (E11/`05`) and the independent red team (J) disagree,
I resolve against code and say which side wins. I did **not** modify any file outside this memo; I ran
only read-only commands. No runtime exploitation was performed by me (no live Postgres/Supabase/Stripe
in the sandbox); where I cite VERIFIED_RUNTIME it is J2's in-process ASGI probe, attributed as such.

**Classification legend:** VERIFIED_CODE (read the code), VERIFIED_TEST (a test asserts it),
VERIFIED_RUNTIME (observed from a running process), DOCUMENTED_ONLY (claimed in docs, not confirmed in
code), INFERRED (reasoned, not directly observed), NOT_VERIFIED (open).
**Severity:** P0 security/data-loss/cross-tenant/unsafe-ad-execution present **today**; P1 production
blocker or serious financial/security risk; P2 substantial deficiency; P3 hardening/quality; GAP =
missing feature not claimed by code.

## 5. Findings K4 vouches for (final severities)

I adopt `05`'s SEC-* catalogue, with the following **changes** after independent re-read:

**Upgrades / additions:**
- **SEC-26 split and upgraded.** The null-`created_by` short-circuit (E10-06) was folded into a P3 in `05`. The four-eyes/separation-of-duties control is materially weaker than the README claims across **three verified vectors**: (a) null `created_by` skips the check for every API-key/engine-created pending (`apply/route.ts:22`); (b) the REST/MCP apply path routes through `PolicyEngine.apply`, which checks provider+hash only and never the actor, so a `tools:write` key can create **and** apply its own pending with no gate (`app/api/v1/tools/[tool]/route.ts:5-13`, `engine.ts:104`); (c) the shipped demo template sets `MARKTING_ALLOW_SELF_APPROVAL=true` (`.env.example:49`). It stays below P1 because exploitation requires an already-authorized owner/admin or a `tools:write` key (owner/admin-created) and is org-scoped — no cross-tenant or unauthorized access. The apply-within-200-cap half (E10-07) remains P3 (availability).
- **SEC-29 (NEW, P2) — cloud master secrets injected into the engine container.** `docker-compose.yml` gives both `cloud` and `engine` `env_file: .env`, so the engine process (which runs model-driven tool code in live mode) holds `SUPABASE_SECRET_KEY`, the superuser `SUPABASE_DB_URL`, `ADPORT_CLOUD_ENCRYPTION_KEY` (the vault key for every tenant's OAuth tokens), `ADPORT_API_KEY_PEPPER`, `ADPORT_MCP_OAUTH_SIGNING_KEY` and `STRIPE_SECRET_KEY` it does not need. An engine compromise becomes a full cloud compromise. VERIFIED_CODE. The E-series missed this; J2-04 found it and I confirm it.
- **SEC-30 (NEW, P3) — engine exposes unauthenticated `/docs`, `/redoc`, `/openapi.json`, `/health`, `/markting/info`** (J2-05). `/markting/info` returns mode, write-provider class, kill-switch state, approver list and account aliases with no auth. ## 6. Contradictions between agents and how I resolved them

1. **Engine reports IDOR severity — E4/E10 (P2-today) vs E1/E5/J2/J3/J5 (P1).**

   runtime probe (B downloaded A's report) settles that the cross-tenant path is real, not theoretical.
   E4/E10 were over-anchored to the demo pin. Winner: J / E1 / E5 / E11.

2. **Self-approval / four-eyes — E10-06 (P3, null-createdBy only) vs J2-03 (P2, three vectors).**
   Resolved **P2**, against code. I re-read all three vectors and confirmed the control is absent on
   the API-key/MCP apply path entirely (PolicyEngine checks no actor) and off by default in the demo
   template. E10-06 under-counted the surface; J2-03 is right that the advertised guarantee does not
   hold outside the narrow dashboard path. Winner: J2.

3. **J2-08 "demo mode mixes synthetic and real paths" vs invariant 14 "demo cannot affect production".**
   **Not a true contradiction.** Both are correct about different things: invariant 14 (no demo write
   ever reaches a real ad platform) **HOLDS** — the sandbox provider is credential-free and
   `PolicyEngine.apply` rejects a provider-mismatched pending. J2-08's valid point is operational
   hygiene: the process-wide flag interleaves sandbox and real audit/pending rows and the UI hint is
   thin. I carry J2-08 as a **P2 hygiene** finding (SEC-ADJ to J2-08) and keep inv 14 HOLDS.

4. **"Cloud master secrets in the engine container" — present in J2-04, absent from E-series.**
   No conflict; a real gap the E-series missed. Adopted as **SEC-29 (P2)**. Winner: J2.

5. **Reports-route line numbers differ between reports** (E11 cites `:17-20`; J2 cites `:35-43`).
   The *behavior* is identical and verified in the current file (GET at 16-24, no org scope); the line
   drift is a stale citation in one report, not a factual disagreement. No severity impact.
