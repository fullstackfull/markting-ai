## Findings (consolidated, deduplicated, final severities)

### I5-01 — No AI/engine usage metering; the product's dominant variable cost is uncapped on every plan
- Severity: **P1** · Classification: VERIFIED_CODE · merges I1-01, I1-02, I3-01, part of I3-05
- Evidence: `app/api/assistant/messages/route.ts`, `app/api/reports/engine/route.ts`, `repository.ts:355` (flat 120/min only), `plans.ts:11-44` (no AI dimension); `rg -niE "usage_event|meter|quota|billMeterEvent|tokens_used"` over `platform/apps/cloud` exit 0, no hits.
- Description: Every Assistant turn and report runs an LLM via the engine; the only guard is a flat, plan-independent rate limit. Free `reader` and `past_due` orgs reach the engine. No ledger exists to bill usage or detect abuse.
- Impact: Unbounded inference cost per org on every tier; margins unprotected; usage/hybrid pricing impossible.
- Recommendation: `private.usage_events` ledger written in-transaction + per-plan quota columns enforced with 402 + optional Stripe metered billing (see `_business-and-pricing-architecture.md` §2–3).

### I5-02 — Enterprise tier is unsellable: no provisioning path and advertised features unimplemented
- Severity: **P1** · Classification: VERIFIED_CODE · merges I4-01, I4-02
- Evidence: `billing.ts:39-46` (`planForPrice` omits enterprise), `:76` (rejects unmapped price); `billing/page.tsx:15,119` (excluded from PLAN_ORDER, mailto CTA); `i18n/billing.ts:58` ("SSO, regional hosting, SLA, dedicated onboarding"); `app/login/actions.ts:8` (social+password only); `config.toml:351,303,308` (region/MFA off).
- Description: Enterprise can only be granted by a manual DB write, and 4 of 5 advertised differentiators (SSO, regional hosting, SLA, dedicated onboarding) have no implementation.
- Impact: The highest-value tier cannot be closed or delivered; sold-vs-shipped contradiction.
- Recommendation: Add an enterprise provisioning path (custom price/invoice + admin console) and implement or remove each advertised capability.

### I5-03 — Pervasive upstream (Adport/Yannick) branding & legal operator identity on revenue + legal surfaces

### I5-04 — Single shared engine instance; report list/fetch unscoped by org → potential cross-tenant exposure
- Severity: **P1** (P0 if confirmed in shared-engine prod) · Classification: VERIFIED_CODE (structure) / INFERRED (leak) · from I2-04
- Evidence: `lib/markting/env.ts:10-12` (one deployment-wide URL+token); `lib/markting/engine-client.ts:127,131,134` (`runReport`/`listReports`/`fetchReportFile` carry no org scope); `app/api/reports/engine/route.ts` (calls `listReports()` directly, not demo-gated).
- Description: Reports are produced/listed from one engine shared by the whole deployment; a tenant cannot scope a report to a client, and a shared-engine deployment would let any org read others' report runs.
- Impact: Per-client reporting (core agency deliverable) impossible; cross-tenant report leak if a real engine is multi-tenant.
- Recommendation: Scope engine calls per org/client (tenant id/token) and filter `listReports`/`fetchReportFile` by caller; add a cross-tenant test. NOT_VERIFIED at runtime (no live engine).

### I5-07 — Churned customers are locked out of in-app re-subscription
- Severity: **P2** · Classification: VERIFIED_CODE · from I3-02
- Evidence: `actions.ts:19` (throws when `providerSubscriptionId` set); `billing.ts:84-85` (writes sub id on delete, never cleared); `plans.ts:64` (returns it regardless of status).
- Description: After full cancellation the dead subscription id is retained, so `startSubscription` refuses and the portal cannot resurrect a deleted subscription — no self-serve path back to paid.
- Impact: Reactivation/revenue recovery broken; support must intervene.
- Recommendation: Gate `startSubscription` on an active-ish status, or clear `provider_subscription_id` on `customer.subscription.deleted`.

### I5-08 — Webhook dedup is not atomic with its effect and has no ordering/recency guard
- Severity: **P2** · Classification: VERIFIED_CODE · merges I3-03, I3-04
- Evidence: `billing.ts:119-138` (dedup `select`, then `applySubscription` transaction, then separate `insert … on conflict do nothing`); `applySubscription:57-89` overwrites plan/status from whatever event arrives.
- Description: Concurrent retries can both pass the dedup select and reprocess; out-of-order Stripe delivery can regress entitlement state.
- Impact: Duplicate processing/audit churn; entitlement can revert to stale state.
- Recommendation: Insert the `billing_events` row inside the effect transaction (treat 0 rows as duplicate); guard updates with event recency or re-fetch authoritative subscription state.

### I5-09 — `past_due` retains full entitlement; no dunning / payment-failure downgrade
- Severity: **P2** · Classification: VERIFIED_CODE · merges I1-06, I3-05
- Evidence: `plans.ts:77` + `billing.ts:91` (`['active','trialing','past_due']` fully entitled); no `invoice.payment_failed` handler (`billing.ts:126-131`).
- Description: A failed-payment org keeps every paid (AI-cost-bearing) capability for the entire dunning window; relies entirely on Stripe eventually sending unpaid/canceled.
- Impact: Revenue leakage + uncapped cost during dunning.
- Recommendation: Define a grace window + soft-lock of write/automation on `past_due`, with an in-app banner.
