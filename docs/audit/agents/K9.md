# K9 — Red-Team Reconciliation (J1–J6 vs A–I and 01–10)

## How to read this

This document reconciles the independent red team (J1–J6, written without sight of the A–I
specialist/lead reports) against the A–I corpus (≈90 agent reports) and the ten team
deliverables `docs/audit/01..10` plus `_business-and-pricing-architecture.md`. I did **not**
take any report at face value: every claim that drives a conclusion below was re-checked
against the repository, and the spot-checks are listed. The headline result is that J found
almost nothing the far larger A–I cohort missed — J's value was *independent corroboration*
of the audit's central theses, not new ground. Four sections follow: (1) genuinely J-only
findings, (2) material findings A–I carried that J missed, (3) direct contradictions with
both sides' evidence and my resolution from code, (4) J's P0/P1 list re-adjudicated. Read
sections 1 and 3 first if you are triaging; section 4 is the bottom line on whether the red
team raised any new fire.

### Classification legend
- **VERIFIED_CODE** — I read the cited code and it says what the claim says.
- **VERIFIED_TEST / VERIFIED_RUNTIME** — confirmed by a test or a command/probe actually run.
- **DOCUMENTED_ONLY** — asserted in docs/README/phase reports; not (yet) proven in code.
- **INFERRED** — a reasoned conclusion from code structure, not directly executed.
- **NOT_VERIFIED** — I could not confirm or refute within this seat's budget/sandbox.
- Severity: **P0** security/data-loss/cross-tenant/unsafe ad execution; **P1** production
  blocker or serious financial risk; **P2** substantial functional/reliability deficiency;
  **P3** quality/polish; **GAP** a missing capability (not a defect unless the code claims it).

### Coverage note
All six J reports and all five `_results-*.json` dumps were present and parsed (J: 14 P1 / 34
P2 / 31 P3 / 5 GAP findings; **zero P0**). No agent report was missing. The A–I structured
dumps (`_results-AB/C/DE/FGHI.json`) and the ten team docs were available and searched. No
coverage gap to record on the input side.

## 3. Direct contradictions — evidence on both sides and my resolution from code

I spot-checked every contradiction below myself.

### C-1. Does a `demo_`/`mock_`/`synthetic_` tool-name refusal guard exist? (J2 vs J6/D0)
- **J2-08 / J2 disagreements:** "Existence of any upstream guard refusing `demo_/mock_/synthetic_`
  tool names was searched for and **not found**, recorded as NOT_VERIFIED." It treats the
  sandbox comment's "evade the refusal" intent as unsubstantiated.
- **J6-15 (VERIFIED_CODE) and D0-10:** the guard exists; the sandbox deliberately avoids the
  prefixes; the production connector refuses demo/mock/synthetic tools and synthetic runtimes.
- **My resolution (VERIFIED_CODE):** the guard **exists** — `platform/packages/mcp/src/index.ts:91-92`
  throws `POLICY_VIOLATION` when `productionOnly && (runtime.dataSource === 'synthetic' ||
  non-standard provider id || tool name matches /^(demo|mock|synthetic)(_|$)/)`. The sandbox
  comment at `sandbox-provider.ts:6-8` literally states the intent to avoid those prefixes.
  **So J6/D0 are right and J2 under-verified** (J2 looked but missed `packages/mcp`). **However**,
  the practical severity is J6's, not an exploit: the same connector also rejects on
  `dataSource === 'synthetic'` and on the `sandbox` provider id not being in `PROVIDER_IDS`, so
  the sandbox cannot reach the production connector *regardless* of its tool names. Resolution:
  **latent/P3, fails closed today** — the prefix-avoidance is belt-and-suspenders, not a live
  bypass. J2's "NOT_VERIFIED" should be corrected to "guard exists; sandbox blocked by provider-id
  and dataSource checks anyway."

### C-2. Is the engine reports surface P0, P1, or P2? (J2 vs J1/J3/J5 vs A–I split)
- **J2-02** rates it **P1** (VERIFIED_RUNTIME probe: caller B downloaded caller A's report).
  **J1-02/J3-03/J5-03** variously **P2/P1**. A–I is split: C4-01/D1-01/D8-01/E1-01/E5-01 **P1**;
  D4-03/D10-08/E4-01 **P2**; arch-map `04` says **P2 today / P0 if `assert_fail_closed` relaxed**.
- **My resolution (VERIFIED_CODE):** `app/api/reports/engine/route.ts:16-24` and `[name]/route.ts:10-26`
  call `sessionPrincipal(organizationId)` but then `engineClient().listReports()` /
  `fetchReportFile(name)` with **no org filter**; the engine index
  (`serve_demo.py:246-264,355-374`) carries no org key and `requested_by` is always
  `adport-bridge`. **I confirmed** the routes pass nothing through. The defect is real and lives
  in production route code. But the only report host shipped is boot-pinned to `sample`
  (`serve_demo.py:163-166,383-388`), so what crosses tenants **today** is run metadata +
  identical fixtures + a global 50-entry eviction cap — not customer data. **Resolution: P1,
  latent-P0** (matches `05-security-threat-model.md:148` SEC-01 exactly). J2's P1 is correct;
  the A–I P2 votes are "today-only" readings; the structural severity attaches to the un-isolated
  route, which nothing prevents from being wired to real data.

### C-3. Does `compare_periods` reject overlapping windows? (J6-07 vs B4-05)
- **J6-07:** overlapping current/previous windows are **accepted**.
- **B4-05:** compare_periods requires "equal-length, complete, contiguously-read windows."
- **My resolution (VERIFIED_CODE):** no contradiction — B4-05 lists the constraints that *are*
  enforced (`same_length`, window-covered-by-read, non-empty) and never claims overlap is
  rejected. `compare_periods.py:43-101` has **no** disjointness check. **J6-07 is correct and
  additive** (see K9-U2); B4-05 is simply silent on the gap. Downgraded by me to P3 for
  reachability.

### C-4. "Live mode = real accounts" (README/phase reports) vs code (all of J, all of A–I)
- **README.md:83,116 / PHASE1-REPORT.md:37-38** present `MARKTING_DEMO_MODE=false` +
  `MARKTING_ENGINE_MODE=live` as operating on real accounts.
- **Every J seat and the A–I consensus** say the engine is fixture-pinned in all modes.
- **My resolution (VERIFIED_CODE):** `serve_demo.py:383-388` — the non-demo branch is
  `base.model_copy(update={"paid_media_data_mode": "sample"})` followed by
  `assert_fail_closed(resolved)` which *requires* `sample`; `demo_settings` also forces `sample`.
  **The README/phase reports are wrong; the code is right.** "Live" changes only the model, not
  the data. This is not a disagreement among auditors — it is a documented-vs-code contradiction,
  and the code wins. (This is the audit's most-corroborated finding; see §4.)

### C-5. "Requester cannot approve" four-eyes claim (README/PHASE1 vs code)
- **README.md:79 / PHASE1-REPORT.md:16** claim a human on the Approvals page approves and
  requester ≠ approver.
- **My resolution (VERIFIED_CODE):** `apply/route.ts:22` —
  `if (row.createdBy && row.createdBy === principal.userId && MARKTING_ALLOW_SELF_APPROVAL !== 'true')`.
  The guard is skipped when `createdBy` is null (every API-key/MCP-created row), is off by
  default because `.env.example:49` ships `MARKTING_ALLOW_SELF_APPROVAL=true`, and exists only on
  the dashboard route (not `/api/v1` or `/mcp`). **J2-03 is right on all three bypasses; A–I
  corroborates (C7-08, D4-05, C13-03).** A mitigating layer J2 did not mention: the same route
  also blocks `viewer`/`member` roles, so the bypass needs an owner/admin-scoped key. Net: the
  doc claim is false as written; the control is real only on one path with the flag off.

**No contradiction survived as unresolved** — every one resolves cleanly from code. The only
residual "disagreement" is severity framing on the reports surface (C-2), and the project's own
security threat model already converged with my resolution (P1 / latent-P0).
