# J3 — Independent senior media buyer skeptic

Question I set out to answer: **would I hand this system a 200k SAR/month Saudi/Gulf account?** Answer: **no, not today**, and not because of the write gate (which is genuinely strong) but because the "AI media buyer" never looks at the tenant's money. Everything the Assistant and the engine reports say is computed over three fictitious US accounts in USD. The approval gate is real; what flows into it is theater.

Rules followed: code is the source of truth; every conclusion carries `path:line` or a command + exit code and a classification tag (VERIFIED_CODE / VERIFIED_TEST / VERIFIED_RUNTIME / DOCUMENTED_ONLY / INFERRED / NOT_VERIFIED). I did not read `docs/audit/**` (other agents) and I read `docs/PHASE*-REPORT.md` and `README.md` only after forming conclusions from code. Nothing outside this file was written; probe scripts live in the session scratchpad.

## Findings

### J3-01 — The engine never analyses the tenant's accounts; "live" mode is an LLM over US fixtures
- Severity: **P1** · Classification: VERIFIED_CODE + VERIFIED_RUNTIME · Capability: **MOCK_ONLY** (README claim: DOCUMENTED_NOT_IMPLEMENTED)
- Evidence: `services/engine-demo/serve_demo.py:163-166` (`assert_fail_closed` refuses to start unless `paid_media_data_mode == "sample"`), `:142-143` (refuses any `PIPEBOARD_API_TOKEN`), `:383-388` (live mode is `base.model_copy(update={"paid_media_data_mode": "sample"})`), `:271-280` (reports read `runtime.profile.accounts`, i.e. `engine/config/accounts.example.toml:5-19`: `fixture-google-0001`, `fixture-meta-0001`, `fixture-reddit-0001`, all `USD`, `America/New_York`); `engine/src/paid_media_agent/fixtures/data/{google_ads,meta_ads,reddit_ads}.json` (`currency: "USD"`, campaign names "Brand Search - US" etc.); runtime probe: `POST /reports/run` → `summary.platforms[].account_ref == ['demo-google','demo-meta','demo-reddit']`, `requested_by: 'adport-bridge'` for every tenant. There is no code path that feeds adport-connected accounts (Snap/TikTok/Google/Meta credentials held by adport) to the engine; the engine's only live data source is the third-party Pipeboard MCP (`engine/src/paid_media_agent/config.py:139-147`), which the host blocks.
- Description: in both `MARKTING_ENGINE_MODE=demo` and `live`, the Assistant and the "AI analysis reports" compute over synthetic data that has nothing to do with the signed-in organisation. In live mode a real model will reason fluently about the same three fake accounts.
- Impact: a buyer asking "what needs attention this week?" about a 200k SAR Snap/TikTok account receives a confident analysis of fictional US Google/Meta/Reddit campaigns. This is the single most important fact about the product and it is not visible on the live-mode Assistant page (only the demo-mode callout mentions fixtures, `platform/apps/cloud/lib/i18n/messages/assistant.ts:7,33`).
- Recommendation: either (a) build an adport→engine read provider (the engine's `ReadDispatcher`/provider protocol is the natural seam) so the engine reads the tenant's normalized reports through adport, or (b) stop calling it analysis of "connected accounts" anywhere until (a) exists, and put a permanent "synthetic data" banner on live mode too.

### J3-02 — In non-demo mode no engine proposal can ever reach a real account: the alias map has no writer
- Severity: **P1** (production blocker for the headline flow) · Classification: VERIFIED_CODE
- Evidence: `platform/apps/cloud/lib/markting/translate.ts:133-134` (unknown `account_ref` → `unsupported`), `repository.ts:40-50` (`loadAliasMap` merges sandbox aliases only when `demoMode`), `repository.ts:52-58` (`upsertAlias` exists) but `grep -rn upsertAlias platform/apps/cloud` finds callers only in `test/markting-repository.database.test.ts:47`; `infra/seed/seed-demo.mjs:50-62` inserts only the four `sandbox` aliases. No page, route or CLI lets an admin bind an engine alias to a real provider/account.
- Impact: with `MARKTING_DEMO_MODE=false` ("real accounts connected through OAuth", `README.md:134`), every proposal ends as "Proposal could not be mapped to an account". Operating the advertised flow on a real account requires hand-written SQL into `markting_account_aliases`, with no validation that the account belongs to the organisation's connections.
- Recommendation: an admin UI/route that derives aliases from `connections`/selected accounts (one alias per connected account, org-scoped, validated), or generate aliases automatically at connection time.

### J3-03 — Engine report list and files are a single global index shared by every organisation
- Severity: **P1** now (fixture data only), **P0 the day real data flows** · Classification: VERIFIED_CODE
- Evidence: `services/engine-demo/serve_demo.py:246-264` (one `workspace/out/markting-reports.json` index, no org key), `:355-358` (`GET /reports` returns the whole index to any valid bearer), `:360-374` (`GET /reports/files/{name}` serves any `rpt_*`/`art_*` file); `platform/apps/cloud/app/api/reports/engine/route.ts:16-24` (any signed-in principal of any org lists them), `app/api/reports/engine/[name]/route.ts:10-26` (any signed-in principal downloads any file; `organizationId` is used only to resolve the session). All runs carry `requested_by: "adport-bridge"` (runtime probe), so provenance cannot be reconstructed.
- Impact: org B sees and downloads org A's report runs. Today they are identical synthetic reports, so no real information leaks; the README's isolation statement (`README.md:136`: "tenant isolation of conversations lives in adport's `markting_threads`") is silent about reports, which have none.
- Recommendation: key the index and file names by organisation (or pass an org tag the host enforces), and filter on the adport side as well.

### J3-04 — The offline demo model keeps global mutable state across threads and tenants
- Severity: **P2** (demo reliability and misleading output) · Classification: VERIFIED_RUNTIME
- Evidence: `services/engine-demo/serve_demo.py:92-115` (`seen_human_messages`, `call_count`, `steps` are instance fields of one model shared by the whole graph; the script restarts only when the *count* of human messages differs from the last call). Probe 2 on one app: tenant A thread, 1 message → full analysis; tenant B thread, 1 message → "This is the offline demo engine… Script exhausted" text; tenant B's next read-only question ("Which campaign had the largest increase in CPA?") → `interrupted: True`, proposal `google_ads__update_campaign_budget g-103 → 240`.
- Impact: in a shared demo (sales team, several evaluators) answers depend on what other users did; a read-only question can produce a pending operation on the Approvals page. Host tests pass because each test builds a fresh app (`test_demo_api.py:56-60`).
- Recommendation: key the script position by `thread_id` (available in `config["configurable"]`), or hold state in the graph state rather than the model object.

### J3-05 — The demo "proposal" is a keyword trigger that always cuts the same Google campaign to 240
- Severity: **P2** · Classification: VERIFIED_CODE + VERIFIED_RUNTIME · Capability: **MOCK_ONLY**
- Evidence: `serve_demo.py:63-66` (`WRITE_INTENT` regex: `budget|ميزاني|reduce|lower|increase|raise|pause|أوقف|خف[ضّ]|قل[لّ]|ارفع|زد|غي[رّ]|change`), `engine/src/paid_media_agent/testing/demo_script.py:158-170` (`_propose` is hard-coded: `demo-google`, `google_ads__update_campaign_budget`, `g-103`, `daily_budget: 240`). Probe 1: Arabic read-only question "ما هي الميزانية الحالية لحملة سناب شات رمضان؟" (what is the current budget of the Snapchat Ramadan campaign?) → proposal to cut Google PMax to 240; "ارفع الميزانية اليومية لحملة Ramadan Awareness - KSA على سناب شات إلى 1000 ريال" (raise the Snap Ramadan campaign to 1000 SAR) → in a fresh app, the same cut-Google-to-240 proposal. The bridge then creates a real `pending_operations` row (`lib/markting/bridge.ts:76-95`) that an admin can apply.
- Misconfiguration hazard: nothing ties engine mode to adport demo mode. `lib/markting/assistant.ts:30-75` never reads `/markting/info`; `.env.example:47-51` ships `MARKTING_ENGINE_MODE=demo` independently of `MARKTING_DEMO_MODE`. An operator who sets `MARKTING_DEMO_MODE=false`, seeds a real `demo-google` alias (J3-02) and leaves the engine in demo mode gets a pending "cut this real campaign to 240 account-currency units" on every budget-related question. Human approval and the 25 % cap still stand (`core/src/policy/engine.ts:133-153`), so this is not unsafe execution, but it is a trap.
- Recommendation: label the card "scripted demo proposal" in both languages, make the bridge refuse to preview when `/markting/info.mode == "demo"` and `MARKTING_DEMO_MODE != true`, and never let a question without an explicit change verb reach the write script.

### J3-06 — Budget-delta cap is skipped when the target has no current budget (Snapchat campaign-level caps)
- Severity: **P2** · Classification: VERIFIED_CODE (cap skip) + INFERRED (Snap practice)
- Evidence: `platform/packages/core/src/policy/engine.ts:143` (`if (pctCap !== null && delta.fromMicros !== undefined && delta.fromMicros > 0)`); `platform/packages/snapchat/src/schemas.ts:17` (`daily_budget_micro` optional on a campaign), `provider.ts:124-129` (`fromMicros` set only when the campaign already has the field; otherwise the patch is `add`); `policy.ts:15` (`max_daily_budget_micros` default `null`). In Snap Ads Manager budgets normally live on ad squads and campaign-level `daily_budget_micro` is an optional cap (INFERRED from Snap product knowledge, not verified against the live API here).
- Impact: a proposal that *adds* a campaign-level daily cap to a Snap campaign that had none passes with no percentage check and (by default) no absolute check; the cap then throttles every ad squad under it. For a Ramadan campaign that is exactly the kind of change you do not want slipping through on a 15-minute TTL.
- Recommendation: treat "no baseline" as a policy violation unless an absolute cap is configured; surface the delta in account currency on the Approvals page.

### J3-07 — Currency is never part of the decision: proposals, caps and previews are unit-less numbers
- Severity: **P2** · Classification: VERIFIED_CODE (INFERRED for the KWD/BHD/OMR point)
- Evidence: engine proposals carry `unit: "account currency per day"` (`engine/config/write-policy.example.toml:23`; `test_demo_api.py:120-122`); `lib/markting/translate.ts:147-153` converts `after.value` straight to micros and ignores `unit`; `translate.ts:52-53` documents alias `currency` as "used for the human preview only"; `core/src/policy/policy.ts:13-15` caps have no currency; `components/ui.tsx:66` formats spend with no currency; `app/dashboard/reports/page.tsx:40-44` shows spend/ROAS without the row's `currency` even though `ReportRow.currency` exists (`core/src/model.ts:41-42`); `translate.ts:107` Meta budgets as `Math.round(micros / 10_000)` cents, i.e. a hard-coded 100 minor-unit offset (fine for SAR/AED; Kuwait, Bahrain and Oman use 3 decimals — INFERRED, Meta's offset handling not verified here).
- Impact: a live model that says "240" meaning USD on a SAR account becomes 240 SAR; an organisation with SAR and USD accounts cannot express a meaningful `max_daily_budget_micros`; the campaign table mixes currencies in one column.
- Recommendation: carry currency on every budget delta, compare against the account currency from the alias/connection, and show money as money.
