# K1 — Head of Paid Media (Final Council memo)

## How to read this

This is the paid-media council seat's final ruling. It takes the eleven-channel capability matrix
(`docs/audit/09-media-buyer-capability-matrix.md`), the executive gap analysis
(`docs/audit/01-media-buying-gap-analysis.md`), the channel/cross-cutting specialists (A1–A16) and the
six independent lead skeptics (J1–J6) as **claims to verify, not facts**. I re-opened code for 23
matrix cells / load-bearing citations before relying on them; every citation below is `path:line`
relative to `/home/user/markting-ai` and tagged. I rule on one product question — *is this a dashboard
with an AI chat layer, or an intelligent media-buying OS?* — from capabilities alone, correct the matrix
where code disagrees, and list the ten gaps that matter most. I did not modify any file outside this one.

**Classification legend:** VERIFIED_CODE (I re-read the code) · VERIFIED_TEST (a test proves it) ·
VERIFIED_RUNTIME (a command was actually run) · DOCUMENTED_ONLY (claimed in docs, not found in code) ·
INFERRED (reasoned, not directly observed) · NOT_VERIFIED (could not confirm).
**Severity:** P0 security/data-loss/cross-tenant/unsafe-execution · P1 production blocker / serious
financial risk · P2 substantial functional deficiency · P3 polish · GAP missing capability the product
*claims* (a mere absent feature is a GAP, not a defect).

## Verdicts

### Verdict 1 — Can the platform act as a media buyer today? **No.**

It can **look** (reporting), with care, on a subset of channels; it cannot **buy**, **diagnose**, or
**reason about the business**. The matrix headline is correct: **no cell is FULL.** The ceiling is
READ_ONLY reporting (a fixed 10-metric, campaign-grain, last-touch, platform-attributed vocabulary) plus a
narrow, policy-gated budget/status **write** surface. Everything a senior buyer calls analysis
(breakdowns, audience, placement, creative, fatigue, pacing-to-action, forecasting, allocation) and
everything that makes a *business* buyer (store revenue, profit, MER, CAC, LTV) is PARTIAL or MISSING
across all eleven channels. I concur with and vouch for the matrix on this.

### Verdict 2 — "Dashboard with an AI chat layer" OR "intelligent media-buying OS"? **Decisively the former — and even less than it appears.**

From capabilities alone, this is **a well-guarded approval-and-reporting dashboard with a chat layer whose
"AI" never observes the customer's accounts.** The disqualifying facts, all VERIFIED_CODE:

- **The brain is blind to the tenant.** The engine host refuses to boot unless its data mode is `sample`,
  and "live" mode only swaps the scripted model for a real LLM while forcing the same synthetic US fixtures
  (`serve_demo.py:163-166,386`). There is no read path from adport's per-tenant credential vault into the
  engine; its only non-fixture source is the third-party Pipeboard MCP, which the host also refuses
  (`:143`). So every analysis, comparison, and proposal the "AI media buyer" produces is computed over three
  shipped JSON files and `engine/config/accounts.example.toml` (USD, America/New_York) — not the customer's
  Meta/Google/Snap/TikTok accounts. An intelligent OS, at minimum, reasons over the operator's own data.
- **The default "AI" is a regex.** In the shipped demo mode the intent router is `WRITE_INTENT`
  (`serve_demo.py:63-66`) and the "proposal" is a hard-coded `g-103 → 240` cut (`demo_script.py:158-170`),
  regardless of the question asked.
- **No decision engine exists.** Grep for `reallocat|allocat|portfolio|marginal|diminishing|saturation|
  scale` over `engine/src`, `platform/apps/cloud/lib`, `platform/packages/core/src`, `services` returns
  nothing (A15-06, which I re-ran the intent of and confirm against the code structure). Scaling judgment
  lives as prose for the LLM; the one demo number is user-dictated.
- **No memory.** No recommendation store, no outcome store, no learning loop (matrix fns 18–20). An OS
  improves from its own history; this does not.

What *is* genuinely strong — and keeps this from being vaporware — is the **safety layer**: the two-step
validate→apply gate, hash-bound pending operations, protected accounts, account-scoping, append-only audit,
and forced-paused creation (`platform/packages/core/src/policy/engine.ts`). That is real engineering. But a
strong gate protects *execution*; it does not make the thing flowing into it *intelligent*. The gate guards a
dashboard; it does not constitute an OS.

**Ruling: Dashboard + AI chat layer + strong safety gate over a reporting/remote-control layer. Not an
intelligent media-buying OS.**

### Verdict 3 — Matrix corrections (capability vs. live reach)

The matrix is accurate about **code capability** but, on four row-groups, it over-credits **live reach**
because it does not separate the two data planes:

- **adport registry tools** (`report`, `audit_run`) run on the tenant's **real** connected accounts. The
  `Metrics`, `ROAS`, `CPA` READ_ONLY cells and the `Anomaly detection` PARTIAL cells are correctly scored
  for live data. (The anomaly cells deserve a footnote that *nothing auto-invokes them*.)
- **engine** features (`Budget analysis`, `Budget pacing`, `Historical learning`/`compare_periods`, and the
  cross-platform blended `ROAS`) run **only on synthetic fixtures** in the shipped product. Per the matrix's
  own legend (MOCK = "only present in fixtures/demo data; no live path"), these cells are effectively **MOCK
  for the tenant's real accounts**, not PARTIAL. A16 applied this discipline to `Conversion lag` (correctly
  MOCK) but not to the budget/pacing/comparison rows. This is a **correction, not a contradiction** — the
  underlying code exists exactly as cited; it simply never touches real data. Net effect: the matrix is, if
  anything, slightly *generous*; my verdict is unchanged and strengthened.

All other cells I spot-checked (18 of them) are scored correctly.

## Top 10 product gaps (priority order)

1. **No data path from the tenant's accounts to the AI engine** (K1-01). Everything else is downstream of
   this. Until the engine reads real rows, the "AI media buyer" analyses fiction. Fix: an adport-backed
   `ReadProvider` + org-scoped alias catalog feeding the engine's existing normalization.
2. **No business-truth / economics layer** (K1-02). Read-only Salla/Zid/Shopify/Woo + CRM feeding revenue
   (gross/net ex-VAT/refunds), COGS/margin, new-vs-returning, joined to spend → optimize MER/CAC/contribution
   margin/profit, not platform-attributed value.
3. **Attribution integrity before any blending** (K1-03, K1-04). Stamp every row with window + conversion
   definition; refuse to sum across incompatible definitions (extend the mixed-currency discipline); stop
   coercing missing conversions to 0 at the provider layer; surface click-vs-view and incomplete windows.
4. **Decision intelligence** (K1-09). Deterministic marginal-ROAS/diminishing-returns, budget sizing,
   cross-channel allocation and forecasting — replacing today's qualitative "consider reducing budget" and the
   hard-coded demo number.
5. **Engine parity across all 11 channels** (K1-07). Fixtures + normalization + write bridge for TikTok, Snap,
   Microsoft, Pinterest, Spotify, Apple — the six Saudi-relevant channels the brain cannot currently read.
6. **Creative intelligence subsystem** (K1-11). A creative entity (format/text/media/landing URL/Arabic-RTL),
   ad-level performance with reach/frequency for fatigue, winner detection with significance — and remove the
   prompt references to tooling that does not exist.
7. **Breakdown & audience analytics as first-class, tested, normalized paths** (K1-08) — placement/geo/device/
   demographic/time — not raw passthrough that nothing consumes.
8. **A memory loop** (K1-10). Persist every recommendation, its approval decision, and its measured outcome,
   and feed that history back into future recommendations.
9. **Trustworthy headline economics** (K1-06). Request `conversion_value`, compute real blended ROAS only after
   attribution is sound, never sum spend across currencies in one tile, and stop rendering missing ratios as 0.
10. **Close the P0/P1 execution-safety defects** (K1-05 currency 100×; and the security-seat items: scope/policy
    bypasses, deletion path, apply-time cap re-check, four-eyes default-off) before any unattended automation,
    and label demo vs live honestly (K1-12).

## Contradictions between agents and how I resolved them

1. **A16 matrix (engine cells = PARTIAL, live capability) vs. J1–J6 (engine runs only on fixtures).**

   comparison/blended-ROAS code exists exactly as cited). J1–J6 measure **runtime reach on real data** (the
   engine is forced to `sample` mode). I re-opened `serve_demo.py:163-166,386` and `config.py:124-125` and
   confirm J's fact. Ruling: those engine-sourced cells are **effectively MOCK for the tenant's real
   accounts**; the matrix slightly over-credits them by labelling them PARTIAL. Not a true disagreement —
   the matrix is generous, not wrong — and the correction only strengthens the "not an OS" verdict.

2. **Is anomaly detection a live capability (matrix PARTIAL) or dead code (findings table never populated)?**
   Initially these look contradictory. *Resolution via my own read:* the audit pack **is** registered into the
   live per-tenant registry (`context.ts:51-52`, `cloud/runtime.ts:145-149`), so it is invokable on real data
   through the `audit_run` tool — PARTIAL is defensible. **But** nothing auto-runs it and the Findings page
   only reads an otherwise-empty table (`findings/page.tsx:12`). So both observations hold: capability present
   and reachable, product surface to trigger it absent. I keep PARTIAL with that footnote.

3. **A4 Snapchat metric citation (`provider.ts:197,320-335`) vs. the 172-line file.** A16 already flagged this
   as a stale-line-number citation defect; I re-opened the file (metric map at `:14/:139`, `adsquad` only as a
   breakdown key at `:15`) and confirm the **substance** (5-field purchases-only map; no ad-squad discovery)
   holds. Resolved as a citation defect, no capability change.

4. **Severity of K1-01/K1-13 — P0 or P1?** A-side underplayed the engine-blindness (it is not in the F-01..F-20
   defect table at all, only in §3.5 as a channel-coverage note); J-side treats it as the headline. *Resolution:*
   engine-blindness is a **production blocker for the core claim** but not, today, "unsafe ad execution"
   (fixture proposals cannot reach a real account — the alias map has no writer in non-demo mode, J5-02), so
   **P1**, not P0. The cross-org report leak (K1-13) is a genuine tenant-isolation defect but the leaked data is
