## Findings

### H1-01 — Cloud build context has no `.dockerignore`; a gitignored local secrets file and 577 MB of host artifacts enter the Docker build
- Severity: P2
- Classification: VERIFIED_CODE (mechanism); INFERRED (exact propagation into the final image)
- Evidence: `infra/cloud.Dockerfile:9` (`COPY . .`, context `./platform` per `docker-compose.yml:13-15`); no `platform/.dockerignore` (verified absent); `platform/apps/cloud/.env.local` present with keys `SUPABASE_SECRET_KEY`, `ADPORT_CLOUD_ENCRYPTION_KEY`, `ADPORT_API_KEY_PEPPER`, `ADPORT_MCP_OAUTH_SIGNING_KEY`; `platform/node_modules` = 577M; `.turbo/`, `supabase/`, `website/` also in context.
- Description: The cloud image copies the entire `./platform` tree with no ignore list. This (a) bakes a developer's gitignored `apps/cloud/.env.local` secrets into the build-stage layer at `/repo/apps/cloud/.env.local`; (b) `next build` auto-loads `.env.local`, so build-time env can override the intended compose runtime config and any `NEXT_PUBLIC_*` value there is inlined into the client bundle; (c) ships 577 MB of host `node_modules`/`.turbo` cache into the builder before `pnpm install --frozen-lockfile`, bloating context and risking host-arch artifacts leaking. The final image is multi-stage (only `.next/standalone` is copied), which limits but does not eliminate the risk — standalone file tracing can pick up `.env*` in the app dir, and the intermediate layer still contains the secrets if that image is ever pushed/cached.
- Impact: Secret leakage into image layers and potentially the client bundle; non-reproducible builds; large slow builds.
- Recommendation: Add `platform/.dockerignore` excluding `node_modules`, `.next`, `.turbo`, `coverage`, `.git`, `**/.env`, `**/.env.*` (keep `!**/.env.example`), `website`, `docs`, `supabase`. Confirm `.env.local` is never traced into `.next/standalone`.

### H1-02 — Engine container runs as root (no non-root user)
- Severity: P3 (P2 if this image is used in production)
- Classification: VERIFIED_CODE
- Evidence: `engine/Dockerfile:1-22` — no `USER` directive; ends `CMD ["paid-media-agent", "serve"]`. Contrast `infra/cloud.Dockerfile:22` which sets `USER node`.
- Description: The `engine` service (which runs `services/engine-demo/serve_demo.py`, writes the kill-switch file and workspace) executes as UID 0 inside the container. The cloud image correctly drops to `node`; the engine image does not drop privileges.
- Impact: A container-escape or RCE in the engine runs as root; also root-owns the `engine-workspace` named volume. Low impact in the localhost-only demo, higher in any hardened deployment.
- Recommendation: Add a dedicated non-root user in `engine/Dockerfile` (create user, `chown` `/app/workspace`, `USER`), matching the cloud image.

### H1-03 — Base images are tag-pinned, not digest-pinned
- Severity: P3
- Classification: VERIFIED_CODE
- Evidence: `infra/cloud.Dockerfile:5,14` (`node:22-bookworm-slim`), `engine/Dockerfile:2` (`python:3.13-slim`), `docker-compose.yml:67` and `engine/docker-compose.yml:28` (`postgres:16-alpine`), `engine/sandbox/Dockerfile:2`. `grep sha256` → no matches.
- Description: No image is pinned to a `@sha256:` digest, so rebuilds are not reproducible and are exposed to upstream tag mutation.
- Impact: Supply-chain drift / non-reproducible builds; acceptable for a demo, a gap for production.
- Recommendation: Pin to digests (or at least patch tags) and refresh via a controlled process.

### H1-04 — Whole root `.env` is injected into the engine container, handing it secrets it never uses
- Severity: P3 (blast-radius; P2 in production)
- Classification: VERIFIED_CODE
- Evidence: `docker-compose.yml:40` (`env_file: .env` on `engine`). Rendered `docker compose config` shows the `engine` service receiving `SUPABASE_SECRET_KEY`, `STRIPE_SECRET_KEY`, `ADPORT_API_KEY_PEPPER`, `ADPORT_CLOUD_ENCRYPTION_KEY`, `ADPORT_MCP_OAUTH_SIGNING_KEY`, `STRIPE_*` — none of which the engine needs.
- Description: Both services load the same full `.env`. The engine only needs `DATABASE_URL`, its `PAID_MEDIA_*` and `MARKTING_ENGINE_TOKEN`, yet it is given every cloud/Stripe/Supabase secret.
- Impact: Expanded blast radius — a compromised engine container exposes cloud, billing and database secrets.
- Mitigation observed (reduces, not removes): safety-critical engine vars are hardcoded in the service `environment:` block (`PAID_MEDIA_WRITES_ENABLED: "false"`, `PAID_MEDIA_DATA_MODE: sample`, `PAID_MEDIA_API_TOKENS`), which override `env_file` (verified in rendered config), and `services/engine-demo/serve_demo.py:139-170` `assert_fail_closed()` refuses to boot if live-write/approver vars arrive. Secret scope, not write-safety, is the issue.
- Recommendation: Replace `env_file: .env` on the engine with an explicit minimal `environment:`/engine-scoped env file.

### H1-05 — Cloud image builds Next.js twice
- Severity: P3
- Classification: VERIFIED_CODE
- Evidence: `infra/cloud.Dockerfile:10-12` runs `pnpm build` then `pnpm --filter @adport/cloud build:standalone`; `platform/apps/cloud/package.json` defines `build:standalone` as `next build && node scripts/prepare-standalone.mjs`. `pnpm build` (turbo) already builds the cloud app, so `next build` runs a second time.
- Description: Redundant full Next build inflates build time.
- Impact: Slower, more expensive builds; no correctness defect (the standalone recipe is otherwise correct — `prepare-standalone.mjs` nests the server at `.next/standalone/apps/cloud/server.js`, matching the Dockerfile's `CMD ["node","apps/cloud/server.js"]` and the extra static/public COPYs).
- Recommendation: Build workspace deps only (`turbo run build --filter=...^`) then a single standalone build, or drop the first `pnpm build`.

### H1-06 — No reverse proxy / TLS in front of the cloud app
- Severity: P2 (production GAP)
- Classification: VERIFIED_CODE / GAP
- Evidence: `docker-compose.yml:28-29` publishes `127.0.0.1:3000:3000` plain HTTP; no nginx/traefik/caddy service anywhere in the stack.
- Description: The stack is localhost HTTP only. Correct and deliberate for a local demo (README/compose say so), but there is no TLS-terminating proxy, HSTS, or edge for any non-local deployment.
- Impact: Not production-deployable as-is; secure cookies / OAuth redirect flows that assume HTTPS will not work behind nothing.
- Recommendation: Document (or add) a TLS reverse proxy for any shared/production deployment; this is out of scope for the demo stack but must not be mistaken for production-ready.

### H1-07 — The primary application database (Supabase) is outside compose; the stack cannot stand up on its own
- Severity: P2 (production GAP)
- Classification: VERIFIED_CODE / GAP
- Evidence: `docker-compose.yml:1-5,23-27` (Supabase deliberately excluded; reached via `host.docker.internal`), `Makefile:25-34` (`supabase start` via CLI before `docker compose up`), `docker-compose.yml:30-32` (`cloud` `depends_on` only `engine`, not any DB readiness).
- Description: `docker compose up` alone does not produce a working system — Supabase must be started separately via the Supabase CLI on the host, and the cloud service has no dependency/healthcheck tying it to Supabase readiness, so it can boot before migrations are applied.
- Impact: Orchestration is split across two tools; no single-command reproducible environment; cloud can start against an unmigrated/absent DB. The rationale (adport migrations need `auth.users`, `pg_cron`, `adport_backend` role) is legitimate, but the result is a non-self-contained stack.
- Recommendation: For production, run a managed Supabase/Postgres with health gating; document that compose alone is not the full stack.

### H1-08 — No healthcheck for the cloud service
- Severity: P3
- Classification: VERIFIED_CODE
- Evidence: `docker-compose.yml` defines healthchecks only for `engine` (`:56`) and `engine-db` (`:73`); `infra/cloud.Dockerfile` has no `HEALTHCHECK`.
- Description: Nothing verifies the cloud app is actually serving; `restart: unless-stopped` will not restart a hung-but-alive process, and no dependent waits on cloud health.
- Impact: Silent cloud failures go undetected by the orchestrator.
- Recommendation: Add a cloud healthcheck (e.g. hit a Next route / `/api/health`).

### H1-09 — Engine image HEALTHCHECK lacks start-period/interval tuning; no `start_period` at compose level either
- Severity: P3
- Classification: VERIFIED_CODE
- Evidence: `engine/Dockerfile:21` (`HEALTHCHECK CMD ...` with no `--start-period`/`--interval`); `docker-compose.yml:56-60` overrides with `interval 10s / timeout 5s / retries 12` and no `start_period`.
- Description: Engine boot does Postgres checkpointer setup and model/graph assembly; with no start_period the first checks count toward failure. 12×10s retries (~120s) is a generous buffer, so flapping is unlikely, but a `start_period` would be more correct.
- Impact: Minor; possible early unhealthy flaps before readiness.
- Recommendation: Add `start_period` (e.g. 20–30s).

### H1-10 — Committed `__pycache__/*.pyc` under the bind-mounted demo service
- Severity: P3 (hygiene; not a container defect)
- Classification: VERIFIED_CODE
- Evidence: `git ls-files services/engine-demo` lists `__pycache__/serve_demo.cpython-311.pyc` and `tests/__pycache__/...cpython-311...pyc`; `docker-compose.yml:53` bind-mounts `./services/engine-demo:/opt/markting:ro`.
- Description: Stale `cpython-311` bytecode is tracked and mounted (read-only) into a `python:3.13` container. It is unused (version mismatch → ignored) and read-only, so harmless at runtime, but it is committed build residue.
- Impact: None at runtime; repository hygiene only.
- Recommendation: Gitignore `__pycache__/` and `.pytest_cache/` under `services/`.

## What a world-class system would need (gaps, concrete)
- `platform/.dockerignore` (and an engine context already covered by `engine/.dockerignore`) so secrets and `node_modules` never enter the build.
- Non-root user in the engine image; read-only root filesystem + `cap_drop: [ALL]` + `no-new-privileges` security options on both services.
- Digest-pinned base images with an automated bump/scan (Trivy/Grype) pipeline.
- Per-service minimal secret injection (Docker/Compose secrets or scoped env files), not one shared `.env`.
- A cloud healthcheck and a `start_period` on engine; cloud `depends_on` a real DB readiness gate.
- A TLS-terminating reverse proxy (traefik/caddy/nginx) for any non-local deployment; managed Supabase/Postgres with migrations gated before cloud starts.
- Single reproducible build (no double Next build) and a committed image/SBOM.
- Resource limits (`mem_limit`/`cpus`/`pids_limit`) — none are set on any service.

## Disagreements / claims in docs that the code contradicts
- `docker-compose.yml:35` comments the engine image is "Upstream image, unchanged." That is accurate for the *image build* (`engine/Dockerfile` is upstream-style), but the running behavior is **not** upstream: the compose `command` replaces the default `paid-media-agent serve` with `services/engine-demo/serve_demo.py`, which swaps in `ProposalOnlyWriteProvider` and engages the kill switch (`serve_demo.py:69-81,173-180`). The safety does not come from the image; it comes from the compose command + env overrides. A reader trusting "unchanged" could wrongly assume the stock image is itself proposal-only — it is not.
- `.env.example:1` / Makefile imply `make env` → `make up` yields a complete stack, but `docker compose up` without the Supabase CLI step is not a working system (H1-07); and `docker compose` alone fails without a root `.env` even for `config` (verified exit 1).
- No doc claims TLS/reverse-proxy or non-root engine; these are GAPs, not contradicted claims.
