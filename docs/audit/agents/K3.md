# K3 — Principal Architect (Final Council memo)

## How to read this

This is the architecture council seat's final ruling. It takes the system architecture map
(`docs/audit/04-system-architecture-map.md`, authored by D11), the eleven D-cohort subsystem reports
(D0–D10), the D11 synthesis, and the SRE/production cluster (H1–H7 via `08`) as **claims to verify,
not facts**. I re-opened code and re-walked every Mermaid diagram in `04` against the repository at
`git HEAD` before relying on it — 27 edge/citation spot-checks, listed below. I rule on one question
per my seat: *is the architecture sound, and what must be decided in Phase 0 before anything else is
built?* Every load-bearing statement carries a `path:line` citation (relative to
`/home/user/markting-ai`) or a command, plus a classification tag. I wrote no file outside this one.

**Classification legend:** VERIFIED_CODE (I read the cited code and it says what is claimed) ·
VERIFIED_TEST (a test asserts it) · VERIFIED_RUNTIME (a command was run and observed) ·
DOCUMENTED_ONLY (claimed in a doc, not confirmed in code) · INFERRED (reasoned, not directly
observed) · NOT_VERIFIED (could not confirm). **Severity:** P0 (security / data loss / cross-tenant /
unsafe ad execution) · P1 (production blocker / serious financial risk) · P2 (substantial functional
or reliability deficiency) · P3 (quality / polish) · GAP (missing capability the product *claims*; a
mere absent feature is a GAP, not a defect).

## Verdicts

- **The map (`04`) is structurally accurate and I endorse it** as the authoritative architecture
  document, with two amendments below (K3-03 on the write-path invariant framing; the `SandboxProvider`
  "near-line-for-line" wording). Its component/flow/ER/topology diagrams, its five duplicated-
  responsibility rows, its coupling list, its SPOF highlighting and its transaction-boundary analysis
  are VERIFIED_CODE and reproduce at HEAD.

- **The two P1s the map elevates are correct.** C1 (non-atomic/double apply) is the single most
  important cross-cutting architecture defect; C2 (engine reasons only over USD fixtures in every mode,
  yet translated proposals can route to real accounts via alias binding) is the correct framing of the
  "AI media buyer" contradiction. I vouch for both.

- **One material amendment (K3-03):** the map's §12 positive finding — *"the single-write-path invariant
  is structurally present and fail-closed"* — is **true for the engine/bridge/Assistant path but
  overstated for adport's own surfaces.** The REST `/api/v1/tools/[tool]` and MCP `/mcp` surfaces apply
  a previewed write on the second call with **scope enforcement only and no requester≠approver / human
  approver** (`app/api/v1/tools/[tool]/route.ts:5-13`; the four-eyes check exists **only** in
  `app/api/approvals/[id]/apply/route.ts:21-24`). This is the K2/C13/C14/J2 finding, and it is an
  architecture-level separation-of-duties gap, not merely an API-surface detail. The map notes it in
  passing (§2 sequence "REST/MCP skip the last", §7 self-approval row) but its positive-findings section
  reads as broader reassurance than the code supports. I resolve this in favour of K2: the invariant is
  **conditional**, holding on the human dashboard path and broken on the machine (API-key) path.

- **Duplicated responsibilities:** real but almost entirely P3 (maintainability/drift). The one that
  intersects a P1 is the pending-row-location duplication, because `listPendingOperations(org,200).find`
  is both a correctness bug (false 404 past 200) and the wrong seam for the atomic claim that C1 needs.

- **Coupling:** the engine host's binding to private/test-only upstream symbols + re-implemented runtime
  + KILL_SWITCH-into-the-tree is a genuine architectural hazard (P2): "engine unmodified" is true for
  tracked files but the coupling is as tight as a patch, with no drift check and no root CI to catch an
  upstream refactor (Python → no compile-time signal).

- **SPOFs:** the engine (one process, one identity, per-process mutable scripted-model state, one global
  `asyncio.Lock`, single-file report index, sync WeasyPrint on the loop) and out-of-band, reset-on-every-
  `make up` Supabase. Both HELD. The engine cannot be horizontally scaled without externalising state and
  giving each tenant its own caller identity.

- **Scaling:** chat is a minutes-long synchronous HTTP call with no queue/stream/idempotency/cancellation,
  behind a `maxDuration=300` that is a no-op on the Node standalone server. It fails behind any LB with a
  60–120s idle timeout. No per-thread serialisation on either side. These are correct and consequential.

- **Migration risk:** the two-database split-brain (no cross-DB transaction, no FK, destructive
  `db reset` on `make up`), the engine's absent migration mechanism, and the machine-uncheckable
  `UPSTREAM.md` register (the planned `check-upstream-edits.sh` does not exist) are all HELD.

## Phase 0 architecture decisions (what everything else depends on)

1. **Make apply atomic and transactional before any live ad write.** Adopt the engine's own
   `UPDATE … WHERE consumed_at IS NULL RETURNING` single-claim pattern on `pending_operations`, and wrap
   provider-write + audit + consume behind one idempotent step with an outbox. This is the seam at
   `apply/route.ts:20` / `engine.ts:88-124` and it blocks K3-01 and the C7 hand-off saga.
2. **Enforce requester≠approver on *all* write-apply surfaces, including REST/MCP** — or explicitly
   disable machine-key write-apply until four-eyes is enforced. Do not ship the dashboard-only guard as
   if it were the system invariant (K3-03).
3. **Decide the engine's multi-tenant model before a second replica or live mode:** per-tenant caller
   identity (not one `:adport-bridge` token), per-thread serialisation, and an externalised report
   store + cluster-wide kill switch. Until then the engine is single-replica-only and must stay
   fixture-only/fail-closed (K3-04/K3-08/K3-09).
4. **Resolve the two-database split-brain:** either collapse to one system of record or define a real
   cross-DB saga with reconciliation; stop `supabase db reset` on anything but local dev; add a
   forward-only migration path (advisory lock) for **both** databases (K3-06/K3-11).
5. **Stand up root CI + an upstream-edit drift check** before trusting "engine unmodified"; the private-
   symbol coupling has no compile-time guard in Python (K3-07).
6. **Keep the fixture-only, fail-closed posture as the default** and gate alias-binding-to-real-accounts
   behind explicit review, so a fixture-derived proposal cannot reach a live account unreviewed (K3-02).
7. **Introduce the event/outbox backbone** (K3-G1) as the substrate for async chat, report jobs,
   expiry, retention and outcome measurement — the one missing primitive the rest of the roadmap needs.
