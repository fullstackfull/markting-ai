# A2 — Google Ads / Performance Max expert

Audit date: 2026-10-02. Repository: `/home/user/markting-ai` (adport vendored at `platform/`, paid-media-agent vendored at `engine/`). All paths below are relative to the repository root. Nothing other than this file was created or modified.

Framing: I audited whether MARKTING-AI can *understand and manage Google Ads like an expert media buyer*, not merely whether a connector exists. The short answer: there is a competent, well-gated, thin REST connector (`platform/packages/google`) with a generic GAQL read tool and 14 guarded write tools, but the normalized model exposes only 10 metrics with no segments, the AI engine (`engine/`) has no Google-specific reader beyond Pipeboard MCP or a 3-campaign fixture, and almost all "expert" surfaces (search terms, negatives, quality signals, impression share, asset groups, recommendations, conversion actions, attribution) exist only if the LLM hand-writes GAQL.

## Findings

### A2-01 — Google reports are silently truncated and then labelled `complete: true`
- Severity: **P2** · Classification: **VERIFIED_RUNTIME**
- Evidence: `platform/packages/google/src/client.ts:131-146` (loop stops when `rows.length >= maxRows`, then `rows.slice(0, maxRows)`); `platform/packages/google/src/provider.ts:176-181` (`search(accountId, gaql, { maxRows: query.limit ?? 1000 })`, returns `{ rows }` with no `truncated`); `platform/packages/core/src/tools/builtin.ts:116,136-138` (`truncated = providerTruncated || rows.length > input.limit`; `summarizeReport(returnedRows, !truncated && …)`); runtime check above.
- Description: The provider trims each account's result set to exactly `limit` rows and never sets `Report.truncated`. Core only detects truncation when a provider returns *more* than `limit` rows, so a Google account with more campaigns/ad groups/ads than `limit` (default 100 in `builtin.ts:64`) yields a report whose totals omit entities while `summary.complete` is `true`. The GAQL has no `ORDER BY`, so which entities are dropped is arbitrary.
- Impact: An AI media buyer reading `summary.groups` will quote wrong spend/conversions as complete for any mid-size account (agencies routinely have >100 ad groups). Ad-level reports (`level: 'ad'`) hit this almost always.
- Recommendation: Request `maxRows: limit + 1` (or track `nextPageToken`/row overflow) and set `truncated: true`; add `ORDER BY metrics.cost_micros DESC` so truncation drops the long tail; add a test for the overflow case.

### A2-02 — `protected_accounts` policy can be bypassed for Google by formatting the customer id
- Severity: **P1** · Classification: **VERIFIED_CODE**
- Evidence: `platform/packages/core/src/policy/engine.ts:127-131` (`this.policy.protected_accounts.includes(op.accountId)` on the raw string); `platform/packages/google/src/provider.ts:266` (`normalizeCustomerId(op.accountId)` accepts `123-456-7890` and `customers/1234567890`, `client.ts:30-36`); `platform/packages/google/test/google.test.ts:184` (dashed id accepted end-to-end). The cloud account-scope wrapper strips dashes only for the *allow* check (`platform/apps/cloud/lib/cloud/account-scope.ts:13-17`), and `protected_accounts` is a real cloud setting (`platform/apps/cloud/test/database.integration.test.ts:317`, `repository.ts:51-56`).
- Description: An operator who protects `1234567890` is not protected against a write addressed to `123-456-7890` (the format Google's own UI displays and LLMs routinely emit). The static check runs before provider normalization and is never re-run on the canonical id.
- Impact: Defeats the one rail meant to make an account read-only (e.g. a client's brand account during a freeze). Same-tenant only; not cross-tenant.
- Recommendation: Canonicalize `op.accountId` per provider (reuse `canonicalAccountId`) before `checkStaticPolicy`, or have providers expose `canonicalAccountId()` and let `PolicyEngine` call it. Add a test with a dashed id.

### A2-03 — Budget rails are currency-blind and do not cap new budgets by default
- Severity: **P2** · Classification: **VERIFIED_CODE**
- Evidence: `platform/packages/core/src/policy/policy.ts:13-15` (`max_budget_delta_pct` default 25, `max_daily_budget_micros` default `null`); `engine.ts:133-153` (pct cap applies only when `fromMicros` is set); `platform/packages/google/src/provider.ts:425` (`google_create_campaign` emits `{ target, toMicros }` only) and `provider.ts:870-881` (`google_api_create campaignBudgets` likewise); `BudgetDelta.currency` exists (`core/src/provider.ts:23-30`) but the Google provider never sets it, nor `ReportRow.currency` (`provider.ts:226-231`).
- Description: (a) New campaign budgets have no "from" value, so with the default policy they are unbounded; the only backstop is `paused_creation`, and a second guarded call `google_set_campaign_status ENABLED` is not budget-checked. (b) `max_daily_budget_micros` is a single number applied identically to USD, SAR, EGP and KWD accounts — for an Arabic-first SaaS where one tenant can hold EGP and USD accounts, one cap cannot be right for both. (c) The 25 % delta cap is a per-call cap; nothing limits cumulative drift across repeated calls within a session.
- Impact: Serious-but-bounded financial risk: unlimited daily budget on a paused campaign plus one enable call; or a cap that is 50× too loose/tight depending on currency.
- Recommendation: Populate `currency` on `BudgetDelta`/`ReportRow` from `customer.currency_code` (already fetched in `listAccounts`), make caps per-currency or expressed in a reference currency with explicit FX, and give new-campaign budgets a default absolute cap.

### A2-04 — Tool descriptions and comments promise "always paused" creation that only policy delivers
- Severity: **P3** · Classification: **VERIFIED_CODE**
- Evidence: `platform/packages/google/src/tools.ts:159` ("Campaign status is forced to PAUSED") vs `provider.ts:310-317` (coerced only `if (guard.forcePausedCreation …)`); `provider.ts:636-637` comment "RSAs always start paused" vs code `guard.forcePausedCreation ? 'PAUSED' : 'ENABLED'`; `platform/docs/providers.md:22` ("Created campaigns are forced paused").
- Description: With `paused_creation: false` in an organization's policy, `google_api_create campaigns` and `google_create_responsive_search_ad` create live, spending objects while the tool text tells the model they are paused.
- Impact: Model reasoning about safety is wrong whenever an org relaxes the default; low likelihood given the default is `true`.
- Recommendation: Make the description conditional ("…forced to PAUSED when the paused_creation policy is on") and default RSAs to PAUSED regardless, as the comment claims.

### A2-05 — Engine marks every live Google row "complete" and inherits currency from config, not from the API
- Severity: **P2** · Classification: **VERIFIED_CODE**
- Evidence: `engine/src/paid_media_agent/tools/pipeboard.py:186-193` (`ProviderResult(payload=payload)` — `data_complete_through`, `currency`, `timezone` never populated for live reads); `engine/src/paid_media_agent/tools/normalize.py:141-142,156` (`is_complete = data_complete_through is None or …`, INCOMPLETE_WINDOW never raised when `None`); `reads.py:245-247` (currency/timezone fall back to the alias binding in `accounts.toml`).
- Description: Google conversions are reported with a lag (conversion-action lag, imported conversions, Smart Bidding attribution updates). The fixture provider models this (`fixtures.py:201-214,363-367`), but the live path cannot: every day, including today's partial day, is flagged complete, and the currency shown in analysis is whatever the operator typed in `accounts.toml`.
- Impact: Week-over-week and anomaly comparisons on Google will systematically report "conversion drop" on the trailing days; mis-typed alias currency silently mislabels money.
- Recommendation: Derive `data_complete_through` per platform (Google: ≥ 3 days lag for conversions; expose as config), and read `customer.currency_code`/`time_zone` via a catalog read on first use.

### A2-06 — `google_create_campaign` accepts PMax/Shopping/Video channel types but builds a Search-shaped campaign
- Severity: **P3** (defect in the claim) / **GAP** (feature) · Classification: **INFERRED** (API semantics from Google Ads knowledge; not verifiable offline)
- Evidence: `platform/packages/google/src/tools.ts:41` (`channel_type` enum includes `PERFORMANCE_MAX`, `SHOPPING`, `VIDEO`, `DISPLAY`); `provider.ts:397-421` (always `manualCpc: {}`, no `networkSettings`, no `shoppingSetting`, no geo/language criteria, no bidding appropriate for PMax); `provider.ts:505-515` (`google_create_ad_group` hard-codes `type: 'SEARCH_STANDARD'`).
- Description: Performance Max requires Maximize Conversions/Conversion Value bidding and asset groups; Shopping requires `shoppingSetting.merchantId`; Video requires CPV/CPM or target-CPM bidding. The server-side `validateOnly` call will reject these, so the failure is safe but the tool advertises capability it does not have. A plain Search create also omits `networkSettings`, so Google's defaults (Search partners and, for Search, Display Network expansion) apply — an expert never ships that.
- Impact: Model wastes turns; defaults create spend on partner/display inventory.
- Recommendation: Either narrow the enum to `SEARCH` or add per-channel payload builders (PMax: bidding + asset group tool; Shopping: merchant id; Video: bidding). Set `networkSettings.targetContentNetwork=false`, `targetSearchNetwork=true`, `targetPartnerSearchNetwork=false` explicitly, and accept geo/language targets.

### A2-07 — Date presets resolve in UTC, not the Google account time zone
- Severity: **P3** · Classification: **VERIFIED_CODE**
- Evidence: `platform/packages/core/src/model.ts:56-71` (`Date.UTC(...)`), consumed by `provider.ts:142`. `customer.time_zone` is never selected (`provider.ts:70`).
- Description: Google aggregates `segments.date` in the account's time zone. For Riyadh/Cairo/Dubai accounts (UTC+3/+2/+4), `today`/`yesterday` requested between midnight local and midnight UTC point at the wrong Google day.
- Impact: Daily pacing and "yesterday" checks are off by one day for a few hours each day; misleading for day-parting decisions.
- Recommendation: Select `customer.time_zone` in `listAccounts` and resolve presets per account.

### A2-08 — `google_gaql` returns up to 10,000 raw rows straight into model context
- Severity: **P3** · Classification: **VERIFIED_CODE**
- Evidence: `platform/packages/google/src/tools.ts:23` (`limit … max(10_000)`), `provider.ts:240-249` (no offload, no projection), handler returns `{ rows, row_count }` (`tools.ts:26-29`). Contrast the engine, which offloads rows to artifacts (`engine/src/paid_media_agent/tools/reads.py:76-97,268-281`).
- Description: Search-term and keyword reads are exactly the large reads an expert runs daily; without summarization the model either truncates or hallucinates aggregates.
- Recommendation: Add server-side aggregation options (group-by/top-N) or artifact offload with a compact summary.

### A2-09 — Apply path does not re-verify budget state or re-run budget policy
- Severity: **P3** · Classification: **VERIFIED_CODE**
- Evidence: `platform/packages/core/src/policy/engine.ts:87-125` (apply re-runs only `checkStaticPolicy`; `pending.preview` is returned but not compared); `platform/packages/google/src/provider.ts:259-263` (`applyWrite` re-plans and re-reads the campaign budget resource at apply time).
- Description: Within the 15-minute TTL the campaign's budget may have been re-pointed to a shared budget or changed by another user; the apply will mutate whatever `campaign.campaign_budget` now resolves to, without re-showing the "SHARED" warning or re-checking the delta.
- Recommendation: Compare the re-planned `budgetDeltas`/`budgetResource` with the stored preview and fail with `PENDING_MISMATCH` on drift.

### A2-10 — Manager-account error path leaks managers into reporting
- Severity: **P3** · Classification: **VERIFIED_CODE**
- Evidence: `platform/packages/google/src/provider.ts:84-86` (any error → account inserted with `status: 'UNKNOWN'`, manager flag lost); `provider.ts:146` filters on `status.includes('manager')`, a value no code path ever sets (dead filter).
- Description: If the `FROM customer` probe for an MCC fails (common: `USER_PERMISSION_DENIED` on manager without `login-customer-id`), the MCC is listed as an account and `report()` queries it; Google rejects metrics on manager accounts (`REQUESTED_METRICS_FOR_MANAGER`), failing the whole cross-provider report unless `continue_on_error` is set.
- Recommendation: Surface the probe error instead of a placeholder account, or mark the account `manager: true` so it is excluded.

### A2-11 — Developer-token removal is asserted by docs and code but cannot be verified here
- Severity: **P1 if wrong**, recorded as risk · Classification: **NOT_VERIFIED** (external API policy)
- Evidence: `platform/packages/google/src/client.ts:7-8` (`developerToken` "@deprecated Ignored"), no `developer-token` header anywhere in `client.ts:84-100`; `google.test.ts:42-66` asserts its absence; `platform/docs/providers.md:26` ("Developer tokens were retired in September 2026").
- Description: Every Google Ads API request in this repository is sent without a `developer-token` header. If Google's API still requires it on the configured `v25` endpoint, 100 % of Google calls fail with 401 `DEVELOPER_TOKEN_PARAMETER_MISSING`. I could not confirm the retirement against Google's live documentation from this sandbox.
- Recommendation: Confirm against the current Google Ads API changelog before launch; keep an opt-in header path behind a flag.

### A2-13 — The AI engine cannot read Google except through Pipeboard MCP or a 3-campaign fixture
- Severity: **GAP** · Classification: **VERIFIED_CODE**
- Evidence: `engine/src/paid_media_agent/tools/direct/__init__.py:18-36` (direct providers exist only for X and OpenAI Ads); `engine/src/paid_media_agent/config.py:140,234` (`pipeboard_google_ads_mcp_url`); `engine/src/paid_media_agent/tools/fixtures.py:62-184` (fixture catalog: `list_campaigns`, `get_campaign_performance`, `get_ad_group_performance`, `get_campaign` + denied `mutate`/`delete_campaign`/`get_legacy_insights`); `fixtures/data/google_ads.json` (3 campaigns, 28 days, campaign grain only; ad groups synthesized 60/40 at `fixtures.py:261-292`); `services/engine-demo/serve_demo.py:142-143` (demo refuses to run with `PIPEBOARD_API_TOKEN` set).

- Recommendation: Implement an adport-backed `ReadProvider` for `google_ads` (GAQL presets for keyword_view, search_term_view, asset_group, campaign with `segments.*`) so the engine's analysis skills see real Google grains.

### Writes and gating (summary)
- All 14 Google write tools are built with `guardedWriteTool` (`tools.ts:31-193`), which always routes through `ctx.engine.validate` → `provider.previewWrite` (server `validateOnly`) → policy budget check → pending id (sha256 of canonical op, 15-min TTL) → `ctx.engine.apply` with hash/expiry/provider match (`core/src/tools/write.ts:39-66`, `core/src/policy/engine.ts:58-125`). VERIFIED_CODE; the two-step gate is unconditional (`require_validation` is unused, VERIFIED_CODE).
- Generic escape hatches `google_api_create/update/remove` accept any REST mutate service name matching `/^[a-z][A-Za-z0-9]{1,80}$/` (`provider.ts:838-843`). Guards: cross-customer `customers/<id>` references rejected (`provider.ts:845-860`), budget updates redirected to the typed tool (`provider.ts:346-351`), campaignBudgets creates must carry a positive `amountMicros` (`provider.ts:870-881`). Not guarded: `google_api_update campaigns` with `update_mask: 'campaign_budget'` *is* blocked by the `/budget/i` regex, but a `google_api_create campaigns` pointing `campaignBudget` at an existing large shared budget is not budget-checked (it is paused under default policy). `customerManagerLinks`/`customerClientLinks` writes are structurally possible but blocked by the cross-customer reference check in practice (INFERRED).
- Cloud: `AccountScopedProvider` and `createAccountScopeAuthorizer` enforce the tenant's enabled account set on `account_id`/`customer_id` (`account-scope.ts:36-91`), dash-insensitive; `customers/`-prefixed ids are rejected (fail-closed). VERIFIED_CODE.
- Server-validated vs client-side: all Google previews are server-validated (`serverValidated: true`); client-side pre-validation exists for RSA limits, strategy/target compatibility, service names, cross-customer references, campaign existence (lookup). Nothing is "preview only" for Google.

## What a world-class system would need (gaps, concrete)

1. **Typed Google read presets** (not raw GAQL): campaign settings (channel, bidding type + targets, budget + shared flag, serving/primary status + reasons, networks, geo, languages, schedule), ad-group settings, keywords with QS components and match type, search terms with added/excluded state, negative lists, RSA assets with performance labels and ad strength, PMax asset groups + search themes + listing groups, conversion actions (category, counting, window, attribution model), change history, recommendations.
2. **Segments in the normalized model**: `segments.date` (daily/weekly), device, ad_network_type, geo (country/region/city), age/gender, conversion_action, hour/day-of-week — exposed through `NormalizedQuery.breakdowns`.
3. **Expert metrics**: search IS, top/abs-top IS, lost IS budget/rank, all_conversions, view-through, cost/all conv, conversion-by-conversion-date, video views/view rate, interaction rate, invalid clicks, avg CPC/CPM native.
4. **Pacing and completeness**: budget vs MTD spend with month-end projection in account time zone; conversion-lag-aware `data_complete_through` (per conversion action), currency and timezone from `customer`.
5. **Writes an expert actually makes**: campaign-level negatives and shared lists, keyword bid/URL edits, ad-group/keyword bid adjustments (device/location/schedule/audience), target tCPA/tROAS edits with current-value preview, TARGET_IMPRESSION_SHARE setup, portfolio strategies, lifetime budgets, campaign network/geo/language/schedule edits, RSA pinning and asset edits, PMax asset group CRUD, Shopping/Merchant Center wiring, ad status, labels, recommendation apply/dismiss, offline conversion upload.
6. **Currency-aware policy**: per-currency or FX-normalized budget caps, cumulative per-session drift caps, new-budget absolute caps, canonical account ids in `protected_accounts`.
7. **Engine integration**: an adport-backed Google `ReadProvider` so the AI engine analyses real keyword/search-term/asset-group grains; Google-specific wiki (brand vs non-brand, match types, QS, IS, PMax cannibalization, Smart Bidding learning, seasonality) with Arabic-market guidance (RTL ad text limits, Arabic keyword normalization/diacritics, Ramadan seasonality).
8. **Observability**: GAQL cost/row budgets, API quota handling (`RESOURCE_EXHAUSTED` backoff — none exists in `client.ts`), request-id logging in audit entries.
