# C3 — AI media buyer reasoning expert

Audit question: what context does the model actually receive before it answers in markting-ai, and how far is that from what a media buyer needs?

Short answer (VERIFIED_RUNTIME, see §2 command 10): the model receives exactly three text blocks in one system message — the unmodified upstream `engine/instructions.md` (4,055 bytes), a Deep Agents "Skills System" block listing the names and descriptions of five generic skills, and one line `Current date (UTC): <date>` — plus 27 bound tools. It receives **no** tenant identity, no business objective, no margin, no country, no target CPA/ROAS, no budget plan, no inventory, no promotions, no change history, no creative history, and no language hint. The only business-context mechanism the code supports (`workspace/skills/company-context/`) is absent from the repository, Git-ignored, and architecturally deployment-global rather than per-tenant. In the product path the account list the model sees is permanently the three US-dollar fixture accounts from `config/accounts.example.toml`, because the engine host hard-codes `PAID_MEDIA_DATA_MODE=sample` and refuses to boot with any live credential.

## 3. Findings

### C3-01 — The engine receives zero tenant or business context per turn
- Severity: **P1** (production blocker for the product's core promise: a media buyer that cannot know whose account, currency, market or goal it is reasoning about cannot give a safe recommendation)
- Classification: VERIFIED_CODE, VERIFIED_RUNTIME
- Evidence: `platform/apps/cloud/lib/markting/engine-client.ts:114-116` (`sendMessage(threadId, text)` posts `{ text }`); `platform/apps/cloud/lib/markting/assistant.ts:43`; `engine/src/paid_media_agent/surfaces/api/app.py:16-17` (`MessageIn.text` is the only field), `:91-101`; `engine/src/paid_media_agent/surfaces/runner.py:86-89` (configurable = `thread_id`, `caller_ref` only); `engine/src/paid_media_agent/assembly.py:175-176, 260-264` (prompt = static file); capture run (§2 #10): system message = `instructions.md` + Skills block + date line, nothing else.
- Description: The only per-request inputs that reach the model are the user's text and the thread id. The organization id and user id are encoded in the thread id string (`repository.ts:12-14`) but are never surfaced to the model or used to select context. The adport side does hold a per-org alias map with a `currency` column (`markting_account_aliases`, migration `:24-35`), but it is used only to translate proposals after the fact (`translate.ts:133-140`), never fed forward.
- Impact: Every recommendation is made without knowing the advertiser's goal, margin, market or currency. In live-model mode the model must either ask the user for these facts each thread (instructions.md:8, 14 tell it to) or guess.
- Recommendation: Add a per-tenant context envelope (org profile, locale, accounts owned, goals) injected into the system message or as a first tool result on every turn, keyed by `organization_id`; see §5.

### C3-02 — In the product path the model only ever sees the three US fixture accounts and synthetic data, even in `MARKTING_ENGINE_MODE=live`
- Severity: **P1** (contradicts the product's stated capability; any "analysis" shown to a paying tenant is about synthetic data)
- Classification: VERIFIED_CODE, VERIFIED_RUNTIME
- Evidence: `services/engine-demo/serve_demo.py:139-171` (`assert_fail_closed` refuses to start if `PIPEBOARD_API_TOKEN`, any X/OpenAI key, or `paid_media_data_mode != "sample"` is set), `:383-387` (both modes copy settings with `paid_media_data_mode="sample"`); `docker-compose.yml:47` (`PAID_MEDIA_DATA_MODE: sample`); `engine/src/paid_media_agent/runtime/profiles.py:72-82` (`sample` → `config/accounts.example.toml`); `engine/src/paid_media_agent/runtime/catalog.py:51-58` (`sample` → fixture catalog, no read provider → `FixtureReadProvider`, `profiles.py:146`); capture run output `list_accounts` = demo-google/demo-meta/demo-reddit, USD, America/New_York.
- Description: The engine host's safety posture (single write path) was implemented by pinning the engine to sample data. The consequence for reasoning is that the model's entire data context is the fixture dataset (`tools/fixtures.py`), regardless of which tenant is asking or what they have connected in adport. `MARKTING_ENGINE_MODE=live` swaps only the LLM (`serve_demo.py:224`).
- Impact: README.md:83 ("Analyses connected accounts (spend, conversions, CPA, ROAS)") and the Assistant page copy (`lib/i18n/messages/assistant.ts:5`, "Ask about performance across your connected accounts") are not true in the shipped configuration. The `placeholderLive` string "Ask about your campaigns…" (`assistant.ts:16`) is shown when `MARKTING_DEMO_MODE=false` even though the engine still answers about fixtures.
- Recommendation: Either route engine reads through adport's tenant runtime (so the data context is the tenant's accounts) or label the Assistant as a synthetic sandbox until that exists. Do not ship the "connected accounts" copy with this host.

### C3-03 — The `company-context` mechanism is documented but absent, and is deployment-global, not per-tenant
- Severity: **P2** as a deficiency; **P0 risk if used as designed** (one tenant's margins/targets would be readable by every tenant's conversations)
- Classification: VERIFIED_CODE (mechanism), VERIFIED_TEST (works when present), DOCUMENTED_ONLY (its content for this product)
- Evidence: directory absent (§2 #1); Git-ignored at `engine/.gitignore:30` (`workspace/skills/company-context/`); mechanism documented at `engine/docs/customization.md:6-55`, `engine/instructions.md:12-14`, `engine/workspace/skills/paid-media-wiki/SKILL.md:31-35`; proven to load when present by `engine/tests/contract/test_read_path_graph.py:55-95` (10 passed, §2 #11); single filesystem root per process: `engine/src/paid_media_agent/runtime/local.py:78` (`FilesystemBackend(root_dir=project_root)`), one compiled graph for all callers `serve_demo.py:225-240`; compose mounts one host folder for everyone `docker-compose.yml:55`; `engine/Dockerfile:15` copies `workspace/skills` to `/app/skills`.
- Description: The engine's only hook for business goals, conversion definitions, targets and naming is a Markdown folder written by a coding agent for *one company* (`.agents/skills/paid-media-org-onboarding/SKILL.md:13-19`). Nothing in `Makefile`, `infra/seed/seed-demo.mjs`, or the cloud app creates or selects such a folder, and no per-organization variant exists. `engine/docs/architecture/capability-map.md:18` lists "Read business context" as a capability; in this product it has no content.
- Impact: Goals, margins, break-even ROAS and target CPA are structurally unavailable to the model. If an operator followed the docs and wrote one file, it would apply to every tenant and leak across tenants.
- Recommendation: Treat company-context as a per-tenant record owned by adport (Postgres, org-scoped) and inject it per turn (C3-01). Do not populate the shared folder with any real tenant's data.

### C3-04 — Demo engine replays a hard-coded budget cut for any message matching a keyword list, including the UI's own analysis suggestion
- Severity: **P2** (demo is the default mode in `.env.example:51` and `docker-compose.yml:51`; the result is a misleading proposal, still gated by adport approvals so not P0)
- Classification: VERIFIED_CODE, VERIFIED_RUNTIME (§2 #13)
- Evidence: `services/engine-demo/serve_demo.py:63-67` (`WRITE_INTENT` regex includes `increase|raise|change|budget|...`), `:96-111` (routes to `write_steps` when matched); `engine/src/paid_media_agent/testing/demo_script.py:158-170` (always proposes `demo-google` `g-103` `daily_budget: 240`); `platform/apps/cloud/lib/i18n/messages/assistant.ts:10` (suggestion2 "Which campaign had the largest increase in CPA?") → routed to WRITE in §2 #13; Arabic equivalent `:36` ("ارتفعت") → ANALYSIS, so behaviour differs by language. `docs/PHASE1-REPORT.md:46` acknowledges the fixed script but not the misrouting.
- Description: A read-only question such as "What changed this week?" produces "A change is waiting for review" plus a pending operation to cut the Performance Max budget. The demo also ignores the requested target and amount ("Increase Meta budget to 500" → proposes Google −60 to 240).
- Impact: Users and evaluators see the "AI media buyer" propose a change nobody asked for. In an org with `MARKTING_DEMO_MODE=false` but engine mode still `demo`, the proposal is `unsupported` only because no real alias is named `demo-google` (`translate.ts:133-134`) — an org that did map that alias would get a real pending budget cut from an analysis question.
- Recommendation: Route the demo on the engine's own tool-call intent (or an allow-list of explicit change verbs with a target) and echo the requested target/amount; show the engine-mode banner independently of `MARKTING_DEMO_MODE`.

### C3-05 — No language or locale context reaches the model; Arabic-first applies to UI chrome only
- Severity: **P2**
- Classification: VERIFIED_CODE; live-model behaviour NOT_VERIFIED
- Evidence: `engine/instructions.md` contains no language directive (full read); `rg "[\x{0600}-\x{06FF}]" engine/src engine/instructions.md engine/workspace/skills` → only the host regex (`serve_demo.py:64`); `assistant.ts:30-47` and `route.ts:9-19` never forward `locale`; `demo_script.py:85-129` composes English-only answers; `README.md:129` admits engine reports are English/LTR but says nothing about chat answers.
- Description: The model gets an English prompt, English skills and the user's text. Whether a live model answers in Arabic depends on the model's default behaviour, not on anything the product controls; currency formatting instructions ("show money with its currency code exactly as the tools return it", instructions.md:54-55) will produce `USD` figures for a SAR market.
- Recommendation: Pass the UI locale and the tenant's reporting currency/timezone in the per-turn context; add an explicit "answer in the user's language; keep ad terms in English" directive in a product-owned prompt layer (outside `engine/`).

### C3-06 — Engine and adport demo worlds disagree: the only MENA-flavoured demo account is invisible to the model
- Severity: **P3**
- Classification: VERIFIED_CODE
- Evidence: `platform/apps/cloud/lib/markting/sandbox-provider.ts:47, 60-61, 210` (`fixture-snap-0001`, SAR, "Ramadan Awareness - KSA", alias `demo-snap`); `engine/config/accounts.example.toml` (three US accounts only; no `demo-snap`); capture run `list_accounts` (3 accounts); `docs/PHASE3-REPORT.md:22` claims the alias lets "the adport side demo Snap previews" — true only for adport-originated previews, never for Assistant proposals.
- Impact: The Assistant can never discuss or propose on the SAR account; the demo cannot show Arabic-market reasoning.

### C3-07 — The account binding schema cannot carry business facts
- Severity: **GAP** (not a defect; the code never claims otherwise)
- Classification: VERIFIED_CODE
- Evidence: `engine/src/paid_media_agent/config.py:60-69` (`alias`, `platform`, `provider_account_id`, `currency`, `timezone` only); `tools/discovery.py:33-40` exposes four of them; adport `markting_account_aliases.targets` is an id map, not goals (`translate.ts:54-55`); `rg` for target/goal/margin in engine source → no matches (§2 #9); `compute.py:349-372` ranks "attention" purely by absolute spend delta, with no goal input.
- Impact: Even a fully live engine would have nowhere to put market/country, target CPA, break-even ROAS, budget plan or attribution settings.

### C3-08 — Date context is UTC-only
- Severity: **P3**
- Classification: VERIFIED_CODE, VERIFIED_TEST
- Evidence: `engine/src/paid_media_agent/middleware/current_date.py:29-30`; `tests/unit/test_runtime_surfaces.py:30-47` (passes).
- Description: For Asia/Riyadh (UTC+3) the stamped date is yesterday for three hours each evening; mitigated by the rule to end windows on `data_complete_through` (instructions.md:25-29). Account timezones are available via `list_accounts` but the prompt never states the tenant's reporting timezone.

### C3-09 — No durable memory, change history or creative history
- Severity: **GAP**
- Classification: VERIFIED_CODE, DOCUMENTED_ONLY
- Evidence: `engine/docs/customization.md:112-129` (memory off by default; MDA-only; "this template does not add a separate long-term memory service"); `docs/ARCHITECTURE.md:704-711` and `self_hosted.py:65-105` (per-thread LangGraph checkpoints only); bound tool list (§2 #10) has no creative, change-history or audience tool; wiki admits "change history is not available on every platform" (`anomaly-and-significance.md:14-16`).
- Impact: Each thread starts from zero; the model cannot know what was changed last week, by whom, or what happened after.

## 6. What a world-class media-buyer context would contain

Everything below should be tenant-scoped, versioned, carry provenance (source, date, author) and freshness, and be injected per turn or retrievable through tenant-isolated tools — never a shared folder.

1. **Advertiser profile**: business model (e-commerce/app/lead-gen/retail), products or categories with price bands, AOV, gross margin per line, LTV and payback window, new vs returning mix, sales cycle length. From these: break-even ROAS and allowable CPA per product line and funnel stage, stated explicitly with the formula used.
2. **Market and locale**: country(ies), language of the operator and of the ads, reporting currency and VAT treatment, reporting timezone, local calendar (Ramadan, Eid al-Fitr/Adha, Saudi National Day, Founding Day, White Friday, back-to-school, summer travel), payment-method constraints (COD rates), delivery coverage.
3. **Objectives and constraints**: current quarter goal (revenue, orders, installs, leads), guardrails (max daily spend, min ROAS, protected brand campaigns), risk tolerance and approval policy (who approves what size of change — mirror adport's policy so the model proposes within the cap instead of discovering refusal).
4. **Budget plan**: monthly/quarterly budget by platform and campaign group, pacing target vs month-to-date actual, committed/contracted spend, planned increases.
5. **Measurement model**: conversion definitions per platform (which event, value source), attribution windows per account as configured, pixel/CAPI/SKAN health, data-completeness lag per platform, offline/CRM/Salla/Zid order joins and their grain, known double-counting.
6. **Inventory and promotions**: stock levels or out-of-stock SKUs, promo calendar with codes and discounts, price changes, landing-page changes — so "CPA rose" can be explained by a promo ending, not a bid.
7. **Account and campaign structure**: naming conventions decoded (brand/non-brand, prospecting/retargeting, geo, language), funnel role per campaign, learning-phase state, bid strategies and targets, audiences and exclusions.
8. **Change history**: every budget/status/bid/creative change with actor, time, reason and the measured outcome after the maturation window — the single most valuable input for "what happened and why".
9. **Creative library and fatigue**: creative ids, formats, launch dates, frequency, CTR/CVR trend by creative, what was retired and why, language variants.
10. **Decisions and experiments**: past recommendations, whether accepted, the outcome; holdouts/geo tests and their results; standing hypotheses.
11. **Conversation memory**: per-tenant summaries of prior threads and operator preferences (reporting cadence, preferred KPIs), clearly separated from authoritative targets (the upstream doc rightly warns learned preferences must not override explicit targets, `customization.md:127-129`).
12. **Delivery**: a compact, structured context block in the system message (identity, locale, currency, timezone, goals, guardrails) plus retrieval tools for the long tail (history, creatives, promos), all scoped by `organization_id`; an explicit instruction to answer in the operator's language and to state which targets were used.
