# A13 — Attribution expert

Audit of attribution handling across `platform/` (adport) and `engine/` (paid-media-agent) plus the markting glue in `platform/apps/cloud`. Question posed by the workstream: where could the system silently compare non-comparable conversions? Short answer: in four places, two of which are upstream behaviour the docs partly acknowledge, and two of which are local glue that contradict the upstream semantics document.

Headline: the engine's deterministic layer is careful about currency, window completeness and missing metrics, but **attribution is never a gate anywhere in code**. `DataQualityFlag.ATTRIBUTION_DIFFERS` exists and is never set; the engine's cross-platform total sums conversions and emits a blended CPA and ROAS across platforms (confirmed at runtime); the platform's `report` tool and MCP card total `conversions` across providers inside one currency group; and the cloud dashboard sums conversions, spend and value across every provider and every currency with a footnote that says only "Provider-reported". Conversion lag / incomplete-window handling is fixture-only in live mode because no live provider path ever populates `data_complete_through`.

## Findings

### A13-01 — Engine cross-platform total sums conversions and emits blended CPA/ROAS across platforms with different attribution; the attribution flag is never set
- Severity: P2
- Classification: VERIFIED_RUNTIME (probe above), VERIFIED_CODE
- Evidence:
  - `engine/src/paid_media_agent/tools/compute.py:278-298` `_combine` sums `conversions` and `conversion_value` across `MetricSet`s and derives `cpa`/`roas`.
  - `engine/src/paid_media_agent/tools/compute.py:309-331` the suppression rules are: no platforms, unavailable sources, mixed currencies, incomplete window, missing metric, window dates differ. Attribution is not among them.
  - `engine/src/paid_media_agent/domain/common.py:64` `ATTRIBUTION_DIFFERS = "attribution_differs"` — `rg` finds no other reference.
  - `engine/src/paid_media_agent/reports/render.py:123-134` renders `cross_platform_total` vs `cross_platform_previous` as the report scorecard (all `_SCORECARD_METRICS`, including conversions, CPA, ROAS) whenever the total is not suppressed and one currency is present.
  - Mitigations present: `compute.py:403-406` the model-facing `AnalysisSummary.cross_platform_total` is spend only; `render.py:169-172` appends "conversions use each platform's own attribution; they are not deduplicated people" to the data-quality list when more than one platform is present; `render.py:323-328` captions the conversions chart "Platform attribution; customers may overlap."
- Description: The engine's own wiki says "Do not add their conversion counts as if they were deduplicated people or incremental outcomes" (`engine/workspace/skills/paid-media-wiki/metrics-and-attribution.md:29-31`), but the deterministic code adds them, divides spend by the sum, and writes the result into the analysis artifact and the PDF/HTML scorecard. The eval expectation for q05 ("blended CPA across all platforms", `engine/tests/eval/questions.json:6`) accepts "a total with explicit caveat", so the project treats the caveat line as sufficient. The caveat is in a footnote list; the number is in the scorecard.
- Impact: A reader of the rendered report sees a portfolio CPA/ROAS that mixes Meta 7d-click/1d-view purchases with Google click-based primary conversions. Budget shifts argued from that number compare non-comparable conversions.
- Recommendation: Either gate `cross_platform_total.conversions/cpa/roas` behind an explicit attribution-compatibility check (set `ATTRIBUTION_DIFFERS` from `source_fields`/payload attribution metadata and suppress those three fields when platforms differ), or render the portfolio scorecard with spend/impressions/clicks only and keep conversions per platform. Add a unit test that two platforms produce no blended CPA.

### A13-02 — `normalize_rows` treats `conversions`, `purchases` and `results` as the same metric and `clicks`/`link_clicks` as the same metric
- Severity: P2
- Classification: VERIFIED_RUNTIME (probe: a Meta row carrying only `results: 5` became `conversions = 5` with no flag), VERIFIED_CODE
- Evidence: `engine/src/paid_media_agent/tools/normalize.py:28` `_CONVERSION_KEYS = ("conversions", "purchases", "results")`; `:29` `_VALUE_KEYS` includes `value`, `action_values`; `:130` `clicks = _int(_first(raw, ("clicks", "link_clicks")))`; `:131-132` first-present key wins per row.
- Description: Meta "results" is objective-dependent (link clicks for a traffic campaign, leads for a lead campaign, purchases for a sales campaign). "purchases" is one action type. The normalizer maps whichever is present first into one `conversions` column, per row, so a single platform read can mix three definitions across campaigns, and `aggregate` (`compute.py:71-95`) then sums them. The chosen key is not recorded anywhere except by inspecting `source_fields`. `clicks` (Meta all-clicks) is preferred over `link_clicks` when both exist, so CTR/CVR denominators also differ by payload shape.
- Impact: Within-platform CPA comparisons between campaigns with different objectives, and the cross-platform total in A13-01, can silently compare link clicks to purchases.
- Recommendation: Record `conversion_source_key` (and `click_source_key`) on `PerformanceRow`; set `MISSING_METRIC` or a new `MIXED_CONVERSION_DEFINITION` flag when more than one key is used inside one artifact; prefer `link_clicks` over `clicks` for Meta.

### A13-03 — Conversion lag / incomplete-window protection is fixture-only: no live provider path ever sets `data_complete_through`
- Severity: P2
- Classification: VERIFIED_CODE
- Evidence:
  - `engine/src/paid_media_agent/tools/pipeboard.py:193` `return ProviderResult(payload=payload)` — no `data_complete_through`, `currency`, `timezone`.
  - `engine/src/paid_media_agent/tools/direct/x_ads.py:363-369` and `direct/openai_ads.py:253-259` return `ProviderResult(payload={...})` only.
  - `engine/src/paid_media_agent/tools/fixtures.py:201-214,363-367` is the only producer (`FIXTURE_LAG_DAYS = 2`, `data_complete_through` from the dataset).
  - `engine/src/paid_media_agent/tools/normalize.py:141-142,156` `INCOMPLETE_WINDOW` and `is_complete=False` are set only when `data_complete_through` is not `None`; otherwise every row is complete.
  - `engine/src/paid_media_agent/tools/reads.py:263-264` the only live source of `INCOMPLETE_WINDOW` is `requested_window != actual_window` (rows missing entirely for a date).
- Description: The wiki tells the model that "last N days" ends on `data_complete_through` (`paid-media-analysis/SKILL.md:19-23`, `metrics-and-attribution.md:17-25`) and that days near `data_complete_through` are still filling in (`anomaly-and-significance.md:13-14`). In live mode the field is always `null` in `ReadResult` (`reads.py:294`), so yesterday's partially-posted Meta/Google conversions are treated as a complete day, and the `compare_periods` total is not suppressed for immaturity. The demo (`docs/ARCHITECTURE.md:654`) shows suppression working — because it runs on fixtures.
- Impact: Period comparisons whose current window ends yesterday understate conversions and overstate CPA for the current period relative to the matured previous period; the engine presents this as complete data.
- Recommendation: Derive a conservative `data_complete_through` per platform in the host (today − configured lag per platform, e.g. from `AccountRegistry` binding or settings) when the provider does not report one; surface it in `ReadResult`; add a live-path test that yesterday is flagged incomplete.

### A13-04 — Platform providers coerce absent conversions to `0`, contradicting the semantics doc, and the `zero-conversion-spend` rule then proposes pausing
- Severity: P2 (financial-risk note; mitigated by the preview/approval gate)
- Classification: VERIFIED_CODE; Meta mapping VERIFIED_TEST
- Evidence:
  - `platform/docs/reporting-semantics.md:13` "Missing metrics remain absent. Adport does not turn an unavailable value into zero."
  - Meta: `platform/packages/meta/src/provider.ts:201-203` only `omni_purchase` counts; `:591-594` `actionValue` returns `0` when the action type is absent; `platform/packages/meta/test/meta.test.ts:197` asserts "omni_purchase only, not link_click". A lead-gen, app-install or traffic campaign therefore reports `conversions: 0`, `cpa: 0`, `roas: 0`.
  - Google: `platform/packages/google/src/provider.ts:188-191` `num()` defaults to `0`. TikTok `:147-153`; Microsoft `:227-228`; Reddit `:226-231`; Apple `:198-211` hard-codes `conversion_value: 0, roas: 0`.
  - Providers that keep absence absent: Pinterest `:170-176`, LinkedIn `:181-186`, Snapchat `:145-147`, Spotify `:183-184` (also drops the `-5` privacy sentinel), X (`x/src/provider.ts:33` refuses conversion normalization).
  - `platform/packages/core/src/audit/packs/core-performance.ts:8-29` flags active campaigns with `spend >= 50` and `conversions === 0`, severity `critical` at 3×, and attaches `proposedAction: ctx.actions.pauseCampaign?.(…)`.
- Description: Half the providers violate the published missing≠zero rule; for Meta the zero is a definition artefact (purchase-only), not an observation. The audit rule cannot tell "no purchases because this is a lead campaign" from "tracking is broken", and its recommendation text (`:22-25`) frames both as waste.
- Impact: Audit output can recommend pausing well-performing non-purchase Meta campaigns. Execution still requires preview + approval (`platform/packages/core/src/provider.ts:76-79`), so this is not P0, but the recommendation is produced from a conversion definition mismatch.
- Recommendation: Return `undefined` (omit) when the mapped action is absent; for Meta pick the conversion action from the campaign objective or expose it as a query parameter; have the rule skip rows whose conversion metric is absent rather than zero.

### A13-05 — Normalized `conversions` mixes click-only and click+view definitions with hardcoded or defaulted windows, and `ReportRow` carries no attribution metadata, so the `report` tool and MCP card total them across providers
- Severity: P2
- Classification: VERIFIED_CODE; VERIFIED_TEST for the summation path
- Evidence:
  - Reddit: `platform/packages/reddit/src/provider.ts:230` `conversions = conversion_purchase_clicks + conversion_purchase_views` (view-through folded in, undisclosed in the row).
  - Snapchat: `platform/packages/snapchat/src/provider.ts:61` `swipe_up_attribution_window: '28_DAY', view_attribution_window: '1_DAY'` hardcoded; `:145` conversions = `conversion_purchases`.
  - Pinterest: `platform/packages/pinterest/src/provider.ts:92` `click_window_days: '30', view_window_days: '1', conversion_report_time: 'TIME_OF_AD_ACTION'` hardcoded; `:17` conversions = `TOTAL_CHECKOUT`.
  - LinkedIn: `platform/packages/linkedin/src/provider.ts:7` `externalWebsiteConversions` (click+view per `engine/workspace/skills/paid-media-wiki/platform-differences.md:16`).
  - Google: `platform/packages/google/src/provider.ts:31-32` `metrics.conversions` / `metrics.conversions_value` (click-based primary actions, no `segments.conversion_action`).
  - Microsoft: `platform/packages/microsoft/src/provider.ts:179` `Conversions`, `Revenue` columns only (no `ViewThroughConversions`).
  - Meta: `platform/packages/meta/src/provider.ts:174-186` requests `actions,action_values` with no `action_attribution_windows` / `use_unified_attribution_setting`; the account default applies and is not recorded. The raw `meta_insights` tool (`meta/src/tools.ts:78-100`, `provider.ts:234-253`) likewise exposes no attribution-window parameter.
  - TikTok: `platform/packages/tiktok/src/provider.ts:123-125,151-153` `conversion` (optimization-event dependent) and `total_complete_payment_rate` as value.
  - `platform/packages/core/src/model.ts:38-45` `ReportRow` has `provider, accountId, currency?, entity, metrics` — no attribution, window or conversion-definition field.
  - `platform/packages/core/src/report-summary.ts:3,8-24` groups rows by **currency only** (falls back to provider+account only when currency is unknown) and sums `conversions` and `conversion_value` across the group; `platform/packages/core/test/report-summary.test.ts:12-19` asserts the summed `conversions: 63`.
  - `platform/packages/mcp/src/ui.ts:236` renders a "Conversions" KPI as `total(rows,'conversions')` for the selected currency group with no attribution notice; the only notice text is about currency, truncation and errors (`:190,236`).
  - `platform/packages/core/src/tools/builtin.ts:55-57` the tool description warns about currencies and ratio averaging but not attribution.
- Description: `platform/docs/reporting-semantics.md:31` correctly says conversions keep each provider's model and are not deduplicated — but then the same package sums them into a currency-group total that the card displays as one number. Nothing in the row, the summary, or the card tells the consumer that 30 of the "63" were view-through or that the Snap window is 28/1 while Google's is click-only. Snapchat and Pinterest docs disclose their windows (`platform/docs/providers/snapchat.md:22`, `pinterest.md:33`), Meta and Google do not.
- Impact: An MCP client (Claude, ChatGPT, the cloud dashboard) that reads `summary.groups[].metrics.conversions` across a USD Meta account and a USD Google account gets a single conversions figure and a spend-weighted ROAS that silently blends attribution models.
- Recommendation: Add `attribution: { model: string; clickWindowDays?: number; viewWindowDays?: number; includesViewThrough?: boolean; conversionDefinition: string }` to `ReportRow`; have `summarizeReport` group by `(currency, attribution signature)` or return `conversions: null` with a `conversions_suppressed_reason` when definitions differ in a group; add that caveat to the card and tool description.

### A13-06 — Cloud dashboard (local glue) sums spend, conversions and value across all providers and all currencies, and its ROAS tile is always `0×`
- Severity: P2
- Classification: VERIFIED_CODE
- Evidence:
  - `platform/apps/cloud/app/dashboard/live-data.tsx:33-41` reduces every row into one `totals` object (`spend`, `conversions`, `value`) with no currency or provider grouping; `:41` `roas = totals.value / totals.spend`.
  - `platform/apps/cloud/lib/cloud/reads.ts:53-55` requests `metrics: ['spend','impressions','clicks','conversions','roas']` — `conversion_value` is never requested — and `app/api/dashboard/summary/route.ts:9-16` passes rows through unchanged. Every provider returns only the requested metrics (e.g. `meta/src/provider.ts:232`, `pinterest/src/provider.ts:182`), so `row.metrics.conversion_value` is always `undefined`, `totals.value` is `0`, and the tile shows `0×` whenever a provider is connected.
  - Footnotes: `platform/apps/cloud/lib/i18n/messages/overview.ts:24-25,61-62` "Provider-reported" / "كما يبلّغ عنها المزوّد" and "Conversion value ÷ spend" / "قيمة التحويلات ÷ الإنفاق". No attribution or currency caveat.
  - Contradicts `platform/docs/reporting-semantics.md:15` "Never sum monetary values across accounts with different currencies" and `:31`.
  - Provenance: `git log` shows `live-data.tsx` touched locally in `4bbb55d` (i18n move); the summation predates or survived that change; this file is in the markting glue, not upstream adport.
- Description: The Arabic-first overview that a media buyer sees first presents one "Conversions" number blending every connected platform's attribution and one ROAS that is structurally zero.
- Impact: Misleading KPI (ROAS) and a blended conversions number with no caveat; a SAR Snap account and a USD Google account would be summed into one spend figure.
- Recommendation: Request `conversion_value` or reuse `summarizeReport` (which at least groups by currency and documents `roas_method`); render per-currency groups; add an attribution footnote; add a test for the ROAS tile with provider rows.

### A13-07 — Cross-platform total ignores timezone mismatch; `TIMEZONE_MISMATCH` and `CURRENCY_MISMATCH` flags are never set
- Severity: P3
- Classification: VERIFIED_RUNTIME (probe combined `America/Los_Angeles` and `Asia/Riyadh` with `all quality flags: []`), VERIFIED_CODE
- Evidence: `engine/src/paid_media_agent/tools/compute.py:152-154` rejects mixed timezones *within* one platform read; `:316-326` the cross-platform gate checks currency, completeness, missing metric and window dates but not `current_window.timezone`; `engine/src/paid_media_agent/domain/common.py:60-61` flags defined, no other references (rg). `platform/docs/reporting-semantics.md:27` acknowledges boundary skew for the platform side.
- Impact: Daily windows for a Riyadh account and a Los Angeles account differ by up to 11 hours; late-day conversions move across the window boundary, and the blended total treats them as the same day.
- Recommendation: Set `TIMEZONE_MISMATCH` on the comparison when platform timezones differ and either suppress the total or state it in `total_suppressed_reason`/notes.

### A13-09 — Engine X adapter reads `placement=ALL_ON_TWITTER` only, while the platform X provider iterates all placements

### A13-10 — Partial-conversion aggregation produces a CPA over full spend but partial conversions
- Severity: P3
- Classification: VERIFIED_CODE
- Evidence: `engine/src/paid_media_agent/tools/compute.py:60-68` `_sum_optional_decimal` skips `None` rows and returns a total when at least one row has a value; `:91` `cpa=_ratio(spend, conversions)` uses the full spend. ## What a world-class system would need (concrete)

1. An `Attribution` descriptor on every normalized row (model, click window, view window, includes-view-through, conversion event, report-time basis, data-complete-through) populated by each provider from the API parameters it actually sent or from the account setting it read; the engine should set `ATTRIBUTION_DIFFERS` from it and suppress blended conversions/CPA/ROAS when signatures differ.
2. Explicit, configurable attribution windows per provider (Meta `action_attribution_windows` + `use_unified_attribution_setting`, Snap/Pinterest window params, Reddit click vs view fields kept separate) so a tenant can choose "7d click only everywhere" for comparability and see what cannot be aligned.
3. Live `data_complete_through` per platform (provider-reported where available, otherwise a configured lag) and conversion-maturity awareness in `compare_periods` (compare matured windows, or restate the previous period at the same maturity).
4. First-party outcome ingestion: Salla/Zid orders and revenue, UTM/click-id capture on landing pages, and server-side conversion forwarding (Meta CAPI, Google enhanced/offline conversions, TikTok Events API) with a pixel-vs-server reconciliation report.
5. A dedup/MTA layer over first-party events (last-click, position-based, data-driven) presented *alongside* platform-attributed numbers, never replacing them silently, plus an incrementality toolkit (geo holdouts, conversion-lift integration, MER as a top-line sanity check).
6. Dashboard and MCP totals that refuse to blend conversions across attribution signatures or currencies, with an Arabic footnote stating which model each platform used.
