# E5 — API security

Audit of the machine/HTTP surface of markting-ai: the adport cloud REST/MCP APIs, the host's
engine-bridge routes (assistant, reports, locale), and the paid-media-agent engine HTTP API plus the
engine-demo report host. Read-only audit; no files changed outside this report.

## Findings

### E5-01 — Engine reports surface is not tenant-isolated (cross-tenant read of report runs/files)
- Severity: **P1** (reaches P0 if one engine serves multiple paying orgs, which the plan tiers sell)
- Classification: **VERIFIED_CODE** + **VERIFIED_TEST**
- Evidence: `platform/apps/cloud/app/api/reports/engine/route.ts:17-20` (GET lists reports after only `sessionPrincipal(organizationId)` — no org filter), `.../reports/engine/[name]/route.ts:13-15` (downloads any file after only a valid session), `services/engine-demo/serve_demo.py:355-358` (`GET /reports` returns the whole `_load_index` after `caller()` bearer check), `serve_demo.py:360-374` (`GET /reports/files/{name}` checks only bearer + name pattern), `serve_demo.py:283` (`requested_by = who`, i.e. the single shared `adport-bridge` caller), `docker-compose.yml` engine token shared by the cloud; `uv run pytest .../test_demo_api.py::test_reports_run_list_and_download` passes with one token.
- Description: The cloud talks to one engine host via one `MARKTING_ENGINE_URL`/`MARKTING_ENGINE_TOKEN` (`lib/markting/assistant.ts:11-14`). The engine report index/files are global to that process with no organization dimension. The two cloud routes authenticate a Supabase session but never check that a report run or file belongs to the caller's organization. Any authenticated member of any org (GET list requires no role at all; download requires only a session) can enumerate and download every report the host has produced.
- Impact: Cross-tenant disclosure of business/ad-performance analysis (spend, ROAS, campaign names) in a multi-org deployment. Even in a single-company deployment it means report access is entirely un-scoped to org/role for GET/download.
- Recommendation: Stamp each report run with the requesting `organization_id`, persist it in the index, and filter `listReports`/`fetchReportFile` by the caller's org on both the cloud route and the host; require a non-viewer role for download as POST already does.

### E5-02 — Engine `/proposals/{id}/reject` and `/edit` perform no caller/ownership authorization
- Severity: **P2** (P1 in any multi-token engine deployment, e.g. Slack multi-user)
- Classification: **VERIFIED_CODE** (acknowledged in `docs/PHASE0-REPORT.md:88`)
- Evidence: `engine/src/paid_media_agent/surfaces/api/app.py:128-146` (reject/edit handlers resolve `who` but pass it straight through), `surfaces/runner.py:257-287` (`reject`/`edit` only `WriteDenied("unknown_proposal")`/state checks — no requester/approver check), `tools/writes.py:457-512` (`revise`/`reject` take `editor_ref`/`actor_ref` only for the history line; only `approve` calls `ApprovalPolicy.may_approve`, `writes.py:513-520`). Contrast `app.py:106-112` (`get_proposal` *does* enforce `view.requester_ref != who and who not in approver_refs`).
- Description: Any holder of a valid engine bearer can reject or revise (edit the proposed field values of) any pending proposal by UUID, regardless of thread ownership — the visibility check applied to reads is absent on these two mutating-adjacent endpoints.
- Impact: In the markting cloud this is mitigated (single `adport-bridge` caller; the cloud `EngineClient` additionally refuses `/approve` and `/edit` via `FORBIDDEN_PATHS`, `lib/markting/engine-client.ts:61,77-79`), so it is not reachable cross-tenant from the product. It remains a genuine horizontal-authz gap in the vendored engine, exploitable if the engine is ever exposed with multiple caller tokens or if the shared token leaks (a leaked token could rewrite a pending proposal before a human sees it).
- Recommendation: In `runner.reject`/`runner.edit` require `who == record.changeset.requester_ref or who in approver_refs`, matching `get_proposal`.

### E5-03 — Trusted `readOnly` annotation is the sole scope gate; no path allowlist is enforced generically
- Severity: **P3** (hardening gap; no current tool is miscategorized)
- Classification: **VERIFIED_CODE**
- Evidence: `lib/cloud/auth.ts:46-48` + `app/api/v1/tools/[tool]/route.ts:10` (`requireScope(principal, definition.annotations.readOnly ? 'tools:read' : 'tools:write')`); `packages/mcp/src/index.ts:121-124` (MCP exposure keyed identically on `tool.annotations.readOnly`); `packages/core/src/tools/registry.ts:84-89` (`registry.call` does **not** enforce scope). The generic passthrough read tools (`apple_api_read`, `microsoft_api_read`, `reddit_api_read`) are `readOnly:true` yet accept `method:POST`+arbitrary `path`/`body` — they are safe only because each provider re-validates the path against a read allowlist: apple `packages/apple/src/provider.ts:85,149-152`, microsoft `packages/microsoft/src/provider.ts:122-132,488-496`, reddit `packages/reddit/src/provider.ts:157-169`.
- Description: Scope enforcement (read vs write) is a single boolean carried by each tool and trusted end to end. The passthrough read tools would let a `tools:read` key reach a write endpoint if their provider allowlist were ever weakened or omitted; today all three verified providers enforce it, so no live defect exists.
- Impact: A future provider adding a passthrough `*_api_read` tool without a provider-side allowlist, or mis-annotating a write tool `readOnly:true`, would silently grant read-only keys write capability with nothing in the route/registry to catch it.
- Recommendation: Enforce the read/write classification centrally (e.g. a registry invariant that `readOnly` passthrough tools must declare a method/path allowlist, or move the allowlist contract into `defineTool`); add a conformance test asserting every `method:'POST'`-capable read tool rejects a known mutation path.

### E5-04 — Engine-error detail is passed through to dashboard users
- Severity: **P3**
- Classification: **VERIFIED_CODE**
- Evidence: `lib/markting/engine-client.ts:112-116` (`Engine returned ${status}: ${detail.slice(0,300)}`), surfaced by `app/api/reports/engine/route.ts:14-17` and `assistant/messages/route.ts` via `apiError` which returns `error.message` for <500; `services/engine-demo/serve_demo.py:349-353` (`report failed: {type(exc).__name__}: {exc}`).
- Description: Upstream engine exception type and up to 300 chars of its message reach the authenticated end user for 4xx and for 5xx mapped to a 4xx-ish message. Not a credential leak (tokens never pass through), but it exposes internal error shapes.
- Impact: Minor information disclosure to authenticated users.
- Recommendation: Log detail server-side; return a generic message to the client for engine-origin errors.

## What a world-class system would need (gaps, concrete)

- Per-organization engine isolation: either a tenant dimension on engine threads/proposals/reports (and routes that filter by it), or a hard, documented "one engine per customer deployment" boundary enforced in config so the multi-org cloud cannot point many orgs at one engine (E5-01).
- Central, testable read/write classification instead of a trusted boolean, with a registry invariant that passthrough read tools must carry a method/path allowlist (E5-03).
- Horizontal-authz checks on every proposal-mutating engine endpoint identical to the read-visibility check (E5-02).
- Per-IP / unauthenticated-route rate limiting at the edge (the durable limit only covers authenticated subjects; `locale` and other unauthenticated POSTs have none).
- Structured, non-leaking error envelope for engine-origin failures (E5-04), and an explicit max body-size guard on JSON routes.

## Disagreements / claims in docs that the code contradicts

- `docs/PHASE0-REPORT.md:88` candidly states `POST /proposals/{id}/reject|edit` "check only that the bearer is valid" — this matches the code (E5-02), so docs and code agree; the gap is acknowledged, not hidden. No contradiction, but the acknowledgment understates that `/edit` can rewrite proposal field values, not merely resume a thread.
- `docs/PHASE1-REPORT.md:13` claims assistant threads "ownership is enforced in `markting_threads`" — VERIFIED at the cloud layer (`assistant.ts:34-38`). But the same report's framing of a tenant-isolated engine does not hold for the **reports** surface, which has no org dimension at all (E5-01); `docs/PHASE0-REPORT.md:88`/`:112` note the engine identity is one `caller_ref` per org — consistent with my E5-01, i.e. the reports routes rely on a tenancy guarantee the engine does not provide.
- README/architecture framing of markting as multi-tenant SaaS vs. the single shared `MARKTING_ENGINE_URL`/token (`lib/markting/assistant.ts:11-14`) is the core unresolved tension behind E5-01.
