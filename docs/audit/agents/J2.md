## Findings

### J2-01 — "Live" mode: the engine always reasons over synthetic fixture data while adport applies the result to real accounts
- **Severity:** P1 (serious financial-risk design flaw once anyone follows the README into live mode; no live deployment exists today)
- **Classification:** VERIFIED_CODE (engine side), DOCUMENTED_ONLY contradicted (README)
- **Evidence:** `services/engine-demo/serve_demo.py:383-387` — in `live` mode settings are `base.model_copy(update={"paid_media_data_mode": "sample"})`; `serve_demo.py:163-166` — `assert_fail_closed` refuses to start unless `paid_media_data_mode == "sample"`; `docker-compose.yml:47` — `PAID_MEDIA_DATA_MODE: sample` unconditionally. `platform/apps/cloud/lib/markting/translate.ts:133-145` resolves the engine's `account_ref` (fixture aliases) through `markting_account_aliases` to any provider/account id; `lib/markting/repository.ts:40-50` merges DB aliases over the fixture defaults; `lib/markting/runtime.ts:50` uses the **real** `createTenantRuntime` when `MARKTING_DEMO_MODE=false`. README.md:116 — "`false` = real accounts connected through OAuth"; README.md:118 — "`live` = `PAID_MEDIA_MODEL` and its key".
- **Description:** The host hard-pins the engine's read side to the bundled sample fixtures in both modes. In `MARKTING_ENGINE_MODE=live` + `MARKTING_DEMO_MODE=false`, the model answers performance questions and generates budget/status proposals from **synthetic** campaigns (`g-103` at 300 USD, etc.), and the bridge translates those proposals onto **real** accounts whenever an alias row maps `demo-google`-style refs to a real account id. The adport preview does show the real current value (provider `previewWrite`), so a careful approver can notice, but the "AI media buyer" analysis the approver reads is fiction about a different account.
- **Impact:** Real money moved on the basis of analysis of data that is not the customer's. The README presents live mode as "real accounts" without this caveat.
- **Recommendation:** Either (a) document loudly that live mode is model-live/data-synthetic and block alias bindings to non-sandbox providers while `paid_media_data_mode == "sample"`, or (b) design the live data path (per-tenant engine instance or per-tenant read credentials) before offering live mode at all. Add a boot assertion that refuses `MARKTING_DEMO_MODE=false` on the cloud unless the engine `/health` reports a non-sample data mode.

### J2-02 — Engine reports are a global, cross-organization resource
- **Severity:** P1 (cross-tenant boundary violation in a multi-tenant SaaS; content is synthetic today, see J2-01, so no customer data leaks yet)
- **Classification:** VERIFIED_CODE + VERIFIED_RUNTIME
- **Evidence:** `platform/apps/cloud/app/api/reports/engine/route.ts:35-43` — `GET` authenticates the session, then returns `engineClient().listReports()` with no organization filter; `route.ts:46-57` — any non-viewer can `POST` a run; `app/api/reports/engine/[name]/route.ts:68-84` — any authenticated user of any organization streams any `rpt_*` file. `services/engine-demo/serve_demo.py:246-307` — one index file `workspace/out/markting-reports.json`, `requested_by` is the caller name (`adport-bridge` for every org), `serve_demo.py:355-374` — list/file routes check only the bearer token. Runtime probe: caller B listed and downloaded caller A's report (200). `docker-compose.yml:49` — a single `adport-bridge` caller for all tenants.
- **Description:** Report runs and their HTML/PDF/JSON files are not tagged with an organization on either side. Org A triggers a run; org B's viewer sees it on their Reports page and downloads it. Rate limiting on `POST` is per org (`route.ts:51`), so N orgs multiply the load on the single engine (WeasyPrint PDF render under one `asyncio.Lock`).
- **Impact:** Today: synthetic report prose visible to every tenant; metadata about when runs happened. The moment the engine's data becomes tenant-specific (the stated direction, `docs/TODO.md:16-20`), this is a P0 data leak with no code change needed.
- **Recommendation:** Store `organization_id` with each run on the adport side (a `markting_report_runs` table), key engine runs by an org-scoped `requested_by` (pass the org id in the request body or use one token per org), and filter list/download by org. Rate-limit the shared engine globally, not only per org.

### J2-03 — The separation-of-duties control on Apply is bypassable three ways
- **Severity:** P2
- **Classification:** VERIFIED_CODE
- **Evidence:**
  1. `.env.example:49` — `MARKTING_ALLOW_SELF_APPROVAL=true` and `.env.example:47` — `MARKTING_DEMO_MODE=true` are the shipped defaults that `make env` copies (`Makefile:21-23`); `lib/markting/env.ts:16` defaults to `'false'` only when the variable is absent.
  2. `app/api/approvals/[id]/apply/route.ts:22` — `if (row.createdBy && row.createdBy === principal.userId && ...)`; `lib/cloud/repository.ts:371-381` — `created_by` is `principal.userId ?? null`; `repository.ts:333` — `authenticateApiKey` returns `{ organizationId, apiKeyId, scopes }` with **no `userId`**, so every preview created through `/api/v1` or `/mcp` has `created_by = null` and the self-approval check is skipped.
  3. `app/api/v1/tools/[tool]/route.ts:5-13` and `app/mcp/route.ts:14` apply with `pending_operation_id` through the same `PolicyEngine` using the **same API key** that created the preview; the markting check exists only in the dashboard route. `packages/core/src/policy/engine.ts:104` verifies provider + hash, not actor.
- **Description:** The README (README.md:79) says "nothing is applied until a human approves it there [Approvals page]" and PHASE1-REPORT.md:16 says "Requester ≠ approver unless `MARKTING_ALLOW_SELF_APPROVAL=true`". In code, the requester can apply via REST/MCP with their own key, can apply in the dashboard anything their key created, and the default `.env` turns the check off anyway.
- **Impact:** The four-eyes guarantee advertised for the product does not hold outside the narrow dashboard-created, dashboard-applied path with a non-default env file.
- **Recommendation:** Ship `MARKTING_ALLOW_SELF_APPROVAL=false` and `MARKTING_DEMO_MODE=false` in `.env.example` with `make env` prompting to enable demo; record `created_by_api_key_id` on pending rows and refuse when the applying principal owns that key; move the self-approval rule into the `PolicyEngine`/pending store so REST/MCP applies are covered too, or document that REST/MCP are single-actor paths.

### J2-04 — The cloud's master secrets are injected into the engine container
- **Severity:** P2 (secret sprawl; an engine compromise becomes a full cloud compromise)
- **Classification:** VERIFIED_CODE
- **Evidence:** `docker-compose.yml:17` and `docker-compose.yml:40` — both `cloud` and `engine` use `env_file: .env`; `.env.example:7-13,39-41,47-50` — that file holds `SUPABASE_SECRET_KEY` (service role), `SUPABASE_DB_URL` (Postgres **superuser** DSN `postgres:postgres@…`, `.env.example:8`), `ADPORT_CLOUD_ENCRYPTION_KEY` (the vault key for all tenants' OAuth tokens), `ADPORT_API_KEY_PEPPER`, `ADPORT_MCP_OAUTH_SIGNING_KEY`, `STRIPE_SECRET_KEY`, `MARKTING_DEMO_PASSWORD`. The engine process runs model-driven code with skills mounted (`docker-compose.yml:56`).
- **Description:** The engine only needs `PAID_MEDIA_*`, `DATABASE_URL`, the model key and `MARKTING_ENGINE_MODE`. Everything else is reachable from any code path in the engine (`os.environ`), including LLM-driven tool execution in live mode.
- **Recommendation:** Give each service its own env file (`infra/env/cloud.env`, `infra/env/engine.env`) or an explicit `environment:` allowlist; never pass the Supabase service key or encryption key to the engine.

### J2-06 — One shared engine token for every tenant; the token can call `approve`/`edit` on the engine
- **Severity:** P3 as a defect today (defense in depth holds), GAP for per-tenant identity
- **Classification:** VERIFIED_CODE + VERIFIED_RUNTIME
- **Evidence:** `docker-compose.yml:49` — `PAID_MEDIA_API_TOKENS=<token>:adport-bridge`; `lib/markting/engine-client.ts:119,135-137` — only a client-side regex blocks `/approve` and `/edit`; `app.py:116-148` — the engine accepts those routes for any valid token. Probe: `approve` with the bridge token → 403 `approver_policy: approver is not an authorized approver` because `serve_demo.py:159-162` refuses to boot with approvers configured and `serve_demo.py:69-81` replaces the write provider. Thread isolation: `lib/markting/assistant.ts:180-184` enforces `org_<org>__u_<user>__` prefixes; `repository.ts:17-27` `claimThread` is org+user scoped; `runner.py:86-89` is per caller. Probe: a second caller could not touch the first caller's thread or proposal.
- **Description:** The bridge token is the only identity the engine sees; all tenants are one caller. Isolation of threads and proposals therefore rests entirely on the cloud's regex and `markting_threads` (documented honestly at README.md:128). Approval on the engine is blocked by policy, not by token scope.
- **Recommendation:** One token per organization (the engine already supports `token:caller` pairs) or a signed per-request tenant claim; keep the kill switch and empty approver set as the second layer.

### J2-08 — `MARKTING_DEMO_MODE` is a global switch that mixes synthetic and real paths in one deployment
- **Severity:** P2 (demo code can reach production paths)
- **Classification:** VERIFIED_CODE; the comment's claim about an upstream guard is NOT_VERIFIED
- **Evidence:** `lib/markting/runtime.ts:49-57` — when the env flag is `true`, the Assistant and Approvals apply paths of **every** organization use `SandboxProvider`, while `/mcp` and `/api/v1` keep real providers (`app/mcp/route.ts:14`, `app/api/v1/tools/[tool]/route.ts:8`). `lib/markting/repository.ts:45` — fixture aliases are injected for every org in demo mode. Sandbox pending rows and audit events land in the same `pending_operations`/`audit_events` tables (`runtime.ts:55`). `sandbox-provider.ts:6-8` states the tool names "deliberately avoid the `demo_`/`mock_`/`synthetic_` prefixes that the production MCP connector refuses" — I could not find such a refusal in `platform/apps/cloud` or `platform/packages/mcp` (`rg` for those prefixes found only the mock/synthetic providers themselves and `account-scope.ts:38`), so that comment is NOT_VERIFIED; what is verified is that the sandbox is reachable only through `createBridgeRuntime`. `PolicyEngine.apply` checks `pending.provider !== provider.id` (`packages/core/src/policy/engine.ts:104`), so a row previewed in one mode cannot be applied in the other (good).
- **Impact:** A deployment that forgets to flip the default `true` serves synthetic previews beside real OAuth connections; the audit log interleaves `sandbox` and real events; the only UI hint is a placeholder string (`assistant-chat.tsx:89`).
- **Recommendation:** Make demo a per-organization attribute (e.g. `organization_settings.demo = true` set by the seed) instead of a process-wide env, show a persistent banner, and exclude sandbox events from the production audit view or tag them.

## What a world-class system would need (gaps, concrete)

1. Per-tenant engine identity: one `PAID_MEDIA_API_TOKENS` pair per organization (or a signed tenant claim per request), and org-tagged report runs stored on the adport side; the engine's `requested_by` must carry the org.
2. Separation of duties enforced in the pending store (`created_by_user_id`, `created_by_api_key_id`, `applied_by`), applied uniformly to dashboard, REST and MCP, with an org-level setting instead of a process env.
3. Demo as a per-organization property with a visible banner, seeded by `make seed`, never a process-wide flag; sandbox events tagged in the audit log.
4. A real live data path before offering live mode: either per-tenant engine instances with the tenant's read credentials, or an adport-side read bridge that feeds the engine the tenant's normalized reports; a hard refusal to bind fixture aliases to non-sandbox providers while the engine is in sample mode.
5. Service-scoped environment files and a `.dockerignore`; build args for `NEXT_PUBLIC_*`; `chmod 0600` on generated env files; a loopback guard in the seed.
6. Approvals UI that renders changes, budget deltas (with currency and percentage), coercions, engine reason and risk flags, and a typed confirmation for destructive/large deltas.
7. Engine FastAPI built without public docs; `/markting/info` behind auth; a global (not per-org) rate limit on report runs.
8. An alias-management UI/API with provider-account validation against `organization_ad_accounts` so live mode does not depend on manual SQL.
