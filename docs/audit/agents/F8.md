## Findings

### F8-01 — The monorepo has no CI; both vendored workflows are inert and `make test` is a subset
- **Severity:** P2 **Classification:** VERIFIED_CODE (absence), INFERRED (GitHub Actions only discovers workflows under the repository-root `.github/workflows`)
- **Evidence:** cmd #1, #2; `platform/.github/workflows/ci.yml:1-45` and `engine/.github/workflows/ci.yml:1-35` assume they are the repo root (`pnpm install`, `uv sync` with no `working-directory`); `Makefile:51-54` runs only six hand-picked cloud test files + `services/engine-demo/tests` + one infra test; it omits `@adport/core` (where `policy-engine.test.ts` lives), the DB-gated suites, engine `tests/`, typecheck and build.
- **Description:** Nothing executes the critical-chain tests on push/PR. The upstream workflows would not trigger because they are nested; even if copied verbatim they would fail (`pnpm` run from root, Node matrix 22/24 vs. Supabase requirement).
- **Impact:** Regressions in `bridge.ts`/`translate.ts`/`PolicyEngine` can merge unnoticed; the Phase reports' "N passed" figures are developer-machine runs only.
- **Recommendation:** Root `.github/workflows/ci.yml` as laid out in §"CI layout" below; delete or `workflow_dispatch`-only the nested files to avoid confusion.

### F8-02 — Re-bridging the same engine proposal creates a second applicable pending operation (no idempotency on `(proposal_id, revision)`)
- **Severity:** P2 **Classification:** VERIFIED_CODE (chain), NOT_VERIFIED at runtime
- **Evidence:** `engine/src/paid_media_agent/surfaces/runner.py:91-93` (`latest_proposal` returns the newest proposal on the thread regardless of state) and `:128` (`_outcome` reports it on every turn); `platform/apps/cloud/lib/markting/assistant.ts:50-51` bridges whenever `proposal.state === 'awaiting_approval'`; `bridge.ts:76` always calls `registry.call` (new `pending_operations` row, `engine.ts:64-75`); `bridge.ts:98-105` swallows hand-off failures; `repository.ts:84-86` upserts `(organization_id, proposal_id, revision)` and **overwrites** `pending_operation_id`; `findEngineProposal` unused on the hot path (cmd #10).
- **Description:** If the engine-side reject fails (engine restarted with memory persistence → `unknown_proposal` 409, network blip, or the 500 in F8-12), the proposal stays `awaiting_approval`. The next message on the same thread (even an analysis question) returns the same proposal, the bridge previews it again, a second pending row is created, and the provenance row now points only at the second one. Both rows are independently applicable within the TTL. Whether LangGraph accepts a plain new message while the interrupt is pending is **NOT_VERIFIED** here; if it does not, the user sees an error instead, which is also untested.
- **Impact:** Duplicate approvals of one recommendation; the first pending row loses its "Assistant" provenance on the Approvals page (`page.tsx:35-37` shows it as "API"); applying both performs two provider writes (idempotent for the two supported operations, but double audit and double API calls).
- **Recommendation:** Before `registry.call`, look up `findEngineProposal(org, proposal_id, revision)`; if a `pending` record exists and its pending row is still open, return it instead of creating a new one. Add the replay scenarios S-R1..R3 below.

### F8-03 — `PolicyEngine.apply` is not atomic: concurrent approvals double-apply on providers without compare-and-set
- **Severity:** P2 **Classification:** VERIFIED_CODE; NOT_VERIFIED at runtime (race not reproduced)
- **Evidence:** `platform/packages/core/src/policy/engine.ts:90-123` — `get` → expiry → hash → `applyWrite` → audit → `delete`, no conditional consume; `platform/apps/cloud/lib/cloud/repository.ts:413-418` `delete` is an unconditional `update … set consumed_at = now()`; `apply/route.ts:20-26` has no lock. Sandbox is protected only by its own CAS (`sandbox-provider.ts:76-79`, `repository.ts:133-141`), real providers (`markting-snapchat-wire.test.ts:59-81` path) are not.
- **Description:** Two admins clicking Apply within the same window both pass `pending.get` (row still `consumed_at is null`), both call `applyWrite`, both append `applied`, both mark consumed.
- **Impact:** Two provider mutations and two `applied` audit events for one approval. Financial impact is bounded today because `set_budget`/`set_status` are idempotent, but the invariant "single-use pending id" (`policy-engine.test.ts:100-103` tests it only sequentially) is not actually enforced under concurrency.
- **Recommendation:** Consume first: `update pending_operations set consumed_at = now() where id = $1 and organization_id = $2 and consumed_at is null and expires_at > now() returning *`; only the winner proceeds to `applyWrite`; on provider failure either re-open the row or write an `apply_failed` audit event. Scenario S-C1/C2 below.

### F8-04 — The shipped environment template enables self-approval by default
- **Severity:** P2 **Classification:** VERIFIED_CODE
- **Evidence:** `.env.example:48-49` `MARKTING_ALLOW_SELF_APPROVAL=true` (copied by `make env`, `Makefile`/README); schema default is `false` (`lib/markting/env.ts:16`); the check lives at `apply/route.ts:22-24`; README (both languages) says "single-user demos only".
- **Description:** The guard that prevents the requester from approving their own change is off in the default `.env`. Flipping `MARKTING_DEMO_MODE=false` for a real account while leaving this line untouched removes the segregation-of-duties control. Owner/admin role gating (`route.ts:19`) still applies.
- **Impact:** A single admin can propose (via the Assistant) and apply a real budget change with no second person.
- **Recommendation:** Default the template to `false` (or make demo-mode imply it), and add scenario S-A4 as a route test that asserts 403 when the creator applies with the flag unset.

### F8-05 — Zero route-level tests for `/api/approvals/[id]/apply` and `/reject`
- **Severity:** P2 (test coverage on the only human-approval surface) **Classification:** VERIFIED_TEST (cmd #9)
- **Evidence:** cmd #9 returns nothing; `apply/route.ts:17-24` carries five independent gates (session, `tools:write` scope, owner/admin role, org-scoped lookup incl. expiry, self-approval) and `reject/route.ts:11-14` three; none is exercised by any test. The nearest coverage is store-level (`database.integration.test.ts:278-299, 349-380`) and the pure bridge (`markting-bridge.test.ts:69-88`).
- **Impact:** The gates that make the chain "human-approved" can regress silently (e.g. the camel-case dependency of `row.createdBy` on `lib/db.ts:16`, or a refactor that drops `requireScope`).
- **Recommendation:** Scenarios S-A1..A9 below, implemented by invoking the route `POST` handlers directly with `vi.mock('@/lib/cloud/auth')` and in-memory/Postgres stores.

### F8-06 — Only the protected-account rule is re-checked at apply; budget caps are not
- **Severity:** P3 **Classification:** VERIFIED_CODE
- **Evidence:** `engine.ts:110-111` comment "Policy may have changed between validate and apply; re-check" followed by `checkStaticPolicy` only; `checkBudgetPolicy` runs only in `validate` (`engine.ts:62`). Org policy is editable at runtime (`database.integration.test.ts:317-322` shows `updateOrganizationSettings` persisting `protected_accounts`/`pending_ttl_minutes`). No test covers either re-check (`policy-engine.test.ts:71-76` tests protected accounts at validate only).
- **Impact:** Tightening `max_budget_delta_pct`/`max_daily_budget_micros` after a preview does not block apply within the 15-minute TTL (`policy.ts:19`). Bounded by TTL; still a documented-intent vs. code gap.
- **Recommendation:** Re-run `previewWrite` + `checkBudgetPolicy` at apply, or store a policy hash in the pending row and refuse on mismatch. Scenarios S-P1..P3.

### F8-07 — The translator ignores `after[].unit`; ARCHITECTURE.md says the bridge must use it
- **Severity:** P3 (latent) **Classification:** VERIFIED_CODE
- **Evidence:** `translate.ts:148-151` reads `after.value` only and multiplies by 1e6 (`toMicros`, `:86-92`); `docs/ARCHITECTURE.md` §4 step 2 ("using each `after[]` item's `unit`"); engine emits exactly one unit today, `write_policy.py:179`; fixtures carry it (`test/fixtures/engine-proposal.ts:13-14`, `test_demo_api.py:120-122`).
- **Impact:** Correct today by coincidence. If a future engine catalog entry emits `micros` or `cents`, a 10^6 or 10^4 error passes silently unless the policy cap or `MAX_DAILY_BUDGET_MICROS` (`translate.ts:84`) happens to catch it.
- **Recommendation:** Treat `unit` as part of the contract: accept only `'account currency per day'` (or `null`) and return `unsupported` otherwise. Scenario S-U1..U3.

### F8-08 — No currency assertion anywhere in the chain
- **Severity:** GAP (P3 if treated as defect) **Classification:** VERIFIED_CODE
- **Evidence:** `translate.ts:52-53` `currency?` "used for the human preview only" and never read in `translateProposal`; `proposalViewSchema` (`translate.ts:24-44`) has no currency field; `SANDBOX_ACCOUNTS` mixes USD and SAR (`sandbox-provider.ts:43-47`); the engine fixture budgets are USD.
- **Impact:** A recommendation computed in one currency can be applied as the same number in an account of another currency; the preview shows the account currency (`sandbox-provider.ts:158`) so a careful reviewer could notice, but nothing enforces it.
- **Recommendation:** Bind alias `currency` to the provider account's reported currency at preview and surface a mismatch as `unsupported`. Scenario S-U4.

### F8-09 — The Postgres sweep turns "expired" into "not found", so `PENDING_EXPIRED` is unreachable in the cloud
- **Severity:** P3 **Classification:** VERIFIED_CODE
- **Evidence:** `engine.ts:59` calls `sweep()` on every validate; `repository.ts:420-425` sweep sets `consumed_at` on expired rows; `repository.ts:397` `get` filters `consumed_at is null`; `engine.ts:88-89` comment says the expired entry must remain readable so the caller gets `PENDING_EXPIRED`; the dashboard route additionally filters `expires_at > now()` (`repository.ts:700`) and returns a generic 404 (`apply/route.ts:21`).
- **Impact:** Error-code fidelity only; the `PENDING_EXPIRED` test (`policy-engine.test.ts:115-130`) runs against the file store and does not represent cloud behaviour.
- **Recommendation:** Either make `get` return expired-but-unconsumed rows or accept and document `PENDING_NOT_FOUND`. Scenario S-T1..T3 should pin whichever is chosen.

### F8-10 — Provenance status `'expired'` is declared but never written
- **Severity:** P3 **Classification:** VERIFIED_CODE
- **Evidence:** `repository.ts:62` and migration `:51` allow `'expired'`; `markPendingOutcome` is called only with `'applied'` (`apply/route.ts:27`) and `'rejected'` (`reject/route.ts:21`) (cmd #10).
- **Impact:** `markting_engine_proposals` rows stay `pending` forever after their pending operation expires; any future reporting on "what the AI proposed vs. what happened" is wrong.
- **Recommendation:** A sweep (pg_cron or on page load) that marks provenance `expired` when the linked pending row is consumed-by-sweep. Scenario S-T3.

### F8-11 — Provider failure at apply is unhandled: no audit event, pending row stays applicable, retry semantics untested
- **Severity:** P3 **Classification:** VERIFIED_CODE
- **Evidence:** `engine.ts:113-123` has no `try/catch` around `applyWrite`; on throw, neither `audit.append` nor `pending.delete` runs; the route maps `PROVIDER_ERROR` to 502 (`lib/http.ts:17`) and skips `markPendingOutcome`. The only provider-level apply test is the success path (`markting-snapchat-wire.test.ts:72-80`).
- **Impact:** A timeout after the provider accepted the PATCH leaves a still-valid pending id; clicking Apply again re-sends the mutation. Audit shows `validated` only, so the operator cannot tell a failed apply from an untried one.
- **Recommendation:** `apply_failed` audit event with the provider error class; decide explicitly whether a failed pending id remains usable. Scenarios S-F1..F4.

### F8-12 — Rejecting an already-terminal proposal on the engine is an unhandled 500 and is untested at the host level
- **Severity:** P3 **Classification:** VERIFIED_CODE
- **Evidence:** `engine/src/paid_media_agent/tools/writes.py:498-511` `reject` calls `transition()` without catching `InvalidTransition` (contrast `mark`, `:574-577`); `surfaces/api/app.py:126-138` catches only `WriteDenied` → 409; `engine-client.ts:101-106` maps 500 → `'upstream'`; `bridge.ts:98-105` swallows it. `test_demo_api.py` rejects once (`:136-144`) and never a second time (cmd #12).
- **Impact:** Works by accident of the swallow; a future change to `handoff` (e.g. surfacing the error) would break the happy path, and no test would warn.
- **Recommendation:** Host test: reject twice → first 200, second 500 (or 409 if the host wraps it); bridge test: `rejectOnEngine` throwing `EngineError(500,'upstream')` still yields `pending`. Scenario S-E2.

### F8-13 — Database suites are gated on env presence, so CI would silently skip them and a stale `.env.local` fails them
- **Severity:** P3 **Classification:** VERIFIED_RUNTIME (cmd #3 exit 1, cmd #4 exit 0) + VERIFIED_CODE
- **Evidence:** `test/setup-env.ts:1-8`; `vitest.config.ts:5` loads `.env.local`; `markting-repository.database.test.ts:13`.
- **Impact:** 16 DB tests (4 markting) never run in a CI job that forgets the Supabase service, and the job stays green.
- **Recommendation:** The CI job must set `ADPORT_RUN_DATABASE_TESTS=1` explicitly and fail if the service is absent (§CI layout).

### F8-14 — Minor ordering issue: provenance is recorded before the scope check
- **Severity:** P3 **Classification:** VERIFIED_CODE
- **Evidence:** `bridge.ts:60-66` records `unsupported` rows for any caller; the `tools:write` check is at `:68`.
- **Impact:** Reader-plan / viewer users can populate `markting_engine_proposals` (bounded, no write path). Not tested.
- **Recommendation:** Move the scope check above the record, or accept and test it explicitly (S-A8).

### F8-15 — `listPendingOperations(…, 200)` caps the apply/reject lookup
- **Severity:** P3 **Classification:** VERIFIED_CODE
- **Evidence:** `apply/route.ts:20`, `reject/route.ts:13`; `repository.ts:696-703` orders by `created_at desc limit`.
- **Impact:** The 201st-oldest open pending row cannot be applied or rejected from the dashboard (edge case; TTL makes it unlikely).
- **Recommendation:** Look up by `(id, organization_id)` directly.

## Proposed CI layout

Single root workflow `.github/workflows/ci.yml` (none exists today). Four jobs, `concurrency: ci-${{ github.ref }}`, `permissions: contents: read`, triggers `push: [main]`, `pull_request`, `workflow_dispatch`. Path filters are optional; the whole run is under ~10 minutes.

### Job 1 — `platform` (adport + markting cloud, with a real Supabase)
- `runs-on: ubuntu-latest`, `defaults.run.working-directory: platform`, Node 22 only (the upstream 22/24 matrix is unnecessary here; `platform/package.json` engines say ≥22.13).
- Steps: `pnpm/action-setup`, `setup-node` with pnpm cache, `pnpm install --frozen-lockfile`, `pnpm build` (turbo `test` depends on `build`, `turbo.json:9-11`), `pnpm typecheck`.
- Start Supabase with the CLI (a plain `postgres` service container is not enough: migrations need `auth.users`, pg_cron and the `adport_backend` role — README "Why Supabase outside docker-compose"): `npx supabase start -x studio,imgproxy,inbucket,edge-runtime,logflare,vector` in `platform/`, then export `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`, `SUPABASE_SECRET_KEY`, `SUPABASE_DB_URL` from `npx supabase status -o env` (ports 553xx per `platform/supabase/config.toml`). Reuse `infra/scripts/sync-supabase-env.mjs` if it already does this mapping.
- **Set `ADPORT_RUN_DATABASE_TESTS=1` explicitly** so a missing database fails instead of skipping (F8-13). Add a one-line preflight `psql "$SUPABASE_DB_URL" -c 'select 1 from public.markting_engine_proposals limit 0'` to prove the markting migration applied.
- `pnpm test` (turbo: core 41 + cloud 308 + DB suites + provider packages).
- Upload `vitest` JUnit output as an artifact; keep the upstream "CLI smoke" step (`platform/.github/workflows/ci.yml:33-45`) because it exercises the file-backed `PendingStore`.

### Job 2 — `engine` (paid-media-agent + markting host)
- `working-directory: engine`, `astral-sh/setup-uv`, Python 3.11 and 3.13 matrix as upstream (`engine/.github/workflows/ci.yml:13-16`).
- `uv sync --frozen --all-extras --dev`, `ruff check .`, `ruff format --check .`, `mypy src`, `pytest -q` (upstream offline suite), **plus** `uv run --frozen python -m pytest -q ../services/engine-demo/tests` (the host contract, `test_demo_api.py:4-5` documents this invocation) and `uv run --frozen paid-media-agent demo --with-proposal`.
- Carry over the Gitleaks job verbatim with `fetch-depth: 0` from the repo root (the nested `.gitleaks.toml` path must be adjusted to `engine/.gitleaks.toml`).

### Job 3 — `infra` (node scripts)
- Root `working-directory`, Node 22, `cd infra && npm ci` (or `pnpm` if the lockfile is added), `node --test infra/scripts/*.test.mjs`, `node --check infra/seed/seed-demo.mjs infra/scripts/*.mjs`, `docker compose -f docker-compose.yml config -q` (validates the compose file without building; builds are out of scope for CI until a registry is chosen).

### Job 4 — `bridge-contract` (cross-stack, new)
- Needs: `engine` (`uv sync`) and `platform` (`pnpm install`) caches.
- Start the host offline: `cd engine && MARKTING_ENGINE_MODE=demo PAID_MEDIA_API_TOKENS=ci-token:adport-bridge PAID_MEDIA_APPROVAL_SIGNING_KEY=<32 bytes> PAID_MEDIA_DATA_MODE=sample uv run --frozen python ../services/engine-demo/serve_demo.py &` and wait for `GET /health`.
- Run a new vitest file `platform/apps/cloud/test/markting-contract.engine.test.ts`, gated on `MARKTING_CONTRACT_ENGINE_URL`, that: sends "Reduce the Performance Max budget to 240" through `EngineClient`, asserts the returned proposal parses with `proposalViewSchema` and `translateProposal(…, SANDBOX_ALIASES).status === 'ok'` with `daily_budget_micros: 240_000_000` (S-H8), rejects it twice and asserts the second status (S-E2), then restarts the host process and asserts `/proposals/{id}` → 404 and `/reject` → 409 `unknown_proposal` (S-E1).
- This job is the only place where engine-side schema drift (new platform enum value, new `unit`) is caught before it reaches `translate.ts`.

### Repository hygiene for the layout
- Remove or neutralise `platform/.github/workflows/*.yml` and `engine/.github/workflows/*.yml` (they cannot run where they are; keeping them invites the false belief that CI exists).
- Make `make test` call the same four commands the workflow runs so local and CI are identical; today it omits `@adport/core` and the DB suites (`Makefile:51-54`).
- Add `platform/apps/cloud/.env.local` guidance to `docs`: when present with a stopped Supabase, `pnpm test` fails (cmd #3).

## What a world-class system would need (gaps, concrete)

1. **Idempotent bridging.** Key pending creation on `(organization_id, proposal_id, revision)`; return the existing open row instead of creating another (F8-02). Add a partial unique index `markting_engine_proposals (pending_operation_id) where status = 'pending'` and a test that `bridgeProposal` twice yields one `pending_operations` row.
2. **Atomic consume-then-apply.** Conditional `update … returning` before `applyWrite`, `apply_failed` audit event, documented retry policy (F8-03, F8-11); a `Promise.all` test with a counting provider stub.
3. **Full policy re-evaluation at apply** or a policy fingerprint in the pending row (F8-06), plus provenance `expired` sweep (F8-10).
4. **Contract-level unit/currency checks** in `translateProposal` (F8-07, F8-08) with property-based tests (fast-check) over amounts and units.
5. **Route-handler tests** for the two approval routes and the assistant route with `vi.mock('@/lib/cloud/auth')`, covering S-A1..A9, S-X1, S-C4, S-T2 — the human gate is currently the least-tested link in the chain.
6. **Cross-stack contract job** (Job 4) so the hand-written `engine-proposal.ts` fixture cannot silently diverge from what `serve_demo.py` actually emits.
7. **Chaos cases for the hand-off**: engine 500/409/timeout and restart between proposal and reject (S-E1, S-E2, S-E6), asserting the adport row count never changes.
8. **Coverage gate** (`vitest --coverage` thresholds) on `platform/apps/cloud/lib/markting/**` and `platform/packages/core/src/policy/**`, since these files are the single write path.
9. **Secure defaults in templates**: `MARKTING_ALLOW_SELF_APPROVAL=false` in `.env.example` with demo-mode opt-in (F8-04).
