## Findings

### B7-01 — Only a 3-stage funnel exists; landing and add-to-cart stages are absent everywhere
- Severity: GAP  Classification: VERIFIED_CODE
- Evidence: `platform/packages/core/src/model.ts:1-12` (`METRICS = spend, impressions, clicks, conversions, conversion_value, ctr, cpc, cpm, cpa, roas`); `engine/src/paid_media_agent/domain/metrics.py:56-66` (`PerformanceRow` = spend/impressions/clicks/conversions/conversion_value only); `engine/src/paid_media_agent/tools/compute.py:76-92` (funnel math: `ctr = clicks/impressions`, `cvr = conversions/clicks`, `cpa = spend/conversions`, `roas = value/spend`).
- Description: The canonical metric vocabulary in both stacks is impressions → clicks → conversions(+value). There is no field, column, or computed stage for landing-page views, add-to-cart, or initiate-checkout. The funnel the task asks about (impressions→clicks→landing→add-to-cart→purchase) is physically representable only as impressions→clicks→purchase.
- Impact: No mid-funnel diagnosis is possible (e.g. "clicks are fine but landing-page drop-off is high" cannot be expressed or detected). CVR is click→conversion only, hiding where in the on-site journey users are lost.
- Recommendation: Add optional funnel-stage fields (`landing_page_views`, `add_to_cart`, `initiate_checkout`) to `MetricName` / `PerformanceRow`, map them per provider where the API exposes them, and keep them nullable so absence stays missing (not zero).

### B7-02 — No on-site / landing-page data is reachable in structured form; GA4 is an unnormalized blob
- Severity: GAP  Classification: VERIFIED_TEST
- Evidence: `engine/src/paid_media_agent/tools/normalize.py:14-26` (`PERFORMANCE_PLATFORMS = frozenset(_SPEND_KEYS)` = GOOGLE_ADS, META_ADS, REDDIT_ADS, LINKEDIN_ADS, X_ADS, OPENAI_ADS only — `google_analytics` excluded); `engine/src/paid_media_agent/tools/reads.py:241` (normalize only when `entry.platform in PERFORMANCE_PLATFORMS`); `reads.py:304-320` (all other platforms, GA4 included, stored as raw `provider_result`); `engine/tests/unit/test_pipeboard_catalog.py:98` asserts `result.artifact_kind == "provider_result"` with the comment "GA4 sessions are not ad-spend rows" (test passes). Skill guidance `engine/workspace/skills/paid-media-analysis/SKILL.md:35` forbids treating GA4 conversions as ad-attributed.
- Description: GA4 is the only possible source of on-site / landing-page / add-to-cart data, and it reaches the agent only as an opaque `provider_result` JSON artifact. It is never normalized, never schema-validated into funnel rows, and never joined to ad rows; the skill explicitly tells the model not to merge it with spend. So landing-page and add-to-cart signals are not structurally reachable by the analytics layer.
- Impact: Any "landing page" or "add to cart" funnel analysis depends entirely on the LLM free-reading an unstructured GA4 blob, with no guaranteed fields, no join key to campaigns, and a standing instruction not to attribute it. Effectively MISSING as a system capability.
- Recommendation: If on-site funnel is a product goal, build a dedicated GA4 normalizer (sessions, landing-page-path, add-to-cart, begin-checkout, purchase) with an explicit, documented non-attribution join (e.g. channel/UTM) rather than leaving it as a raw artifact.

### B7-03 — Meta fetches full-funnel action data from the API, then discards all of it except purchases
- Severity: P3  Classification: VERIFIED_CODE
- Evidence: `platform/packages/meta/src/provider.ts:174` (requests `actions` and `action_values` arrays); `meta/src/provider.ts:201-203` (`conversions = actionValue(row.actions, 'omni_purchase')`, `conversionValue = actionValue(row.action_values, 'omni_purchase')`); `meta/src/provider.ts:591-594` (`actionValue` returns a single action-type value). The `actions[]` array Meta returns also carries `landing_page_view`, `add_to_cart`, `initiate_checkout`, etc., none of which are read.
- Description: For Meta the raw mid-funnel data is already on the wire (one API field set away) but `toReportRow` extracts only `omni_purchase`. This is the one provider where adding landing/ATC would cost no extra API round-trip.
- Impact: Available funnel detail is thrown away for the richest provider; not a correctness bug, but a concrete, cheap capability left on the table.
- Recommendation: Extract additional `action_type`s from the already-fetched arrays into new optional metric fields.

### B7-04 — Cross-platform funnel aggregation sums incompatible conversion definitions
- Severity: P2  Classification: VERIFIED_CODE
- Evidence: conversion definitions differ per provider — Google `metrics.conversions` (all configured conversion actions) `platform/packages/google/src/provider.ts:31`; Microsoft `Conversions` (generic) + `Revenue` `microsoft/src/provider.ts:179,227-228`; Meta `omni_purchase` `meta/src/provider.ts:202`; Snapchat `conversion_purchases` `snapchat/src/provider.ts:14`; Pinterest `TOTAL_CHECKOUT` `pinterest/src/provider.ts:17`; Reddit purchase clicks + views `reddit/src/provider.ts:230`; LinkedIn `externalWebsiteConversions` `linkedin/src/provider.ts:7`; Apple `totalInstalls` `apple/src/provider.ts:199`; Spotify `PURCHASES` `spotify/src/provider.ts:16`. The engine then sums `conversions`/`conversion_value` across all platforms (`engine/src/paid_media_agent/tools/compute.py:280-295`) and computes a single cross-platform CVR/CPA/ROAS.
- Description: One field named `conversions` holds purchases for some platforms, generic all-conversions for Google/Microsoft, and app installs for Apple. Summing them and deriving portfolio CPA/ROAS mixes non-comparable events; Apple installs have no revenue so they also drag blended ROAS. Nothing in the normalized row records which event each conversion count represents.
- Impact: Blended funnel KPIs (portfolio CVR, CPA, ROAS) can be materially misleading, and these KPIs drive budget-reallocation recommendations — a financial-interpretation risk.
- Recommendation: Carry a per-row `conversion_event`/`conversion_kind` tag and refuse (or clearly segment) cross-platform aggregation across differing event kinds; the `source_fields` dict already preserves the raw payload to back this.

### B7-05 — Engine normalizes a funnel for only 6 of its 10 platforms; TikTok/Pinterest/Snap/GA4 reads carry no structured funnel
- Severity: P2  Classification: VERIFIED_CODE
- Evidence: `engine/src/paid_media_agent/domain/common.py:13-22` (10 platforms incl. TIKTOK_ADS, PINTEREST_ADS, SNAP_ADS, GOOGLE_ANALYTICS); `engine/src/paid_media_agent/tools/normalize.py:14-26` (`_SPEND_KEYS`/`PERFORMANCE_PLATFORMS` cover only GOOGLE_ADS, META_ADS, REDDIT_ADS, LINKEDIN_ADS, X_ADS, OPENAI_ADS); `reads.py:241,304-320` (anything outside that set is written as raw `provider_result`, not `performance_rows`).
- Description: In the engine (Python/agent) stack, reads for TikTok, Pinterest, and Snapchat — which the adport TS stack *does* normalize — fall through to the raw-blob branch. Their funnel rows are never turned into `PerformanceRow`, so engine-side compute/compare tools (`compute.py`) cannot operate on them.
- Impact: The engine agent cannot compute ctr/cvr/cpa/roas or run deltas for TikTok/Pinterest/Snap even though those platforms report the needed fields; funnel analysis for them is only as good as the LLM reading an unstructured blob. This contradicts any claim of uniform cross-platform funnel analytics.
- Recommendation: Either add verified spend-unit mappings for TikTok/Pinterest/Snap to `_SPEND_KEYS`, or document explicitly that the engine funnel layer is scoped to the 6 direct-adapter platforms.

### B7-06 — `normalize.py` treats a generic "results" field as purchases
- Severity: P3  Classification: VERIFIED_CODE
- Evidence: `engine/src/paid_media_agent/tools/normalize.py:27` (`_CONVERSION_KEYS = ("conversions", "purchases", "results")`); line 130 reads the first present key into `conversions`.
- Description: "results" is a generic optimization-outcome count (whatever the campaign optimizes for — leads, installs, video views), not necessarily purchases. If a raw row carries `results` and not `conversions`/`purchases`, it is silently promoted to the purchase-stage `conversions` field and flows into CPA/ROAS.
- Impact: Potential conflation of a non-purchase optimization event with purchases. Not currently reachable for the fixtures of the 6 normalized platforms (none emit `results`), so impact is latent, hence P3.
- Recommendation: Drop `results` from the purchase key list, or gate it behind a known conversion-event tag.

### B7-07 — X funnel ends at clicks (no conversion/value stage); Apple has no revenue stage
- Severity: EXISTS_BUT_LIMITED (capability)  Classification: VERIFIED_CODE
- Evidence: `platform/packages/x/src/provider.ts:8` (`BaseMetric = 'spend' | 'impressions' | 'clicks'`), `x/src/provider.ts:35` ("conversion normalization is not yet verified" — request rejected if conversion metrics asked); `platform/packages/apple/src/provider.ts:198-199` ("Apple has taps, not clicks; installs are the conversion event. No revenue metric exists."), conversion_value never set.
- Description: X exposes only impressions→clicks (CPM/CPC/CTR), no purchase stage at all. Apple exposes impressions→taps→installs but no revenue, so ROAS is undefined for Apple.
- Impact: Portfolio funnel/ROAS silently omits X (no conversions) and Apple (no value); blended denominators include their spend but not their outcomes unless excluded.
- Recommendation: Flag these platforms as funnel-incomplete in reporting so blended ROAS/CPA are not computed over their spend.

## What a world-class system would need (gaps, concrete)
- Explicit multi-stage funnel in the row model with nullable stages: impressions, clicks, landing_page_views, view_content, add_to_cart, initiate_checkout, add_payment_info, purchase — each tagged with the native event it came from and whether click- or view-attributed.
- Per-provider mapping of the above to native fields where exposed (Meta `actions[]`, Google conversion-action segmentation, TikTok `web_event_*`, Pinterest `TOTAL_ADD_TO_CART`/`TOTAL_CHECKOUT`, Snap `conversion_add_cart`), plus honest "not exposed" for the rest.
- A first-party on-site/analytics ingestion (GA4 and/or store webhooks) normalized into funnel rows with a documented, non-silent attribution join to campaigns.
- Guardrails that forbid blending conversion counts/values across incompatible event definitions, and funnel-completeness flags per platform (X, Apple).
- Stage-to-stage conversion rates (click→LP, LP→ATC, ATC→purchase) so drop-off can be localized, not just a single click→conversion CVR.

## Disagreements / claims in docs that the code contradicts
- `platform/docs/providers/pinterest.md` states "Conversion semantics are checkouts, not every conversion event" — consistent with code (`pinterest:17` `TOTAL_CHECKOUT`); disclosed but means Pinterest reports only one point of the funnel and no add-to-cart.
- `engine/workspace/skills/paid-media-analysis/SKILL.md:27,35` presents GA4 as an available analysis source; the code confirms GA4 is only an unnormalized `provider_result` the skill itself tells the model not to attribute — so any implication of integrated on-site funnel analysis is not backed by structured code (B7-02). No code-level doc claims landing-page or add-to-cart coverage; those are GAPs rather than contradicted claims.
