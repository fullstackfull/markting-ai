## Findings

### H6-01 — No automated backup or restore for any data store
- **Severity:** P1
- **Classification:** VERIFIED_CODE (absence across the whole repo) + DOCUMENTED_ONLY (acknowledged as a gap)
- **Evidence:** `find ... -iname "*backup*"/"*restore*"/"*pg_dump*"` → 0 matches repo-wide; `docker-compose.yml:78-80` declares `engine-workspace` and `engine-pgdata` as plain Docker named volumes with no backup sidecar; `Makefile` has `env/up/down/seed/test` targets only — no `backup`/`restore`; `platform/.github/workflows/*.yml` has no backup step; `docs/TODO.md:20` lists "Postgres **with backups** for `pma_*` and LangGraph checkpoints" as still-open engine work; `platform/docs/deployment-model.md:52` lists "backup policy" and `:58` "restore … runbooks tested before launch" as unmet production gates.
- **Description:** There is no backup mechanism — no `pg_dump`/WAL/PITR config, no volume snapshot job, no object-store export — for (a) the Supabase/adport database, (b) the engine Postgres (`engine-pgdata`), or (c) the engine workspace volume (`engine-workspace`, which holds generated reports and logs). The only scheduled DB jobs *delete* data (see H6-04). Backup is deferred entirely to an unwritten operator runbook.
- **Impact:** Any loss of a DB volume or the host loses all tenant configuration, encrypted provider credentials, approvals/receipts, and audit history with zero recovery path. RPO/RTO are undefined and unbounded.
- **Recommendation:** For the cloud DB in production, rely on hosted Supabase automated daily backups + PITR and document the retention/restore procedure. For the engine Postgres, add scheduled logical dumps (or managed Postgres with PITR) covering `pma_*` and the LangGraph `checkpoints*` tables. Treat `engine-workspace/out` reports as either reproducible (document that) or back them up to object storage.

### H6-02 — Master encryption key has no escrow/KMS and is unrecoverable; a DB restore is useless without it
- **Severity:** P1
- **Classification:** VERIFIED_CODE + DOCUMENTED_ONLY
- **Evidence:** `platform/apps/cloud/lib/crypto.ts:5-9` derives a single 32-byte key straight from `env().ADPORT_CLOUD_ENCRYPTION_KEY`; `platform/apps/cloud/lib/env.ts:11` requires it as a plain string; `infra/scripts/fill-env.mjs:9` generates it with `randomBytes(32)` into `.env`; `.gitignore:2-4` keeps `.env` untracked (no escrow). `private.provider_credentials.ciphertext` (`20260817171039_cloud_initial_schema.sql:73-77`) stores AES-256-GCM ciphertext of OAuth refresh tokens, decryptable only with that exact key. `platform/docs/deployment-model.md:44-45` itself says the local env key "is not the intended production key-delivery mechanism" and that production "must provide that value through a managed secret/KMS boundary … define rotation and recovery procedures" — i.e. KMS/escrow is prescribed but not implemented.
- **Description:** Credential confidentiality rests on a single symmetric key living in an env var / `.env`. There is no KMS integration, no key escrow, and no copy stored separately from the operator's environment. A DR backup of the database alone is non-restorable: without the matching `ADPORT_CLOUD_ENCRYPTION_KEY`, every `provider_credentials.ciphertext` and `oauth_transactions.verifier_ciphertext` is permanently undecryptable. Conversely, if the key is captured in the same backup as the DB, the backup leaks all tenant credentials in plaintext-equivalent form.
- **Impact:** Loss of the key = irreversible loss of every tenant's ad-platform credentials (reconnect required for all orgs). A credential-confidentiality vs. recoverability tension that no documented procedure resolves.
- **Recommendation:** Move the key to a KMS/secret manager with its own backup and access policy; document that DR restore requires recovering the key version(s) separately from the DB; record which key version each ciphertext was written with (see H6-03).

### H6-03 — Key rotation is documented and schema-provisioned but not implemented (rotation would destroy all ciphertext)
- **Severity:** P2
- **Classification:** DOCUMENTED_NOT_IMPLEMENTED
- **Evidence:** `platform/docs/deployment-model.md:45` prescribes "define rotation and recovery procedures, and record the key version stored with each ciphertext." The schema provides for it: `provider_credentials.key_version integer not null default 1 check (key_version > 0)` (`20260817171039_cloud_initial_schema.sql:76`). But `platform/apps/cloud/lib/crypto.ts:5-27` reads exactly one key and the ciphertext envelope `v1` is a *format* version, not a key version; `platform/apps/cloud/lib/cloud/repository.ts:162` hardcodes `key_version = 1` on every write; `rg key_version platform --type ts` finds no code that *reads* `key_version` to select a decryption key. No re-encryption/rotation script exists anywhere.
- **Description:** The groundwork (a `key_version` column) exists, but there is no multi-key decryption path and no bulk re-encrypt tool. Rotating `ADPORT_CLOUD_ENCRYPTION_KEY` in place makes every stored ciphertext fail its GCM auth tag — effectively a self-inflicted data-loss event — because old ciphertext cannot be read with the new key and nothing re-wraps it.
- **Impact:** Key rotation — a core DR/security control — cannot be performed safely. A compromised key cannot be rotated out without forcing every tenant to reconnect.
- **Recommendation:** Implement envelope rotation: keep a keyring keyed by `key_version`, write new ciphertext at the current version, and provide a re-encrypt job that reads old versions and rewrites to the new one. Only then is `key_version` meaningful.

### H6-04 — The only scheduled data job deletes records irreversibly, and with no backup there is no recovery
- **Severity:** P2
- **Classification:** VERIFIED_CODE
- **Evidence:** `private.apply_data_retention()` (`20260828120000_cloud_plans_and_account_scope.sql:131-164`) hard-`delete`s `audit_events`, `pending_operations`, `findings`, `deletion_requests` older than `data_retention_days`, plus fixed-interval purges of `oauth_transactions`, `rate_limit_buckets`, `billing_events`; scheduled daily at 03:17 via `cron.schedule('adport-data-retention', '17 3 * * *', …)` (`20260817171039_cloud_initial_schema.sql:408`). Default retention was lowered 90→30 days (`docs/ARCHITECTURE.md:354`).
- **Description:** Audit/compliance and operational records are permanently deleted on a schedule. Because no backup exists (H6-01), the effective RPO for audit history is "whatever the daily purge last removed," and deleted rows are unrecoverable.
- **Impact:** A compliance/forensic gap: after a security incident, audit evidence older than `data_retention_days` is gone with no restore option. Also no protection against an accidental/malicious early purge.
- **Recommendation:** Ensure PITR/backups predate and outlive the retention window; consider exporting audit events to an append-only store before deletion.

### H6-05 — Engine data volumes and generated reports are ephemeral, unversioned, and undocumented for restore
- **Severity:** P3
- **Classification:** VERIFIED_CODE
- **Evidence:** `docker-compose.yml:78-80` — `engine-workspace` (mounted `/app/workspace`) and `engine-pgdata` (`/var/lib/postgresql/data`) are plain named volumes. Reports render to `workspace/out` (`engine/src/paid_media_agent/tools/reports.py` → `artifacts.root / "out"`; dirs `engine/workspace/out`, `engine/workspace/logs`). Engine schema is created at runtime via `SCHEMA_SQL` `CREATE TABLE IF NOT EXISTS pma_*` in `engine/src/paid_media_agent/persistence/postgres.py:11-62` and LangGraph tables via `AsyncPostgresSaver.setup()` (`engine/src/paid_media_agent/runtime/self_hosted.py:45-62`); there is no migration framework or schema-version table (`find engine -iname "*migration*"` excl .venv → 0).
- **Description:** The engine's durable state (proposals, approval claims, receipts, dedupe keys, thread ownership, and LangGraph checkpoints) and its generated artifacts live in container-local volumes with no snapshot/export. Schema is idempotent-at-boot, so a logical restore would recreate tables, but there is no documented dump/restore procedure and no version pinning to detect checkpoint-format drift across LangGraph upgrades.
- **Impact:** Removing the engine container/volume (common on redeploy) loses in-flight proposals and checkpoints; reports must be regenerated. Low direct harm (proposal-only demo writer, previews reproducible) but real for a self-hosted production engine.
- **Recommendation:** Document whether `workspace/out` is reproducible; if not, back it up. For the engine DB, add logical dumps and pin the LangGraph checkpoint schema version for restore validation.

### H6-06 — No RPO/RTO targets and no tested restore drill exist
- **Severity:** GAP
- **Classification:** NOT_VERIFIED (absence) + DOCUMENTED_ONLY
- **Evidence:** No RPO/RTO string anywhere (`rg -i "rpo|rto"` finds only this audit scope). `platform/docs/deployment-model.md:58` names "restore … runbooks tested before launch" as an unmet gate; `README.md` makes no DR claim.
- **Description:** There is no recovery-point/recovery-time objective, no restore runbook, and no evidence any restore has ever been exercised.
- **Impact:** DR readiness is unknowable; a real outage would be an improvised recovery.
- **Recommendation:** Define RPO/RTO per store, write a restore runbook (DB + matching key version), and run a drill that restores into a scratch project and decrypts a sample credential.

## What a world-class system would need (gaps, concrete)
1. Managed Postgres with daily automated backups + PITR (WAL) for both the cloud DB and the engine DB, with retention longer than `data_retention_days`.
2. A KMS-held master key with its own backup/rotation lifecycle; each ciphertext tagged with the `key_version` actually used, and a multi-key decryption path plus a bulk re-encrypt job (make H6-03 real).
3. A documented, scripted restore runbook that restores the DB and the matching key version together, and a scheduled restore *drill* into a scratch environment that proves a sample credential still decrypts.
4. Object-storage backup (or an explicit "reproducible, not backed up" decision) for `workspace/out` reports; versioned checkpoint schema so LangGraph upgrades do not silently break restore.
5. Defined RPO/RTO per data class (credentials: near-zero RPO; audit: bounded by compliance), and an append-only audit export so the retention purge (H6-04) never destroys the only copy.
6. Separation of backup custody from the key, so a single backup can neither be useless (missing key) nor a plaintext-equivalent credential leak (key bundled in).

## Disagreements / claims in docs that the code contradicts
- `platform/docs/deployment-model.md:45` implies ciphertext records a usable key version for rotation; the code hardcodes `key_version = 1` (`repository.ts:162`) and never reads it to select a key (`crypto.ts:5-27`), so documented rotation is not achievable with current code — a DOCUMENTED_NOT_IMPLEMENTED mismatch (H6-03).
- No doc overstates backup existence: `docs/TODO.md:20` and `deployment-model.md:52,58` correctly flag backups/restore runbooks as *not done*. README/UPSTREAM make no DR claim to contradict. (So the documentation is honest about this gap; the risk is operational, not a doc overclaim.)
