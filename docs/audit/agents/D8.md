## Findings

### D8-01 — Engine report surface is shared across all tenants (listing, download, run)
- **Severity:** P1 (cross-tenant by construction; today the content is synthetic fixture data, which is the only reason this is not P0)
- **Classification:** VERIFIED_CODE
- **Evidence:**
  - `platform/apps/cloud/app/api/reports/engine/route.ts:16-24` — `GET` authenticates the session for the requested org (`sessionPrincipal(organizationId)`) and then returns `engineClient().listReports()` unfiltered.
  - `platform/apps/cloud/app/api/reports/engine/[name]/route.ts:13-15` — any member of any organization can stream any `rpt_*`/`art_*` file by name.
  - `platform/apps/cloud/app/api/reports/engine/route.ts:27-36` — `POST` runs a report; the org id is used for membership and rate limiting only and is never passed to the engine.
  - `services/engine-demo/serve_demo.py:246-249, 263-264, 304-306` — one index file `workspace/out/markting-reports.json` for the whole process; `serve_demo.py:355-358` — `GET /reports` returns the whole index after only checking the bearer; `serve_demo.py:360-374` — `GET /reports/files/{name}` checks only bearer + filename pattern; `serve_demo.py:283` — `requested_by` is the caller_ref (`adport-bridge` for every tenant, `docker-compose.yml:49`).
  - `services/engine-demo/serve_demo.py:275` — the report is computed over `runtime.profile.accounts`, the engine's single configured account set, not the tenant's accounts.
  - `platform/apps/cloud/app/dashboard/reports/page.tsx:10,20` and `engine-reports.tsx:20-29` — the UI presents this global list inside a tenant's dashboard as that tenant's reports.
  - Synthetic-only today: `serve_demo.py:163-166` refuses to boot unless `PAID_MEDIA_DATA_MODE == "sample"`, and `serve_demo.py:386` forces `sample` in live model mode.
- **Description:** The report surface has no tenant dimension at any layer: no org in the index entries, no org in file names, no org in the engine request, no filtering on the platform. Tenant A can see when Tenant B ran a report, what window it covered, its summary numbers, and download the HTML/PDF/JSON. Isolation is not even a convention here; it is absent.
- **Impact:** Cross-tenant visibility of report metadata and files. Because the engine is pinned to fixture data, the leaked content is synthetic and identical for every tenant, so the practical exposure today is metadata (who ran what, when) plus the shared summary. If the fail-closed check at `serve_demo.py:163` is ever relaxed, this becomes a straightforward P0 data leak.
- **Recommendation:** Give the report run an `organization_id` (pass it from the platform, store it in the index entry and in a per-org directory under `out/<org>/`), filter `GET /reports` on the platform by org, and have `GET /reports/files/{name}` verify the file belongs to an entry owned by the requesting org. Record an adport audit event per run (`recordAudit`) so the tenant's audit log has attribution instead of `requested_by: adport-bridge`.

### D8-02 — One engine identity for every tenant: engine-side ownership and visibility checks are tautological; isolation rests on the thread-id convention
- **Severity:** P2
- **Classification:** VERIFIED_CODE
- **Evidence:**
  - `docker-compose.yml:49` — `PAID_MEDIA_API_TOKENS: ${MARKTING_ENGINE_TOKEN}:adport-bridge`; `platform/apps/cloud/lib/markting/env.ts:11-12`, `assistant.ts:12-15` — the platform holds exactly one token.
  - `engine/src/paid_media_agent/surfaces/runner.py:86-89` — thread ownership is first-caller-wins on `caller_ref`; `persistence/postgres.py:39-42, 237-244` — `pma_thread_owners(thread_id, caller_ref)`; with one caller every thread is owned by `adport-bridge`, so `ThreadAccessDenied` (`app.py:97-100`) can never fire between tenants.
  - `engine/src/paid_media_agent/surfaces/api/app.py:103-109` — `GET /proposals/{id}` is visible when `view.requester_ref == who`; every proposal is requested by `adport-bridge`, so every tenant's proposal is visible to the bridge token by UUID. (The platform currently never calls `getProposal`; `engine-client.ts:118-120` is dead code for routes.)
  - `engine/src/paid_media_agent/surfaces/api/app.py:126-138` and `tools/writes.py:498-511` — `POST /proposals/{id}/reject` has no actor check at all; any valid bearer rejects any proposal (already noted in `docs/ARCHITECTURE.md:824`).
  - Compensating controls on the platform: `platform/apps/cloud/lib/markting/assistant.ts:34-38` — regex `^org_<uuid>__u_<uuid>__<suffix>$`, `startsWith(org_${org}__u_${user}__)`, then `claimThread`; `lib/markting/repository.ts:17-27` — `insert … on conflict (id) do update … where organization_id = $org and (user_id is null or user_id = $user)`; returns false (→ 403) when the row belongs to someone else. `recordEngineProposal` keys provenance by `(organization_id, proposal_id, revision)` (`repository.ts:84`, migration `:56`).
  - LangGraph conversation state lives in the engine Postgres keyed only by `thread_id` (`engine/src/paid_media_agent/runtime/self_hosted.py:45-53`, `serve_demo.py:219,228-230`).
- **Description:** The engine is tenant-blind. Every isolation property for conversations is enforced in one place — `assistant.ts:34-38` + `claimThread` — and depends on the thread-id *format* (`org_<org>__u_<user>__…`) being generated and checked correctly by the platform. Anything else that holds `MARKTING_ENGINE_TOKEN` (another service, an operator with `.env`, a future route that forwards a client-supplied thread id or proposal id without the same checks) has full read/write access to every tenant's threads and proposals on the engine. README:128 and PHASE1:44 state this honestly; it remains a single point of failure.
- **Impact:** No defense in depth for conversation data; a single missed check in the platform exposes every tenant's chat history and proposals. The `proposal.state === 'awaiting_approval'` object bridged into adport comes from the engine response for the caller's own thread (`assistant.ts:43,50-51`), so there is no *current* cross-tenant path; the risk is structural.
- **Recommendation:** Either (a) one engine token per organization (the engine already supports `token:caller,…` pairs, `config.py:258-267`) with the platform selecting the token by `principal.organizationId`, or (b) propagate an `X-Organization-Id` header into the engine host and have `serve_demo.py` namespace thread ownership, proposal visibility and reports by it. Add a test in `test_demo_api.py` with two callers to pin the engine-side behaviour, and a platform test for `runAssistantTurn` rejecting a foreign thread id (none exists today; only `markting-engine-client.test.ts:18-20` touches the id format).

### D8-03 — Server role bypasses RLS on every tenant table; isolation is a per-query `where organization_id` convention with no second layer
- **Severity:** P2
- **Classification:** VERIFIED_CODE
- **Evidence:**
  - `platform/supabase/migrations/20261002000000_markting_bridge.sql:83-89` — `create policy … for all to adport_backend using (true) with check (true)` on all four markting tables; `20260817171039_cloud_initial_schema.sql:319-327, 338-341` — same for every upstream tenant table.
  - `platform/apps/cloud/lib/db.ts:13` — the app connects with `role: env().ADPORT_DB_ROLE` (default `adport_backend`, `lib/env.ts:9`).
  - Scan result (command above): every statement against `organizations`, `organization_memberships`, `organization_settings`, `connections`, `api_keys`, `pending_operations`, `audit_events`, `findings`, `organization_ad_accounts`, `organization_subscriptions`, `provider_credentials`, `markting_*` carries an `organization_id` predicate or is a by-design global lookup (`repository.ts:100` OAuth state hash with user check at `:91`; `:332` API-key hash; `:357,366` rate-limit buckets; `mcp-oauth-repository.ts:290-313` token lookups with an org/claims cross-check at `:287-289`; `account-selection.ts:145` is `where id = … and organization_id = …` — the scanner mis-flagged a multi-line statement). `PostgresPendingStore`, `PostgresAuditStore`, `PostgresFindingsStore`, `PostgresSandboxStore` are constructed from the principal (`repository.ts:371,429,438`, `markting/repository.ts:117`).
  - No `set local` of a tenant GUC and no RLS policy that reads one: `grep -rn "set local\|current_setting" platform/apps/cloud/lib` returns nothing (checked while scanning).
- **Description:** Tenant isolation at the data layer is correct today but is enforced exclusively by application code; the database would happily return another tenant's rows to the same connection. The browser roles (`authenticated`) are locked out of the markting tables entirely (`:74-81, 88`), which is good, but the server path has no safety net.
- **Impact:** Any future query that forgets the predicate (or a `.find()` over an unscoped list) is an immediate cross-tenant bug with nothing to catch it.
- **Recommendation:** Add a second layer: per-request `set local app.organization_id = …` inside a transaction plus RLS policies on `adport_backend` that compare `organization_id = current_setting('app.organization_id')::uuid`, or at minimum a lint/test that asserts every tenant-table statement contains `organization_id`. Run the existing database suite in CI (it is `describe.skip` without `ADPORT_RUN_DATABASE_TESTS=1`, `markting-repository.database.test.ts:13`).

### D8-04 — Engine-side tenant data has no organization column and is never deleted or retained per tenant
- **Severity:** P2
- **Classification:** VERIFIED_CODE
- **Evidence:**
  - `engine/src/paid_media_agent/persistence/postgres.py:11-43` — `pma_proposals`, `pma_approvals`, `pma_receipts`, `pma_thread_owners` have no tenant column; LangGraph checkpoints are keyed by `thread_id` only (`runtime/self_hosted.py:45-53`).
  - `platform/apps/cloud/app/api/deletion/route.ts` — no reference to the engine or the markting tables (grep exit 1); markting tables cascade on `organizations` delete (`20261002000000_markting_bridge.sql:13,25,39,62`), the engine rows do not.
  - `20260817171039_cloud_initial_schema.sql:382-401` — `private.apply_data_retention()` deletes from `audit_events`, `pending_operations`, `deletion_requests`, `oauth_transactions`, `rate_limit_buckets` only; nothing for `markting_threads`/`markting_engine_proposals` and nothing reaches the engine.
  - Plans promise `maxRetentionDays` (`lib/cloud/plans.ts:18,26-42`).
- **Description:** A tenant's full conversation history (including whatever they typed), proposals and receipts persist indefinitely in the engine database after the organization is deleted, identifiable only by a thread id that encodes the (now deleted) org and user UUIDs.
- **Impact:** Deletion requests and plan retention limits are not honoured for engine-side data; data-protection exposure for the operator.
- **Recommendation:** On org deletion and retention runs, delete engine rows whose `thread_id like 'org_<org>__%'` (and the corresponding checkpoints), or give the engine host an org-scoped purge endpoint; extend `apply_data_retention()` to `markting_threads` / `markting_engine_proposals`.

### D8-05 — Thread rows with `user_id is null` are claimable by any member of the organization
- **Severity:** P3
- **Classification:** VERIFIED_CODE
- **Evidence:** `platform/apps/cloud/lib/markting/repository.ts:22-23` — `and (user_id is null or user_id = $user)`; `20261002000000_markting_bridge.sql:14` — `user_id … on delete set null`; `assistant.ts:37` — the `startsWith` check includes the user id, which blocks this through the assistant route, but `claimThread` itself does not.
- **Description:** When a user is deleted, their threads become claimable by any other member of the same org via `claimThread`; same-tenant only, and currently unreachable through the only caller because of the prefix check. Convention (`startsWith`) rather than the repository enforces the user boundary.
- **Recommendation:** Drop the `user_id is null` branch or make the repository check the `org_…__u_…` prefix itself.

### D8-06 — Engine report lock is global; one tenant can serialize every other tenant's report runs
- **Severity:** P3
- **Classification:** VERIFIED_CODE
- **Evidence:** `services/engine-demo/serve_demo.py:324,344` — a single `asyncio.Lock` around `run_report`; `platform/apps/cloud/app/api/reports/engine/route.ts:32` — the platform rate limit is per org (120/min, `repository.ts:355`), so N orgs can queue N×120 runs/min; `GET /api/reports/engine` (`route.ts:16-24`) has no rate limit at all.
- **Description / Impact:** Noisy-neighbour: report runs (which render HTML/PDF) from all tenants share one lock and one `maxDuration = 300` route budget; a hostile or busy tenant delays everyone.
- **Recommendation:** Per-org quotas on report runs, a bounded queue on the engine host, and a rate limit on the listing route.

### D8-07 — `GET /markting/info` is unauthenticated
- **Severity:** P3
- **Classification:** VERIFIED_CODE
- **Evidence:** `services/engine-demo/serve_demo.py:326-336` — no `caller(authorization)` call, unlike every other added route; exposes mode, write-provider class, kill-switch state, approver refs and account aliases. Mitigated by the engine port not being published (`docker-compose.yml:64`).

### D8-08 — Demo flags are global environment switches that reach every tenant's write path
- **Severity:** P3 (fails toward the sandbox, not toward real accounts)
- **Classification:** VERIFIED_CODE
- **Evidence:** `platform/apps/cloud/lib/markting/runtime.ts:18-26` — when `MARKTING_DEMO_MODE=true`, `createBridgeRuntime` returns the sandbox runtime for **every** organization, without `AccountScopedProvider`/`authorizeToolCall`; `.env.example:47,49` ships `MARKTING_DEMO_MODE=true` and `MARKTING_ALLOW_SELF_APPROVAL=true` (the per-app `platform/apps/cloud/.env.example:106,108` ships `false`); `app/api/approvals/[id]/apply/route.ts:22-23` honours the global self-approval flag for all orgs.
- **Description:** Demo mode and self-approval are deployment-wide, not per-tenant. A production stack started from the root `.env.example` would run every tenant against the sandbox with self-approval enabled. The sandbox has no real credentials and its accounts are fixed (`sandbox-provider.ts:42-48`), and sandbox state is per org (`PostgresSandboxStore`, `markting/repository.ts:117-142`), so this is not a cross-tenant or real-spend defect — it is a demo path that can silently reach production.
- **Recommendation:** Make demo/sandbox a per-organization setting (e.g. in `organization_settings`), and gate `MARKTING_ALLOW_SELF_APPROVAL` per org or remove it from the production image.

### D8-09 — No way to populate the live alias map or resume a thread; dashboard is single-org
- **Severity:** GAP
- **Classification:** VERIFIED_CODE
- **Evidence:** `upsertAlias` is called only from tests; aliases are seeded only by `infra/seed/seed-demo.mjs:56-63`, and only the four sandbox aliases; `listThreads` (`markting/repository.ts:29-36`) has no caller; the thread id lives in React state only (`app/dashboard/assistant/assistant-chat.tsx:25,45`); `requireDashboardTenant` always picks the oldest membership (`lib/cloud/dashboard.ts:27-43`), while API routes accept `organizationId` in the body (`auth.ts:9-13`). `clientWorkspaces` on the agency/enterprise plans (`plans.ts:38,42`) appears only as a billing bullet (`app/dashboard/billing/page.tsx:95`).

## What a world-class system would need

1. A tenant dimension inside the engine host: org id on threads, proposals, reports and artifacts (header or per-org token), enforced in `serve_demo.py` and verified by two-caller tests.
2. Defense in depth in Postgres: `set local app.organization_id` per request + RLS policies for `adport_backend`, and CI running the database suite.
3. Per-org report storage (`out/<org>/…`), org-filtered listing/download, per-org run quotas and a bounded engine queue; adport audit events for report runs.
4. Tenant lifecycle: org deletion and retention purging engine rows and checkpoints by thread prefix; retention for `markting_*` tables.
5. Per-organization demo/sandbox and self-approval settings instead of process-wide env flags.
6. Org switcher, alias management UI, thread history — the operational surface a multi-org agency tenant needs.
7. Secret hygiene for the shared token: rotate `MARKTING_ENGINE_TOKEN` without `.env` rewrites; today one leaked token is every tenant.

The architecture doc describes the engine as imported, not as deployed.
- `docs/ARCHITECTURE.md:882` / `docs/PHASE0-REPORT.md:154`: identity mapping "Decision pending" — the code has decided: one token, one caller (`docker-compose.yml:49`). `docs/TODO.md:27` acknowledges it as a future consideration only.
- `docs/PHASE0-REPORT.md:112`: the assistant route "requires `tools:write`" and thread ids are `{org}:{user}:{thread}` — the route does not require `tools:write` for a turn (`messages/route.ts:9-19`); only the bridge does when a proposal arrives (`bridge.ts:68`); the id format is `org_<org>__u_<user>__<suffix>` (`markting/repository.ts:12-14`).
- `platform/apps/cloud/lib/cloud/plans.ts:38,42` advertises `clientWorkspaces` for agency/enterprise; nothing implements it (D8-09).
- Out of my workstream but observed: with `MARKTING_DEMO_MODE=false` the engine still analyses fixture data (`serve_demo.py:163-166,386`) while the alias map would point its proposals at real accounts; the "live" bridge therefore applies real changes derived from synthetic analysis.
