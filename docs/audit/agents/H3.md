## Findings

### H3-01 — Ad-platform write ("apply") produces no audit event, no structured log, no metric
- Severity: P2 (financial/operational: the money-spending mutation is the least observable step)
- Classification: VERIFIED_CODE
- Evidence: `platform/apps/cloud/app/api/approvals/[id]/apply/route.ts:26-28` (`applyPending(...)` then `markPendingOutcome(..., 'applied')`, no `recordAudit`); contrast `platform/apps/cloud/app/api/approvals/[id]/reject/route.ts:17` which does call `recordAudit`. Preview/note is audited in `lib/markting/bridge.ts:90-95` but the *apply* (the real registry write) is not.
- Description: The two-step contract's second call — the one that actually mutates the ad account — writes only a `pending_operations.status = 'applied'` flag. There is no `audit_events` row recording who applied which operation at what time with what result, no structured log line, and no success/failure counter. On failure, `applyPending` throws into `apiError` (`lib/http.ts:29`) which emits a bare `console.error(error)` only for HTTP >= 500 and records nothing in the audit trail; `markPendingOutcome('applied')` is skipped so the row silently stays `pending`.
- Impact: For an "AI media buyer" that spends real budget, the highest-risk action leaves the weakest trail. Post-incident "who approved and applied this spend change, and did it land?" cannot be answered from the cloud audit log; failed applies are invisible to operators (no alert, no audit row).
- Recommendation: Emit an `audit_events` row on both success and failure of apply (actor, org, pendingId, tool, accountId, outcome, latency, error class), a structured log line with org/user/request ids, and increment success/failure counters feeding an alert on elevated apply-failure rate.

### H3-02 — No metrics anywhere (requests, engine runs, LLM token/cost)
- Severity: P2
- Classification: VERIFIED_CODE (absence verified by tree-wide search)
- Evidence: tree-wide grep for prometheus/opentelemetry/otel/statsd/datadog/instrument over `platform/apps/cloud`, `engine/src`, `services` returned no telemetry (only `metrics` as ad-performance UI fields, e.g. `app/dashboard/live-data.tsx:35`). `platform/apps/cloud/package.json` and `engine/pyproject.toml` declare no metrics/OTel dependency. No request latency/count instrumentation (`grep duration|latency|histogram|counter` → only `maxDuration` route config, `app/api/assistant/messages/route.ts:7`).
- Description: There is no request rate/latency/error metric, no engine run count/duration metric, and — despite an LLM-driven agent — no token or cost metric or log. Nothing records per-org model spend.
- Impact: No way to detect latency regressions, error spikes, saturation, or runaway model cost in production; capacity planning and cost attribution per tenant are impossible.
- Recommendation: Add a minimal metrics layer (OTel or Prometheus) with request count/latency/error by route and status; engine run count/duration/outcome; and LLM `prompt_tokens`/`completion_tokens`/estimated cost labeled by org — at least logged as structured events if a metrics backend is not yet chosen.

### H3-03 — Engine logging is unstructured plaintext with no correlation/tenant identifiers, and barely used
- Severity: P2
- Classification: VERIFIED_CODE
- Evidence: `engine/src/paid_media_agent/cli.py:23-26` (`logging.basicConfig(level=..., format="%(levelname)s %(name)s: %(message)s")`); only 5 logger call sites in the entire engine src tree (`middleware/authorization.py:82,89`, `surfaces/slack/delivery.py:152,156`, `tools/pipeboard.py:118`). `services/engine-demo/serve_demo.py:399` uses the same plain `basicConfig`.
- Description: Logs are human-readable lines, not JSON; there is no thread id, proposal id, org/tenant id, caller ref, or trace/correlation id on any log record. The apply/preview/report paths emit essentially no application logs (the FastAPI handlers in `surfaces/api/app.py` log nothing; only `serve_demo.py:376` logs on report failure via `log.exception`).
- Impact: Production incidents cannot be correlated across a request or traced to a tenant/thread; log aggregation and search by org/thread are not possible. Effectively no application-level log signal for the write pipeline.
- Recommendation: Switch to structured JSON logging (e.g. a formatter emitting `ts, level, logger, msg, org_id, thread_id, proposal_id, caller_ref, trace_id`), add request-scoped trace ids, and log at the boundaries of every write/preview/apply/report operation with outcome and duration.

### H3-04 — `/markting/info` is unauthenticated and discloses approver identities and account aliases
- Severity: P2 (information disclosure)
- Classification: VERIFIED_CODE
- Evidence: `services/engine-demo/serve_demo.py:326-337` — `@app.get("/markting/info")` has no `caller`/bearer dependency (unlike `/reports/run` et al. which call `caller(authorization)`), and returns `approvers: sorted(approval_policy.approver_refs)` and `aliases: list(accounts.aliases())`, plus `write_provider`, `kill_switch`, `writes_enabled`, `mode`.
- Description: An unauthenticated caller can enumerate the approver reference list (which in the Slack surface are user identifiers) and the configured account aliases, and read the write-gate posture (kill switch, writes_enabled) of the engine host.
- Impact: Leaks internal operator/approver identities and account naming, plus the live write-safety posture, to anyone who can reach the engine host — useful reconnaissance for targeting approvers or timing writes.
- Recommendation: Require the bearer `caller` dependency on `/markting/info` (same as `/reports`), or strip `approvers`/`aliases` from the unauthenticated response. `/health` (`engine .../api/app.py:80-89` and the demo) also discloses `catalog_revision`/`writes_enabled` unauthenticated — acceptable for a liveness probe but should not grow to include tenant data.

### H3-05 — Cloud log redaction in `reads.ts` is narrower than the engine's and can leak credential-shaped values
- Severity: P3
- Classification: VERIFIED_CODE
- Evidence: `platform/apps/cloud/lib/cloud/reads.ts:19-24` redacts only `/(bearer|token|secret|authorization)[=: ]+[^\s,;]+/gi` then slices to 500 chars. The engine's `engine/src/paid_media_agent/middleware/redaction.py:16-28` is far broader (Slack `xox*`/`xapp-`, `sk-`/`sk-ant-`, Google `AIza…`, `pb_…`, generic `api_key|token|secret|password|authorization: value`, and `postgres://` URLs).
- Description: A provider error surfaced into the cloud `console.error('Provider read failed', …)` whose message embeds an `AIza…` key, an `sk-…` key, a bare Pipeboard `pb_…` token, or a `postgres://` DSN would not be redacted by the cloud regex (it only catches the four labelled prefixes with a following delimiter). `lib/http.ts:29` logs the raw `Error` object for 5xx with no redaction at all.
- Impact: Upstream error text containing a secret can be written verbatim to cloud stdout/log aggregation.
- Recommendation: Reuse a shared redaction routine on the cloud side mirroring the engine patterns, and apply it in `http.ts` before `console.error(error)`.

### H3-06 — Cloud logging is inconsistent and carries no tenant/trace context
- Severity: P3
- Classification: VERIFIED_CODE
- Evidence: 9 `console.*` sites. Structured JSON: `app/oauth/token/route.ts:19`, `app/api/oauth/[provider]/callback/route.ts:107`, `app/api/support/route.ts:39`. Plain strings / raw objects: `reads.ts:19` (object, no ids), `lib/http.ts:29` (raw Error), `app/api/billing/webhook/route.ts:13`, `app/api/oauth/[provider]/callback/route.ts:125`, `app/api/waitlist/route.ts:94` (message only, no ids). No `middleware.ts` and no request-logging layer (`find platform/apps/cloud -name middleware.ts` → none).
- Description: Half the log sites are JSON and half are free-form; none include `organizationId`/`userId`/request id even where the principal is in scope (e.g. `reads.ts` has `principal.organizationId`). There is no per-request access log.
- Impact: Logs cannot be filtered by tenant or stitched into a request; mixed formats defeat structured ingestion.
- Recommendation: Standardize on one structured logger, always attach org/user/request ids, and add a request-level access log (method, path, status, duration, org) via middleware.

### H3-07 — LangSmith "tracing" is documented but not actually enabled by the project
- Severity: GAP
- Classification: DOCUMENTED_ONLY / INFERRED
- Evidence: `docs/ARCHITECTURE.md:776` and `engine/.env.example:31` state `LANGSMITH_API_KEY` "serves tracing". No `LANGCHAIN_TRACING_V2`/`LANGSMITH_TRACING` flag is set or documented anywhere (grep → 0 in non-venv). The key's verified uses in code are the model gateway, sandboxes, and `mda deploy` (`cli.py:304-333`, `admin/actions.py:219,343`, `.env.example:91-93`).
- Description: Modern LangSmith SDKs require an explicit tracing flag in addition to the API key; the project neither sets nor documents it, so having the key does not by itself yield traces. Even if enabled, LangSmith traces only the engine's LangGraph runs — the adport/cloud bridge and apply path (where real writes happen) are never traced.
- Impact: Operators following the docs may believe runs are traced when they are not; and the write-critical cloud path has no tracing regardless.
- Recommendation: Either wire and document the tracing flag explicitly, or correct the docs; add first-party trace propagation across cloud → engine (a shared trace id) so the apply path is observable independent of LangSmith.

## What a world-class system would need (gaps, concrete)
- One structured JSON logger per service, every record carrying `org_id`, `user_id`/`caller_ref`, `request_id`/`trace_id`, `thread_id`, `proposal_id` where applicable; a request-level access log via Next.js middleware and FastAPI middleware.
- A trace id generated at the cloud edge and propagated to the engine over the `EngineClient` headers so a single apply can be followed cloud → engine → provider.
- Metrics: request count/latency/error by route+status; engine run count/duration/outcome; apply success/failure counters; per-org LLM token and estimated-cost counters.
- A durable, append-only audit of every apply (success and failure) with actor, operation, account, outcome, latency, and error class — the write that spends money must be the best-logged event, not the least.
- Alerting: page on sustained apply-failure rate, engine `/health` down, model/cost anomalies, and 5xx spikes.
- A shared redaction utility used by both runtimes on every log/error path (cloud currently diverges from the engine's stronger patterns).
- Auth on introspection endpoints (`/markting/info`) and a minimal, data-free liveness `/health`.

## Disagreements / claims in docs that the code contradicts
- `docs/ARCHITECTURE.md:776` / `engine/.env.example:31` imply `LANGSMITH_API_KEY` enables tracing; no tracing flag is set or documented, so the key alone does not produce traces (see H3-07).
- Workstream hypothesis that Supabase analytics is "disabled in the alt config": the single `platform/supabase/config.toml` has `[analytics] enabled = true` (line 388-391, local Logflare, backend postgres); only `[storage.analytics]` is `enabled = false` (line 137-138). No alternate config file exists (`find config*.toml` → one file). This is the Supabase CLI *local dev* stack, not a production app-observability mechanism either way.
- Phase reports (e.g. `docs/PHASE1-REPORT.md:30`) cite `/markting/info` as a verification probe without noting it is unauthenticated and leaks approver/alias data (H3-04).
