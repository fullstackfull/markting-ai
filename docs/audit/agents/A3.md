## Findings

### A3-01 — Generic `tiktok_api_update` reaches permanent deletion (TikTok deletes via `*/status/update` + `DELETE`)
- **Severity:** P2 (unsafe-execution labelling; still behind the two-step gate)
- **Classification:** VERIFIED_CODE (mechanism), INFERRED (TikTok endpoint semantics)
- **Evidence:** `platform/packages/tiktok/src/provider.ts:284-300` (`planApiUpdate` only requires the path to end in `/update` and the body to contain no `*budget*` key), `provider.ts:445-451` (`validateTikTokMutationPath`), `tools.ts:241-248` (`tiktok_api_update` declared `kind: 'update'`, description "Update non-budget fields"), `tools.ts:249-257` (`tiktok_api_delete` requires `/delete` suffix and is the only tool marked `destructive: true`).
- **Description:** In TikTok Marketing API v1.3, campaigns, ad groups and ads are deleted by POSTing `operation_status: "DELETE"` to `campaign/status/update`, `adgroup/status/update`, `ad/status/update` — there is no `campaign/delete` endpoint (INFERRED from domain knowledge; docs fetch blocked). The code accepts `{ path: 'campaign/status/update', body: { campaign_ids: [...], operation_status: 'DELETE' } }` through `tiktok_api_update`: it is recorded in the audit log as `kind: 'update'`, summarised as "Update TikTok resource via /campaign/status/update" (`provider.ts:294`), and nothing in the preview flags irreversibility (compare `planApiDelete`'s "Permanently delete" summary at `provider.ts:310`). The typed `tiktok_set_campaign_status` correctly restricts to `ENABLE|DISABLE` (`tools.ts:140`), so this is a generic-tool hole only. Conversely, `tiktok_api_delete` is largely useless for the ad hierarchy because the `/delete` suffix it demands does not exist for campaign/adgroup/ad (INFERRED).
- **Impact:** Irreversible deletion of live campaigns is mis-categorised as an update in audit and policy terms; any downstream consumer that treats `kind: 'remove'`/`destructive` differently (UI warnings, future policy rules) is bypassed. The raw JSON body is shown in `changes`, so a careful human approver can still see `DELETE`.
- **Recommendation:** In `planApiUpdate`, detect `operation_status === 'DELETE'` (recursively, like `coerceTikTokCreatedStatuses`) and either reject with "use a destructive tool" or re-classify the plan as a delete with an explicit "Permanently delete" summary. Add a test.
- **No test covers this** (`tiktok.test.ts:273-283` only tests wrong-suffix and budget rejection).

### A3-02 — `paused_creation` policy does not cover ad groups / ads created through `tiktok_api_create` when `operation_status` is omitted
- **Severity:** P1 (financial risk: entity can go live under an active campaign despite policy saying created objects are paused)
- **Classification:** VERIFIED_CODE (behaviour), NOT_VERIFIED (TikTok default = ENABLE; docs fetch blocked; my domain recollection is that `adgroup/create` and `ad/create` default `operation_status` to `ENABLE`)
- **Evidence:** `provider.ts:268-274` — `coerceTikTokCreatedStatuses` only flips an **explicit** `'ENABLE'` to `'DISABLE'` (`provider.ts:457-468`); the "add DISABLE when absent" branch is restricted to `path === 'campaign/create'` (`provider.ts:270-273`). Policy intent at `platform/packages/core/src/policy/policy.ts:303-304`: "Created campaigns/ad groups/ads are coerced to PAUSED." Test coverage at `tiktok.test.ts:255-271` uses `campaign/create` with explicit `ENABLE` only.
- **Description:** `tiktok_api_create` with `path: 'adgroup/create'` (or `ad/create`) and a body that simply omits `operation_status` is sent unchanged. If TikTok defaults the new ad group to ENABLE (as I believe it does), it begins delivering immediately when its parent campaign is ENABLE — exactly what `paused_creation` exists to prevent. The preview shows no coercion, so the approver has no hint.
- **Impact:** Spend starts without the "create paused, then enable" two-step the product promises.
- **Recommendation:** For any `/create` path whose body is an ad-hierarchy object (`campaign/create`, `adgroup/create`, `ad/create`), set `operation_status = 'DISABLE'` when absent, not only for campaigns. Add tests for adgroup/create and ad/create with and without the field. Verify the TikTok default against the official reference once network access permits.

### A3-03 — Generic `tiktok_api_read` forces `advertiser_id` but not `advertiser_ids`/`bc_id`; account-scope can be sidestepped inside the tenant's own grant
- **Severity:** P2 (policy bypass within one tenant's OAuth grant; not cross-tenant)
- **Classification:** VERIFIED_CODE (mechanism), INFERRED (which endpoints honour alternative scoping params)
- **Evidence:** `provider.ts:202-209` (`{ ...input.params, advertiser_id: input.account_id }` — only the singular key is overridden), `platform/apps/cloud/lib/cloud/account-scope.ts:48-54` (authorizer checks only `input.account_id` / `input.customer_id`), `provider.ts:83-85` (the package itself uses `advertiser/info` with plural `advertiser_ids`).
- **Description:** A model call `tiktok_api_read({ account_id: <enabled>, path: 'advertiser/info', params: { advertiser_ids: ['<not-enabled advertiser>'] } })` passes the authorizer (account_id is enabled), the forced `advertiser_id` is ignored by that endpoint, and data for an advertiser the workspace admin deliberately did **not** enable is returned. Business-Center endpoints keyed by `bc_id` (e.g. BC-level reports/asset lists) have the same property (INFERRED). The same spread pattern in `planApiCreate/Update/Delete` (`provider.ts:266,292,307`) forces `body.advertiser_id` only.
- **Impact:** The "Enable it in Accounts before using it" promise (`account-scope.ts:24`) is advisory for TikTok generic reads. Cross-tenant isolation is unaffected (token is the tenant's).
- **Recommendation:** Reject params/body keys matching `/^(advertiser_ids|bc_id|owner_bc_id)$/` (or any value equal to a non-enabled advertiser id) in `apiRead` and the generic mutation planners, mirroring the engine's `raw_account_id_rejected` rule (`engine/src/paid_media_agent/tools/reads.py:176-182`). `account-scope.test.ts` has no TikTok generic-tool case (`rg api_read|advertiser_ids platform/apps/cloud/test/account-scope.test.ts` → none).

### A3-04 — No path to change an ad-group budget (TikTok's primary budget lever)
- **Severity:** P2 (substantial functional deficiency; README claims "budgets" write capability)
- **Classification:** VERIFIED_CODE
- **Evidence:** `tools.ts:220-231` (`tiktok_set_budget` takes `campaign_id` only), `provider.ts:387-422` (`planSetBudget` → `campaign/update`), `provider.ts:289-291` (`planApiUpdate` throws `budget updates require a typed budget tool` for any body containing a key matching `/budget/i`), `provider.ts:396-398` (BUDGET_MODE_INFINITE campaigns rejected). Claim: `platform/README.md:116` "TikTok Ads | ... | campaigns, budgets, status".
- **Description:** In TikTok most campaigns use `BUDGET_MODE_INFINITE` at campaign level with budgets set per ad group (Campaign Budget Optimization is opt-in). The typed tool rejects exactly those campaigns, and the generic update tool rejects any budget field. Result: for the most common account structure, **no budget can be changed at all**, and the `max_budget_delta_pct` policy never gets exercised for TikTok ad groups.
- **Recommendation:** Add `tiktok_set_adgroup_budget` (live lookup via `adgroup/get`, `budget_mode`, 105% note, from/to micros) so the policy delta cap applies; update the README to say "campaign budgets only" until then.

### A3-05 — Reporting silently truncates: only page 1 is fetched and `truncated` is never set
- **Severity:** P2 (reliability; wrong totals without warning)
- **Classification:** VERIFIED_CODE
- **Evidence:** `provider.ts:110-136` (`page: 1`, `page_size: Math.min(query.limit ?? 200, 1000)`, `page_info.total_number` read into the type but never used; returns `{ rows }` without `truncated`), `provider.ts:188-200` (`rawReport` same), `platform/packages/core/src/model.ts:47-50` (`Report.truncated` exists), `platform/packages/core/src/tools/builtin.ts:116,136` (core report tool relies on `report.truncated` to mark summaries incomplete).
- **Description:** An advertiser with >200 campaigns (or >`limit`) at campaign level, or >1000 ads at ad level, gets a partial report whose `summary.complete` is `true`. Account-level totals in `summarizeReport` are therefore understated with no signal.
- **Recommendation:** Loop on `page` until `page * page_size >= total_number` or set `truncated: true` when `total_number > rows.length`. Add a test with `page_info.total_number > list.length`.

### A3-06 — Report rows carry no `status`, so the audit harness treats paused TikTok campaigns as active
- **Severity:** P3
- **Classification:** VERIFIED_CODE
- **Evidence:** `provider.ts:166-176` (`entity: { level, id, name }` — no `status`), `platform/packages/core/src/audit/packs/core-performance.ts:4-6` (`isActive(status?)` defaults to `'ENABLED'` when undefined), `core-performance.ts:14-28` (`zero-conversion-spend` proposes `pauseCampaign` for rows that pass `isActive`).
- **Impact:** Findings and "pause" proposals are generated for campaigns that are already DISABLED; the `secondary_status` TikTok returns (e.g. `CAMPAIGN_STATUS_BUDGET_EXCEED`, `..._NOT_START`, `..._DELETE`) is read nowhere, so pacing/health signals are discarded.
- **Recommendation:** Join `campaign/get` (`operation_status`, `secondary_status`) into report rows at campaign level, or request them as report metrics where TikTok supports it.

### A3-07 — Engine cannot read, normalize, fixture-test or write TikTok Ads
- **Severity:** GAP (not a defect: the engine code does not claim TikTok support; but product docs do)
- **Classification:** VERIFIED_CODE
- **Evidence:** `engine/src/paid_media_agent/domain/common.py:36-41` (`FIXTURE_PLATFORMS` = google, meta, reddit), `engine/src/paid_media_agent/fixtures/data/` (3 files, no `tiktok_ads.json`), `engine/src/paid_media_agent/tools/normalize.py:14-27,95-97` (`_SPEND_KEYS` has no `TIKTOK_ADS`; `normalize_rows` raises `NormalizationError("platform metrics have no verified spend-unit mapping")`), `engine/config/write-policy.example.toml:38-92` (no tiktok rows), `engine/src/paid_media_agent/tools/fixtures.py:26-33` (`FIXTURE_ADMITTED_MUTATIONS` google/meta/reddit only), `engine/src/paid_media_agent/tools/direct/` (`x_ads.py`, `openai_ads.py` only), `engine/src/paid_media_agent/config.py:143,237` (Pipeboard URL for tiktok_ads), `engine/src/paid_media_agent/tools/catalog.py:107` (`PlatformPolicy(TIKTOK_ADS, account_arg_names=("advertiser_id",))`).
- **Description:** TikTok reaches the engine **only** via Pipeboard MCP (`https://tiktok-ads.mcp.pipeboard.co/`), requires a `PIPEBOARD_API_TOKEN`, and even then any read is stored as a raw `provider_result` artifact rather than `PerformanceRow`s, so `compare_periods`, cadence reports and anomaly logic never see TikTok numbers (`docs/ARCHITECTURE.md:646` states this and the code agrees). Offline/fixture mode has zero TikTok data. The engine can never emit a `tiktok_ads__update_campaign_*` proposal because no write-policy row admits one, so the bridge's TikTok branch (`platform/apps/cloud/lib/markting/translate.ts:110,121`) is reachable only from unit tests (`docs/PHASE1-REPORT.md:38` says so honestly).
- **Recommendation:** If TikTok is a launch channel, add `tiktok_ads.json` fixtures, a spend mapping (TikTok `spend` is float whole units, strings), and admitted write-policy rows; otherwise mark TikTok "platform-only (no AI analysis)" in the Arabic README.

## What a world-class system would need (TikTok-specific, concrete)

1. **Ad-group as first-class entity:** typed `tiktok_adgroups` read (budget, budget_mode, bid_type, bid_price, optimization_goal, optimization_event, schedule, placement_type, `secondary_status`, learning status) and typed `tiktok_set_adgroup_budget` / `tiktok_set_adgroup_status` with live from/to lookups so the 25% delta cap actually protects TikTok spend.
2. **Reporting depth:** `report_type` selectable (BASIC/AUDIENCE/PLAYABLE_MATERIAL/CATALOG), typed dimension sets (age, gender, country_code, province_id, placement, platform/OS, stat_time_day/hour), full pagination, `reach`/`frequency`/`video_play_actions`/`video_watched_2s/6s`/`average_video_play`/`cost_per_1000_reached`, and `conversion` qualified by the ad group's optimization event.
3. **Attribution + events:** pass explicit attribution windows (click/view, 1d/7d/28d) and surface pixel/app-event health (`pixel/list`, event counts, last-fired), since TikTok's "conversion" is meaningless without the event name.
4. **Pacing & health:** spend-to-date vs budget per campaign/ad group in the advertiser timezone (currently fetched then dropped), `secondary_status` decoding (BUDGET_EXCEED, NOT_START, REVIEW/REJECT, LEARNING), advertiser balance.
5. **Creative intelligence:** `creative/report/get` + `ad/get` creative metadata (Spark Ads authorization, video id, CTA) feeding a frequency/CTR-decay fatigue rule; TikTok creative half-life is days, not weeks.
6. **Safety:** fix A3-01/02/03; reject generic bodies that touch `bid_price`, `operation_status: DELETE`, `advertiser_ids`, `bc_id`; pre-check the 105% rule against today's spend; enforce TikTok minimum budgets and 2-decimal rounding before validation.
7. **Engine parity:** TikTok fixtures + spend mapping + admitted write rows + a TikTok playbook in `paid-media-wiki` (learning phase thresholds, SPC/Smart+ behaviour, Spark vs non-Spark, Shop Ads, auction vs reservation) so the Arabic-first analyst can actually reason about the channel.
8. **Hosted sandbox** path (store `sandbox` on the cloud credential and expose it in the connection UI) so a GCC advertiser can rehearse before touching a live advertiser.
