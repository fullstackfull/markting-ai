## Findings

### D10-01 — The engine can never read connected accounts; "live" mode is a real model over fixture data, while proposals can still be routed to real accounts through the alias table
- **Severity:** P1  **Classification:** VERIFIED_CODE (behaviour), DOCUMENTED_NOT_IMPLEMENTED (README claim)
- **Evidence:** `services/engine-demo/serve_demo.py:163-166` (`assert_fail_closed` refuses any `paid_media_data_mode` other than `sample`), `:183-191` (`demo_settings` forces `sample`), `:383-387` (live mode: `base.model_copy(update={"paid_media_data_mode": "sample"})`), `engine/src/paid_media_agent/runtime/catalog.py` via `docs/ARCHITECTURE.md:758` (sample mode forces the example alias file); `README.md:83` ("Analyses connected accounts (spend, conversions, CPA, ROAS)"), `README.md:116` (`MARKTING_DEMO_MODE=false` = "real accounts connected through OAuth"); `platform/apps/cloud/lib/markting/repository.ts:40-50` (any org row may bind alias `demo-google` to `provider='google', account_id=<real>`), `translate.ts:133-142` (binding resolves the target with an optional `targets` map).
- **Description:** Every engine mode the host can boot in reads only the shipped fixtures (`google_ads.json`, `meta_ads.json`, `reddit_ads.json`) and the three example aliases. OAuth-connected adport accounts are never visible to the engine; there is no data path from adport reports into the engine. Yet the bridge will happily translate an engine proposal whose `account_ref` is `demo-google` into a guarded write on whatever real account an operator binds to that alias (and `targets` can remap `g-103` to a real campaign id). The policy engine preview (real current value from the provider), the 25 % default delta cap (`platform/packages/core/src/policy/policy.ts:13`) and the human apply step are the only things between a synthetic-data recommendation and a real budget change.
- **Impact:** The product's central promise (AI analysis of the customer's accounts) is not implemented; in live mode the Assistant's "analysis" and the Approvals preview can describe two different worlds. The README does not say this; `docs/TODO.md` does not list it either.
- **Recommendation:** State plainly in README/TODO that the engine is fixture-only today. Before any live rollout either (a) feed the engine real reads (an adport-backed read provider or Pipeboard credentials with `PAID_MEDIA_DATA_MODE=live`, which the host currently forbids), or (b) make the bridge refuse to bind a non-`sandbox` provider while the engine reports `catalog_source == "fixture"` (`/health` already exposes it; `engine-client.ts:166-173` already types it).

### D10-02 — Demo scripted model keeps per-process state keyed on the human-message count, so the second thread (second user) gets "script exhausted" instead of analysis or a proposal
- **Severity:** P2  **Classification:** VERIFIED_TEST
- **Evidence:** `services/engine-demo/serve_demo.py:84-115` (`LoopingScriptedChatModel.seen_human_messages`/`call_count` are instance fields; reset only when `len(humans) != self.seen_human_messages`), `:194-198` (one model instance for the whole process), `engine/src/paid_media_agent/testing/scripted_model.py:64-70,96-109` (`call_count` is shared mutable state). Probe `test_second_thread_first_message_gets_real_analysis` and `test_second_thread_change_request_after_other_threads_change` both failed: thread B's first message returned the `_exhausted_text()` and `proposal: null` while thread A got the full script. The shipped test suite only ever sends one message per fresh app (`services/engine-demo/tests/test_demo_api.py:93-144`), which is why it passes.
- **Impact:** In the compose stack (one engine process, `MARKTING_ENGINE_MODE=demo` by default, `.env.example:51`) every user's first message in a new thread after any other thread's first message yields the fallback text; the README walkthrough ("What needs attention this week?" then "Reduce…", `README.md:103`) works only for the first thread. Demo-only, but demo is the default mode and the only mode exercised.
- **Recommendation:** Key the script position per `thread_id` (available in `RunnableConfig`/`kwargs`), or compare against the last human message content rather than the global count.

### D10-03 — No (proposal_id, revision) pre-check before preview; the engine keeps returning an un-rejected proposal on every later turn, so a failed hand-off produces a new pending operation per message and overwrites provenance
- **Severity:** P2  **Classification:** VERIFIED_CODE (bridge) + VERIFIED_TEST (engine behaviour)
- **Evidence:** `platform/apps/cloud/lib/markting/assistant.ts:335` (bridges whenever `proposal.state === 'awaiting_approval'`; no lookup of `findEngineProposal`), `bridge.ts:58-96` (never consults existing records), `repository.ts:84-86` (`on conflict … do update set pending_operation_id = excluded.pending_operation_id` — the earlier pending id is lost), `engine/src/paid_media_agent/surfaces/runner.py:90-92,134` (`latest_proposal` is simply the last record for the thread). Probe `test_message_on_interrupted_thread_without_reject`: after an un-rejected proposal, the next message returned `interrupted=False`, normal analysis text and the **same** `awaiting_approval` proposal id. `docs/PHASE0-REPORT.md:113-114` promised "an unseen `(proposal_id, revision)`" check and "GET … only if still awaiting, reject" — neither exists.
- **Impact:** Any hand-off failure (engine 5xx/timeout on `/reject`, swallowed at `bridge.ts:98-105`; or the throw paths in D10-04) turns every subsequent message in that thread into another `pending_operations` row for the same proposal, each applicable within the 15-minute TTL, with `markting_engine_proposals` pointing only at the newest one. Orphaned rows show on Approvals with no engine provenance. The write is idempotent in value (absolute budget/status), so this is reliability/auditability, not double-spend.
- **Recommendation:** Before previewing, `findEngineProposal(org, id, revision)`; if a row exists with status `pending` and a live pending operation, return it instead of re-previewing; otherwise record a new revision/attempt rather than overwriting. Record hand-off failures in `detail`.

### D10-04 — Access errors are thrown after the engine proposal exists but before the hand-off, leaving the engine thread stuck; a reader-plan user then receives 403 on every later message in that thread
- **Severity:** P2  **Classification:** VERIFIED_CODE + VERIFIED_TEST (engine side)
- **Evidence:** `bridge.ts:68-70` (`tools:write` check throws `BridgeAccessError` **after** `translateProposal` succeeded and without calling `handoff`), `:71-72` and `:85-87` (same for non-write tool / no preview), `assistant.ts:339-350` (the thrown error becomes the HTTP response; `outcome.text` is discarded). Combined with the engine returning the same awaiting proposal on each later turn (probe above), every subsequent `runAssistantTurn` on that thread hits the same throw. `docs/PHASE0-REPORT.md:113` says the route "requires `tools:write`" up front; the route does not (`app/api/assistant/messages/route.ts:9-19` has no `requireScope`).
- **Impact:** A `reader`-plan member (fresh orgs default to `reader`, `docs/TODO.md:5`) can trigger a change request, lose the engine's reply, and be unable to use that thread again; the engine proposal stays `awaiting_approval` forever.
- **Recommendation:** Check `tools:write` before calling the engine (or at least before preview) and always hand the proposal back to the engine (`reject` with "not permitted") on every non-pending outcome.

### D10-05 — Meta budget conversion assumes a 2-decimal currency; alias `currency` is loaded but never used
- **Severity:** P2  **Classification:** VERIFIED_CODE (bridge/adport), INFERRED (Meta API behaviour for zero-decimal currencies)
- **Evidence:** `translate.ts:107` (`daily_budget_cents: Math.round(micros / 10_000)`), `translate.ts:52-53` ("ISO currency code … used for the human preview only"), `platform/packages/meta/src/tools.ts:152` (`'Minor currency units (cents for EUR/USD)'`), `platform/packages/meta/src/provider.ts:447-452,503-516` (upstream passes the value straight through as `daily_budget` and converts with a fixed `CENTS_TO_MICROS`; no currency offset handling anywhere in `platform/packages/meta/src`). The engine value is "account currency per day" (`engine/src/paid_media_agent/tools/write_policy.py:179`).
- **Description:** For accounts in zero-decimal currencies (JPY, KRW, …) Meta's minor unit equals the major unit, so 24 000 ¥ → 24 000 000 000 micros → 2 400 000 "cents" is interpreted as 2 400 000 ¥ (100×). The bridge inherits upstream's assumption but is the only layer that *knows* the account currency and does nothing with it. Mitigations that exist: the preview shows the provider's current value and the proposed one (a human can notice), and the default 25 % delta cap (`policy.ts:13`) would normally reject a 100× jump at preview — but the cap is nullable per organization.
- **Recommendation:** Use `binding.currency`: refuse (`unsupported`) Meta budget translations for currencies whose minor-unit exponent is not 2, or apply the correct exponent. Same review for TikTok "whole units" with 3-decimal Gulf currencies (KWD/BHD/OMR) once those providers are live.

### D10-06 — Proposal `version` and `after[].unit` are accepted but never checked; the bridge hard-codes the current semantics
- **Severity:** P3  **Classification:** VERIFIED_CODE
- **Evidence:** `translate.ts:25` (`version: z.string().optional()`, never compared to `presentation/1`), `translate.ts:21,148-151` (`unit` parsed, never read; `toMicros` always multiplies by 1e6), `engine/src/paid_media_agent/domain/presentation.py:27` (`PRESENTATION_VERSION`), `docs/ARCHITECTURE.md:826` (plan: "using each `after[]` item's `unit`").
- **Impact:** An upstream bump that changes units or the view shape would pass validation silently and be converted wrongly; the only backstop is the policy cap and the human preview. The ARCHITECTURE plan is contradicted by the code.
- **Recommendation:** Pin `version === 'presentation/1'` and require `unit` to be the known literal before converting; treat anything else as `unsupported`.

### D10-08 — Engine report surface is global: one index file, one lock, no organization scoping
- **Severity:** P2 (design; no tenant data is exposed today because the engine is fixture-only, see D10-01)  **Classification:** VERIFIED_CODE
- **Evidence:** `serve_demo.py:62,246-264` (`out/markting-reports.json` shared by all callers), `:324,344` (one `asyncio.Lock` serialises every organization's report runs), `:267-307` (`requested_by` is the token's caller, always `adport-bridge`), `platform/apps/cloud/app/api/reports/engine/route.ts:16-24` (any signed-in member of any organization lists every run) and `[name]/route.ts:10-26` (downloads any file).
- **Impact:** The moment the engine reads anything real (D10-01 fix), every organization sees and downloads every other organization's reports. The route layer has nowhere to filter because the engine records no tenant.
- **Recommendation:** Pass an organization key to `/reports/run` (header or body), index per key, and filter `GET /reports` and `/reports/files/{name}` by it; or keep one engine per tenant.

### D10-10 — `expired` provenance status is never written; apply/reject lookups scan at most 200 rows
- **Severity:** P3  **Classification:** VERIFIED_CODE
- **Evidence:** `repository.ts:62,107` define/accept `'expired'`; `rg "'expired'"` finds no caller in `lib/markting` or `app/api`. `app/api/approvals/[id]/{apply,reject}/route.ts:20,13` (`listPendingOperations(org, 200).find(...)`).

## What a world-class system would need (gaps, concrete)

1. A real data path into the engine (adport-backed read provider or live Pipeboard reads) and a hard refusal in the bridge to bind non-sandbox providers while `/health.catalog_source == "fixture"`.
2. A proposal contract: pinned `version`, mandatory `unit`, and an explicit `before`-state check at preview (engine `before[]` vs the provider's current value from the preview `changes`/`budgetDeltas`) so stale or synthetic proposals are flagged, not just previewed.
3. Exactly-once bridging: idempotency pre-check, per-attempt provenance rows (not overwrite), hand-off failure recorded, retry/reconcile job that re-rejects engine proposals left `awaiting_approval`.
4. Tenancy inside the engine: an organization key on threads and reports (or one token per organization, which `docs/TODO.md:27` already floats), per-tenant report index.
5. Currency-aware conversions driven by the alias currency (minor-unit exponent table), covering Meta minor units and TikTok whole units for 0- and 3-decimal currencies.
6. Operational tooling: alias/target admin UI with audit, `check-upstream-edits.sh` + import-symbol smoke test in CI, split per-service env files, `MARKTING_ALLOW_SELF_APPROVAL=false` by default.
7. A per-thread scripted demo (or a recorded-replay model) so the offline demo survives more than one user.
8. Asynchronous/streaming engine turns with a resumable job id, so a 240 s synchronous HTTP call is not the only transport (`engine-client.ts:219`, `assistant/messages/route.ts:7`).
