## Findings

### F5-01 — No provider client retries or backs off on 429/5xx; zero read-path tests for those statuses
- **Severity:** GAP (capability), with a P2 reliability note
- **Classification:** VERIFIED_CODE, VERIFIED_TEST
- **Evidence:** `platform/packages/meta/src/client.ts:73-87` (single `fetch`, throw on `!ok`); `platform/packages/google/src/client.ts:102-111`; `platform/packages/tiktok/src/client.ts:16-21,72-75` (rate-limit codes 40100/40133 only produce a hint string "back off and retry"); `platform/packages/microsoft/src/client.ts:166` (code 117 hint only); `platform/packages/x/src/client.ts:63` (429 message only). Grep for `retry|backoff|Retry-After` over `platform/packages/*/src/*.ts` finds no retry loop. Tests: the only 429/5xx assertions anywhere are X's non-replay checks for **writes** (`platform/packages/x/test/x.test.ts:73-78`, statuses 401/403/429/500) and `oauth.test.ts:83-88`. No provider test issues a 429 or 5xx on a **read**.
- **Description:** Every provider client is one-shot. A 429 or transient 503 during `report()` surfaces as `PROVIDER_ERROR`. The repo is consistent and honest about this for writes ("not retried", "write outcome unknown") — which is the correct safety posture — but reads have no resilience and no tests. `Retry-After` and Meta's `x-business-use-case-usage` / `x-app-usage` headers are never parsed.
- **Impact:** Reporting and audit runs over many accounts (the agentic use case) will fail noisily under normal provider throttling; nothing in the test suite would catch a regression in error classification for throttling.
- **Recommendation:** Add an idempotent-read retry policy (bounded, jittered, honouring `Retry-After`) in each client's GET path only, and tests that return 429 then 200, 503 then 200, and 429 with `Retry-After`. Keep writes non-replaying. Docs make no retry claim, so this is a gap, not a contradiction.

### F5-02 — Meta `getPaged` multi-page path is untested and follows `paging.next` without an origin check
- **Severity:** P2
- **Classification:** VERIFIED_CODE, VERIFIED_TEST
- **Evidence:** `platform/packages/meta/src/client.ts:89-116` — subsequent pages do `this.fetchImpl(url, { headers: { authorization: Bearer … } })` where `url = data.paging?.next` with no host/path validation. Compare the hardened equivalents: `platform/packages/reddit/src/client.ts:67-71` (origin must be `https://ads-api.reddit.com` and path `/api/v3/`), Snapchat tests `platform/packages/snapchat/test/snapchat.test.ts:91-99` ("rejects unsafe pagination", "detects pagination cycles"), X `x.test.ts:103-109`. Meta fixtures only ever contain `paging.cursors` (`meta.test.ts:38,59`), never `paging.next`; `platform/packages/mcp/test/meta-e2e.test.ts:74` likewise. No Meta test asserts a second page is fetched, that `maxItems` slicing works, or that a cycle terminates.
- **Description:** `getPaged` is the primary read primitive for Meta (`listAccounts`, `listPages`, `report`, `insights`, `apiRead` all use it: `provider.ts:99,113,187,252,268`), yet only its first-page branch is exercised. The Bearer token is sent to whatever URL Meta returns; the newer providers in the same repo explicitly guard against this and test it.
- **Impact:** A regression in page accumulation (duplicate rows, lost rows, infinite loop on a repeated `next`) would pass CI. The token-forwarding hazard requires a malicious or tampered Graph response, so it is defence-in-depth rather than an active exploit path, but the inconsistency with the repo's own standard is real.
- **Recommendation:** Add tests with a two-page `paging.next` chain, a `maxItems` cut-off mid-page, and a repeated `next`; validate `next` against `https://graph.facebook.com/<version>/` before sending credentials, as Reddit/Snapchat/X already do.

### F5-03 — Six providers silently cap report rows without setting `truncated`; no tests cover the limit path
- **Severity:** P2
- **Classification:** VERIFIED_CODE
- **Evidence:** Shared contract has `truncated?: boolean` (`platform/packages/core/src/model.ts:49`). Meta `report()` returns `{ rows }` after `getPaged(..., query.limit ?? 1000)` (`platform/packages/meta/src/provider.ts:181-192`); Google `search(..., { maxRows: query.limit ?? 1000 })` then `{ rows }` (`platform/packages/google/src/provider.ts:177-182`, `client.ts:140-141` slices); TikTok `page_size: Math.min(query.limit ?? 200, 1000)` single page (`tiktok/src/provider.ts:129-130`); Apple `pagination: { offset: 0, pageSize: Math.min(query.limit ?? 200, 5000) }` single page (`apple/src/provider.ts:175`). `grep -c truncated` = 0 in apple, google, meta, microsoft, reddit, tiktok `src/`. By contrast LinkedIn/Pinterest/Snapchat/Spotify/X set and **test** it (`linkedin.test.ts:171-176` 15,000-element ceiling; `pinterest.test.ts:157-160`; `snapchat.test.ts:168-176`; `spotify.test.ts:145-151`; `x/test/report.test.ts:89-95`).
- **Description:** For the six older providers, a report whose entity count exceeds the limit returns a prefix of rows that is indistinguishable from a complete report. No test in those six packages requests `limit` and checks the outcome.
- **Impact:** An AI media buyer summing `spend` across rows will under-count on large accounts and may conclude budgets are under-delivering. The audit/recommendation layer (`audit_run`) consumes these reports. This is a correctness deficiency, not a missing feature, because the shared type advertises the flag.
- **Recommendation:** Set `truncated: true` whenever the slice/page cap is hit (Meta: `items.length === maxItems && paging.next` present; Google: `nextPageToken` present at cut-off; TikTok/Apple: `total_number`/`totalCount` > returned). Add one limit test per provider mirroring the LinkedIn one.

### F5-04 — TikTok and Apple reports and entity lists fetch only page 1; no pagination tests exist for either
- **Severity:** P2 (shares root cause with F5-03)
- **Classification:** VERIFIED_CODE, VERIFIED_TEST
- **Evidence:** TikTok `report/integrated/get` built with `page: 1` and no loop over `page_info.total_page` (`platform/packages/tiktok/src/provider.ts:112,129-132`); `campaign/get` `page: 1` (`:196-197`); `apiRead` likewise. Apple `reports/apps/campaigns/query` uses `offset: 0` only (`platform/packages/apple/src/provider.ts:175`), `campaigns/query` `offset: 0` (`:125`). Tests assert the first-page request shape only (`tiktok.test.ts:117-159`, `apple.test.ts:138-199`); no fixture returns `total_page > 1` or `totalCount > pageSize`.
- **Description:** Both providers read `page_info`/`pagination` from the response but never use it to continue. Google, Meta (first page tested only, see F5-02), Reddit, LinkedIn, Pinterest, Snapchat, Spotify and X all loop.
- **Impact:** Accounts with more campaigns/ad groups/ads than one page return partial data with no signal (see F5-03).
- **Recommendation:** Loop until `page >= total_page` (TikTok) / `offset + pageSize >= totalCount` (Apple) bounded by `limit`, set `truncated`, and add two-page fixtures.

### F5-05 — Test depth is highly uneven: Reddit (8), TikTok (12) and Microsoft (13) lack coverage of entire code paths that the newer providers test routinely
- **Severity:** P3 (test-coverage deficiency; the untested paths are production write/read paths)
- **Classification:** VERIFIED_TEST
- **Evidence (source-level `it(` blocks / vitest-expanded):** x 29+20+10 → 91; pinterest 31 → 49; linkedin 34 → 46; spotify 31 → 45; snapchat 25 → 37; google 21+2 → 25; meta 23 → 23; apple 20 → 20; microsoft 13 → 13; tiktok 12 → 12; reddit 8 → 8. Reddit source is 782 lines (`wc -l platform/packages/reddit/src`), larger than Pinterest (348) or Snapchat (416), yet has one-sixth the tests. Specific holes verified by reading `reddit.test.ts` end to end: no `listCampaigns` test, no `reddit_set_campaign_status` apply, no `apiRead` happy path, no `reddit_api_create`/`reddit_api_delete` test, no non-2xx response (`grep -nE 'status: 4|status: 5' reddit.test.ts` → none), no `redditErrorMessage` mapping test, no 401/refresh-failure test, no pagination-cycle test. TikTok: no `tiktok_set_budget` apply (only preview, `tiktok.test.ts:199-220`), no `tiktok_api_delete` test, no `adgroup`/`ad` level report test, no rate-limit code test (`grep 40100|40133 tiktok.test.ts` → none), no access-token-expiry handling test (TikTok tokens are long-lived; `client.ts:4`). Microsoft: no poll-exhaustion (`pollMaxAttempts`) test, no `Status: 'Error'` test (`provider.ts:201-203`), no `Success` with `null` download URL test (`:206`), no `api_update` happy path, no `apiRead` non-campaign service.
- **Description:** The five providers added later (LinkedIn, Pinterest, Snapchat, Spotify, X) follow a visibly stricter template — malformed-success rejection, cross-account rejection, pagination cycle detection, path-injection rejection, secret-leak checks on error bodies, non-replay of writes, shared policy-gate round trip, credential-store rotation. The six original providers (Meta, Google, TikTok, Apple, Microsoft, Reddit) test the happy wire shape and the policy guard but almost none of the defensive properties.
- **Impact:** The weakest-tested providers are the ones with the broadest generic write surface (`*_api_create/update/delete`), so regressions in exactly the riskiest code are the least likely to be caught.
- **Recommendation:** Port the newer providers' defensive test template (malformed success, cross-account, cycle, path injection, secret leak, non-replay) to Reddit, TikTok and Microsoft first, then Meta/Google/Apple.

### F5-06 — Microsoft test title claims it "surfaces PartialErrors" but the fixture only ever returns `PartialErrors: []`
- **Severity:** P3
- **Classification:** VERIFIED_TEST
- **Evidence:** `platform/packages/microsoft/test/microsoft.test.ts:167-195` — title "creates campaigns via POST with Paused default and surfaces PartialErrors"; reply at `:174` is `{ CampaignIds: [9992], PartialErrors: [] }`; no assertion mentions a partial error. The production handling exists (`platform/packages/microsoft/src/provider.ts:353,391,416` call `formatPartialErrors`) but is unexercised.
- **Description:** Microsoft's bulk endpoints return HTTP 200 with per-item `PartialErrors`; a campaign create can "succeed" at the HTTP layer while the item failed. This is the one Microsoft-specific failure mode that most needs a test, and the title suggests it has one.
- **Impact:** A regression that ignored `PartialErrors` would report `applied: true` with a non-existent campaign id, and CI would stay green.
- **Recommendation:** Add a fixture with one non-empty `PartialErrors` entry and assert the write rejects with the formatted message; rename the existing test.

### F5-07 — Error mapping is tested for exactly one code per provider; rate-limit and permission codes are unmapped or untested
- **Severity:** P3
- **Classification:** VERIFIED_CODE, VERIFIED_TEST
- **Evidence:** Meta `formatMetaError` special-cases only `code === 190` (`platform/packages/meta/src/client.ts:161`); Graph rate-limit codes 4/17/32/613/80004 are rendered generically; test covers 190 only (`meta.test.ts:72-91`). Google test covers one 400 with field path (`google.test.ts:124-146`); no test for `RESOURCE_EXHAUSTED`/`QUOTA_ERROR`, nor for OAuth refresh failure (`client.ts:70-77`). TikTok hints for 40105 tested (`tiktok.test.ts:92-101`); 40102/40100/40133 untested. Microsoft 105 tested (`microsoft.test.ts:84-96`); 117 `CallRateExceeded` untested. Apple one 400 tested (`apple.test.ts:103-110`); 401 hint untested. Reddit: none.
- **Description:** Error formatting is where an agent gets its self-correction signal ("re-run connect", "wait 60s"). Coverage is a single sample per provider.
- **Impact:** Low direct risk; mainly maintainability and agent UX.
- **Recommendation:** Table-driven error-mapping tests per provider covering token-expired, permission, rate-limit, validation and unknown shapes.

### F5-08 — Minor-unit scaling is fixed per provider and only ever tested with 2-decimal currencies (EUR/USD)
- **Severity:** P3 (no present financial impact because the only policy cap is percentage-based)
- **Classification:** VERIFIED_CODE
- **Evidence:** `CENTS_TO_MICROS = 10_000` (`platform/packages/meta/src/provider.ts:20`) applied regardless of account currency; Meta budgets for zero-decimal currencies (JPY, KRW, …) are whole units, so previews would show 100× too few micros. Policy cap is `max_budget_delta_pct` only (`platform/packages/core/src/policy/policy.ts:12-13`), so from/to scale identically and the ratio check is unaffected. Apple/Microsoft/TikTok multiply decimal units by `UNITS_TO_MICROS` without rounding in several paths (`apple/src/provider.ts:316,391,436,460`; `microsoft/src/provider.ts:383,457`; `tiktok` via `UNITS_TO_MICROS`) — floating products like `1.15 * 1e6` are non-integers; only the generic-tool paths use `Math.round` (`apple:817,825`, `microsoft:555`, `meta:614`). LinkedIn alone has exact decimal conversion with precision tests (`linkedin.test.ts:180-185`, `decimalToMicros`). Every provider fixture uses EUR or USD; no test uses a 0- or 3-decimal currency. Reddit's test asserts `conversion_purchase_total_value: 2500 → 25` as "cents" (`reddit.test.ts:91-111`) — the cents assumption is **NOT_VERIFIED** against Reddit's reference from inside this sandbox. Pinterest `SPEND_IN_MICRO_DOLLAR` is treated as account-currency micros (`pinterest.test.ts:22,127`); whether the column is USD-denominated is **NOT_VERIFIED**.
- **Description:** Units work for the currencies tested. The surface for currency bugs is untested rather than known-broken.
- **Impact:** Would become P1 if an absolute budget cap (micros) is ever added to the policy; preview text already mislabels for zero-decimal Meta accounts.
- **Recommendation:** Thread account currency into Meta's minor-unit scaling (Meta exposes per-currency offsets); `Math.round` all unit→micros products; add JPY and KWD fixtures; confirm Reddit value units and Pinterest column denomination against the live references.

### F5-09 — Timezone day boundaries: two providers hard-code UTC, two compute account-local midnight with DST tests, the rest are untested
- **Severity:** P3
- **Classification:** VERIFIED_CODE, VERIFIED_TEST
- **Evidence:** Apple `timeRange: { …, timeZone: 'UTC' }` (`platform/packages/apple/src/provider.ts:177`), enshrined by `apple.test.ts:177`; Reddit `time_zone_id: 'UTC'` with `ends_at` = end+1 day (`reddit/src/provider.ts:114,412`), enshrined by `reddit.test.ts:114-116`. Snapchat `accountMidnight` with six DST/IST/PST vectors (`snapchat.test.ts:122-131`) and X `xAccountMidnight` DST + half-hour-offset rejection + timezone-switch guard (`x/test/report.test.ts:78-88`) are strong. Meta/Google/TikTok/Microsoft/LinkedIn/Pinterest pass date strings interpreted server-side in account time; untested but there is no client-side boundary logic to test.
- **Description:** Apple and Reddit reports will not reconcile to the native UI for accounts whose timezone is not UTC (every daily total shifts by the offset). The tests lock this in rather than flag it.
- **Impact:** Day-level spend anomalies and pacing checks on Apple/Reddit accounts may be off by one day's partial spend.
- **Recommendation:** Use `ORTZ` (Apple) and the ad account's `time_zone_id` (Reddit) or document the UTC choice in the report metadata; add boundary tests as Snapchat/X do.

### F5-10 — Google: developer-token omission is enshrined by test and docs but cannot be verified offline; refresh-failure and 401 paths untested
- **Severity:** P3 (NOT_VERIFIED risk, not a confirmed defect)
- **Classification:** DOCUMENTED_ONLY / NOT_VERIFIED (token policy); VERIFIED_TEST (coverage gaps)
- **Evidence:** `platform/packages/google/src/client.ts:7-8` marks `developerToken` deprecated/ignored; `:88-91` sends only `authorization` and `content-type` (plus `login-customer-id`); `google.test.ts:42-66` asserts `headers['developer-token']` is undefined. `platform/docs/providers.md:26,35` states developer tokens "were retired in September 2026". No network verification is possible from this sandbox. Coverage gaps: no test for refresh-token revocation (`client.ts:70-77` error path), no test for a 401 on an API call (code has no re-auth; cached token is reused until `expiresAt`, `:57-58`), no report test for `conversions`/`conversion_value`/`roas` or for `ad_group`/`ad` levels (`google.test.ts:477-503` covers campaign + spend/clicks/ctr only), no multi-account report test.
- **Description:** If the docs' policy claim is wrong, every Google call fails with an authentication error — and the test suite is written to *require* that behaviour. This is the single highest-leverage external fact the Google tests depend on.
- **Impact:** Binary: either fine or total Google outage. Cannot be settled here.
- **Recommendation:** Verify once against the live API from a networked environment; keep a feature flag to re-enable the header; add refresh-failure, 401, and full-metric report tests.

### F5-11 — Generic `*_api_*` tools: guard heuristics are tested with one budget field name each and never through the MCP registry except `meta_api_read`
- **Severity:** GAP (test coverage); P3
- **Classification:** VERIFIED_TEST
- **Evidence:** 23 generic tools (`grep -rhoE "name: '[a-z]+_api_[a-z_]+'"`). Per-provider generic-tool tests: Meta — `apiRead` (`meta.test.ts:387-396`), `api_create` paused coercion + `daily_budget` delta (`:398-418`), `api_delete` ownership + no DELETE in preview (`:420-435`), `api_update` cross-account + `lifetime_budget` rejection (`:437-450`). Google — `api_create` campaigns/campaignBudgets (`google.test.ts:282-322`), `api_update` budget rejection (`:315-321`), `api_remove` cross-customer (`:324-333`); **no** `api_update` happy path. Apple — `apiRead` allow/deny (`apple.test.ts:272-287`), `api_create` ×2 (`:289-352`), `api_update` monetary rejection + bulk POST (`:413-457,574-577`), `api_delete` (`:432-439`). Microsoft — `apiRead` (`microsoft.test.ts:252-262`), `api_create` (`:264-281`), `api_update` rejection (`:283-292`), `api_delete` (`:294-308`). TikTok — `apiRead` (`tiktok.test.ts:161-168`), `api_create` (`:255-271`), `api_update` rejections (`:273-283`); **no** `api_delete` test. Reddit — `api_update` budget rejection and `apiRead` POST-smuggling rejection only (`reddit.test.ts:162-183`); **no** `api_read` happy path, **no** `api_create`, **no** `api_delete`. Through MCP: `provider-surface.test.ts:57-70` asserts the names/annotations exist; `meta-e2e.test.ts:139-150` exercises `meta_api_read` end-to-end; no `*_api_create/update/delete` is called through `createMcpServer` in any test. Budget-field heuristics are each probed with a single field (`daily_budget`, `lifetime_budget`, `DailyBudget`, `budget`, `amountMicros`, `dailyBudget.value`); alternates such as Meta ad set `bid_amount`/`daily_min_spend_target`, Google `cpcBidMicros` on generic creates, TikTok `bid_price` are not tested.
- **Description:** The generic tools are the provider surface with the least structure and the most reach (arbitrary edge/path/service). Their safety relies on field-name heuristics and ownership reads; the tests demonstrate the heuristics on the canonical name only.
- **Impact:** A generic create that spends via a non-canonical field could pass `budgetDeltas: []` and never hit the percentage cap. Not shown to be exploitable here; flagged because the tests do not try.
- **Recommendation:** Property-style tests enumerating each provider's monetary field names (from the reference docs) against `*_api_create/update`; an MCP-level e2e for one generic write per provider.

### F5-12 — Positive: write safety invariants are consistently tested across all 11 providers

- **Recommendation:** Extend the registry round-trip test to TikTok, Apple, Microsoft, Google and Reddit.

## What a world-class system would need (gaps, concrete)

1. **Read-path resilience tests and code**: per provider, `429 → Retry-After → 200`, `503 → 200`, `429` with exhausted budget → typed `RATE_LIMITED` error; Meta `x-business-use-case-usage` parsing; TikTok 40100/40133 and Microsoft 117 mapped to the same typed code.
2. **Uniform pagination contract**: multi-page, cut-off mid-page, cycle detection, origin validation of `next` URLs, and `truncated` set — with the same five-test template in all 11 packages (today only 5 have it).
3. **Currency matrix**: fixtures for a 0-decimal (JPY), 2-decimal (EUR) and 3-decimal (KWD) account per provider, asserting both wire body and `budgetDeltas` micros; Meta per-currency offset handling; integer `Math.round` on every unit→micros product.
4. **Timezone matrix**: Apple `ORTZ` vs UTC, Reddit account `time_zone_id`, and DST-day fixtures like Snapchat/X for every provider that constructs timestamps.
5. **Token-lifecycle tests**: refresh-token revoked (`invalid_grant`) for Google/Microsoft/Pinterest/Snapchat/Spotify; expired long-lived token for Meta/TikTok (code 190 / 40102 on a real request path, not just the formatter); Apple JWT clock-skew.
6. **Generic-tool monetary-field enumeration**: a per-provider list of every documented money field (budgets, bids, spend caps, min-spend targets) asserted to produce a `budgetDeltas` entry or a rejection on `*_api_create/update`.
7. **Partial-success semantics**: Microsoft `PartialErrors` non-empty, Pinterest batch `exceptions` (already tested), Google `partialFailure` responses, Meta batch endpoints — each asserted to *not* return `applied: true`.
8. **Registry round-trip for every provider** (`createContext` → `registry.call` two-step) so the policy gate is exercised with the real tool schemas, not only the provider methods (currently 6/11).
9. **Contract tests against recorded live fixtures** (sanitised cassettes refreshed on a schedule) to catch API-version drift — all fixtures today are hand-written from docs ("doc-faithful", dated 2026-08).
10. **Mutation-safety fuzzing**: random field injection into generic payloads to confirm the paused/ownership/budget guards cannot be bypassed by casing or nesting.
