## Findings

### E2-01 — No resource-owner / admin revocation of MCP OAuth grants
- Severity: P1 — Classification: VERIFIED_CODE
- Evidence: `platform/apps/cloud/app/api/api-keys/route.ts:26` (grants only *listed* via `listMcpOAuthGrants`); no mutation route for `mcp_oauth_*` exists — `grep mcp_oauth platform/apps/cloud/app` returns only `getMcpOAuthClient`/`listMcpOAuthGrants`/`revokeMcpOAuthToken` and the last is reachable only from `app/oauth/revoke/route.ts:15` (RFC 7009, token holder only). `mcp-oauth-repository.ts:300-317`.
- Description: The dashboard surfaces connected MCP clients (`oauthGrants`) but provides no endpoint for an owner/admin to revoke a grant. The only revocation path is `POST /oauth/revoke`, which requires the *client* to present its own token; a resource owner has no server-side kill switch.
- Impact: A rogue, compromised, or simply unwanted MCP client cannot be disconnected by the workspace. Access tokens live 1h (`mcp-oauth-repository.ts:17`) and refresh tokens 30 days (`:18`); a stolen/abused grant remains usable for up to 30 days of continued refresh with no tenant-side remedy. For an agent that can spend ad budget, this is a serious containment gap.
- Recommendation: Add an authenticated owner/admin endpoint that sets `revoked_at` on all `mcp_oauth_refresh_tokens` and `mcp_oauth_access_tokens` for a given (client_id, user_id, resource) grant, wired to the existing dashboard listing.

### E2-02 — Refresh-token rotation has no reuse detection / family revocation
- Severity: P2 — Classification: VERIFIED_CODE
- Evidence: `platform/apps/cloud/lib/cloud/mcp-oauth-repository.ts:239-255`. A presented refresh token that is already `consumed_at` is accepted inside a 60s grace (`:22`, `:239-240`) and rejected afterwards (`:241-243`) — but reuse never triggers revocation of the descendant/family tokens.
- Description: RFC 9700 §4.14.2 recommends that detected reuse of a rotated refresh token revoke the entire token family. Here a consumed token used after 60s is merely rejected; the legitimately-rotated chain keeps working and the reuse is not treated as a breach signal.
- Impact: Classic refresh-token theft: an attacker who steals a refresh token and redeems it *before* the legitimate client rotates obtains a fresh valid pair; the victim's next rotation still succeeds within 60s and then starts failing (`already rotated`), silently locking out the legitimate client while the attacker holds live credentials. No automated detection or containment occurs.
- Recommendation: On presentation of a `consumed_at` refresh token outside the grace window, revoke all refresh+access tokens for that (client_id, user_id, resource) and log a security event, rather than only rejecting the single request.

### E2-03 — Token revocation does not cascade between access and refresh tokens
- Severity: P2 — Classification: VERIFIED_CODE
- Evidence: `platform/apps/cloud/lib/cloud/mcp-oauth-repository.ts:300-317` — revoking an access token updates only `mcp_oauth_access_tokens` (`:304-307`); revoking a refresh token updates only `mcp_oauth_refresh_tokens` (`:313-316`).
- Description: RFC 7009 §2.1 states that revoking a refresh token SHOULD invalidate access tokens derived from it where feasible. Neither direction cascades here.
- Impact: After a client revokes its refresh token, already-issued access tokens remain valid until their 1h expiry (and are DB-checked but not marked revoked), leaving a window of continued authorized access after an explicit revoke. Conversely, revoking an access token leaves the refresh token live to mint new ones.
- Recommendation: In `revokeMcpOAuthToken`, when a refresh token is revoked also revoke access tokens for the same (client_id, user_id, resource); optionally revoke the sibling refresh token when an access token is revoked.

### E2-04 — Consent endpoint relies on cookie SameSite, no explicit anti-CSRF token
- Severity: P3 — Classification: INFERRED
- Evidence: `platform/apps/cloud/app/oauth/authorize/consent/route.ts:5-24` — `POST` reads the authorization params from form fields, calls `sessionPrincipal()` (`:20`), and mints an auth code to the registered `redirect_uri` with no CSRF/nonce check. Cookie attributes are Supabase `@supabase/ssr` defaults (SameSite=Lax); not overridden in `platform/apps/cloud/lib/supabase/server.ts:10-21` (cannot verify runtime value → INFERRED).
- Description: The only barrier between a logged-in session and an issued authorization code is the consent POST. There is no anti-forgery token binding the POST to the GET consent render. Dynamic client registration is open (see E2-06), so an attacker can pre-register a client with their own `redirect_uri` + `code_challenge`.
- Impact: If the Supabase session cookie is ever served with `SameSite=None` (or a future config change), a cross-site auto-submitting form could cause a logged-in victim's browser to mint and deliver an authorization code to the attacker's redirect URI (attacker knows the verifier), yielding tokens bound to the victim's org without informed consent. With the Lax default this is blocked, so this is defense-in-depth today.
- Recommendation: Add a per-session signed CSRF token embedded in the consent form and verified on POST; pin the Supabase cookie `sameSite` explicitly to `lax`/`strict` in code.

### E2-05 — Bounded 60s refresh-token replay window (documented tradeoff)
- Severity: P3 — Classification: VERIFIED_CODE
- Evidence: `platform/apps/cloud/lib/cloud/mcp-oauth-repository.ts:19-22,239-240`.
- Description: A consumed refresh token is deliberately accepted for 60s to let concurrent scheduled clients complete. This is intentional and documented. Each acceptance mints a fresh pair.
- Impact: A 60-second replay window for a captured refresh token. Low risk given rotation and the 60s bound; raised here for completeness and because it slightly weakens the reuse-detection that E2-02 recommends.
- Recommendation: Acceptable if E2-02 is implemented (reuse outside the window should then revoke the family). Consider narrowing the grace or scoping it to the same client fingerprint.

### E2-06 — Open dynamic client registration (observation, per spec)
- Severity: GAP — Classification: VERIFIED_CODE
- Evidence: `platform/apps/cloud/app/oauth/register/route.ts:6-22` — unauthenticated `POST`, rate-limited 20 per 60s per forwarded-IP (`:8-11`, `repository.ts:355`). Redirect URIs validated (`lib/mcp-oauth.ts:80-99`): HTTPS or loopback HTTP only, no creds/fragment, no duplicates.
- Description: Anyone may register an MCP client (standard for MCP/OAuth DCR). Combined with E2-01 (no admin revocation) this enlarges the blast radius of a tricked consent.
- Impact: Not a defect by itself; amplifies E2-01/E2-04. The per-IP limit is weak against distributed registration.
- Recommendation: Keep registration open per spec but ensure E2-01 lands; consider a global/registration cap and pruning of unused clients.

## What a world-class system would need (gaps, concrete)
- Owner/admin "disconnect this app" that server-side-revokes all tokens for a grant (closes E2-01).
- Refresh-token reuse detection with full-family revocation and a security audit event (closes E2-02).
- Revocation cascade across access/refresh tokens (closes E2-03).
- Explicit CSRF token on the consent form + explicit cookie SameSite (closes E2-04).
- Audit events for authorize/exchange/refresh/revoke beyond the current `console.info` diagnostics (`token/route.ts:18-19`).
- Consider mTLS/DPoP sender-constrained tokens for high-value automation; current bearer tokens are bearer-only.

## Disagreements / claims in docs that the code contradicts
- The MCP OAuth header comment and surrounding design imply standard refresh rotation security; the code omits the reuse-detection/family-revocation that RFC 9700 expects (E2-02). Not a false doc claim, but the implementation is weaker than the "rotation" framing suggests.
- `listMcpOAuthGrants` docstring (`mcp-oauth-repository.ts:45-49`) calls grants "credential metadata" visible to the tenant; the product exposes visibility but no revocation action, which users would reasonably expect from such a list (E2-01).
- No code contradicts the broker's stated guarantees ("state is single-use, hashed at rest, bound to the signed-in user and organization, expires in ten minutes"; `start/route.ts:14-18`) — VERIFIED_CODE against `repository.ts:58-104`.
