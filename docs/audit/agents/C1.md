# C1 — LangGraph / Deep Agents architect

Audit of the engine's agent graph: how `paid_media_agent` assembles a Deep Agent, what state and
nodes the compiled LangGraph has, which tools are bound, how interrupts/retries/timeouts/limits
work, which checkpointer each runtime uses, how the system prompt and skills are constructed, and
how thread/caller identity flows. Repository code is the source of truth; docs are claims that
were checked against it. Paths are relative to `/home/user/markting-ai`.

Pinned versions (VERIFIED_RUNTIME, `engine/.venv`): deepagents 0.7.12, managed-deepagents (no
`__version__`, lock `>=0.6.1,<0.7`), langchain 1.3.18, langgraph 1.2.11
(`engine/pyproject.toml:20-25`).

### Tools bound to the model (fixture catalog: 21; VERIFIED_RUNTIME)

- Core (5, always included): `list_accounts`, `discover_tools`, `compare_periods`,
  `summarize_window`, `render_report` (`assembly.py:60-66,201-207`).
- Writes (4, always included): `discover_write_operations`, `propose_change`, `execute_change`,
  `get_proposal` (`assembly.py:67-72`; implementations `tools/write_tools.py:117-236`).
- Platform reads: one `StructuredTool` per READ catalog entry, account id replaced by
  `account_alias` (`tools/reads.py:111-128`); 12 with the fixture catalog (`metadata.read_tool_count`).
  Mutations are never bound (`tools/catalog.py:224-225`; test
  `engine/tests/contract/test_read_path_graph.py:186`).
- Deep Agents filesystem tools reach the model: `ls, read_file, write_file, edit_file, glob, grep`
  are allowed (`assembly.py:59,211`); `execute`, `delete` and the subagent `task` tool are registered
  by deepagents (filesystem tool names `delete, edit_file, execute, glob, grep, ls, read_file,
  write_file`; general-purpose subagent auto-added at `deepagents/graph.py:524-525`) but hidden from
  the model request and denied on call (`middleware/authorization.py:22,58-93`).
- Selection: `anthropic:*`/`openai:*` without `base_url` → `ProviderToolSearchMiddleware` over the
  platform read tools; others → `PortableToolSelectorMiddleware` (`LLMToolSelectorMiddleware`
  subclass, `max_tools=PAID_MEDIA_MAX_SELECTED_TOOLS=6`, fail-closed to core tools on an invalid

### Interrupt protocol (VERIFIED_CODE + VERIFIED_TEST)

- Only `execute_change` is under `interrupt_on`; `allowed_decisions=["approve","reject"]` (no `edit`)
  and `when` = the `proposal_id` argument belongs to the current `thread_id`
  (`tools/write_tools.py:82-114`). `thread_id` comes from `get_config()["configurable"]` inside the
  HITL predicate (`langchain/.../human_in_the_loop.py:372-403`).
- The interrupt fires in `HumanInTheLoopMiddleware.after_model`, i.e. after the model emits the
  tool call and before the `tools` node; the checkpoint is written there.
- Resume: `AgentRunner.resume` sends `Command(resume={"decisions":[{"type": decision[, "message"]}]})`
  with the **requester's** `caller_ref` (`surfaces/runner.py:215-232,242-255`). `approve` first
  creates the signed claim host-side (`ProposalService.approve`, `tools/writes.py:514-551`); a
  rejection is persisted before the resume so the `when` predicate stays stable
  (`write_tools.py:85-88`).
- Inside the resumed tool: if no host claim exists for the current revision (the MDA card path), the
  tool self-approves as the acting caller only when the frozen `revision` argument still matches
  (`write_tools.py:164-181`); `ApprovalPolicy.may_approve` then requires that caller to be in
  `PAID_MEDIA_APPROVER_IDS` and not the requester unless self-approval is enabled
  (`writes.py:129-141`). Proven by `tests/contract/test_write_flows_graph.py:56-114,258-273`
  (these pass once the stray kill switch is out of the way; see C1-06).
- Resume to `reject` yields a HITL-generated ToolMessage and the model gets one more turn
  (`human_in_the_loop.py:337-355`).

### Thread / caller configuration

- Self-hosted/API: `RunnableConfig(configurable={"thread_id", "caller_ref"})`, thread ownership is
  first-caller-wins in `ThreadOwnershipStore` (`runner.py:86-89`; `persistence/memory.py:87-96`;
  `persistence/postgres.py:226-244`). Tools read `runtime.config["configurable"]["caller_ref"]`,
  defaulting to `"local-user"` and `"local-thread"` (`write_tools.py:57-67`).
- MDA: `managed_deepagents` wraps every authored tool so `runtime.identity` is present
  (`_managed_tools.py:174-200`, `runtime.py:848-859`); the engine then uses `identity.user.id`, or
  `"anonymous"` (`write_tools.py:62-66`). `langchain.tools.ToolRuntime` has no `identity` field in
  1.3.18 (fields: state, context, config, stream_writer, tool_call_id, store, tools, execution_info,
  server_info), so the branch is never taken locally (VERIFIED_RUNTIME).
- markting-ai: one token → one `caller_ref` (`adport-bridge`, `docker-compose.yml:49`); thread ids
  are `org_<org>__u_<user>__<id>` built by adport (`docs/PHASE1-REPORT.md:13`). The engine therefore
  has no tenant notion of its own (README.md:128 says so).

## Findings

### C1-01 — The engine in markting-ai can only ever analyse synthetic accounts, in `demo` and `live` mode alike
- Severity: P2 (product coherence / misleading capability); Classification: VERIFIED_CODE; capability: MOCK_ONLY
- Evidence: `services/engine-demo/serve_demo.py:383-388` sets `paid_media_data_mode="sample"` in both
  modes; `serve_demo.py:163-166` refuses to boot otherwise; `engine/src/paid_media_agent/runtime/catalog.py:51-58`
  returns the fixture catalog and `read_provider=None` for `sample`; `runtime/profiles.py:72-77`
  loads `config/accounts.example.toml` in `sample` mode; compose pins `PAID_MEDIA_DATA_MODE: sample`
  (`docker-compose.yml:48`).
- Description: `MARKTING_ENGINE_MODE=live` only swaps the scripted model for a real LLM
  (`serve_demo.py:224`). The catalog, accounts and reads stay the three fixture accounts
  (`demo-google`, `demo-meta`, `demo-reddit`). A tenant with real OAuth connections in adport gets
  Assistant answers and engine reports about synthetic data.
- Impact: any marketing of "AI analysis" of the customer's accounts is not backed by this code path;
  `docs/PHASE1-REPORT.md:42` ("Live mode has no such limit") reads as if live mode were
  unrestricted, which is true only for the script, not the data.
- Recommendation: state the limitation in README/ARCHITECTURE explicitly; a real product needs either
  Pipeboard credentials per tenant with a per-tenant engine process (the engine's profile is
  process-global) or an adport-backed `ReadProvider` implementation — both are design work, not a fix.

### C1-02 — Catalog is loaded once per process, partial failures are silent, and nothing re-loads it
- Severity: P2 (reliability; dormant in markting-ai because `sample` mode never calls Pipeboard); Classification: VERIFIED_CODE
- Evidence: `tools/pipeboard.py:95-99` (`current()` returns the one snapshot), `:111-121` (per-endpoint
  failure logged at WARNING and replaced by `[]`), `runtime/mda.py:55` (one `load_catalog` per
  assembly), `agent.py:12-13` (runs at module import for MDA).
- Impact: a 20 s hiccup on one Pipeboard endpoint at boot removes that platform's read tools for the
  life of the process; the model is told nothing. Writes are protected because the revision hash
  changes and `WriteGate.check` refuses `stale_catalog` (`tools/writes.py:189-193`), but analyses
  silently omit platforms. Single point of failure for every live deployment profile.
- Recommendation: surface partial loads in `/health` and `metadata.catalog_source`; add a bounded
  refresh (operator-triggered or on `unknown_tool`) that re-assembles the read tools.

### C1-03 — No per-thread serialization of graph runs
- Severity: P2 (reliability / state corruption); Classification: VERIFIED_CODE (absence), INFERRED (effect)
- Evidence: `surfaces/runner.py:150-213` runs `ainvoke`/`astream` directly after `claim()`;
  `grep -rn "Lock\|Semaphore" engine/src/paid_media_agent/{surfaces,runtime,assembly.py}` is empty;
  the host's only lock guards `/reports/run` (`serve_demo.py:324,344`).
- Impact: two concurrent `POST /threads/{id}/messages` for the same thread (same `caller_ref`, which
  in markting-ai is always `adport-bridge`) run two graph executions over one checkpoint; the
  second may resume an interrupt the first is still producing, or interleave messages.
- Recommendation: a per-`thread_id` asyncio lock (single process) or a Postgres advisory lock
  (multi-process) in `AgentRunner`; or make the adport route serialize per thread (not verified).

### C1-04 — No end-to-end run deadline; API calls are synchronous
- Severity: P2 (operability); Classification: VERIFIED_CODE
- Evidence: bounds are per-call only — model 120 s × `max_retries=2` SDK retries × 3 middleware
  attempts (`assembly.py:166,240`), reads 60 s (`tools/reads.py:40`), mutation 30 s and readback 20 s
  (`tools/writes.py:67-70`), 40 model calls per run (`config.py:120`); `runner.send` awaits the whole
  run (`runner.py:208-213`); `on_event` streaming is used only by Slack.
- Impact: a single HTTP request can legitimately last tens of minutes; uvicorn/adport timeouts will
  cut the response while the graph keeps running and checkpointing (`docs/PHASE0-REPORT.md:88`
  acknowledges). In `scripted:` mode there is no call limit at all (`assembly.py:236`).
- Recommendation: a wall-clock budget per run (cancel + checkpoint), and background execution with
  polling or streaming for the HTTP surface.

### C1-05 — Blocking Postgres pool inside the async graph
- Severity: P3; Classification: VERIFIED_CODE
- Evidence: `persistence/postgres.py:52` (sync `psycopg_pool.ConnectionPool`, `max_size=4`) used from
  async tools (`write_tools.py:118-185` → `writes.py` repository calls) and from `AgentRunner`
  (`runner.py:91-93,134-138`); the checkpointer uses a separate async pool also capped at 4
  (`runtime/self_hosted.py:52-58`).
- Impact: every proposal/claim/receipt query blocks the event loop; the two pools cap concurrency at
  four connections each regardless of load.
- Recommendation: psycopg async repositories or `asyncio.to_thread` wrappers; size pools from config.

### C1-06 — A stray `engine/workspace/KILL_SWITCH` makes the upstream test gate fail in this checkout
- Severity: P3 (CI/DX; it also masks the real write-flow coverage); Classification: VERIFIED_TEST
- Evidence: `uv run --frozen pytest -q` → 19 failed / 158 passed / 3 skipped. Failing tests:
  `tests/behavior/test_scripted_behavior.py::test_demo_uses_the_fixture_anchor_and_fails_on_unreconciled_analysis`;

### C1-07 — Demo model is process-global, not thread-safe, and is the default production path
- Severity: P3 (demo-code-on-production-path); Classification: VERIFIED_CODE (race inferred)
- Evidence: one `LoopingScriptedChatModel` instance per process (`serve_demo.py:194-198,224-227`)
  keeps `seen_human_messages`, `steps`, `call_count` as instance state (`serve_demo.py:92-115`);
  compose defaults `MARKTING_ENGINE_MODE` to `demo` (`docker-compose.yml:52`).
- Impact: two users chatting concurrently in demo mode reset each other's script position
  (`len(humans) != self.seen_human_messages` flips between threads), producing out-of-order tool
  calls or the "Script exhausted" text mid-flow. Harmless for safety (fixture provider, proposal-only)
  but visible to every multi-user demo tenant.
- Recommendation: key script state by `thread_id` (available in `RunnableConfig`), or instantiate the
  model per run.

### C1-08 — Deep Agents summarization writes conversation history outside the workspace, undocumented
- Severity: P3; Classification: VERIFIED_CODE (path), INFERRED (occurrence)
- Evidence: `deepagents/graph.py:617` always installs `_DeepAgentsSummarizationMiddleware`; with a
  plain `FilesystemBackend` the history prefix is `/conversation_history` and
  `/large_tool_results` (`deepagents/middleware/summarization.py:608-611`), i.e. `<project_root>/conversation_history/`
  — outside `workspace/`, outside the compose volume (`docker-compose.yml:53-55`), and not in
  `engine/.gitignore`. Trigger: 85 % of the model's context (`compute_summarization_defaults`).
- Impact: long threads will persist (already-redacted) prompts and tool outputs into the image
  layer/repo root; lost on container restart, and the summary tells the model to `read_file` a path
  that may no longer exist. None of `engine/docs/architecture/*.md` mentions summarization.
- Recommendation: use a `CompositeBackend` with `artifacts_root="/workspace"` or exclude the
  middleware explicitly; document the behaviour.

### C1-09 — Engine-level tenant boundary is a single shared caller and a shared artifact store
- Severity: P3 at the engine boundary (cross-tenant exposure depends on adport's route checks — out of this workstream's scope); Classification: VERIFIED_CODE + INFERRED
- Evidence: one `caller_ref` for all tenants (`docker-compose.yml:49`); thread ownership is
  first-caller-wins with caller-chosen ids (`runner.py:86-89`); one `ArtifactStore(workspace)` for all
  threads (`runtime/profiles.py:143`); `compare_periods`/`summarize_window` take model-supplied
  artifact ids guarded only by the 64-bit random id format (`tools/artifacts.py:17`);
  `GET /reports/files/{name}` serves any `rpt_*` to any valid bearer (`serve_demo.py:360-374`).
- Impact: the engine cannot distinguish organisations; a bug or injection in the bridge's thread-id
  construction (`org_<org>__u_<user>__<id>`) is not caught engine-side. README.md:128 and
  `docs/TODO.md:27` acknowledge this design.
- Recommendation: per-tenant `caller_ref` tokens (TODO item) and tenant-prefixed artifact/report
  directories, or an engine-side thread-id namespace check.

### C1-10 — Timeouts, limits and recursion budget differ by runtime and are documented nowhere
- Severity: P3 (documentation); Classification: VERIFIED_CODE / VERIFIED_RUNTIME
- Evidence: `recursion_limit` 9,999 locally/self-hosted (`deepagents/graph.py:700`) vs 200 under MDA
  (`managed_deepagents/runtime.py:182`); `ModelTimeoutMiddleware` sync no-op (`timeout.py:27-28`);
  `ModelRetryMiddleware(on_failure="continue")` turns exhausted retries into an assistant message
  (`model_retry.py:197-219`) so a dead model key returns HTTP 200 with error prose
  (`docs/PHASE0-REPORT.md:57` observed exactly this); no thread-level model-call limit.
- Impact: operators cannot reason about worst-case run time; the 40-call limit ends a run with no
  user-visible explanation other than what the model last said.
- Recommendation: an "Operational limits" section in `engine/docs/architecture/runtime-profiles.md`
  and a terminal note in `RunOutcome` when the call limit or retry exhaustion ended the run.

### C1-11 — MDA profile keeps proposals, claims and receipts in process memory
- Severity: GAP (documented) with P2 consequence if MDA were used for writes; Classification: VERIFIED_CODE
- Evidence: `build_mda_components` → `configured_profile` → `fixture_profile` with
  `InMemory*Repository` defaults and no override (`runtime/mda.py:57-82`, `runtime/profiles.py:153-155`);
  the ephemeral signer when `PAID_MEDIA_APPROVAL_SIGNING_KEY` is unset (`profiles.py:104-109`).
  `engine/docs/architecture/runtime-profiles.md:56` admits "in-memory proposal state per process".
- Impact: a pending `execute_change` interrupt survives in MDA's checkpointer, but after a worker
  restart the proposal it references is gone → `unknown_proposal` denial. Not used by markting-ai.

## What a world-class system would need

1. A run-level budget (wall clock + tokens) that cancels cleanly, checkpoints, and reports *why* the
   run stopped (limit, retry exhaustion, timeout) in `RunOutcome`, plus HTTP streaming or a job model
   so the bridge never holds a multi-minute request.
2. Per-thread execution locks and idempotent message ingestion (the Slack path has `dedupe`; the API
   path has none).
3. A tenant-aware runtime: per-organisation credentials, catalog, accounts, artifacts and
   `caller_ref`, or one engine process per tenant — today the profile is process-global.
4. Catalog lifecycle management: health reporting of partial loads, controlled refresh with
   re-binding of read tools, and alerting when the revision drifts from the pinned one.
5. Observability of the graph: LangSmith tracing is implied by README but the self-hosted path has
   no tracing or metrics configuration in code (`grep -rn langsmith engine/src` only finds the
   `langsmith:` model prefix and the sandbox client) — NOT_VERIFIED whether env-based tracing is
   intended.
6. Documentation of the full middleware stack including the Deep Agents base (summarization,
   patching, prompt caching, the hidden general-purpose subagent) and of the recursion/limit
   differences between MDA and self-hosted.
7. Async persistence and pool sizing driven by configuration (C1-05).
