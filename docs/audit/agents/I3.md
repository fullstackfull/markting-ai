## Findings

### I3-01 — No usage metering of AI/LLM turns or report runs; the dominant variable cost is unbilled and uncapped per plan
- Severity: P1
- Classification: VERIFIED_CODE
- Evidence: `platform/apps/cloud/app/api/assistant/messages/route.ts:13`; `platform/apps/cloud/app/api/reports/engine/route.ts:32`; `platform/apps/cloud/lib/cloud/repository.ts:355`; `platform/apps/cloud/lib/cloud/plans.ts:23-44`; grep for `usage_event|quota|meter|usage_record|billMeterEvent` returned no billing-metering code.
- Description: The product is an "AI media buyer": every Assistant turn (`runAssistantTurn`, `assistant.ts:28`) and every report run forwards to the paid-media engine, which runs an LLM — the main variable cost. The only guard is a flat, plan-independent rate limit of 120 requests/minute per org+user (`enforceRateLimit(subject, limit=120, windowSeconds=60)`, repository.ts:355). There is no per-org daily/monthly cap, no token/cost accounting, no `usage_events` table, no Stripe metered price / `billMeterEvent`, and no plan field that bounds AI calls or reports. Plans gate only static resources (accounts/members/retention/write — plans.ts:11-44).
- Impact: Unbounded LLM/engine cost per organization on every tier, including Free `reader` (a signed-in reader is not blocked from Assistant turns or report GET — only tools:write and the viewer role are gated). Margins are unprotected; a single org can consume 120 engine turns/minute indefinitely. No data exists to later bill usage or detect abuse. This is a serious financial-risk gap for a usage-heavy AI SaaS.
- Recommendation: Add a `private.usage_events` table (org_id, user_id, kind in {assistant_turn, report_run, engine_tokens}, quantity, cost_micros, occurred_at, idempotency_key) written in the same transaction as the audited action; add per-plan monthly quotas (new `maxAiTurns`/`maxReports`/`tokenBudget` columns on `PlanDefinition`) enforced at the assistant/report routes with a 402 `PlanLimitError`; optionally wire Stripe metered billing (`billMeterEvent`) for overages. Meter engine token usage returned by the engine, not just request counts.

### I3-02 — Churned (fully canceled) customers are locked out of re-subscribing in-app
- Severity: P2
- Classification: VERIFIED_CODE
- Evidence: `platform/apps/cloud/app/dashboard/billing/actions.ts:19`; `platform/apps/cloud/lib/cloud/billing.ts:84-85`; `platform/apps/cloud/lib/cloud/plans.ts:64,77`; `platform/apps/cloud/test/database.integration.test.ts:238` (after `customer.subscription.deleted` the row keeps `plan='operator'` with `status='canceled'`).
- Description: `startSubscription` refuses with "Manage the existing subscription in the billing portal." whenever `entitlement.providerSubscriptionId` is set (actions.ts:19). On `customer.subscription.deleted`, `applySubscription` writes `provider_subscription_id = subscription.id` (billing.ts:85) and does not clear it, and `getOrganizationEntitlement` returns that id regardless of status (plans.ts:64). The integration test confirms the row retains the (now-dead) subscription id and a `canceled` status. The Stripe billing portal cannot resurrect a deleted subscription, so a fully-churned org has no in-app path back to a paid plan.
- Impact: Revenue recovery / reactivation is broken for churned customers; they fall back to Free with no self-serve way to resubscribe. Support must intervene.
- Recommendation: Gate `startSubscription` on an *active-ish* subscription (status in active/trialing/past_due/unpaid) rather than the mere presence of `providerSubscriptionId`; or clear `provider_subscription_id` on `customer.subscription.deleted` while preserving `provider_customer_id` for reuse.

### I3-03 — Webhook idempotency guard is not atomic with the effect it protects
- Severity: P2
- Classification: VERIFIED_CODE
- Evidence: `platform/apps/cloud/lib/cloud/billing.ts:119-138` (duplicate `select` at 120-123, `applySubscription` at 129, `billing_events` insert at 132-136 — outside the `db().begin` transaction in applySubscription at 78-116).
- Description: `processStripeEvent` checks `private.billing_events` for the event id, then calls `applySubscription` (its own transaction), then inserts the event id in a *separate* statement afterward. The dedup read and the effect are not in one transaction, and the dedup write happens after the effect commits. Two concurrent deliveries of the same event (Stripe retries; at-least-once delivery) can both pass the select and both run `applySubscription`. A crash between the applySubscription commit and the `billing_events` insert causes the next retry to reprocess.
- Impact: Duplicate processing on retry/concurrency: repeated account downscaling (idempotent in effect but re-disables) and, more visibly, duplicate `subscription_updated` audit events (one per reprocess). Weakens the "exactly once" claim.
- Recommendation: Insert the `billing_events` row inside the same transaction as `applySubscription` before applying the effect, relying on the `event_id` primary key + `on conflict do nothing` to short-circuit duplicates atomically (treat 0 rows inserted as "duplicate, skip").

### I3-04 — Webhook applies events without ordering/recency guards (out-of-order Stripe delivery can regress state)
- Severity: P2
- Classification: VERIFIED_CODE
- Evidence: `platform/apps/cloud/lib/cloud/billing.ts:57-89` (`applySubscription` unconditionally overwrites plan/status/period from whatever event arrives); `processStripeEvent:126-131` handles created/updated/deleted identically.
- Description: Stripe does not guarantee webhook ordering. `applySubscription` always overwrites the subscription row with the current event's fields and never compares against the stored state or an event/`created` timestamp. A stale `customer.subscription.updated` delivered after a newer one (or a late `created` after an `updated`) overwrites the row with older data.
- Impact: Entitlement can regress (e.g., a late event re-activating a canceled plan or reverting a plan change), causing incorrect access and account enable/disable churn.
- Recommendation: Guard the update with the subscription's monotonically-advancing data — e.g., only apply if the incoming event is newer (store `last_event_at`/Stripe `created`), or re-fetch the subscription from Stripe inside the handler and apply the authoritative current state rather than the event payload.

### I3-05 — Free `reader` tier and `past_due` both retain full engine access; no payment-failure downgrade path
- Severity: P2
- Classification: VERIFIED_CODE
- Evidence: `platform/apps/cloud/lib/cloud/plans.ts:77` and `billing.ts:91` (`['active','trialing','past_due'].includes(status)` keeps the paid plan); no handler for `invoice.payment_failed` in `processStripeEvent` (billing.ts:126-131); Assistant/report routes do not check `writeAccess`/plan, only role and the flat rate limit (assistant route.ts:13; reports route.ts:31-32).
- Description: `past_due` orgs keep full entitlement, and there is no `invoice.payment_failed`/dunning-driven downgrade — the code relies solely on Stripe eventually sending `unpaid`/`canceled` via `subscription.updated`. Separately, because AI turns/reports are ungated by plan (see I3-01), a Free org consumes paid engine capacity.
- Impact: A delinquent customer keeps full paid access (including unmetered AI cost) for the entire dunning window; Free users consume paid-cost AI. Financial leakage.
- Recommendation: Decide the dunning policy explicitly (e.g., restrict after N days past_due), and combine with I3-01 metering so the cost ceiling is enforced regardless of billing status.

### I3-06 — Demo seed grants a paid plan by direct DB write with no environment guard
- Severity: P3
- Classification: VERIFIED_CODE
- Evidence: `infra/seed/seed-demo.mjs:44` (`update public.organization_subscriptions set plan = 'operator', status = 'active' ...`); no `NODE_ENV`/host guard (script reads whatever `.env` path is passed, lines 13-18).
- Description: The demo seed bypasses Stripe entirely and sets `plan='operator', status='active'` directly in `organization_subscriptions`. This is a legitimate local-dev convenience (documented at seed-demo.mjs:1-8), but it has no guard preventing it from being pointed at a production database — it simply uses the `SUPABASE_DB_URL`/service key from the supplied `.env`. Entitlement for this org then has no `provider_subscription_id`, so it is never reconciled by webhooks.
- Impact: Operationally risky: running the dev seed against prod (or reusing a prod `.env`) grants a free, Stripe-less paid plan that billing never reconciles. Not reachable from app runtime code, so not a production code defect, but a foot-gun.
- Recommendation: Guard the seed (refuse unless the DB URL is localhost / an explicit `MARKTING_ALLOW_SEED=1`), and document that seeded orgs are unbilled.

### I3-07 — `applySubscription` trusts `subscription.metadata.organizationId` without binding it to the customer
- Severity: P3
- Classification: VERIFIED_CODE
- Evidence: `platform/apps/cloud/lib/cloud/billing.ts:60,66-74` (metadata path short-circuits the customer/subscription lookup and does not verify `customerId` matches the org's existing `provider_customer_id`).
- Description: When `subscription.metadata.organizationId` is present it is used directly as the target org, skipping the `provider_subscription_id`/`provider_customer_id` lookup, with no check that the customer actually belongs to that org. In the normal flow metadata is written by our own Checkout (actions.ts:28-31) and events are Stripe-signature-verified (webhook route.ts:9), so this is low risk. But because `provider_customer_id`/`provider_subscription_id` are `UNIQUE` (migration 20260828120000:9-10), a mismatched write can also throw a unique-violation and fail the webhook.
- Impact: Low in practice (metadata is first-party and signed), but the missing cross-check removes defense-in-depth and can surface as webhook failures on edge cases.
- Recommendation: After resolving via metadata, assert the resolved org's stored `provider_customer_id` is null or equals the event's customer id before overwriting.

### I3-08 — `applySubscription` webhook path (status mapping, downscaling, canceled handling) is not exercised by a runnable unit test
- Severity: GAP
- Classification: VERIFIED_TEST
- Evidence: Only `platform/apps/cloud/test/database.integration.test.ts:193-241` covers `processStripeEvent` (a `customer.subscription.deleted` downscaling case), and it requires a live Supabase DB (not runnable in this sandbox). `test/billing-actions.test.ts` covers only Checkout; `subscriptionStatus` mapping, trial/active transitions, multi-account downscaling boundaries, and the premium plan have no fast unit coverage.
- Description: The most financially sensitive code (entitlement transitions, account disabling) depends on an integration test against Postgres; there is no pure unit test over `subscriptionStatus`/downscaling math/`getOrganizationEntitlement` thresholds.
- Impact: Regressions in status mapping or the `slice(maxActiveAccounts)` downscaling boundary can ship undetected in environments without the DB-backed integration suite.
- Recommendation: Add unit tests for `subscriptionStatus` over all Stripe statuses, `getOrganizationEntitlement` downgrade boundaries, and the downscaling slice with off-by-one cases.

## What a world-class system would need (gaps, concrete)
- A `private.usage_events` ledger (append-only, idempotency-keyed) written in-transaction with each billable action, plus a rollup (`organization_usage_monthly`) for fast quota checks and dashboards.
- Per-plan quota columns (`maxAiTurnsPerMonth`, `maxReportsPerMonth`, `tokenBudget`/`costBudgetMicros`) enforced at the assistant/report routes with 402 + `PlanLimitError`, and surfaced in the UI as a usage meter.
- Stripe metered/graduated prices + `billMeterEvent` (or invoice line items) for overage, reconciled from the ledger; token cost captured from the engine response, not request counts.
- Atomic webhook processing (dedup insert inside the effect transaction) and ordering/recency guards (store Stripe `created`/`last_event_at` or re-fetch authoritative state).
- Explicit dunning policy driven by `invoice.payment_failed`/`customer.subscription.updated(past_due/unpaid)` with a grace window and automated downgrade.
- A clean reactivation path for churned customers (I3-02), and trial-abuse controls (currently one trial per org, but a user can create unlimited orgs → unlimited 7-day trials: actions.ts:19 + per-org subscription row).
- Enforcement (or removal) of the `clientWorkspaces` plan flag.

## Disagreements / claims in docs that the code contradicts
- `docs/billing.md` and `docs/ARCHITECTURE.md` describe the billing system as complete adport plumbing ("five plans… Stripe Checkout… webhook… duplicate protection via private.billing_events"). The code matches at the surface, but: (a) the "duplicate protection" is not atomic with the effect (I3-03); (b) neither doc acknowledges that there is **no usage metering** for the AI/report workload the product is built around (I3-01) — a material omission for an "AI media buyer" billing story; (c) `clientWorkspaces` is presented as an Agency/Enterprise feature but is not enforced in code.
- No doc claims metering exists, so there is no direct contradiction on that point — rather a documented-feature vs. business-need gap.
- `docs/TODO.md`/`PHASE0-REPORT.md` correctly state the demo seed sets the plan directly in the DB; this matches `seed-demo.mjs:44` (no contradiction, but see I3-06 for the missing guard).
