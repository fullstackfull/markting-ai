## Findings

### D7-01 — PolicyEngine.apply has no atomic claim: concurrent applies of one pending id execute the provider write twice
- Severity: **P1** (serious financial risk; duplicate live writes of an operation that was approved once). Not cross-tenant.
- Classification: VERIFIED_CODE + VERIFIED_RUNTIME
- Evidence:
  - `platform/packages/core/src/policy/engine.ts:90` reads the pending row, `:113` calls `provider.applyWrite`, `:123` deletes the row afterwards. Nothing between `:90` and `:113` marks the row as taken.
  - `platform/packages/core/src/policy/pending.ts:17-22`: the `PendingOperationStore` contract is `get/put/delete/sweep`; `delete` returns `void`, so no implementation can report "someone else already consumed this".
  - `platform/apps/cloud/lib/cloud/repository.ts:413-418`: `delete` is `update ... set consumed_at = now() where id = ... and organization_id = ...` with no `consumed_at is null` guard and no `returning`.
  - `platform/apps/cloud/app/api/approvals/[id]/apply/route.ts:20-27`: no transaction, no `for update`, no advisory lock around find → apply → `markPendingOutcome`.
  - Scratch probe `S1` (two `engine.apply` calls for the same id with a 5 ms store latency): `applyWrite calls = 2`, both outcomes `fulfilled`, two `applied` audit events.
  - `platform/apps/cloud/app/dashboard/approvals/approval-actions.tsx:15,34` disables the buttons per component instance only; two admins, two tabs, or a retried request are not guarded.
  - `kind: 'create'` guarded tools exist in 10 provider packages (`rg "kind: 'create'" platform/packages/*/src`), e.g. `platform/packages/snapchat/src/provider.ts:95-110` posts a new campaign on apply; a duplicate apply creates a second campaign with real spend.
- Description: the two-step contract guarantees hash/expiry/policy checks but not exactly-once execution. The soft-delete happens after the write, so every concurrent caller that passes `get` executes. For `update` writes (set budget, set status) the platform effect is idempotent but the audit log double-counts; for `create` writes it is a duplicate resource.
- Impact: two approvers clicking at once, a double-submitted request, or a proxy retry can create duplicate campaigns or double audit evidence on a live account.
- Recommendation: add a claim step to the store contract (`claim(id): Promise<PendingOperation | undefined>` implemented as `update pending_operations set consumed_at = now() where id = $1 and organization_id = $2 and consumed_at is null and expires_at > now() returning *`) and call it before `applyWrite`; on write failure, either leave the row consumed with a `failed` outcome (require a new preview) or restore it explicitly. Alternatively wrap the apply route in `db().begin` with `select ... for update` on the row. Add a concurrency test like the probe above to `packages/core`.

### D7-02 — Apply ordering (write → audit → delete) lets a post-write failure leave the row consumable, so a retry executes the write again
- Severity: **P1** (same risk class as D7-01, different trigger: any DB error after the live write)
- Classification: VERIFIED_CODE + VERIFIED_RUNTIME
- Evidence:
  - `platform/packages/core/src/policy/engine.ts:113-123`: `applyWrite` → `audit.append('applied')` → `pending.delete`. An exception from `audit.append` (Postgres insert in `platform/apps/cloud/lib/cloud/repository.ts:282-289`) propagates before `delete`.
  - `platform/apps/cloud/app/api/approvals/[id]/apply/route.ts:26-27`: `markPendingOutcome(...,'applied')` is a third, separate statement after the registry call; the route returns 500 to the user if any of the three fails.
  - Scratch probe `S2`: with `audit.append` throwing once, the first apply threw `audit db down`, the pending row was still present, the second apply succeeded, `applyWrite calls = 2`.
- Description: three non-transactional writes across two systems (ad platform, Postgres) with the irreversible one first. The user sees "could not apply", the Approvals page still lists the row, and the natural human reaction (click again) re-executes the write.
- Impact: duplicate live writes after transient database errors; audit log that says nothing happened when something did.
- Recommendation: claim first (D7-01), then write, then record the outcome; if recording fails, log loudly and keep the row consumed (never re-executable). Longer term, an outbox row per apply with `requested → executing → applied/failed` states and a background reconciler.

### D7-03 — Reject and apply can both "win": reject consumes unconditionally while an apply that already passed `get` continues to the write
- Severity: **P2** (window is one DB round trip plus provider latency, but the outcome is executing a rejected change)
- Classification: VERIFIED_CODE
- Evidence: `platform/apps/cloud/app/api/approvals/[id]/reject/route.ts:13-16` does `listPendingOperations(...).find` then `PostgresPendingStore.delete` with no conditional; `platform/packages/core/src/policy/engine.ts:90-113` checks the row once, before `applyWrite`.
- Description: approver A rejects, approver B applies within the same window; B's `get` returns the row (not yet consumed), A consumes it and records `rejected`, B's `applyWrite` executes anyway and then re-soft-deletes. The audit log then contains both `rejected` and `applied` for the same pending id, and `markting_engine_proposals.status` ends as whichever update ran last (`platform/apps/cloud/lib/markting/repository.ts:107-112`).
- Recommendation: same fix as D7-01 (atomic claim with a terminal state column `outcome in ('applied','rejected','expired')` instead of a bare `consumed_at`).

### D7-04 — The demo engine model shares mutable script state across all threads and requests: the second conversation gets a non-answer, concurrent conversations corrupt each other
- Severity: **P2** (substantial functional defect in the default, shipped mode; not a security issue)
- Classification: VERIFIED_RUNTIME + VERIFIED_CODE
- Evidence:
  - `services/engine-demo/serve_demo.py:84-115`: one `LoopingScriptedChatModel` instance per process (`build_demo_model`, `:194-198`, passed into `build_agent_components` `:225`), with instance fields `steps`, `call_count`, `seen_human_messages`. The reset condition at `:104` is `len(humans) != self.seen_human_messages`, i.e. the number of human messages in *this* thread compared with the count remembered from *whatever thread ran last*.
  - `engine/src/paid_media_agent/testing/scripted_model.py:71,102-104`: `call_count` is a per-instance counter incremented on every model call.
  - Probe, sequential threads A then B, both first messages: `A has analysis: True | B has analysis: False | B exhausted: True` (B received "This is the offline demo engine: it replays a fixed investigation ...").
  - Probe, concurrent threads C (analysis question) and D (change request): C answered `The proposal could not be staged.` (it consumed D's write script), D returned `interrupted=False` with a proposal and text `No receipt was returned: ...`.
  - Defaults: `.env.example:51` `MARKTING_ENGINE_MODE=demo`, `docker-compose.yml:51` `${MARKTING_ENGINE_MODE:-demo}`, `serve_demo.py:133` default `demo`.
  - The existing suite cannot see this: `services/engine-demo/tests/test_demo_api.py:56-60` builds a fresh app (fresh model) per test.
- Description: in the stack `make up` produces, the first user's first chat works; the next new thread (same or another user, same or another organization) whose first message arrives while the counter is equal receives the "exhausted" text; two users chatting at the same time interleave each other's scripts. Every cloud chat starts a new thread (`platform/apps/cloud/lib/markting/assistant.ts:34-36`), so this is the common path, not an edge case.
- Impact: the Assistant demo is unreliable past the first conversation; `README.md:87` ("A complete demo mode ...") is contradicted.
- Recommendation: key script progress by `thread_id` (available in the run config) rather than by a process-global counter, or instantiate a model per request/thread; add a two-thread test and a `gather` test to `services/engine-demo/tests`.

### D7-05 — The chat turn is a single synchronous HTTP call held open for minutes with no job, no idempotency key and no cancellation propagation
- Severity: **P2** (reliability deficiency in the primary user flow; becomes a blocker behind any proxy/LB with a 60–120 s idle timeout)
- Classification: VERIFIED_CODE (timeouts, absence of job/idempotency) + INFERRED (engine keeps running after client abort)
- Evidence:
  - `platform/apps/cloud/lib/markting/engine-client.ts:73` default 240 s abort; `env.ts:156` allows `MARKTING_ENGINE_TIMEOUT_MS` up to 900 000 ms while `app/api/assistant/messages/route.ts:7` declares `maxDuration = 300` (Vercel-only hint; `next.config.ts` `output: 'standalone'` on Docker, where it is ignored).
  - `assistant-chat.tsx:37-40`: browser `fetch` with no `AbortController`/timeout; the only guard is `busy`.
  - `engine/src/paid_media_agent/surfaces/api/app.py:91-101` → `runner.send` → `graph.ainvoke` (`runner.py:150-154`) with no timeout; nothing watches request disconnect. `rg dedupe engine/src/paid_media_agent/surfaces` finds the dedupe store used only by the Slack surface, not by `POST /threads/{id}/messages`.
  - `engine-client.ts:76-109`: no retry, no circuit breaker; `EngineClient.health()` has no caller in the cloud app (`rg "\.health\(\)" platform/apps/cloud` → none), so an unhealthy engine costs each chat the full timeout before a 503.
  - Cloud `db()` pool `max: 10` (`platform/apps/cloud/lib/db.ts:8`) is not held during the engine call (postgres.js releases per query), so the long call does not starve the pool — checked and fine.
- Description: when the cloud aborts at 240 s the engine finishes the turn anyway (Starlette does not cancel a non-streaming handler on disconnect — INFERRED, not observed here); the model's text is lost to the user, and if the turn produced a proposal it is only bridged when the user sends the *next* message on the same thread (`assistant.ts:50-51` bridges whatever `latest_proposal` is `awaiting_approval`). A network error after the engine processed the message cannot be retried safely because there is no request id: a retry runs the turn twice. The rate limit (`messages/route.ts:13`, 120/min per user) bounds request count, not concurrently held engine runs.
- Recommendation: turn the chat into a job: cloud enqueues `(thread_id, message_id, text)` into a Postgres-backed queue (pg-boss/graphile-worker or a `markting_turns` table polled by a worker), returns 202 with a turn id, UI polls or subscribes (SSE). Give the engine an idempotency key per turn (its dedupe store already exists: `persistence/postgres.py:213-223`) and a server-side run timeout. Fast-fail on `/health` before enqueueing.

### D7-06 — No per-thread mutual exclusion anywhere: concurrent messages on one thread run two graph invocations on the same checkpoint
- Severity: **P2**
- Classification: VERIFIED_CODE + VERIFIED_RUNTIME (result confounded by D7-04; the absence of a lock is code-verified)
- Evidence:
  - `platform/apps/cloud/lib/markting/repository.ts:17-27` `claimThread` is an upsert (ownership check), not a lease; `assistant.ts:38-43` proceeds straight to `sendMessage`.
  - `engine/src/paid_media_agent/surfaces/runner.py:86-89,208-213`: `_config` only checks ownership; `rg "Lock|Semaphore" engine/src/paid_media_agent/surfaces engine/src/paid_media_agent/runtime` → none.
  - Probe, two simultaneous change requests on thread `t-F`: both responses returned the same proposal id with `interrupted=False`, and the thread ended with one proposal `awaiting_approval` while the graph was not paused.
- Description: the UI's `busy` flag is the only serialisation. Two tabs, a retried request, or a future API client produce interleaved checkpoint writes. With the Postgres checkpointer each run writes its own checkpoint for the same thread; the last writer wins and the HITL interrupt can be lost while the proposal remains `awaiting_approval` in `pma_proposals`.
- Recommendation: per-thread lease in the cloud (`insert into markting_thread_locks ... on conflict do nothing` with expiry, or `pg_try_advisory_xact_lock(hashtext(thread_id))` inside a transaction that spans the enqueue) and a 409 when a turn is in flight; in the engine, an `asyncio.Lock` per thread id (single process) or a DB lease (multi-process).

### D7-07 — Report index: non-atomic file write, lock only around the writer, silent data loss on corruption, global head-of-line blocking, synchronous PDF render on the event loop
- Severity: **P2**
- Classification: VERIFIED_CODE + VERIFIED_RUNTIME
- Evidence:
  - `services/engine-demo/serve_demo.py:263-264` `_save_index` is a bare `write_text` (no temp file + `os.replace`); `:252-260` `_load_index` returns `[]` on `JSONDecodeError`; `:304-306` read-modify-write truncates to 50.
  - `:324` one `asyncio.Lock` per process wraps only `/reports/run` (`:344`); `/reports` (`:355-358`) is a sync `def` run in Starlette's threadpool and reads the file unlocked while a run may be writing it.
  - Probe: after truncating the index file mid-JSON, `GET /reports` returned `{'reports': []}` with status 200 — all runs disappear from every tenant's Reports page until the next run rewrites the file (and even then the old entries are gone, since the writer starts from the `[]` it loaded).
  - Head-of-line blocking: the lock is global, so one tenant's run blocks every other tenant's `/reports/run` for its duration while the cloud waits up to 240 s (`engine-client.ts:73`) and the UI shows "running".
  - Event-loop blocking: `engine/src/paid_media_agent/reports/cadence.py:132-141` calls `run_render_report(...)` synchronously from an `async def`; `render.py:265-270` `HostPdfEngine.write_pdf` runs WeasyPrint synchronously. Whether WeasyPrint's native libraries are present in the engine image is NOT_VERIFIED (Docker build blocked); if they are, every PDF render freezes chat and health for its duration.
  - Multi-process: the lock, the file and the `out/` directory live on one container volume (`docker-compose.yml:54`), so two engine replicas would have divergent indexes and `/reports/files/{name}` would 404 on the replica that did not render the file.
- Recommendation: store run metadata in the engine's Postgres (it already has a pool and schema at `persistence/postgres.py:11-43`), or at minimum write via temp file + `os.replace` under a file lock and never swallow decode errors silently; run rendering in `asyncio.to_thread`; replace the global lock with a per-tenant lock or a job queue.

### D7-08 — The engine is a single-tenant, single-process service shared by every tenant; the cloud boots only if it is healthy
- Severity: **P2** today (fixture data only), **P0 if the engine ever reads tenant accounts** without a tenant key
- Classification: VERIFIED_CODE
- Evidence:
  - One token, one caller for all organizations: `docker-compose.yml:49` `PAID_MEDIA_API_TOKENS=${MARKTING_ENGINE_TOKEN}:adport-bridge`; `README.md:128` acknowledges this.
  - Reports are global: `serve_demo.py:355-358` lists the whole index, `:360-374` serves any file to any bearer; `platform/apps/cloud/app/api/reports/engine/route.ts:16-24,27-36` forward without any organization key; `requested_by` is always `adport-bridge` (`serve_demo.py:343,347`). Every organization sees and can download every other organization's report runs. Data is forced to fixtures (`serve_demo.py:163-166,383-388`), so no real data crosses tenants *now*.
  - No horizontal scaling: in-memory demo model (D7-04), file index (D7-07), `asyncio.Lock`, `engine-workspace` volume. `docker-compose.yml:34-64` one replica, no `deploy.replicas`.
  - Persistence fallback: `serve_demo.py:207-229` uses `InMemorySaver`, `InMemoryDedupeStore`, `InMemoryThreadOwnershipStore` when `DATABASE_URL` is unset; a restart then loses every interrupted graph and proposal. Compose sets `DATABASE_URL` (`:43`), so the demo stack is Postgres-backed; other deployments are not forced to be.
  - Pool sizes `max_size=4` for both the repositories (`persistence/postgres.py:52`) and the checkpointer (`runtime/self_hosted.py:52-56`): 5+ concurrent turns queue on connections.
  - Boot coupling: `docker-compose.yml:30-32` `cloud.depends_on.engine.condition: service_healthy`; the dashboard, OAuth and Approvals (which do not need the engine) cannot start if the engine is unhealthy. At runtime the assistant degrades to 503 (`assistant.ts:45`) while approvals keep working — that part is correct.
- Recommendation: put `organization_id` on the engine's caller (`token:caller` per tenant, or a signed header) and scope threads, proposals and reports by it; move report metadata to Postgres; make the engine stateless per request so it can run N replicas; drop the `depends_on` health condition (or make it `service_started`).

### D7-09 — Pending TTL (15 min default) vs four-eyes approval with no notification, and `expired` is never recorded
- Severity: **P2** functional / GAP
- Classification: VERIFIED_CODE
- Evidence:
  - TTL: `platform/packages/core/src/policy/policy.ts:19` default 15; `platform/supabase/migrations/20260817171039_cloud_initial_schema.sql:48` seeded 15; editable per organization in `app/dashboard/policies/policy-form.tsx:107` (so a longer TTL is possible — the README's "need a new proposal" is a default, not a limit).
  - Requester ≠ approver by default: `app/api/approvals/[id]/apply/route.ts:22-24`, `env.ts:154`; `.env.example:49` sets `MARKTING_ALLOW_SELF_APPROVAL=true` for the demo.
  - No notification path: `rg -i "notify|email|webhook" platform/apps/cloud/lib/markting platform/apps/cloud/app/api/approvals` → none. The approver must be watching `/dashboard/approvals` within the TTL.
  - Expiry is lazy: `listPendingOperations` filters `expires_at > now()` (`repository.ts:699`); `PolicyEngine.validate` sweeps (`engine.ts:59`); `markPendingOutcome(..., 'expired')` has no caller (`rg "'expired'" platform/apps/cloud` → only the type union and the migration check), so `markting_engine_proposals.status` stays `pending` forever for every expired preview.
  - The engine was told "rejected" at hand-off (`bridge.ts:94`), so once the preview expires there is nothing to resume: the user must re-chat and re-generate the proposal.
- Description: the TTL protects against stale previews (correct), but the workflow it gates is a human review by a *different* person with no push. Expiry is invisible except as a row vanishing from the list.
- Recommendation: a background sweeper (pg_cron is available in the Supabase image per `docker-compose.yml:3-5`) that marks expired rows and provenance, emits an audit event and notifies the requester; an approver notification on preview (email/WhatsApp are listed as TODO); optionally a "re-preview" action that re-runs `validate` from the stored provenance instead of a new chat turn.

### D7-11 — Re-bridging the same engine proposal creates a second pending operation and overwrites provenance
- Severity: **P3** (mechanics verified; trigger requires a hand-off failure or a crash between validate and hand-off)
- Classification: VERIFIED_CODE (mechanics) + INFERRED (trigger frequency)

### D7-12 — Hand-off failure is silent and leaves orphan proposals `awaiting_approval` in the engine

- Classification: VERIFIED_CODE + VERIFIED_RUNTIME
- Evidence: `bridge.ts:98-105` swallows every `rejectOnEngine` error with no log, metric or audit note; probe: after a turn that produced proposal `f8ac...` with no reject, a second change request on the same thread produced `0ab8...`, and `list_for_thread` showed both `awaiting_approval`. `docs/PHASE1-REPORT.md:15` states "the engine is told the proposal was handled" without the best-effort caveat; the test `markting-bridge.test.ts:118-123` does cover tolerance of the failure but nothing asserts it is observable.

### D7-13 — Sandbox compare-and-set is correct but compares the whole document, ignores its own `version` column and reuses the `PENDING_MISMATCH` error code
- Severity: **P3**
- Classification: VERIFIED_CODE (+ VERIFIED_TEST for the in-memory variant: `markting-sandbox.test.ts:71-76` passed; Postgres variant covered by the DB-gated suite, NOT run here)
- Evidence: `platform/apps/cloud/lib/markting/repository.ts:133-141` `update ... where organization_id = $1 and campaigns = $expected::jsonb returning version`; `jsonb` equality is structural, so key order does not matter — correct. `version = version + 1` is written but never read as the CAS token. `sandbox-provider.ts:178-182` `applyWrite` re-plans from a fresh load and CASes on it, so concurrent sandbox applies cannot lose updates (one fails with `PENDING_MISMATCH`). Seed race in `load()` (`:124-130`) is benign (`on conflict do nothing`, both callers return the same seed).
- Impact: none functional; the error text "Request a new preview" is right, but the code `PENDING_MISMATCH` is also what the policy engine uses for hash mismatch, which will confuse any UI or operator triaging failures.
- Recommendation: CAS on `version` (cheaper than comparing a JSON blob) and a distinct `SANDBOX_CONFLICT` code. Note this store is demo-only; live providers have no equivalent protection (see D7-14).

### D7-14 — Apply does not re-preview: the budget-delta check and the `fromMicros` baseline are frozen at preview time
- Severity: **P3** (upstream adport design; relevant here because the TTL is user-configurable upward)
- Classification: VERIFIED_CODE
- Evidence: `engine.ts:110-113` re-runs `checkStaticPolicy` only; `checkBudgetPolicy` (`:133-153`) runs at validate time against `preview.budgetDeltas` whose `fromMicros` came from the provider's read at that moment. For live providers `applyWrite` re-reads the target (e.g. `snapchat/src/provider.ts:88-92` re-plans), but nothing re-applies the percentage cap to the fresh baseline.
- Impact: a budget that moved on the platform between preview and apply can make an approved "≤25 %" change exceed the cap at execution.
- Recommendation: re-run `previewWrite` + `checkBudgetPolicy` inside `apply` and fail with `PENDING_MISMATCH` if the preview differs materially.

## What a world-class system would need

1. **Transactional claim before execution.** `pending_operations.outcome` (`applied|rejected|expired|failed`) set by a single conditional `update ... returning` before `applyWrite`; `PendingOperationStore.claim()` in the core contract; a `packages/core` test that fires N concurrent applies and asserts one write.
2. **Outbox + reconciler for live writes.** Record `executing` before the provider call and `applied/failed` after; a worker reconciles `executing` rows older than X by reading the platform (resource id / readback), never by re-writing.
3. **Asynchronous turns.** `POST /api/assistant/messages` returns 202 + `turn_id`; a worker (pg-boss / graphile-worker on the existing Supabase Postgres, or a dedicated queue) calls the engine with an idempotency key; UI subscribes via SSE/polling; server-side run timeout and cancellation in the engine.
4. **Per-thread lease** on both sides; 409 for a turn already in flight.
5. **Tenant identity in the engine.** Per-tenant caller ref or signed header; `organization_id` on `pma_*` tables and on report runs; the cloud passes it on every call and the engine filters on it.
6. **Report metadata in Postgres**, rendering off the event loop, per-tenant locks, N engine replicas behind the compose network.
7. **Expiry as an event.** Scheduled sweeper (pg_cron) that marks expired rows and provenance, audits it and notifies; approver notification on preview; configurable TTL with a floor/ceiling.
8. **Observability of the seams.** Log/metric for hand-off failures, engine timeouts, double-apply attempts (claim misses), report index rewrites.
9. **Demo engine isolation.** Per-thread script state; tests for two sequential threads and concurrent threads.
