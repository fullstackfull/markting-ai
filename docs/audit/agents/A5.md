# A5 — LinkedIn Ads expert

Audit question: can MARKTING-AI understand and manage LinkedIn Ads like a senior B2B media buyer, or does it merely have a connector? Code is the source of truth; README/UPSTREAM/docs are treated as claims.

Short answer: the LinkedIn connector (`platform/packages/linkedin`) is a small, carefully written, well-tested **campaign-shell + campaign budget/status** adapter with five normalized metrics and no breakdowns. It is safe (every write is gated by `PolicyEngine`), but it is far from an expert-grade LinkedIn surface: no leads, no reach/frequency, no demographics, no daily series, no creative or campaign-group reporting, no bid/optimization controls, and the AI engine (`engine/`) cannot read LinkedIn offline at all and has no test covering its LinkedIn normalization.

## Findings

### A5-01 — "conversions" means website conversions only; lead-gen leads are invisible, and the audit pack will propose pausing lead-gen campaigns
- Severity: **P2**
- Classification: VERIFIED_CODE (mapping and rule), INFERRED (impact on a live lead-gen account)
- Evidence: `platform/packages/linkedin/src/provider.ts:7` (`conversions: 'externalWebsiteConversions'`), `schemas.ts:14-15` (only `externalWebsiteConversions`/`conversionValueInLocalCurrency` parsed), `schemas.ts:25` (`LEAD_GENERATION` is a creatable objective), `platform/packages/core/src/audit/packs/core-performance.ts:8-30` (`zero-conversion-spend` flags `conversions === 0` and attaches `proposedAction: ctx.actions.pauseCampaign`), `provider.ts:30` (LinkedIn supplies `pauseCampaign`), `engine/workspace/skills/paid-media-wiki/platform-playbooks.md:25` ("Lead-gen forms and website conversions are different events").
- Description: LinkedIn's dominant B2B objective is Lead Generation, whose outcomes are reported as `oneClickLeads` / `oneClickLeadFormOpens` (and `qualifiedLeads`), not `externalWebsiteConversions`. The provider never requests those fields, so every lead-gen campaign reports `conversions` absent or 0 and `cpa` absent. The generic rule pack then classifies an active lead-gen campaign that spent ≥ 50 units with "0 conversions" as `warn`/`critical` and proposes a pause. The pause still goes through the two-step gate, so this is not an unsafe-execution P0, but it is a systematically wrong signal on the channel's most important campaign type. The provider doc (`platform/docs/providers/linkedin.md:30`) does disclose the field choice, which is why this is not rated higher.
- Impact: misleading CPA/ROAS and wrong "wasted spend" recommendations for LinkedIn lead-gen; an operator trusting the audit output could pause healthy campaigns.
- Recommendation: add `oneClickLeads`, `oneClickLeadFormOpens`, `qualifiedLeads` (and `landingPageClicks`) to `FIELDS`/`reportRowSchema`; expose `leads` as a provider-specific metric or map `conversions` by campaign `objectiveType`; make the `zero-conversion-spend` rule skip LinkedIn `LEAD_GENERATION` campaigns until leads are read.

### A5-02 — Engine cannot read LinkedIn offline and its LinkedIn normalization is untested and only half-matches LinkedIn field names
- Severity: **P2**
- Classification: VERIFIED_CODE (absence of fixture/tests, key tables), NOT_VERIFIED (actual Pipeboard LinkedIn MCP payload shape)
- Evidence: `engine/src/paid_media_agent/domain/common.py:36-40` (`FIXTURE_PLATFORMS` = google, meta, reddit), `engine/src/paid_media_agent/fixtures/data/` (three JSON files, none for linkedin), `tools/fixtures.py:40-44,65` (`_ACCOUNT_ARG` has no LinkedIn entry), `tools/normalize.py:22` (spend keys `spend`, `costInLocalCurrency`), `normalize.py:28-29` (`_CONVERSION_KEYS = conversions|purchases|results`, `_VALUE_KEYS` without `conversionValueInLocalCurrency`), `normalize.py:106-109` (row must carry a string `date|day|date_start`), `normalize.py:27` docstring "Platforms with verified mappings"; `grep -rn "LINKEDIN\|linkedin_ads" engine/tests --include=*.py` → no matches.
- Description: The engine advertises `linkedin_ads` as a `PERFORMANCE_PLATFORM` with a "verified" spend mapping, yet nothing in the repo exercises that mapping. The mapping itself is inconsistent: it anticipates LinkedIn's native `costInLocalCurrency` but not LinkedIn's native conversion/value names, and it requires a per-day date string whereas LinkedIn's native analytics rows carry `dateRange: {start:{year,month,day},...}`. Whether Pipeboard's LinkedIn MCP flattens rows into `date`/`spend`/`conversions` is unknown from this repo. If it does not, `normalize_rows` raises `row without a date` → `ReadDenied("normalization_failed")` (`tools/reads.py:256-257`) and LinkedIn is unreadable through the engine.
- Impact: the AI engine's LinkedIn analysis depends entirely on an unverified third-party schema; there is no demo/sample mode for LinkedIn and no regression test.
- Recommendation: add a synthetic `linkedin_ads.json` fixture shaped like the Pipeboard LinkedIn tool output (after capturing one live sample), extend `_CONVERSION_KEYS`/`_VALUE_KEYS` or add a LinkedIn-specific adapter, and add a `normalize_rows` test for `Platform.LINKEDIN_ADS`. Remove "verified" from the `PERFORMANCE_PLATFORMS` docstring until then.

### A5-03 — `doctor` tells operators LinkedIn is a direct adapter; the code routes it through Pipeboard
- Severity: **P3**
- Classification: VERIFIED_CODE

### A5-04 — `clicks` is LinkedIn "chargeable clicks" yet is presented as the cross-platform normalized `clicks`
- Severity: **P3**
- Classification: VERIFIED_CODE (mapping), DOCUMENTED_ONLY (semantics stated in provider doc)
- Evidence: `provider.ts:7` (`clicks: 'clicks'`), `provider.ts:8` (ctr/cpc derived from it), `platform/docs/providers/linkedin.md:30` ("chargeable `clicks`"), `platform/packages/core/src/tools/builtin.ts:54-57` (report tool describes metrics as normalized/cross-platform).
- Description: LinkedIn's `clicks` counts chargeable clicks, which for Sponsored Content under CPC billing includes social actions, not only landing-page clicks; the comparable field to Meta "link clicks" is `landingPageClicks`, which is not requested. The cross-platform `report` tool and the `low-ctr` rule (`core-performance.ts:32-51`) treat LinkedIn CTR/CPC as commensurable with other providers.
- Impact: inflated LinkedIn CTR / deflated CPC relative to other channels in blended views; mis-ranked campaigns in `cpa-outlier`/`low-ctr`.
- Recommendation: request `landingPageClicks` and either map `clicks` to it or surface both with explicit labels.

### A5-06 — Non-political advertising attestation is a model-settable boolean
- Severity: **P3**
- Classification: VERIFIED_CODE (mechanism), INFERRED (who actually sets it in practice)
- Evidence: `schemas.ts:34,36` (`non_political_consent: z.literal(true)`), `provider.ts:159,171` (`politicalIntent: 'NOT_POLITICAL'` written when the flag is true), `tools.ts:10-11` (flag is an ordinary tool argument), `test/linkedin.test.ts:198-203` (only checks the provider does not default it).
- Description: LinkedIn requires an advertiser declaration about political content. Here the declaration is an argument the calling agent supplies; nothing binds it to a human in the organization. The provider correctly refuses to invent it, but an LLM driving the MCP tools can simply pass `true`.
- Impact: legal attestation made on the advertiser's behalf without a recorded human act; audit log records only the tool call.
- Recommendation: capture the attestation once per organization/account in the cloud UI (persisted, with user id and timestamp) and have the provider read it from the runtime context instead of the tool payload.

## What a world-class system would need (gaps, concrete)

1. Lead metrics first: `oneClickLeads`, `oneClickLeadFormOpens`, `qualifiedLeads`, cost per lead by objective; lead-form listing and CRM/webhook sync.
2. Daily time series (`timeGranularity=DAILY`) with the month-rounding guard retained, so pacing, trend and anomaly detection work.
3. Demographic pivots (`MEMBER_COMPANY`, `MEMBER_JOB_TITLE`, `MEMBER_SENIORITY`, `MEMBER_INDUSTRY`, `MEMBER_COMPANY_SIZE`, `MEMBER_COUNTRY_V2`/`MEMBER_REGION_V2`) and `SERVING_LOCATION` for LAN vs feed.
4. Reach/frequency (`approximateMemberReach`), video (`videoViews`, `videoCompletions`), engagement (`totalEngagements`, `reactions`, `follows`), `landingPageClicks`, `costInUsd` for optional cross-currency reads.
5. Campaign-group reporting (`CAMPAIGN_GROUP` pivot) and group budget/schedule reads, since groups are the budget-holding tier for many B2B accounts.
6. Creative listing and status (`adCreatives`/`posts`), creative-level names, creative rotation (`creativeSelection`), and creative fatigue detection using frequency.
7. Bid and optimization controls: `optimizationTargetType` (max delivery, target cost, manual), bid updates, `audienceExpansionEnabled`/`offsiteDeliveryEnabled` as explicit, policy-gated options.
8. Targeting intelligence: audience-count estimates (`audienceCounts`), targeting facet lookup (`adTargetingFacets`/`adTargetingEntities`), matched audiences and exclusions.
9. Conversion configuration reads (`conversions` resource: types, attribution rules, post-click/view windows) and Insight Tag health.
10. Account health: billing status, serving status, review outcomes, token expiry countdown (A5-07), API quota.
11. Engine side: a LinkedIn fixture dataset, platform-specific normalizer tests, LinkedIn rows in the write policy only after a live schema review, and a bridge mapping `linkedin_ads → linkedin` so approved proposals can reach the gated provider.
12. Domain skill content for the model: objective↔metric map, format constraints, minimum bids/budgets, lead-form best practices, B2B sample-size guidance.
