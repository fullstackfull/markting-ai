## Findings

### A15-01 — Zero-decimal currencies produce a 100× budget (Meta minor-unit assumption is hard-coded)
- Severity: **P1** (financial risk / unsafe ad execution) · Classification: **VERIFIED_CODE**
- Evidence: `platform/packages/meta/src/provider.ts:20` (`CENTS_TO_MICROS = 10_000`), applied with no
  currency check at `:334,452,523,568`; `platform/apps/cloud/lib/markting/translate.ts:107`
  (`daily_budget_cents: Math.round(micros / 10_000)`), also unconditional.
- Description: Both the bridge and the Meta provider assume every account is a 2-decimal currency
  (100 minor units = 1 major). Meta's Marketing API expects **whole units** for zero-decimal
  currencies (JPY, KRW, CLP, …) and 1,000 minor units for 3-decimal currencies (KWD, BHD). A JPY
  proposal of ¥30,000 → `toMicros` `3.0e10` → `daily_budget_cents = 3,000,000`, which Meta reads as
  ¥3,000,000 — a 100× overspend. There is no per-currency minor-unit offset anywhere in the bridge
  or any provider; `AliasBinding.currency` (`translate.ts:54`) is used only for the human preview.
- Impact: Live Meta budget writes in any non-2-decimal currency would set a budget 100× (or 10×)
  wrong. Internal consistency is preserved (the percentage-delta cap compares micros-to-micros so it
  does not catch this), so the guardrail is blind to the error.
- Recommendation: Thread account currency into minor-unit scaling (Meta publishes per-currency
  offsets); add JPY/KWD fixtures and an end-to-end bridge test. Note: currently reachable only via the
  live-write path (demo/fixtures are USD), so it is latent, not yet exploited.

### A15-02 — The absolute budget cap is currency-blind
- Severity: **P2** · Classification: **VERIFIED_CODE**
- Evidence: `platform/packages/core/src/policy/policy.ts:15` (`max_daily_budget_micros: number|null`);
  `engine.ts:135,137` compares `delta.toMicros > absCap` for every provider/account.
- Description: The absolute cap is a single scalar in micros compared against normalized micros from
  every account regardless of currency. 100,000,000 micros is $100/day but also ¥100/day and
  د.ك100/day. A cap meaningful for a USD account is meaningless for a JPY or KWD account on the same
  org policy. The policy schema has no currency dimension and no per-account override.
- Impact: An org cannot set a budget ceiling that is correct across accounts of different currencies;
  the cap is either far too loose or far too tight for any account not in the calibration currency.
- Recommendation: Express caps in the account's currency (major units) and convert at check time, or
  key caps per currency/account.

### A15-03 — Percentage-delta cap is silently bypassed when the prior budget is unknown; default policy has no absolute ceiling
- Severity: **P2** · Classification: **VERIFIED_CODE**
- Evidence: `engine.ts:143` (`pctCap !== null && delta.fromMicros !== undefined && delta.fromMicros > 0`);
  `policy.ts:13-15` (`max_budget_delta_pct` default 25, `max_daily_budget_micros` default **null**).
  Deltas emitted with `toMicros` but no `fromMicros`: all campaign creations
  (`meta:452`→ actually create at `:452` has from; creation at `meta` create-campaign `~:445` and
  `create_ad_set` push `toMicros` only; `google/src/provider.ts:430`; `x/src/writes.ts:24`;
  `reddit/src/provider.ts:298`; `tiktok/src/provider.ts:336`) and Apple *update* when the current
  value is unreadable (`apple/src/provider.ts:459` — `fromMicros` added only when `fromAmount !== undefined`).
- Description: When `fromMicros` is absent the percentage cap is skipped entirely; the only remaining
  numeric guard is the absolute cap, which defaults to `null` (no ceiling). So under the shipped
  default policy, any operation without a known prior budget (every create, and an Apple update whose
  readback lacked a budget) passes with an unbounded budget. The core test suite exercises the abs cap
  only with an explicit non-null value (`policy-engine.test.ts:64-65`); the unknown-`fromMicros` path
  is untested.
- Impact: A newly created campaign (or an Apple update with unverifiable prior budget) can be assigned
  an arbitrarily large daily budget and pass policy. Partially mitigated for creation because
  `paused_creation` coerces new entities to PAUSED (`engine.ts:55`, provider guards), but the budget
  is still written and a later status flip starts delivery at that budget.
- Recommendation: Require an explicit absolute cap (reject `null` in production), and treat an
  absent `fromMicros` as "cannot verify" → fail closed rather than skip the percentage check.

### A15-04 — Budget policy is not re-checked at apply(); only protected-accounts is
- Severity: **P3** · Classification: **VERIFIED_CODE**
- Evidence: `engine.ts:110-111` apply() re-runs `checkStaticPolicy` only; `checkBudgetPolicy` runs
  solely in `validate()` (`engine.ts:62`).
- Description: The operation hash + TTL prevent the budget value from drifting between validate and
  apply, so this is low-risk. But if the org tightens `max_budget_delta_pct`/`max_daily_budget_micros`
  within the pending TTL window, an already-validated oversized budget still applies. The comment at
  `engine.ts:110` acknowledges "policy may have changed … re-check" but only re-checks protected
  accounts.
- Impact: A budget approved under a looser policy executes after the policy tightens (bounded by the
  15-minute default TTL, `policy.ts:19`).
- Recommendation: Call `checkBudgetPolicy` against the stored `pending.preview.budgetDeltas` at apply.

### A15-05 — translate.ts ignores the declared `unit` on the proposal field
- Severity: **P2** · Classification: **VERIFIED_CODE**
- Evidence: `translate.ts:21` (`fieldValue` carries optional `unit`); `translate.ts:86-92` `toMicros`
  and `:148-152` the budget path read only `after.value` and multiply by `1_000_000` — `unit` is
  never consulted.
- Description: The bridge assumes the engine always emits `daily_budget` in whole account-currency
  units. It is true for the current fixture catalog (`engine/.../tools/fixtures.py:118,123,440` store
  `daily_budget` as a whole-unit float and the schema says "account currency"), but nothing enforces
  it. If a future/live engine read ever surfaced a budget in minor units or micros and the proposal
  carried `unit:"cents"`/`"micros"`, translate would still multiply by 1e6 → a 100× or 1,000,000×
  error. The declared unit is dropped on the floor.
- Impact: A latent unit-confusion fault; the whole correctness of the budget pipeline rests on an
  unvalidated convention between two codebases (Python engine ↔ TS bridge).
- Recommendation: Validate `after.unit` against an expected enum and reject or convert explicitly;
  fail `unsupported` on any unexpected unit.

### A15-06 — No budget optimization, scaling, pacing-to-action, saturation, marginal-ROAS, diminishing-returns, or account/channel allocation logic exists in code
- Severity: **GAP** (capability) · Classification: **VERIFIED_CODE**
- Evidence: repo-wide grep `reallocat|allocat|portfolio|marginal|diminishing|saturation|scale.up|
  scale.down|scaling` over `engine/src`, `platform/apps/cloud/lib`, `platform/packages/core/src`,
  `services` → **no matches**. The only budget computations are:
  pacing = avg daily spend / configured daily budget (`summary.py:104`), `over_budget` = pacing>1
  (`summary.py:145-147`), day flag at ±50% dod (`summary.py:120-124`, `DAY_CHANGE_FLAG=0.5`), and
  period-over-period deltas + "largest absolute spend mover" attention lines
  (`compute.py:98-114,349-372`). All scaling judgement ("steps of 20–30%", "increase where marginal
  result is efficient", saturation, learning state) lives as **prose for the LLM** in
  `engine/workspace/skills/paid-media-wiki/bidding-and-budget.md:13-20` and `decision-model.md:30-37`
  — advice, not implemented algorithms. The demo proposal (`demo_script.py:158-170`) hard-codes
  `daily_budget: 240` against g-103's fixture baseline of `300.0`
  (`fixtures/data/google_ads.json`); the 20% cut is dictated by the user prompt
  (`demo_script.py:261-266` "Reduce … to 240"), not derived by any optimizer.
- Description: The system is a deterministic **measurement + guarded-write proposal** engine, not a
  budget optimizer. It can tell you pacing and which entities moved; it does not compute how much to
  scale, where to reallocate, or when returns diminish. Every such decision is delegated to the LLM
  under skill guidance, with the human stating the number.
- Impact: Not a defect — but the "AI media buyer" framing (`README.md:72`) implies autonomous budget
  and scaling decisions the code does not make. A reader expecting algorithmic scale-up/down,
  marginal-ROAS reallocation, or portfolio allocation will not find it.
- Recommendation: Either build deterministic allocation/marginal-efficiency tools (so numbers trace to
  code, consistent with the project's own "do not compute in prose" rule, `bidding-and-budget.md:34`)
  or scope the product claim to "assisted proposals".

### A15-07 — Pacing denominator is active days, not window days; `over_budget` can mislabel under-delivery
- Severity: **P3** · Classification: **VERIFIED_CODE**
- Evidence: `summary.py:88-90` `active_days = len({r.window.start for r in own})`,
  `average_daily = metrics.spend / active_days`; pacing = `average_daily / budget` (`:104`);
  `over_budget` = pacing>1 (`:145`). Skill defines pacing as "average daily spend over a window
  divided by the daily budget" (`bidding-and-budget.md:3-5`).
- Description: A campaign that spent on only 2 of 14 window days has its average computed over 2 days,
  inflating `average_daily` and pacing. Such a campaign can appear `over_budget` (pacing>1) while
  actually under-delivering across the window. The metric label ("pacing against daily budget",
  `summary.py:217`) implies window-day averaging; the code uses active-day averaging.
- Impact: `over_budget` and the pacing figure can point the LLM/operator toward cutting a budget on a
  campaign that is in fact under-pacing over the period, or vice-versa, for sparse-delivery entities.
- Recommendation: Report both active-day and window-day averages, and base `over_budget` on window
  coverage; or rename the field to "average over active days" to match the math.

## What a world-class system would need (gaps, concrete)

1. A deterministic allocation/marginal-efficiency tool: per-entity marginal CPA/ROAS vs spend,
   saturation/elbow detection, and a portfolio reallocation proposal with explicit constraints —
   so scaling numbers trace to code, not prose.
2. Currency-aware money handling end to end: per-currency minor-unit offsets (2/0/3-decimal),
   caps expressed in major units per account, and fixtures for JPY/KRW/KWD (A15-01/02).
3. Fail-closed budget rails: reject `null` absolute cap in production; treat unknown prior budget as
   a hard stop for the percentage cap; re-check budget policy at apply (A15-03/04).
4. A unit contract between engine and bridge that is validated, not assumed (A15-05).
5. Pacing that distinguishes budget-constrained from under-delivering entities over the full window
   (A15-07), with learning-phase and seasonality awareness before any scale recommendation.

  imply autonomous budget/scaling intelligence. The code does no budget optimization or scaling math;
  the 240 is hard-coded and user-dictated (`demo_script.py:166,261-266`) — **A15-06**.
- `engine/config/write-policy.example.toml` annotates budget units as "account currency per day" and

  is 2-decimal-only and the declared unit is ignored — **A15-01, A15-05**.
- `bidding-and-budget.md:3-5` defines pacing as window-day averaging; `summary.py` uses active-day
  averaging — **A15-07**.
