# A15 — Budget and scaling expert

Audit date: 2026-10-02. Repository: `/home/user/markting-ai` (HEAD `11784fd`). Scope: budget intelligence — caps, provider budget units, unit/currency conversion between the engine and adport, pacing, anomaly flags, scaling logic, and the demo budget proposal. Read-only audit; the only file written is this report (a throwaway vitest file was created under `platform/packages/core/test/` for one runtime check and deleted in the same command; `git status` confirms no residue).

Headline: the system has a **single, per-operation, currency-blind budget rail** (adport `PolicyEngine.checkBudgetPolicy`, default ±25 % and no absolute cap) and **deterministic descriptive arithmetic** (totals, CPA, ROAS, pacing = average daily spend / daily budget, ±50 % day-over-day flags). There is **no** scaling logic of any kind in code: no marginal ROAS, saturation, diminishing-returns, allocation, scale-up/down rules, cumulative/daily caps, or account- or channel-level budgets. Everything about "when and how much to scale" lives in prose skills for the LLM. The budget proposal shown in the README/demo (`g-103` 300 → 240) is a hard-coded scripted step, not a computed recommendation. Unit handling is correct for the fixture/demo path and for the bridge's five provider mappings under USD-like 2-decimal currencies, but the engine→adport contract that `daily_budget` is in "account currency per day" is an unverified assertion in a TOML data file, and several provider paths let the percentage cap fall through when the current value is unknown or zero.

## Findings

### A15-01 — Budget caps are per-operation only; sequential approved steps compound without any cumulative, daily, account- or channel-level ceiling
- Severity: **P2** (financial risk; the rail exists but is weaker than README implies)
- Classification: VERIFIED_RUNTIME
- Evidence: `platform/packages/core/src/policy/engine.ts:133-153` (loop over `preview.budgetDeltas`, compares `toMicros` with `fromMicros` only); `policy.ts:7-20` (no cumulative/daily/account fields); throwaway runtime test above (10 × +24 % → 8.59× in one session, all accepted); README.md:85 ("guarded by the organization policy (budget-delta cap …)").
- Description: `checkBudgetPolicy` evaluates each pending operation in isolation against the current provider value. There is no state across operations (no per-day delta budget, no account spend ceiling, no rate limit on budget changes, no "max total daily budget for the organization"). `max_daily_budget_micros` defaults to `null` (`policy.ts:15`), so out of the box the only protection is the 25 % step.
- Impact: an operator (or a compromised/over-eager approver flow) can grow a campaign ~8.6× with ten approvals; the Approvals UI shows each step as "+24 %". For an "AI media buyer" the per-step cap alone does not bound spend.
- Recommendation: add cumulative rails (per-campaign and per-account delta over a rolling 24 h/7 d; organization-level absolute daily ceiling; minimum dwell time between changes to the same target, consistent with the wiki's "give a change a full weekly cycle" at `engine/workspace/skills/paid-media-wiki/bidding-and-budget.md:19`). Default `max_daily_budget_micros` to a non-null value per account currency.

### A15-02 — Caps are currency-blind: `max_daily_budget_micros` compares raw micros regardless of `budgetDeltas.currency`
- Severity: **P2**
- Classification: VERIFIED_CODE
- Evidence: `engine.ts:137` (`delta.toMicros > absCap`, `delta.currency` never read); `platform/packages/core/src/tools/outputs.ts:56-58` (`currency` optional); only the sandbox provider sets it (`platform/apps/cloud/lib/markting/sandbox-provider.ts:160`); Google/Meta/TikTok/Reddit/Snapchat omit it (`platform/packages/google/src/provider.ts:478-483`, `meta/src/provider.ts:519-524`, `tiktok/src/provider.ts:406-411`, `reddit/src/provider.ts:336`, `snapchat/src/provider.ts:129`); policy form converts a single number × 1e6 (`platform/apps/cloud/app/dashboard/policies/policy-form.tsx:56,97`); sandbox demo already mixes USD and SAR accounts (`sandbox-provider.ts:43-47`).
- Description: one absolute cap per organization applies to every account whatever its currency. 1,000 "units" is 1,000 USD on one account, 1,000 SAR (~267 USD) on another, 1,000 JPY (~7 USD) on a third. The MCP UI falls back to the label "(account units)" when currency is absent (`platform/packages/mcp/src/ui.ts:246`), so the reviewer also lacks currency context on live providers.
- Impact: a Gulf agency running SAR, AED, EGP and USD accounts cannot express a meaningful absolute ceiling; the cap is either too loose for strong currencies or too tight for weak ones.
- Recommendation: carry `currency` on every `budgetDeltas` entry (providers already know the account currency: `google/src/provider.ts:71-83`, `meta/src/provider.ts:97-104`) and make the absolute cap per-currency (or convert with a pinned FX table, with refusal when currency is unknown).

### A15-03 — Percentage cap silently falls through when the provider cannot supply a positive current value (Google `amountMicros` missing → 0; Reddit `goal_value` undefined; Snapchat budget unset; Meta/Google creates)
- Severity: **P2**
- Classification: VERIFIED_CODE
- Evidence: `engine.ts:143` (`delta.fromMicros !== undefined && delta.fromMicros > 0` guards the pct check); `platform/packages/google/src/provider.ts:833` (`budgetMicros: Number(budget.amountMicros ?? 0)` → `fromMicros: 0`); `reddit/src/provider.ts:336` (`fromMicros: campaign.goal_value` may be undefined); `snapchat/src/provider.ts:129` (`fromMicros` omitted when `previous` is not a number); `docs/ARCHITECTURE.md:173` acknowledges "creations and null caps skip it".
- Description: by design a create has no `from`, so only the (default-null) absolute cap applies. But for updates the same guard means a lookup that returns an empty/0 budget disables the only default rail: the delta check is skipped, and with `max_daily_budget_micros = null` any value passes. The Google GAQL row may legitimately omit `campaign_budget.amount_micros` (e.g. permission-restricted or shared-budget edge cases); the code defaults to 0 instead of refusing.
- Impact: a budget update of arbitrary size can pass validation on a live account whenever the current budget cannot be read. Google's `validateOnly` dry run (`google/src/provider.ts:253`) checks API validity, not policy.
- Recommendation: treat an unknown/zero `fromMicros` on an **update** as a policy failure ("current budget unknown; refusing to compute delta"), and make the absolute cap mandatory (non-null) whenever the pct cap cannot be applied.

### A15-04 — Budget caps are not re-checked at apply; the stored preview is returned, not a fresh one (TOCTOU within the 15-minute TTL)
- Severity: **P2**
- Classification: VERIFIED_CODE (also DOCUMENTED in `docs/TODO.md:38`, `docs/PHASE0-REPORT.md:89`)
- Evidence: `engine.ts:110-124` (apply re-runs only `checkStaticPolicy`; `provider.applyWrite` re-plans but `checkBudgetPolicy` is never called on the new plan; audit summary and return use `pending.preview`); only `synthetic-provider.ts:95,115` carries an `expected_daily_budget_micros` guard — Google/Meta/TikTok/Reddit/Snapchat do not.
- Description: validation computes the delta against the budget at time T0. Apply at T0+14 min re-reads the campaign (e.g. `google/src/provider.ts:466`) and writes the approved absolute value even if the budget changed in between (another user, Ads Manager, a scheduled rule). The approved "+20 %" can therefore land as +150 % or −60 % relative to the then-current budget, and the audit row records the stale summary.
- Impact: the approval card the human saw may not describe the change that executes. The engine side (paid-media-agent) does better: it re-reads and compares before/after in readback (`engine/src/paid_media_agent/tools/writes.py:720-770`) but that path is not the one adport executes in this product.
- Recommendation: re-run `checkBudgetPolicy` on the fresh plan in `apply`, and have providers assert `fromMicros` equality (as the synthetic provider does) or reject with `PENDING_MISMATCH` when the current value moved.

### A15-05 — Engine→adport unit contract ("daily_budget is account currency per day") is asserted by data files, not enforced; a live provider returning minor units would be scaled 100× by the bridge
- Severity: **P1** (serious financial risk on live Meta; mitigated by the default 25 % cap, unmitigated when that cap is relaxed)
- Classification: VERIFIED_CODE (mechanism) + NOT_VERIFIED (what a live Pipeboard Meta read actually returns)
- Evidence: `platform/apps/cloud/lib/markting/translate.ts:86-92` (`toMicros = Math.round(amount * 1_000_000)`, unconditional), `:107` (Meta: `Math.round(micros / 10_000)` cents), `:110` (TikTok: `micros / 1e6`); the engine's `before` value is the **raw** readback field (`engine/src/paid_media_agent/tools/writes.py:405-409`, `state.get(operation.readback_fields[f])`) and the `after` value is whatever the model passes (`:410-413`); `unit` is a free-text label from TOML (`engine/config/write-policy.example.toml:23,43,61`; `write_policy.py:34,81`); `translate.ts:21` parses `unit` but never checks it (`:148-151` only reads `.value`); `AliasBinding.currency` is documented "for the human preview only" (`translate.ts:52-53`) and in fact unused; Meta's native unit is minor units (`platform/packages/meta/src/provider.ts:19`, `tools.ts:152`); the TOML itself warns the rows "match the fixture catalog" and live rows must be added "only after reading the live schema" (`write-policy.example.toml:11-15`).
- Description: nothing in code pins what unit the engine's `daily_budget` is in. In the offline fixture it is whole currency (`engine/src/paid_media_agent/tools/fixtures.py:117-126`), and the bridge assumes that. On a live catalog the engine will show the reviewer `before = <raw readback>` labelled "account currency per day" and the model will propose a number in the same scale. If that scale is cents (Meta Graph API) the bridge multiplies by 1e6 and then divides by 1e4, i.e. the proposed `28000` (meaning $280.00) becomes `2,800,000` cents = $28,000/day. The default 25 % cap would catch this particular 100× jump because `fromMicros` would also be derived from Meta cents correctly on the adport side (`meta/src/provider.ts:507,522`), **but** only while `max_budget_delta_pct` is non-null and `fromMicros` is known (see A15-03).
- Impact: wrong-by-100× budgets are one policy toggle away on live Meta; the unit label is never machine-checked anywhere between engine and provider.
- Recommendation: make `unit` a closed enum (`currency_units_per_day | minor_units_per_day | micros_per_day`) in the engine policy and refuse in `translateProposal` when `after.unit` is absent or not `currency_units_per_day`; have the engine normalise live readback values into that unit before building `before`/`after`; add a bridge test with a non-fixture `unit`.

### A15-06 — Meta conversion assumes 100 minor units per currency unit; no `currency_offset` handling for zero-decimal (JPY, KRW, …) or other-offset currencies
- Severity: **P2** (wrong by 100× for affected currencies; Arabic-market majors SAR/AED/EGP/QAR are 2-decimal and unaffected)
- Classification: VERIFIED_CODE (absence) + INFERRED (Meta behaviour for offset-1 currencies, from training knowledge; not web-verified)
- Evidence: `platform/packages/meta/src/provider.ts:20` (`CENTS_TO_MICROS = 10_000` constant), `:507,522-523,614`, `translate.ts:107`; `rg -n "offset|JPY|KWD|zero.decimal" platform/packages/meta/src` → no matches; `meta/src/tools.ts:114-118,152` describe the field as "cents for EUR/USD".
- Description: Meta expresses budgets in the account currency's smallest unit; for offset-1 currencies the API value is whole units. The code hard-wires ×10,000, so for such accounts `fromMicros`/`toMicros` are both 100× too small (pct cap still right, absolute cap 100× too loose) and the bridge's `Math.round(micros / 10_000)` turns an engine value of 240 into `24000` sent to Meta.
- Recommendation: read the account's currency and apply the correct offset (or refuse non-2-decimal currencies explicitly); encode the supported currency set in a test.

### A15-07 — Bridge forces Reddit `budget_type: 'DAILY_SPEND'` and writes TikTok `budget` irrespective of the campaign's current budget mode
- Severity: **P2**
- Classification: VERIFIED_CODE
- Evidence: `translate.ts:108` (`budget_type: 'DAILY_SPEND'` always), `:110` (`budget` always); `platform/packages/reddit/src/provider.ts:337-339` (patch sends `goal_type: DAILY_SPEND` with the new `goal_value`; `fromMicros: campaign.goal_value` may be a LIFETIME value); `platform/packages/tiktok/src/provider.ts:396-417` (only `BUDGET_MODE_INFINITE` is refused; a `BUDGET_MODE_TOTAL` campaign gets its total budget overwritten with a daily number; the preview label does say "total budget").
- Description: the engine proposes a *daily* budget; on Reddit a lifetime-budget CBO campaign would be converted to a daily-spend goal with the daily amount, and on TikTok a total-budget campaign would have its lifetime cap replaced by the daily figure. The delta check then compares lifetime-vs-daily numbers.
- Impact: Reddit: campaign semantics silently change from lifetime to daily (ongoing spend). TikTok: total budget collapses to a daily-sized number (delivery stops) or, if the engine's daily number exceeds the total, the cap is raised.
- Recommendation: have the Reddit/TikTok plans refuse when the current `goal_type`/`budget_mode` is not daily unless the tool input explicitly says so; have the bridge map only to daily modes.

### A15-08 — Google shared budgets: change is applied to the shared `campaign_budget` resource with only a warning line
- Severity: **P2**
- Classification: VERIFIED_CODE
- Evidence: `platform/packages/google/src/provider.ts:470-472` (`changes.push('! this budget is SHARED …')`), `:485-496` (mutates `current.budgetResource` regardless); `budgetDeltas` target names a single campaign (`:479`).
- Description: the engine proposes a change to one campaign; if that campaign uses an explicitly shared budget, every campaign on that budget changes. The 25 % delta is computed once, not once per affected campaign, and the Approvals page shows only the summary (`docs/TODO.md` §6 notes the full preview is not shown inline).
- Recommendation: refuse shared budgets by default (or require an explicit `allow_shared_budget` flag) and enumerate affected campaigns in the preview.

### A15-09 — `summarize_window` pacing divides by *active* days and trusts raw `daily_budget` units from `list_campaigns`
- Severity: **P3** (correct for fixtures; unit-coupled on live data)
- Classification: VERIFIED_CODE / VERIFIED_TEST (fixture path)
- Evidence: `engine/src/paid_media_agent/tools/summary.py:88-89` (`average_daily = metrics.spend / active_days`), `:61-69` (`Decimal(str(campaign["daily_budget"]))`, no unit or currency check), `:145-147` (`over_budget` when pacing > 1); spend is normalised to whole currency per platform (`normalize.py:14-25`); `test_summarize_window.py:72-74,116-117` cover the arithmetic.
- Description: pacing is average spend on days with rows divided by the configured daily budget. A campaign that ran 2 of 7 days is paced on 2 days (reasonable for "did it hit its daily cap", misleading for "did it spend its weekly allotment"). The budget value is used as-is: if a live `list_campaigns` returns cents or micros, pacing is off by 100×/10⁶× with no flag. The X Ads direct adapter does convert (`tools/direct/x_ads.py:263-264`), showing the authors know the problem exists elsewhere.
- Recommendation: expose both `active_days` and `calendar_days` pacing; validate the budget field's unit per platform (same unit registry as A15-05) and attach `currency`.

### A15-10 — Engine proposal path has no magnitude policy; fixture schema admits `daily_budget: 0`
- Severity: **P3** (GAP relative to the wiki's "20–30 % steps"; adport is the real gate in this product)
- Classification: VERIFIED_CODE
- Evidence: `engine/src/paid_media_agent/tools/writes.py:84-127` (`classify_risk` emits `budget_delta`/`budget_increase` flags only); `rg -i "max_|delta|pct|cap"` over `write_tools.py`, `writes.py`, `config.py`, `domain/proposals.py` → no magnitude settings; `fixtures.py:123` (`"minimum": 0`); `write_policy.py` has no min/max fields; `translate.ts:88` rejects `<= 0` on the adport side.
- Description: the engine's "write policy" is an allow-list of tools and fields, not a magnitude policy. Any size of change becomes a proposal; magnitude discipline is prose (`bidding-and-budget.md:17`).
- Recommendation: add `max_relative_change` / `min_value` / `max_value` per editable field in `WritePolicyEntry`, enforced in `_scoped_args`, so the engine refuses to even stage out-of-policy proposals.

### A15-11 — The showcase budget proposal (g-103 300 → 240) is a hard-coded scripted step, not a computed recommendation
- Severity: **P3** (not a defect — a demo fixture — but README framing overstates it)
- Classification: VERIFIED_CODE

## What a world-class system would need (gaps, concrete)

1. **Typed money everywhere**: `{ amount_micros, currency }` on every budget value crossing a boundary (engine proposal `before/after`, adport `budgetDeltas`, UI), with a closed unit enum and refusal on mismatch. Today the type is `number` + a free-text label.
2. **Multi-layer caps**: per-op %, per-op absolute per currency, rolling 24 h/7 d cumulative % per campaign, account daily ceiling, organization ceiling, minimum dwell time between changes to the same entity, and a "shared budget" guard. Re-evaluate all of them at apply on a fresh preview.
3. **Marginal economics**: per-entity marginal CPA/ROAS between consecutive windows at different spend levels; flag saturation when spend ↑ and conversions flat (the wiki describes this verbally at `bidding-and-budget.md:20-22`; make it a deterministic tool output like `compare_periods`).
4. **Pacing done properly**: calendar-day and active-day pacing, month-to-date vs monthly budget for platforms that balance monthly (Google), learning-phase and change-history awareness (budget-change log joined to daily series), weekday-baseline anomaly scores instead of a flat ±50 %.
5. **Allocation layer**: account- and channel-level budget envelopes, a deterministic reallocation proposal generator bounded by the caps above, with reversal plans auto-populated from `before` values.
6. **Currency intelligence**: per-account currency offset tables (Meta), FX-pinned conversion for portfolio totals, Arabic-locale money formatting.
7. **Verification parity**: adport apply should do what the engine executor does — read back and prove the resulting value (`writes.py:720-770`) and refuse when the pre-state moved.
