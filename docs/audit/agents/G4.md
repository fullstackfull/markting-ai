## Findings

### G4-01 — Default (free) plan silently makes the whole write-preview promise impossible, and onboarding never says so
- Severity: P2
- Classification: VERIFIED_CODE
- Evidence: `platform/supabase/migrations/20260828120000_cloud_plans_and_account_scope.sql:5` (`plan ... default 'reader'`); `platform/apps/cloud/lib/cloud/plans.ts:25-26` (reader `writeAccess:false`), `plans.ts:103` (`scopes.filter(... 'tools:write' || writeAllowed)` strips write), `plans.ts:69-78` (missing row defaults to reader); `platform/packages/core/src/tools/write.ts:38,52-62` (the *dry-run preview* is the same `readOnly:false` tool, so previewing needs `tools:write`); `platform/apps/cloud/app/api/v1/tools/[tool]/route.ts:11` + `lib/cloud/auth.ts:39-41` (`requireScope` throws raw `API key lacks required scope: tools:write`, 403); `app/api/approvals/[id]/apply/route.ts:18` (same for dashboard apply); onboarding copy that promises it anyway: `lib/i18n/messages/onboarding.ts:15` (`pointPreview: 'Every write requires an exact preview'`) and `lib/i18n/messages/agents.ts:50` (`tipPreview: 'Review the exact preview before applying any write.'`). No upgrade/plan context anywhere in `app/onboarding/onboarding-flow.tsx` or the onboarding messages.
- Description: Every new signup lands on `reader`/Free. Reader strips `tools:write`, and because the preview (validate) call is the first half of the same write tool, a Free user cannot even *preview* a write — the thing the welcome screen and agent tips present as the core safety feature. The seed script's own comment states this: `infra/seed/seed-demo.mjs:5-6` ("reader strips tools:write, so no previews"). The onboarding flow never discloses the plan, its limits, or that writes require Operator+.
- Impact: A buyer completes the "about four minutes" wizard, sets up their agent, runs the suggested first write, and hits a 403 scope error (raw on the REST path). The onboarding's headline value proposition is undeliverable on the default plan with no explanation or upgrade affordance.
- Mitigant (verified): the MCP path degrades gracefully — `app/mcp/route.ts:20-39` builds a `PLAN_LIMIT` denial with an upgrade message, surfaced by `packages/mcp/src/index.ts:122-136` as "Unavailable on the current plan…". But it fires only when `grantedScopes` still includes `tools:write` and only over MCP; the REST `/api/v1/tools` and dashboard apply paths return the raw scope error.
- Recommendation: Add a plan/limits panel to onboarding (welcome or a dedicated step) stating Free is read-only and writes need Operator+, with an upgrade link; make the REST tool route and apply route return the same structured `PLAN_LIMIT` message the MCP path uses.

### G4-02 — No organization switcher: invited members can never reach the workspace they were invited to
- Severity: P2
- Classification: VERIFIED_CODE
- Evidence: `platform/apps/cloud/lib/cloud/dashboard.ts:38-41` (`requireDashboardTenant` selects membership `order by membership.created_at asc limit 1`); `platform/apps/cloud/app/api/members/route.ts` + `lib/cloud/tenant-admin.ts` (invite via `inviteUserByEmail` then membership insert); `platform/supabase/migrations/20260828140646_onboarding_feedback_and_premium_plan.sql:44-51` and the `handle_new_user` trigger (each new auth user gets a personal org/membership at signup). No org-param/cookie read in `app/dashboard` (`rg organization_id app/dashboard` → only `principal.organizationId`); `components/shell.tsx`/`nav` have no org switcher.
- Description: Tenant resolution is hardwired to the *oldest* membership. A user invited to an agency/team workspace already has (or is given, by the invite's `inviteUserByEmail`) a personal org created at signup, which is always older than the invited membership. They therefore always land in their own empty personal org and have no UI to switch to the org they were invited to.
- Impact: Breaks the Agency plan's team / client-workspace onboarding (`plans.ts:36-39` `clientWorkspaces:true`): invited teammates cannot access the shared workspace at all. The invite feature appears functional (member row + audit event) but is unreachable by the invitee.
- Recommendation: Add an organization selector (and persist the active org in a cookie/session), or route a freshly-invited user to the inviting org on first login.

### G4-03 — Provider cards have no "awaiting app approval" state; the opaque "Unavailable" is a silent dead-end and contradicts the docs
- Severity: P3
- Classification: VERIFIED_CODE (behavior) / DOCUMENTED_ONLY (the contradicted claim)
- Evidence: `platform/apps/cloud/lib/i18n/messages/connections.ts:20,57` (only states: `unavailable: 'Unavailable'` / `'غير متاح'`); `app/dashboard/connections/provider-connections.tsx:76` (card shows "Unavailable" when `!provider.available`), `provider-connections.tsx:89` (`connection || provider.available ? (...) : null` → when unavailable AND unconnected the Actions column renders nothing — no button, no reason); `lib/cloud/provider-oauth.ts:393-411` (`oauthAvailability` = `configured()` i.e. env creds present) ANDed with `lib/cloud/provider-rollout.ts:9-16` (rollout allowlist). Contradicting docs: `docs/snapchat-live-checklist.md:17` ("card must no longer say '…approval'") and `docs/PHASE0-REPORT.md` ("cards stay '…approval' until the provider env blocks are set") describe copy that does not exist.
- Description: A single "Unavailable" conflates three very different causes (OAuth app not configured on this deployment, provider gated behind `ADPORT_PROVIDER_TEST_ORGANIZATION_IDS`, or synthetic-reviewer suppression) and, crucially, gives the user neither a Connect button nor an explanation. On a deployment where provider OAuth env blocks are unset — which README/TODO list as an un-met production gate (`README.md:124-131`, `docs/TODO.md §cloud`) — *every* card is "Unavailable" and a new user can connect nothing.
- Impact: First-run dead-end with no feedback: the connect step looks broken rather than "this platform isn't enabled yet." The documented "awaiting approval" affordance that would have explained provider-review status is absent.
- Recommendation: Distinguish states (not-configured / pending platform review / rollout-gated / ready) with specific copy, and show a disabled card with a tooltip reason rather than an empty actions cell; fix or remove the doc references to the non-existent "approval" copy.

### G4-04 — Two different "accounts" surfaces; the account picker is not inside the onboarding stepper
- Severity: P3
- Classification: VERIFIED_CODE
- Evidence: `app/onboarding/onboarding-flow.tsx:77-82` (accounts step renders `AccountAccessManager`, which only enables/disables already-added accounts — `app/dashboard/accounts/account-access-manager.tsx:36-50`, gated by `maxActiveAccounts`); the *picker* that chooses which discovered accounts to add is a separate page `app/account-selection/page.tsx` + `provider-account-picker.tsx`; `app/api/oauth/[provider]/callback/route.ts:96` always redirects to `/account-selection?selection_id=...` after connect (via the popup → `/oauth/provider-complete` → main-window navigate, `lib/oauth-popup.ts`), then `provider-account-picker.tsx:37` returns to `returnPath` (`/onboarding`). `/account-selection` renders its own header with no onboarding progress bar (`page.tsx:26-27`).
- Description: Connecting from onboarding bounces the user out of the stepper into `/account-selection` to pick accounts, then back to the onboarding accounts step to *separately* enable each for agent access — subject to the Free cap of 3 (`plans.ts:25` `maxActiveAccounts:3`, enforced with a modal). The "add" vs "enable" distinction is real but under-explained and the picker sits outside the progress UI.
- Impact: Confusing first-run; the user can leave onboarding believing they "added accounts" yet none are agent-enabled, or hit the 3-account cap mid-flow. If a provider requires selection and the user doesn't finish it, the onboarding accounts step shows "No accounts discovered yet" with no in-flow path to the picker (that link lives on Connections: `provider-connections.tsx:80`).
- Recommendation: Embed the account picker as a sub-step within the onboarding shell (preserve the progress indicator), and merge or clearly sequence "add" and "enable."

### G4-05 — First-run for an Arabic-first media buyer lacks commercial localization and guided activation (GAP)
- Severity: GAP
- Classification: VERIFIED_CODE
- Evidence: `platform/apps/cloud/lib/cloud/plans.ts:11-44` (prices are `monthlyPriceEur`/`annualPriceEur` only — EUR, no SAR, no VAT); onboarding has no pricing/plan step (`onboarding-flow.tsx`); the only "guided first task" is one string, `lib/i18n/messages/agents.ts:48,116` (`safePromptText`); `README.md` and `docs/TODO.md` acknowledge "no VAT or SAR pricing yet." Positive counter-evidence (i18n layer is strong): `app/layout.tsx:19` (`<html lang dir>`), `lib/i18n/config.ts` (`DEFAULT_LOCALE = ar`, `dirOf → rtl`), and fully bilingual onboarding/agents message files.
- Description: The language layer is correctly Arabic-first and RTL. What is missing for the target buyer is market fit in the first run: SAR/VAT pricing, an up-front explanation of plan limits, and a guided first analysis on the user's own connected account rather than a single copy-paste prompt. There is no seeded sample data or activation checklist on the real (non-demo) path.
- Impact: A Saudi/MENA buyer sees EUR prices, no plan context, and an empty dashboard after setup on the Free plan — weak activation despite a polished Arabic UI.
- Recommendation: Localize currency (SAR) and tax, add a plan/limits step, and add a guided first-report/first-analysis action on a connected account.

### G4-06 — Vendored "Adport" branding and a hardcoded English title leak through the Arabic-first product
- Severity: P3
- Classification: VERIFIED_CODE
- Evidence: `app/onboarding/page.tsx:13` (`metadata = { title: 'Set up Adport' }` — hardcoded English, not localized); onboarding copy references "Adport" in both locales (`lib/i18n/messages/onboarding.ts:12,44` heroCopy "add Adport to…", "أضف Adport إلى…"); `BrandLockup` used in onboarding/account-selection headers.
- Description: The product is the Arabic-first "markting" layer over vendored `adport`, yet onboarding surfaces the upstream brand name and an un-localized page title.
- Impact: Brand/polish inconsistency in the most brand-sensitive screen (first run). Minor.
- Recommendation: Replace with the product brand and localize the metadata title via the i18n layer.

## What a world-class system would need (gaps, concrete)

1. Plan transparency in onboarding: a step/panel stating Free is read-only, listing caps (3 active accounts, 1 member, 30-day retention from `plans.ts:25`), with an inline upgrade CTA; structured `PLAN_LIMIT` errors on *all* write paths, not just MCP.
2. Organization switcher + invite landing: persist an active org and route invited users to the inviting workspace, so Agency/team onboarding works.
3. Honest provider states: separate copy for not-configured / pending-review / rollout-gated / ready, and never render a card with no action and no reason.
4. Unified account step inside the stepper so "add" and "enable for agent" are one guided sequence with the progress indicator intact.
5. Arabic-first commercial fit: SAR pricing + VAT, and a guided first analysis/report on a real connected account (the only current guidance is one `safePromptText` string).
6. Brand consistency: remove upstream "Adport" leakage from first-run copy and localize the page title.

## Disagreements / claims in docs that the code contradicts

- `docs/snapchat-live-checklist.md:17` and `docs/PHASE0-REPORT.md` tell operators to watch for provider-card copy saying "…approval". No such UI string exists; the only unavailable state is `unavailable: 'Unavailable'`/`'غير متاح'` (`connections.ts:20,57`). (Independently confirmed; also noted by A4.)
- Onboarding's own copy — `pointPreview` "Every write requires an exact preview" (`onboarding.ts:15`) and `tipPreview` (`agents.ts:50`) — contradicts the default-plan reality that previews/writes are impossible on `reader` (`plans.ts:25,103`; `write.ts:38`). The welcome screen promises a capability the default plan denies.
- The invite/team UI (`app/dashboard/team/team-members.tsx`, `app/api/members/route.ts`) implies a working team workspace, but `dashboard.ts:38-41` prevents invitees from ever reaching it — the feature is functionally unreachable for the invited user.
