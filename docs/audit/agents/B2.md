## Findings

### B2-01 — `ATTRIBUTION_DIFFERS` quality flag is dead: never emitted, attribution metadata is captured then dropped
- Severity: GAP (capability DOCUMENTED_NOT_IMPLEMENTED)
- Classification: VERIFIED_CODE
- Evidence: `engine/src/paid_media_agent/domain/common.py:64` defines `ATTRIBUTION_DIFFERS = "attribution_differs"`. A full `grep` over `engine/src` and `engine/tests` finds no other occurrence — it is never appended, added to a set, or compared. The only attribution data in the pipeline are literal strings: `engine/src/paid_media_agent/tools/fixtures.py:323` (`"attribution": "7d_click_1d_view"` on Meta native rows), `engine/src/paid_media_agent/tools/direct/x_ads.py:367` (`"x_web_conversion_purchases"`), `engine/src/paid_media_agent/tools/direct/openai_ads.py:249` (`"openai_ads_reported_conversions"`). None is ever read back: `normalize.py` only reads spend/entity/metric keys and copies `source_fields=dict(raw)` (normalize.py:164); nothing consumes `source_fields["attribution"]`.
- Description: The data model reserves a flag for "attribution differs across sources" and providers even emit their attribution model as metadata, but there is no code that detects differing attribution models or sets the flag. For X Ads / OpenAI Ads the attribution string sits at the payload top level (sibling to `rows`), while `reads.py` normalizes only `payload["rows"]`, so it is discarded before reaching `source_fields`.
- Impact: The one machine-readable signal designed to warn users that providers use incompatible attribution is inert. Analysts never see it; downstream code cannot branch on it.
- Recommendation: Either implement detection (carry the per-provider attribution model into `PerformanceRow`/artifact metadata, set `ATTRIBUTION_DIFFERS` when a cross-platform combination spans more than one model) or remove the enum value so it does not imply a capability that does not exist.

### B2-02 — Cross-platform conversion / ROAS totals combine different attribution windows with no flag
- Severity: P2
- Classification: VERIFIED_CODE
- Evidence: `engine/src/paid_media_agent/tools/compute.py:310-326` is the entire suppression ruleset for `cross_platform_total`: it suppresses on no data, unavailable sources, mixed currencies, incomplete windows, a missing metric, or differing window date-ranges. Attribution is not among the checks. When none trip, `_combine` sums `conversions` and `conversion_value` straight across platforms (compute.py:282-283). So a Meta artifact (`7d_click_1d_view`) + Google (its default) + Reddit can be summed into one conversions/ROAS total with `total_suppressed_reason is None`. The `compare_periods` tool advertises exactly the opposite guarantee: "a cross-platform total appears only when sources are compatible" (`engine/src/paid_media_agent/tools/compare_periods.py:140`), and "compatible" silently excludes attribution. The summary note list carries no attribution caveat (`compute.py:407-409`).
- Description: Cross-platform conversion counts are summed as if comparable, but each platform counts conversions under its own attribution window/model. This is the core attribution-mixing hazard and it is not surfaced in the `compare_periods` output at all.
- Impact: A combined conversions figure and the ROAS derived from it (`cross_platform_total.roas`) overstate or distort true business results, and are presented as a clean "compatible" total. Decisions (budget shifts, pause/scale) taken on that number are made on apples-to-oranges conversions. Financial-interpretation risk, not data loss, hence P2.
- Mitigation that exists: the *rendered report* adds a prose note when >1 platform — "conversions use each platform's own attribution; they are not deduplicated people" (`engine/src/paid_media_agent/reports/render.py:169-171`) and "Platform attribution; customers may overlap." (render.py:327). That mitigates the final report but not the `compare_periods` analysis artifact/summary that models and other tools consume.
- Recommendation: Add attribution to the compatibility gate (suppress or at minimum flag the cross-platform conversions/value/ROAS total when attribution models differ), and surface a note in `summarize()` whenever more than one platform contributes conversions.

### B2-03 — Direct X Ads / OpenAI Ads providers never set `data_complete_through`, so conversion lag is not surfaced and recent days count as complete
- Severity: P2
- Classification: VERIFIED_CODE
- Evidence: `ProviderResult.data_complete_through` defaults to `None` (`engine/src/paid_media_agent/tools/providers.py:19`). The X and OpenAI performance reads return `ProviderResult(payload={...})` with no `data_complete_through` (`x_ads.py:363-369`, `openai_ads.py:245-251`). In `normalize.py`, the lag flag is only added when a boundary exists — `if data_complete_through is not None and day > data_complete_through` (normalize.py:141) — and completeness is `is_complete=data_complete_through is None or day <= data_complete_through` (normalize.py:156). With `None`, every row is `is_complete=True` and no row ever gets `INCOMPLETE_WINDOW`. `INCOMPLETE_WINDOW` is the system's only conversion-lag / freshness signal (it drives the `incomplete window` suppression at compute.py:319-322).
- Description: `INCOMPLETE_WINDOW` is the mechanism that keeps immature, still-converting recent days out of a confident cross-platform total. X Ads and OpenAI Ads bypass it entirely by not declaring a completeness boundary, so their most recent (laggiest) days are treated as fully settled. Contrast the fixture path, which does ship a boundary and even encodes differing lags (reddit `2026-08-26` vs google/meta `2026-08-28`).
- Impact: For these two direct providers, reports built on the last few days silently include undercounted conversions as if complete, and the cross-platform total is not suppressed for incompleteness. This is the conversion-lag blind spot in production code (fixtures are safe; two real providers are not).
- Recommendation: Require each read provider to supply a `data_complete_through` (or make its absence a loud `SOURCE_UNAVAILABLE`/`PARTIAL_SOURCE` rather than a silent "everything complete"). At minimum flag rows from providers that declare no completeness boundary.

### B2-04 — Platform `report` tool: docstring is accurate for math but omits any attribution/freshness caveat, and `complete` means "no truncation/errors," not "data settled"
- Severity: P3
- Classification: VERIFIED_CODE
- Evidence: Tool description at `platform/packages/core/src/tools/builtin.ts:54-57` promises "normalized metrics (spend, clicks, conversions, ROAS, ...)", "currency-separated totals and spend-weighted ROAS; never average row ratios or combine currencies. Null metrics are unavailable." `report-summary.ts` honours the math claims: it groups by a validated 3-letter currency else keeps rows account-scoped (report-summary.ts:9-14), totals only when every row has the metric else `null` (report-summary.ts:19-23), reconstructs ROAS spend-weighted via `conversion_value` or `spend*roas` (report-summary.ts:27-31), and labels `roas_method` (report-summary.ts:38). But `conversions` is an additive metric summed across all rows in a currency group (report-summary.ts:3, 21) — i.e. across providers/accounts that share a currency — with no attribution disclosure field. The `complete` flag passed in is `!truncated && errors.length === 0` (builtin.ts:138), so a "complete" report can still be built on unsettled, attribution-mismatched conversions.
- Description: On the platform (adport) side there is no attribution or data-freshness concept at all; the docstring's silence is consistent with the code, but the summary nonetheless sums cross-provider conversions per currency with nothing analogous to the engine's prose disclosure. The field name `complete` reads as data-completeness but only means "all requested rows returned without provider errors."
- Impact: A user (or model) reading `summary.groups[].metrics.conversions` across, say, Google-USD + Meta-USD gets one summed conversions number mixing attribution windows, labelled by a `complete:true` that says nothing about freshness. Lower severity than the engine case because this path exposes the contributing `accounts` list, so the multi-provider nature is at least visible.
- Recommendation: Add an attribution/overlap caveat to the `report` tool description and, ideally, a per-group flag when a currency group spans more than one provider (differing attribution). Consider renaming or documenting `complete` to avoid the freshness reading.

## What a world-class system would need (gaps, concrete)
- A first-class attribution descriptor on every normalized row/artifact (model + click/view windows), not a free-text string that gets dropped. Carry it through to `PlatformComparison`.
- Attribution-aware combination: suppress or explicitly flag any cross-platform conversions / conversion_value / ROAS total that spans more than one attribution model; wire this into `ATTRIBUTION_DIFFERS` so it is machine-readable, and echo it in `summarize()` notes and the platform `report` summary.
- Separate "reporting lag / freshness" from "attribution maturity." `data_complete_through` today conflates them; even a day `<= data_complete_through` can still gain conversions under a 7-day window. A world-class system models a conversion-maturity curve (or at least a second boundary) so recent-but-reported days are marked still-maturing.
- A hard requirement that every read provider declare a completeness boundary; absence must degrade to a loud flag, never silent completeness (fixes B2-03 for X/OpenAI).

## Disagreements / claims in docs that the code contradicts
- `compare_periods` tool docstring: "a cross-platform total appears only when sources are compatible" (compare_periods.py:140). The code's notion of "compatible" (compute.py:310-326) excludes attribution, so totals that combine different attribution windows are produced and presented as compatible. The claim overstates the guarantee (B2-02).
- The `DataQualityFlag.ATTRIBUTION_DIFFERS` enum member implies the system can report attribution divergence; the code never produces it (B2-01).
- Platform `report` summary field `complete` reads as data-completeness but is only "no truncation and no provider errors" (builtin.ts:138); it is unrelated to attribution maturity or freshness (B2-04).
