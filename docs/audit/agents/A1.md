## Findings

### A1-01 — Typed status/budget writes never verify the object belongs to `account_id` (policy and account-scope bypass)
- Severity: **P1** (borderline P0: it is an unsafe-ad-execution path that defeats two explicit safety controls, but the blast radius is limited to ad accounts the tenant's own token can already reach, so it is not cross-tenant).
- Classification: VERIFIED_CODE
- Evidence: `platform/packages/meta/src/provider.ts:319-341` (`planSetLifetimeBudget`), `:478-500` (`planSetStatus`), `:503-534` (`planSetBudget`) read `payload.object_id` / `campaign_id` / `ad_set_id` with `fields: 'name,daily_budget'` etc. and never call `assertObjectOwnedByAccount`. Only the generic tools do: `:379` (`planApiUpdate`) and `:394` (`planApiDelete`). `act` is computed at `:293` and then unused for the typed update/status plans. Account-level controls key on `op.accountId` only: `platform/apps/cloud/lib/cloud/account-scope.ts:81-89` (`AccountScopedProvider.previewWrite/applyWrite`), `:48-54` (authorizer checks `input.account_id`), `platform/packages/core/src/policy/engine.ts:127-131` (`protected_accounts`). Test `meta.test.ts:437-450` covers cross-account rejection for `meta_api_update` only; no test asserts the typed tools reject a foreign `object_id`.
- Description: A Meta user/system-user token typically spans many ad accounts. A caller (LLM via MCP, the markting proposal bridge `platform/apps/cloud/lib/markting/translate.ts:107,118`, or a dashboard user) can pass an enabled, unprotected `account_id` together with an `object_id` from (a) an ad account the workspace admin deliberately did not enable in Accounts, or (b) an account listed in `protected_accounts`. The Graph call `POST /{object_id}` succeeds because the token has rights there. The audit row records the wrong account.
- Impact: pause/activate campaigns or change daily/lifetime budgets on accounts the workspace excluded or protected; audit trail mis-attributes the change. The 25 % delta cap still applies because the current value is looked up, but the absolute cap and protected-account rail are account-agnostic in practice.
- Recommendation: call `assertObjectOwnedByAccount(objectId, act)` in `planSetStatus`, `planSetBudget`, `planSetLifetimeBudget` (one extra GET of `account_id`, or fold `account_id` into the existing lookup `fields`), and add tests mirroring `meta.test.ts:437-450` for all three typed tools.

### A1-02 — Budget unit conversion assumes a 2-decimal currency everywhere (`CENTS_TO_MICROS = 10_000`)
- Severity: **P2** (financial risk for zero-decimal-currency accounts; no risk for SAR/USD/EUR)
- Classification: VERIFIED_CODE (the fixed constant and absence of currency awareness); INFERRED (Meta's per-currency minor-unit semantics are from the Marketing API reference, not re-verified against a live account)
- Evidence: `provider.ts:20` constant; used at `:333-334`, `:452`, `:522-523`, `:568`, `:614`. `BudgetDelta.currency` exists in core (`platform/packages/core/src/provider.ts:91-98`) but every Meta delta omits it (`provider.ts:331-335, 450-453, 519-524, 566-569, 614`). Policy abs cap is in micros (`policy/policy.ts:15`). Bridge: `translate.ts:107` `Math.round(micros / 10_000)` regardless of account currency. Tool text hard-codes "cents for EUR/USD" (`tools.ts:119,152`). No `JPY|exponent|minor unit` handling anywhere in `platform/packages/meta`, `core`, or `apps/cloud/lib` (rg, 0 hits).
- Description: Meta budgets are integers in the account currency's minor unit; for currencies Meta treats as having no minor unit (e.g. JPY, KRW, TWD, HUF, CLP, ISK, VND) the integer *is* the whole unit. The code multiplies by 10,000 regardless, so a ¥50,000 daily budget is reported to the policy engine as ¥500 (50,000 × 10,000 micros = 500 units) and the bridge turns a ¥50,000 proposal into `daily_budget_cents: 5,000,000`, i.e. ¥5,000,000.
- Impact: 100x over-/under-statement of budget to the absolute cap and in the human preview for those accounts; a bridge-originated approval could set a budget 100x the intended value. Not reachable for SAR/USD/EUR accounts.
- Recommendation: fetch `currency` with the budget lookup (`fields: 'name,daily_budget,account_id,currency'` via the owning account), carry a per-currency exponent table, set `BudgetDelta.currency`, and reject unknown currencies instead of assuming 2 decimals.

### A1-03 — Normalized "conversions" are hard-wired to `omni_purchase`; non-purchase objectives read as zero and trigger an auto-proposed pause
- Severity: **P2**
- Classification: VERIFIED_CODE; VERIFIED_TEST (test asserts the omni_purchase-only behaviour, `meta.test.ts:197`)
- Evidence: `provider.ts:174` requests `actions,action_values`; `:202-203` `actionValue(row.actions, 'omni_purchase')`; `:213-214` derive cpa/roas from that. Audit rule `platform/packages/core/src/audit/packs/core-performance.ts:8-30` flags `spend >= 50 && conversions === 0` as warn/critical and attaches `proposedAction: ctx.actions.pauseCampaign` (Meta maps that to `meta_set_campaign_status` PAUSED, `provider.ts:84-91`). No attribution-window parameter is ever sent (`rg attribution platform/packages/meta` -> 0 hits), so counts follow the account's attribution setting silently.
- Description: Lead, app-install, messaging, engagement, awareness and traffic campaigns (five of the six objectives the create tool offers, `tools.ts:9-16`) report `conversions = 0`, `cpa = 0`, `roas = 0` in `report()`.
- Impact: every healthy OUTCOME_LEADS / OUTCOME_APP_PROMOTION campaign above $50 spend is flagged "spent X with 0 conversions – critical" with a ready-to-run pause. In the cloud this is still gated by the approval flow, but it is a systematically wrong recommendation, and the dashboard KPIs for those accounts are misleading. The raw `meta_insights` tool returns the full `actions` array, so an LLM can work around it, but the normalized/report/audit path cannot.
- Recommendation: map conversions per campaign objective (or accept a configurable action type list: `omni_purchase`, `lead`, `omni_app_install`, `onsite_conversion.messaging_conversation_started_7d`, `offsite_conversion.fb_pixel_custom`, …), expose `action_attribution_windows`/`use_unified_attribution_setting`, and record the window used on each row.

### A1-04 — Engine (paid-media-agent) Meta normalization only understands the synthetic fixture shape; Graph-shaped `actions`/`action_values` arrays are dropped
- Severity: **P2** (reliability of the AI engine's Meta analysis in live mode)
- Classification: VERIFIED_CODE (the mapping); NOT_VERIFIED (the live Pipeboard Meta MCP response shape)
- Evidence: `engine/src/paid_media_agent/tools/normalize.py:20` (`META_ADS: ("spend", 1)`), `:28-29` (`_CONVERSION_KEYS = conversions|purchases|results`, `_VALUE_KEYS` includes `action_values` as a scalar), `:130-132` (`_first(raw, ("clicks","link_clicks"))`, `_decimal(...)`). `_decimal(list)` -> `Decimal(str(list))` raises `InvalidOperation` -> `None` (`:58-64`). Fixture rows are hand-shaped (`fixtures.py:313-324`: `date_start`, `link_clicks`, `purchases`, `purchase_value`, `attribution: "7d_click_1d_view"`), which is not what `act_<id>/insights` returns. The write policy expects Pipeboard tools named `meta_ads__update_campaign_budget` / `meta_ads__get_campaign` and says so: "The rows below match the fixture catalog used by the offline demo" (`engine/config/write-policy.example.toml:295-297, 321-337`). Live Pipeboard catalog is loaded at runtime (`tools/pipeboard.py:147-180`) and the test for account discovery assumes a tool `meta_ads__get_ad_accounts` returning `{"data":[{"id":"act_999",...}]}` (`engine/tests/unit/test_admin_console.py:203-233`).
- Description: Offline, the engine reads Meta from fixtures convincingly (3 campaigns, 84 days, ad-group split that reconciles, `test_entity_grain.py[meta_ads]` passes). Live, the engine depends entirely on a third-party MCP (Pipeboard, `config.py:141`) whose Meta tool names and row shapes are not in this repository; if rows arrive Graph-shaped, conversions/value normalize to `None`, every row gets `MISSING_METRIC`, and cross-platform totals are suppressed (by design, `test_compute.py:149-165`).
- Impact: the "AI media buyer" cannot be shown to analyse real Meta data; the only end-to-end evidence is synthetic.
- Recommendation: add a Graph-shaped normalization branch (`actions[]` by `action_type`, `action_values[]`, `reach`, `frequency`, `date_start/date_stop`), pin and record the live Pipeboard Meta schema (the write-policy file already says to), or (architecturally) let the engine read through the platform's native `MetaAdsProvider` so both halves see the same numbers.

### A1-05 — Generic Meta create/update previews are client-side only although the provider advertises `serverDryRun: true`
- Severity: **P3** (an approver reviews an unvalidated payload; the apply then fails loudly rather than silently)
- Classification: VERIFIED_CODE; VERIFIED_TEST (`meta.test.ts:409-410` asserts `serverValidated === false` and zero network calls)
- Evidence: `provider.ts:81` `capabilities(): { serverDryRun: true }`; `:361`, `:385`, `:398` set `serverValidated: false` for `meta_api_create`, `meta_api_update`, `meta_api_delete`; `:273-274` skips `execute(true)` when not server-validated. `platform/docs/providers.md:19` only documents client-side preview for *deletes*. `docs/ARCHITECTURE.md:73` states "Only Google and Meta report serverDryRun: true" without noting that 3 of the 9 Meta writes are not server-validated.
- Description: Meta supports `execution_options=["validate_only"]` on campaign/ad set/ad POSTs, and the code already has `withExecutionOptions` (`:416-418`), yet the generic tools do not use it during preview.
- Impact: the richest write surface (the only way to set bids, placements, promoted objects, schedules) gives the approver a JSON echo, not a Meta-validated plan.
- Recommendation: run `validate_only` for `meta_api_create`/`meta_api_update` on `campaigns|adsets|ads` edges and keep client-side only for edges that lack it.

### A1-06 — Typed `meta_create_ad_set` cannot build a production-grade ad set
- Severity: GAP (capability PARTIAL), with one P3 defect
- Classification: VERIFIED_CODE; NOT_VERIFIED (current Marketing API required-field rules such as `targeting_automation.advantage_audience`)
- Evidence: `provider.ts:536-588`, `tools.ts:155-172`: fields are `name, campaign_id, optimization_goal (default LINK_CLICKS), billing_event (default IMPRESSIONS), targeting.geo_locations.countries, status, daily_budget`. P3 defect: the default `optimization_goal: LINK_CLICKS` is applied even inside an `OUTCOME_SALES`/`OUTCOME_LEADS` campaign, which Meta rejects or which silently optimizes for the wrong event; the preview does not warn.

- Recommendation: either grow the typed tool (objective-aware defaults, promoted_object, bid strategy, schedule, placements, audiences) or document it as "smoke-test ad set only".

### A1-07 — Boolean/non-budget fields matching `/budget/i` produce spurious policy deltas and block legitimate updates

## What a world-class system would need (concrete gaps)

1. Objective-aware conversion mapping and explicit attribution windows (`action_attribution_windows`, `use_unified_attribution_setting`) recorded on every row; expose `results`/`cost_per_result` per objective.
2. Typed discovery tools: campaigns (with `effective_status`, `objective`, `bid_strategy`, `daily/lifetime_budget`, `is_budget_schedule_enabled`, CBO flag), ad sets (with `learning_stage_info`, `optimization_goal`, `promoted_object`, `targeting` summary, `attribution_spec`), ads (with `effective_status`, review/`issues_info`), creatives (preview URLs, asset feed, thumbnails).
3. Insights with `time_increment=1`, `breakdowns` (age, gender, country/region, publisher_platform, platform_position, device_platform, impression_device), `action_breakdowns`, `filtering`, `sort`, and normalized `reach`, `frequency`, `cpm`, `link_clicks`, `outbound_clicks`, `video_*`, `quality_ranking`/`engagement_rate_ranking`/`conversion_rate_ranking`.
4. Meta-specific health rules: frequency > N with CPM rising and CTR falling (fatigue), learning-limited ad sets, ad sets with < 50 conversions/week, disapproved ads, spend cap near, account `disable_reason`, pixel/CAPI event match quality.
5. Pacing and spend-cap reads (`spend_cap`, `amount_spent`, lifetime budget burn vs schedule) in the platform, not only in the engine's fixture path.
6. Bid controls as typed, policy-checked tools (`bid_strategy`, `bid_amount`, `roas_average_floor`) with delta caps like budgets.
7. Currency-exponent-aware budget math and `BudgetDelta.currency` everywhere (A1-02).
8. Ownership checks on every object-addressed write (A1-01) and `validate_only` on generic create/update (A1-05).
9. Token lifecycle UX for 60-day user tokens or a system-user path in the cloud (A1-08).
10. One Meta data path: the engine should read the platform's provider (or the platform should expose the engine's normalized rows) so the AI's analysis and the dashboard's numbers agree; today they are two independent integrations with different conversion definitions and units.
11. Arabic-market specifics: SAR is 2-decimal (safe), but KWD/BHD/OMR are 3-decimal and Meta does not support them as ad-account currencies — document supported Gulf currencies; RTL/Arabic creative text inspection is absent.
