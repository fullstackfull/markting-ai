## Findings

### B8-01 — Partial per-row impressions/clicks silently undercount totals and distort ratios
- **Severity:** P2
- **Classification:** VERIFIED_RUNTIME
- **Evidence:** `engine/src/paid_media_agent/tools/normalize.py:129-144` (only `conversions`/`conversion_value` absence sets `MISSING_METRIC`; impressions/clicks absence sets nothing); `compute.py:49-68` (`_sum_optional_int`/`_sum_optional_decimal` skip `None` but return a total when *any* value was seen); `compute.py:76-95` (ratios derived from those partial sums). Runtime probe (exit 0): two days, day-2 impressions missing → `missing=()`, both rows `quality_flags=[]`, `aggregate.impressions=1000` (should be 2000), `ctr=0.20` vs true `0.10`.
- **Description:** When a metric is present on some rows and absent on others, the sum is taken over present rows only, with no flag. CTR/CPM/CVR are then computed from a denominator that silently omits the gapped rows while the numerator may not, inflating or deflating the ratio.
- **Impact:** Thin or gapped provider coverage looks like a complete window. The model/report presents double-counted CTR/under-counted CPM as fact; an AI budget recommendation can be built on a silently wrong rate.
- **Recommendation:** Treat a metric present on a strict subset of in-window rows as `MISSING_METRIC`/`PARTIAL_SOURCE` for that entity; or require per-metric day-coverage == window day-count before emitting a ratio. Extend the flag to impressions/clicks, not only conversions.

### B8-02 — Live Pipeboard reads never report completeness, so every live row is marked complete
- **Severity:** P2
- **Classification:** VERIFIED_CODE
- **Evidence:** `engine/src/paid_media_agent/tools/pipeboard.py:186-193` — live `call_read` returns `ProviderResult(payload=payload)` with `data_complete_through`, `currency`, `timezone` all left at their `None` defaults (`providers.py:19-21`). `reads.py:235-238` sets `complete_through=None` when the provider gives none; `normalize.py:141` only flags `INCOMPLETE_WINDOW` when `data_complete_through is not None and day > data_complete_through`, and `normalize.py:156` sets `is_complete = data_complete_through is None or day <= data_complete_through` → **True for every live row**. Fixtures, by contrast, always set these (`fixtures.py:364-366`).
- **Description:** The only residual guards for live data are the requested-vs-actual window span check (`reads.py:263-264`) and the day-count check in compute (`compute.py:128,204`). Both catch *missing/extra days*, but a provider that returns rows for all requested days whose most recent day is still accumulating (standard for "today/yesterday") passes all of them: full day count, `is_complete=True`, no flag.
- **Impact:** Trailing still-maturing days are treated as final for 8 of 10 platforms (all Pipeboard-routed). Period-over-period deltas and the cross-platform total include unsettled spend/conversions presented as complete.
- **Recommendation:** Derive `data_complete_through` on the host for live reads (e.g. `today - provider_lag` per platform, or parse it from the MCP payload) and pass it into `normalize_rows`; never default completeness to "complete" when the provider is silent.

### B8-03 — "reconciled" is tautological for live data; the only real reconciliation runs for fixtures
- **Severity:** P2
- **Classification:** VERIFIED_CODE
- **Evidence:** `compute.py:217-224` — `entity_rows_sum_to_platform_spend` compares `sum(entity.current.spend)` to `aggregate(current_rows).spend`; both are derived from the same `current_rows`, so it passes by construction (modulo rounding). The non-trivial checks `rows_reconcile_to_provider_spend` / `row_count_matches_provider` run only `if provider_totals is not None` and only use `provider_totals["spend"]`/`["row_count"]` (`compute.py:225-248`). `reads.py:266` sets `provider_totals = result.payload.get("totals") or {}`; fixtures populate `totals` (`fixtures.py:386-391`), but the live Pipeboard payload has no guaranteed `totals` key and the host never synthesizes one. `PeriodComparison.reconciled` is `all(check.passed ...)` (`domain/analysis.py:124`).
- **Description:** For live reads the provider-spend/row-count checks never fire, so `reconciled` collapses to the always-true entity-sum check. The green "reconciled" signal therefore means "internally self-consistent," not "agrees with what the ad platform reports."
- **Impact:** Operators and the model read `reconciled=yes` as proof the numbers match the platform's own billing/UI; for live accounts that assurance is empty. A provider that returns a truncated or partial row set still reconciles.
- **Recommendation:** Require a provider-reported control total for live reads and fail/flag when it is absent; do not count the tautological entity-sum check as reconciliation evidence.

### B8-04 — render_report stamps `reconciled: true` unconditionally
- **Severity:** P2
- **Classification:** VERIFIED_CODE
- **Evidence:** `engine/src/paid_media_agent/tools/reports.py:50-52,67` — `reconcile_report(payload, comparison)` is the only gate, and `report_summary(..., reconciled=True)` is hardcoded. `reports/render.py:204-236` shows `reconcile_report` only checks that rendered numbers/missing-fields/scorecard/unavailable-sources reproduce the analysis artifact — it never inspects `comparison.reconciled` or `p.reconciliation`. The honest per-platform "reconciliation failed for …" line is added to `data_quality` (`render.py:160-164`), so the summary can simultaneously say `reconciled: true` and list a failure.
- **Description:** An analysis whose provider-spend reconciliation failed renders successfully and returns a summary headline `reconciled: true`.
- **Impact:** The headline boolean the model cites contradicts the report body; downstream surfaces that key on `reconciled` (not on the free-text `data_quality`) show a false pass.
- **Recommendation:** Pass `reconciled=comparison.reconciled` into `report_summary`, or refuse to render when `comparison.reconciled is False`.

### B8-05 — Cloud read boundary discards the currency-safe summary and drops provider warnings
- **Severity:** P2
- **Classification:** VERIFIED_CODE
- **Evidence:** `platform/packages/core/src/tools/builtin.ts:138` returns `{ rows, summary, truncated, errors, warnings }`; `summarizeReport` (`report-summary.ts:7-41`) is the component that groups by currency, refuses to sum across currencies, computes spend-weighted ROAS, and sets `complete`. `platform/apps/cloud/lib/cloud/reads.ts:53-58` casts the result as `{ rows; truncated; errors }` only — it never reads `summary` or `warnings`, and `warnings()` (`reads.ts:27-29`) is built solely from `errors`. The builtin currency-safety warning "Account currency lookup failed; unlabelled monetary values must remain separated by account" (`builtin.ts:118-124`) is therefore dropped before the UI.
- **Description:** The cloud dashboard (`app/api/dashboard/summary/route.ts:11-15`, `app/dashboard/reports/page.tsx:12`) receives raw rows + `truncated` only. The vetted currency-grouped/`complete` summary is unused, and rows whose currency could not be resolved arrive with no caution.
- **Impact:** Any client-side aggregation of the summary endpoint can cross-currency sum or miss the completeness caveat; the one safeguard the core computed for exactly this case is silently dropped. (The campaign table at `reports/page.tsx` renders per-row and is not itself summing, so the live blast radius is the summary endpoint's consumers.)
- **Recommendation:** Propagate `summary` (with `complete` and currency groups) and `warnings` through `reads.ts` and surface both; never expose raw rows for aggregation without the currency grouping.

### B8-06 — MISSING_METRIC coverage is asymmetric (conversions only)
- **Severity:** P3
- **Classification:** VERIFIED_CODE
- **Evidence:** `normalize.py:143-144` flags `MISSING_METRIC` only when `conversion_value is None or conversions is None`; impressions/clicks are never cause for the flag. Suppression of the cross-platform total keys on `MISSING_METRIC` (`compute.py:323-324`), so a platform missing impressions/clicks does not suppress the total.
- **Description:** The data model documents "missing metrics stay None, never zero" (`metrics.py:1`), but only two of four additive metrics participate in the missing-metric guard.
- **Impact:** Spend/impression/click-only gaps pass suppression and flagging; combined with B8-01 the ratios are wrong and unflagged.
- **Recommendation:** Flag any additive metric that is `None` where the platform's query requested it, and feed that into suppression.

### B8-07 — Sandbox synthetic metrics look complete and are enabled by a deploy-wide flag into the real pipeline
- **Severity:** P2
- **Classification:** VERIFIED_CODE
- **Evidence:** `platform/apps/cloud/lib/markting/sandbox-provider.ts:99-143` generates deterministic synthetic spend/clicks/conversions/ROAS with **no quality flags and no synthetic marker on report rows** (rows carry only `provider:'sandbox'` and names prefixed "Demo ·"; the `data_source:'sandbox'`/`real_ad_spend:false` markers exist only on the list tool and write result, `:181,194`). `env.ts:14,29` — `MARKTING_DEMO_MODE` is a single process-level env flag. `runtime.ts:18-26` — when set, `createBridgeRuntime` swaps the provider for the sandbox for **every** principal while keeping the SAME `PolicyEngine`, Postgres pending/audit, and findings stores; it feeds `assistant.ts` and the approvals `apply/route.ts`.
- **Description:** Demo data is intentionally routed through the production approvals/audit path. The guard against it reaching real users is a global boolean, not a per-tenant or per-environment check, and report rows themselves carry no field a downstream consumer can key on to tell synthetic from real.
- **Impact:** If `MARKTING_DEMO_MODE=true` ships to production (or a staging DB is shared), all tenants see synthetic, fully-"complete" performance data driving the assistant's analysis, with audit/approval records indistinguishable from real ones except by provider id. This is demo code reaching a production path.
- **Recommendation:** Gate demo mode per-organization (not a global env flag), stamp every sandbox report row with an explicit `synthetic:true`/`data_source` field, and assert at the write/apply boundary that synthetic providers cannot run under a non-demo organization.

### B8-08 — Live currency/timezone taken from local alias config, with no mismatch detection
- **Severity:** P3
- **Classification:** INFERRED
- **Evidence:** `reads.py:247-248` uses `result.currency or binding.currency` and `result.timezone or binding.timezone`; live `ProviderResult` leaves both `None` (`pipeboard.py:193`), so live rows are always labeled from the alias binding. `CURRENCY_MISMATCH`/`TIMEZONE_MISMATCH` flags are defined (`common.py:60-61`) but produced nowhere (see B8-09). Mixed currency/timezone *within one platform read* raises a hard `ComputeError` (`compute.py:150-154`), but a uniformly mislabeled binding passes silently.
- **Description:** If an alias is configured with the wrong currency/timezone, every row is stamped with it and nothing reconciles the label against the provider.
- **Impact:** Silent mislabeling of money; cross-platform suppression keys on currency equality (`compute.py:316-318`), so a wrong-but-consistent label can even enable an invalid cross-currency total.
- **Recommendation:** Capture the provider's own currency/timezone from the live payload and flag `CURRENCY_MISMATCH`/`TIMEZONE_MISMATCH` when it disagrees with the binding.

### B8-09 — Half the DataQualityFlag taxonomy is declared but never produced (GAP)
- **Severity:** GAP
- **Classification:** VERIFIED_CODE
- **Evidence:** `rg "DataQualityFlag.<F>" engine/src` finds **zero** producers for `SOURCE_UNAVAILABLE`, `CURRENCY_MISMATCH`, `TIMEZONE_MISMATCH`, `ATTRIBUTION_DIFFERS`, `STALE_CATALOG` (`common.py:59-65`). Only `INCOMPLETE_WINDOW`, `MISSING_METRIC`, `PARTIAL_SOURCE`, `DUPLICATE_ROWS`, `SUPPRESSED_TOTAL` are ever set (`compute.py:127,129,131,185`, `compare_periods.py:112`).
- **Description:** The taxonomy advertises guards (source unavailability as a row flag, currency/timezone mismatch, differing attribution windows, stale catalog) that no code path emits. `ATTRIBUTION_DIFFERS` in particular is the hook for the cross-platform attribution caveat and is unused.
- **Impact:** Readers of the enum (and of docs that cite it) overestimate the implemented data-quality coverage.
- **Recommendation:** Either implement producers for each declared flag or remove the unused ones so the taxonomy reflects reality.

## T0–T5 data trust levels (from the brief) mapped to current code

The audit brief frames trust as a ladder from synthetic data up to store-verified business truth (the e-commerce profit tiers). Reconstructed as a 6-level data-trust model and mapped to code:

| Tier | Meaning | Where code sits | Verdict |
|---|---|---|---|
| **T0 — Synthetic / demo** | Data fabricated for demos; must never drive real decisions | `sandbox-provider.ts:99-143` — deterministic metrics, no flags, no per-row synthetic marker; enabled deploy-wide by `MARKTING_DEMO_MODE` into the real PolicyEngine/audit (`runtime.ts:18-26`) | Present but **leaky** (B8-07). |
| **T1 — Raw provider, completeness unknown** | Live read, not yet validated | Live Pipeboard (`pipeboard.py:193`): no `data_complete_through`, no `totals`, no currency/tz | This is where **all live data actually sits**, yet it is presented with T2/T3 confidence. |
| **T2 — Normalized + flagged** | Rows typed, gaps flagged | `normalize.py` emits `INCOMPLETE_WINDOW`/`MISSING_METRIC` | Only fully exercised when the provider reports completeness — i.e. fixtures. Live silently skips most flags (B8-01, B8-02, B8-06). |
| **T3 — Reconciled to provider totals** | Rows agree with the platform's own control totals | `compute.py:225-248` | **Fixture-only**; live `reconciled` is tautological (B8-03), and the report labels it `true` regardless (B8-04). |
| **T4 — Cross-platform compatible total** | A single total that is currency/window-compatible and complete | `compute.py:309-331` | Logic is sound, but its "complete"/"missing" inputs are the under-firing T2 flags, so a T1 input can still produce a T4 total. |
| **T5 — Business-verified truth** | Store net revenue after returns, COGS/fees, true profit/ROAS | — | **MISSING**: ROAS is platform-attributed `conversion_value/spend` only (`compute.py:92`); no store/order/refund/COGS reconciliation, no `ATTRIBUTION_DIFFERS` producer. |

**The core failure mode:** the ladder is designed so trust is earned tier by tier, but live data enters at T1 and is *rendered as if it had climbed to T3/T4* because the gates that should hold it back (completeness, provider reconciliation) are fixture-only and the `reconciled` headline is hardcoded. Where bad/partial data silently looks complete: trailing unsettled days (B8-02), partial impressions/clicks (B8-01, B8-06), unreconciled live totals shown as reconciled (B8-03, B8-04), and synthetic data in prod (B8-07).

## Disagreements / claims in docs that the code contradicts

- `tools/reports.py:92` and the render-report tool description advertise a "reconciled report," and `render.py:174` prints "all sources complete and reconciled." For live data `reconciled` is tautological (B8-03) and the summary flag is hardcoded `true` (B8-04). The word "reconciled" overstates what the live code verifies.
- `domain/metrics.py:1` / `normalize.py:1`: "Missing metrics stay None; they are never zero." True for storage, but `aggregate` sums a metric over only the rows that have it (B8-01), so a *partially* missing metric is neither None nor correct — it is a silently reduced number with a derived ratio built on it.
- `domain/common.py:55-65` presents a 10-value quality taxonomy implying broad coverage; 5 of the 10 are never produced (B8-09).
- `sandbox-provider.ts:6-8` states the sandbox is "enabled only by `MARKTING_DEMO_MODE`" as if that bounds the risk; the flag is deploy-wide and the provider runs through the production PolicyEngine/audit path, so the bound is weaker than the comment implies (B8-07).
