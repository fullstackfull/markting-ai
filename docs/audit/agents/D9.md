## Findings

### D9-01 — Apply has no atomic consume and no idempotency: concurrent or retried Apply can execute the provider write twice
- **Severity:** P1 (financial risk; unsafe for non-idempotent write kinds)
- **Classification:** VERIFIED_CODE (race and crash window read in source; not reproduced against a provider because no live write path exists in this sandbox)
- **Evidence:** `platform/packages/core/src/policy/engine.ts:87-125` — `apply()` does `pending.get` (no lock, `repository.ts:385-411` plain `select ... limit 1`), then `provider.applyWrite` (`:113`), then `audit.append('applied')` (`:114-122`), then `pending.delete` (`:123`). `PostgresPendingStore.delete` is an unconditional soft-consume `update ... set consumed_at = now()` (`platform/apps/cloud/lib/cloud/repository.ts:413-418`) with no `returning`/`where consumed_at is null` guard. The route does `listPendingOperations(...).find(id)` and then `applyPending` with no transaction (`app/api/approvals/[id]/apply/route.ts:20-27`); `markPendingOutcome` runs afterwards, outside any transaction (`:27`). The only guard against double submission is a client-side `busy` flag (`app/dashboard/approvals/approval-actions.tsx:15,34`).
- **Description:** Two admins (or one admin in two tabs, or a retry after a gateway timeout) applying the same pending id both pass `get`, both call `applyWrite`, and both then consume the row. A crash or process kill between `:113` and `:123` leaves the row unconsumed and the write unrecorded; the next Apply re-executes it. For `update_campaign_budget`/`set_status` the second write is idempotent in effect, but for create/duplicate kinds (`WriteKind`) it is not, and in all cases the audit trail shows two `applied` events (or none) for one human decision.
- **Impact:** Duplicate ad-platform mutations and an audit log that does not match what happened — exactly the class of failure an outbox/idempotent-consumer design prevents.
- **Recommendation:** Make consumption the first durable step: `update pending_operations set consumed_at = now(), consumer = ... where id = $1 and consumed_at is null returning *` inside a transaction that also inserts an `approval.apply_requested` outbox row; let a worker (or the same request, after the claim) perform the provider write with the pending id as provider idempotency key where the provider supports one, then record `approval.applied` or `approval.apply_failed` (which re-opens the row explicitly rather than implicitly). This is upstream adport code, so the change belongs in `PolicyEngine`/`PendingOperationStore` as a `claim()` primitive.

### D9-02 — Chat turns are end-to-end synchronous with no cancellation or idempotency; a client timeout orphans engine work and invites duplicate turns
- **Severity:** P2
- **Classification:** VERIFIED_CODE (timeouts, lack of idempotency key); INFERRED (orphaned work after abort — the engine continues because nothing propagates the abort)
- **Evidence:** Browser `fetch('/api/assistant/messages')` with no timeout (`app/dashboard/assistant/assistant-chat.tsx:37`) → Next route `maxDuration = 300` (`app/api/assistant/messages/route.ts:7`) → `runAssistantTurn` awaits `client.sendMessage` (`lib/markting/assistant.ts:43`) → `EngineClient` aborts at `MARKTING_ENGINE_TIMEOUT_MS` default 240 000 ms (`lib/markting/engine-client.ts:73,81-82`) and reports `unreachable` 503 (`:97`). The engine endpoint has no idempotency key (`MessageIn` is only `text`, `engine/src/paid_media_agent/surfaces/api/app.py:15-16,91-99`), runs `graph.ainvoke` to completion (`surfaces/runner.py:150-154,197-202`) and has no server-side deadline (`docs/ARCHITECTURE.md:510-514` agrees: "no fixed upper bound on a request's duration"). The engine's only dedupe primitive is used by the Slack adapter alone (`surfaces/slack/service.py:79,142`; `persistence/interfaces.py:39-42`). `docs/TODO.md:31` acknowledges "the engine API is synchronous today".
- **Description:** A live-model turn that exceeds 240 s returns 503 to the user while the engine keeps running and may create a proposal nobody bridges (see D9-03 for what then happens). The natural user reaction, re-sending the message, appends a second human message to the same thread, producing a second investigation and potentially a second proposal. On Vercel the 300 s route budget is a plan feature, not a guarantee (INFERRED, deployment-dependent); in compose there is no limit but the browser tab is held open for minutes.
- **Impact:** Lost or duplicated proposals, wasted model spend, unbounded request lifetimes on both services, and no way to show progress or resume.
- **Recommendation:** Turn a chat turn into a job: `POST /api/assistant/messages` inserts `assistant_turns(id, org, user, thread_id, text, idempotency_key, status='queued')` and returns 202 with the turn id; a worker calls the engine (passing the turn id as an `Idempotency-Key`/dedupe key the host can honour via `DedupeStore`), writes `turn.completed`/`turn.failed`, and the UI polls or subscribes (SSE/Supabase Realtime on the row). The engine host already streams events internally (`runner.py:155-195` `astream`), so a streaming surface is feasible without editing `engine/`.

### D9-03 — Stale `awaiting_approval` proposals are re-bridged on later unrelated turns; unsupported proposals are never handed back to the engine
- **Severity:** P2
- **Classification:** VERIFIED_RUNTIME (engine returns the stale proposal on the next turn), VERIFIED_CODE (bridge conditions)
- **Evidence:** `lib/markting/assistant.ts:50-51` bridges whenever `proposal.state === 'awaiting_approval'` without checking `outcome.interrupted` or whether the proposal belongs to this turn. The engine returns the newest proposal on the thread regardless of turn (`surfaces/runner.py:91-93,134`). Probe: turn 1 (change request) → `interrupted=true, state=awaiting_approval, id=b3f6cff2`; turn 2 on the same thread ("What needs attention?") → `interrupted=false`, `proposal` = the same `b3f6cff2` still `awaiting_approval`. In `bridgeProposal` the `unsupported` branch records and returns without `handoff` (`lib/markting/bridge.ts:61-66`), so the engine proposal stays `awaiting_approval` forever; for supported proposals a failed `rejectOnEngine` is swallowed (`bridge.ts:98-105`), leaving the same state. Provenance upsert keys on `(organization_id, proposal_id, revision)` and overwrites `pending_operation_id` (`lib/markting/repository.ts:84-86`).
- **Description:** Whenever the hand-off does not happen (unsupported translation — the normal path for any proposal the allowlist does not cover — or a hand-off/HTTP failure, or the D9-02 timeout), every subsequent message in that thread re-translates the stale proposal. For an unsupported proposal the user sees the "unsupported" bridge card on every turn. For a supported one, the next turn runs `PolicyEngine.validate` again: a second `pending_operations` row and a second `validated` audit event for the same engine proposal, and the provenance row now points at the newer pending id, orphaning the first from the Approvals "Source" column.
- **Impact:** Duplicate approval items for one request, confusing UI, and audit rows that cannot be traced back to a decision. This is the dual-write problem between two databases (engine Postgres and Supabase) with no saga state.
- **Recommendation:** Bridge only proposals created in this turn (compare `proposal_id`/`created_at` against a per-turn marker, or require `interrupted === true`), always hand off (reject) unsupported proposals too, and persist the hand-off as a step with its own status (`handoff_pending` → `handed_off`/`handoff_failed`) retried by a worker. Never swallow `rejectOnEngine` failures silently; emit `engine.handoff_failed`.

### D9-04 — Report runs are synchronous, globally serialized by one in-process lock, block the engine event loop, and are not tenant-scoped
- **Severity:** P1 (cross-organization visibility of report runs; availability of the shared engine)
- **Classification:** VERIFIED_RUNTIME (serialization and event-loop stall), VERIFIED_CODE (global index, no tenant key)
- **Evidence:** `services/engine-demo/serve_demo.py:324` creates one `asyncio.Lock()`; `:344` wraps the whole run in `async with lock`. The run is CPU-bound synchronous code called from the async handler: `run_compare_periods` (`engine/src/paid_media_agent/reports/cadence.py:118`) and `run_render_report` → Jinja + WeasyPrint `write_pdf` (`cadence.py:134`; `reports/render.py:417-432, 268-271`). Probe: three concurrent runs completed strictly serially (0 overlapping intervals, 4.16 s total); during a single 1.42 s weekly run a concurrent task's 50 ms sleep overshot by 1.363 s, i.e. the loop was blocked for essentially the whole run. The index is one JSON file per workspace with a read-modify-write (`serve_demo.py:252-264, 304-306`) and `GET /reports` returns the whole index (`:355-358`); the cloud route authenticates the caller's organization and then returns that global list unchanged (`app/api/reports/engine/route.ts:16-24`). Failures are only logged (`serve_demo.py:349-353`); no failed-run record exists. The UI awaits the POST with a `busy` flag and no timeout (`app/dashboard/reports/engine-reports.tsx:33-40`). Compose healthcheck: 10 s interval / 5 s timeout (`docker-compose.yml:56-60`).
- **Description:** One engine process serves every organization. While any org's report renders, no chat turn, health check or other report makes progress (the stall scales with real data volume and PDF size — INFERRED beyond fixture size). The lock is per process, so running more than one uvicorn worker or replica would race on the index file. Every org sees every other org's runs (`requested_by`, windows, file names) and can download their files through `/api/reports/engine/[name]` — the data is the engine's single global account set rather than another org's credentials, but the model has no tenant dimension at all.
- **Impact:** Head-of-line blocking across tenants; health-check flaps under load; cross-organization report visibility; no record of failed runs.
- **Recommendation:** Treat a report run as a job row owned by an organization (`report_runs(id, org, cadence, end, status, requested_by, error, artifacts)`), enqueue from the cloud, let a worker call the engine and move CPU work off the loop (`asyncio.to_thread` / a process pool in the host, which is markting code and can change), and scope `GET /reports` by organization. Until then, at minimum add `asyncio.to_thread` around compute/render and return 202 + poll.

### D9-05 — Monthly report always fails on the demo fixture; the Reports page exposes the button anyway
- **Severity:** P2 (functional)
- **Classification:** VERIFIED_RUNTIME
- **Evidence:** `POST /reports/run {"cadence":"monthly"}` → `500 report failed: ComputeError: ... the previous window starts 2026-07-04 but the read begins 2026-08-01; re-read the union of both windows` with the pinned anchor 2026-08-28 and `... starts 2026-08-06 but the read begins 2026-09-03` with the default anchor (2026-09-30). The host test covers weekly only (`services/engine-demo/tests/test_demo_api.py:160`). The UI offers "Run monthly" (`engine-reports.tsx:54`).
- **Description:** The fixture read returns 28 days of rows while the monthly comparison needs 56; the host passes `cadence` straight through (`serve_demo.py:272-280`). In demo mode the monthly button can never succeed.
- **Impact:** A visible dashboard action fails 100% of the time in the shipped demo; because failures are not persisted (D9-04), nothing but a transient error toast records it.
- **Recommendation:** Either hide/disable monthly in demo mode or widen the fixture read window; add a monthly case to the host tests. Record failed runs as `report.run.failed` events.

### D9-06 — Stripe webhook processing is inline, its idempotency check is non-atomic, and there is no ordering guard
- **Severity:** P2
- **Classification:** VERIFIED_CODE (race, no `created` check); INFERRED (out-of-order delivery consequence — Stripe does not guarantee order; this is a property of the provider, not verified here)
- **Evidence:** `app/api/billing/webhook/route.ts:9-11` verifies the signature and awaits `processStripeEvent` in the request. `lib/cloud/billing.ts:120-123` does `select ... from private.billing_events` and returns `duplicate`; the insert that would make a replay a duplicate happens only after `applySubscription` and outside its transaction (`:132-136`, `on conflict do nothing`). `applySubscription` never reads `event.created` or compares with the stored `current_period_end` (`:57-117`). Any processing error returns 400 with the same body as a bad signature (`route.ts:12-15`). The only test exercises a single `customer.subscription.deleted` event through `processStripeEvent` and is gated behind `ADPORT_RUN_DATABASE_TESTS` (`test/database.integration.test.ts:217-247`); there is no route-level test. `docs/billing.md:27` describes "duplicate protection via `private.billing_events`" (true for sequential replays, not concurrent ones). `billing.ts` is unmodified upstream code (`git log`).
- **Description:** Two concurrent deliveries of one event (Stripe retries on slow 2xx) both see no row, both run `applySubscription`, and both insert a `subscription_updated` audit event. A late-arriving older `customer.subscription.updated` overwrites a newer state (plan/cancel flag/period end). A transient DB failure is reported to Stripe as 400 "Invalid Stripe webhook", indistinguishable in Stripe's dashboard from signature tampering, although Stripe will still retry.
- **Impact:** Plan state can regress or flap; billing audit rows duplicate; operational signal is muddied.
- **Recommendation:** Insert the event id first (`insert ... on conflict do nothing returning event_id`; no row → duplicate) inside the same transaction as the state change, store `event.created` and skip events older than the last applied one per subscription, return 2xx quickly and do the work from an outbox/worker, and return 5xx (not 400) for processing failures so retries are visibly distinct from rejected signatures.

### D9-07 — Refresh-token rotation is performed inline during reads; a persistence failure loses a rotated token
- **Severity:** P2
- **Classification:** VERIFIED_CODE; VERIFIED_TEST for the compare-and-set logic itself (`credential-rotation.test.ts`, 4 passing)
- **Evidence:** `lib/cloud/runtime.ts:62-67` wires `persistTokens` into each provider client per request. Snapchat sets `this.refreshToken = token.refresh_token` and then `await onRefreshToken` (`platform/packages/snapchat/src/client.ts:145-148`); Pinterest and Spotify identical (`pinterest/src/client.ts:85-88`, `spotify/src/client.ts:89-92`); LinkedIn awaits `onTokens` before assigning (`linkedin/src/client.ts:104-105`). `rotateProviderTokens` runs `select ... for update`, decrypt, compare, encrypt, update in one transaction (`lib/cloud/credential-rotation.ts:23-42`) and throws on mismatch or missing row (`:30,34`). The runtime (and thus the client instance) is created per request (`createTenantRuntime(principal)` from `lib/markting/runtime.ts:19`), so an in-memory token does not survive the request.
- **Description:** For providers that rotate the refresh token on every refresh, the provider has already invalidated the old token when the callback runs. If the DB write fails for any reason other than "grant changed" (connection pool exhaustion, lock timeout, deploy), the request fails and the new refresh token exists only in a request-scoped object that is discarded. The connection is then dead until the user re-authorizes. The two legitimate rejection reasons (`:30,34`) are fine; the problem is coupling a durability-critical write to the read request's success path with no retry.
- **Impact:** Silent loss of provider connections under transient DB trouble; the user-facing symptom is an unrelated read failing followed by "reauthorize".
- **Recommendation:** Persist first with retry (bounded, same CAS), and emit `credential.rotated` / `credential.rotation_failed` events so operators see it; consider a dedicated rotation job for near-expiry tokens instead of rotating only on demand inside reads.

### D9-08 — Retention is pg_cron only, unbatched, unobserved, and misses the markting and engine tables; the MCP OAuth purge is never scheduled
- **Severity:** P3
- **Classification:** VERIFIED_CODE
- **Evidence:** `select cron.schedule('adport-data-retention', '17 3 * * *', 'select private.apply_data_retention()')` (`20260817171039_cloud_initial_schema.sql:408`); the function issues unbounded `delete ... using organization_settings` statements in one transaction (`20260828120000_cloud_plans_and_account_scope.sql:131-163`). `adport-account-selection-expiry` every 10 minutes (`20260831152537_provider_account_selection.sql:22-23`). `private.purge_expired_mcp_oauth_records()` is defined and granted but no `cron.schedule` or application call exists (`20260825120000_mcp_oauth.sql:71-94`; repo-wide grep returns only the definition) — `docs/ARCHITECTURE.md:396-397` says the same and the code confirms it. `markting_threads`, `markting_engine_proposals`, `markting_sandbox_state` have no retention rule (`20261002000000_markting_bridge.sql`); `markting_engine_proposals.pending_operation_id` is `on delete set null` (`:50`), so retention of `pending_operations` strips provenance rather than ageing it together. Engine `pma_*` tables and LangGraph checkpoints have no retention (`engine/src/paid_media_agent/persistence/postgres.py:12-43`); the report index is capped at 50 entries (`serve_demo.py:306`) but report files on disk are never pruned. `enforceRateLimit` also performs a 1 %-probability inline cleanup in the hot path (`lib/cloud/repository.ts:365-367`), duplicating the cron's job.
- **Description:** Retention works for the upstream tables on a Supabase image, but there is no run log, no batching (a large tenant's delete can hold locks for a long time at 03:17), no coverage of the glue and engine stores, and the MCP OAuth tables grow unbounded.
- **Impact:** Unbounded growth of chat/provenance/checkpoint data; a daily lock-heavy maintenance window; no evidence that retention ran.
- **Recommendation:** Schedule `purge_expired_mcp_oauth_records`, extend retention to `markting_*` (threads by `last_message_at`, proposals by `updated_at`), delete in bounded batches (`limit` loop) and record each run in a `maintenance_runs` table or emit `retention.applied` events; give the engine host its own bounded cleanup of `pma_*`, checkpoints and `workspace/out`.

### D9-09 — Audit writes are inline and partly non-transactional; the audit log doubles as the only event stream but cannot carry new event types without a migration
- **Severity:** P3
- **Classification:** VERIFIED_CODE
- **Evidence:** `recordAudit` is a single insert outside any transaction (`lib/cloud/repository.ts:268-290`); `PolicyEngine` appends after the provider call (`engine.ts:114-122`) and separately from the pending consume (`:123`); some admin paths insert inside `db().begin` (`repository.ts:299-315, 338-352, 672-681`; `billing.ts:78-116`). The `event` column is a CHECK enum of 15 values (`20260828120000:165-171`); engine provenance is encoded as `event='note', tool='engine_proposal'` (`bridge.ts:81, 89-93`). The bridge performs three writes across two systems with no transaction (`bridge.ts:88-94`: pending row via registry, provenance row, note, then engine hand-off). `deletion_requests` is never written by application code (grep: only migrations) while `POST /api/deletion` performs an inline Google revoke with no timeout (`lib/cloud/google-oauth.ts:62-70`) before the cascade delete (`app/api/deletion/route.ts:16-25`), so a slow or failing revoke blocks deletion entirely.
- **Description:** There is no append-only domain event table and no outbox; `audit_events` is simultaneously the human-facing log and the only machine-readable history, but new facts (proposal created, hand-off failed, token rotated, report failed, pending expired) either need a migration or get squeezed into `note`.
- **Impact:** Partial writes under failure (pending row without provenance, provider write without audit), and an event vocabulary that cannot evolve with the product.
- **Recommendation:** Introduce `domain_events(id, org, aggregate_type, aggregate_id, type, payload, created_at, published_at)` written in the same transaction as the state change, and derive `audit_events` rows from it (projection) rather than the other way round.

### D9-10 — Same-thread concurrent chat turns are not serialized anywhere
- **Severity:** P3 (demo); risk rises with a live model and Postgres checkpointer (NOT_VERIFIED for live)
- **Classification:** VERIFIED_RUNTIME (demo), VERIFIED_CODE (no lock)
- **Evidence:** No per-thread lock in `app.py:91-99` or `runner.py:197-202`; `claimThread` is an upsert, not a lease (`lib/markting/repository.ts:17-27`); the per-user rate limit (120/min, `messages/route.ts:13`, `repository.ts:355`) does not prevent concurrency. Probe: two concurrent change requests on `t-race` → one response `interrupted=true` with a proposal, the other `interrupted=false, proposal=None`; one proposal stored.
- **Description:** Two in-flight turns on one thread produce divergent outcomes with no error; with `AsyncPostgresSaver` and a real model the interleaving of checkpoints is undefined.
- **Recommendation:** Serialize per thread (advisory lock on the thread row in the cloud, or a per-thread `asyncio.Lock` map in the host) and reject or queue the second turn with 409/202.

## What a world-class system would need (design, not implemented)

### 1. Event model (append-only, written in the same transaction as state)

`public.domain_events (id bigint identity, organization_id uuid, aggregate_type text, aggregate_id text, type text, version int, payload jsonb, actor jsonb, created_at timestamptz, published_at timestamptz null)` plus a partial index on `published_at is null`. Event types (dotted, versioned in `payload.schema`):

- `assistant.turn.requested|started|completed|failed` (aggregate: thread)
- `proposal.received` (engine proposal first seen by the cloud), `proposal.translated|unsupported`
- `preview.created` (pending op issued; carries `pending_operation_id`, `op_hash`, `expires_at`), `preview.expired`, `preview.rejected`
- `engine.handoff.succeeded|failed`
- `approval.apply_requested` (atomic claim), `approval.applied`, `approval.apply_failed`
- `outcome.readback_requested`, `outcome.measured` (post-apply readback of the changed entity plus a KPI snapshot window; today nothing measures anything)
- `report.run.requested|started|completed|failed` (aggregate: report run, tenant-keyed)
- `billing.webhook.received` (event id, `created`), `subscription.changed`
- `credential.rotated|rotation_failed`
- `retention.applied` (per table counts)

`audit_events` becomes a projection of a subset of these (one consumer), keeping the current dashboard untouched.

### 2. Queue options compared

| Option | Fit | Why |
| --- | --- | --- |
| **Postgres outbox + `SKIP LOCKED` worker** (recommended first step) | Best | Supabase is already the system of record; the cloud's `postgres` client supports transactions (`db().begin`) so state + event are atomic; a worker (new compose service or a Next.js route invoked by cron) polls `domain_events where published_at is null for update skip locked limit N`; retries with backoff and a dead-letter column. Works identically in compose and on Supabase hosted. No new infrastructure. |
| **pg_cron as the tick** | Good complement | Already a hard dependency (`initial:373`). Use it to (a) call a Supabase Edge Function / `pg_net` HTTP hook that wakes the worker every minute, (b) run `preview.expired` emission (`update pending_operations ... returning` → insert events), (c) run batched retention and the MCP purge, (d) emit `report.run.requested` on the weekly/monthly cadence per organization. Limitation: SQL only; cannot call the engine directly without `pg_net`. |
| **Supabase Realtime / LISTEN-NOTIFY** | For UI only | Push `assistant.turn.completed` and `report.run.completed` to the dashboard instead of long-held fetches. Not a delivery guarantee; always pair with the outbox. |
| **External broker (SQS/Redis/NATS)** | Later | Justified only when more than one worker type or cross-region fan-out appears. Adds an at-least-once hop that still needs the outbox for atomicity; premature for the current two-service footprint. |
| **Engine-side BackgroundTasks/threads** | Not sufficient alone | Would hide the event-loop stall (D9-04) but keeps state in the engine process; combine with `asyncio.to_thread` in the host for CPU work, driven by the cloud's job table. |

### 3. Flows re-shaped

- **Chat turn:** route inserts `assistant_turns` + `turn.requested` (202). Worker: claim → `POST /threads/{id}/messages` with a dedupe key the host honours via `DedupeStore` (markting host code, no `engine/` edit) → on `awaiting_approval` *created in this turn*: translate, `validate`, write provenance + `preview.created` in one transaction → `engine.handoff.*` as its own retried step → `turn.completed`. UI polls `/api/assistant/turns/{id}` or subscribes.
- **Apply:** `update pending_operations set consumed_at=now(), claimed_by=... where id=$1 and consumed_at is null returning *` + `approval.apply_requested` in one transaction; provider write with pending id as idempotency key where supported; `approval.applied` + `applied` audit + `markting_engine_proposals.status` in one transaction; failure → `approval.apply_failed` and an explicit operator decision, never an implicit re-open. Follow with `outcome.readback_requested` → worker reads the entity back and emits `outcome.measured`.
- **Reports:** `report_runs` row per organization; worker calls the engine host, which moves compute/render to a thread; `GET /reports` scoped by organization; `report.run.failed` persisted with the error class.
- **Webhooks:** insert `billing_events` first (atomic duplicate detection), store `created`, respond 2xx, process from the outbox with per-subscription ordering; 5xx on processing failure.
- **Rotation:** persist-with-retry before returning from the refresh; emit `credential.rotated`; near-expiry rotation job for LinkedIn-style fixed refresh lifetimes.
- **Retention:** batched, per-table, logged; covers `markting_*`, MCP OAuth, engine `pma_*`/checkpoints/`workspace/out`.
- **Observability:** every job row has `attempts`, `last_error`, `next_attempt_at`; a `/dashboard/jobs` or admin query shows dead letters.
