# C4 — AI memory architect

Audit of every place the system "remembers": LangGraph checkpoints, the engine's `pma_*` tables, thread ownership, proposals / approval claims / receipts, the Slack dedupe store, the shared artifact workspace, and the adport-side `markting_threads`, `markting_engine_proposals`, `pending_operations`, `audit_events` and `findings` tables. The goal was to determine what conversation, tenant, account and long-term memory actually exists, how it is bounded per organization, and what a per-organization "Marketing Memory" would have to look like.

Every claim below carries a classification tag: VERIFIED_CODE (read in source), VERIFIED_TEST (an existing test asserts it), VERIFIED_RUNTIME (I ran it), DOCUMENTED_ONLY (a document says it, code does not show it), INFERRED (reasoned, not observed), NOT_VERIFIED.

## Findings

### C4-01 — Engine report memory is one global index shared by every tenant
- Severity: **P1** (becomes P0 the moment the engine reads live accounts)
- Classification: VERIFIED_CODE
- Evidence: `services/engine-demo/serve_demo.py:62,246-264` (one `workspace/out/markting-reports.json` index, no caller/tenant key), `serve_demo.py:355-358` (`GET /reports` returns the whole index to any valid bearer), `serve_demo.py:360-374` (`GET /reports/files/{name}` serves any file by name to any bearer), `platform/apps/cloud/app/api/reports/engine/route.ts:16-24` (authenticates the session, then passes the full engine list through with no `organization_id` filter), `platform/apps/cloud/app/api/reports/engine/[name]/route.ts:10-26` (same for file download), `docker-compose.yml:49,54` (one token `adport-bridge` and one `engine-workspace` volume for all tenants). Mitigating fact: `serve_demo.py:139-170` forces `PAID_MEDIA_DATA_MODE=sample` and refuses live credentials, so today every report is built from the same fixture accounts (`engine/config/accounts.example.toml`).
- Description: report runs, their summaries, analysis artifact ids and rendered HTML/PDF are stored in a single file on a volume shared by all organizations and listed/downloaded without any organization scoping on either side. `requested_by` is always `adport-bridge`, so the index cannot even be filtered after the fact.
- Impact: no real tenant data leaks today because the engine only has fixture data. The design, however, has no tenant boundary at all; enabling live reads (the stated roadmap, `docs/TODO.md:5` "Live model mode", and any future per-org accounts) would expose one org's performance reports to every signed-in user of every other org.
- Recommendation: key the report index by organization (or by a per-org caller) and filter `GET /reports` by caller; put report files under a per-tenant prefix and check it on download; have the cloud routes pass and enforce `organization_id`. Treat this as a release gate before any live-read enablement.

### C4-02 — Organization deletion and data retention never reach the engine's memory
- Severity: **P1**
- Classification: VERIFIED_CODE
- Evidence: `platform/apps/cloud/app/api/deletion/route.ts:21` (deletes the `organizations` row; FK cascades delete `markting_threads`, `markting_engine_proposals`, `markting_sandbox_state` per `20261002000000_markting_bridge.sql:13,39,62`), `private.apply_data_retention` (`20260828120000_cloud_plans_and_account_scope.sql:131-160`) covers `audit_events`, `pending_operations`, `findings`, `deletion_requests`, OAuth/rate-limit/billing rows only; the bridge migration does not extend it; engine side: `persistence/postgres.py:11-42` tables carry no org column and `thread_id` embeds `org_<uuid>__u_<uuid>__…` (`platform/apps/cloud/lib/markting/repository.ts:12-14`); `rg "delete_thread|adelete_thread|prune|retention"` over `engine/src` and `services/engine-demo` finds nothing; LangGraph checkpoints are keyed only by `thread_id`/`checkpoint_ns` (`langgraph/checkpoint/postgres/aio.py:195-199`); `pma_dedupe` has no expiry (`postgres.py:35-38`).
- Description: the full conversation transcript (user prose, model output, tool results) lives in LangGraph `checkpoints`/`checkpoint_blobs`/`checkpoint_writes`, and every proposal (`reason`, `before/after`, `requester_ref`, `thread_id`) lives in `pma_proposals`, all in `engine-db`. Nothing deletes them when an organization deletes its data, nothing ages them out, and the thread id permanently ties them to the deleted organization's and user's UUIDs. The platform-side `markting_threads.title` also stores the first 80 characters of the user's first message (`assistant.ts:38`), which is covered by the cascade but not by `apply_data_retention`.
- Impact: a "delete my organization" request leaves the most sensitive memory (what a human said to the agent about their business) in place indefinitely; `data_retention_days` is silently not honoured for conversations; the engine database grows without bound (checkpoints are the heaviest table in any LangGraph deployment).
- Recommendation: add an engine purge endpoint (`DELETE /threads/{thread_id}` → `checkpointer.adelete_thread` + `pma_proposals`/`pma_receipts`/`pma_thread_owners` by thread, and a by-prefix purge for `org_<id>__`) called from the deletion route; add `markting_*` and engine-side retention to the retention job (or a scheduled engine-side sweep keyed on the org prefix); add TTL on `pma_dedupe`.

### C4-03 — Tenant isolation of conversation memory rests on one platform check; the engine sees a single identity
- Severity: **P2** (design debt acknowledged in docs; the one check is correct as written)
- Classification: VERIFIED_CODE (platform logic), NOT_VERIFIED by test in this environment (DB test did not run)
- Evidence: `docker-compose.yml:49` (`PAID_MEDIA_API_TOKENS=${MARKTING_ENGINE_TOKEN}:adport-bridge`), `platform/apps/cloud/lib/markting/env.ts:12` (one token), `lib/markting/assistant.ts:34-38` (regex, prefix check against `org_<org>__u_<user>__`, then `claimThread`), `lib/markting/repository.ts:17-27` (insert-or-update guarded by organization and user), `engine/src/paid_media_agent/surfaces/runner.py:86-89` and `persistence/postgres.py:39-42,226-244` (ownership is per `caller_ref`, which is always `adport-bridge`), `surfaces/api/app.py:103-114` (`GET /proposals/{id}` is visible to the requester, i.e. to the shared caller, for every org's proposal), `tools/write_tools.py:67` (`requester_ref` = that same caller), `docs/TODO.md:27` and `README.md:128` acknowledge it. The isolation test exists (`test/markting-repository.database.test.ts:39-44`) but is gated on `ADPORT_RUN_DATABASE_TESTS=1` and failed to connect here.
- Description: the engine cannot distinguish organizations: ownership, proposal visibility, rejection rights and artifact access all collapse onto `adport-bridge`. Every tenant boundary therefore lives in two lines of `assistant.ts`. The thread id is fully predictable from two UUIDs the user can see in the dashboard. Any other process holding `MARKTING_ENGINE_TOKEN` (ops scripts, a future WhatsApp channel, a misconfigured route) can post into or read from any org's thread.
- Impact: no defense in depth. One missed `startsWith` check in a future route (the engine-reports routes in C4-01 are exactly such routes) or one leaked token equals cross-tenant conversation access.
- Recommendation: carry the organization into the engine's identity — a per-organization token (`<token>:org_<uuid>`) or a signed `caller_ref` header — so `pma_thread_owners`, proposal visibility and artifact access are keyed by tenant on the engine side too; make the DB isolation test part of CI.

### C4-04 — The agent's filesystem and artifact store are one shared, writable workspace across all tenants' threads
- Severity: **P2** (becomes P0 with live reads)
- Classification: VERIFIED_CODE (permissions and store), INFERRED (model behaviour)
- Evidence: `engine/src/paid_media_agent/runtime/local.py:281-292` (`FilesystemBackend(root_dir=project_root, virtual_mode=True)`; `deepagents/backends/filesystem.py:132-166` documents that virtual mode only blocks traversal, not isolation), `local.py:257-259` (write allowed on `/workspace/**` for every thread; reads of `/workspace/analysis` and `/workspace/out` are not denied), `tools/artifacts.py:63-80` (artifact ids are global `art_<16 hex>` under one root, no thread or tenant component), `tools/compare_periods.py:57-58` (any artifact id can be loaded by any thread), `middleware/offload.py:33-41` (large tool results are written to that shared store), `docker-compose.yml:54` (one `engine-workspace` volume), `engine/workspace/analysis/art_*.json` (13 artifacts from earlier local runs present on disk).
- Description: every tool result, every `performance_rows` artifact and every report is written to a directory tree that every other thread can `ls`, `read_file`, `write_file` and `compare_periods` over. Nothing namespaces by thread or organization.
- Impact: (a) cross-tenant read of analysis data once accounts are real (today: fixture-only, same for all orgs); (b) a cross-thread persistence channel: a model turn in thread A can write a file that a later model turn in thread B reads, which is the classic vector for persisted prompt injection and is an unintended, ungoverned "memory".
- Recommendation: give each organization its own workspace root (`workspace/<org_id>/…`) and `ArtifactStore`, resolved from the request's tenant; deny model writes outside `/workspace/<org>/`; include the tenant in artifact ids or verify ownership on read.

### C4-05 — Engine-side outcome memory is systematically wrong: every bridged proposal is recorded as "rejected"
- Severity: **P2**
- Classification: VERIFIED_CODE
- Evidence: `platform/apps/cloud/lib/markting/bridge.ts:94,98-105` (after a successful preview the bridge calls `rejectOnEngine(proposal_id, "handled by adport pending operation …")`), `lib/markting/assistant.ts:61`, `engine/src/paid_media_agent/tools/writes.py:498-511` (state → `rejected`, history line "rejected by adport-bridge: handled by …"), `surfaces/runner.py:257-275` (the graph resumes with a `reject` decision, so the model's own conversation memory records a rejection), `lib/markting/repository.ts:107-112` (`markPendingOutcome` writes the true outcome only to `markting_engine_proposals`), `rg "'expired'"` → never called, so provenance rows for pending operations that lapse after the 15-minute TTL (`platform/packages/core/src/policy/policy.ts:19`) stay `pending` forever; `domain/presentation.py` exposes no `history` field, so even the engine's own history is invisible through the API.
- Description: the hand-off is deliberate and safe (the engine must never execute), but its side effect is that the engine's durable memory of what happened to a recommendation is always "rejected", while the real decision (applied / rejected / expired) lives only on the adport side and is never fed back to the engine or the next conversation. A follow-up question in the same thread ("did my budget change go through?") is answered from a checkpoint that says the reviewer rejected it.
- Impact: no accepted/rejected learning is possible from engine data; the conversation memory actively misleads; provenance never reaches a terminal state for expired items.
- Recommendation: send a neutral hand-off (a dedicated "handed_off" decision, or a reject message that the system prompt teaches the model to interpret as "pending in adport"); write the adport outcome back to the thread (a system message or a `markting_decision_outcomes` row injected as context on the next turn); mark `expired` in the retention/sweep job.

### C4-06 — Conversation memory is write-only: nothing can read a thread back
- Severity: **GAP** (not claimed by code; acknowledged in `docs/TODO.md:31`)
- Classification: VERIFIED_CODE
- Evidence: `engine/src/paid_media_agent/surfaces/api/app.py` has no endpoint that returns a thread's messages (only `POST /threads/{id}/messages` and artifacts); `platform/apps/cloud/app/dashboard/assistant/assistant-chat.tsx:24-25,45` keeps `threadId` and messages in React state only (reload = new thread); `lib/markting/repository.ts:29-36` `listThreads` is never called; `markting_threads` stores only id/title/timestamps, no messages.
- Description: the checkpointer faithfully persists every turn, but no product surface can list or resume a conversation; the user-visible "memory" is the current browser tab.
- Recommendation: add `GET /threads` (platform, from `markting_threads`) and an engine `GET /threads/{id}/messages` (from `graph.aget_state`) scoped by the tenant identity from C4-03; resume `threadId` from the URL or local storage.

### C4-07 — The only durable memory path (Postgres) is untested in this repository
- Severity: **P2**
- Classification: VERIFIED_RUNTIME (skips/failures observed), NOT_VERIFIED (Postgres behaviour)
- Evidence: `engine/tests/integration/test_live_readonly.py:38-40` (`pytest.skip("DATABASE_URL not configured")`; observed "2 skipped"), no test anywhere references `_postgres_checkpointer` or `AsyncPostgresSaver` (`rg` over `engine/tests`, `services/engine-demo/tests`), `services/engine-demo/tests/test_demo_api.py` runs in-memory only, `platform/apps/cloud/test/markting-repository.database.test.ts` needs the local Supabase stack (ECONNREFUSED here) and is excluded from `make test` (Makefile:52), `docs/PHASE0-REPORT.md:58` records a one-off manual check that the tables were created.
- Description: compose runs the engine with `DATABASE_URL` set (`docker-compose.yml:43`), so production memory is Postgres, yet the optimistic-concurrency path (`postgres.py:70-110`, whole-record JSON equality in the `WHERE`), the two independent pools (sync `ConnectionPool` for repositories, async pool for the saver — `postgres.py:50`, `self_hosted.py:52-62`), and the hand-off between them under concurrent requests have no automated verification in this checkout. The JSONB equality comparison in `save(expected=…)` relies on Postgres JSONB normalisation matching `json.dumps(model_dump)`; that is plausible but NOT_VERIFIED.
- Recommendation: make `ADPORT_RUN_DATABASE_TESTS=1` and an engine Postgres service part of CI (`make test` currently cannot catch a regression in either memory store); add a test for `_postgres_checkpointer` + `AgentRunner.send` round trip.

### C4-08 — Shared workspace state from the markting host breaks the upstream engine test-suite
- Severity: **P3**
- Classification: VERIFIED_RUNTIME
- Evidence: `engine/workspace/KILL_SWITCH` exists with the markting host's text (`services/engine-demo/serve_demo.py:173-180` writes it at the default relative path `workspace/KILL_SWITCH`, `engine/src/paid_media_agent/config.py:158`); `runtime/profiles.py:411-414` resolves that relative path against `project_root`; upstream contract tests `test_api_and_slack_share_persisted_state` and `test_slack_review_and_button_approval_resume_the_same_graph` fail (receipt `rejected`), and pass (7/7) with `PAID_MEDIA_KILL_SWITCH_PATH` pointed to a non-existent file.
- Description: not a product defect (the kill switch is meant to be engaged wherever adport is the writer) but a demonstration that `engine/workspace` is global mutable state shared between processes, and that the "unchanged upstream" claim in `UPSTREAM.md` does not extend to its tests passing in this checkout.
- Recommendation: have the host write the kill switch under its own workspace root (it already receives `settings.paid_media_workspace_root`), or document the env override for running upstream tests.

### C4-09 — Audit memory stores more than it can show; receipts keep only the latest revision
- Severity: **P3**
- Classification: VERIFIED_CODE
- Evidence: `platform/apps/cloud/lib/markting/bridge.ts:89-93` writes `details` (proposal id, revision, digest, risk flags, reason, translation notes) into `audit_events.details`; `lib/cloud/repository.ts:720-726` (`listAuditEvents`) does not select `details`; `engine/src/paid_media_agent/persistence/postgres.py:195-196` upserts `pma_receipts` by `proposal_id`, so a revision-1 receipt is overwritten by revision 2 (documented in `docs/ARCHITECTURE.md:726`).
- Impact: the richest per-org record of why a recommendation was made is written but not surfaced; the engine's receipt history is lossy (moot while the engine is proposal-only).
- Recommendation: expose `details` in the audit UI/API; if the engine ever executes, key receipts by `(proposal_id, revision)`.

### C4-10 — Engine memory database: hard-coded credentials, no backups, unbounded growth
- Severity: **P3** (local stack today; `docs/TODO.md:20` already lists backups as a production gate)
- Classification: VERIFIED_CODE
- Evidence: `docker-compose.yml:43,69-71` (`paid_media:paid_media`), no backup/retention tooling for `engine-pgdata`, no pruning (C4-02).
- Recommendation: secret-managed credentials, backups, and the retention job from C4-02 before any non-demo deployment.

### C4-11 — No tenant memory, account memory, long-term learning or outcome learning exists
- Severity: **GAP** (no code claims it; upstream docs explicitly say memory is off)
- Classification: VERIFIED_CODE, DOCUMENTED_ONLY for the MDA alternative
- Evidence: no LangGraph `store` is passed to `create_deep_agent` (`runtime/local.py:281-292`; the parameter exists, `deepagents/graph.py:287`); `engine/memory.py` absent; `engine/docs/customization.md:112-125` ("Durable learned memory is off by default… shared by every caller… Keep it off when callers should not influence one another"), `engine/OPERATIONS.md:78-79`; business context is a single global `workspace/skills/company-context/` (`engine/OPERATIONS.md:14`, `engine/README.md:114-118`, `engine/instructions.md:13`), not per organization; the engine's account registry is one global TOML (`runtime/profiles.py:426-436`, `config/accounts.example.toml`); the per-org alias map and its `targets` (`markting_account_aliases`, `repository.ts:40-50`) are used only for translation and never reach the model's context; `ChangeSet.measurement_plan`/`reversal_plan` (`domain/proposals.py:105-106`) are parsed by the bridge (`translate.ts:38-39`) but nothing schedules a measurement or stores an outcome; the adport `findings` table (`20260828120000…sql:33-43`) is wired into the bridge runtime (`lib/markting/runtime.ts:25`) but the bridge never saves a finding.
- Description: within a thread, the model has context (checkpoints plus deepagents' default summarization middleware, `deepagents/graph.py:803,888`); across threads, per organization, per account, or over time, it has nothing. Every conversation starts from zero knowledge of the org's goals, past recommendations, what was accepted, or what happened afterwards.
- Recommendation: see "What a world-class system would need" — this is the core of the Marketing Memory design and must be built on the adport side where tenancy already exists.

## What a world-class system would need ("Marketing Memory" boundaries, design only)

Principles that fall directly out of the findings:

1. **Tenancy is decided before the model runs, and the engine must know it.** The organization id must be part of the engine's identity (per-org token or a signed `caller_ref`), so `pma_thread_owners`, proposal visibility, artifact roots and report indexes are all keyed by tenant on the engine side as well as on the platform side. Every memory table gets `organization_id NOT NULL` plus RLS like the existing `markting_*` tables.

2. **Memory lives in adport's Postgres, not in the engine.** The engine is stateless per tenant except for checkpoints; everything that should outlive a thread is written by the platform (which already has the principal, RLS, retention and deletion) and injected into the engine as read-only context at the start of each turn. The engine never persists cross-thread memory itself (the upstream's own warning: shared memory lets every caller influence every other caller).

3. **Memory layers and their keys**
   - *Conversation* — LangGraph checkpoints, keyed `thread_id = org_<id>__u_<id>__<rand>` as today, plus `checkpoint_ns`/workspace root per organization; readable through `GET /threads/{id}/messages` only by that tenant; purgeable by prefix.
   - *Tenant memory* — `markting_memory_facts(organization_id, scope ∈ {org, account, campaign}, scope_ref, key, value jsonb, source ∈ {user_stated, derived, imported}, confidence, created_by, created_at, expires_at, superseded_by)`. Holds business goals, target CPA/ROAS per account, seasonality notes, approved vocabulary (Arabic names for campaigns), and "never touch" lists. Only `user_stated` facts and human-reviewed `derived` facts are injected into prompts; the model may *propose* a fact (a tool that writes a row with `status=proposed`), a human confirms it on a Memory page.
   - *Account memory* — per `(organization_id, provider, account_id)`: baselines (rolling 7/28-day metrics snapshots), structure digests (campaign/ad set inventory with last-seen timestamps), connected-account scope. Fed from the platform's own provider reads, not from the engine's fixture catalog.
   - *Decision memory* — `markting_decision_outcomes(organization_id, proposal_id, revision, pending_operation_id, tool, account_id, target_ref, before, after, decided_by, decision ∈ {applied, rejected, expired, unsupported, rejected_by_policy}, decided_at, measurement_plan, measure_at, baseline jsonb, measured jsonb, verdict ∈ {improved, neutral, worse, inconclusive}, measured_at)`. The existing `markting_engine_proposals` is the seed; add the outcome columns, set `expired` from the retention sweep, and schedule the post-apply measurement from `measurement_plan` using the platform's read tools.
   - *Audit memory* — keep `audit_events` as the immutable log; surface `details`.

4. **Injection contract.** Each turn the platform builds a compact, bounded "memory brief" (org goals, account targets, last N decisions with verdicts, open pending operations, explicit do-not-touch list) and sends it with the message (a system-prefixed section in `text`, or a new engine endpoint that accepts `context` separately so it is never confused with user prose). The engine treats it as data, never as instructions to loosen policy; budget caps and protected accounts stay in `organization_policy`, never in memory.

5. **Hand-off semantics that keep engine memory truthful.** Replace "reject" with a `handed_off` decision (or a reject message the system prompt defines as "pending human review in adport"), and write the final adport decision back into the thread as a system message so follow-up questions are answered correctly.

6. **Isolation of the model's scratch space.** Per-organization workspace root and `ArtifactStore`; deny writes outside it; artifact ids carry or are verified against the tenant; the report index is per tenant.

7. **Lifecycle.** Deletion route calls the engine purge (checkpoints, `pma_*`, artifacts by org prefix); `apply_data_retention` covers `markting_*`, memory facts (by `expires_at`), decision outcomes and engine tables (via a scheduled engine sweep); `pma_dedupe` gets a TTL; backups for both databases.

8. **Learning, governed.** Learning is restricted to (a) facts the user stated, (b) measured outcomes of applied decisions, (c) acceptance/rejection rates per tool/account used only to rank or annotate proposals ("similar changes were rejected 3 times on this account"). No learned value ever changes a policy limit, an approver set, or a protected-account list. Everything the model can write to memory is visible and revocable by the organization owner.
