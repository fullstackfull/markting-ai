## Findings

### B4-01 — No forecasting / prediction logic exists anywhere
- Severity: GAP (not a defect; nothing in the code claims to forecast)
- Classification: VERIFIED_CODE (absence established by exhaustive grep over engine + platform, exit-coded above)
- Evidence: `rg -ni "forecast"` returns only `platform/docs/provider-landing-pages.md:` (marketing prose); `predict|holt|arima|ewma|moving_average|rolling` = 0 files; `engine/src/paid_media_agent/domain/analysis.py:107-121` (`PeriodComparison` has only `requested_current`, `requested_previous`, `platforms`, `cross_platform_total/previous` — no predicted/expected/baseline field).
- Description: There is no statistical or ML forecasting layer. No time-series model, no fitted baseline, no expected-value computation, no confidence/prediction interval. Every number the system emits is an exact aggregate of observed rows for an explicitly requested window.
- Impact: The product cannot answer "what will spend/CPA/conversions be next week/month", cannot produce a budget pacing projection to month-end, and cannot say whether a current value is above/below an expected level. For an "AI media buyer" this is a core missing capability, but it is honestly absent rather than faked.
- Recommendation: Treat as a roadmap gap. If added, do it as a new deterministic tool (parallel to `compare_periods`) so numbers stay code-derived and auditable, and keep the model out of the arithmetic (consistent with `cadence.py:2-5`).

### B4-02 — No trend-detection logic; "trend" is guidance prose, not computation
- Severity: GAP
- Classification: VERIFIED_CODE + DOCUMENTED_ONLY
- Evidence: all `trend` hits are documentation or UI copy — `engine/workspace/skills/paid-media-wiki/anomaly-and-significance.md:25` ("Call a change a trend only when it persists across several days or two full windows"), `benchmarks.md:30`, `report-design/SKILL.md:26` ("Do not create trends or benchmarks to fill a layout"), and the X placement constant `platform/packages/x/src/analytics.ts:8` (`'TREND'`). No slope, no multi-point regression, no persistence detector in code.
- Description: Trend is explicitly delegated to the LLM's judgement as a reading convention, not computed. There is no code that fits a line or detects direction across more than two windows.
- Impact: "Trends" shown to a user are the model's narrative over at most a two-window delta; they are not statistically derived and could be hallucinated if the wiki guidance is not followed.
- Recommendation: If trend is to be a product claim, implement a deterministic multi-window/daily-series slope or persistence check; until then, do not advertise trend detection as a capability.

### B4-03 — No seasonality, holiday, or Ramadan/Eid awareness (notable for an Arabic-first MENA product)
- Severity: GAP (P3-adjacent for an Arabic-first positioning, but still a missing feature, not a defect)
- Classification: VERIFIED_CODE + DOCUMENTED_ONLY
- Evidence: `rg -ni "ramadan|holiday|eid|seasonal"` finds only prose — `engine/workspace/skills/paid-media-wiki/decision-model.md:35` and `benchmarks.md:10` mention "seasonality" as something the model should *consider*; `engine/docs/customization.md:38` lets a user describe "seasonal changes" as free text context. No calendar, no holiday table, no Hijri calendar, no weekend-locale logic. Report windows are UTC and calendar-agnostic (`reports/cadence.py:37-49`).
- Description: There is no seasonal baseline, no holiday/Ramadan adjustment, and no notion of the MENA work-week (Fri/Sat weekend). `anomaly-and-significance.md:3,19` even tells the model weekends matter and to compare same-weekday-a-week-earlier, but no code performs that same-weekday comparison — it is left to the model.
- Impact: For a product targeting Arabic/MENA advertisers, Ramadan and Eid are the dominant seasonal effects on spend and conversion behaviour; the system has no structural awareness of them. Any seasonal reasoning depends entirely on the LLM and on whatever free-text the user supplied.
- Recommendation: A seasonality layer would need a Gregorian+Hijri holiday calendar (Ramadan start/end per year, the two Eids, national days per GCC country), configurable weekend days per account/geo, and same-weekday / year-over-year baselines. None of this exists today.

### B4-04 — No baseline / moving-average / regression statistical engine (and the code is explicit about it)
- Severity: GAP
- Classification: VERIFIED_CODE + DOCUMENTED (self-disclosed)
- Evidence: all `baseline` hits are CSS (`align-items: baseline`) or screenshot "visual baselines"; all `regression` hits are CI/test regression suites — neither is a statistical baseline/regression. The wiki states the stance directly: `engine/workspace/skills/paid-media-wiki/anomaly-and-significance.md:21-28` — "Significance without a statistics engine … Deterministic tools report exact values; they do not run significance tests … Do not extrapolate a partial week to a full week."
- Description: There is deliberately no statistics engine — no rolling average, no standard-deviation band, no significance test, no extrapolation. The product's philosophy (`cadence.py:2-5`) is that all arithmetic is exact aggregation and the model only narrates.
- Impact: "Is this change significant / is this value normal?" cannot be answered quantitatively; the model is instructed to hedge with qualitative language and base sizes instead. This is a conscious design choice, not a bug, but it caps the analytical ceiling.
- Recommendation: Document this limitation in user-facing capability claims. A future "expected range" feature would need a rolling baseline (e.g. trailing N same-weekdays) with dispersion, implemented deterministically.

### B4-05 — `compare_periods` is a two-window delta only; equal-length, complete, contiguously-read windows required
- Severity: GAP (capability boundary); the enforcement itself is a correctness strength
- Classification: VERIFIED_CODE + VERIFIED_TEST
- Evidence: `engine/src/paid_media_agent/tools/compare_periods.py:44-53` (rejects end<start and unequal day counts via `MetricWindow.same_length`), `:64-79` (rejects a window that starts before the read's first row, or a window with no rows — refuses to treat missing data as zero), and `compute.py:98-115` (`deltas` = `current - previous` with `relative = absolute/previous`, no modelling). Comparison is strictly two periods; `domain/metrics.py:45` `same_length` enforces equal day count. Tests: `tests/unit/test_compute.py`, `test_report_cadence.py` pass (exit 0).
- Description: The only comparison primitive compares a current window against a previous equal-length window and reports per-metric absolute and relative change. It has no baseline/expected concept and no year-over-year wiring. Because `previous_start`/`previous_end` are free arguments, an equal-length prior-year window is *theoretically* expressible, but it requires one `performance_rows` artifact that contiguously covers from `previous_start` through `current_end` (`compare_periods.py:67-72`), i.e. ~13 months of daily rows in a single read — and no schedule or UI wires a YoY comparison (INFERRED).
- Impact: Seasonal/YoY comparison is not available as a product feature even though the delta primitive could support an equal-length window if fed a long enough read. The strict coverage checks are good (they prevent partial-window drops from reading as spend declines).
- Recommendation: If seasonal comparison is desired, add a dedicated path that reads the aligned prior-year (and Ramadan-shifted) window and routes it through `compare_periods`; keep the coverage guards.

### B4-06 — Report cadence windows are fixed rolling 7/28-day UTC blocks, not calendar months or locale weeks
- Severity: GAP / P3 (maintainability + MENA-fit)
- Classification: VERIFIED_CODE
- Evidence: `engine/src/paid_media_agent/reports/cadence.py:37-49` — `days = 7 if weekly else 28`; current = trailing `days` ending on `end`, previous = the equal `days` immediately before. Schedules: `engine/schedules/weekly_report.py:7` `cron="0 13 * * MON"` reading "the last 14 complete days" (7 vs prior 7); `engine/schedules/monthly_report.py:7` `cron="0 13 1 * *"` reading "the last 56 complete days" (28 vs prior 28). Timezone hard-coded `"UTC"` (`cadence.py:37`).
- Description: "Monthly" is a 28-day block, not a calendar month, so month-length and month-boundary effects are not represented; windows are UTC regardless of account geography; weekly windows do not align to a MENA Sun–Thu work week.
- Impact: Period-over-period comparisons can misalign with how MENA advertisers think about months/weeks (and with billing cycles). 28-day blocks drift relative to calendar months over a year.
- Recommendation: Offer calendar-month and locale-week cadence options and an account timezone, while keeping equal-length comparison for the delta math.

### B4-07 — Budget "pacing" is a within-window ratio, not a month-end projection (consistent and safe)
- Severity: GAP (no projection) — not a defect
- Classification: VERIFIED_CODE
- Evidence: `engine/src/paid_media_agent/tools/summary.py:88-105` — `average_daily = metrics.spend / active_days`; `"pacing": _ratio_str(average_daily, budget)`; `over_budget` = entities whose `average_daily/daily_budget > 1` (`:145-147`). The only "anomaly" output is a day-over-day flag when spend or conversions move ≥50% vs the prior day (`summary.py:27 DAY_CHANGE_FLAG = 0.5`, `:119-124`).
- Description: "Pacing" compares average daily spend over observed days to the daily budget — a present-pace ratio, not a forecast of month-end spend. It divides by `active_days` (days with rows), not elapsed calendar days, so it is not a run-rate-to-period-end projection. This matches the wiki rule against extrapolating (`anomaly-and-significance.md:28`).
- Impact: The system will not tell a user "at this rate you will spend X by month end" or "you will under-deliver the budget". Day-over-day flags are heuristic (fixed 50% threshold, no base-size gating in code — the base-size caution is wiki guidance only), so they can over-flag small-number metrics unless the model applies judgement.
- Recommendation: A pacing projection (spend-to-date + run-rate × remaining days vs period budget) is a concrete, low-risk deterministic feature to add; if added, divide by elapsed calendar days of the period, not active days.

## What a world-class system would need (gaps, concrete)
1. **Data granularity.** Daily rows already exist (`PerformanceRow.window` is per-day; `summary.py:110-124` builds a daily series), which is the minimum for forecasting. Hour-of-day/day-of-week breakdowns are not read, so intra-week seasonality would need provider breakdown reads that are not wired for this purpose.
2. **History length.** Forecasting/seasonal baselines need 13+ months of daily history per account to capture Ramadan year-over-year; the only reads wired are 14-day (weekly) and 56-day (monthly) windows (`schedules/*.py`). No long-history store or backfill exists; artifacts are per-read, not a durable time-series warehouse.
3. **Holidays / Ramadan.** A Gregorian+Hijri calendar with per-year Ramadan and Eid dates, GCC national days, and configurable weekend days per account/geo. None exists; seasonality is entirely LLM prose today.
4. **Currency / FX.** Currency is tracked per platform and cross-platform totals are correctly suppressed on mixed currencies (`compute.py:316-318`), but there is no FX conversion or base-currency normalization — a forecast in a single reporting currency across platforms would need an FX layer that does not exist.
5. **Model + uncertainty.** A deterministic forecaster (e.g. seasonal-naive or additive decomposition) returning point estimate + interval, implemented as a tool so numbers stay code-derived (matching `cadence.py:2-5`), plus a pacing-to-period-end projection.
6. **Comparison alignment.** YoY and Ramadan-aligned window selection on top of the existing equal-length `compare_periods` primitive, plus calendar-month and locale-week cadence options.

## Disagreements / claims in docs that the code contradicts
- No documentation reviewed **claims** forecasting/trend/seasonality as an implemented capability. `engine/docs/architecture/capability-map.md:9` lists only `compare_periods` (period comparison) and no forecasting row — the docs and code agree that forecasting is absent. So there is no doc-vs-code contradiction to report here; the honest gap is simply that the capability does not exist.
- Minor internal tension (not a contradiction): `anomaly-and-significance.md:19` instructs the model to "compare the day with the same weekday a week earlier before calling it unusual", but **no code performs a same-weekday comparison** — the day-over-day flag (`summary.py:119-124`) compares only adjacent days. The quantitative primitive the guidance assumes is not provided; it relies on the model.
