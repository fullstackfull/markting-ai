## Findings

The consolidated, deduplicated team findings are in the structured JSON (`findings`) and the `08-production-readiness.md` matrix. I did not open new code defects of my own; my job was to verify the specialists' and reconcile severities. The two severity adjustments I made as lead:

### H7-01 — Raised H5-03 (no production migration path) and H1-06 (no TLS edge) from P2 to P1
- Severity: n/a (meta)
- Classification: VERIFIED_CODE
- Evidence: `Makefile:25-28` (`supabase db reset` is the only documented apply path — destructive); `docker-compose.yml:28-29` (plain HTTP). Rationale: both are hard prerequisites to serve a *remote paying* customer, not merely quality gaps — a destructive-only migration path risks data loss on first deploy, and OAuth/secure-cookie flows do not function without HTTPS. In the "first paying customer" frame these are blockers, so I rank them P1 in the consolidated list while noting the specialists' original P2 was correct for a pure local-demo frame.

### H7-02 — Confirmed the demo write-safety does NOT cover the cloud apply path
- Severity: n/a (clarification that elevates H3-01's real-world impact)
- Classification: VERIFIED_CODE
- Evidence: `app/api/approvals/[id]/apply/route.ts:26` calls `applyPending(...)` through the adport provider registry, independent of the proposal-only engine (`docker-compose.yml:48` `PAID_MEDIA_WRITES_ENABLED=false` only constrains the engine). So H1/H4's kill-switch and `assert_fail_closed` safety are real for the engine but do **not** make the production cloud deployment write-safe; the unaudited apply (H3-01) is the true money-spending mutation. This strengthens H3-01's impact for any live cloud deployment.
