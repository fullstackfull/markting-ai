## Findings

### E10-01 — Pending-operation apply is not atomic: concurrent double-apply (replay) to ad platforms
- Severity: **P1** · Classification: **VERIFIED_CODE**
- Evidence: `platform/apps/cloud/lib/cloud/repository.ts:385-411` (`PostgresPendingStore.get` — plain `select ... where consumed_at is null`, **no `for update`**); `platform/apps/cloud/lib/cloud/repository.ts:413-418` (`delete` → `update ... set consumed_at = now() where id = ... and organization_id = ...`, **no `and consumed_at is null`**, not in a txn with `get`); `platform/packages/core/src/policy/engine.ts:87-125` (`apply`: `get` → `applyWrite` → `audit.append` → `delete`, no lock); `platform/apps/cloud/app/api/approvals/[id]/apply/route.ts:20-27` and `platform/apps/cloud/lib/markting/bridge.ts:119-121` (no transaction wrapping find→apply→consume). Contrast `repository.ts:81-104` where OAuth consume correctly uses `db().begin` + `for update` + `consumed_at` check.
- Description: Two near-simultaneous `POST /api/approvals/{id}/apply` (double-click, client retry, two admins) both pass `listPendingOperations` and `PostgresPendingStore.get` (both read `consumed_at = null`), both call `provider.applyWrite`, then both set `consumed_at`. Nothing serializes the read-check-consume.
- Impact: Duplicate real-platform writes — e.g. two campaigns created, a budget change applied twice — i.e. unsafe/duplicated ad execution with direct financial effect. The core `policy-engine.test.ts:94-105` only proves **sequential** replay returns `PENDING_NOT_FOUND`; there is no concurrency test.
- Recommendation: Make consume compare-and-set: `update ... set consumed_at = now() where id = ... and consumed_at is null returning id`, run it (and ideally `select ... for update`) inside `db().begin` **before** `applyWrite`, and treat 0 rows as `PENDING_ALREADY_CONSUMED`. Mirror the OAuth-transaction pattern already in the file.

### E10-02 — Engine report surface has no tenant scoping (cross-tenant visibility of report runs/files)
- Severity: **P2** · Classification: **VERIFIED_CODE** (confirmed by test `test_demo_api.py:157-177`)
- Evidence: `services/engine-demo/serve_demo.py:252-307` (`_load_index`/`run_report` read/write a single `out/markting-reports.json`; `requested_by` = the single shared caller) and `:355-374` (`/reports`, `/reports/files/{name}` gated only by the one bearer token, no org); `platform/apps/cloud/app/api/reports/engine/route.ts:16-23` (`GET` returns `engineClient().listReports()` with no org filter) and `platform/apps/cloud/app/api/reports/engine/[name]/route.ts:10-26` (streams any `(rpt|art)_*.{html,pdf,json}` by name). The engine is a single shared host authenticated by one `MARKTING_ENGINE_TOKEN`.
- Description: Every cloud tenant that calls `/api/reports/engine` receives the global report index (all tenants' runs, timestamps, summaries, file names) and can download any listed file. There is no `organizationId` partition anywhere in the engine report store.
- Impact: Cross-tenant metadata/report exposure. Current real impact is bounded because `assert_fail_closed` forces `PAID_MEDIA_DATA_MODE=sample` (`serve_demo.py:163-166`), so report bodies are synthetic/fixture data identical for all tenants and `requested_by` is a shared label — so no real per-tenant ad data leaks today. The isolation model is nonetheless absent: if the engine were ever pointed at real per-tenant data this becomes P0.
- Recommendation: Namespace report runs/files by `organizationId` (pass it from the cloud and scope the index + file reads), or document explicitly that the engine report surface is global sample-only and must never carry tenant data.

### E10-03 — Budget-delta and absolute budget caps are not re-checked at apply
- Severity: **P2** · Classification: **VERIFIED_CODE**
- Evidence: `platform/packages/core/src/policy/engine.ts:110-113` — `apply()` re-runs only `checkStaticPolicy` (protected accounts), then calls `provider.applyWrite`. `checkBudgetPolicy` (`:133-153`) runs only in `validate()` (`:62`). The guard passed to `applyWrite` (`:54-56`) carries only `forcePausedCreation`.
- Description: Budget caps (`max_budget_delta_pct`, `max_daily_budget_micros`) are enforced against the preview computed at validate time. Between validate and apply, the organization policy can be tightened, or the account's current budget can change, and apply will not re-evaluate the caps. The op hash locks the *target* micros, so the absolute value applied equals what was reviewed; but a policy tightened after preview (e.g. owner lowers `max_daily_budget_micros`) is silently not enforced on an in-flight pending op.
- Impact: A pending op validated under looser rails can be applied after the rails are tightened, up to the per-op TTL (default 15 min). Financial guardrail bypass window.
- Recommendation: Re-run `checkBudgetPolicy` in `apply()` against the current policy (the preview's `budgetDeltas` are already stored on the pending row), or re-preview and compare before executing.

### E10-04 — Preview shown to the approver can be stale relative to the applied effect
- Severity: **P3** · Classification: **VERIFIED_CODE**
- Evidence: `platform/packages/core/src/policy/engine.ts:113,124` — apply executes `provider.applyWrite(op)` (a fresh provider call) and returns the **stored** `pending.preview`; there is no comparison of the fresh apply result against the preview. The hash (`:31-40`) covers op inputs only, not that the provider's preview and apply semantics agree.
- Description: The approver reviews `pending.preview.summary`/`budgetDeltas` captured at validate time (including `fromMicros` = account state then). If the account state changed after preview, the displayed "from → to" and percentage are stale, and no post-apply reconciliation is surfaced.
- Impact: Operator sees a delta that no longer matches reality at apply. Target value is still deterministic (hash-locked), so the material change is bounded; this is a trust/clarity defect, not a value-divergence.
- Recommendation: Either re-preview at apply and show/compare, or annotate the preview with "as of <validated-at>" and fail if `fromMicros` drifted beyond a tolerance.

### E10-05 — Completed write with no audit entry if the audit append fails after `applyWrite`
- Severity: **P2** · Classification: **VERIFIED_CODE**
- Evidence: `platform/packages/core/src/policy/engine.ts:113-123` — order is `applyWrite` (external side effect) → `audit.append('applied')` → `pending.delete`. Cloud audit append is a DB insert (`repository.ts:431-433` → `recordAudit` `:282-289`). No pre-write "applying" intent record exists at apply time (only `validated` at `:76-83`).
- Description: If `audit.append` throws after `applyWrite` succeeds (DB hiccup, constraint, outage), the platform write has already happened, the `applied` audit row is never written, and because `delete` is never reached the pending row stays applicable — enabling a retried second write (compounds E10-01).
- Impact: Invariant #13 (audit cannot silently omit writes) fails under audit-store failure: a real write can exist with no `applied` audit record, and the un-consumed pending allows a duplicate.
- Recommendation: Write an `applying` intent audit row before `applyWrite`, and/or consume the pending in the same transaction as the audit append; reconcile intent vs applied asynchronously.

### E10-06 — Null `created_by` silently disables the self-approval guard
- Severity: **P3** · Classification: **VERIFIED_CODE**
- Evidence: `platform/apps/cloud/app/api/approvals/[id]/apply/route.ts:22` — `if (row.createdBy && row.createdBy === principal.userId && ...)`. Pending ops created by an API key or by the engine bridge have `created_by = null` (`repository.ts:379-381` stores `principal.userId ?? null`).
- Description: The four-eyes check short-circuits when `createdBy` is null, so any owner/admin may apply such an op (expected for engine-originated proposals, but also true for API-key-originated ones). Not cross-tenant (still org-scoped), but the separation-of-duties rail silently does not apply to a class of operations.
- Impact: Weaker-than-advertised maker/checker control for API-key- and engine-created pendings. Low.
- Recommendation: Record a stable actor identity for API-key/engine-created pendings and define approval policy for them explicitly rather than relying on a null short-circuit.

### E10-07 — Dashboard apply can't reach a valid pending op beyond the 200 most-recent
- Severity: **P3** · Classification: **VERIFIED_CODE**
- Evidence: `platform/apps/cloud/app/api/approvals/[id]/apply/route.ts:20` — `(await listPendingOperations(principal.organizationId, 200)).find(c => c.id === id)`; `repository.ts:696-704` orders by `created_at desc limit`.
- Description: Apply/reject fetch a capped, ordered list and `.find` by id instead of fetching the row by id. With >200 live pending ops an older valid op returns 404.
- Impact: Availability/correctness edge, not a security bypass.
- Recommendation: Fetch the pending row by id directly (scoped by org), not via a capped list.

## What a world-class system would need (concrete)
- Compare-and-set consume (`... where consumed_at is null returning id`) inside a transaction with a `select ... for update` on the pending row, before `applyWrite`; a concurrency test that fires two parallel applies and asserts exactly one platform write.
- Idempotency keys forwarded to each provider's mutation call so a retried apply is a no-op at the platform even if the gate is bypassed.
- Re-evaluate full policy (static **and** budget) at apply against current org policy and current account state; re-preview-and-diff with an explicit tolerance.
- Two-phase audit: `applying` intent row before the external call, reconciled to `applied`/`orphaned`; alert on orphans.
- Per-`organizationId` partitioning of the engine's threads, proposals, and reports, and/or per-tenant engine tokens, so the engine is not a single trust boundary behind one shared secret.
- Fetch pending rows by id (org-scoped), not via a capped list.

## Disagreements / claims in docs that the code contradicts
- `app/api/approvals/[id]/apply/route.ts:9-12` comment ("the exact second call … routed through the same registry and PolicyEngine") is accurate for the mechanism but omits that the find→apply→consume is **not atomic** (E10-01), unlike the sibling OAuth consume which is.
- `serve_demo.py` docstring guarantees ("nothing in this process can reach an advertising platform") are substantiated, but the reports surface it adds (`:310-374`) is **not** tenant-scoped, which the "single write path" framing does not flag (E10-02).
- `engine.ts:110` comment "Policy may have changed between validate and apply; re-check" overstates the re-check: only `checkStaticPolicy` runs, not `checkBudgetPolicy` (E10-03).
