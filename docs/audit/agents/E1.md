## Findings

### E1-01 — Report list/download is not organization-scoped (cross-tenant exposure) — P1 — VERIFIED_CODE + INFERRED
Evidence: `app/api/reports/engine/route.ts:18-20` and `app/api/reports/engine/[name]/route.ts:13-15` authenticate with `sessionPrincipal(organizationId)` but then call `engineClient().listReports()` / `fetchReportFile(name)` with **no organization identifier**. `lib/markting/assistant.ts:12-15` builds one global `EngineClient` from a single `MARKTING_ENGINE_URL` + `MARKTING_ENGINE_TOKEN` (`lib/markting/env.ts:10-12`), and `lib/markting/engine-client.ts:131` (`GET /reports`) / `:134-136` (`GET /reports/files/{name}`) send only the shared bearer token. The session's `organizationId` is used solely to prove the caller is logged into *some* org; it never filters which reports are returned.
Description/impact: On any deployment where one engine host serves more than one organization, an authenticated member of org A can call `GET /api/reports/engine?organizationId=<A>` and receive the report runs of every org on that engine, and `GET /api/reports/engine/<file>?organizationId=<A>` to download any other tenant's report file (ad spend, performance figures, model-written analysis). The assistant path, by contrast, scopes correctly via the `org_…__u_…` thread prefix (`lib/markting/assistant.ts:34-38`); reports do not.
Recommendation: Pass and enforce the tenant (e.g. thread/run ownership keyed on `organizationId`) on `/reports` and `/reports/files/*`, or run one engine per organization and assert that in config. Until then treat reports as a cross-tenant leak.
NOT_VERIFIED: whether the engine (`engine/`, out of scope) independently isolates reports by caller, and whether production runs one engine per org (which would downgrade this). If the engine does not isolate and the engine is shared, this is effectively P0.

### E1-02 — OAuth access/refresh tokens survive member deprovisioning — P2 — VERIFIED_CODE
Evidence: `lib/cloud/mcp-oauth-repository.ts:263-298` (`authenticateMcpOAuthAccessToken`) looks up the token row by `jti` and checks revocation/expiry/claim-consistency but never re-checks `organization_memberships`. `exchangeMcpRefreshToken` (:215-261) likewise never re-validates membership. `lib/cloud/repository.ts:317-334` (`authenticateApiKey`) is org-scoped (acceptable), but OAuth tokens are tied to a specific `user_id` (sub).
Description/impact: When an owner/admin removes a user (`removeOrganizationMember`, `tenant-admin.ts:117`), the member's still-valid MCP access token (1h, `ACCESS_TOKEN_SECONDS`) and refresh token (30d, `REFRESH_TOKEN_SECONDS`) keep authenticating and can mint fresh access tokens against that org for up to 30 days. `sessionPrincipal` re-checks membership on every call (`auth.ts:13`), so only the token path is affected. Member removal has no code path that revokes that user's `mcp_oauth_*` tokens.
Recommendation: Join `organization_memberships` in `authenticateMcpOAuthAccessToken`/`exchangeMcpRefreshToken`, and revoke the user's access+refresh tokens inside `removeOrganizationMember`/`changeOrganizationMemberRole`.

### E1-03 — Production CSP permits `script-src 'self' 'unsafe-inline'` — P3 — VERIFIED_TEST
Evidence: `next.config.ts:17` emits `script-src 'self' 'unsafe-inline'` outside development; `test/security-headers.test.ts:13-17` only asserts `unsafe-eval` is excluded, so inline script execution is permitted site-wide by design. No nonce/hash-based policy is used.
Description/impact: `'unsafe-inline'` on `script-src` neuters CSP as an XSS mitigation. No injection sink was found (no `dangerouslySetInnerHTML`, React auto-escapes, report bodies are streamed as `attachment` with `nosniff` — `reports/engine/[name]/route.ts:22-24`), so current exploitability is low; this is a weakened defense-in-depth control for a product that executes ad-budget changes.
Recommendation: Move to nonce-based CSP (Next.js middleware nonce) and drop `'unsafe-inline'` from `script-src`.

### E1-04 — Internal error messages returned to clients via forced 403 — P3 — VERIFIED_CODE
Evidence: `lib/http.ts:24-32` — `apiError` only masks the message (`'Internal server error.'`) and logs when `responseStatus >= 500`. Several routes catch everything and force 403: `app/api/account-selection/route.ts:18-20`, `app/api/account-access/route.ts:31-33`, `app/api/settings/route.ts:32-34`, `app/api/deletion/route.ts:27-29`, `app/api/members/route.ts` (all handlers). An unexpected DB/runtime error therefore returns status 403 with the raw `error.message` and is never logged (`console.error` is gated on `>=500`).
Description/impact: Low-sensitivity internal detail (e.g. `postgres` constraint/column text) can leak to the caller, and genuine 500s are swallowed without server logs.
Recommendation: Let `apiError` derive status from the error (`errorStatus`) and reserve the forced-403 override for actual authorization failures; always log unexpected errors.

### E1-05 — No HSTS header set by the application — P3 — VERIFIED_CODE
Evidence: `next.config.ts:36-64` sets X-Content-Type-Options, Referrer-Policy, X-Frame-Options, Permissions-Policy, COOP and CSP, but no `Strict-Transport-Security`. Grep for `strict-transport`/`hsts` returned no matches.
Description/impact: Without HSTS the app relies on the hosting edge to enforce HTTPS; if a deployment target does not add it, downgrade/SSL-strip exposure remains. Low given Vercel typically injects it.
Recommendation: Add `Strict-Transport-Security: max-age=63072000; includeSubDomains; preload` to the `/(.*)` header block.

### E1-06 — Cookie-authenticated JSON routes have no explicit CSRF defense — P3 — INFERRED
Evidence: Dashboard mutation routes (e.g. `app/api/settings/route.ts`, `members`, `account-access`, `account-selection`, `connections/[provider]`, `deletion`) authenticate purely from the Supabase session cookie via `sessionPrincipal` and perform no Origin/Referer check or CSRF token. Server actions (`app/login/actions.ts`, `app/dashboard/billing/actions.ts`) are covered by Next.js's built-in same-origin check; the public `waitlist` route does add an explicit Origin allowlist (`app/api/waitlist/route.ts:13-19`), these JSON routes do not.
Description/impact: Protection currently rests implicitly on SameSite=Lax cookie default plus the fact that `application/json` cross-site fetches trigger a CORS preflight these routes never grant. If the Supabase cookie were ever issued SameSite=None, or a route added permissive CORS, these would become CSRF-able. Defense-in-depth gap, not a confirmed exploit.
Recommendation: Add a shared Origin/Referer allowlist (as waitlist already does) to state-changing JSON handlers.

### E1-07 — Member directory readable by any workspace member, including viewers — P3 — VERIFIED_CODE
Evidence: `app/api/members/route.ts:15-23` GET requires only membership (`sessionPrincipal(organizationId)`), no role gate, and returns emails/display names/roles via `listOrganizationMembers` (`tenant-admin.ts:20-24`). Mutations (POST/PATCH/DELETE) are correctly gated inside `tenant-admin.ts` (`requireMemberAdmin`/`requireAssignableRole`).
Description/impact: A viewer-role user can enumerate all workspace members and their emails. Likely acceptable by product design; flagged for completeness.
Recommendation: If member emails are considered sensitive, gate the list to owner/admin or return self-only for viewers.

## Positives verified (not defects)
- Crypto is sound: AES-256-GCM with per-record AAD + random IV (`lib/crypto.ts:11-27`), API keys stored as HMAC-with-pepper (`:33-35`), timing-safe comparisons (`:37-40`, `mcp-oauth.ts:181`). Secrets length-validated in `lib/env.ts`.
- MCP OAuth is robust: mandatory PKCE S256 with 43-char challenge (`mcp-oauth.ts:131-133`), single-use authorization codes under `for update` + `consumed_at` (`mcp-oauth-repository.ts:182-211`), refresh-token rotation with bounded reuse grace (`:215-261`), RFC 8707 resource binding (`mcp-oauth.ts:109-123`), DB-backed access tokens verified by `jti` with full claim cross-check (`:263-298`), HS256 verified via `timingSafeEqual` (`mcp-oauth.ts:175-206`). DCR limited to public `none` clients and rate-limited (`oauth/register/route.ts:8-11`).
- Open-redirect guard `safeReturnPath` rejects `//`, backslash and absolute origins (`lib/return-path.ts`); OAuth callbacks always redirect against `ADPORT_CLOUD_BASE_URL`, never the inbound Host (`oauth/[provider]/callback/route.ts:24-28`). Popup `next` is allow-listed to four paths (`lib/oauth-popup.ts:9-15`).
- Provider OAuth state is hashed at rest, single-use (`for update` + `consumed_at`), user+org bound, 10-min TTL, PKCE verifier encrypted; role is re-checked after consent (`oauth/[provider]/callback/route.ts:58-61`).
- Report filename guarded against path traversal (`engine-client.ts:135`) and streamed as `attachment` with `nosniff`.
- No SSRF: every outbound `fetch` targets a fixed/env-configured host (engine, provider token URLs defaulting to real endpoints in `lib/env.ts`, Stripe, Resend, Supabase); no user-controlled URL is fetched.
- All SQL uses `postgres` tagged-template parameterization (`lib/db.ts`, repositories) — no injection observed. Connection pinned to a dedicated DB role (`ADPORT_DB_ROLE`).
- Four-eyes approval: self-approval of a pending op is blocked unless `MARKTING_ALLOW_SELF_APPROVAL==='true'` (off by default) (`approvals/[id]/apply/route.ts:22`). Engine client structurally cannot approve/edit (`engine-client.ts:61,77-79`).
- Rate limiting keyed on the authenticated key, not client headers (`auth.ts:31-35`); waitlist bounds body size, honeypots, and rate-limits per IP+global.
- Stripe webhook verifies signature via `constructEvent` (`billing/webhook/route.ts:9`).

## What a world-class system would need
- Org-scoped engine report access (ownership check on every `/reports*` call) or hard one-engine-per-tenant isolation asserted in config and tests.
- Token-time membership re-validation plus cascade revocation of `mcp_oauth_*` tokens on member removal/role change.
- Nonce-based CSP without `'unsafe-inline'`, HSTS, and an explicit Origin allowlist on all state-changing JSON routes.
- Centralized error handler that never leaks internal messages regardless of the forced status, and always logs unexpected failures.
- Consider RLS in Postgres as a second isolation layer behind the app-level `organization_id` filters.

## Disagreements / claims in docs that the code contradicts
- Code comments assert the reports path keeps "the engine token … server-side" (`reports/engine/route.ts:15`) — true, but this does not provide tenant isolation; the comment can mislead a reader into assuming reports are org-safe when they are not (E1-01).
- `engine-client.ts:5-6` claims the bridge "never approves or edits" — verified correct (`FORBIDDEN_PATHS`, no approve/edit methods).
