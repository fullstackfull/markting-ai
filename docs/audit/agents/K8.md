## How to read this
This is the final-council SRE seat. My job is to produce the authoritative production-readiness blocker list for markting-ai (blockers that must close before a first paying customer vs. should-haves before scale / live writes), to state what this sandbox could **not** verify, and to vouch for final severities after re-deriving the load-bearing claims from code myself. My primary inputs were the SRE cluster reports H1–H7, the consolidated readiness doc `docs/audit/08-production-readiness.md` (authored by the H7 lead), the CI-relevant build/test evidence in the F cluster (F1 build-verifier, F9 QA lead), and the secrets evidence in E3 / E11. I treat all of those as **claims to verify**: I re-ran 10+ load-bearing citations against the code and report HELD/FAILED/PARTIAL below. Repository code is the source of truth; every conclusion carries a path:line or a command with its exit code.

**Classification legend:** `VERIFIED_CODE` (read in source), `VERIFIED_TEST` (a test asserts it), `VERIFIED_RUNTIME` (I ran it and saw the result), `DOCUMENTED_ONLY` (claimed in docs, not independently confirmed in code), `INFERRED` (logical deduction, not direct observation), `NOT_VERIFIED` (could not check in this sandbox). **Severity:** P0 security/data-loss/cross-tenant/unsafe-ad-execution; P1 production blocker / serious financial risk; P2 substantial functional/reliability deficiency; P3 quality/polish; GAP = missing capability the code does not claim to have.

**One framing fact governs every severity below.** The shipped artifact is a **local, proposal-only demo**, not a product: `docker-compose.yml:41-48` runs `services/engine-demo/serve_demo.py` with `PAID_MEDIA_WRITES_ENABLED: "false"` and `PAID_MEDIA_DATA_MODE: sample`, Supabase is deliberately outside compose, and the edge is plain `127.0.0.1:3000` HTTP. "Accepting a paying customer" therefore means standing up a production topology (hosted Supabase, TLS edge, real Stripe, real OAuth, live model mode) **that does not exist in the repo and could not be built or run here.** Many items below are P3-for-the-demo but P1-for-production; I rank them for the production frame and say so, because that is the frame the blocker list is for.

## Findings I vouch for (final severities)

IDs preserve the `08-production-readiness.md` B#/S# scheme for traceability. Severities are for the **production / first-paying-customer frame**; I note where the demo frame would be lower.

### Blockers (P1 — close before the first paying customer)

- **B1 — No backup or restore for any data store.** `VERIFIED_CODE + DOCUMENTED_ONLY`. No `pg_dump`/WAL/PITR/snapshot/export anywhere (spot-check 5); `docker-compose.yml:78-80` plain named volumes; the only scheduled DB jobs *delete* data (H6-04). A lost volume loses all tenant config, encrypted credentials, approvals, and audit history with zero recovery. Managed-Supabase platform backups *might* cover the cloud DB in prod but are not configured or documented in-repo (NOT_VERIFIED), and the **engine Postgres + workspace** are covered by nothing either way.

- **B2 — Master encryption key has no KMS/escrow and no working rotation.** `VERIFIED_CODE`. `lib/crypto.ts:5-9` reads one symmetric key from an env var; `repository.ts:162` hardcodes `key_version = 1` and no code reads it to select a key (E3-02 confirmed). A DB restore without the exact key renders every `provider_credentials.ciphertext` permanently undecryptable; rotating the key in place destroys all ciphertext (self-inflicted data loss). `deployment-model.md:44-45` prescribes KMS; code does not implement it.

- **B3 — No usage metering; the dominant variable cost (LLM/engine turns, report runs) is unbilled and uncapped per plan.** `VERIFIED_CODE`. No `usage_events` ledger (spot-check 7); plans carry no AI/report fields; the only guard is a flat `enforceRateLimit(…, 120, 60)` that is plan-independent (`repository.ts:355`). A Free-tier org can consume unbounded model/engine cost. For an AI product this is a direct margin/financial blocker, hence P1.

- **B4 — The business cannot contract under its own name.** `VERIFIED_CODE / DOCUMENTED_ONLY`. Privacy/terms and in-app support/enterprise CTA name the upstream third party (`billing/page.tsx:119` `mailto:yannick@adport.dev`; `website/privacy.html`, `terms.html`); no DPA/subprocessor register/SCCs. This is a business-legal blocker rather than an SRE one, but it is a hard gate to taking payment and I keep it P1 in the consolidated list.

- **B5 — No production migration path; only the destructive `supabase db reset` is documented.** `VERIFIED_CODE / GAP`. `Makefile` `supabase-start` runs `supabase db reset --local --yes` (spot-check 9); no forward-only `db push`, ordering doc, rollback, or pg_cron promotion step. An operator following the repo would wipe production. (Raised from H5's P2 — correct for the prod frame.)

- **B6 — No TLS edge / reverse proxy.** `VERIFIED_CODE / GAP`. `docker-compose.yml:29` plain `127.0.0.1:3000`; no nginx/traefik/caddy anywhere (spot-check 10). Secure cookies and OAuth redirect flows that assume HTTPS do not work for a remote customer. (Raised from H1's P2 — correct for the prod frame.)

- **B7 — No CI at the monorepo root; the tenant-isolation DB suite never runs mechanically.** `VERIFIED_CODE`. The six upstream workflows live at `platform/.github/` and `engine/.github/` — paths GitHub never reads for this repo (spot-check 1). Nothing runs on push/PR; the `*.database*.test.ts` cross-tenant suites and all net-new glue code have zero automated gate. Docs (`PHASE0-REPORT.md:24,44`, `ARCHITECTURE.md:863`) cite these orphaned workflows as if live — a doc-vs-reality contradiction.

- **B8 — No graceful shutdown / connection draining (borderline-blocker).** `VERIFIED_CODE`. No FastAPI `lifespan`, no `timeout_graceful_shutdown`; `postgres.py:64` `close()` is defined but never called (spot-check 2). SIGTERM stalls on a ≤300s in-flight run or SIGKILLs it, aborting work and leaking DB connections — no safe zero-downtime deploy. **P1 the moment the engine is operated as a real service**; harmless in a start-once local demo.

- **B9 — Shared mutable engine state is not cluster-safe (borderline-blocker).** `VERIFIED_CODE`, conditional on multi-replica / live-write. The report index is one global 50-entry JSON file for all tenants (spot-check 3) and the kill switch is a per-process local file (spot-check 4). Two engine replicas corrupt the index and cannot share the emergency brake. **This gates any second replica and any live ad write.** (The report-index cross-tenant *exposure* is also a security concern that E11 rates P1/latent-P0 for the un-isolated `/reports` route; that is consistent with — not contradictory to — H4's operability framing.)

## Contradictions between agents and how I resolved them

1. **Can pnpm run in this sandbox? (F1 vs H2/E-cluster) — RESOLVED, not a code contradiction.**
   F1 executed `pnpm --filter @adport/cloud test` and reported 308 cloud tests passing + a clean `typecheck` (VERIFIED_TEST, run 2026-10-02 at `d9c79f6`). H2-08 and my own run report `pnpm --version` failing offline: `Cannot find module '/root/.cache/node/corepack/v1/pnpm/12.8.1/bin/pnpm.cjs'` (the repo pins `pnpm@11.8.0`). **Resolution:** both are true of their moment — this is sandbox/corepack network state, not a repository fact. corepack here resolves pnpm **12.8.1** (not the pinned 11.8.0) and cannot fetch it offline. So: F1's green results stand as VERIFIED_TEST evidence that the cloud suite passes when pnpm is available; **the current sandbox cannot execute the Node half**, so no later agent (H2, me) re-confirmed green. The corepack-version drift (12.8.1 vs 11.8.0) is a genuine repro smell worth pinning in CI, but it is not a defect in the application code.

2. **Engine pytest "19 failed" (F1) vs. "the suite is sound" — RESOLVED.**
   F1 ran `uv run --frozen pytest -q` → 19 failed / 158 passed, then showed by override that 18 of the 19 failures come from a **stale `engine/workspace/KILL_SWITCH` file** left in the workspace. I confirmed that file exists (`engine/workspace/KILL_SWITCH`, 60 bytes, git-ignored residue). **Resolution:** the engine test suite is **not broken in code**; the failures are a sandbox-residue artifact. Implication for B7: any root CI job must run against a **clean workspace** (no pre-engaged kill switch), or it will inherit these false failures.

3. **Reports-IDOR severity (H4 operability vs. E-cluster security) — RESOLVED as consistent, not contradictory.**
   H4-02 flagged the global 50-entry report file as an **operability** defect and explicitly deferred the cross-tenant **security** classification to the security workstream. E11 resolved the security view to **P1 (latent-P0)** on the un-isolated `/reports` route. These describe the same shared-state defect from two lenses; I record B9 (operability, P1-conditional) and note the security seat's P1/latent-P0 on the same mechanism. No conflict to resolve.

4. **H7's severity promotions (H5-03, H1-06: P2→P1).** Not a contradiction — H7 explicitly kept the specialists' P2 correct for the *demo* frame and promoted to P1 for the *paying-customer* frame. I **endorse** the promotions and apply the same frame discipline throughout.

**No material unresolved contradictions remain in the SRE/secrets cluster.** The eight SRE reports corroborate each other, and E11 reports 22/22 security citations held; where reports erred they erred toward caution (INFERRED/NOT_VERIFIED on anything needing a running stack).

## What was NOT verified (the authoritative sandbox-limits ledger)
These are genuine unknowns — **GAP / NOT_VERIFIED**, not passing grades. They must be closed by a networked CI runner and a staging environment before launch. This list is itself a production-readiness gate.

- **Docker image builds (`cloud`, `engine`, `sandbox`).** Network-blocked (`deb.debian.org`, registry pulls); per task rules, not retried. Whether any Dockerfile builds, whether `pnpm --filter @adport/cloud build:standalone` and `uv sync --extra …` succeed inside the images, and whether `next build` traces `.env.local` into `.next/standalone` (the H1-01 secret-leak reach) are all NOT_VERIFIED. `docs/TODO.md:21` records the same limitation.
- **`docker compose up` / live-stack runtime.** `docker compose config` validates only with a supplied root `.env`; no container was started. Graceful-shutdown behaviour on SIGTERM with a 300s in-flight request, real event-loop blocking from sync psycopg calls on the async loop, healthcheck timing under real boot, and the WeasyPrint OOM footprint are **INFERRED from code, NOT measured**.
- **Live Stripe.** No webhook exercised end-to-end (no live keys/signatures). The non-atomic dedup / ordering race (S9) is a code-path inference; `database.integration.test.ts` needs a live Supabase DB and was **not run** here.
- **Live OAuth (Google/Meta/TikTok/Microsoft/Apple/…).** No provider app approval, redirect URIs, or token exchange tested. `deployment-model.md:49-58` lists OAuth verification evidence as an explicit unmet gate. Apple Ads ES256 delegated flow and refresh-token handling are NOT_VERIFIED at runtime.
- **Live model mode / real LLM turns.** The demo is boot-pinned to `sample` data and proposal-only; no real model call, token-cost, or latency was observed. The cloud **apply** path (real ad-account write via the adport registry, independent of the proposal-only engine) was never exercised against a real provider — its write-safety and audit gap (S1) are VERIFIED_CODE, not VERIFIED_RUNTIME.
- **Real Supabase project.** Whether a production Supabase enables platform backups + PITR, actually runs the two pg_cron jobs (`adport-data-retention`, `adport-account-selection-expiry`), and overrides the committed `config.toml` (MFA/TOTP disabled, region pinned `us`) is an out-of-repo managed-service setting — NOT_VERIFIED; the repo configures none of it.
- **Node/pnpm suites in this sandbox.** `pnpm` is non-runnable offline (corepack fetching an uncached pnpm 12.8.1; contradiction 1), so cloud vitest/typecheck/build green status is NOT re-confirmed by the current sandbox. F1's earlier green run is the only VERIFIED_TEST evidence; the `uv`/Python half remains runnable.
- **Horizontal scaling / failover / restart drills.** No load test, SIGTERM/kill drill, Postgres-outage test, or restore drill was run (read-only scope). The multi-replica defects in B9/H4-02/H4-03 are stated for the per-replica-volume case and flagged conditional.
