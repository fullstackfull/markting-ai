## Findings

### I2-01 — "Separate client workspaces" is an advertised, billed Agency feature with zero implementation
- Severity: **P2** · Classification: **VERIFIED_CODE** (DOCUMENTED_NOT_IMPLEMENTED capability)
- Evidence: flag defined `platform/apps/cloud/lib/cloud/plans.ts:20`; set `true` only for Agency/Enterprise `plans.ts:38,42`; the **only** reader in the whole app is a billing marketing bullet `platform/apps/cloud/app/dashboard/billing/page.tsx:95` rendering `featureClientWorkspaces` = "Separate client workspaces" `platform/apps/cloud/lib/i18n/messages/billing.ts:53`. `rg clientWorkspaces` finds no code path that branches on it.
- Description: `PlanDefinition.clientWorkspaces` is a dead entitlement. The Agency plan (EUR 149/mo, `plans.ts:37`) and its description "...client workspaces..." (`billing.ts:34`) are purchasable via live Stripe checkout (`billing/actions.ts:13`), yet nothing in the product creates, isolates, or scopes a "client workspace."
- Impact: a paying Agency customer is charged for a feature that does not exist; this is a contractual/representation risk, not merely a missing feature — the code (billing UI) claims to provide it.
- Recommendation: either implement client-scoped sub-workspaces or remove the flag, the bullet, and the plan copy until it exists.

### I2-02 — No agency/client hierarchy exists; the data model is a flat single-tenant org
- Severity: **GAP** · Classification: **VERIFIED_CODE**
- Evidence: `handle_new_user` creates exactly one org + one `owner` membership per signup `platform/supabase/migrations/20260817171039_cloud_initial_schema.sql:220-243`; `organization_ad_accounts` has **no** client/group column — PK is `(organization_id, provider, account_id)` `...20260828120000_...:32-45`; no org-creation route exists (grep, exit 0, trigger-only).
- Description: There is no "client" entity. All of an agency's advertiser accounts live flat inside one organization, keyed only by provider + account_id, with no grouping, labeling, or ownership-by-client.
- Impact: an agency cannot represent "Client A vs Client B" at all; everything (accounts, findings, audit, members, policy, billing) is pooled into one undifferentiated tenant.
- Recommendation: introduce a first-class client/sub-account grouping (e.g. a `clients` table with account membership) before marketing an agency tier.

### I2-03 — Organization "switching" has no UI and silently strands multi-org users
- Severity: **P2** · Classification: **VERIFIED_CODE**
- Evidence: `sessionPrincipal(requestedOrganizationId)` only *validates* the requested org against a membership (`auth.ts:14`, `repository.ts:30-48`); **every** dashboard caller passes the user's own `tenant.organizationId` (grep of `app/`), and the shell renders a single static `tenant.organizationName` with no switcher `components/shell.tsx:27`. `requireDashboardTenant` always picks `order by membership.created_at asc limit 1` `lib/cloud/dashboard.ts` (the oldest membership).
- Description: The parameter plumbing for multi-org exists but there is no way to be in, or switch to, a second org through product flows. Worse, a user who owns org A and is later invited to org B is permanently pinned to org A by the `created_at asc limit 1` tenant resolver and can never reach org B in the UI.
- Impact: an agency owner cannot operate more than one organization; invited collaborators who also own their own org become unable to reach the org they were invited to.
- Recommendation: add an org-switcher UI that threads a chosen org id through `requestedOrganizationId`, and let the tenant resolver honor a persisted "active org" instead of the oldest membership.

### I2-04 — Per-client reporting is impossible; the engine is a single shared instance for all tenants
- Severity: **P1** · Classification: **VERIFIED_CODE** (cross-tenant exposure: **INFERRED**, deployment-dependent)
- Evidence: the engine client is built from one deployment-wide `MARKTING_ENGINE_URL` + `MARKTING_ENGINE_TOKEN` `platform/apps/cloud/lib/markting/env.ts:10-12` with no org parameter `lib/markting/assistant.ts:12-14`; `runReport(cadence, end)` and `listReports()` carry **no** org/account scope `lib/markting/engine-client.ts:166-172`; the reports route calls `engineClient().listReports()` directly and is **not** demo-gated `app/api/reports/engine/route.ts:21-23`.
- Description: Reports are produced by, and listed from, one engine instance shared by the entire cloud deployment. A tenant cannot request a report for a specific account/client, and `GET /api/reports/engine` returns whatever reports that single engine holds regardless of which org asks. Only membership of *an* org is checked (`sessionPrincipal`), not ownership of the reports.
- Impact: (1) an agency cannot generate or deliver a report scoped to one client — the core agency deliverable; (2) if a real engine is pointed at a multi-tenant deployment, every org sees every other org's report runs and can stream their files via `fetchReportFile` — a cross-tenant leak. Severity would be P0 if confirmed in a shared-engine production deployment.
- Recommendation: scope the engine per org/client (token or tenant id per call) and filter `listReports`/`fetchReportFile` by the caller's org; add a test asserting an org cannot read another org's report run.

### I2-05 — No white-label, branding, or custom-domain capability
- Severity: **GAP** · Classification: **VERIFIED_CODE**
- Evidence: `rg -ni "white.?label|branding|logo|custom domain|subdomain"` over `platform/apps/cloud` returns only MCP-OAuth client registration and provider SVG logo files; nothing configures agency branding, a client-facing portal, or custom domains.
- Description: There is no way to put an agency's logo/brand on reports or a client portal, nor any client-facing surface at all (reports download as engine HTML/PDF with no tenant branding).
- Impact: an agency cannot present deliverables under its own brand — table-stakes for reselling the product to clients.
- Recommendation: add org-level branding (logo, colors, domain) applied to reports and any client-facing view.

### I2-06 — "Approvals" are an internal maker-checker gate, not client sign-off
- Severity: **GAP** · Classification: **VERIFIED_CODE**
- Evidence: `app/api/approvals/[id]/apply/route.ts:15-23` — only `owner`/`admin` may apply; the requester cannot self-approve unless `MARKTING_ALLOW_SELF_APPROVAL=true`. The two-step preview→apply is internal to the org; no advertiser/client is a participant.
- Description: The approval workflow is a safety gate between the person who proposes a change and the owner/admin who applies it. There is no mechanism to route a proposed change to the end client (the advertiser) for authorization before it executes.
- Impact: an agency cannot obtain documented client approval for budget/campaign changes before applying them — a common agency compliance requirement.
- Recommendation: if client approvals are a selling point, add an external approval actor/role and an approval-request surface; otherwise do not describe this as a client approval feature.

### I2-07 — Member access is organization-wide; no per-client access scoping
- Severity: **P2** · Classification: **VERIFIED_CODE**
- Evidence: ad-account / findings RLS grants access to **any** member of the org `...20260828120000_...:102-115`; invites add users straight into the single org `lib/cloud/tenant-admin.ts:65-70`; roles are org-global (`owner/admin/member/viewer`) with no account dimension (grep for per-account ACL, exit 0, none).
- Description: Every invited member sees every account, finding, and audit entry in the org. There is no way to restrict an account manager (or a client's own staff) to only that client's accounts.
- Impact: an agency cannot give a client self-service visibility, nor confine a junior buyer to their book of business, without exposing all clients' data; the Agency plan's 15-member limit (`plans.ts:37`) all share full visibility.
- Recommendation: add per-account (per-client) role assignments and enforce them in RLS and the bridge runtime.

## What a world-class system would need (gaps, concrete)
- A `clients`/sub-account entity with accounts assigned to clients; all reads (dashboard, reports, findings, audit) filterable and RLS-scoped by client.
- Per-account role assignments so members (or client users) see only their accounts; enforced in Postgres RLS and in `createBridgeRuntime`.
- Org/client-scoped reporting: engine calls carry a tenant id; `listReports`/`fetchReportFile` filtered by org; per-client scheduled report cadence.
- White-label: org branding (logo/colors/domain) applied to a client-facing report/portal view.
- Client-approval actor and surface, with an audit trail of who (including external client) authorized each applied change.
- Org switcher + "active org" persistence; an in-product path to create or be granted additional organizations.
- Agency with 50 accounts today: blocked — Agency caps at 40 active accounts (`plans.ts:37`, enforced via `setOrganizationAdAccountEnabled`/`maxActiveAccounts`), forcing Enterprise; even then all 50 are pooled in one flat org with no client separation, one shared report engine, org-wide member visibility, and no white-label.

## Disagreements / claims in docs that the code contradicts
- Billing UI/plan copy claims Agency/Enterprise provide "Separate client workspaces" (`billing/page.tsx:95`, `billing.ts:34,53`). The code contains no implementation of client workspaces (I2-01). This is an advertised paid feature the code does not deliver.
- The word "workspace" throughout the UI (e.g. "the workspace owner", `billing/actions.ts:9`) denotes the single organization, not a per-client workspace — reinforcing the gap between the "client workspaces" marketing and the flat single-org reality.
