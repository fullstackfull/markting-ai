## Findings

### C12-01 — No end-to-end trace/correlation id across cloud → engine
- Severity: P2 · Classification: VERIFIED_CODE
- Evidence: `platform/apps/cloud/lib/markting/engine-client.ts:84-99` (request headers are only `authorization`, `content-type`, `accept`; no `x-request-id`/`traceparent`); `engine/src/paid_media_agent/surfaces/api/app.py:39-168` (no request-id middleware, no access logging, `/health:80-89` exposes no trace/version correlation); `surfaces/runner.py:86-89` (`RunnableConfig` carries only `configurable={thread_id, caller_ref}`).
- Description: A single user action spans Next.js route → `EngineClient.sendMessage` → FastAPI → LangGraph. Nothing generates or forwards a correlation id, so there is no key to join a browser request, an engine turn, a tool call, and an audit row.
- Impact: Incidents cannot be reconstructed per request; a slow or failed turn cannot be tied to the user/org that triggered it or to the writes it produced.
- Recommendation: Mint a request id in the cloud route, forward it as a header, bind it in engine logs and into `RunnableConfig.metadata`, and stamp it onto `audit_events`/`markting_engine_proposals`.

### C12-02 — LangSmith tracing is never configured; the only tracing call disables it
- Severity: P2 · Classification: VERIFIED_CODE
- Evidence: `engine/src/paid_media_agent/testing/demo_script.py:207-210` (`with tracing_context(enabled=False)` — the single `langsmith` runtime use, and it turns tracing OFF for the fixture demo); grep for `LANGSMITH_TRACING|LANGCHAIN_TRACING|LANGSMITH_PROJECT|OTEL` over all source/config/docs => exit 1 (no matches). The engine knows the `langsmith:` prefix only as a model gateway (`assembly.py:154`), not as tracing.
- Description: In the self-hosted `serve` path there is no code that enables LangSmith/OTel tracing, sets a project, or attaches run metadata. Even if an operator sets `LANGSMITH_API_KEY` + `LANGSMITH_TRACING=true` manually, `RunnableConfig` has no `metadata`/`tags`/`run_name` (C12-01), so traces would not be attributable to org/user/thread.
- Impact: Per-request model/tool/latency traces are not captured by default; the "inspect your agent in LangSmith" story (`engine/README.md:141`, `OPERATIONS.md:62-68`) applies only to the managed-MDA deployment, not to the compose/self-hosted stack this product ships.
- Recommendation: Decide one backend (LangSmith or OTel), enable it in `serve`, and bind org/user/thread/request-id as run metadata and tags.

### C12-03 — No token or cost accounting anywhere in the engine
- Severity: P2 · Classification: VERIFIED_CODE
- Evidence: grep `usage_metadata|input_tokens|output_tokens|total_tokens|token_usage` over `engine/src` => exit 1; `RunOutcome` (`surfaces/runner.py:26-32`) exposes `text/interrupted/proposal/receipt` only — no tokens, no latency; the sole latency measurement is the doctor "test model" action (`admin/actions.py:360,380-388`), not the serving path.
- Description: The model-call path records nothing about tokens spent, cost, or turn latency. `docs/TODO.md:8` lists per-organization engine metering as an open question — the code confirms it is absent.
- Impact: No per-request/per-org cost attribution, no budget enforcement, no latency SLOs; runaway or expensive runs are invisible. Capability: cost observability MOCK/MISSING.
- Recommendation: Capture `response.usage_metadata` per model call, convert to cost via a price table, and emit tokens+cost+latency per turn keyed by org/user/request-id.

### C12-04 — Host read audit is in-memory, capped, and consumed only by the demo
- Severity: P2 · Classification: VERIFIED_CODE
- Evidence: `engine/src/paid_media_agent/tools/reads.py:137` (`self.audit: list[...] = []`), `:65-66` ("Reads kept in the in-memory audit trail; the demo prints it, long-running servers do not"), `:210-219` (ring buffer of last `AUDIT_LIMIT=500`, fields `tool/account_alias/catalog_revision/policy/artifact_id` only — no timestamp, no caller, no row counts, no window); only reader is `testing/demo_script.py:250`.
- Description: Every provider read the model performs is appended to a process-local list that no server endpoint persists, logs, or exposes, and that is silently truncated at 500. Which account/tool/date-window a model actually read on behalf of a request is therefore not recoverable server-side.
- Impact: No durable record of data access per request/tenant — a gap for debugging, abuse investigation, and data-access compliance.
- Recommendation: Persist read-audit rows (with timestamp, caller_ref, thread_id, request-id, window, row_count, artifact_id) to durable storage, or emit them as structured log events.

### C12-05 — Near-zero operational logging in the engine; no structured/request logging
- Severity: P2 · Classification: VERIFIED_CODE
- Evidence: `engine/src/paid_media_agent/cli.py:23-26` (`_configure_logging` sets level + `"%(levelname)s %(name)s: %(message)s"` only — no JSON, no handler, no request context); the entire engine has 5 log sites: `middleware/authorization.py:82,89` (denied tool calls), `surfaces/slack/delivery.py` (two failure logs), `tools/pipeboard.py:119` (catalog load failure). The serving path (`surfaces/api/app.py`, `runner.py`, graph, `ReadDispatcher.execute`, write execution) logs nothing on success or failure.
- Description: There is no per-turn log line recording model spec, selection strategy, tool calls, latency, caller, or failure cause. Logs are plain text, so they cannot be indexed by org/request-id even if emitted.
- Impact: Production turns are effectively opaque; a failed or slow run leaves no trace beyond whatever the client surfaced. Combined with C12-01/C12-02, the self-hosted path has no observability floor.
- Recommendation: Emit structured (JSON) per-turn logs bound to request-id/org/user/thread covering model, strategy, tool-call outcomes, latency, and sanitized errors.

### C12-06 — Cloud chat turns write no usage/audit record; `audit_events` is a change-log, not a request log
- Severity: P3 · Classification: VERIFIED_CODE
- Evidence: `platform/apps/cloud/lib/markting/assistant.ts:30-79` — `runAssistantTurn` calls `recordAudit`/`recordEngineProposal` ONLY inside the `proposal.state === 'awaiting_approval'` branch; a plain question→answer turn records nothing. `audit_events` events are the adport set (`validated/applied/rejected/note/connected/...`, `20260817171039_cloud_initial_schema.sql:152-160`), all tied to connections or the proposal lifecycle.
- Description: "User X in org Y asked prompt P and got answer A at time T" is not recorded on the cloud side; only the engine's `markting_threads`/thread messages hold it, and those carry no model/token/latency. The audit log answers "what changed", not "what was requested or spent".
- Impact: No cloud-side usage/interaction trail for support, analytics, or abuse review of read-only conversations.
- Recommendation: Record a lightweight per-turn usage row (org, user, thread, request-id, latency, tokens from the engine) distinct from the change-audit.

### C12-07 — Write-outcome provenance is real and tenant-scoped, but the `expired` outcome is never written
- Severity: P3 (GAP) · Classification: VERIFIED_CODE
- Evidence: Provenance row exists and is rich (`20261002000000_markting_bridge.sql:40-60`: `proposal_id, revision, thread_id, engine_platform/account_ref/tool/target_ref, payload_digest, proposal jsonb, translation jsonb, pending_operation_id, status, created_by`). Outcome updated by `markPendingOutcome` on apply (`app/api/approvals/[id]/apply/route.ts:29`) and reject (`.../reject/route.ts`), status enum includes `'expired'`, but no caller ever passes `'expired'` (grep); `PostgresPendingStore.sweep` (`lib/cloud/repository.ts:420-425`) only sets `pending_operations.consumed_at` and is itself called nowhere outside tests.
- Description: The proposal→pending→approval→applied/rejected chain is genuinely traceable and RLS-scoped per org, with an engine-side append-only `history` ("proposed/revised/approved/rejected by <ref> @ ts", `domain/proposals.py:208` persisted in `pma_proposals.record`). But expired previews leave `markting_engine_proposals.status = 'pending'` indefinitely, and no sweep job runs.
- Impact: Outcome chain is accurate for explicit apply/reject but incomplete for expiry; dashboards/metrics over proposal outcomes will over-count "pending".
- Recommendation: Run the pending sweep on a schedule and have it set the provenance row to `expired`; verify a job invokes `sweep`.

### C12-08 — Redaction covers tool output and errors but not logs, prompts, or stored artifacts
- Severity: P3 · Classification: VERIFIED_CODE
- Evidence: `middleware/redaction.py:49-87` redacts only `ToolMessage` content and tool exceptions before they reach the model; `sanitize_exception` (`:42-46`) is applied at tool/report boundaries (`tools/reports.py:87`, `tools/writes.py` etc.). It is not applied to the stdlib logging configured in `cli.py:23-26`, nor to persisted artifacts/thread messages. Patterns are credential-shaped only (`:16-28`) — no PII.
- Description: If request/trace logging is added later (the fix for C12-01/02/05), prompts and tool results logged there would bypass this middleware, which only sits on the model-facing path.
- Impact: Observability work risks logging secrets/PII unless redaction is explicitly placed on the logging/trace sinks.
- Recommendation: Route any new structured logs/traces through `redact()` and extend patterns to PII before enabling prompt/response capture.

## What a world-class system would need (gaps, concrete)
1. One correlation id minted at the cloud edge, forwarded to the engine, bound into logs + `RunnableConfig.metadata` + every audit/provenance row.
2. Per-turn telemetry record: request-id, org, user, thread, model spec, selection strategy, tool calls (name/args-hash/latency/status), input/output tokens, computed cost, total latency, failure class.
3. Enabled tracing backend (LangSmith or OTel) in `serve`, with runs tagged by org/user/thread/request-id, redaction on the sink.
4. Durable, queryable read-audit (replacing the demo-only in-memory list) for data-access compliance.
5. A complete outcome state machine (apply/reject/expire) driven by a scheduled sweep, so provenance never sticks at `pending`.
6. A join view: prompt → engine turn → tool reads → proposal → pending op → approval → provider apply → verified receipt, all addressable by one id.

## Disagreements / claims in docs that the code contradicts
- `docs/ARCHITECTURE.md:776-777` and `engine/.env.example:31-33,91-93` present `LANGSMITH_API_KEY` as serving "tracing"; the serving code never enables tracing and the only `langsmith.tracing_context` call DISABLES it (`demo_script.py:207-210`). Tracing in this repo is aspirational for the self-hosted path.
- `engine/README.md:141` / `OPERATIONS.md:62-68` ("open the printed LangSmith URL to inspect your agent") hold for managed MDA only; the compose/self-hosted stack has no equivalent observability wired.
- `markting_engine_proposals.status` enum advertises `expired` (`20261002000000_markting_bridge.sql:54`) but no code path writes it and the pending sweep has no scheduler.
