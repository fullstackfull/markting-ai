## Findings

### C2-01 — Only Anthropic, OpenAI and OpenAI-compatible endpoints can work in the shipped engine container
- Severity: P2 · Classification: VERIFIED_CODE (+ VERIFIED_RUNTIME for the dev venv)
- Evidence: `engine/Dockerfile:13` (`uv sync --frozen --no-dev --extra self-host --extra slack --extra reports`); `engine/pyproject.toml:38-39` (core: `langchain-anthropic`, `langchain-openai`) vs `:52-53,63-67` (google/groq/xai/mistral/deepseek are optional extras); `engine/uv.lock` `[package.optional-dependencies]` for `paid-media-agent`; `docker-compose.yml:36-37,41` (the compose `engine` service builds that Dockerfile and runs `serve_demo.py` inside it); `engine/src/paid_media_agent/admin/model_presets.py:45-99` advertises Google, Groq, xAI, Mistral, DeepSeek; `engine/.env.example:19-25` lists their keys.
- Description: the image never installs the provider extras, so `PAID_MEDIA_MODEL=google_genai:…|groq:…|xai:…|mistralai:…|deepseek:…` would fail at `init_chat_model` import time inside the container, while the same specs work in the dev venv (command 1). `doctor.py:60-70` and `actions.model_test` (`admin/actions.py:336-350`) would report "install the extra", but the compose stack offers no hook to do so. The root `.env.example:54-56` and `README.md:50,119` only promise Anthropic/OpenAI, so the stack's own docs are consistent; the engine's preset list and `.env.example` are not.
- Impact: provider breadth is smaller than the configuration surface suggests; an operator choosing a cheaper/regional provider from the presets gets a crash loop in live mode.
- Recommendation: either extend the image build (a markting-owned Dockerfile layered on the upstream one, outside `engine/`) with the extras the product intends to support, or trim the advertised providers in the markting docs to what the image can run. Add a boot-time import check in `serve_demo.py` live mode (see C2-06).

### C2-02 — No per-organization identity, quota, or cost accounting reaches the model layer
- Severity: P2 (serious financial exposure once `MARKTING_ENGINE_MODE=live`) · Classification: VERIFIED_CODE
- Evidence: one shared bearer for every org: `docker-compose.yml:49` (`PAID_MEDIA_API_TOKENS=<token>:adport-bridge`), `platform/apps/cloud/lib/markting/assistant.ts:12-14,40-42`; one process-wide model: `engine/src/paid_media_agent/config.py:113` and `assembly.py:189-195` (resolved once at assembly, never per request); no usage capture: command 5 (no `usage_metadata` anywhere), `docs/TODO.md:8` ("whether engine usage … is metered per organization" is open); request-count rate limit only: `platform/apps/cloud/app/api/assistant/messages/route.ts:13` → `lib/cloud/repository.ts:355` (`limit = 120` per 60 s per org+user); per-run bound only: `config.py:120` (`PAID_MEDIA_MAX_MODEL_CALLS=40`); no engine-side concurrency bound on chat (only the report route takes a lock, `services/engine-demo/serve_demo.py:324`).
- Description: a single signed-in user may trigger up to 120 engine turns per minute, each up to 40 model calls, each retried up to 3× (C2-03), against one shared provider key with no spend ceiling, no per-org allowance and no attribution. Org identity is recoverable only from the thread id prefix (`platform/apps/cloud/lib/markting/repository.ts:12-13`: `org_<id>__u_<id>__…`), which nothing in the engine reads.
- Impact: a noisy or malicious tenant can burn the whole model budget; the product cannot bill or cap model usage per plan; incident forensics cannot say which org caused a spend spike. This is a GAP for metering but a P2 defect for the uncapped shared key in live mode.
- Recommendation: before enabling live mode for more than one trusted org, add (a) a per-org token budget enforced in the cloud route from a `markting_model_usage` ledger, (b) a usage callback in `serve_demo.py` (markting-owned, so no `engine/` edit) that reads `usage_metadata` from AI messages and attributes it to the org parsed from `thread_id`, (c) a global concurrency semaphore on `/threads/*/messages` in the host. See options below for where quotas should live.

### C2-03 — Timeout budgets are inconsistent between engine and cloud, and a run has no deadline
- Severity: P2 · Classification: VERIFIED_CODE
- Evidence: SDK `timeout=120, max_retries=2` on every provider client (`assembly.py:166`); middleware order `ModelRetry(2, on_failure="continue") → ModelTimeout(120 s) → ModelCallLimit(40)` (`assembly.py:239-245`; first entry is outermost); `middleware/timeout.py:30-38` bounds each attempt, `:24-28` is a no-op on the sync path; retry backoff defaults `initial_delay=1.0, backoff_factor=2.0, jitter` (`.venv/.../langchain/agents/middleware/model_retry.py:116-124`); cloud default abort 240 s (`platform/apps/cloud/lib/markting/env.ts:18`, `engine-client.ts:73`), route `maxDuration = 300` (`app/api/assistant/messages/route.ts:7`); synchronous `graph.ainvoke` with no run-level deadline (`engine/src/paid_media_agent/surfaces/runner.py:150-154`); `docs/ARCHITECTURE.md:511-514` already notes "no fixed upper bound on a request's duration".
- Description: one logical model step may take 3 × 120 s + backoff (≈ 6 min) before the retry middleware gives up; a run allows 40 such steps plus tool time. The cloud aborts the HTTP call at 240 s, but aborting a fetch does not cancel the engine's run, which keeps consuming model calls and may leave a proposal awaiting approval that the user never sees.
- Impact: wasted spend, orphaned threads/proposals, and a user-facing timeout error while the engine is still working. In an Arabic-first chat UI this surfaces as an unexplained failure.
- Recommendation: define one budget: engine per-run deadline (e.g. `asyncio.wait_for` around `ainvoke` in the host) < cloud `MARKTING_ENGINE_TIMEOUT_MS` < route `maxDuration`; lower per-call retry depth when the cloud deadline is short; return a "still working" state or move to the streaming surface the runner already has (`runner.py:155+`), which `docs/TODO.md:31` lists as polish.

### C2-04 — `PAID_MEDIA_MODEL_API_KEY_ENV` pointing at an unset variable silently uses a different key
- Severity: P3 · Classification: VERIFIED_RUNTIME
- Evidence: `assembly.py:169-170` (`if api_key_env and os.environ.get(api_key_env): kwargs["api_key"] = …`); command 1 ("api_key_env unset -> used key: fallback" — the Anthropic default key was used); `admin/actions.py:353-360` catches this only in the console's `model_test`, not in `serve_demo.py` live boot.
- Description: a typo or a missing secret in the compose `.env` degrades to whatever default key the provider SDK finds, so traffic that was meant for an OpenAI-compatible endpoint's own key (Moonshot, OpenRouter, a future self-hosted gateway) goes out with the wrong credential, or a gateway deployment quietly bills a direct provider account.
- Impact: misattributed spend and bypassed gateway controls, without any log line.
- Recommendation: fail fast when `api_key_env` is set but empty (host-side check in `serve_demo.py` live mode, or upstream PR).

### C2-05 — The tool-selector model never receives the custom key or base URL
- Severity: P3 · Classification: VERIFIED_CODE
- Evidence: `assembly.py:216-221` resolves `PAID_MEDIA_TOOL_SELECTOR_MODEL` via `resolve_model(selector_config, timeout_seconds=…)` with neither `api_key_env` nor `base_url`; `config.py:30-31,48-52` only attaches `base_url` to the main spec; `admin/envfile.py:41-46` documents the selector as "cheaper model for the portable tool selector".
- Description: when the main model is on an OpenAI-compatible endpoint (`openai:… + PAID_MEDIA_MODEL_BASE_URL + PAID_MEDIA_MODEL_API_KEY_ENV`), the cheaper selector cannot be placed on the same endpoint; it can only be a provider with a default key env. The `langsmith:` path works because the gateway key is read from the environment by langchain itself (`.venv/.../langchain/chat_models/base.py:27-38`).
- Impact: limits the "cheap selector + strong main model" cost pattern to gateway or direct-provider setups; relevant to Option B below.
- Recommendation: give the selector its own `base_url`/`api_key_env` settings, or route both through one gateway (Option B/C) where the env key applies to both.

### C2-06 — Live-mode boot has no model readiness check; failure mode depends on the provider
- Severity: P3 · Classification: VERIFIED_RUNTIME
- Evidence: `services/engine-demo/serve_demo.py:234-237` (`model = build_demo_model(...) if mode == "demo" else None` → `resolve_model` at `assembly.py:190-195`); command 1 (`openai:` with no key → eager `OpenAIError`; `anthropic:` with no key → lazy construction); `/health` reports only selection strategy and persistence (`engine/src/paid_media_agent/surfaces/api/app.py:80-89`); retry middleware converts exhausted failures into an `AIMessage("Model call failed after N attempts with …")` (`.venv/.../model_retry.py:179-195`) that `runner.py` returns as ordinary `text` with HTTP 200.
- Description: with a missing/invalid Anthropic key the container is "healthy", the cloud's health probe passes, and every Assistant turn returns an English error sentence as if it were an answer; with a missing OpenAI key the container crash-loops at boot instead. Neither is surfaced as a model-configuration failure. `docs/TODO.md:26` and `docs/PHASE1-REPORT.md:37` confirm live mode was never exercised.
- Impact: silent degradation in production; no alert path; unlocalized provider error text shown to Arabic users.
- Recommendation: in live mode, run a one-token smoke call (or at least `model_key_env` presence + import check) during `build_app_async`, expose `model_ready` in `/markting/info`, and map `Model call failed…` AIMessages to a structured error the cloud can localize.

### C2-07 — "No implicit gateway" is contradicted by the installed provider SDKs honouring `LANGSMITH_GATEWAY`
- Severity: P3 (operational surprise / unexpected data egress path) · Classification: VERIFIED_CODE
- Evidence: claims: `config.py:24` ("A gateway is used only via an explicit `langsmith:` spec"), `assembly.py:154` ("No implicit gateway"), `engine/docs/architecture/README.md:18`; behaviour: `.venv/.../langchain_anthropic/chat_models.py:1426-1435` and `.venv/.../langchain_openai/chat_models/base.py:1321-1327` call the gateway resolver; `.venv/.../langchain_core/utils/_gateway.py:96-103,150-158` (if `LANGSMITH_GATEWAY` is truthy and no explicit base URL is set, the base URL becomes the LangSmith gateway and the key preference flips to `LANGSMITH_GATEWAY_API_KEY`/`LANGSMITH_API_KEY`); `engine/src/paid_media_agent/doctor.py:106-113` acknowledges exactly this ("provider SDKs route through LangSmith").
- Description: a stray `LANGSMITH_GATEWAY=true` in the compose `.env` silently sends `anthropic:`/`openai:` traffic (prompts, fixture data, user text) through a third-party gateway. `plan_selection` would still choose provider-native tool search because `config.base_url is None` (`tool_selection.py:160`), although the request now goes through a proxy — the very case the code says it does not assume (`tool_selection.py:166-167`).
- Impact: docs mislead operators about egress; residency and vendor exposure are decided by an env var the markting docs never mention.
- Recommendation: either pin `LANGSMITH_GATEWAY=` empty in the compose environment and document it, or embrace the gateway explicitly (Option C) and make `plan_selection` read the resolved base URL.

### C2-08 — Model keys and unrelated secrets are shared across both containers; model keys are not in the redaction list
- Severity: P3 · Classification: VERIFIED_CODE
- Evidence: `docker-compose.yml:16` and `:40` (`env_file: .env` for both `cloud` and `engine`); `.env.example:54-56` (model keys live in that same file); `assembly.py:293-306` (`_secret_values` excludes the model key); `middleware/redaction.py:16-28` (regexes cover `sk-`, `sk-ant-`, `AIza`, Slack, Pipeboard; not Groq `gsk_`, xAI, Mistral, DeepSeek or Moonshot key shapes).
- Description: in live mode the Next.js container receives `ANTHROPIC_API_KEY`/`OPENAI_API_KEY` it never uses, and the engine receives Supabase/Stripe/adport encryption secrets it never uses. Tool results that echo an environment (e.g. a future diagnostics tool) would not have a non-OpenAI-shaped model key redacted.
- Impact: larger blast radius for either container; low likelihood of key echo today because no tool reads the environment.
- Recommendation: split env files per service in compose; add the resolved model key (from `model_key_env`) to the redaction secrets in the host.

### C2-09 — `.env.example` and ARCHITECTURE.md give an unnecessary instruction for the gateway key
- Severity: P3 · Classification: VERIFIED_CODE
- Evidence: `engine/.env.example:6-8` and `admin/envfile.py:283-288` ("point `PAID_MEDIA_MODEL_API_KEY_ENV` at `LANGSMITH_GATEWAY_API_KEY`"); `docs/ARCHITECTURE.md:777` ("read only via `PAID_MEDIA_MODEL_API_KEY_ENV`"); actual behaviour `.venv/.../langchain/chat_models/base.py:27-38` (`_init_langsmith` reads `LANGSMITH_GATEWAY_API_KEY` first, then `LANGSMITH_API_KEY`).
- Description: the installed langchain already prefers the gateway key; the extra setting is redundant and, per C2-04, a typo in it silently changes the key used.
- Recommendation: correct the markting docs; leave upstream text as-is or raise it upstream.

### C2-10 — Model identifiers in presets and the capability registry are unverifiable here
- Severity: P3 · Classification: NOT_VERIFIED
- Evidence: `admin/model_presets.py:38,49,71` (`openai:gpt-5.5`, `google_genai:gemini-3-flash`, `xai:grok-4`), `middleware/tool_selection.py:91-115` (`verified=True` entries such as `anthropic:claude-opus-5`, `langsmith:moonshotai/kimi-k3`), `tool_selection.py:41-42` ("True only for entries checked against current provider documentation").
- Description: no test or runtime check in this repository confirms that these ids exist or that the named native tool-search capability holds; "verified" is an upstream assertion. The registry is exact-match (`tool_selection.py:135-137`), so any id not listed silently drops to the weaker portable selector with a `warn` only in `doctor` (`doctor.py:71-77`).
- Recommendation: treat the registry as a claim; add a live `paid-media-agent test model` run to the release checklist and log the selection strategy at boot in the host.

### C2-11 — `litellm:` parses but cannot run; `litellm` is absent from the lock and the import map
- Severity: GAP (informational for the architecture options) · Classification: VERIFIED_RUNTIME
- Evidence: command 1 (`'litellm:gpt-4o' parses to litellm:gpt-4o`; `langchain_litellm installed: False`); `.venv/.../langchain/chat_models/base.py:86` (`"litellm": ("langchain_litellm", "ChatLiteLLM", _call)`); `admin/model_presets.py:161-171` and `tool_selection.py:127-132` have no `litellm` entry, so `doctor`/`model_test` cannot explain the failure.

## Architecture options (analysis only — nothing implemented)

Constraints that shape every option, all VERIFIED_CODE: the engine resolves one model per process at assembly (`assembly.py:189-195`); the only per-request identity the engine sees is `thread_id` with the org id embedded by the cloud (`repository.ts:12-13`) and a single `caller_ref` (`docker-compose.yml:49`); any `PAID_MEDIA_MODEL_BASE_URL` switches tool selection to the portable LLM selector (`tool_selection.py:166-167`), which costs one extra model call per turn and loses provider-native deferred tool search; `engine/` must stay unmodified (`UPSTREAM.md:66-68`), so markting-owned logic belongs in `services/engine-demo/serve_demo.py` or a new sidecar.

### Option A — Harden the in-process LangChain routing (no new infrastructure)
What: keep `init_chat_model` direct providers. In `serve_demo.py` live mode add: fail-fast key/import/smoke check at boot; a model **allowlist** env (`MARKTING_ALLOWED_MODELS`) checked against `PAID_MEDIA_MODEL`; a per-run deadline aligned with `MARKTING_ENGINE_TIMEOUT_MS`; a usage callback (`usage_metadata` on AI messages) writing `org_id, model, input_tokens, output_tokens, latency` to the engine Postgres, attributed from the `thread_id` prefix; a `with_fallbacks([...])` chain for a secondary provider; `LANGSMITH_TRACING` or an OpenTelemetry callback for tracing; a process-wide semaphore on chat turns. Quotas stay in the cloud route (plan-aware, reading the usage ledger).
- Routing/fallback: static primary + fallback chain; no load balancing. Fallback across providers changes the tool-search strategy mid-run only if the fallback also has native search; keep both in the same family or accept portable selection.
- Cost controls: budget checks happen in the cloud before the turn; the engine can only stop after the fact (per-call cap 40).
- Pros: smallest change set, keeps native tool search for Anthropic/OpenAI, no extra hop, no new secrets.
- Cons: every control is bespoke Python in the host; per-org keys/virtual keys impossible without one engine process per org; caching and circuit breaking are DIY; metrics live in two databases.
- Fits when: one or two trusted orgs, Anthropic/OpenAI only, near-term launch.

### Option B — Self-hosted central AI gateway (LiteLLM proxy or equivalent OpenAI-compatible router) as a compose sidecar
What: run a gateway service on the compose network; set `PAID_MEDIA_MODEL=openai:<gateway-alias>`, `PAID_MEDIA_MODEL_BASE_URL=http://ai-gateway:4000/v1`, `PAID_MEDIA_MODEL_API_KEY_ENV=MARKTING_GATEWAY_KEY`. The gateway owns provider keys, model aliases, allowlists, retries, fallback groups, circuit breaking, spend logs, budgets per virtual key, response caching and OTel/Langfuse tracing; the engine container holds **no** vendor key.
- Per-org quotas: a gateway enforces budgets per **virtual key**, but the engine sends one key for everyone (single process-wide model, `assembly.py:189-195`). Two ways out, both markting-side: (1) keep one engine key and have the host stamp an org tag into the request (`user`/metadata field via a `RunnableConfig`/callback in `serve_demo.py`), using gateway "team/tag" budgets; or (2) run the cloud-side quota from the gateway's spend log. Neither needs `engine/` edits; both need verification against the chosen gateway's API (NOT_VERIFIED here).
- Tool selection: `base_url` set → portable selector for all models (`tool_selection.py:166-167`): one extra cheap call per turn and loss of Anthropic/OpenAI native tool search. The selector itself cannot be pointed at the gateway with its own key unless it is the same provider prefix (C2-05) — with Option B it is (`openai:`), so `PAID_MEDIA_TOOL_SELECTOR_MODEL=openai:<cheap-alias>` works through the same base URL only if the gateway key is readable as `OPENAI_API_KEY`-style default or the env is set accordingly; confirm before relying on it.
- API shape: `openai:` without `use_responses_api` uses Chat Completions; gateways translate to Anthropic etc. Structured output/strict schema quirks already seen with the LangSmith gateway (`tool_selection.py:221-228`) may recur; the lenient selector wrapper is only applied for `provider == "langsmith"` (`tool_selection.py:265-269`).
- Pros: one place for keys, routing, fallback, budgets, caching, tracing; vendor-neutral; no provider extras needed in the engine image (C2-01 disappears); data stays in your network until the gateway egresses.
- Cons: new stateful service (+DB for spend logs), new secrets, an extra hop and failure point, portable-selector cost, Responses-API features lost, LiteLLM licensing/ops knowledge required.
- Fits when: several orgs, multiple providers (including Arabic-capable or regional models), need for per-org budgets and auditability before billing.

### Option C — Managed gateway: LangSmith LLM Gateway (`langsmith:provider/model`, the upstream "recommended" preset)
What: one `LANGSMITH_API_KEY`, every provider, traced. Already supported end to end (`config.py:43-44`, `model_presets.py:11-21`, `tool_selection.py:72-80,110-114,265-269`, `admin/model_catalog.py:19`), with tests (`tests/unit/test_lenient_selector.py`, `tests/contract/test_selection_matrix.py::test_configured_gateway_selector_is_used`, command 2).
- Routing/fallback/budgets/caching: whatever the service provides; none of it is verifiable from this repository (NOT_VERIFIED). Per-org attribution again depends on the engine passing an org tag, which it does not today.
- Pros: zero infrastructure, tracing comes with it, broadest model list without image changes.
- Cons: third-party dependency on the critical path; data residency/egress question for a KSA-focused product; portable selector path (no native tool search, `_GATEWAY native_tool_search=False`); vendor pricing; the implicit `LANGSMITH_GATEWAY` behaviour (C2-07) must be managed deliberately.

### Recommendation (architect's opinion, INFERRED from the evidence above)
Ship Option A's safety items regardless (boot readiness check, allowlist, run deadline, usage ledger keyed by org from `thread_id`, semaphore) because they are prerequisites for any option and live entirely in markting-owned code. Choose Option B when live mode goes multi-tenant: it is the only option that keeps vendor keys out of both application containers and gives per-key budgets and fallback without further engine changes; accept the portable-selector cost and measure it. Keep Option C as the fast path for internal evaluation of many models, not for tenant traffic, unless residency is cleared.

## What a world-class system would need (gaps, concrete)
1. A model-usage ledger per organization (tokens, model, latency, outcome) feeding plan limits and invoices; today there is none (command 5, `docs/TODO.md:8`).
2. Per-org model policy: allowlist, default model per plan, optional customer-provided key (BYOK) — nothing in the schema or API today.
3. One timeout budget across cloud route, bridge client, engine run and model call, plus cancellation propagation or a streaming/async turn surface (`runner.py:155+` exists but is unused by the host).
4. Fallback groups and a circuit breaker per provider with health signals exported to `/markting/info`.
5. Tracing of every model call with org/thread tags (LangSmith or OpenTelemetry) and redaction at the exporter.
6. Boot-time model readiness and periodic canary (`paid-media-agent test model` equivalent) wired to the compose healthcheck.
7. Prompt-cache–aware system prompt layout (the system prompt and skills are static per process) and response caching for repeated fixture/report questions.
8. Arabic-aware evaluation of candidate models (the product is Arabic-first; nothing in the registry records language capability) and localized error mapping for model failures.
9. Secret hygiene: per-service env files, model key in the redaction list, no `LANGSMITH_GATEWAY` surprises.
10. Live-mode contract tests for the host (today all 7 host tests run the scripted model, command 3).
