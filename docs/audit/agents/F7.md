## Findings

### F7-01 — Pending-operation consumption is not atomic: concurrent or retried applies execute the provider write twice
- Severity: P1 · Classification: VERIFIED_RUNTIME (engine logic, harness E2/E3/E4) + VERIFIED_CODE (Postgres store has identical semantics)
- Evidence: `platform/packages/core/src/policy/engine.ts:90-124` (order: `pending.get` → expiry → hash → `checkStaticPolicy` → `provider.applyWrite` → `audit.append` → `pending.delete`); `platform/apps/cloud/lib/cloud/repository.ts:383-411` (`get` is a plain `select ... where consumed_at is null`), `:413-418` (`delete` is an unconditional `update ... set consumed_at = now()` with no `returning`/`where consumed_at is null` claim); `platform/supabase/migrations/20260817171039_cloud_initial_schema.sql:130-142` (no claim/lock column); `platform/apps/cloud/app/api/approvals/[id]/apply/route.ts:20-27` (no lock, applies any active row of the organization); harness E2–E4.
- Description: Nothing claims the pending row before `applyWrite`. Two admins approving the same row concurrently (or a retried request after a network blip) both pass `get`, both call the provider, and both append `applied` (E4). If Postgres fails after the provider write but before `pending.delete` (E2, E3), the row remains active and the Approvals page still shows it, so a second approval repeats the write. The existing test "Pending id is single-use" (`platform/packages/core/test/policy-engine.test.ts:100-103`) only proves the sequential case.
- Impact: For the bridge-mapped tools the payload is an absolute value (`kind: 'update'` only, `platform/apps/cloud/lib/markting/translate.ts:61,153,159`), so a repeat is a redundant same-value write plus a duplicated audit trail. The dashboard apply route, however, applies any active `pending_operations` row of the organization, including rows created through MCP/REST for `kind: 'create'` tools (`platform/packages/google/src/tools.ts:37,96,116,145,161`, `meta/src/tools.ts:108`, `linkedin/src/tools.ts:10`, `apple/src/tools.ts:48-152`); a repeated `create_campaign` makes a duplicate budgeted campaign. Requires a coincidence (concurrency or a post-write infra failure), so P1 rather than P0.
- Recommendation: Claim before writing (`update pending_operations set consumed_at = now() where id = $1 and organization_id = $2 and consumed_at is null returning *`, or a `claimed_at`/`claimed_by` column) and treat "0 rows" as `PENDING_NOT_FOUND`; record the provider result in the same statement or an outbox so a retry after a post-write failure is detected; pass an idempotency key to providers where their API supports one. Add tests for concurrent apply and for audit/delete failure after `applyWrite`.

### F7-02 — An executed provider write can leave no `applied` audit event
- Severity: P2 · Classification: VERIFIED_RUNTIME (harness E2)
- Evidence: `platform/packages/core/src/policy/engine.ts:113-123` (`applyWrite` at 113, audit at 114, delete at 123); `platform/apps/cloud/lib/cloud/repository.ts:428-434` (`PostgresAuditStore.append` is a plain insert, not in a transaction with the consume).
- Description: When `audit.append` fails after `applyWrite` succeeds, the platform changed but the audit log shows only `validated` and the pending row stays active; the dashboard shows "Internal server error." (`platform/apps/cloud/lib/http.ts:26-28`) and no outcome is marked (`apply/route.ts:27` is never reached).
- Impact: The audit trail — the product's accountability story — can be silent about a real ad-platform mutation.
- Recommendation: Write an `apply_started` marker before the provider call and an `applied`/`apply_failed` outcome after it, both via the pending row itself; make the UI show "outcome unknown, verify on the platform" for that state.

### F7-03 — Infrastructure failures at preview are recorded and reported to the engine as policy rejections
- Severity: P2 · Classification: VERIFIED_RUNTIME (scratch F3) + VERIFIED_CODE
- Evidence: `platform/apps/cloud/lib/markting/bridge.ts:76-83` (any thrown error → `code = 'ERROR'`, status `rejected_by_policy`, note "Engine proposal refused at preview", hand-off "adport refused the preview (ERROR)"); `platform/packages/core/src/policy/engine.ts:67-83` (pending row written at 67 before the `validated` audit at 76; harness E5 shows the row survives when the audit insert fails).
- Description: A Postgres/network error inside `validate` is indistinguishable from a `POLICY_VIOLATION` in provenance (`markting_engine_proposals.status`), in the audit note, and in the message sent to the engine thread (the model is told adport "refused"). In the E5 variant an approvable pending row also exists with `pendingOperationId = null` in provenance, i.e. without a provenance link.
- Impact: Misleading audit/provenance; the engine thread is told the change was refused; a pending row may appear on the Approvals page with no "source: Assistant" provenance.
- Recommendation: Branch on `error instanceof AdportError && code in {POLICY_VIOLATION, INVALID_INPUT, PROVIDER_ERROR}` vs. everything else; for unknown errors record `status = 'error'` (new value), do not tell the engine "refused", and return a 503 to the user. Add a test with a throwing audit store.

### F7-04 — Hand-off ordering: a failure after preview leaves an approvable row, an untold engine, and a re-bridge of the same proposal on the next turn
- Severity: P2 · Classification: VERIFIED_RUNTIME (scratch F1/F2 for the bridge; probe S2 for the engine) + INFERRED (the two combined across turns with a live database was not executed end-to-end)
- Evidence: `platform/apps/cloud/lib/markting/bridge.ts:76,88,89,94` (preview → `record` → `note` → `handoff`); `:99-104` (only the hand-off step is fault-tolerant); `platform/apps/cloud/lib/markting/assistant.ts:49-66` (bridges whenever `proposal.state === 'awaiting_approval'`, regardless of `interrupted`; no lookup of an existing provenance row); `platform/apps/cloud/lib/markting/repository.ts:84-86` (`on conflict (organization_id, proposal_id, revision) do update set pending_operation_id = excluded.pending_operation_id`); `engine/src/paid_media_agent/surfaces/runner.py:134` (`latest_proposal(thread_id)` is attached to every outcome); probe S2 (`same_as_orphan=True`, `interrupted=False`).
- Description: If `record()` (F1) or `note()` (F2) throws after a successful preview, the pending row exists, the engine is never told, and the user receives a 500. On the user's next message the engine returns the same still-`awaiting_approval` proposal; `assistant.ts:51` bridges it again, creating a second pending row for the same proposal, and the provenance upsert re-points `pending_operation_id` to the new row, so the first row remains approvable but loses its "source: Assistant" link on `platform/apps/cloud/app/dashboard/approvals/page.tsx:12-13`. The same re-bridge happens after an engine-side timeout (F7-05) even without any adport failure.
- Impact: Duplicate approvable rows for one intent; stale proposals surfacing a turn late; provenance that no longer covers all rows. Existing coverage is limited to the `rejectOnEngine` failure (`platform/apps/cloud/test/markting-bridge.test.ts:118-123`).
- Recommendation: Before previewing, look up `findEngineProposal(org, proposal_id, revision)` and skip/re-use when a `pending` row exists; wrap `record` + `note` in one transaction and run the preview inside a unit of work that compensates (consume the pending row) when persistence fails; only bridge when `outcome.interrupted` is true or dedupe by `payload_digest`.

### F7-05 — Engine timeout: the client aborts at 240 s but the engine keeps running; the orphaned proposal has no TTL and resurfaces later
- Severity: P2 · Classification: VERIFIED_CODE (timeouts) + VERIFIED_RUNTIME (orphan persists and resurfaces, probe S2/S3) + INFERRED (server-side continuation after client abort)
- Evidence: `platform/apps/cloud/lib/markting/engine-client.ts:73,82,96-97` (240 s default, `AbortController`, abort → `EngineError('unreachable', 503)`); `platform/apps/cloud/lib/markting/env.ts:18` (bound 5 s–900 s); `platform/apps/cloud/app/api/assistant/messages/route.ts:7,13` (`maxDuration = 300`; rate-limit token consumed before the engine call); engine budget: `engine/src/paid_media_agent/config.py:118,120` (120 s per model call, 40 calls), `engine/src/paid_media_agent/assembly.py:73,166,240-243` (SDK `max_retries=2` plus `ModelRetryMiddleware(2)`) — in live mode a single turn may legitimately exceed 240 s (`docs/ARCHITECTURE.md:511-512` documents the same budget; `docs/TODO.md:26` admits live timeouts are untested); `engine/src/paid_media_agent/surfaces/api/app.py:92-100` (no cancellation hook); probe S3 (old proposal still `awaiting_approval` after two more turns).
- Description: On abort the user sees "Internal server error." (see F7-06) and has spent a rate-limit token. The engine finishes the turn later; if it produced a proposal it stays `awaiting_approval` indefinitely (no sweep found: the only TTL is the approval-claim `ttl_seconds`, `engine/src/paid_media_agent/tools/writes.py:134,537`) and is attached to the next turn's outcome, where `assistant.ts:51` previews it as if the user had just asked (F7-04).
- Impact: Stale change previews appear after the user has moved on; wasted engine work; no reconciliation path. No test exercises `AbortError` (the client test only covers a thrown `TypeError`, `platform/apps/cloud/test/markting-engine-client.test.ts:51-52`) and none covers `assistant.ts`.
- Recommendation: Make the chat asynchronous (job id + polling/SSE) or at least align the engine's per-turn budget with the client's; on abort, record the thread as "turn in flight" and, on the next turn, only bridge proposals whose `created_at` is after the last user message or when `interrupted` is true; add an engine-side sweep that rejects proposals older than N minutes with "expired, never reviewed".

### F7-06 — The "engine not reachable" message can never reach the user; engine 4xx detail can
- Severity: P3 · Classification: VERIFIED_CODE
- Evidence: `platform/apps/cloud/lib/markting/assistant.ts:45` (builds the friendly message with status 503); `platform/apps/cloud/lib/http.ts:26-28` (any status ≥ 500 → "Internal server error."); `platform/apps/cloud/app/dashboard/assistant/assistant-chat.tsx:41-43` (renders `result.error`); for engine 401/404/409 the raw "Engine returned 401: <detail>" text is forwarded to the browser (`engine-client.ts:106` → `assistant.ts:45` → `http.ts:27`).
- Description: Dead-code message for the unreachable case; leakage of engine-internal detail for 4xx.
- Recommendation: Return a dedicated `{ error, code: 'engine_unavailable' }` body for 503 in this route, and map engine 4xx to fixed product messages.

### F7-07 — Apply and reject routes are multi-statement without a transaction
- Severity: P2 · Classification: VERIFIED_CODE
- Evidence: `platform/apps/cloud/app/api/approvals/[id]/reject/route.ts:16-21` (`delete` → `recordAudit` → `markPendingOutcome`, three separate statements); `platform/apps/cloud/app/api/approvals/[id]/apply/route.ts:26-27` (`applyPending` → `markPendingOutcome`); `platform/apps/cloud/lib/db.ts:8-17` (pool; `db().begin` exists and is used elsewhere, e.g. `platform/apps/cloud/lib/cloud/repository.ts:81,135,300,337`, but not here).
- Description: Postgres failing between statements leaves: a consumed row with no `rejected` audit event (silent consumption), or an applied operation whose provenance stays `pending` (and vice-versa). No test covers these partial states.
- Recommendation: Put consume + audit + provenance update in one `db().begin`; derive provenance status from the pending row instead of storing it twice.

### F7-08 — Provenance rows are never marked `expired`
- Severity: P3 · Classification: VERIFIED_CODE
- Evidence: `platform/apps/cloud/lib/markting/repository.ts:62,107` (`'expired'` is an allowed `BridgeStatus` and `markPendingOutcome` accepts it); `rg "'expired'" platform/apps/cloud/app platform/apps/cloud/lib` finds no caller; expiry happens only by `PostgresPendingStore.sweep` (`platform/apps/cloud/lib/cloud/repository.ts:420-425`) and the `expires_at > now()` filter (`:700`).
- Description: `markting_engine_proposals.status` stays `pending` forever for operations that expired unreviewed; provenance and pending state diverge.
- Recommendation: Derive status at read time from the joined pending row, or add the expiry transition to the sweep.

### F7-09 — Stripe webhook: check-then-insert idempotency and no ordering guard
- Severity: P2 · Classification: VERIFIED_CODE + INFERRED (Stripe retry semantics are external behaviour)
- Evidence: `platform/apps/cloud/lib/cloud/billing.ts:119-137` (`select` for duplicate → `applySubscription` → `insert ... on conflict do nothing`); `:56-100` (plan/status applied from the event object as-is; accounts beyond the new cap are disabled, `:85-100`); `platform/apps/cloud/app/api/billing/webhook/route.ts:8-15` (processing failures and signature failures both return 400 "Invalid Stripe webhook."); test coverage `platform/apps/cloud/test/database.integration.test.ts:219-243` (one `processed` event only; no duplicate/out-of-order/retry test).
- Description: A failed `applySubscription` returns non-2xx, so Stripe will retry (INFERRED) — correct. But two concurrent deliveries of one event both pass the pre-check and both apply (benign for the row update, duplicate `subscription_updated` audit event). More importantly, retries over Stripe's multi-day window can deliver `customer.subscription.updated` events out of order; nothing compares the event's `created` or the subscription's version, so an older state can overwrite a newer one and disable ad accounts under the wrong cap.
- Recommendation: Insert the event id first (claim) and roll back on failure; store and compare `event.created`/subscription `status`+`current_period_end` monotonically; return 500 (not 400) for processing errors so operators can distinguish them in Stripe's dashboard.

### F7-10 — Supabase Auth outage presents as "Authentication required." (401) everywhere
- Severity: P3 (GAP in resilience, fail-closed) · Classification: VERIFIED_CODE + INFERRED (SDK returns error objects rather than throwing on network failure)
- Evidence: `platform/apps/cloud/lib/cloud/auth.ts:10-12` (`getUser()` error of any kind → `throw new Error('Authentication required.')`); routes map that message to 401 (`app/api/assistant/messages/route.ts:17`, `app/api/approvals/[id]/apply/route.ts:30`); `platform/apps/cloud/lib/supabase/proxy.ts:21` (`await supabase.auth.getUser()` without error handling). The API-key/MCP path does not touch Supabase Auth (`auth.ts:22-37`), only the database.
- Description: During an Auth outage, signed-in dashboard users are told they are logged out; there is no retry, backoff, or distinct status. No test simulates it.
- Recommendation: Distinguish `AuthRetryableFetchError`/network errors from "no session" and return 503 with a clear message; consider short-lived JWT verification locally for read paths.

### F7-11 — Engine: duplicate `/reject` is an unhandled 500; a late reject resumes whichever interrupt is current
- Severity: P3 (engine cannot write; impact is logs/UX) · Classification: VERIFIED_RUNTIME (probe S4, S6) + VERIFIED_CODE
- Evidence: `engine/src/paid_media_agent/surfaces/api/app.py:127-137` (only `WriteDenied` is caught); `engine/src/paid_media_agent/domain/proposals.py:62,74` (`InvalidTransition` is a plain `Exception`); `engine/src/paid_media_agent/surfaces/runner.py:257-275` (`service.reject` then `resume(thread)` — the resume targets the thread's current interrupt, not the rejected proposal); `platform/apps/cloud/lib/markting/bridge.ts:99-104` (the bridge swallows hand-off errors, so adport is unaffected). This confirms `docs/ARCHITECTURE.md:824`.
- Description: A bridge retry of the hand-off produces a traceback in the engine; rejecting an orphan (F7-05) while a newer proposal is awaiting review injects the reject decision into the newer proposal's interrupt (S4), after which the newer proposal's own reject still succeeds (S5).
- Recommendation: Catch `InvalidTransition` → 409 in `app.py`; in `runner.reject`, resume only when the current interrupt belongs to the rejected proposal.

## What a world-class system would need (gaps, concrete)

1. Atomic claim of the pending row before the provider call (`update ... where consumed_at is null returning`), with `apply_started`/`applied`/`apply_failed` states and an "outcome unknown" UI state; provider idempotency keys where available.
2. One transaction per user action across `pending_operations`, `audit_events`, `markting_engine_proposals`; derive provenance status from the pending row rather than duplicating it.
3. Dedupe engine proposals by `(proposal_id, revision)`/`payload_digest` before previewing; bridge only when `interrupted` is true or the proposal is newer than the last user message.
4. Asynchronous chat turns (job + poll/SSE) so a 240 s HTTP budget does not define correctness; an engine-side sweep for proposals left `awaiting_approval` beyond a TTL; alignment of engine model-call budget with the client timeout.
5. A failure-injection test suite: throwing audit/pending stores, concurrent apply, `AbortError` from the engine client, `record()` failures, Stripe duplicate and out-of-order events, Supabase `getUser` network errors. The in-memory stores already used in `markting-bridge.test.ts` make most of these cheap.
6. Distinguish infrastructure errors from policy rejections in provenance, audit, and the engine hand-off message.
7. Stripe: claim-first event insert, monotonic ordering by `event.created`, 500 for processing failures.

## Disagreements / claims in docs that the code contradicts

- `platform/packages/core/test/policy-engine.test.ts:100-103` labels the pending id "single-use". True only sequentially; two concurrent applies both execute (harness E4), and a failure after `applyWrite` leaves it reusable (E2/E3).
- `platform/apps/cloud/lib/markting/assistant.ts:45` intends a user-facing "The analysis engine is not reachable right now." message; `platform/apps/cloud/lib/http.ts:26-28` guarantees it is never shown.
- `docs/PHASE1-REPORT.md:28` lists "engine hand-off failure tolerated" among the bridge tests; that tolerance covers only the `/reject` call (`bridge.ts:99-104`), not failures of `record`/`note` after a successful preview (scratch F1/F2).
- `docs/ARCHITECTURE.md:824` states that rejecting an already-terminal proposal raises an unhandled `InvalidTransition` → HTTP 500. Confirmed at runtime (probe S6); the bridge's silent catch depends on this undocumented-in-code behaviour.
- `docs/TODO.md:26` says live-mode timeouts are unverified; the code's own budgets (`config.py:118`, `assembly.py:73,166,240-243`) already exceed the client's 240 s default (`engine-client.ts:73`) in the worst case — this is a design mismatch, not just an untested path.
- `platform/apps/cloud/lib/markting/bridge.ts:103` comment "The adport record is the source of truth" assumes the record exists; in the F1 path (record throws) there is a pending row with no record at all.
