## Findings

### H5-01 — markting_* bridge tables are excluded from the retention job (unbounded JSONB growth)
- Severity: P2
- Classification: VERIFIED_CODE
- Evidence: `platform/supabase/migrations/20260828120000_cloud_plans_and_account_scope.sql:131-166` (final definition of `private.apply_data_retention()` — prunes `audit_events`, `pending_operations`, `findings`, `deletion_requests`, `oauth_transactions`, `rate_limit_buckets`, `billing_events` only); `platform/supabase/migrations/20261002000000_markting_bridge.sql:38-66` (adds `markting_engine_proposals`, `markting_threads`, `markting_sandbox_state`, `markting_account_aliases` later, and does NOT touch the retention function); `platform/apps/cloud/lib/markting/repository.ts:76-88` (one `markting_engine_proposals` row per proposal+revision, each carrying full `proposal` and `translation` JSONB).
- Description: The markting bridge migration (timestamp 20261002, the newest migration) adds four tenant tables but never extends `apply_data_retention()`. `markting_engine_proposals` is an append/upsert provenance log holding the complete engine proposal and its translation as JSONB for every proposal revision; `markting_threads` grows one row per assistant conversation. Nothing ever deletes them except an organization cascade delete.
- Impact: These tables grow without bound in normal operation. They hold per-tenant conversation provenance and ad-change payloads, so they are exactly the kind of tenant data the product's retention policy is meant to bound. Storage grows forever and the documented `data_retention_days` guarantee silently does not apply to them.
- Recommendation: Add `markting_engine_proposals` (by `created_at`), `markting_threads` (by `last_message_at`), and sandbox state to `apply_data_retention()` keyed on `organization_settings.data_retention_days`; add a covering index for the delete predicate. Add a test asserting pruning of these tables.

### H5-02 — The engine Postgres instance has no retention/pruning of any kind
- Severity: P2
- Classification: VERIFIED_CODE
- Evidence: `engine/src/paid_media_agent/persistence/postgres.py:11-43` (five `pma_*` tables, none with TTL/cleanup; `pma_dedupe` inserts one permanent row per dedupe key, `seen()` at `:217-223`); `engine/src/paid_media_agent/runtime/self_hosted.py:45-62` (`AsyncPostgresSaver` LangGraph checkpointer, no retention); `services/engine-demo/serve_demo.py:208-219` (demo host also persists checkpoints + repos to the engine DB when `DATABASE_URL` is set, as it is in `docker-compose.yml:43`). No `apply_data_retention`/cron exists anywhere under `engine/`.
- Description: The second Postgres instance (`engine-db`, `docker-compose.yml:66-78`) stores LangGraph checkpoints plus `pma_proposals`, `pma_receipts`, `pma_approvals`, `pma_dedupe`, `pma_thread_owners`. LangGraph checkpoints retain full graph state (messages, tool state) per thread and are never pruned; `pma_dedupe` accumulates one row per event forever.
- Impact: The engine DB grows unbounded with conversation/checkpoint data and dedupe keys, independent of the Supabase retention policy. In the demo compose this is where assistant conversation state actually lands. No runbook addresses engine-DB growth, vacuum, or checkpoint pruning.
- Recommendation: Document and implement engine-side retention (periodic `DELETE` of old checkpoints by thread/updated_at and old `pma_dedupe` rows), or a cron. State explicitly in OPERATIONS that engine-db has no automatic retention.

### H5-03 — No production migration runbook; the only documented apply mechanism is destructive `supabase db reset`
- Severity: P2
- Classification: VERIFIED_CODE / GAP
- Evidence: `Makefile:25-28` (`supabase start` then `supabase db reset --local --yes` — this is the whole apply path); `platform/docs/cloud-local-development.md:12-16` (same `db reset`); `platform/docs/cloud-waitlist.md:23-24` and `platform/docs/cloud-account-selection.md:32-34` only say "the normal migration process" / "apply the migration before deploying" without defining the command; no `supabase db push` / `migration up` is documented or scripted; `platform/docs/deployment-model.md:58` lists "operational runbooks tested before launch" as an unmet production gate.
- Description: `supabase db reset` drops and recreates the entire database; it is correct for local dev but catastrophic against production. There is no forward-only production migration command, ordering doc, or rollback story. Several migrations run `select cron.schedule(...)` and `create extension pg_cron` which assume the managed Supabase environment but have no documented promotion step.
- Impact: Production migration is undefined. An operator following the repo's only documented workflow would wipe data; nothing describes how migrations reach prod safely, how pg_cron is enabled there, or how to roll back a bad migration.
- Recommendation: Add a production DB runbook: `supabase db push` (or equivalent) ordering, pg_cron enablement, pre-migration backup, and rollback. Explicitly warn that `db reset` is local-only.

### H5-04 — Cloud pool `max:10` with a direct (non-pooler) connection string is unsafe on the supported serverless target
- Severity: P2
- Classification: VERIFIED_CODE / INFERRED
- Evidence: `platform/apps/cloud/lib/db.ts:7-18` (`postgres(env().SUPABASE_DB_URL, { max: 10, idle_timeout: 20, connect_timeout: 10, prepare: false, ... })`); `.env.example:8` and `platform/apps/cloud/.env.example:5` (`SUPABASE_DB_URL=postgresql://postgres:postgres@...:55322/postgres` — the direct Postgres port, not the transaction pooler); `platform/apps/cloud/next.config.ts:25` (`output: process.env.VERCEL ? undefined : 'standalone'` — Vercel serverless is an intended target).
- Description: On a standalone node server (the Dockerfile path) `max:10` is one pool per process and fine. On Vercel each warm function instance instantiates its own module-scoped pool of up to 10 connections; many concurrent instances multiply that against the direct Postgres connection limit. `prepare:false` shows pgbouncer-compatibility was intended, but the example URL points at the direct port, not the Supabase transaction pooler (6543).
- Impact: A serverless deployment pointed at the direct DB URL can exhaust Postgres connections under load (connection storms, `too many clients`). The sample env encourages the direct URL.
- Recommendation: For serverless, require the Supabase transaction pooler URL and a low `max` (e.g. 1-3); document the per-target pool math. Keep the direct URL only for the standalone/long-running container.

### H5-05 — Idempotent DDL at every engine boot has a multi-replica race and no schema-evolution path
- Severity: P3
- Classification: VERIFIED_CODE
- Evidence: `engine/src/paid_media_agent/persistence/postgres.py:59-62` (`setup()` runs the whole `CREATE TABLE/INDEX IF NOT EXISTS` block on each process start); `engine/src/paid_media_agent/runtime/self_hosted.py:76-85` and `services/engine-demo/serve_demo.py:211-219` (both call `repos.setup()` and `await saver.setup()` unconditionally at boot).
- Description: `CREATE TABLE IF NOT EXISTS` / `CREATE INDEX IF NOT EXISTS` are not fully concurrency-safe in Postgres; two engine replicas starting simultaneously can deadlock or error. Separately, `IF NOT EXISTS` only creates missing objects — it can never `ALTER` an existing `pma_*` table, so there is no way to evolve the engine schema once deployed.
- Impact: Flaky startup under horizontal scaling; and any future engine schema change requires a manual, undocumented migration. LangGraph `saver.setup()` has the same at-boot-migration shape.
- Recommendation: Gate `setup()` behind an advisory lock or a one-shot init job; add a real migration tool for the engine schema; document that `pma_*` cannot be altered via `setup()`.

### H5-06 — Two connection pools per engine process (up to 8 connections) is undocumented
- Severity: P3
- Classification: VERIFIED_CODE
- Evidence: `engine/src/paid_media_agent/persistence/postgres.py:50-52` (sync `ConnectionPool(min_size=1, max_size=4)`); `engine/src/paid_media_agent/runtime/self_hosted.py:52-59` (separate async `AsyncConnectionPool(min_size=1, max_size=4)` for the checkpointer). Both are created when `DATABASE_URL` is set.
- Description: Each engine process opens two independent pools against engine-db, so up to 8 connections per process, not the 4 the code comments imply. Nothing documents the aggregate against `engine-db` `max_connections` (default 100) when scaling engine replicas.
- Impact: Connection budgeting for engine-db is easy to under-provision; no runbook states the per-replica connection cost.
- Recommendation: Document combined pool sizing (8 × replicas) and set engine-db `max_connections` / a pooler accordingly.

### H5-07 — No statement_timeout or idle_in_transaction_session_timeout on either DB client or role
- Severity: P3
- Classification: VERIFIED_CODE (by absence)
- Evidence: `platform/apps/cloud/lib/db.ts:7-18` (sets `idle_timeout`/`connect_timeout` only, no `statement_timeout`/`idle_in_transaction_session_timeout`); engine pools in `postgres.py:50-52` and `self_hosted.py:52-59` set none; grep for these settings across `platform/engine/services` returned only one local `lock_timeout` in `20260831010651_provider_expansion.sql:2`.
- Description: Neither the `adport_backend` role nor the `paid_media` engine user has a server-side statement or idle-in-transaction timeout, and the clients do not set one.
- Impact: A slow/hung query or an abandoned open transaction can pin a pooled connection indefinitely, amplifying the pool-exhaustion risk in H5-04.
- Recommendation: Set `statement_timeout` and `idle_in_transaction_session_timeout` on `adport_backend` (via `ALTER ROLE`) and the engine user; add to the production runbook.

### H5-08 — Nightly retention delete on pending_operations uses an unindexed expression
- Severity: P3
- Classification: VERIFIED_CODE
- Evidence: `platform/supabase/migrations/20260828120000_cloud_plans_and_account_scope.sql:143-146` (`... where operation.organization_id = setting.organization_id and coalesce(operation.consumed_at, operation.expires_at) < now() - make_interval(...)`); the only indexes are `pending_operations_active_idx (organization_id, expires_at) where consumed_at is null` and a partial `created_by` index (`20260817171039_cloud_initial_schema.sql:144-148`).
- Description: The retention predicate is on `coalesce(consumed_at, expires_at)`, which no index covers, so the nightly job scans each organization's pending operations. `audit_events` retention (same function) is index-supported; this one is not.
- Impact: As `pending_operations` grows, the 03:17 retention run does progressively larger scans. Low urgency (off-peak, nightly) but a scaling cliff.
- Recommendation: Add an index on the coalesced expression (or on `expires_at` without the `consumed_at IS NULL` partial filter) to support the delete.

## What a world-class system would need (gaps, concrete)

- A forward-only production migration pipeline (`supabase db push` or equivalent) with ordering, pre-migration backup, and tested rollback — plus an explicit "`db reset` is local-only / destructive" warning.
- Retention coverage for every tenant table, including the markting bridge tables and the engine checkpoint/dedupe stores, each driven by `data_retention_days`, with tests that assert pruning per table.
- A documented backup/restore runbook and PITR expectations for both Postgres instances (the production-gates list in `deployment-model.md:52,58` names these as unmet).
- Per-target connection-pool guidance: transaction-pooler URL + low `max` for serverless; statement/idle-transaction timeouts on both DB roles; documented connection budget vs. replica count for both instances.
- A real engine-schema migration tool and a startup init that is safe under concurrent replicas (advisory lock or one-shot job).
- An index supporting the `coalesce(consumed_at, expires_at)` retention delete.

## Disagreements / claims in docs that the code contradicts

- `platform/docs/deployment-model.md:38` states "Audit, pending-operation, OAuth-transaction, and rate-limit retention is enforced by a scheduled Postgres job." Verified for those tables — but the later markting bridge tables (`20261002000000_markting_bridge.sql`), which store per-tenant conversation provenance and ad-change JSONB, are NOT covered by the job (H5-01), and the engine Postgres instance has no retention at all (H5-02). The implied "tenant data retention is enforced" is incomplete.
- `platform/docs/cloud-local-development.md:81` lists "scheduled retention deletion" among verified behaviors; the backing test (`database.integration.test.ts:331-336`) only asserts `audit_events` pruning — findings, pending_operations, deletion_requests, billing_events, and all markting/engine tables are unverified by the suite.
- `platform/docs/cloud-waitlist.md:23-24` / `cloud-account-selection.md:32-34` reference "the normal migration process" as if one is defined; the repository defines only the destructive local `supabase db reset` path (H5-03).
