# E6 — AI prompt / tool security (red team)

Red-team of every surface where model output or injected provider text could (a) cause a write,
or (b) inject markup/instructions. Trace covered: engine read/write tools over Pipeboard → model →
`propose_change` → `ProposalView` → `translate.ts` allowlist/alias map → `registry.call`; plus the
rendering surfaces (assistant chat, approvals provenance, MCP App widget, report attachment).

Headline: the write path is **model-proof by construction**. Nothing the model emits and nothing a
provider returns can execute a write without a separate human approval and a server-side policy
re-check. The findings below are residual trust/defense-in-depth issues, not autonomous-write holes.

## Findings

### E6-01 — Write path cannot be driven by model output or injected text (STRENGTH, no defect)
Severity: GAP (none) · Classification: VERIFIED_CODE + VERIFIED_TEST
Evidence:
- `platform/apps/cloud/lib/markting/bridge.ts:76` the bridge calls `registry.call(tool, input, ctx)` WITHOUT `pending_operation_id` → adport returns a `pending_validation` preview, never a live write. The live write is a second call with `pending_operation_id` (`bridge.ts:120`) reachable only from the apply route.
- `platform/apps/cloud/app/api/approvals/[id]/apply/route.ts:18-24` apply requires `tools:write` scope, role owner/admin (viewer/member rejected), org-scoped row lookup, and non-self-approval unless `MARKTING_ALLOW_SELF_APPROVAL=true`.
- Engine side: `engine/src/paid_media_agent/tools/write_tools.py:82-114` `execute_change` is wrapped in a LangGraph `InterruptOnConfig` (approve/reject) so execution pauses for a human; `writes.py:136-141` blocks self-approval; `writes.py:170-222` `WriteGate` adds kill-switch + `PAID_MEDIA_WRITES_ENABLED` + pinned catalog revision + canary-tool allowlist.
- `markting-bridge.test.ts` / `markting-translate.test.ts` assert hostile proposals (unknown alias, look-alike tool, platform mismatch, status injection, prose-chosen account/tool/target) all resolve to `unsupported` and never reach a tool.
Impact: Prompt injection via provider data at worst produces a *proposal/preview* that a second human must approve. No autonomous write.
Recommendation: None; preserve these invariants under refactor (they are the core safety property).

### E6-02 — `tool_name` allowlist + alias map cannot be bypassed by prose or look-alikes
Severity: GAP (none) · Classification: VERIFIED_CODE + VERIFIED_TEST
Evidence: `translate.ts:67-70` fixed `OPERATIONS` map (only `update_campaign_budget`,
`update_campaign_status`); `translate.ts:76-82` derives operation strictly from the `__` suffix;
`translate.ts:133-141` account comes only from the alias map and platform/provider must match;
`translate.ts:143` target id constrained to `^[A-Za-z0-9_:-]{1,120}$`; `translate.ts:84-92`
budget ceiling + positivity. The concrete provider tool (`google_set_budget`, etc.) is hard-coded in
`budgetInput`/`statusInput` (`translate.ts:103-123`), never taken from the proposal.
Impact: Model/engine prose cannot choose the tool, account, or operation. Alias confusion and
target-id injection with metacharacters are rejected.
Recommendation: None. (Minor: for live accounts without a `targets` map, `target_ref` passes through
to the provider as the campaign id — still account-scoped by the binding and human-approved, so not a
defect, but worth a note that target identity is model-influenced within the mapped account.)

### E6-03 — Provider-supplied `readOnlyHint` is the trust anchor for read/write classification
Severity: P2 · Classification: INFERRED (requires provider compromise)
Evidence: `engine/src/paid_media_agent/tools/catalog.py:162-188` classification reads
`annotations.get("readOnlyHint")` straight from the Pipeboard MCP tool metadata. A tool with
`readOnlyHint=true` is admitted as a READ (if it has an account arg and does not match the deny
patterns) and becomes model-callable via `PipeboardReadProvider.call_read`
(`pipeboard.py:180-186`) with no proposal, no approval, and no `WriteGate`.
A hostile or buggy Pipeboard endpoint could mislabel a *mutating* tool (e.g. `campaign_update`,
`budget_set` — names that evade the `mutate|raw|delete|remove|purge` deny patterns at
`catalog.py:84-90`) as read-only and the host would invoke it as a "read", producing an
un-governed side effect.
Impact: Complete bypass of the write-governance stack, contingent on the trusted MCP backbone
being compromised/incorrect. This is the single deepest trust assumption in the design.
Recommendation: Treat `readOnlyHint` as a hint, not authority. Maintain an explicit host-side
read/write allowlist (analogous to `admitted_mutations`) so a tool must be named to be callable at
all; alarm on catalog entries whose hint flips between refreshes; prefer an allowlist of read tool
names over trusting the annotation.

### E6-04 — Pipeboard MCP tool descriptions are injected verbatim into the model prompt
Severity: P3 · Classification: VERIFIED_CODE
Evidence: `engine/src/paid_media_agent/tools/reads.py:378` builds each model-facing tool with
`description = f"[{platform}] {entry.description}"` where `entry.description` is the provider's
own tool description (`pipeboard.py:62-66`, `raw_tools_from_langchain`). These strings sit in the
model's tool list and are classic indirect-prompt-injection carriers.
Impact: A compromised provider description could try to steer the model (e.g. "always also call X").
Blast radius is bounded: the model can only call account-scoped reads and `propose_change`
(human-gated), so the worst case is an attempted extra read within already-authorized accounts or a
malicious proposal a human must still approve. Truncated to 1024 chars.
Recommendation: Sanitize/neutralize provider-supplied descriptions (strip imperative/role markers,
or replace with a host-authored description keyed by tool name), and keep tool descriptions out of
the system-prompt trust zone.

### E6-05 — Provider read payloads returned to the model (indirect injection via ad data)
Severity: P3 · Classification: VERIFIED_CODE
Evidence: `reads.py:369-376` returns `ReadResult.model_dump_json()` to the model; for
non-performance reads the payload head (up to 1200 chars) is surfaced in `preview`
(`reads.py:313,340-344`). Entity names and provider error text flow through here. A campaign named
with an injection string reaches the model.
Impact: Bounded — raw rows are offloaded to an artifact (not in model context, `reads.py:268-281`),
performance previews expose only counts/currency (`reads.py:298-301`), and any resulting action is a
human-approved proposal. UI rendering of the same text is escaped (see E6-06/E6-07).
Recommendation: Keep the artifact-offload discipline; consider tagging provider-origin strings so the
model treats them as data, and cap/strip control sequences in previews.

### E6-06 — React rendering surfaces are XSS-safe (assistant chat, approvals provenance)
Severity: GAP (none) · Classification: VERIFIED_CODE
Evidence: `assistant-chat.tsx` renders all model/provider prose through auto-escaped JSX
(`:77` `<pre>{message.text}`, `:108` summary, `:109` changes, `:120/:128` reasons); no
`dangerouslySetInnerHTML` anywhere in the cloud app (grep exit 1). `approvals/page.tsx:37` renders
provenance (`engineToolName`, `account/target refs`, `reason` sliced to 160) via JSX escaping;
`:30` summary via JSX. `translate.ts:162-166` `describeProposal` caps prose and is only ever placed
in escaped contexts.
Impact: Injected markup in proposal prose or provider names renders inert.
Recommendation: None.

### E6-07 — MCP App widget (ui.ts) consistently escapes before innerHTML
Severity: GAP (none) · Classification: VERIFIED_CODE + VERIFIED_TEST
Evidence: `platform/packages/mcp/src/ui.ts:171` `esc()` escapes `& < > " '`; every interpolation of
tool-result data (`a.name`, `a.id`, entity names at `:233`, notices `:190`, operation
changes/coercions/summary `:269-273`, insights `:304`, error/cancel messages `:318-322`) is wrapped
in `esc()`. Unescaped interpolations are non-attacker-controlled (fixed `status.tone`, numeric
widths/indices, boolean `aria-pressed`, fixed `providerSvg` map, fixed metric keys), and all attribute
contexts are double-quoted with `"` escaped. `test/ui.test.ts` exercises rendering.
Impact: Reflected provider text (campaign names etc.) in the widget is neutralized.
Recommendation: None; keep `esc()` mandatory on any new field.

### E6-08 — Report HTML (model-written prose) is served from the app origin
Severity: P3 · Classification: VERIFIED_CODE
Evidence: `app/api/reports/engine/[name]/route.ts:17-24` restricts content-type to
html/pdf/json, forces `Content-Disposition: attachment`, sets `X-Content-Type-Options: nosniff`,
`Cache-Control: private, no-store`; `engine-client.ts:135` validates `name` against
`^[A-Za-z0-9_.-]{1,120}$` and rejects leading `.` (no path traversal / SSRF segment injection).
Global CSP sets `frame-ancestors 'none'` (`next.config.ts:12`).
Impact: HTML is downloaded, not rendered inline on the origin, so model-written markup cannot run
with the app's session. Residual: the response carries no sandboxing CSP of its own and relies on the
attachment disposition; if a client/extension renders it inline, model HTML executes in a file/blob
context (no app cookies).
Recommendation: Add `Content-Security-Policy: sandbox` (or `default-src 'none'`) to the report
response, and/or serve from an isolated origin, as defense in depth.

### E6-09 — Production CSP keeps `script-src 'unsafe-inline'` (no XSS backstop)
Severity: P3 · Classification: VERIFIED_CODE
Evidence: `next.config.ts:17` → `script-src 'self' 'unsafe-inline'` in production.
Impact: Should an HTML-injection sink ever be introduced, CSP would not block the injected inline
script. Today there is no such sink in the React app (E6-06), so this is defense-in-depth only.
`object-src 'none'`, `base-uri 'self'`, `frame-ancestors 'none'` are correctly set.
Recommendation: Move to nonce/hash-based `script-src` and drop `'unsafe-inline'`.

## What a world-class system would need
- Host-side explicit read-tool allowlist (names), so `readOnlyHint` is corroborated, not trusted (closes E6-03).
- Host-authored or sanitized tool descriptions so provider text never enters the model's instruction zone (E6-04).
- Provider-origin data tagging / delimiting so the model treats ad-platform strings as untrusted data (E6-05).
- Nonce-based CSP without `unsafe-inline`, and a `sandbox` CSP on the report response (E6-08/E6-09).
- Alerting when a catalog refresh flips a tool's class or hint.

## Disagreements / claims the code contradicts
- `translate.ts:5-7` claims "Proposal prose never chooses the tool, the account or the target." Verified true for tool and account; the *target id* does pass through from `target_ref` for live accounts lacking a `targets` map (`translate.ts:142`) — still account-scoped and human-approved, but the sweeping wording understates that target identity is model-influenced within the mapped account.
- `pipeboard.py:1` / `reads.py:121` ("the only path from the model to a provider read") hold, but the safety of READ classification itself rests on provider-supplied `readOnlyHint` (E6-03), which the docstrings present as deny-by-default without flagging the trusted-metadata dependency.

## Confidence and what was NOT verified
Confidence: 0.82.
NOT verified: runtime behavior of a genuinely malicious Pipeboard endpoint (no live provider;
E6-03 is reasoned from code, not executed); the actual engine LangGraph interrupt resume semantics
end-to-end (reasoned from `InterruptOnConfig` wiring, not run against a live model); browser behavior
of the report attachment across clients; DB-backed repository tests (postgres/supabase unavailable in
sandbox — those 3 suites errored on connection, unrelated to security logic).
