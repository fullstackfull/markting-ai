## Findings

### E3-01 Direct-adapter credentials (X Ads, OpenAI Ads) and model API keys are omitted from the redaction secret list
- Severity: P2  | Classification: VERIFIED_CODE
- Evidence: engine/src/paid_media_agent/assembly.py:293-305 (`_secret_values` enumerates only pipeboard_api_token, paid_media_approval_signing_key, slack_bot_token, slack_app_token, slack_signing_secret, database_url, paid_media_api_tokens); assembly.py:254 `RedactionMiddleware(secrets=(*secrets, *runtime.extra_secrets))`; runtime/profiles.py:54 `extra_secrets` defaults to `()` and is never assigned anywhere in src (grep for `extra_secrets=` returns nothing); config.py:150-154 defines x_ads_* and openai_ads_api_key as live credentials used by tools/direct/x_ads.py:199-201 and openai_ads.py:124.
- Description: Every tool result and tool exception is scrubbed by RedactionMiddleware (redaction.py:49-90). Scrubbing is value-based for the explicit `secrets` list plus a fixed regex set (redaction.py:16-28). The X Ads consumer key/secret and OAuth access token/secret, which are the credentials actually used to call X's API, are never added to the explicit list. They are arbitrary opaque strings; the generic regex only matches them when they appear adjacent to an `api_key=/token=/secret=` label, so a raw token echoed standalone in an upstream HTTP error body or stack string would reach the model (and Slack/logs) unredacted. (OpenAI Ads keys happen to match the `sk-` regex; model provider keys like ANTHROPIC_API_KEY/GROQ_API_KEY are likewise absent from the explicit list.)
- Impact: Possible leakage of live ad-platform credentials into model context, Slack messages, and logs when a direct adapter errors.
- Recommendation: Add all `*_ads_*` SecretStr values and model-provider API keys to `_secret_values` (or populate `extra_secrets` from them). The value-based pass is the only reliable scrubber for opaque tokens.

### E3-02 No key rotation / key-version support in the cloud vault despite a key_version column
- Severity: P3  | Classification: VERIFIED_CODE
- Evidence: platform/apps/cloud/lib/crypto.ts:5-26 (single `ADPORT_CLOUD_ENCRYPTION_KEY`; ciphertext prefix `v1` is a *format* version, no key id embedded); repository.ts:162 hardcodes `key_version = 1` on upsert; grep for key_version/rotateKey across cloud finds only this line and tests. digestApiKey/ADPORT_API_KEY_PEPPER (crypto.ts:35-37) similarly has no pepper versioning.
- Description: The schema carries a `key_version` column but crypto has no multi-key map or key-id selection. Rotating ADPORT_CLOUD_ENCRYPTION_KEY (or ADPORT_API_KEY_PEPPER) would make every stored provider credential undecryptable (and every API key unverifiable) with no envelope/re-encrypt path.
- Impact: Operationally, encryption-key compromise cannot be remediated by rotation without bespoke migration; emergency rotation is effectively a data-loss event for the credential vault.
- Recommendation: Embed a key id in the ciphertext envelope, keep a keyring (primary + decrypt-only old keys) in crypto.ts, and provide a re-encrypt job; version the API-key pepper the same way.

### E3-03 ADPORT_CLOUD_ENCRYPTION_KEY env check is weaker than the real requirement
- Severity: P3  | Classification: VERIFIED_CODE
- Evidence: platform/apps/cloud/lib/env.ts:11 `ADPORT_CLOUD_ENCRYPTION_KEY: z.string().min(40)`; crypto.ts:6-7 requires base64 decode to exactly 32 bytes.
- Description: The schema accepts any >=40-char string; the hard 32-byte check lives only in crypto.ts and fires lazily on first encrypt/decrypt rather than at boot/env-parse. A misconfigured 40-char non-32-byte key passes env validation and fails only when the first credential is used.
- Impact: Misconfiguration surfaces late (at first OAuth connect) instead of at startup. Not a confidentiality defect (crypto fails closed).
- Recommendation: Validate base64-decodes-to-32-bytes in the zod schema so it fails at env parse.

### E3-04 (NON-DEFECT, documented) Engine PAID_MEDIA_API_TOKENS stored in plaintext .env
- Severity: GAP  | Classification: VERIFIED_CODE
- Evidence: engine/.env.example `PAID_MEDIA_API_TOKENS=`; config.py:174,260-266 parses `token:caller` pairs, held in memory only; surfaces/api/app.py:28-36 compares with `hmac.compare_digest` (constant-time). admin/envfile.py:478 writes .env at 0o600; admin/envfile.py masked_env masks secret values with bullets (envfile.py masked_env); generate_secret shows the token once (actions.py:300-312).
- Description: Bearer API tokens live as plaintext `token:caller` pairs in a 0600 .env, by design (self-hosted single-file config, documented). Comparison is constant-time and tokens "never leave" resolve_caller (app.py:28). This is acceptable for a self-hosted bearer scheme; flagged only as a hardening gap (no hash-at-rest), not a defect.
- Recommendation: Optional: store only a hash of each bearer token and compare hashes, so a leaked .env does not yield usable tokens.

## What a world-class system would need
- KMS/HSM-backed envelope encryption with a key id in each ciphertext and a decrypt-only keyring for zero-downtime rotation (addresses E3-02); same for the API-key pepper.
- Redaction driven by a single registry of all SecretStr settings (not a hand-maintained subset), so new credentials are scrubbed automatically (addresses E3-01).
- Boot-time validation of key material (length/entropy) rather than lazy failure (E3-03).
- Hashed-at-rest bearer tokens for the engine API (E3-04) and audit logging of credential decryption events.

## Disagreements / claims in docs that the code contradicts
- surfaces/api/app.py:28 docstring "Constant-time bearer token lookup": the per-token comparison is constant-time (hmac.compare_digest), but the loop returns early on match, so total time depends on token position. Only observable to a holder of a valid token; immaterial, but the comment overstates it.
- No doc overclaims the vault; crypto/AAD/rotation behavior matches code. engine/.env.example comment "Values stay in memory only" for api tokens is accurate (config.py:266, app.py:28).
