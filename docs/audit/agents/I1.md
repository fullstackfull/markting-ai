## Findings

### I1-01 — Plan model has only 5 flat dimensions; none fit an AI media buyer's cost drivers
- Severity: P2 (GAP for the product category; substantial monetization deficiency)
- Classification: VERIFIED_CODE
- Evidence: `platform/apps/cloud/lib/cloud/plans.ts:11-44` (`PlanDefinition` = `maxActiveAccounts`, `maxMembers`, `maxRetentionDays`, `writeAccess`, `clientWorkspaces` only).
- Description: The entire pricing surface is five booleans/counts. For an "AI media buyer" the real cost and value drivers are AI inference (agent turns, tokens, recommendations generated), managed ad spend, automated report volume, and connector/platform count. None of these exist as a plan dimension. The product sells agent write access as a single boolean toggle (`writeAccess`), so a €19 Operator and a heavy automated account both cost Anthropic/Stripe-side inference the same, with no price capture.
- Impact: Margin risk — unlimited AI consumption on any paid tier; no lever to price heavy automation; cannot sell "X automated reports/mo" or "up to $Y managed spend" tiers that competitors in this space use.
- Recommendation: Add usage dimensions (agent runs, recommendations, report exports, managed-spend band) as metered entitlements; see architecture section.

### I1-02 — No usage-metering tables or AI-cost accounting anywhere in the cloud app
- Severity: P2 (GAP)
- Classification: VERIFIED_CODE
- Evidence: search across `platform/apps/cloud` found zero `usage_*`/`metering`/`cost`/`token` tables or writers; billing schema is only `organization_subscriptions` + `private.billing_events` (`...20260828120000...sql:3-56`). The markting bridge tables (`markting_threads`, `markting_engine_proposals`, `markting_sandbox_state`, `...bridge.sql`) store no per-run cost/token counters.
- Description: There is no ledger of how much AI/agent work each organization consumes, so even if a metered price were added there is nothing to report to Stripe or to enforce a quota against.
- Impact: Usage-based or hybrid pricing is impossible today; no data to detect abusive consumption or to attribute inference cost per tenant.
- Recommendation: Introduce an append-only `usage_events` table (org, metric, quantity, occurred_at, idempotency_key) written at each agent run / recommendation / report, plus a rollup for enforcement and Stripe usage-record reporting.

### I1-03 — `clientWorkspaces` entitlement is advertised but never enforced or implemented
- Severity: P2 (advertised capability with no backing code)
- Classification: VERIFIED_CODE
- Evidence: flag set true for agency/enterprise in `plans.ts:38,42`; rendered as the feature bullet "Separate client workspaces" at `app/dashboard/billing/page.tsx:95` and `lib/i18n/messages/billing.ts:53,119`; the Agency description promises "client workspaces" (`billing.ts:34,92`). No code reads `clientWorkspaces` and no sub-organization / client-workspace feature exists (`rg` for the concept returns nothing outside the flag definition and UI copy).
- Description: The Agency tier (€149/mo) is marketed on a feature that the codebase does not provide and does not gate. A customer buying Agency for client workspaces receives the same single-workspace product as Premium plus higher count limits.
- Impact: Mis-sold capability → chargeback / churn risk and a per-dimension price justification that does not exist. Because the task rule treats an advertised-but-absent capability as a defect (the code claims to provide it), this is a defect, not a mere gap.
- Recommendation: Either implement multi-tenant client workspaces (child org scoping) and gate it on the flag, or remove the claim from Agency marketing until shipped.

### I1-04 — Entitlement is a thin inline DTO, not an entitlement service; no feature flags or overrides
- Severity: P3 (architecture/maintainability; blocks pricing flexibility)
- Classification: VERIFIED_CODE
- Evidence: `getOrganizationEntitlement` is a single-row read of `organization_subscriptions` mapped to the hard-coded `PLANS` object (`plans.ts:55-79`); the principal only ever carries `{planId, planName, writeAccess}` (`lib/cloud/types.ts:10-14`, set at `plans.ts:98-102`). There is no per-org override table, no feature-flag table, no trial/credit/grandfather mechanism.
- Description: Every entitlement decision is `PLANS[planId].<field>` evaluated at each call site (`tenant-admin.ts:33,174`, `repository.ts:656-662`, `mcp/route.ts:20-40`). Changing packaging (e.g. an add-on, a custom enterprise bundle, a promotional bump) requires editing `plans.ts` and redeploying; enterprise has `null` limits hard-coded rather than negotiated per-contract values.
- Impact: No pricing flexibility — cannot grant a one-off account bump, run an A/B price test, or honor a custom enterprise contract without code changes; enterprise (the highest-value tier) has no persisted negotiated limits at all.
- Recommendation: Extract a central `resolveEntitlement(org)` that merges plan defaults with a per-org `entitlement_overrides` row and a feature-flag set; make limits data, not code.

### I1-05 — Enterprise sales leads are routed to the upstream author's personal email
- Severity: P2 (direct monetization leak / branding defect)
- Classification: VERIFIED_CODE
- Evidence: `app/dashboard/billing/page.tsx:119` — `href="mailto:yannick@adport.dev?subject=Adport%20Enterprise"`.
- Description: The highest-value (Enterprise, "contact us") conversion path on a product branded `markting-ai` sends the prospect's email to `yannick@adport.dev` (the vendored adport project's author) with subject "Adport Enterprise". This is an unmodified upstream leftover on a revenue-critical CTA.
- Impact: Every enterprise inbound lead is delivered to the wrong party and carries the wrong brand; lost revenue and a trust/brand break at the exact moment of highest intent.
- Recommendation: Route to the operator's sales address and rebrand the subject; make the address configurable (env), not hard-coded.

### I1-06 — `past_due` retains full plan entitlement (including write) with no in-app dunning limit
- Severity: P3 (revenue risk, mitigated by Stripe)
- Classification: VERIFIED_CODE
- Evidence: `plans.ts:77` and `billing.ts:91` both treat `['active','trialing','past_due']` as fully entitled; `getOrganizationEntitlement` returns the full plan for `past_due`.
- Description: A failed-payment subscription keeps every paid capability (write tools, account/member/retention limits) until Stripe itself transitions the subscription to `unpaid`/`canceled`. There is no application-side grace window, no soft-lock, no banner, and no downgrade on `past_due`.
- Impact: Customers can continue consuming the paid (AI-cost-bearing) product during an indefinite dunning period; relies entirely on Stripe retry settings, which are not asserted in code.
- Recommendation: Keep read access on `past_due` but soft-lock write/automation after a defined grace window and surface a payment-failed banner; document the assumed Stripe dunning policy.

### I1-07 — Downgrade webhook clamps active accounts only; members and retention are not reconciled
- Severity: P3
- Classification: VERIFIED_CODE
- Evidence: `billing.ts:91-106` disables ad accounts beyond `maxActiveAccounts` on plan change, but there is no equivalent reconciliation of `maxMembers` or `maxRetentionDays`. Member and retention limits are enforced only at mutation time (`tenant-admin.ts:33-42,174-178`); the one-time retention clamp exists only in the migration (`...20260828120000...sql`, `least(..., 30)` for reader at install).
- Description: An org that downgrades keeps all existing members and its previously-set retention window; only new invites / new retention edits are blocked. So a former Agency org on Reader can retain 15 seats and 730-day history indefinitely.
- Impact: Paid value persists after downgrade — seats and long audit retention (a storage/cost item) are not reclaimed, weakening the downgrade price signal.
- Recommendation: On downgrade, either reconcile members/retention to the new ceiling (with notice) or explicitly document grandfathering as intended policy.

## What a world-class system would need (gaps, concrete)
1. **Usage-metering substrate**: append-only `usage_events(org_id, metric, quantity, occurred_at, idempotency_key)` written at each agent run, recommendation, and report export; a `usage_rollups` monthly aggregate for enforcement and display.
2. **Metered Stripe billing**: metered price items (e.g. AI runs beyond quota, managed-spend band) reported via Stripe usage records on period boundaries; graduated/overage tiers rather than only flat `quantity:1`.
3. **Entitlement service**: one `resolveEntitlement(org)` that composes plan defaults + `entitlement_overrides` (per-org bumps, trials, credits, grandfathering) + a `feature_flags` set; all current call sites consume it instead of indexing `PLANS` directly. Enterprise limits become data rows, not `null` code.
4. **Media-buyer-relevant dimensions**: managed-ad-spend bands, connected-platform count, automated-report count, recommendation quota, AI-run quota — expressed as entitlements, metered where consumption-based.
5. **Seat billing**: pass seat quantity to Stripe (per-seat line item) instead of a flat price + a soft member ceiling, so seats are actually monetized and reconciled on change.
6. **Dunning state machine**: explicit grace window and soft-lock of write/automation on `past_due`, with an in-app payment-failed banner, independent of Stripe retry config.
7. **Downgrade reconciliation + grandfathering policy** for members and retention, made explicit in code.
8. **Operator-configurable sales/branding** (enterprise contact, product name) via env, removing the adport author leftover.
