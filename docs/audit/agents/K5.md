# K5 — Data Scientist (Final Council memo)

## How to read this

I am the council seat responsible for ruling on the **trustworthiness of every number
the product shows or the AI reasons over**: metric definitions, currency/unit handling,
attribution gaps, and sample sufficiency. My primary inputs were the B-cluster
specialist reports (B1–B9), the consolidated deliverable `10-data-attribution-audit.md`,
and the money/attribution/budget leads A12, A13, A15. I re-verified 12 load-bearing
citations directly in the code (every one held), then set final severities for the
findings I am willing to vouch for, resolved the severity disagreements between agents,
and defined the **minimum data-trust floor** that must exist before any recommendation
may carry a confidence score. Read §Verdicts first for the one-line rulings, §Findings
for the severities I stand behind, and §Minimum data-trust requirements for the gate
contract. This is an audit; I changed no source file (only this memo).

**Classification legend:** VERIFIED_CODE (read the code, claim holds) · VERIFIED_TEST
(a test exercises it) · VERIFIED_RUNTIME (a probe/command actually run) · DOCUMENTED_ONLY
(asserted in docs/prose, not enforced in code) · INFERRED (reasoned, not directly
observed) · NOT_VERIFIED (could not confirm; usually needs prohibited live access).

**Severity legend:** P0 security/data-loss/cross-tenant/unsafe-ad-execution · P1
production blocker or serious financial risk · P2 substantial functional/reliability
deficiency · P3 quality/polish · GAP missing capability the code does not claim.

## Verdicts (one line each)

- **Arithmetic correctness of the engine: TRUSTWORTHY.** Decimal math, never-average-
  ratios, zero/None-safe denominators, missing-stays-None storage, intra-read currency
  hard-error, suppression gate logic — all EXISTS_AND_STRONG and test-covered. The engine
  does not lie about the data it is *handed*. (B1, A12, A13 agree; `test_compute.py` passes.)
- **Provenance / trust machinery on the live path: NOT TRUSTWORTHY.** Every gate that is
  supposed to say "this number is not settled / not reconciled / not comparable yet"
  (completeness, provider reconciliation, attribution compatibility) is fixture-only,
  tautological, or prose-only in live mode. Live data enters at trust tier T1 and is
  rendered with T3/T4 confidence. This is the central finding and it is correct.
- **Sample sufficiency: ABSENT.** No significance, variance, CI, or minimum-base anywhere;
  no statistics library is even a dependency; the one structured "anomaly" signal fires on
  2→3-conversion noise. Recommendations rest on point estimates with nothing forbidding an
  over-claim on a thin window. This is my seat's headline gap.
- **Currency/unit handling: SAFE where it reads, UNSAFE where it writes.** Display-side
  refusal to mix currencies is correct in the engine and in `report-summary.ts`; the
  merchant dashboard tile and the Meta/bridge budget-write path are not currency-aware
  (0× ROAS tile, cross-currency sum, 100× zero-decimal budget).
- **No metric the product surfaces may legitimately carry a computed "confidence" today**
  — "confidence" is a free-text word the model may write, with no computation behind it.

## Findings I vouch for (final severities)

Severities are mine; where I overrode an agent I say so. IDs are K5-local; the DA/source
IDs are cross-referenced.

### K5-01 — Partial-conversion ratios emit an authoritative CPA/ROAS that can be ~3.5× wrong — P2 — VERIFIED_RUNTIME (B1) / VERIFIED_CODE (me)
- Evidence: `compute.py:60-68` (sum over present rows only), `:71-73` (spend over all
  rows), `:91-92` (`cpa`/`roas` from those), per-entity/per-platform ratios still emitted
  in headlines (`compute.py:389-390`). Sources DA-06, B1-02, A13-10.
- Description: Within one entity/window, spend is summed over every row but conversions /
  conversion_value only over rows that reported them, so a window with conversions on 2 of
  7 days yields CPA = full_spend ÷ partial_conversions. B1's probe: 7×$100 with 10 conv on
  2 days → CPA 70 vs true 20.
- **Severity ruling:** B1-02 said P2; A13-10 said P3 (because the *cross-platform* total is
  suppressed via `MISSING_METRIC`). I rule **P2**: A13-10's downgrade only covers the
  blended total; the per-entity and per-platform ratio is *not* suppressed and is the
  number a budget argument rests on.
- Recommendation: Emit the ratio only when numerator and denominator cover the same
  row/day set; else `None` with a "partial basis" label.

### K5-02 — Partial impressions/clicks silently undercount totals and distort CTR/CPM/CVR — P2 — VERIFIED_RUNTIME (B8)
- Evidence: `normalize.py:141-144` (MISSING_METRIC only for conversions/value), `compute.py:49-68`
  (optional sums over present rows), suppression keys on MISSING_METRIC only
  (`compute.py:323-324`). Sources DA-07, B8-01/06.
- Description: A gapped impressions day sets no flag; `aggregate` returns a reduced
  denominator and the derived CTR/CPM/CVR are wrong while `missing=()`. The bad window is
  not suppressed because suppression never looks at impressions/clicks gaps.
- Recommendation: Extend the missing-metric guard to all four additive metrics; require
  per-metric day-coverage == window day-count before emitting a ratio.

### K5-03 — "reconciled" means "our sum equals our own sum" on live data, and the report stamps reconciled:true regardless — P2 — VERIFIED_CODE
- Evidence: `compute.py:216-224` (tautological self-check), `:225-248` (provider checks
  gated on `provider_totals` keys that live reads never carry), `reads.py:266` (empty dict
  live), `reports.py:67` (`reconciled=True` hardcoded), `render.py:204-236` (reconcile only
  checks value-fidelity). Sources DA-04+DA-05, B1-01, B8-03/04.
- Description: The only unconditional reconciliation check compares two quantities derived
  from the same rows. Provider control totals exist only in fixtures. The report then emits
  the headline boolean `reconciled:true` even when a per-platform reconciliation listed in
  the body *failed*.
- Recommendation: Tri-state reconciliation (`reconciled` / `not_reconciled` /
  `no_external_oracle`), require an external oracle before `reconciled` can be true, cover
  conversions/value not just spend, and pass `comparison.reconciled` into `report_summary`.

### K5-04 — Cross-platform blended CPA/ROAS mixes incompatible attribution and reaches the rendered report; the attribution flag is dead — P2 — VERIFIED_RUNTIME (A13/B2)
- Evidence: `compute.py:278-298` (sums conversions/value, derives blended CPA/ROAS),
  `:309-331` (suppression gate omits attribution and timezone), `common.py:64`
  (ATTRIBUTION_DIFFERS never produced), `render.py:123-134` (full scorecard rendered),
  `render.py:166-172` (caveat only a footnote, only when >1 platform); mitigation
  `compute.py:404-406` (model summary spend-only). Sources DA-01+DA-02, A13-01, B2-02, A12-04.
- Description: The blended portfolio CPA/ROAS sums Meta 7d-click/1d-view purchases with
  Google click-based conversions (and, via DA-08, Apple installs / Pinterest checkouts).
  The model's structured view is protected (spend only), but the human PDF/HTML report
  shows the blended figure with only a footnote caveat.
- **Severity ruling:** A12-04 said P3 ("labeled and caveated"); A13-01/B2-02 said P2. I
  rule **P2**: the figure is a decision input in the human report, the caveat is a footnote
  not a property of the number, and the machine-readable guard (`ATTRIBUTION_DIFFERS`)
  that should suppress it is inert.
- Recommendation: Populate an `Attribution` descriptor per row; set `ATTRIBUTION_DIFFERS`
  and suppress blended conversions/CPA/ROAS when signatures differ; render per-platform.

### K5-05 — Conversion-definition conflation within and across platforms — P2 — VERIFIED_CODE
- Evidence: `normalize.py:28` (`results`/`purchases`/`conversions` one column),
  cross-platform sum `compute.py:278-298` mixing Google all-conversions, Meta purchases,
  Apple installs (`apple/src/provider.ts:~200`), Pinterest checkouts (`pinterest:17`),
  Reddit click+view (`reddit:230`); nothing records which event each count is. Sources
  DA-08, A13-02, B7-04/06.
- Description: One field named `conversions` holds purchases for some platforms, any
  configured action for Google/TikTok, and installs for Apple. Summing them and deriving a
  portfolio CPA/ROAS compares non-comparable events. The `results` key in particular can
  promote a non-purchase optimisation event (leads, installs) into the purchase column.
- Recommendation: Carry `conversion_event`/`conversion_source_key` on every row; refuse or
  segment cross-platform aggregation across differing event kinds; drop `results` from the
  purchase key list.

### K5-06 — Conversion-lag / incompleteness protection is fixture-only; live trailing days are treated as settled — P2 — VERIFIED_CODE
- Evidence: `pipeboard.py:186-193` (live read sets no `data_complete_through`),
  `x_ads.py`/`openai_ads.py` same, `normalize.py:141,156` (flag/complete gated on the
  field), `fixtures.py:201-214,363-367` (the only producer). Sources DA-03, B2-03, A13-03,
  B8-02.
- Description: The wiki tells the model "last N days" ends at `data_complete_through`, but
  no live path ever sets it, so yesterday's still-maturing conversions are treated as
  final. Period deltas understate the current window vs a matured previous window.
- Recommendation: Derive `data_complete_through` on the host (provider-reported, else
  `today − per-platform lag`); treat an unknown boundary as immature, never as complete.

### K5-07 — No statistical significance / sample-sufficiency engine; small-base noise is emitted as a structured signal — P2 — VERIFIED_RUNTIME (B3)
- Evidence: `compute.py:98-114` (absolute + relative deltas only), no scipy/statsmodels/
  numpy dependency (B3's pyproject/uv.lock scan), `summary.py:27,118-125` (relative-only day
  flag, no floor; B3 runtime: 2→3 conversions → `conversions_moved_up`). Sources DA-10,
  B3-01/02.
- Description: The only "analysis" is arithmetic deltas; a 100% swing on a base of 1 looks
  identical to a real trend, and the structured `flags`/`flagged_days` the model consumes
  carry noise as if it were signal. Sample size never gates anything.
- Recommendation: Attach the base (conversions/clicks) to every rate delta; compute a
  crude CI / small-base floor so the output itself distinguishes signal from noise.

### K5-08 — Proposals carry no evidence linkage and blank-able plans; risk classification is blind to data basis — P2 — VERIFIED_CODE
- Evidence: `write_tools.py:30-44` (`reason` required free text; `measurement_plan`/
  `reversal_plan` default `""`, no `analysis_artifact_id`, no sample size, no window),
  `writes.py:77-125` (classify_risk from operation name/values only). Sources DA-11,
  B3-03/04.
- Description: A proposal cannot be traced to the data that justified it; a budget cut
  backed by 36 conversions and one backed by 3,600 produce identical risk surfaces, and
  the measurement plan can be empty for a budget/status flip. This is the single most
  important enabler of "recommend on insufficient data."
- Recommendation: Require a cited analysis-artifact id, a non-empty measurement + rollback
  plan for budget/status ops, and surface observed sample size + trust tier on the approval
  card. (Backstops today: unenforced prose + the human approval gate — real but not a
  data-sufficiency check. Hence P2, not P1/P0.)

### K5-09 — Merchant-facing overview ROAS tile is structurally 0× and sums across currencies/providers — P2 — VERIFIED_CODE (static)
- Evidence: `reads.ts:54` (`metrics` omits `conversion_value`), `live-data.tsx:33-41`
  (reduces every row; `value += conversion_value ?? 0` → 0; `roas = value/spend` → 0; no
  currency grouping), demo seed ships USD + a SAR Snapchat account (`sandbox-provider.ts`).
  Sources DA-12, A12-01/02, A13-06.
- Description: The first "profitability" number an Arabic-first merchant sees is wrong by
  construction (0×) while the per-campaign table on the same page shows real per-row ROAS;
  the headline Spend/Conversions tiles sum USD + SAR and double-count purchases. The
  upstream `summarizeReport` already groups by currency and reconstructs ROAS, and is not
  used here. Violates the project's own `reporting-semantics.md:15`.
- Recommendation: Request `conversion_value` (or reuse `summarizeReport`), render one tile
  group per currency, label tiles "platform-attributed." Add a test asserting the tile is
  non-zero for sandbox data. (Honest classification: VERIFIED_CODE; I did not run the app.)

### K5-10 — Zero-/three-decimal currency produces a 100×/10× budget write; the declared unit is ignored — P1 — VERIFIED_CODE
- Evidence: `meta/src/provider.ts:20` (`CENTS_TO_MICROS = 10_000`) applied with no currency
  check; `translate.ts:107` same; `translate.ts:86-92,148-152` multiply by 1e6 and drop the
  declared `unit`. Sources DA-15+DA-17, A15-01/05.
- Description: Both the bridge and the Meta provider assume 2-decimal currency. A ¥30,000
  Meta budget is written as ¥3,000,000; the percentage-delta cap compares micros-to-micros
  so it is blind to the error.
- **Severity ruling:** I keep A15's **P1** (serious financial risk / unsafe execution) but
  note explicitly it is **latent**: reachable only on the live-write path, and demo/fixtures
  are USD. It belongs to my seat as a currency/unit trust defect on numbers the product
  *acts on*. Not P0 because it requires live credentials + a non-2-decimal account + an
  approved write.
- Recommendation: Per-currency minor-unit offsets (2/0/3 decimal); validate `after.unit`
  against an enum; JPY/KWD fixtures and an end-to-end bridge test.

### K5-11 — Budget percentage cap bypassed when prior budget unknown; default policy has no absolute ceiling — P2 — VERIFIED_CODE
- Evidence: `engine.ts:143` (pct check skipped when `fromMicros` absent), `policy.ts:15`
  (`max_daily_budget_micros` default `null`). Sources DA-16, A15-03.
- Description: Under shipped defaults, any operation without a known prior budget (every
  create; an Apple update with an unreadable prior) passes with no numeric ceiling.
  Partially mitigated by `paused_creation`, but the budget is still written.
- Recommendation: Reject a `null` absolute cap in production; treat an absent `fromMicros`
  as "cannot verify" → fail closed.

### K5-12 — Two divergent measurement engines with different null semantics; no cross-engine golden test — P2 — VERIFIED_CODE
- Evidence: `compute.py:71-95` (Decimal, sum over present rows) vs `report-summary.ts:19-31`
  (float, `null` unless every row has the metric; spend-weighted ROAS reconstruction).
  Sources DA-09, B1-05.
- Description: The same account/window can yield a different spend/ROAS/CPA and a
  different null-vs-number decision depending on which subsystem rendered it. The
  null-semantics divergence is the material risk; float drift on money is low-magnitude.
- Recommendation: One canonical metric contract (precision, rounding, null policy,
  ratio-basis) enforced by both engines, with a cross-engine golden test.

### K5-13 — Providers coerce missing conversions to 0; the zero-conversion rule then proposes a pause — P3 — VERIFIED_CODE/TEST
- Evidence: `meta/src/provider.ts:591-594` (0 when action absent) and Google/TikTok/
  Microsoft/Reddit/Apple similar; `core-performance.ts:8-29` flags `spend≥50 &
  conversions===0` as critical and attaches `pauseCampaign`. Contradicts
  `reporting-semantics.md:13`. Sources DA-18, A13-04, A12-07.
- Description: A lead-gen / traffic / install campaign reads `conversions:0, ROAS:0`
  indistinguishably from broken tracking; the rule can recommend pausing a healthy
  non-purchase campaign. Mitigated by the preview/approval gate (so P3, not P2).
- Recommendation: Emit `undefined` for absent metrics; have the rule skip rows whose
  conversion metric is absent rather than zero.

### K5-14 — "Below break-even" = ROAS < 1.0, margin-blind — P3 — VERIFIED_CODE
- Evidence: `core-performance.ts:76-99` (threshold 1.0, "below break-even", "tracked
  revenue"); no margin input anywhere. Sources DA-19, A12-03, B6-06.
- Description: True break-even is `1 / contribution-margin`; a 1.8× ROAS campaign that is
  losing money for any merchant with COGS is never flagged, while the label gives false
  reassurance. The only profit-sounding concept in the codebase is wrong for e-commerce.
- Recommendation: Relabel "gross ROAS < 1.0 (revenue < spend)" until a margin profile
  exists; then threshold at `1 / margin` per store/product line.

### K5-15 — Timezone-, pacing- and day-adjacency mislabels (cluster) — P3 — VERIFIED_RUNTIME/CODE
- Evidence: cross-platform total ignores timezone (`compute.py:325` compares `(start,end)`
  only; `TIMEZONE_MISMATCH` never set); pacing divides by active days not window days
  (`summary.py:88-104`) so a 2-of-14-day burst reads `over_budget`; day-over-day change
  compares the nearest *present* day across calendar gaps (`summary.py:108-125`). Sources
  DA-20/DA-24, B1-07/08/09, A13-07, A15-07.
- Description: Each individually low-magnitude, but together they mean several
  product-surfaced labels ("over budget", "day-over-day +X%", a combined cross-TZ total)
  do not mean what the reader assumes.
- Recommendation: Gate combination on matching timezone or flag it; report both active-day
  and window-day pacing; compute day change against the calendar-prior day with a gap
  marker.

## Minimum data-trust requirements (my seat's deliverable)

**No number may carry a computed confidence score, and no recommendation may state a
numeric magnitude, until the figure clears every gate below.** This endorses and tightens
deliverable 10 §5. These are the *floor*, enforced in code (not prose), evaluated at the
moment a figure is surfaced or a proposal is accepted.

1. **Trust tier must be explicit and gating.** Every figure carries its tier (T1 raw-live /
   T2 normalized+flagged / T3 provider-reconciled / T4 cross-platform-compatible / T5
   store-verified). A figure may *drive a proposed action* only at or above the tier
   required for that action class: diagnostics T1+, budget proposals T3+, "profitable /
   incremental / break-even" wording T5 only. (Closes K5-03/04/06/14.)
2. **Reconciliation must be earned, not asserted.** Tri-state; `reconciled=true` requires at
   least one provider-sourced control total that matched (within one minor unit), covering
   conversions/value, not just spend. The tautological self-check alone yields
   `no_external_oracle`. The rendered report must reflect the real value, not a literal.
   (Closes K5-03.)
3. **Maturity gate.** If the current window includes days at or past an unknown or
   still-open `data_complete_through`, the window is `immature`; magnitude claims and
   automated/proposed actions are blocked or down-tiered. Unknown boundary == immature,
   never complete. (Closes K5-06.)
4. **Ratio integrity.** A ratio (CPA/ROAS/CTR/CPM/CVR) is emitted only when its numerator
   and denominator cover the same row/day set; otherwise `unavailable`, never a precise
   number. Extend the missing-metric guard to all four additive metrics. (Closes K5-01/02.)
5. **Sample-sufficiency floor.** A recommendation leaning on a rate metric requires observed
   conversions ≥ a configured floor and clicks ≥ a floor; below it, confidence is forced to
   "insufficient data" and the magnitude claim is suppressed. The day-anomaly flag gets an
   absolute base floor. (Closes K5-07.)
6. **Attribution-compatibility gate.** A cross-platform CPA/ROAS/conversions claim is blocked
   when platforms differ in attribution model/window/conversion event; `ATTRIBUTION_DIFFERS`
   must be populated from a per-row `Attribution` descriptor and actually suppress the
   blended figure. Per-platform figures only, otherwise. (Closes K5-04/05.)
7. **Evidence linkage on every proposal.** `propose_change` must cite the analysis-artifact
   id, window dates, observed sample size and `data_complete_through`; measurement + rollback
   plans must be non-empty for budget/status-flip ops; the approval card must show sample
   size and trust tier. No numeric magnitude without a code-derived basis (or an explicit
