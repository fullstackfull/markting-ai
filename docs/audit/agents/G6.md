## Findings

### G6-01 — RBAC is a coarse flat 4-role model; no custom roles, no per-account/provider scoping
- Severity: P2 | Classification: VERIFIED_CODE
- Evidence: `platform/apps/cloud/lib/cloud/types.ts:7` (fixed enum `owner|admin|member|viewer`); enforcement is scattered boolean checks: `platform/apps/cloud/lib/cloud/dashboard.ts:56-57`, `onboarding.ts:27`, `account-selection.ts:18`, `tenant-admin.ts:10-17`, `plans.ts:93`, `app/api/approvals/[id]/apply/route.ts:21`.
- Description: Roles are a hard-coded enum enforced ad hoc per call site (`['owner','admin'].includes(...)`). There is no permission matrix, no custom/least-privilege roles, no per-ad-account or per-provider access control, and no team/group construct. Effective capabilities: owner/admin = administer (invite, keys, settings, apply, delete-owner-restricted); `member` = can create previews and reject, cannot apply/invite/manage keys; `viewer` = read-only (write scope stripped at `plans.ts:93`). `member` and `viewer` differ only in that a member may reject a pending op (`reject/route.ts:12`).
- Impact: Enterprises/agencies cannot express "this user may only touch Client X's Google account" or "finance approves budgets only". Access is all-or-nothing at the org boundary.
- Recommendation: Introduce resource-scoped permissions (per connection/ad-account), a declarative permission matrix, and optional custom roles.

### G6-02 — Approval workflow is single-approver only; no multi-step/quorum/SLA/delegation, and the API/MCP write path has no second approver at all
- Severity: P2 | Classification: VERIFIED_CODE
- Evidence: `app/api/approvals/[id]/apply/route.ts:19-26` (any single owner/admin applies; requester≠approver check is bypassable via `MARKTING_ALLOW_SELF_APPROVAL`, `lib/markting/env.ts:16`); `app/api/v1/tools/[tool]/route.ts:7-13` (REST/MCP write: the same API key both validates and applies — no human gate). Searches for quorum/delegate/SLA/escalation returned nothing.
- Description: Dashboard approval = exactly one owner/admin presses apply; the only control is the "creator cannot approve" rule, which a single env flag disables. There is no sequential/multi-step approval, no N-of-M quorum, no budget-threshold-driven approval tiers, no SLA/auto-escalation on pending ops (they merely expire via `pending_ttl_minutes`, default 15, `platform/packages/core/src/policy/policy.ts:19`), and no delegation/out-of-office. Separately, the REST/MCP tool path (`v1/tools/[tool]`) executes writes directly under one credential with no approval step at all — separation-of-duties exists only for dashboard-originated bridge operations.
- Impact: No separation of duties for automated writes; regulated/enterprise change-control (e.g. two-person rule for ad spend) cannot be satisfied.
- Recommendation: Add configurable approval policies (threshold-based, N-of-M, role-targeted), SLA/escalation timers, delegation, and an option to force API/MCP writes through the pending-approval queue.

### G6-03 — "Separate client workspaces" is a paid, advertised feature that is not implemented
- Severity: P1 | Classification: VERIFIED_CODE
- Evidence: `platform/apps/cloud/lib/cloud/plans.ts:20,38,42` (`clientWorkspaces: true` for agency & enterprise); shown to customers at `app/dashboard/billing/page.tsx:95` with copy `lib/i18n/messages/billing.ts:53` ("Separate client workspaces" / "مساحات عمل منفصلة للعملاء"). The flag is read **only** in the billing page bullet — grep found no code consuming it to create, isolate, or switch between client workspaces, and no schema for sub-accounts/parent-child orgs (`migrations/20260817171039_cloud_initial_schema.sql` has only flat `organizations` + `organization_memberships`).
- Description: Agencies are sold "separate client workspaces" and "client workspaces" as the Agency/Enterprise differentiator, but the only isolation unit in the data model is the flat organization. There is no code path to partition one organization's connections/ad accounts/audit into per-client workspaces.
- Impact: Agencies (the named target market) cannot segregate clients. The feature is billed but absent — functional deficiency plus a misrepresentation/financial-risk exposure.
- Recommendation: Either implement workspace partitioning (parent org + child workspaces with scoped connections, billing roll-up, and workspace-scoped roles) or remove the feature claim from paid tiers until shipped.

### G6-04 — No enterprise SSO (SAML/OIDC) or SCIM, despite the Enterprise tier advertising "Includes SSO"
- Severity: P2 | Classification: VERIFIED_CODE
- Evidence: `app/login/actions.ts:8` (`socialProviders = new Set(['google','github'])`) + password sign-in only; `lib/i18n/messages/billing.ts:58` enterprise copy "Includes SSO…"; `config.toml` external providers are consumer social OAuth, no SAML; no SCIM endpoint exists (`find app -type d | grep scim` → none).
- Description: Authentication is Supabase email/password + Google/GitHub social OAuth. There is no SAML/enterprise OIDC IdP integration, no SCIM user provisioning/deprovisioning, and no domain-capture/auto-join. Membership is manual invite only (`tenant-admin.ts:26`).
- Impact: Enterprises cannot enforce centralized identity, automatic offboarding, or SSO — a hard procurement blocker and a contradiction of the sold Enterprise feature.
- Recommendation: Add SAML/OIDC (Supabase Pro SSO or equivalent) and SCIM provisioning; gate behind the enterprise entitlement.

### G6-05 — Audit log cannot be exported; UI is capped, unfiltered, and hides actor identity
- Severity: P2 | Classification: VERIFIED_CODE
- Evidence: `app/dashboard/audit/page.tsx` renders `listAuditEvents(org,150)` as a table with no export/download/CSV/API; actor column shows only generic `actorApiKey`/`actorMember`/`actorSystem`, never the person/email. `repository.ts:719-731` (`listAuditEvents` hard-limited; `countAuditEvents` exists but UI ignores it — no pagination/date filter). No audit-export route under `app/api`.
- Description: The audit view is a last-150-rows table with no way to export for SIEM/compliance, no time-range or actor/provider filters, and no per-actor attribution in the UI. `actor_user_id` is stored but never resolved to a name/email for display.
- Impact: Compliance teams cannot pull a full, filterable, exportable trail; you cannot determine *who* did something from the dashboard.
- Recommendation: Add a paginated, filterable audit view and an export API (CSV/JSON) plus SIEM streaming; resolve and display actor identity.

### G6-06 — Audit trail is non-durable and loses attribution: hard-deleted by retention cron, actor nulled on user delete, no IP/user-agent
- Severity: P2 | Classification: VERIFIED_CODE
- Evidence: `migrations/20260817171039_cloud_initial_schema.sql:150-168` (`audit_events`: `actor_user_id … on delete set null`, no IP/user-agent columns); `migrations/20260828120000_cloud_plans_and_account_scope.sql:131-164` (`private.apply_data_retention()` `delete from public.audit_events … created_at < now() - retention`) scheduled daily via `cron.schedule('adport-data-retention','17 3 * * *', …)` (`20260817…:408`). Default retention 30 days (`20260828…:83`).
- Description: Audit events are **hard-deleted** after `data_retention_days` (default 30) with no archival or immutable export, deleting a user **nulls** their audit attribution (`on delete set null`), and no source IP or user-agent is captured. This is the opposite of an immutable/forensic audit trail.
- Impact: Fails SOC 2 / financial-audit expectations (tamper-evident, long-retained, attributable logs); forensic reconstruction after offboarding is impossible.
- Recommendation: Capture IP/user-agent, preserve actor identity (snapshot email, restrict the FK action), and archive audit events to immutable/WORM storage before retention purge.

### G6-07 — API keys never expire, are org-wide, and support only two coarse scopes
- Severity: P3 | Classification: VERIFIED_CODE
- Evidence: `repository.ts:292-313` (`createApiKey` inserts without `expires_at`); `migrations/20260817171039_cloud_initial_schema.sql:110-124` (`expires_at` column exists but is only honored at auth time, `repository.ts:331`); scopes constrained to `tools:read`/`tools:write` (`api-keys/route.ts:11`, schema check `scopes <@ {tools:read,tools:write}`). `authenticateApiKey` returns no role (`repository.ts:333`); for keys `role` stays undefined so `writeAllowed` in `plans.ts:93` is not blocked by a viewer role.
- Description: Keys are created with no expiry (no rotation/TTL enforcement), are scoped to the whole organization (no per-account/provider restriction), and offer only read vs write. `connections:manage`/`keys:manage` are session-only and never grantable to a key (fine), but there is no mechanism for short-lived or least-privilege machine credentials.
- Impact: Long-lived org-wide secrets with no rotation increase blast radius; cannot issue a key limited to one client/account.
- Recommendation: Default/forced key expiry + rotation reminders; resource-scoped key scopes.

### G6-08 — MFA is disabled in configuration; no org-level MFA enforcement
- Severity: P2 | Classification: VERIFIED_CODE (config) / DOCUMENTED_ONLY (hosted override possible)
- Evidence: `platform/supabase/config.toml:303-304` (`[auth.mfa.totp] enroll_enabled=false, verify_enabled=false`) and `:308-309` (phone MFA disabled); WebAuthn block commented out.
- Description: The committed Supabase config disables TOTP and phone MFA entirely, and there is no application-level "require MFA for org members" control.
- Impact: No second factor for human sign-in; enterprises that mandate MFA cannot be satisfied by the product as configured. (A hosted Supabase project could re-enable factors in its own dashboard, hence not fully VERIFIED_RUNTIME.)
- Recommendation: Enable TOTP/WebAuthn and add an org policy to require MFA (and step-up for apply/delete).

### G6-09 — No organization hierarchy / teams / groups / consolidated billing
- Severity: P3 | Classification: VERIFIED_CODE
- Evidence: `migrations/20260817171039_cloud_initial_schema.sql:25-47` — `organizations` (flat, no parent_id) + `organization_memberships` (flat (org,user,role)); `organization_subscriptions` is per-org (`plans.ts:getOrganizationEntitlement`). No teams/groups/workspace tables.
- Description: The tenancy model is a single flat level: one org, one membership list, one subscription. Multi-brand enterprises or agencies with many clients must spin up independent orgs with duplicated connections, separate billing, and no cross-org role, parent-admin visibility, or consolidated invoicing.
- Impact: Does not scale to enterprise/agency org structures; administration and billing fragment across orgs.
- Recommendation: Add an org hierarchy (parent account → workspaces/teams), cross-org admin roles, and roll-up billing.

### G6-10 — Offboarding/deletion is synchronous, revokes only Google at the IdP, and ignores the designed deletion-request lifecycle; no data export (DSAR)
- Severity: P3 | Classification: VERIFIED_CODE
- Evidence: `app/api/deletion/route.ts:13-24` — owner-only; revokes only `loadGoogleCredential`/`revokeGoogleToken`, then immediate `delete from public.organizations`; other providers' external OAuth grants are not revoked (DB rows cascade-deleted only). The `deletion_requests` table + `deletion_status` enum (`requested|processing|completed|failed`, `migrations/20260817171039_cloud_initial_schema.sql:184+`) are designed for an async lifecycle but unused here. No org data-export/portability endpoint exists.
- Description: Org deletion hard-deletes immediately, leaving Meta/TikTok/Microsoft/Reddit/etc. grants live at the provider, and does not use the tracked deletion-request workflow. There is no GDPR/DSAR data export before deletion.
- Impact: Residual third-party authorizations after offboarding; no portability; weaker compliance story.
- Recommendation: Revoke all provider grants on deletion, drive deletion through the tracked `deletion_requests` lifecycle, and offer a pre-deletion data export.

## What a world-class system would need (gaps, concrete)
- Resource-scoped RBAC (per connection/ad-account), custom roles, and a central permission matrix instead of scattered `includes()` checks.
- Configurable approval policies: budget-threshold tiers, N-of-M quorum, sequential multi-step chains, delegation/out-of-office, SLA timers with auto-escalation; option to force API/MCP writes through human approval.
- Real agency/enterprise tenancy: parent account → client workspaces/teams with scoped connections, workspace-scoped roles, and consolidated billing (deliver the sold `clientWorkspaces`).
- Enterprise identity: SAML + OIDC SSO, SCIM provisioning/deprovisioning, domain auto-join, enforced MFA with step-up on apply/delete.
- Compliance-grade audit: IP/user-agent capture, immutable/WORM archival, preserved actor identity, full filterable + exportable log, SIEM streaming, and retention as archive-then-purge (not hard delete).
- Machine-credential hygiene: scoped, expiring, rotatable API keys; key-to-account binding.
- Complete offboarding: revoke all provider grants, tracked deletion lifecycle, DSAR/data-export before deletion.

## Disagreements / claims in docs that the code contradicts
- Billing Enterprise copy "Includes SSO … SLA …" (`lib/i18n/messages/billing.ts:58`) — no SSO/SAML/OIDC and no SLA/escalation logic in code (`login/actions.ts:8`; no approval SLA).
- Billing Agency/Enterprise feature "Separate client workspaces" (`billing.ts:53`, plan flag `plans.ts:38/42`) — no implementation; flag consumed only to render a bullet (`billing/page.tsx:95`).
- Retention framed as "longer audit history" upsell (`lib/i18n/messages/support.ts:38`) — retention cron **hard-deletes** audit events with no archival (`apply_data_retention`), so history is destroyed, not preserved.
