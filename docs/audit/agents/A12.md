# A12 — E-commerce performance marketing expert

Audit question: what does MARKTING-AI actually have for **business-profit optimization** versus
**platform-reported ROAS**, and what would it need to optimize for real merchant profit?

Short answer (details and citations below): every number the system computes, surfaces, labels
"ROAS", or flags as "below break-even" is derived from **ad-platform-attributed conversion value**.
There is no store, order, refund, COGS, margin, CAC, MER or FX concept anywhere in code. The
engine's arithmetic over that platform data is careful and well-tested; the adport cloud overview
that most merchants will look at first is not (its headline ROAS tile is structurally 0× and its
headline spend tile sums currencies). `docs/TODO.md` is honest that store revenue "does not exist
yet"; the only place code *claims* a profit concept ("break-even") implements ROAS < 1.0, which is
only break-even for a merchant with 100 % gross margin.

## Findings

### A12-01 — Overview "ROAS" tile is structurally 0×: `conversion_value` is never requested
- **Severity:** P2  **Classification:** VERIFIED_CODE (static call chain; runtime not executed)
- **Evidence:**
  - `platform/apps/cloud/app/api/dashboard/summary/route.ts:9` → `readReport(principal, 'last_7_days')`
  - `platform/apps/cloud/lib/cloud/reads.ts:54` requests `metrics: ['spend', 'impressions', 'clicks', 'conversions', 'roas']` — `conversion_value` is absent
  - Providers project output to exactly the requested metrics: `platform/packages/meta/src/provider.ts:230` (`Object.fromEntries(query.metrics.map((m) => [m, all[m]]))`), `platform/apps/cloud/lib/markting/sandbox-provider.ts:138` (same pattern), `platform/packages/snapchat/src/provider.ts:151` (`metrics.filter(...)`)
  - `platform/apps/cloud/app/dashboard/live-data.tsx:40` sums `row.metrics.conversion_value ?? 0`; `:41` `roas = totals.spend > 0 ? totals.value / totals.spend : 0`
  - Footnote shown to the merchant: `platform/apps/cloud/lib/i18n/messages/overview.ts:25,62` "Conversion value ÷ spend" / "قيمة التحويلات ÷ الإنفاق"
- **Description:** `totals.value` is always 0 because no row ever carries `conversion_value`; whenever spend > 0 the headline tile renders `0×` while the per-campaign table on the same page (`live-data.tsx:76`) shows the real per-row `roas`. The upstream `summarizeReport` has a correct fallback (`platform/packages/core/src/report-summary.ts:105-107`: spend-weighted reported ROAS when value is absent) but the overview does not use it.
- **Impact:** The first "profitability" number an Arabic-first merchant sees on the dashboard is wrong by construction. In demo mode it is also wrong (sandbox rows go through the same projection). This is upstream adport code (commit `fa7bf19` import; `4bbb55d` touched only copy).
- **Recommendation:** Either add `conversion_value` to the requested metrics in `reads.ts:54` or compute the tile with `summarizeReport` (which already returns `roas_method`). Add a test asserting the tile is non-zero for sandbox data. Separately label the tile "platform-attributed".

### A12-02 — Overview totals add spend and value across providers and currencies
- **Severity:** P2  **Classification:** VERIFIED_CODE
- **Evidence:**
  - `platform/apps/cloud/app/dashboard/live-data.tsx:34-41` reduces every row into one `spend`/`value`/`conversions` total with no grouping by currency, provider or account
  - adport's own contract: `platform/docs/reporting-semantics.md:15` "Never sum monetary values across accounts with different currencies"; `:31` "Adport does not deduplicate cross-platform conversions"
  - Demo seed ships mixed currencies: `platform/apps/cloud/lib/markting/sandbox-provider.ts:164-168` (three USD accounts + one **SAR** Snapchat account) and `SANDBOX_ALIASES` `:331` `currency: 'SAR'`
  - The core library already does this correctly: `platform/packages/core/src/report-summary.ts:85-119` groups by currency and refuses to average ratios; tested in `platform/packages/core/test/report-summary.test.ts:9-50`
- **Description:** The headline "Spend" and "Conversions" tiles are a raw sum of USD + SAR and of Meta-attributed + Google-attributed purchases. For a KSA merchant with a SAR Snapchat account and a USD Meta account this misstates spend by the FX ratio (~3.75×) and double counts purchases both platforms claim.
- **Impact:** Headline KPIs in the Arabic-first product violate the project's own reporting semantics; the demo (the configuration every evaluator will see first) exercises the bug.
- **Recommendation:** Render one tile group per currency (reuse `summarizeReport` groups) and caption conversions as "platform-attributed, not deduplicated".

### A12-03 — "Below break-even" rule equates break-even with ROAS 1.0; no margin exists anywhere
- **Severity:** P3 (mislabel; informational rule, human must act)  **Classification:** VERIFIED_CODE
- **Evidence:**
  - `platform/packages/core/src/audit/packs/core-performance.ts:76-99`: rule `negative-roas`, description "ROAS is below break-even" (`:79`), predicate `(row.metrics.roas ?? 0) < 1` (`:88`), title "(below break-even)" (`:93`), detail calls `conversion_value` "tracked revenue" (`:94`)
  - No margin/COGS/fee input in `RulePack.defaults` (`:105-111`) or anywhere in the repo (grep above)
  - Marketing repeats the claim: `platform/website/index.html:330` "ROAS 0.8×, below break-even"
  - The engine wiki knows better: `engine/workspace/skills/paid-media-wiki/goals-and-economics.md:24` "gross margin or allowable acquisition cost when supplied"
- **Description:** Break-even ROAS for a store is `1 / contribution-margin %` (e.g. 2.5× at 40 % margin, before refunds, shipping, payment fees and VAT treatment). The rule stays silent for a campaign at 1.8× ROAS that is losing money for every merchant with COGS, and the recommendation text ("Check margins") pushes the arithmetic onto the human.
- **Impact:** The only profit-sounding concept in the codebase produces false reassurance for e-commerce accounts.
- **Recommendation:** Rename to "ROAS below 1.0 (revenue < spend)" until a margin profile exists; once it exists, make the threshold `1 / margin` per store/product line and label the input source.

### A12-04 — Engine cross-platform scorecard sums platform-attributed conversions/value across platforms into one "ROAS"
- **Severity:** P3  **Classification:** VERIFIED_CODE
- **Evidence:**
  - `engine/src/paid_media_agent/tools/compute.py:278-298` `_combine` sums `conversions` and `conversion_value` across platforms and derives `roas`, `cpa`
  - `engine/src/paid_media_agent/reports/render.py:124-135` renders that total as the report scorecard when currencies match and windows are complete
  - Doctrine: `engine/workspace/skills/paid-media-wiki/metrics-and-attribution.md:66-68` "Do not add their conversion counts as if they were deduplicated people or incremental outcomes"
  - Mitigations present: caveat line `render.py:168-171` ("conversions use each platform's own attribution; they are not deduplicated people"); the model-facing `AnalysisSummary` exposes only the spend total (`compute.py:403-406`); total suppressed on mixed currency / incomplete window / missing metric (`compute.py:316-325`)
- **Description:** The rendered cross-platform ROAS is "sum of what each platform claims ÷ total spend", which is neither MER (needs store revenue) nor a deduplicated figure. It is labeled as a total and caveated, so this is a doctrine/implementation inconsistency rather than silent error.
- **Recommendation:** In the scorecard, present cross-platform `conversions`/`conversion_value`/`roas` as "sum of platform-attributed" with the caveat on the row itself, and reserve "blended ROAS / MER" for a store-revenue numerator.

### A12-05 — Normalizer's `action_values` mapping can never parse Meta's list shape
- **Severity:** P3  **Classification:** VERIFIED_RUNTIME
- **Evidence:** `engine/src/paid_media_agent/tools/normalize.py:173` `_VALUE_KEYS = (..., "action_values")`; `:202-208` `_decimal` does `Decimal(str(value))` which raises on a list and returns `None`. Probe (exit 0): a Meta-shaped row with `action_values=[{"action_type":"omni_purchase","value":"55.0"}]` normalizes to `conversion_value=None`, `missing=('conversion_value',)`, flag `missing_metric`.
- **Description:** Behavior is *safe* (missing, not zero — and the cross-platform total is then suppressed via `MISSING_METRIC`), but the key is dead code for the one platform that uses it, and the generic key `"value"` (`:173`) is ambiguous (fixtures use it for conversion value; other payloads may not). What Pipeboard actually emits for Meta is NOT_VERIFIED here.
- **Recommendation:** Parse `action_values` by `action_type` (omni_purchase) explicitly, and document per-platform value semantics in the normalizer.

### A12-06 — `aggregate()` / `summarize_window` do not guard against mixed currencies inside one artifact
- **Severity:** P3  **Classification:** VERIFIED_RUNTIME
- **Evidence:** `engine/src/paid_media_agent/tools/compute.py:71-95` sums `spend` with no currency check; `tools/summary.py:132` reports `selected[0].currency` for the whole window. `compare_platform` does guard (`compute.py:149-151`, raises `ComputeError("mixed currencies ...")`). Probe: `aggregate([USD 10, SAR 10])` → `spend=20.000000`, `roas=10.000000`, no error.
- **Description:** Low likelihood today because every read artifact is one account with one currency (`tools/reads.py:246`), but the invariant is enforced in only one of the two compute entry points.
- **Recommendation:** Hoist the single-currency assertion into `aggregate()` or into `summarize_rows`.

### A12-07 — adport providers coerce missing purchase data to 0, contradicting `reporting-semantics.md`
- **Severity:** P3  **Classification:** VERIFIED_CODE
- **Evidence:** `platform/packages/meta/src/provider.ts:591-594` `actionValue` returns `0` when no `omni_purchase` stat exists; `:198-214` `conversions`, `conversion_value`, `cpa`, `roas` all become `0` (not null) for a campaign with no purchases; `platform/packages/google/src/provider.ts:187-202` `num()` defaults to 0 and `roas: spend > 0 ? ... : 0`; `platform/packages/tiktok/src/provider.ts:148-164` same pattern. Contract: `platform/docs/reporting-semantics.md:13` "Missing metrics remain absent. Adport does not turn an unavailable value into zero." Snapchat is closer to the contract (`snapchat/src/provider.ts:138-150` leaves a metric undefined when the raw field is absent, but still emits `0` for a zero denominator).
- **Impact:** A campaign whose pixel is broken reads "CPA 0, ROAS 0" rather than "unavailable"; the `zero-conversion-spend` rule (`core-performance.ts:8-30`) and any ROAS-based reasoning cannot distinguish "no purchases" from "no tracking". The engine side gets this right (`domain/metrics.py:1`, `normalize.py:287-288`).
- **Recommendation:** Emit `undefined` for ratios with zero denominators and for value metrics the provider did not return; keep `0` only when the provider literally reported zero.

### A12-09 — Per-provider "conversion" definitions differ and the UI does not say which
- **Severity:** P3  **Classification:** VERIFIED_CODE (definitions) / INFERRED (attribution defaults)
- **Evidence:** Meta counts only `omni_purchase` actions and values (`meta/src/provider.ts:201-203`), with no `action_attribution_windows`/`use_unified_attribution_setting` parameter sent (`:174-186`; grep for `attribution` in `platform/packages/meta/src/*.ts` returned nothing), so the account default window (click + view-through) applies. Google uses `metrics.conversions`/`metrics.conversions_value`, i.e. every conversion action included in "Conversions" (leads, calls, purchases) (`google/src/provider.ts:160,190-193`). TikTok uses `conversion` (all optimisation events) for the count but purchase value for the value (`tiktok/src/provider.ts:150-153`); the claim that `total_complete_payment_rate` is total purchase value is a code comment I could not verify against TikTok docs (NOT_VERIFIED). Snapchat uses `conversion_purchases(_value)` (`snapchat/src/provider.ts:14,139`); Microsoft `Revenue` (`microsoft/src/provider.ts:179,228-234`); Spotify `PURCHASES`/`REVENUE` (`spotify/src/provider.ts:16`).
- **Description:** "Conversions" means purchases on Meta/Snap/Spotify but any configured action on Google/TikTok; "ROAS" on Meta may include view-through value. `reporting-semantics.md:31-33` documents the caveat, but neither the cloud tables (`live-data.tsx:66-76`, `reports/page.tsx:33-44`) nor the engine scorecard definition "conversion_value / spend" (`reports/render.py:39`) carries the per-provider definition.
- **Recommendation:** Attach a `conversion_definition` and `attribution` descriptor to every provider row (and to engine `PerformanceRow.source_fields`), render it as a footnote, and pin Meta's attribution window explicitly.

## What a world-class system would need (design only — nothing here is implemented)

Goal: make every recommendation and every "is this profitable?" answer rest on **store-verified
contribution profit**, with platform ROAS demoted to a leading indicator. The design below fits the
existing architecture (engine = read-only analysis + proposals; adport = credentials, policy, writes).

### 1. Entities (adport side, Postgres, org-scoped like `markting_*`)

- `markting_store_connections` — org_id, platform (`salla`, `zid`, `shopify`, `woocommerce`, `custom_webhook`), store_ref (opaque alias, never the merchant id in prompts), encrypted OAuth/refresh tokens (same KMS path as provider credentials), store currency, store timezone, VAT mode (prices inclusive/exclusive, 15 % KSA), status, last_sync_at, scopes (read-only; writes refused at the type level).
- `store_orders` — store_ref, order_id, created_at (store TZ), status lifecycle (`placed`, `paid`, `shipped`, `delivered`, `cancelled`, `returned`, `refunded`), payment method (`card`, `mada`, `apple_pay`, `cod`, `bnpl_tabby`, `bnpl_tamara`), gross_subtotal, discounts, shipping_charged, vat, gross_total, currency, customer_ref (hashed), is_first_order, attribution hints (utm_*, `fbclid`, `gclid`, `ScCid`, `ttclid`, landing page, referrer), raw payload hash.
- `store_order_lines` — order_id, sku, qty, unit_price, unit_cogs (snapshot at order time), category.
- `store_refunds` — order_id, refunded_at, amount, reason, restock flag.
- `product_costs` — store_ref, sku, cogs, effective_from/to, source (`manual`, `csv`, `salla_cost_field`), confidence.
- `margin_profiles` — store_ref, default gross margin %, shipping cost per order, payment fee % by method (mada/card/BNPL), packaging, COD failure rate, return rate by category; used when SKU-level COGS is absent; each field carries `source` and `as_of`.
- `fx_rates` — base, quote, rate, as_of, source (e.g. SAMA/ECB), used only for *presentation* across ad accounts in different currencies; never for store revenue (store currency is canonical).
- `profit_targets` — store_ref, objective (`profit`, `revenue_growth`, `cac_cap`), target break-even ROAS derived from margin, allowable CAC for new customers, payback horizon; versioned.
- `daily_store_facts` (materialized, immutable per `as_of`) — store_ref, date, orders, new_customer_orders, gross_revenue, net_revenue (ex-VAT, ex-discount), refunds_to_date, cancellations_to_date, COGS, contribution_profit, by acquisition channel bucket (`paid_meta`, `paid_google`, `paid_snap`, `paid_tiktok`, `organic`, `direct`, `unknown`).

### 2. Data flows

1. **Ingest:** OAuth per store (Salla/Zid both expose OAuth 2 + webhooks; Shopify Admin API; Woo REST). Pull orders incrementally by `updated_at`, subscribe to order/refund webhooks, verify signatures, store raw payload + hash, upsert `store_orders`. Read-only scopes; the adport policy engine gets a `store_write` denylist so no tool can ever mutate a store.
2. **Recognize revenue by status, not by placement:** for KSA COD-heavy merchants, placement ≠ sale. Report three columns: placed gross, delivered net, and net after returns, each with a maturity window (e.g. 14 days delivered, 30 days returns). Mark figures inside the window as `immature`.
3. **Cost attach:** join lines to `product_costs` by SKU/effective date; fall back to `margin_profiles` with an explicit `estimated` flag that propagates to every derived number.
4. **Engine read tool (`get_store_facts`)** in `assembly.py` core tools, following `customization.md:161-170`: bounded aggregates only, by day and channel bucket, in store currency, with `as_of`, `maturity`, `estimated_fields`, and a content hash. No raw orders or customer data in model context.
5. **Deterministic compute extension:** a new `profit_compute.py` beside `compute.py` producing a `ProfitComparison` artifact (`profit-comparison/1`): MER = net_revenue ÷ total paid spend (same currency only, else suppressed); contribution profit after ads = contribution_profit − spend; break-even ROAS = 1 ÷ contribution-margin %; CAC = spend ÷ new_customer_orders; per-platform *attributed* ROAS kept side by side with store MER. All rules from `compute.py` (None never zero, equal windows, completeness flags, reconciliation checks) apply.
6. **Report:** add a "Business outcomes" scorecard section (the wiki already requires it, `reporting.md:12`) with two columns per metric: platform-attributed vs store-verified, plus the gap. Arabic rendering is a separate TODO (`docs/TODO.md:27`).
7. **Decision layer:** proposals cite `ProfitComparison` artifact ids; the policy engine gains a rule "no budget increase when store MER is below break-even for the matured window" and "no automated action on `estimated` margins".

### 3. Reconciliation (what must agree before a number is shown)

- Sum of `store_order_lines` = `store_orders.gross_subtotal`; orders by day reconcile to the store's own daily totals endpoint where available (Salla/Zid report APIs).
- Platform-attributed purchases per day ≤ store orders per day × (1 + tolerated view-through factor); flag `ATTRIBUTION_EXCEEDS_STORE` when platforms together claim more purchases than the store recorded.
- Platform `conversion_value` vs store `gross_total` for click-id-matched orders: report match rate; below a threshold, downgrade trust.
