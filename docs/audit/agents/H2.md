## Findings

### H2-01 — Zero CI runs on push or PR at the monorepo root
- **Severity:** P1
- **Classification:** VERIFIED_CODE
- **Evidence:** root `ls -la .github` → does not exist; `find . -type d -name workflows` returns only `platform/.github/workflows` and `engine/.github/workflows`; `git rev-parse --show-toplevel` → `/home/user/markting-ai` (the monorepo is the git root, not `platform/` or `engine/`).
- **Description:** GitHub Actions only evaluates workflow YAML found at `<repo-root>/.github/workflows/`. The git root here is `/home/user/markting-ai`, which has no `.github` directory. The six workflow files that exist are nested at `platform/.github/workflows/` and `engine/.github/workflows/` — paths GitHub never reads for this repository. Therefore **nothing runs today** on `push`, `pull_request`, tag, or schedule.
- **Impact:** No automated gate on any merge. Typecheck, lint, tests, secret scanning, and release automation that the upstream projects relied on are all silently inert in this monorepo. Regressions, leaked secrets, and cross-tenant bugs (the DB suites below) reach `main` with no mechanical check. This is a production-readiness blocker.
- **Recommendation:** Add `.github/workflows/` at the repo root (spec in "What a world-class system would need").

### H2-02 — Six upstream workflows are tracked but orphaned, creating a false impression of CI coverage
- **Severity:** P2
- **Classification:** VERIFIED_CODE
- **Evidence:** `git ls-files platform/.github/workflows/ engine/.github/workflows/` lists all six as tracked; `docs/PHASE0-REPORT.md:24` and `:44` cite "`.github/workflows/ci.yml`" as the build/test authority; `docs/ARCHITECTURE.md:863` references "`platform/.github/workflows/ci.yml`" as the CI that omits DB tests.
- **Description:** The vendored `platform/.github/workflows/ci.yml` (node 22/24 matrix: `pnpm build/typecheck/test`, provider-page check, connector-catalog guard, CLI fail-closed smoke), `platform/.github/workflows/release.yml` (npm publish with provenance), `platform/.github/workflows/verify-release.yml`, `engine/.github/workflows/ci.yml` (ruff check + ruff format --check + mypy strict + pytest + fixture demo + MDA import smoke, plus a gitleaks history scan), `engine/.github/workflows/compatibility.yml` (weekly `uv lock --upgrade` smoke), and `engine/.github/workflows/release.yml` (uv build + GH release) are all intact and well-formed — but none execute at the monorepo root. They read as if CI exists; docs cite them as the source of truth.
- **Impact:** Readers (and the phase reports) assume these gates run. They do not. The gap is invisible unless someone checks the Actions tab. Also, if someone later promotes `platform/` or `engine/` to its own repo the files work, but in this monorepo they are dead weight that misleads.
- **Recommendation:** Either delete/relocate the orphaned trees with a note, or (better) author a single root pipeline that invokes each suite with the correct `working-directory`, and update the docs that cite the subdir paths.

### H2-03 — The net-new "glue" code (markting bridge, engine-demo host, infra scripts) has no CI gate at all
- **Severity:** P2
- **Classification:** VERIFIED_CODE
- **Evidence:** `make test` (`Makefile:51-54`) is the only aggregate harness and runs locally only — it is wired into no workflow. It runs: `pnpm --filter @adport/cloud exec vitest run` over the six `markting-*`/`i18n` suites; `uv run python -m pytest ../services/engine-demo/tests`; `node --test infra/scripts/stripe-setup.test.mjs`. The upstream `platform` CI runs `pnpm test` (turbo) which does **not** target `apps/cloud` markting suites by the same path, and the upstream `engine` CI runs `pytest -q` scoped to `engine/tests`, not `services/engine-demo/tests`. No workflow anywhere invokes `make test`, the infra `.test.mjs`, or `services/engine-demo/tests/test_demo_api.py`.
- **Description:** The modules this project actually adds (`platform/apps/cloud/lib/markting/**`, the assistant/approvals/reports API routes, the engine-demo serving host, the Stripe/seed infra scripts) are exercised only by `make test`, run by hand. The CI that upstream shipped covers upstream code, not the integration layer that is markting-ai's whole reason to exist.
- **Impact:** The highest-risk, least-reviewed code (tenant bridge, sandbox write policy, billing scripts) is the part with zero automated gating. A regression in `lib/markting/repository.ts` or `serve_demo.py` passes review with no mechanical check.
- **Recommendation:** Make the root pipeline run `make test` (or its three sub-commands) as a first-class job.

### H2-04 — `markting-repository.database.test.ts` (tenant-isolation DB suite) runs in no CI and would need a Supabase/Postgres service
- **Severity:** P2
- **Classification:** VERIFIED_CODE
- **Evidence:** `platform/apps/cloud/test/markting-repository.database.test.ts:13` gates on `process.env.ADPORT_RUN_DATABASE_TESTS === '1'` and `:16` requires `SUPABASE_DB_URL`; `make test` (`Makefile:52`) lists only the non-`.database` markting suites, so even locally the DB suite is skipped by default; `grep 'services:' platform/.github/workflows/ci.yml` → empty (upstream CI provisions no DB); `docs/ARCHITECTURE.md:863` states DB tests are "not run in CI".
- **Description:** Four `*.database*.test.ts` suites exist, including `markting-repository.database.test.ts` which directly asserts cross-tenant behavior (two orgs, `claimThread`, alias maps, `provenanceForPending`). All are `describe.skip` unless a live Supabase stack is wired in. Nothing — not `make test`, not any workflow — provides that stack.
- **Impact:** The tests that would catch a cross-tenant data leak on the bridge tables are never executed mechanically. Tenant isolation is asserted only by hand-run, env-gated suites. Given P0 sensitivity of tenant isolation, the absence of a CI job with a Postgres service is a material reliability gap.
- **Recommendation:** Root CI cloud job must stand up a Postgres/Supabase service (service container or `supabase start`), set `ADPORT_RUN_DATABASE_TESTS=1` + `SUPABASE_DB_URL`, apply migrations (incl. `20261002000000_markting_bridge.sql`), and run the `.database` suites.

### H2-05 — No Docker image build or root-level secret scan in any (would-be) pipeline
- **Severity:** GAP
- **Classification:** VERIFIED_CODE (absence) / DOCUMENTED_ONLY (acknowledged)
- **Evidence:** `docs/TODO.md:21` explicitly lists as outstanding: "Docker images built in CI (this sandbox could not reach `deb.debian.org`), secrets scanning (the engine repo ships `.gitleaks.toml`), a CI workflow that runs `make test` plus the upstream suites, and a `scripts/check-upstream-edits.sh`". `find . -iname '*gitleaks*'` → only `engine/.gitleaks.toml`; the only gitleaks job (`engine/.github/workflows/ci.yml:37-56`) runs `gitleaks git .` from the `engine/` working dir, so it scans only the engine subtree's history and is itself orphaned. Three Dockerfiles exist (`engine/Dockerfile`, `infra/cloud.Dockerfile`, `engine/sandbox/Dockerfile`) and `docker-compose.yml:12-38` builds `cloud` and `engine` — but no workflow builds them.
- **Description:** The project self-documents (`docs/TODO.md:21`) that CI docker builds, repo-wide secret scanning, and a `make test` workflow are not yet done. Gitleaks config and SHA-pinned install exist only inside the engine upstream job; there is no root-scoped scan over the monorepo history where the markting glue, infra scripts, and `.env.example` live.
- **Impact:** No image is proven buildable per-commit; a leaked credential in the glue/infra code or history is not caught (engine's scan does not cover `platform/`, `infra/`, `services/`, or `docs/`). These are known gaps, correctly flagged in TODO — not hidden defects.
- **Recommendation:** Add a root `gitleaks` job (reuse `engine/.gitleaks.toml` or a root config, scan full history) and a docker-build job for `cloud` + `engine` images. Note the docker build is unverifiable here (H2-07).

### H2-06 — Upstream platform CI pins `actions/checkout@v7` and `actions/setup-node@v7`; copying verbatim to root may not resolve
- **Severity:** P3
- **Classification:** NOT_VERIFIED
- **Evidence:** `platform/.github/workflows/ci.yml:21,23`, `release.yml:24,28`, `verify-release.yml:21` use `actions/checkout@v7` and `actions/setup-node@v7`; engine workflows use `actions/checkout@v4` / `astral-sh/setup-uv@v5-v6`.
- **Description:** The adport workflows pin major versions (`@v7`) that may not exist in the GitHub Actions marketplace. I cannot reach the marketplace from this sandbox to confirm which majors are published, so I cannot assert they fail — only that the pins are inconsistent with the engine workflows and higher than the versions commonly available. If a root pipeline copies these steps unchanged, resolution could fail at runtime.
- **Impact:** Potential immediate CI breakage if the pinned major does not exist; at minimum a maintenance inconsistency across the two subtrees.
- **Recommendation:** When authoring the root pipeline, pin action versions to a known-good, SHA- or tag-verified set and keep them consistent across jobs. Verify availability against the live marketplace (NOT_VERIFIED here).

### H2-07 — Docker build cannot be validated in this sandbox
- **Severity:** GAP
- **Classification:** NOT_VERIFIED
- **Evidence:** per task constraints, Docker builds are network-blocked; `infra/cloud.Dockerfile:5` (`FROM node:22-bookworm-slim` + `pnpm install`) and `engine/Dockerfile:2-7` (`apt-get install` of pango/cairo from Debian mirrors) both require network pulls; `docs/TODO.md:21` records the sandbox "could not reach `deb.debian.org`".
- **Description:** I did not run any `docker build`. Whether the three Dockerfiles build cleanly, and whether `pnpm --filter @adport/cloud build:standalone` and `uv sync --extra self-host --extra slack --extra reports` succeed inside the images, is unverified.
- **Impact:** Image build health is unknown; the compose stack (`make up`) is unproven here.
- **Recommendation:** A CI docker-build job (on a network-enabled runner) must be the authority for this. Treat as NOT_VERIFIED until that job exists and is green.

### H2-08 — Toolchain note: pnpm is not runnable in this sandbox as configured
- **Severity:** P3
- **Classification:** VERIFIED_RUNTIME
- **Evidence:** `pnpm --version` → exit 1: `Cannot find module '/root/.cache/node/corepack/v1/pnpm/12.8.1/bin/pnpm.cjs'`. `platform/package.json:7` pins `packageManager: pnpm@11.8.0`; corepack here is resolving `pnpm@12.8.1` and failing to fetch it offline.
- **Description:** The platform workspace cannot be installed/built/tested via `pnpm` in this environment without network to fetch the corepack-managed pnpm binary. This is an environment limitation, not a repo defect, but it means I could not execute the cloud vitest or typecheck suites to confirm green.
- **Impact:** The Node/pnpm half of `make test` and the platform CI steps are unexecutable here → those suites are NOT_VERIFIED by me (the Python/uv half is runnable: `uv` 0.8.17 present).
- **Recommendation:** Root CI should rely on `pnpm/action-setup` + `corepack enable` on a networked runner; locally document the corepack prefetch.

## What a world-class system would need (gaps, concrete)
A single root `.github/workflows/ci.yml` on `push`+`pull_request`+`workflow_dispatch`, with path-scoped or always-on jobs and correct `working-directory`:
1. **cloud** job: `corepack enable`; `working-directory: platform`; `pnpm install --frozen-lockfile`; `pnpm build`; `pnpm typecheck`; `pnpm test`; then the markting vitest set (`pnpm --filter @adport/cloud exec vitest run test/markting-*.test.ts test/i18n.test.ts`). Node 22 (match `engines`/`packageManager` pnpm 11.8.0 — do not let corepack drift to 12.x, cf. H2-08).
2. **cloud-db** job (or a step in `cloud`): a Postgres service or `supabase start`, apply `supabase/migrations/**` (incl. `20261002000000_markting_bridge.sql`), export `ADPORT_RUN_DATABASE_TESTS=1` + `SUPABASE_DB_URL`, run the four `*.database*.test.ts` suites — this is the only mechanical guard on tenant isolation (H2-04).
3. **engine** job: `working-directory: engine`; `uv sync --frozen --all-extras --dev`; `uv run --frozen ruff check .`; `uv run --frozen ruff format --check .`; `uv run --frozen mypy src`; `uv run --frozen pytest -q`; `uv run --frozen paid-media-agent demo --with-proposal`; `import agent` smoke. Python 3.11 + 3.13 matrix (per `engine/pyproject.toml` requires-python and the existing matrix).
4. **engine-demo / infra** job: `uv run python -m pytest services/engine-demo/tests`; `node --test infra/scripts/stripe-setup.test.mjs` (i.e. the rest of `make test`).
5. **secret-scan** job: gitleaks over the **whole** monorepo history (`fetch-depth: 0`), SHA-pinned binary (reuse the pattern at `engine/.github/workflows/ci.yml:44-56`), root-level config.
6. **docker-build** job: build `cloud` (`infra/cloud.Dockerfile`, context `platform/`) and `engine` (`engine/Dockerfile`) images (networked runner); NOT_VERIFIED here (H2-07).
7. **upstream-drift** job: the `scripts/check-upstream-edits.sh` named in `docs/TODO.md:21` — diff `platform/` and `engine/` against the SHAs in `UPSTREAM.md` so vendored trees don't silently drift.
8. Housekeeping: move/dedupe the two `dependabot.yml` files to root (`package-ecosystem` per dir) so updates actually run; pin all `uses:` to known-good SHAs/tags consistently (H2-06); set `concurrency` cancel-in-progress (adport already models this at `platform/.github/workflows/ci.yml:9-11`).
