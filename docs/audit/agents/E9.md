Audit only. No source files were modified. Read-only commands plus `pnpm audit --prod` were run.

## Findings

### E9-01 — Pinned Next.js 16.3.1 carries 3 critical RCE advisories
- Severity: P1 (borderline P0) · Classification: VERIFIED_RUNTIME
- Evidence: `platform/apps/cloud/package.json:35` (`"next": "16.3.1"`); `pnpm audit --prod` (exit 1): GHSA-p293-qw3h-jr36 (Windows RCE, <16.3.3), GHSA-2xp9-vwfh-vxw4 (Image Optimization AVIF RCE, <16.3.3), GHSA-vcvr-r3jv-pc5j (`next/og` ImageResponse RCE, <16.3.6). Patched >=16.3.6.
- Description: The production, internet-facing surface (apps/cloud) is pinned to a Next.js release with three known critical RCE CVEs. The Windows-hosted RCE does not apply (deploy image is `node:22-bookworm-slim`, Linux — `infra/cloud.Dockerfile:14`), but the AVIF Image-Optimization and `next/og` RCEs are platform-independent and apply if those features are reachable.
- Impact: Potential unauthenticated remote code execution on the cloud app. Escalates to P0 if image optimization or `next/og`/`ImageResponse` is used in any route.
- Recommendation: Bump to `next >= 16.3.6` and regenerate `pnpm-lock.yaml`; add this to the release gate.

### E9-02 — All CI, secret-scanning and dependabot config is inert at the monorepo root
- Severity: P1 · Classification: VERIFIED_CODE (structure) / INFERRED (non-execution)
- Evidence: `find . -maxdepth 3 -name .git` → only `./.git`; `cat .gitmodules` → exit 1; workflows exist only at `platform/.github/workflows/` and `engine/.github/workflows/`, with no `.github/` at `/home/user/markting-ai`. Both `platform/.github/dependabot.yml` and `engine/.github/dependabot.yml` target `directory: "/"` relative to their own subtree.
- Description: This is a single git repository with the two upstream projects vendored as plain directories (not submodules). GitHub Actions, Dependabot and the Gitleaks secret-scan job are discovered only from `<repo-root>/.github`. Nothing lives there, so — if this monorepo is pushed as one GitHub repo — none of the vendored workflows run: no build/test/typecheck gate, no `engine` Gitleaks history scan (`engine/.github/workflows/ci.yml:38-63`), no weekly dependency updates.
- Impact: No automated supply-chain, secret, or regression gate on the actual shipped repository. The Next.js CVEs in E9-01 would never be surfaced by the vendored tooling as configured.
- Recommendation: Add a root `.github/workflows` that invokes the platform and engine jobs with correct `working-directory`/path filters, and a root `dependabot.yml` listing `platform/`, `platform/apps/cloud/`, `engine/`, and `infra/` ecosystems. Confirm what actually runs on the hosting repo.

### E9-03 — No dependency-vulnerability scanning in any workflow
- Severity: P2 · Classification: VERIFIED_CODE
- Evidence: `grep -rniE "audit|pip-audit|npm audit|pnpm audit|trivy|snyk|osv" platform/.github engine/.github` → only `platform/.github/workflows/ci.yml:47` (`adport ... --demo audit run`, an application feature, not a dependency scan).
- Description: Even if the vendored workflows ran (they do not, per E9-02), none include `pnpm audit`, `pip-audit`/`uv pip-audit`, OSV, Trivy or equivalent. There is no gate that would catch vulnerable transitive packages.
- Impact: Known-vulnerable dependencies ship undetected.
- Recommendation: Add `pnpm audit --prod` (failing on high/critical) to platform CI and a `pip-audit`/`osv-scanner` step to engine CI.

### E9-04 — High/moderate transitive vulns reach the cloud app and MCP server
- Severity: P2 · Classification: VERIFIED_RUNTIME
- Evidence: `pnpm audit --prod` (exit 1): `fast-uri` <3.1.6 host-confusion (high) via `@modelcontextprotocol/sdk>ajv`; `sharp` <0.35.4 (high) via `next`; `ip-address` <=10.7.0 (high) and `qs` (high) via `@modelcontextprotocol/sdk>express`/`express-rate-limit`; `hono` <4.13.7 XSS (moderate) via the MCP SDK. Paths include `apps__cloud>...` and `packages__mcp>@modelcontextprotocol/ext-apps>@modelcontextprotocol/sdk>...`.
- Description: The `@modelcontextprotocol/sdk` (pinned `^1.30.0`, `apps/cloud/package.json:24`) pulls a vulnerable Express/ajv/hono chain into production; `next` pulls a vulnerable `sharp`. 6 high + 11 moderate total.
- Impact: Host-confusion/SSRF-style and XSS exposure on the MCP/cloud surface; image-processing CVEs via sharp.
- Recommendation: Upgrade the MCP SDK and Next.js to versions whose transitive graph clears audit, or add `pnpm.overrides` to force patched `fast-uri`/`qs`/`ip-address`/`hono`/`sharp`.

### E9-05 — GitHub Actions referenced by mutable tags, not pinned to SHAs
- Severity: P3 · Classification: VERIFIED_CODE
- Evidence: `platform/.github/workflows/ci.yml:21-23` (`actions/checkout@v7`, `pnpm/action-setup@v6`, `actions/setup-node@v7`); `release.yml:24-28`; `engine/.github/workflows/ci.yml:18-19` (`checkout@v4`, `astral-sh/setup-uv@v5`); `release.yml:15` (`setup-uv@v6`), `:26` (`softprops/action-gh-release@v2`). Only the engine `secrets` job pins one action by digest (`ci.yml:40`, `checkout@11bd719... # v4.2.2`).
- Description: Moving tags let a compromised/retagged action execute in CI, including the `release.yml` job that holds `NPM_TOKEN` and `id-token` (OIDC) permissions.
- Impact: Supply-chain tampering of the build/publish pipeline (matters once E9-02 is fixed and workflows actually run).
- Recommendation: Pin every `uses:` to a full commit SHA with a version comment; enable Dependabot `github-actions` updates at root.

### E9-06 — Setup path downloads and executes `supabase@latest` unpinned
- Severity: P3 · Classification: VERIFIED_CODE
- Evidence: `Makefile:15` (`SUPABASE ?= npx --yes supabase@latest`); `infra/scripts/sync-supabase-env.mjs:10` (`execFileSync('npx', ['--yes','supabase@latest',...])`).
- Description: `make up` / `make supabase-start` fetch and run whatever is the newest Supabase CLI at run time (`--yes` auto-approves the install), then run `db reset --local`. No version pin, no integrity check.
- Impact: Non-reproducible local setup and a run-time execution-trust dependency on the npm registry; a compromised `supabase` release would run during developer onboarding.
- Recommendation: Pin to an exact version (`supabase@<x.y.z>`) or add it as a dev dependency in the lockfile.

### E9-07 — Docker base images pinned by tag only (no digests)
- Severity: P3 · Classification: VERIFIED_CODE
- Evidence: `engine/Dockerfile:2` (`FROM python:3.13-slim`); `infra/cloud.Dockerfile:5,14` (`FROM node:22-bookworm-slim`); `docker-compose.yml:67` and `engine/docker-compose.yml:28` (`image: postgres:16-alpine`).
- Description: Floating tags resolve to different digests over time; builds are not reproducible and a re-pull can silently change the base layer.
- Impact: Reproducibility and integrity gap for the shipped images.
- Recommendation: Pin `FROM ...@sha256:<digest>` and bump via Dependabot/renovate.

### E9-08 — `infra/` has no lockfile; `npm install --no-audit` resolves ranged deps while Stripe keys are in env
- Severity: P3 · Classification: VERIFIED_CODE
- Evidence: no `infra/package-lock.json` (ls exit 2); `infra/package.json:9` (`"stripe": "^22.5.0"`); `Makefile:48,52` run `cd infra && npm install --no-audit --no-fund --silent` for `seed` and `stripe-setup`; `stripe-setup` then runs with `.env` sourced (`Makefile:52`).
- Description: Without a lockfile the transitive tree is resolved fresh each run, `--no-audit` suppresses npm's own advisory check, and the install can execute package lifecycle scripts in a shell that subsequently has Stripe (test) credentials in its environment.
- Impact: Unpinned/unaudited local dependency surface adjacent to credential-bearing scripts.
- Recommendation: Commit `infra/package-lock.json` (or fold infra into the pnpm workspace), pin `stripe` exactly, and drop `--no-audit`.

## What a world-class system would need
- A root CI that actually runs on the shipped repo: build/test/typecheck + `pnpm audit`/`pip-audit`/`osv-scanner` + gitleaks over the whole tree, blocking on high/critical.
- Dependabot/renovate at root covering platform, apps/cloud, engine, and infra ecosystems plus github-actions and Docker digests.
- SBOM generation (CycloneDX) and signed/provenanced images, with SHA-pinned base images and actions.
- A policy that production dependencies cannot ship with an open critical advisory (would have blocked Next.js 16.3.1).
- Lockfiles for every manifest (infra included) and removal of unpinned run-time downloads (`supabase@latest`).

## Disagreements / claims the code contradicts
- `infra/cloud.Dockerfile` header claims the standalone image follows upstream docs; the audit confirms it builds, but it ships Next.js 16.3.1 with open critical CVEs (E9-01) — "production-mode" is not patch-current.
- The presence of CI/Gitleaks/Dependabot files implies an active supply-chain gate, but their location under subtree `.github` means they do not run at the monorepo root as structured (E9-02). This is a documentation-vs-reality gap, not a working control.
