## Findings

### D4-01 — Apply of a pending operation is not atomic: a concurrent second apply can execute the provider write twice
- **Severity:** P1 (financial risk; 26 adport write tools are `kind: 'create'`, so a duplicate apply creates duplicate campaigns/ad sets, not an idempotent re-set)
- **Classification:** VERIFIED_CODE for the missing compare-and-consume; INFERRED for the actual double write (not reproduced — no provider or DB in sandbox)
- **Evidence:** `platform/packages/core/src/policy/engine.ts:87-124` — `apply()` reads the pending row (`:90`), calls `provider.applyWrite` (`:113`) and only then `pending.delete` (`:123`). `platform/apps/cloud/lib/cloud/repository.ts:385-399` (`get` filters `consumed_at is null`) and `:413-418` (`delete` is an unconditional `update ... set consumed_at = now()` with no `returning`, no row-count check, no `consumed_at is null` guard). `platform/apps/cloud/app/api/approvals/[id]/apply/route.ts:20-27` — `find` over `listPendingOperations`, then `applyPending`, then `markPendingOutcome`; no lock, no CAS. `grep -rhoE "kind: '[a-z_]+'" platform/packages/*/src | sort | uniq -c` → 26 create, 8 remove, 42 update. The dashboard only disables the button client-side (`approval-actions.tsx:33-34`).
- **Description:** Two requests for the same `pending_operation_id` (double submit, two admins, a REST client retrying after a timeout, or dashboard + MCP simultaneously) both pass `get` before either reaches `delete`, both pass the hash check, and both call the provider. The same applies to the REST/MCP second call. This is upstream adport behaviour, but the host's product promise is "the adport policy engine is the only write path", so its atomicity is the host's safety boundary.
- **Impact:** duplicate ad objects or double budget writes; audit shows two `applied` events for one pending id.
- **Recommendation:** consume first, atomically: `update pending_operations set consumed_at = now() where id = $1 and organization_id = $2 and consumed_at is null returning *`, fail with `PENDING_NOT_FOUND` (or a new `PENDING_IN_PROGRESS`) when zero rows return, and restore the row (or record `apply_failed`) if the provider call throws. Alternatively take `pg_advisory_xact_lock(hashtext(id))` around apply. Add a route-level test that fires two concurrent applies and asserts exactly one provider call.

### D4-02 — `DELETE /api/members` is unreachable from the Team page: the client sends a JSON body, the route reads query parameters
- **Severity:** P2 (shipped UI feature cannot work)
- **Classification:** VERIFIED_CODE
- **Evidence:** `platform/apps/cloud/app/api/members/route.ts:47-57` parses `organization_id` and `user_id` from `url.searchParams` with `z.string().uuid()`; `platform/apps/cloud/app/dashboard/team/team-members.tsx:27` sends `fetch('/api/members', { method, ..., body: JSON.stringify({ organizationId, ...body }) })` and `:65` invokes `call('DELETE', { userId })`. With no query string, `z.string().uuid().parse(null)` throws and `apiError(error, 403)` returns 403 with the Zod issue blob. `docs/TODO.md:37` and `docs/PHASE0-REPORT.md:89` list the mismatch as known and unfixed.
- **Impact:** "Remove member" always fails with an opaque 403.
- **Recommendation:** accept the body on DELETE (or switch the client to query params); add a route test.

### D4-03 — Engine report surface is global, not tenant-scoped; the cloud exposes it to every organization
- **Severity:** P2 today (engine is forced into `sample` data mode, so content is synthetic); would be P0 the moment the engine serves real account data
- **Classification:** VERIFIED_RUNTIME
- **Evidence:** probe: `POST /reports/run` as caller `someone-else` → 200 `requested_by: someone-else`; `GET /reports` as caller `adport-bridge` → `['someone-else']`; `GET /reports/files/<that file>` as `adport-bridge` → 200 `text/html`. Code: `serve_demo.py:246-307` one `markting-reports.json` index per workspace, `:355-358` list returns it whole, `:360-374` file route checks only the bearer. Cloud: `app/api/reports/engine/route.ts:16-24` and `[name]/route.ts:10-26` require only *a* session (`sessionPrincipal(organizationId)` with any org the user belongs to) and forward with the single shared `MARKTING_ENGINE_TOKEN` (`lib/markting/assistant.ts:12-15`); `requested_by` recorded on the engine is the token's caller, never the user or org. `assert_fail_closed` (`serve_demo.py:163-166`) forces `paid_media_data_mode == 'sample'`.
- **Impact:** every tenant sees and can download every other tenant's report runs (metadata, windows, and files). Data is fixture-only today, but the architecture has no tenant key on this path and the cloud does not add one.
- **Recommendation:** either make reports a cloud-owned resource (store run metadata per organization in Postgres; pass an org scope header the engine namespaces its index/files by; verify ownership on download) or stop exposing the engine's global list and only show runs the current org triggered. Also record the real actor (`principal.userId`) in provenance.

### D4-04 — Engine `/proposals/{id}/edit` and `/reject` are authorized for any valid bearer, inconsistent with `GET /proposals/{id}`; repeated reject is an unhandled 500
- **Severity:** P2 (auth inconsistency on a write-adjacent resource; `PAID_MEDIA_API_TOKENS` supports many tokens, `config.py:263`). Mitigated in the host deployment by a single token and no approvers.
- **Classification:** VERIFIED_RUNTIME
- **Evidence:** probe with two tokens: `GET /proposals/{id}` as the non-requester → 403 `not visible to this caller` (`app.py:108-109`), yet `POST /proposals/{id}/edit` as the same caller → 200 revision 2, and `POST /proposals/{id}/reject` → 200 `rejected`. `app.py:126-148` passes only `who` to `runner.reject/edit`; `runner.py:257-286` performs no caller check. Second reject raised `InvalidTransition: cannot apply reject in state rejected` out of the ASGI app (no handler in `app.py`; `domain/proposals.py:62-74`), i.e. HTTP 500. The cloud bridge tolerates this only by swallowing all errors in `handoff` (`lib/markting/bridge.ts:173-180`).
- **Impact:** any token holder can revise or kill another caller's proposal without being able to read it; the API's only non-2xx on a repeated terminal action is a 500, so clients cannot distinguish "already handled" from an outage. `docs/ARCHITECTURE.md:824,873` already documents both; nothing was changed.
- **Recommendation:** in the host, do not touch `engine/` (per UPSTREAM policy) but add an exception handler and an ownership check in `serve_demo.py` via `app.add_exception_handler(InvalidTransition, ...)` → 409, and a dependency that rejects `/edit` for non-requesters. Upstream: raise `WriteDenied("not_requester")` in `runner.reject/edit`.

### D4-05 — The "requester ≠ approver" rule exists only in the dashboard route; REST and MCP apply with no such check and no role
- **Severity:** P2 (documented safety property narrower than claimed)
- **Classification:** VERIFIED_CODE
- **Evidence:** `app/api/approvals/[id]/apply/route.ts:18-24` enforces `tools:write`, non-viewer/member role, and `row.createdBy !== principal.userId` unless `MARKTING_ALLOW_SELF_APPROVAL`. `app/api/v1/tools/[tool]/route.ts:5-15` and `app/mcp/route.ts:40-63` only check scope; `authenticateApiKey` returns a principal with no `userId` or `role` (`repository.ts:333`), and `ToolRegistry.call` (`core/src/tools/registry.ts:82-90`) and `PolicyEngine.apply` do not know who validated. `docs/PHASE1-REPORT.md:16`: "Requester ≠ approver unless `MARKTING_ALLOW_SELF_APPROVAL=true`" is stated without qualification.
- **Impact:** an API key or MCP client with `tools:write` validates and applies alone within the 15-minute TTL; policy caps still apply, four-eyes does not. Rows created by API keys have `created_by = null`, so even the dashboard self-approval check is skipped for them (`route.ts:22`, `PostgresPendingStore.put` `:381`).
- **Recommendation:** either record `created_by_principal` (user or api_key_id) on the pending row and enforce the separation in `PolicyEngine.apply`/the REST route, or amend the documentation to say the rule covers the dashboard only.

### D4-06 — Session-route error contract is unreliable: wrong status classes, raw Zod/DB messages, 500 for authorization failures
- **Severity:** P2 (consumers cannot act on statuses; internal messages leak)
- **Classification:** VERIFIED_CODE (status mapping) + VERIFIED_RUNTIME (Zod message shape)
- **Evidence:**
  - Fixed-status pattern `apiError(error, 403)` in 11 routes (`account-access:32`, `account-selection:19`, `api-keys:30,49`, `api-keys/[id]:14`, `connections/[provider]:44`, `deletion:28`, `members:21,32,43,56`, `settings:33`) maps *every* failure — Zod validation, "Authentication required.", unknown provider, transient provider revocation failure (`connections/[provider]/route.ts:31,35`), and Postgres errors — to 403 and echoes `error.message` verbatim (`lib/http.ts:24-33`). For a ZodError that is a multi-line JSON array (node probe above). For a non-UUID `id` on `DELETE /api/api-keys/[id]` (`route.ts:10-11`, no validation) the client receives Postgres' `invalid input syntax for type uuid: ...` text with status 403.
  - `apiError(error)` pattern in the host-added routes: `resolveMembership` throws a plain `Error('You do not have access to this organization.')` (`repository.ts:47`), which `errorStatus` maps to **500 "Internal server error."** in `approvals/[id]/apply:30`, `approvals/[id]/reject:24`, `assistant/messages:17`, `reports/engine:9-13` — an authorization failure reported as a server fault. `body.organizationId` is not validated as UUID in any of these, so a malformed value also becomes a 500 via Postgres.
  - `/api/oauth/[provider]/start/route.ts:51` → every error 401, including "Owner or admin access is required." (should be 403).
  - `/api/dashboard/summary/route.ts:18` → every non-auth error 400 "Unable to read provider data.", including DB outages.
  - `/api/v1/tools/[tool]/route.ts:12` → malformed JSON body throws `SyntaxError` → 500 instead of 400.
  - `/api/onboarding` and `/api/support` alone return 400 for Zod (`:20`, `:43`); `docs/ARCHITECTURE.md:331` documents this split accurately.
- **Impact:** a client cannot distinguish "fix your input" from "not allowed" from "retry later"; internal DB messages reach browsers; monitoring on 5xx is polluted by user errors.
- **Recommendation:** one error pipeline: `ZodError → 400 {error, code:'INVALID_INPUT', issues}`, auth → 401, membership/role → 403, `HttpError` as-is, `AdportError` per the existing map, everything else 500 with a request id and no message. Validate `organizationId`/path ids with Zod before touching the DB.

### D4-07 — `/mcp` turns every unexpected error into 401 with a `WWW-Authenticate` challenge
- **Severity:** P3
- **Classification:** VERIFIED_CODE
- **Evidence:** `platform/apps/cloud/app/mcp/route.ts:64-72`: `status = error instanceof HttpError ? error.status : 401`, message = raw `error.message`, challenge header added on 401. `createTenantRuntime` and DB failures are not `HttpError`.
- **Impact:** a Postgres outage or runtime construction bug makes well-behaved MCP clients discard tokens and re-run OAuth in a loop; internal error text is returned to the client.
- **Recommendation:** only `HttpError(401)` and `apiPrincipal` failures should produce the challenge; everything else 500 with a generic body.

### D4-08 — Engine host exposes `/docs`, `/openapi.json`, `/health` and `/markting/info` without authentication
- **Severity:** P3 (compose does not publish the engine port — `docker-compose.yml:64`; binds `0.0.0.0` inside the network, `:45`)
- **Classification:** VERIFIED_RUNTIME (`UNAUTH GET /docs 200`, `/openapi.json 200`, `/markting/info 200` in the probe)
- **Evidence:** `app.py:51` `FastAPI(title=..., version=...)` with default `docs_url`/`openapi_url`; `serve_demo.py:326-336` `info()` has no `caller` dependency and returns approvers and account aliases.
- **Impact:** anything on the compose network (or any misconfigured publish) learns the full API shape and the alias→account map.
- **Recommendation:** in the host, `app.docs_url = None` is not settable after construction, but `attach_report_routes` can `app.router.routes = [r for r in app.router.routes if r.path not in ('/docs', '/openapi.json', '/redoc', '/docs/oauth2-redirect')]`, and `/markting/info` should require the bearer.

### D4-09 — Rate limiting is partial, mislabeled, and partly keyed on client-controlled input
- **Severity:** P3
- **Classification:** VERIFIED_CODE
- **Evidence:** `lib/cloud/repository.ts:355-369`: the bucket is always `date_trunc('minute', now())`; the `windowSeconds` parameter only affects the 1 %-probability cleanup, so every caller gets a fixed 60 s window whatever it passes. `/oauth/register/route.ts:8` keys the limit on `x-vercel-forwarded-for ?? x-forwarded-for ?? 'unknown'` — off Vercel the client sets this header freely (the waitlist route explicitly refuses to do this, `waitlist/route.ts:81-85`). No limit on `/api/members`, `/api/settings`, `/api/api-keys` POST, `/api/approvals/*`, `/api/support`, `/api/deletion`, `/oauth/token`. No `Retry-After`/`X-RateLimit-*` headers anywhere except waitlist. Engine: no rate limit at all (`app.py`), synchronous turns up to minutes, one lock on reports only.
- **Recommendation:** derive the window from the parameter; key register/token limits on client_id + a trusted edge IP; add `Retry-After` in `apiError` for 429; put a per-token concurrency cap in front of `/threads/*/messages`.

### D4-10 — No pagination; silent truncation
- **Severity:** P3
- **Classification:** VERIFIED_CODE
- **Evidence:** `GET /api/api-keys` and `GET /api/members` return unbounded lists; `GET /reports` returns the whole index, which `run_report` trims to the newest 50 (`serve_demo.py:306`) — older runs and their files become unlisted (files remain on disk and downloadable by name). `/api/approvals/[id]/{apply,reject}` locate the row with `listPendingOperations(org, 200).find(...)` (`apply/route.ts:20`, `reject/route.ts:13`) so a pending row older than the newest 200 answers 404 "not found, expired, or already applied".
- **Recommendation:** fetch by id (`PostgresPendingStore.get`) instead of list+find; add `limit`/`cursor` to list endpoints; keep the report index unbounded or paginate it.

### D4-11 — Inconsistent parameter naming across routes
- **Severity:** P3
- **Classification:** VERIFIED_CODE
- **Evidence:** query `organization_id` (`api-keys`, `api-keys/[id]`, `connections`, `members`, `dashboard/summary`, `oauth/start`) vs query `organizationId` (`reports/engine/route.ts:18`, `[name]/route.ts:13`); body `organization_id` (`api-keys/route.ts:9`, `deletion/route.ts:9`) vs body `organizationId` (`account-access`, `account-selection`, `members`, `settings`, `approvals`, `assistant`, `reports`). Engine uses snake_case throughout.

### D4-13 — Engine exception text is forwarded to the browser via the reports route

### D4-14 — No CSRF defense beyond SameSite=Lax on JSON session routes; apply/reject accept an absent body
- **Severity:** P3 / GAP
- **Classification:** VERIFIED_CODE
- **Evidence:** no route checks `Origin` or `Sec-Fetch-Site` (grep over `app/api` and `lib`: only the waitlist route does). Supabase SSR sets cookies `sameSite: "lax"` (`node_modules/@supabase/ssr/dist/main/utils/constants.js:6`). `approvals/[id]/apply/route.ts:16` uses `request.json().catch(() => ({}))`, so a body-less or non-JSON POST is accepted.
- **Impact:** safe today because Lax cookies are not sent on cross-site POST; a future cookie-policy change or a subdomain takeover removes the only barrier.
- **Recommendation:** reject state-changing session requests whose `Sec-Fetch-Site` is `cross-site` or whose `Origin` is not `ADPORT_CLOUD_BASE_URL`.

## What a world-class system would need

1. **Atomic consume-then-apply** for pending operations (single `UPDATE … RETURNING` or advisory lock), with an `apply_failed` audit event and a documented retry contract; a concurrency test.
2. **One error envelope** across cloud routes: `{ error: <stable code>, message, details?, request_id }`; `400` for validation (with issues), `401` unauthenticated, `403` forbidden, `404` unknown resource, `409` state conflicts (`PENDING_*`, `NOT_CONNECTED`), `429` with `Retry-After`, `5xx` redacted. Same envelope from `/mcp` error responses that are not JSON-RPC.
3. **Tenant-scoped engine surface**: an `X-Markting-Org` (or per-org token) that namespaces engine threads, proposals, reports and files server-side, verified on every read; `requested_by` = real user.
4. **Public REST completeness** for agents and integrators: `GET /api/v1/tools` (schemas + annotations), `GET /api/v1/pending-operations[/{id}]`, `POST /api/v1/pending-operations/{id}/reject`, `GET /api/v1/audit?cursor=`, `GET/POST /api/v1/assistant/threads`, `GET /api/v1/assistant/threads/{id}/messages`, all cursor-paginated, all under `/api/v1`, published as OpenAPI 3.1 with the auth schemes above.
5. **Idempotency-Key** on every POST that creates something (assistant turn, report run, API key, invite), stored per org for 24 h, replaying the original response.
6. **Rate-limit design**: sliding window keyed on principal (never on forwardable headers off Vercel), standard `RateLimit-*` headers, per-token concurrency cap for long engine turns, and a 503 + `Retry-After` from the engine when its report lock is held.
7. **Engine hardening at the host layer** (without editing `engine/`): disable `/docs`/`/openapi.json`, authenticate `/markting/info`, add exception handlers (`InvalidTransition` → 409), bind an ownership check to `/edit`.
8. **CSRF belt-and-braces**: `Sec-Fetch-Site`/`Origin` check on all session mutations; reject empty bodies on apply/reject.
9. **Contract tests** for every route handler (status matrix per role) and a runnable HTTP suite in CI (Supabase + Postgres service containers) so `http.integration.test.ts` stops being skipped.
10. **Versioning policy**: `/api/v1` for everything machine-facing; check `presentation/1` on engine responses and fail closed on a newer major.
