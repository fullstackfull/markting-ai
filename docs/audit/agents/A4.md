# A4 — Snapchat Ads expert

Audit date: 2026-10-02. Repository: `/home/user/markting-ai` (HEAD `d9c79f6`). Nothing outside this file was modified.

Question asked: can MARKTING-AI understand and manage Snapchat Ads like an expert media buyer, or does it merely have a connector? Short answer (evidence below): it has a small, carefully hardened **campaign-level connector** (accounts, campaign list, five base metrics, two campaign-level writes plus paused campaign creation), all gated through the shared PolicyEngine and covered by wire-format tests. It has **no** ad-squad/ad/creative model, no breakdowns beyond entity, no time series, no bidding/optimization surface, and the AI engine cannot read Snapchat at all offline and cannot normalize it live. Nothing has been verified against the real Snap Marketing API.

## Findings

### A4-01 — Normalized Snapchat metrics are five base fields; "conversions" means purchases only
- Severity: GAP (functional ceiling; the code documents the choice)  Classification: VERIFIED_CODE
- Evidence: `platform/packages/snapchat/src/provider.ts:197` (`FIELDS = 'spend,impressions,swipes,conversion_purchases,conversion_purchases_value'`), `provider.ts:322` (clicks = swipes, conversions = conversion_purchases, conversion_value = conversion_purchases_value, both monetary fields / 1e6), `platform/packages/core/src/model.ts:1-12` (ten metric names total), `platform/docs/providers/snapchat.md:22`.
- Description: The only metrics ever requested from `/adaccounts/{id}/stats` are spend, impressions, swipes, purchase count and purchase value. Derived ctr/cpc/cpm/cpa/roas are recomputed from these. No reach, frequency, video views / completions, story opens, screen time, saves, shares, app installs, sign-ups, leads, add-to-cart, page views, or any `conversion_*` event other than purchases. Units: spend and purchase value are micro-currency divided by 1,000,000 into account-currency units; counts are integers; strings are coerced (`schemas.ts:363-364`).
- Impact: For a Gulf advertiser running app-install or lead campaigns (the sandbox's own demo campaign is "App Installs - Gulf", `sandbox-provider.ts:61`), "conversions" is zero and CPA/ROAS are meaningless. An expert cannot judge Snap creative performance without view/completion/frequency metrics.
- Recommendation: Extend `FIELDS` to Snap's conversion family and delivery metrics, make the conversion event configurable per account (purchase vs install vs lead), and carry a `conversion_definition` in row metadata.

### A4-02 — Zero-denominator ratios are emitted as 0, contradicting the "no fabricated zeroes" doc
- Severity: P3  Classification: VERIFIED_CODE
- Evidence: `platform/packages/snapchat/src/provider.ts:331` (`mapped[metric] = mapped[denominator] ? ... : 0`), `platform/docs/providers/snapchat.md:23` ("Missing metrics remain absent, not fabricated zeroes"), test `platform/packages/snapchat/test/snapchat.test.ts:150-160` covers only absent fields, not a present zero denominator. Same pattern upstream in `platform/packages/meta/src/provider.ts:210-214`, `tiktok/src/provider.ts:160-164`.
- Description: Snap returns requested fields with `0` when there is no activity. A campaign with spend > 0 and `conversion_purchases = 0` is reported with `cpa: 0`; clicks = 0 yields `cpc: 0`. The doc statement is true for base metrics but false for derived ratios.
- Impact: A CPA of 0 reads as "free conversions" in the Reports table and in anything the Assistant summarizes; sorting by CPA puts the worst campaigns first.
- Recommendation: Omit the ratio (leave undefined/null) when the denominator is 0; add a test with `conversion_purchases: 0`.

### A4-03 — Report rows carry IDs as names, no currency, no status at campaign/ad-squad/ad level
- Severity: P3  Classification: VERIFIED_CODE
- Evidence: `provider.ts:260` (`entity: { level, id: stat.id, name: stat.id }`), `provider.ts:234-235` (account currency is fetched but never put on the row), `platform/packages/core/src/model.ts:38-45` (`currency?` and `status?` exist on `ReportRow`), `platform/apps/cloud/app/dashboard/reports/page.tsx:37` (`row.entity.name || row.entity.id`), `platform/packages/core/src/report-summary.ts:10-11` (rows without currency group per account, `currency: null`).
- Description: Campaign-level rows show the Snap UUID instead of the campaign name; the campaign list endpoint is never joined. Rows carry no `currency` even though it is known, so `summarizeReport` cannot label SAR vs USD totals. The Reports page requests `level: 'campaign'` only (`platform/apps/cloud/lib/cloud/reads.ts:54`); ad_group/ad levels are reachable through the MCP `get_report` tool (`core/src/tools/builtin.ts:61`) and produce ID-only rows.
- Impact: A buyer cannot read the Snap report without cross-referencing IDs; multi-currency orgs get unlabeled totals.
- Recommendation: Join `listCampaigns` (and add adsquad/ad listing) to name rows; set `currency: account.currency` and `status` on each row.

### A4-04 — Update wire format (JSON Patch over PATCH) is unverified against Snap's API and is a single point of failure for all writes
- Severity: P2 (conditional; would be P1 if the format is wrong, because every budget/status apply would fail)  Classification: NOT_VERIFIED
- Evidence: `platform/packages/snapchat/src/client.ts:105` (`content-type: application/json-patch+json` for PATCH), `provider.ts:308` (`[{ op: 'add'|'replace', path: '/daily_budget_micro'|'/lifetime_spend_cap_micro'|'/status', value }]`), `provider.ts:313-315` (`PATCH adaccounts/{account}/campaigns/{campaign}`), `platform/docs/providers/snapchat.md:7` claims "partial JSON Patch updates" reviewed 2026-08-31; `docs/snapchat-live-checklist.md:30` schedules the live check. `curl` to developers.snap.com failed (exit 56, proxy 403).
- Description: My recollection of Snap's public Campaigns reference is that updates are `PUT /v1/adaccounts/{ad_account_id}/campaigns` with full campaign objects; I could not confirm or refute from inside this sandbox, and the vendored tests only prove the code sends what the code intends (`test/snapchat.test.ts:195-203`, `apps/cloud/test/markting-snapchat-wire.test.ts:74-78`). If Snap does not accept this method/media type, the failure is fail-closed (HTTP 4xx -> `PROVIDER_ERROR`, `client.ts:114-117`) and no partial write occurs.
- Impact: Possible total non-functionality of Snapchat writes in production, discovered only at step D of the live checklist.
- Recommendation: Verify against the vendor reference and a test account before enabling `SNAPCHAT_OAUTH_ENABLED=true` for any customer; record the result in the checklist table (`docs/snapchat-live-checklist.md:39-42`, currently empty).

### A4-05 — Budget writes to a campaign with no existing campaign-level budget bypass the percentage rail and insert a new spend cap
- Severity: P2  Classification: VERIFIED_CODE
- Evidence: `provider.ts:307-308` (`previous = current[field]`; `op: previous === undefined ? 'add' : 'replace'`), `provider.ts:312` (`fromMicros` only set when `previous` is a number), `platform/packages/core/src/policy/engine.ts:143` (`if (pctCap !== null && delta.fromMicros !== undefined && delta.fromMicros > 0)`), `core/src/policy/policy.ts:15` (`max_daily_budget_micros` default `null`), `platform/apps/cloud/lib/markting/translate.ts:84-91` (bridge path has a 1,000,000-unit sanity ceiling; the direct MCP/Assistant path has none).
- Description: On Snapchat, `daily_budget_micro` and `lifetime_spend_cap_micro` are optional at campaign level (budgets normally live on ad squads). When unset, the provider plans a JSON Patch `add` and reports a delta with no `fromMicros`, so `max_budget_delta_pct` (default 25 %) is never evaluated; only the absolute cap applies and it defaults to unlimited. The preview text shows `unset → value` (`provider.ts:311`), which is honest, but the policy engine treats it as unconstrained.
- Impact: Two financial failure modes with no rail: (1) an AI-proposed "set budget" on an unbudgeted campaign adds a campaign cap below the ad squads' budgets and throttles delivery; (2) an arbitrarily large campaign budget can be approved with no percentage check. Both are human-approved (two-step) but the policy is the stated safety claim.
- Recommendation: Treat `fromMicros === undefined` as requiring the absolute cap to be set (reject if `max_daily_budget_micros` is null), or add a per-provider "creating a new budget" rule; for Snap, surface the ad-squad budgets in the preview so the operator sees the throttle risk.

### A4-06 — Attribution windows are hard-coded (28-day swipe / 1-day view) and invisible in output
- Severity: GAP  Classification: VERIFIED_CODE
- Evidence: `provider.ts:244`, `test/snapchat.test.ts:147-148`, `platform/docs/providers/snapchat.md:22`.
- Description: The query always sends `swipe_up_attribution_window=28_DAY&view_attribution_window=1_DAY`. Rows carry no attribution metadata; the engine's `ATTRIBUTION_DIFFERS` flag (`engine/.../domain/common.py:64`) is never populated for Snap because the engine never sees Snap rows.
- Impact: Matches Snap Ads Manager defaults, so numbers reconcile by default; any account configured for 7-day/1-day will not reconcile and nothing says why.
- Recommendation: Expose the windows as a query option and record them on the row.

### A4-07 — Empty accounts (no campaigns / no breakdown) surface as a provider error
- Severity: P3  Classification: VERIFIED_CODE (behavior); NOT_VERIFIED (what Snap returns for empty accounts)
- Evidence: `provider.ts:247-248`, test `test/snapchat.test.ts:161-167` ("rejects missing breakdowns rather than showing a healthy empty account"); `docs/snapchat-live-checklist.md:22` expects this.
- Description: If `breakdown_stats[campaign]` is absent the report throws `PROVIDER_ERROR`. This is deliberate fail-loud design, but a brand-new ad account with zero campaigns will show an error, not zero rows, if Snap omits the breakdown key in that case.
- Recommendation: Confirm Snap's empty-account response on the test account; if it omits the key, return zero rows with an explicit `note`.

### A4-08 — Campaign creation accepts any `objective` string, hard-codes `buy_model`, and cannot create anything that delivers

### A4-10 — Per-request runtime construction refreshes the Snap access token on every request; rotation races are possible
- Severity: P3  Classification: INFERRED
- Evidence: `client.ts:44,126-130` (access token held in instance memory only), `client.ts:145-147` (rotated refresh token persisted via callback), `platform/apps/cloud/lib/cloud/runtime.ts:44,69-72` (a new `SnapchatAdsClient` per `createTenantRuntime` call), `lib/cloud/credential-rotation.ts` (compare-and-set persistence, not read in full).
- Description: Each tenant request builds a fresh client, so the first Snap call of every request hits the token endpoint. If Snap rotates refresh tokens on every refresh, two concurrent requests from one org race; the compare-and-set in `rotateProviderTokens` protects the DB row but the loser's in-flight refresh token may already be invalid at Snap.
- Impact: Possible spurious "re-authorize" errors under concurrency; token-endpoint rate limiting. Not a security issue.
- Recommendation: Cache the access token per connection (encrypted, with expiry) or verify Snap's rotation semantics on the test account and document the result.
